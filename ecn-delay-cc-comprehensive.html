ECN & Delay-based Congestion Control

Transport Layer — Section 3.7.2 | Network-Assisted & Proactive Approaches

ECN Overview

Explicit Congestion Notification (ECN) is a network-assisted congestion control mechanism defined in RFC 3168. It uses two bits in the IP Type of Service (ToS) field to signal congestion before packet loss occurs.

ECN Codepoints (2 bits in IP ToS field)
00 = Not ECN-Capable (Non-ECT)
01 or 10 = ECN-Capable Transport (ECT)
11 = Congestion Experienced (CE)
Routers set the CE codepoint (00→11) when a packet encounters congestion. The receiver is notified and echoes the signal back to the sender.

Why ECN?

• Classic TCP detects congestion only after packet loss

• ECN detects impending congestion before buffers overflow

• Avoids costly retransmissions

• Reduces latency for interactive traffic

• Especially beneficial in data centers

Router Marking

Router monitors queue length

When queue exceeds threshold:

• If ECT(0) or ECT(1): change to CE(11)

• If Not-ECT: drop packet (no ECN support)

Threshold is configurable by operator

ECN Protocol Stack Interaction

Layer Component Role
Network (IP) ToS field (2 ECN bits) Routers mark CE to signal congestion
Transport (TCP) ECE bit in ACK Receiver echoes congestion to sender
Transport (TCP) CWR bit in data Sender confirms window reduction
Transport (TCP) cwnd halving Sender reduces rate (same as loss reaction)
Common Mistake: ECN does NOT replace loss-based congestion detection. It provides earlier notification. TCP still uses loss detection as a fallback when ECN is not supported along the path.

ECN in TCP

The ECN feedback loop involves the receiver echoing the congestion indication back to the sender via TCP header bits.

ECN Feedback Loop
IP CE(11) → Receiver → ACK[ECE=1] → Sender → halve cwnd → ACK[CWR=1]
Full loop takes 1 RTT. Sender halves cwnd (same as triple dupACK reaction) and sets CWR bit to acknowledge the reduction.

TCP Header Bits for ECN

ECE (ECN Echo)

Receiver→Sender: "I received a CE-marked packet"

CWR (Congestion Window Reduced)

Sender→Receiver: "I halved my cwnd"

Both bits in TCP header flags (Figure 3.29)

ECN Extensions

DCTCP — Data Center TCP

Uses ECN marking fraction to fine-tune cwnd

DCQCN — Data Center QCN

For RDMA over Converged Ethernet

Both widely deployed in modern data centers

DCTCP Algorithm

On each ACK: if ACK has ECE=1: mark_count++ alpha = (1 - g) * alpha + g * (mark_count / total_ACKs) cwnd = cwnd * (1 - alpha/2)

DCTCP uses the fraction of marked packets (α) rather than a binary signal. This allows more precise congestion control, keeping queues short in data center networks.

Deployment Status: Recent measurements show increasing ECN deployment on popular servers and intermediate routers. However, not all paths are ECN-capable, so TCP must always fall back to loss-based detection.

Delay-based Congestion Control

Delay-based approaches detect congestion before loss by measuring changes in RTT. The core idea: increasing queueing delay signals building congestion.

TCP Vegas

Vegas Congestion Detection
Throughput_expected = cwnd / RTTmin
Throughput_actual = cwnd / RTTcurrent
If Throughput_expected − Throughput_actual > threshold → congested
RTTmin = minimum observed RTT (uncongested path). When actual throughput is significantly less than expected, the path is congested.
Vegas cwnd Adjustment
If diff < α: cwnd += 1  (underutilized)
If diff > β: cwnd -= 1  (congested)
Else: cwnd unchanged  (just right)
diff = expected − actual throughput difference. α and β are thresholds (typically 1 and 3 packets).

BBR (Bottleneck Bandwidth and Round-trip)

BBR, developed at Google, models the path as a pipe with bandwidth × RTT capacity. The key principle: "Keep the pipe just full, but no fuller."

BBR Key Insight
BDP = Bottleneck Bandwidth × RTTmin
Bandwidth-Delay Product. Sending at this rate keeps the pipe full without building queues.

TCP Vegas

• Proactive: reduces rate before loss

• Uses RTTmin as uncongested baseline

• Measures throughput deviation

• Can be unfair against Reno (which fills buffers)

BBR

• Bandwidth-delay product model

• Used in Google B4 network

• Deployed on YouTube servers

• Fairness mechanisms for Reno coexistence

• RFC 8312

Feature TCP Reno TCP Vegas BBR
Signal Packet loss RTT increase Bandwidth + RTT
Proactive? No (reacts after loss) Yes (reduces before loss) Yes (models path capacity)
Queue buildup High (fills buffers) Low (avoids queueing) Minimal (targets BDP)
Deployment Legacy/fallback Limited Google, YouTube
Common Mistake: Delay-based approaches (Vegas, BBR) do NOT replace loss-based congestion control entirely. They work best when competing with similar flows. When a Vegas flow shares a link with a Reno flow, Vegas may get less bandwidth because Reno aggressively fills buffers while Vegas backs off.

Worked Examples

Example 1 — Full ECN Signaling Walkthrough

Setup: Host A (sender) → Router R → Host B (receiver). A sends data at 100 Mbps. R's link is 80 Mbps. ECN enabled.

Step 1: A sets ECT(1) in IP header (both hosts ECN-capable).

Step 2: R's queue grows past threshold. R sees ECT(1), changes it to CE(11). Forwards packet.

Step 3: B receives packet with CE=11. B's TCP sets ECE=1 in the next ACK back to A.

Step 4: A receives ACK[ECE=1]. A halves cwnd (e.g., from 100 to 50 segments). A sets CWR=1 in next data segment.

Step 5: B receives CWR=1, stops setting ECE bit.

Time: Full feedback loop takes ~1 RTT. No packets were dropped, no retransmissions needed.

Example 2 — TCP Vegas Throughput Calculation

Setup: cwnd = 24 KB, RTTmin = 100ms (uncongested). Current RTT = 120ms. MSS = 1 KB.

Expected throughput: 24 KB / 0.100s = 240 KB/s

Actual throughput: 24 KB / 0.120s = 200 KB/s

diff: 240 − 200 = 40 KB/s = 40 packets/sec

Analysis: diff is large → path is congested (queueing delay = 20ms). Vegas would decrease cwnd by 1 MSS to reduce the queue buildup.

After decrease: cwnd = 23 KB. New expected rate = 23/0.1 = 230 KB/s. New actual ≈ 23/0.115 = 200 KB/s (assuming reduced queue). Vegas converges to keep diff within [α, β] where buffers stay small.

Example 3 — DCTCP Fine-Tuned cwnd Control

Setup: Data center flow, RTT = 200µs. In a window of 100 packets, 30 have CE marking.

α calculation (with g = 0.0625):

Fraction marked = 30/100 = 0.3

αnew = (1−0.0625) × αold + 0.0625 × 0.3

If αold = 0.1: αnew = 0.9 × 0.1 + 0.0625 × 0.3 = 0.09 + 0.01875 = 0.10875

cwnd adjustment: cwnd = cwnd × (1 − 0.10875/2) = cwnd × 0.9456

Result: Only 5.4% reduction. In classic ECN, cwnd would be halved (50% reduction). DCTCP's gentler reaction keeps queues short while maintaining high throughput.
