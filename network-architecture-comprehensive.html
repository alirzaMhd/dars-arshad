Network Architecture

Client/Server Model • Peer-to-Peer Model — Complete Guide for Exam Preparation

Network Architecture Overview

Core Concept:
Network architecture defines how devices communicate, share resources, and organize their roles in a network.
Two fundamental models exist: Client/Server (centralized) and Peer-to-Peer (decentralized).
Key Exam Point: The choice between Client/Server and P2P depends on scale, security requirements, cost budget, and administration needs — not on the number of devices alone.

Key Terminology

Client:
A device or application that requests services or resources from a server.
Clients initiate communication and depend on servers to fulfill requests (e.g., web browser, email client).
Server:
A powerful computer that provides services, resources, or data to clients.
Servers are always-on, centralized, and manage shared resources (e.g., web server, database server, file server).
Peer:
A device that acts as both client and server simultaneously.
Each peer can request AND provide services. No hierarchy exists between peers (e.g., BitTorrent nodes).
Service:
Any functionality or resource provided over a network (file access, printing, web pages, email).
Services are identified by protocols and port numbers (HTTP=80, HTTPS=443, FTP=21, SSH=22).

Architecture Types Summary

Centralized (Client/Server)

• One or more dedicated servers

• Clients connect to servers

• Server controls access

• Professional administration

Decentralized (Peer-to-Peer)

• No dedicated servers

• All nodes are equal

• Each peer shares resources

• Self-organized

Client/Server Model — Definition

Definition:
A centralized network architecture where dedicated servers provide services to multiple clients.
Clients request services; servers respond. The server is always available and manages all shared resources, security, and data storage.
Communication Pattern:
Client → Request → Server → Response → Client
Communication is asymmetric: clients initiate, servers respond. Servers can handle multiple clients concurrently.

Key Characteristics

Centralization

• Data stored on servers

• Authentication centralized

• Single point of control

• Easier backup & recovery

Security

• Access controlled by server

• User permissions managed

• Audit trails centralized

• Updates deployed from server

Scalability

• Add more servers to scale

• Load balancing possible

• Client hardware can be thin

• Server upgrades independent

Administration

• Dedicated IT staff needed

• Centralized management console

• Policy enforcement

• Software license management

Client/Server Formulas

Max Simultaneous Clients:
Max Clients = Server Resources / Resource per Client
Example: Server with 64 GB RAM, each client uses 256 MB → 64 × 1024 / 256 = 256 clients max
Server Capacity Planning:
Required Servers = Peak Load / (Server Capacity × Availability Factor)
Peak Load = 10,000 req/s, Capacity = 5,000 req/s, Availability = 0.9 → Servers = 10,000 / (5,000 × 0.9) = 2.22 → 3 servers
Load Balancing Distribution:
Load per Server = Total Requests / Number of Servers
Ideal with N servers: each handles 1/N of total load. Uneven distribution wastes resources.
Client-Server Latency:
Total Latency = Network Latency + Server Processing Time + Database Query Time
Each hop adds latency. Server bottlenecks compound delays. Client/server can have higher latency than P2P for distant resources.

Peer-to-Peer Model — Definition

Definition:
A decentralized network architecture where every device (peer) can act as both client and server simultaneously.
No dedicated servers exist. Each peer contributes resources and can request services from any other peer. The network is self-organizing.
Communication Pattern:
Peer A ↔ Peer B (bidirectional, symmetric)
Any peer can initiate or respond to requests. Roles are fluid: a peer may serve one request while requesting another.

Key Characteristics

Decentralization

• No single point of failure

• Resources distributed across peers

• Self-organizing network

• No central authority

Scalability

• Each new peer adds resources

• Natural load distribution

• Grows organically

• No server bottleneck

Cost

• No server hardware needed

• Minimal administration

• Free software (often)

• Uses existing hardware

Challenges

• Security is harder

• No centralized backup

• Performance varies

• Difficult to manage

Types of P2P Networks

Type Description Example
Unstructured P2P No organized topology; peers connect randomly. Flood-based search. High bandwidth usage. Early Gnutella, Napster (search phase)
Structured P2P Organized using Distributed Hash Tables (DHT). Efficient lookup. O(log N) hops. Chord, Kademlia, BitTorrent DHT
Hybrid P2P Combines P2P with centralized components (index server). Most common practical model. BitTorrent (tracker), Skype (supernodes)
Super-Peer P2P Some peers become super-peers acting as local hubs. Hierarchical but decentralized. Kazaa, eDonkey

P2P Formulas

Number of Connections in Full P2P:
Connections = n(n − 1) / 2
Each peer connects to every other peer. n = number of peers. Example: 10 peers = 10(9)/2 = 45 connections
Search Complexity (Unstructured):
Search = O(N) where N = total peers in network
Flooding-based search visits all peers. TTL (Time To Live) limits breadth but may miss results.
Search Complexity (Structured/DHT):
Search = O(log N) where N = total peers
DHT-based routing reduces hops. Each peer maintains O(log N) neighbors. Efficient for large networks.
Network Throughput (BitTorrent model):
Download Speed = sum of upload speeds from all connected seeds
More seeders = faster download. If 5 peers upload at 1 Mbps each, theoretical max = 5 Mbps.
Chord Lookup (DHT):
Hops = O(log N) where N = number of nodes in Chord ring
Each node maintains a finger table of size O(log N). Lookups resolve in O(log N) hops.

Performance Comparison

C/S Throughput:
Throughput = min(Server Bandwidth, Network Capacity, Client Speed)
Server is the bottleneck. All clients share server bandwidth. Performance degrades with more clients.

Throughput = Sum of upload rates from all connected seeders
More seeders = higher throughput. Can exceed single-server bandwidth. Decentralized advantage.

Worked Examples

Example 1: Server Capacity Planning

A company has 500 employees who all access a centralized file server simultaneously during peak hours. Each employee needs 50 MB of concurrent bandwidth.

Question: What minimum server bandwidth is needed?

Solution:

Total bandwidth = Number of clients × Bandwidth per client

Total = 500 × 50 MB = 25,000 MB = 25 GB/s

With load balancing across 5 servers: 25 GB/s ÷ 5 = 5 GB/s per server. In practice, not all clients peak simultaneously (utilization factor ~0.7): 25 × 0.7 = 17.5 GB/s effective.

Example 2: BitTorrent vs. Centralized Download

A 1 GB file needs to be distributed to 1000 users. The server has 100 Mbps upload speed. In the P2P model, each peer uploads at 5 Mbps after downloading.

Question: Calculate time to distribute the file using both models (assuming all users start simultaneously).

Solution:

Client/Server:

Time per client = File size / Server bandwidth per client

If server serves 10 clients simultaneously: 100 Mbps / 10 = 10 Mbps per client

Time = 8000 Mb / 10 Mbps = 800 seconds (~13.3 minutes) per batch

Total for 1000 users (100 batches) = 800 × 100 = 80,000 seconds (~22.2 hours)

Peer-to-Peer:

After first peer downloads (8000 Mb / 100 Mbps = 80 seconds), it uploads to others.

With 1000 peers each contributing 5 Mbps: total upload capacity = 5000 Mbps

Time for last peer to finish ≈ ~160 seconds (~2.7 minutes)

P2P is dramatically faster for mass distribution because the network bandwidth grows with each peer.

Example 3: Identifying Architecture in a Scenario

A hospital has a central server storing all patient records. Doctors access records from tablets. The server requires login credentials and logs all access. No doctor can modify records without server authorization.

Question: What network architecture is this? Why?

Solution:

Identifying characteristics:

1. Central server → Client/Server

2. Tablets are clients (request data)

3. Authentication centralized (login credentials)

4. Access logging on server (audit trail)

5. Server controls modifications (authorization)

Healthcare requires HIPAA compliance, which mandates centralized access control and audit logs — impossible with P2P.

Example 4: P2P Network Scalability

A P2P file-sharing network starts with 4 peers. Each peer connects to every other peer.

Question: How many connections exist? If the network grows to 50 peers, how many connections?

Solution:

Formula: Connections = n(n-1)/2

For 4 peers: 4(3)/2 = 6 connections

For 50 peers: 50(49)/2 = 1,225 connections

This exponential growth is why full mesh P2P doesn't scale. Practical P2P uses structured overlays (DHT) with O(log N) connections per peer instead.

Example 5: Hybrid Architecture Analysis

BitTorrent uses a tracker server to help peers find each other, but files are transferred directly between peers.

Question: Is BitTorrent Client/Server, P2P, or Hybrid? Explain.

Solution:

BitTorrent is a Hybrid architecture.

1. Tracker server → Centralized component (Client/Server aspect)

• Tracker maintains peer lists

• Tracker failure temporarily disrupts discovery

2. File transfer → Peer-to-Peer aspect

• Data flows directly between peers

• No server involved in file transfer

• Each peer uploads AND downloads

Modern BitTorrent also uses DHT (trackerless) making it more P2P, but the original design was hybrid.

Exam-Style Questions

Q1: Architecture Choice

A startup with 20 employees needs a network for sharing documents and email. They have a limited budget and no IT staff. Which architecture should they choose?

Answer: Client/Server (even small-scale). Email requires centralized mail server. Document sharing needs access control. Limited budget → use open-source (Linux server + Samba + Dovecot). 20 users is manageable with one server.

Q2: Single Point of Failure

In a Client/Server network with one server and 100 clients, the server crashes. What happens? How can this be mitigated?

Answer: All 100 clients lose service immediately. Mitigation: redundant servers (failover clustering), load balancers, RAID storage, UPS power backup, hot spare servers.

Q3: P2P Security Challenge

Why is security more difficult in P2P networks than in Client/Server networks?

Answer: No central authority to enforce policies. Each peer is responsible for its own security. Malicious peers can inject false data. No centralized authentication. Difficult to audit or trace attacks. No single entity to trust.

Q4: Scalability Comparison

A video streaming service expects 10 million simultaneous viewers. Compare C/S vs. P2P for this scenario.

C/S: Needs massive server farm (CDN). 10M × 5 Mbps = 50 Tbps server bandwidth required. Very expensive. P2P: Each viewer shares stream with others. Self-scaling. But quality inconsistent, buffering issues, and legal concerns.

Q5: Formula Application

A Chord DHT network has 1024 nodes. How many hops needed to locate a key? How many entries in each node's finger table?

Hops = O(log₂ N) = log₂(1024) = 10 hops. Finger table size = O(log₂ N) = 10 entries per node. Very efficient for 1024 nodes.

Common Mistakes & Warnings

Mistake 1: P2P = No Servers at All

Many P2P systems use some centralized components (trackers, bootstrap nodes, DHT introduction points). BitTorrent's tracker is a server. Pure P2P is rare; most real-world systems are hybrid.

Mistake 2: Client/Server is Always Better

C/S is better for security and control, but P2P excels at scalability, cost, and fault tolerance. The right choice depends on requirements. For file distribution to millions, P2P is superior.

Mistake 3: Confusing Client/Server with Mainframe

Client/Server ≠ mainframe/terminal. In C/S, clients have processing power (fat clients). Mainframe: all processing on server, terminals are dumb display-only. Modern C/S distributes processing.

Mistake 4: P2P has No Cost

P2P eliminates server costs but adds hidden costs: user time for setup, troubleshooting, security, and inconsistent performance. Bandwidth usage may also increase ISP costs.

Mistake 5: All Traffic Goes Through Server in C/S

In pure C/S, yes. But modern networks use peer-to-peer optimizations (direct database replication, CDN edge caching). Some traffic bypasses the central server while maintaining C/S architecture.
