TCP Congestion Control

Transport Layer — Section 3.7.1 | Classic TCP Tahoe & Reno, CUBIC

Overview of TCP Congestion Control

TCP limits its sending rate using a congestion window (cwnd). The sender cannot have more than cwnd bytes of unacknowledged data. The rate is roughly cwnd/RTT.

Fundamental Constraint
LastByteSent − LastByteAcked ≤ min{cwnd, rwnd}
Unacknowledged data limited by both congestion window and receive window. cwnd primarily limits rate during congestion control.
Send Rate (approx)
rate ≈ cwnd / RTT  bytes/sec
When loss/delay is negligible and cwnd bytes sent per RTT.

Three Principles

1. Loss → Congestion

Timeout or 3 duplicate ACKs = loss event

2. ACK → Good

ACK signals successful delivery, increase rate

3. Bandwidth Probing

Increase until loss, then back off, repeat

Key Variables

cwnd — congestion window

ssthresh — slow start threshold

Loss event: timeout OR 3 dupACKs

Self-clocking: ACKs trigger cwnd increase

Self-Clocking: TCP uses ACKs to trigger its increase in cwnd. Faster ACK arrival → faster window growth. This naturally adapts to the RTT of the path.

Slow Start

At connection start, cwnd is initialized to 1 MSS (RFC 3390). TCP doubles cwnd every RTT until it detects congestion or reaches ssthresh.

Slow Start Growth (per ACK)
cwnd += 1 MSS  (doubles every RTT)
For each ACK received, cwnd increases by 1 MSS. This doubles the window per RTT (exponential growth).
On Loss (timeout)
ssthresh = cwnd/2    cwnd = 1 MSS
After timeout, reset to 1 MSS and start slow start again. ssthresh records half the loss window.

Slow Start Timeline

t=0: cwnd = 1 MSS, send 1 segment

t=RTT: ACK arrives, cwnd = 2 MSS, send 2

t=2RTT: both ACKed, cwnd = 4, send 4

t=3RTT: cwnd = 8, send 8

... Exponentially fast

When Slow Start Ends

1. Timeout → cwnd=1, ssthresh=cwnd/2

2. cwnd ≥ ssthresh → transition to congestion avoidance

3. 3 duplicate ACKs → fast retransmit + fast recovery

Common Mistake: Despite the name "slow start," the growth is exponential, not slow at all! The name comes from the fact that it starts from cwnd=1 rather than pumping the full receiver window immediately.

Congestion Avoidance

Once cwnd reaches ssthresh, TCP switches to linear (additive) increase: +1 MSS per RTT. This is the AIMD phase.

Linear Increase (per ACK)
cwnd += MSS × (MSS / cwnd)
This gives +1 MSS per RTT. If cwnd = 10 MSS, each ACK increases cwnd by MSS/10.
On Loss
Timeout:  cwnd = 1 MSS, ssthresh = cwnd/2
Triple dupACK:  cwnd = cwnd/2, ssthresh = cwnd/2
Timeout is treated more severely (full reset to 1). Triple dupACK only halves cwnd (Reno).

TCP Tahoe

• On any loss: cwnd = 1 MSS

• Always enters slow start after loss

• Simpler, more aggressive reduction

• Lower throughput after triple dupACK

TCP Reno

• On timeout: cwnd = 1 MSS (slow start)

• On 3 dupACK: cwnd = cwnd/2 (fast recovery)

• Differentiates between mild and severe loss

• Better throughput than Tahoe

Key Difference: Tahoe always goes back to slow start (cwnd=1). Reno distinguishes: timeouts are severe (cwnd=1), but triple dupACKs are mild (cwnd/=2). This makes Reno much more efficient when packet loss is due to occasional drops.

Fast Recovery & AIMD

Fast Recovery (Reno only)

After receiving 3 duplicate ACKs, Reno enters fast recovery:

On Each Duplicate ACK (fast recovery)
cwnd += 1 MSS
Inflates cwnd to keep pipe full while waiting for retransmission.
On New ACK (exit fast recovery)
cwnd = ssthresh
Returns to congestion avoidance at half the pre-loss rate.

AIMD: Additive Increase / Multiplicative Decrease

The saw-tooth pattern: cwnd increases by 1 MSS per RTT (additive), halves on triple dupACK (multiplicative).

Average Throughput (Reno)
Average Throughput = 0.75 × W / RTT
W = window size at loss event. W/2 at bottom, W at top, average = 0.75W.

AIMD Properties

• Fairness: converges to equal share

• Efficiency: probes available bandwidth

• Stability: reduces rate on congestion

• Distributed: no central coordinator

Saw-Tooth Pattern

cwnd: 10 → 11 → 12 → ... → 20 (loss)

↓

cwnd: 10 (after halving)

→ 11 → 12 → ... → 20 (loss again)

Average ≈ 15 segments

Common Mistake: Fast recovery is NOT present in TCP Tahoe. Tahoe always goes to slow start (cwnd=1). Fast recovery is a Reno-specific optimization. Many exam questions test this distinction.

TCP CUBIC

T he default congestion control algorithm in Linux. Unlike Reno's linear growth, CUBIC uses a cubic function to grow cwnd, allowing faster recovery to the pre-loss rate.

CUBIC Window Growth
W(t) = C × (t − K)³ + Wmax
C = scaling constant, t = time since loss, K = time to reach Wmax. When t < K, growth is fast near Wmax; when t > K, growth accelerates to find new bandwidth.

CUBIC vs Reno

CUBIC — Quickly ramps to Wmax

Gentle probing near Wmax

If congestion unchanged, stays near Wmax

If congestion changed, probes quickly

Deployment

~50% of top 5000 web servers

Default in Linux kernel

Widely deployed in data centers

RFC 8312

Why Cubic? In high-BW long-RTT paths, Reno's linear growth takes too long to reach the pre-loss rate. CUBIC's cubic growth gets there fast, then probes carefully near the known congestion point.

Example 4 — Average Throughput Calculation

Setup: MSS = 1500 bytes, RTT = 200ms. Loss occurs when cwnd = 60 KB (40 segments).

The Reno saw-tooth: cwnd ranges from W/2 = 30 KB to W = 60 KB.

Average cwnd: (30 + 60) / 2 = 45 KB (0.75 × 60 KB = 45 KB ✓)

Average throughput: (45 KB × 8 bits/byte) / 0.200 sec = 360 Kb / 0.2 = 1.8 Mbps

Throughput = 0.75 × 60 KB / 200ms = 1.8 Mbps

Loss Rate vs Throughput
Average Throughput = (1 / RTT) × √(1.5 × MSS / loss_rate)
For the example, to achieve 1.8 Mbps (1500 KB/s) with MSS=1500B, RTT=200ms: loss_rate ≈ 1.5 / (37.5²) ≈ 0.1%
Example 5 — CUBIC Ramp-Up Comparison

Setup: Wmax = 100 segments. Loss at t=0. RTT = 100ms.

Reno: cwnd drops to 50. Grows by 1 MSS/RTT. Takes 50 RTTs (5 sec) to return to 100.

CUBIC: Calculates K such that cwnd reaches Wmax quickly. For typical C, K ≈ 5 RTTs. CUBIC grows fast initially (cubic), then gently probes near 100. Returns to 100 in ~5 RTTs (0.5 sec).
