Principles of Reliable Data Transfer

Computer Networking — Complete Guide for 20/20 Exam

rdt1.0 — Perfectly Reliable Channel

The simplest case: underlying channel is completely reliable. No bit errors, no loss, no reordering. Both sender and receiver have just one state.

rdt1.0 Sender (FSM):
State: Wait for call from above
Event: rdt_send(data)
Action: packet = make_pkt(data); udt_send(packet)

rdt1.0 Receiver (FSM):
State: Wait for call from below
Event: rdt_rcv(packet)
Action: extract(packet, data); deliver_data(data)
rdt1.0 assumes perfect channel — no error checking, no ACKs, no NAKs, no sequence numbers. This is purely theoretical; real channels have bit errors and loss.

rdt2.0 — Channel with Bit Errors

Adds three capabilities (ARQ — Automatic Repeat reQuest):

Error Detection

Checksum bits added to the packet. Receiver detects corrupted bits.

Receiver Feedback

ACK (positive acknowledgment) and NAK (negative acknowledgment) packets sent from receiver to sender.

Retransmission

Sender retransmits packets received in error. This is a stop-and-wait protocol — sender waits for ACK/NAK before sending next packet.

Fatal flaw: ACK/NAK packets can themselves be corrupted! The sender cannot know whether the receiver got the last packet correctly.

Three Approaches for Corrupted ACK/NAK

1. "What did you say?"

Add a new sender-to-receiver packet asking the receiver to repeat its reply. But that new packet could also be corrupted — leading to an infinite loop of meta-questions.

2. Enough Checksum Bits

Add enough checksum bits to allow the sender not only to detect but also to recover from bit errors without retransmission. Works for corruption but not for packet loss.

3. Resend + Sequence Numbers

Simply resend the current data packet when a garbled ACK/NAK is received. This introduces duplicate packets, which sequence numbers handle. This approach is adopted in almost all existing protocols including TCP.

rdt2.1 — Sequence Numbers to the Rescue

Adds a 1-bit sequence number (0 or 1) to data packets. Now the receiver can distinguish new data from retransmissions. The sender has 4 states (wait for call 0/1, wait for ACK/NAK 0/1).

rdt2.1 Sender (key additions):
- Packet numbered: make_pkt(seq#, data, checksum)
- On corrupted ACK/NAK: retransmit current packet (doesn't advance seq#)
- On valid ACK: advance to next seq# (flip 0↔1)

rdt2.1 Receiver (key additions):
- Tracks expected sequence number (0 or 1)
- If out-of-order seq# received: send ACK for expected packet (duplicate)
- If corrupted: send NAK

rdt2.2 — NAK-Free Protocol

Eliminates NAK packets entirely. Instead, the receiver sends an ACK for the last correctly received packet. A sender receiving duplicate ACKs knows the next packet was not received correctly.

rdt2.2 Key Innovation:
Duplicate ACKs Replace NAKs
Receiver sends ACK with seq# of last correctly received in-order packet.
Two ACKs for the same seq# → sender knows to retransmit the next packet.

rdt3.0 — Lossy Channel with Bit Errors

Now the channel can lose packets too (not just corrupt them). This requires a countdown timer to detect and recover from lost packets.

Key Mechanisms

  • Timer: Started when a packet is sent. If timeout fires before ACK received → retransmit
  • Timeout period: Set to at least RTT + processing time. In practice, a conservative estimate is used
  • Sequence numbers: 1-bit alternating (0, 1, 0, 1...) — known as the alternating-bit protocol
rdt3.0 Sender FSM (simplified):
State: Wait for call 0 from above
├─ rdt_send(data) → make_pkt(0,data,chk), start_timer
└─ goto: Wait for ACK 0

State: Wait for ACK 0
├─ rcv ACK(0) → stop_timer, goto: Wait for call 1
├─ timeout → resend pkt0, start_timer
└─ rcv corrupt/ACK(1) → do nothing (wait)

Stop-and-Wait Performance

Sender Utilization:
Usender = (L/R) / (RTT + L/R)
L = packet size (bits), R = transmission rate (bps), RTT = round-trip time (sec)
Example: Stop-and-Wait Performance Problem

Given: R = 1 Gbps, L = 1000 bytes (8000 bits), RTT = 30 ms

dtrans = L/R = 8000 / 109 = 8 microseconds

Usender = 0.008 / (30 + 0.008) = 0.00027 = 0.027%

Effective throughput = 0.00027 × 1 Gbps = 267 kbps — terrible for a 1 Gbps link!

The sender was busy only 2.7 hundredths of one percent of the time. This motivates pipelining.

Bandwidth-Delay Product (BDP)
BDP = Bandwidth × RTT
With R = 1 Gbps, RTT = 30 ms: BDP = 10⁹ × 0.03 = 30,000,000 bits = 3.75 MB
This is the number of bytes that can be "in flight" before the first ACK returns.
To fully utilize the link, the window must be at least BDP / MSS ≈ 3750 packets of 1000 bytes each.

Four Scenarios (Fig 3.16)

(a) No loss — normal operation

(b) Data packet lost → timeout → retransmit

(c) ACK lost → timeout → retransmit (duplicate at receiver)

(d) Premature timeout → duplicate ACK received

Retransmission = Panacea

Sender doesn't know if DATA was lost, ACK was lost, or just delayed. In all cases: retransmit. Sequence numbers handle duplicates.

Pipelining and Go-Back-N (GBN)

Stop-and-wait protocols are too slow. Pipelining allows the sender to transmit multiple packets without waiting for acknowledgments. This fills the "pipeline" and dramatically improves utilization.

Pipelined Utilization:
Upipelined ≈ N × (L/R) / (RTT + L/R)
N = number of packets in flight. With N large enough, U → 1 (full utilization).

Go-Back-N (GBN)

The sender is allowed to have up to N unacknowledged packets in the pipeline. Sequence number space: [0, 2k - 1].

Sender Variables

base: seq# of oldest unacknowledged packet

nextseqnum: smallest unused seq#

Window: [base, base+N-1] for in-transit packets

Sender Events

1. From above: if window not full, send; else refuse

2. ACK receipt: cumulative ACK; slide window

3. Timeout: retransmit ALL packets from base to nextseqnum-1

GBN Sender Pseudocode:
rdt_send(data):
  if nextseqnum < base + N:
    sndpkt[nextseqnum] = make_pkt(nextseqnum, data, checksum)
    udt_send(sndpkt[nextseqnum])
    if base == nextseqnum: start_timer
    nextseqnum++
  else: refuse_data(data)

rdt_rcv(rcvpkt) && notcorrupt:
  base = getacknum(rcvpkt) + 1
  if base == nextseqnum: stop_timer else: start_timer

timeout:
  start_timer
  for i in [base, nextseqnum-1]: udt_send(sndpkt[i])

GBN Receiver

The receiver maintains only expectedseqnum. It:

  • ✓ Accepts only in-order packets (seq# == expectedseqnum)
  • ✗ Discards all out-of-order packets (correctly received but out of order are thrown away!)
  • ✓ Sends cumulative ACK for the highest consecutive packet received
GBN discards correctly-received out-of-order packets! This seems wasteful, but the receiver has no buffer for them — they'll be retransmitted anyway when the lost packet times out. This is GBN's main performance weakness.

Selective Repeat (SR)

Selective Repeat improves on GBN by retransmitting only lost/corrupted packets instead of the entire window. This avoids the "unnecessary retransmissions" problem of GBN when many packets are in the pipeline.

SR Sender

• Window of N sequence numbers

• Individual timers per packet (logical timers)

• Only retransmit the timed-out packet

• ACK received → mark packet as received

• Window advances when send_base is ACKed

SR Receiver

• Acknowledges each correctly received packet (individual ACKs)

• Buffers out-of-order packets

• Delivers batch of consecutive packets in order when gap filled

• Re-ACKs packets in [rcv_base-N, rcv_base-1] range

SR Receiver Events:

1. Packet seq in [rcv_base, rcv_base+N-1] received correctly:
  → Send selective ACK; buffer if not already received
  → If seq == rcv_base: deliver consecutive run, advance window

2. Packet seq in [rcv_base-N, rcv_base-1] received correctly:
  → Send ACK (re-acknowledge — critical!)

3. Otherwise: ignore

Critical Constraint: Window Size

SR Window Size Constraint:
Window Size ≤ (Max Seq# + 1) / 2
With k-bit seq#: N ≤ 2k-1. Otherwise sender and receiver may disagree on whether packet is new or a retransmission.
Example: Why Window Size Must Be ≤ Half of Seq# Space

Given: Sequence numbers 0,1,2,3 (2-bit field, max=4). Window size N=3.

Scenario A: Packets 0,1,2 sent. ACKs lost. Sender retransmits 0,1,2. Receiver thinks 0 is a retransmission of old data.

Scenario B: Same packets, ACKs received. Sender sends new packets 3,0,1. Packet 0 arrives — receiver sees seq=0.

Problem: The receiver cannot distinguish Scenario A (retransmission) from Scenario B (new data with seq=0)!

Solution: N ≤ 4/2 = 2. With window size 2, the ambiguity disappears.

SR is complex because sender and receiver windows are not synchronized. The sender doesn't know which packets the receiver has buffered. This is why re-ACKing packets in [rcv_base-N, rcv_base-1] is essential — it prevents the sender's window from stalling.

Worked Examples: RDT Mechanisms

Example 1: GBN Window Sliding

Given: N=4, base=2, nextseqnum=5. Packets 2,3,4 are in flight.

ACK for packet 2 arrives.

Action: base = 2+1 = 3. Window now covers [3, 6]. Sender can transmit packet 5 (if data available).

Before: Window [2,3,4,5]. After: Window [3,4,5,6]. Slid forward by 1.

Example 2: GBN Timeout — "Go-Back-N" in Action

Given: N=5, sender has sent packets 0 through 4. Packet 2 is lost.

Receiver gets: pkt0 ✓ (send ACK0), pkt1 ✓ (send ACK1).

Receiver gets: pkt3 ✗ (out of order — discard), pkt4 ✗ (discard).

Sender receives ACK0, ACK1. Timer for oldest unACKed (pkt2) eventually fires.

Sender retransmits: packets 2, 3, 4 (all from base to nextseqnum-1).

Packets 3 and 4 were correctly received but discarded and retransmitted — this is GBN's weakness!

Example 3: SR Recovery — Individual Retransmission

Given: N=4, seq# space [0..7]. Sender sends pkts 0,1,2,3. Pkt 2 is lost.

Receiver: pkt0 ✓ → ACK0; pkt1 ✓ → ACK1; pkt3 ✓ → ACK3 (buffered).

Sender receives ACK0, ACK1, ACK3. Only pkt2's timer remains active.

pkt2 times out. Sender retransmits ONLY pkt2.

Receiver gets pkt2 ✓ → delivers pkt2 AND buffered pkt3 to upper layer. Both windows advance.

SR saves N-1 = 3 unnecessary retransmissions compared to GBN!

Example 4: rdt3.0 — Premature Timeout

Scenario: Sender sends pkt0. The packet and ACK are both fine (no loss), but the ACK is delayed (congestion).

Timer fires before ACK arrives → sender retransmits pkt0 (duplicate).

Receiver sees seq=0 again → detects duplicate via seq# → sends ACK0 again (duplicate ACK).

Original (delayed) ACK0 arrives → sender ignores (already advanced? No, rdt3.0 is stop-and-wait).

Correct behavior: Both ACKs are identical (seq#0). The sender receives the first ACK, advances to seq#1. The second ACK0 is a duplicate and is ignored (rdt3.0 sender discards ACK with wrong seq#).

Example 5: Sender Utilization Calculation

Given: R = 10 Mbps, L = 2000 bytes (16000 bits), RTT = 100 ms.

dtrans = L/R = 16000 / 107 = 0.0016 s = 1.6 ms

Stop-and-wait: U = 1.6 / (100 + 1.6) = 0.0157 → 1.57%

Pipelined with N=10: U ≈ 10 × 0.0157 = 0.157 → 15.7%

N needed for 100% utilization: N ≥ (RTT + L/R) / (L/R) = 101.6 / 1.6 ≈ 64 packets

Summary Table: RDT Mechanisms

Mechanism Purpose Used In
Checksum Detect bit errors in transmitted packet rdt2.0, rdt2.1, rdt2.2, rdt3.0, GBN, SR, TCP
Timer Timeout/retransmit when packet or ACK is lost rdt3.0, GBN (single timer), SR (per-packet timer), TCP
Sequence Number Detect lost packets (gaps), detect duplicates rdt2.1, rdt2.2, rdt3.0, GBN, SR, TCP
ACK Tell sender packet(s) received correctly rdt2.0+, GBN (cumulative), SR (individual), TCP (cumulative)
NAK Tell sender packet received incorrectly rdt2.0, rdt2.1 (eliminated in rdt2.2+ via duplicate ACKs)
Window / Pipelining Allow multiple unacknowledged packets; improve utilization GBN (size N), SR (size N), TCP (adaptive)

RDT Evolution Summary

rdt1.0: Perfect channel (no errors)

rdt2.0: +ACK/NAK (bit errors)

rdt2.1: +Seq# (corrupted ACK/NAK)

rdt2.2: -NAK (duplicate ACKs)

rdt3.0: +Timer (packet loss)

GBN: +Pipelining, cumulative ACK

SR: +Selective retransmission

Common Exam Mistakes

• Confusing GBN vs SR retransmission behavior

• Forgetting SR's window size constraint (≤ half)

• Misunderstanding cumulative vs individual ACKs

• Thinking rdt2.2 uses NAKs (it doesn't!)

• Not wrapping overflow in checksum calculation
