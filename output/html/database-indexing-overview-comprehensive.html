Database Indexing Overview

Database Systems — Complete Guide for 20/20 Exam

Why Do We Need Indexes?

Without an index, the database must perform a full table scan — reading every single row to find matching records. This is extremely slow for large tables.

Full Table Scan Cost:
O(n) per query
n = number of rows in the table. A table with 1 million rows means 1 million reads per query.
Index Lookup Cost:
O(log n) per query
A B+ tree index on 1 million rows needs only ~20 comparisons (log1000 1,000,000 ≈ 2).
Warning: Indexes speed up reads but slow down writes. Every INSERT, UPDATE, or DELETE must also update every index on that table. Over-indexing kills write performance.

The Book Index Analogy

An index in a database works exactly like the index at the back of a textbook.

Without Index (Full Scan): ┌─────────────────────────────────────────┐ │ To find "B+ Tree" in this textbook: │ │ 1. Open page 1, scan all content... │ │ 2. Open page 2, scan all content... │ │ 3. Open page 3, scan all content... │ │ 4. ... repeat for all 400 pages │ │ Total: 400 page reads │ └─────────────────────────────────────────┘ With Index (Index Lookup): ┌─────────────────────────────────────────┐ │ Go to Index at back of book: │ │ "B+ Tree" ........... page 312 │ │ Flip directly to page 312. │ │ Total: 1 index read + 1 page read │ └─────────────────────────────────────────┘

Table of Contents (No Index)

  • Lists topics in order of appearance
  • Does NOT help find a specific concept fast
  • Like scanning every row sequentially
  • Good for browsing, bad for searching

Back-of-Book Index (With Index)

  • Alphabetical listing of key terms
  • Directly points to the page number
  • Like a database index pointing to rows
  • Excellent for finding specific data fast

What Exactly Is a Database Index?

A database index is a separate data structure (typically a B+ tree or hash table) that stores a copy of selected columns along with a pointer to the actual row in the table.

Structure

Contains: search key + record pointer

The search key is the column(s) being indexed

Location

Stored in a separate file from the table data

Can exist on different disk pages

Automatic Use

The query optimizer decides when to use an index

You don't manually tell DB which index to use

Multiple Indexes

A table can have many indexes

Each index is a separate B+ tree

Types of Database Indexes

1. Clustered Index

The clustered index determines the physical order of data on disk. The table data is stored in the same order as the clustered index. Only one clustered index per table.

Clustered Index (e.g., on StudentID): ┌──────────────────────────────────────────┐ │ Disk pages contain actual row data │ │ sorted by the index key │ │ │ │ Page 1: [1, Alice, CS] [2, Bob, Math] │ │ Page 2: [3, Carol, CS] [4, Dave, Eng] │ │ Page 3: [5, Eve, Math] [6, Frank, CS] │ │ │ │ B+ Tree leaf nodes = data pages │ └──────────────────────────────────────────┘

Key Properties

• One per table (only one physical order)

• Leaf nodes contain the actual row data

• Usually created on PRIMARY KEY

• Fastest for range queries

Best For

• Columns used in ORDER BY

• Range queries (BETWEEN, >, <)

• Primary key lookups

• Columns with high cardinality

2. Nonclustered Index

A nonclustered index has a separate structure from the data rows. The leaf nodes contain pointers (row locators) to the actual data, not the data itself.

Nonclustered Index (e.g., on LastName): ┌───────────────────┐ ┌──────────────────────┐ │ Index Structure │ │ Table Data (heap) │ │ │ │ │ │ Adams ──────────┼────▶│ Row 5 │ │ Brown ──────────┼────▶│ Row 2 │ │ Chen ───────────┼────▶│ Row 8 │ │ Davis ──────────┼────▶│ Row 1 │ │ │ │ (scattered on disk) │ └───────────────────┘ └──────────────────────┘

Key Properties

• Many per table (up to 999 in SQL Server)

• Leaf nodes contain pointers, not data

• Separate structure from table

• Requires bookmark lookup to get full row

Best For

• Columns in WHERE clauses

• Columns used in JOINs

• Columns in SELECT lists

• Covering indexes avoid lookup

3. Hash Index

Uses a hash function to map keys to buckets. Provides O(1) average-case lookup for exact-match queries.

Hash Index Structure: ┌──────────────┐ ┌──────────────────────┐ │ Hash Function│ │ Buckets │ │ │ │ │ │ h("Alice")=3├────▶│ Bucket 0: [...] │ │ h("Bob") =7├────▶│ Bucket 1: [...] │ │ h("Carol")=1├────▶│ Bucket 2: [...] │ │ h("Dave") =3├────▶│ Bucket 3: [Alice,Dave]│ │ │ │ ... │ └──────────────┘ │ Bucket 7: [Bob] │ └──────────────────────┘

Key Properties

• O(1) lookup for equality

• No range queries possible

• Sensitive to hash collisions

• Not stored in sorted order

Best For

• Exact match lookups only

• Equality predicates (=, IN)

• NOT for range, ORDER BY, JOINs

• Memory-resident tables

Read Speed vs Write Speed

Indexes create a fundamental trade-off: faster reads at the cost of slower writes.

Read Benefits

  • SELECT queries become dramatically faster
  • JOIN operations use index for matching
  • ORDER BY can use sorted index
  • GROUP BY benefits from sorted index

Write Costs

  • INSERT must update every index
  • DELETE must update every index
  • UPDATE may re-index if key changes
  • B+ tree splits add overhead
Example: Impact of Adding 3 Indexes

Without indexes: INSERT takes 1ms, SELECT takes 500ms

With 3 indexes: INSERT takes 4ms (4x slower), SELECT takes 2ms (250x faster)

The write penalty is usually acceptable for the massive read improvement.

Index Overhead

Storage Overhead

Each index is a separate B+ tree stored on disk.

Example:

A 1 GB table with 5 indexes may use ~2 GB total (table + indexes).

Index size depends on: key size, number of rows, fanout.

Maintenance Overhead

Every data modification must update all indexes.

Operations affected:

• INSERT: Insert into each index B+ tree

• DELETE: Remove from each index B+ tree

• UPDATE: If indexed column changes, re-index

Rebuild Overhead

Indexes fragment over time (page splits).

Maintenance needed:

• Periodic REBUILD or REORGANIZE

• Takes time and I/O resources

• Scheduled during low-traffic periods

Optimizer Overhead

More indexes = more choices for optimizer.

Consequence:

• Query plan compilation takes longer

• May pick wrong index (suboptimal plan)

• Statistics must be kept up to date

Warning: The "index every column" approach is a trap. More indexes do NOT always mean better performance. Each index costs storage, memory, and write time. Choose indexes strategically based on actual query patterns.

When to Use Indexes — Decision Guide

Scenario Create Index? Reason
Column in WHERE clause frequently YES Speeds up row filtering
Column used in JOINs YES Speeds up join matching
Column with LOW cardinality (e.g., Gender: M/F) MAYBE Index may not help; full scan might be faster
Column with HIGH cardinality (e.g., Email) YES Many distinct values = efficient index
Small table (<1000 rows) NO Full scan is fast enough; index overhead not worth it
Large table (1M+ rows) YES Full scan is prohibitively slow
Table is write-heavy (many INSERT/UPDATE) MINIMAL Each index slows writes; only index critical columns
Table is read-heavy (many SELECT) YES (multiple) Read performance is priority; write cost acceptable
Column is rarely queried NO Index wastes storage and slows writes for no benefit
Column used in ORDER BY YES Index provides pre-sorted data

Key Decision Factors

When deciding whether to create an index, evaluate these three factors:

1. Table Size

Small tables (<1K rows):

• Full table scan is fast enough

• Index overhead exceeds benefit

• Skip indexing

Medium tables (1K-100K rows):

• Index on frequently queried columns

• Consider covering indexes

Large tables (>100K rows):

• Index on all frequently queried columns

• Consider composite indexes

2. Query Patterns

Analyze workload type:

• Read-heavy: Many indexes beneficial

• Write-heavy: Fewer indexes needed

• Mixed: Balance carefully

Check query execution plans:

• Use EXPLAIN / EXPLAIN ANALYZE

• Identify full table scans

• Add indexes where scans are costly

3. Update Frequency

Tables that change rarely:

• Index aggressively (read performance wins)

• Can afford many indexes

Tables that change frequently:

• Index conservatively

• Only index critical query paths

• Monitor write performance

Index Selection Checklist

Use this checklist before creating an index:

Pre-Index Checklist

  • [ ] Is the column used in WHERE, JOIN, or ORDER BY?
  • [ ] Is the table large enough to benefit? (>1K rows)
  • [ ] Does the column have sufficient cardinality?
  • [ ] Will the index be used frequently enough to justify write cost?
  • [ ] Check existing indexes — is a covering index possible?
  • [ ] Monitor query plans after creating the index
  • [ ] Schedule periodic index maintenance (rebuild/reorganize)
Common Mistake: Creating an index and assuming it helps. Always verify with EXPLAIN that the query optimizer actually uses the new index. Sometimes the optimizer still prefers a full scan due to statistics or selectivity.

Composite Indexes & Column Order

When creating an index on multiple columns, column order matters.

Composite Index: (LastName, FirstName)

This index can efficiently answer:

• WHERE LastName = 'Smith' — Uses index (prefix match)

• WHERE LastName = 'Smith' AND FirstName = 'John' — Uses index (full prefix)

• WHERE FirstName = 'John' — Cannot use index (skips prefix)

Rule: Put the most selective / most frequently queried column first.

Composite Index Rule (Leftmost Prefix):
INDEX(a, b, c) can serve: a | a,b | a,b,c — NOT b,c or c alone
The index can only be used if the query includes the leftmost column(s) of the index.

Worked Examples

Example 1: Choosing an Index for a Student Table
CREATE TABLE Students ( id INT PRIMARY KEY, first_name VARCHAR(50), last_name VARCHAR(50), gpa DECIMAL(3,2), department VARCHAR(30) );

Query pattern: SELECT * FROM Students WHERE last_name = 'Smith'; (run 1000x/day)

Query pattern: SELECT * FROM Students ORDER BY gpa DESC; (run 50x/day)

Decision:

• Clustered index on id (PRIMARY KEY) — default

• Nonclustered index on last_name — frequently queried, high cardinality

• Nonclustered index on gpa — used in ORDER BY

Don't index department (low cardinality: few distinct values).

Example 2: Write-Heavy Table — Log Entries
CREATE TABLE AccessLog ( log_id INT PRIMARY KEY, user_id INT, action VARCHAR(20), timestamp DATETIME, ip_address VARCHAR(45) );

Write rate: 50,000 inserts/day

Read pattern: SELECT * FROM AccessLog WHERE user_id = ? AND timestamp BETWEEN ? AND ?;

Decision:

• Clustered index on log_id (PRIMARY KEY)

• Nonclustered index on (user_id, timestamp) — composite, supports both WHERE and range

• Do NOT index ip_address or action — rarely queried, would slow 50K daily inserts

Balance: only 1 extra index to keep write performance acceptable.

Example 3: Composite Index Column Order
CREATE INDEX idx_name ON Employees(last_name, first_name, hire_date);

Which queries can use this index?

Example 4: Identifying When NOT to Index

Scenario: A Gender column with values 'M' and 'F' (low cardinality).

Query: SELECT * FROM Users WHERE gender = 'M';

Analysis:

• Index selectivity = 50% (half the rows match)

• Optimizer will likely prefer full table scan

• Index wastes storage and slows every INSERT/UPDATE

Decision: Do NOT create index on Gender.

Rule of thumb: Index selectivity should be <10-15% (index returns a small fraction of rows) to be beneficial.

Example 5: Covering Index

Query: SELECT first_name, last_name FROM Employees WHERE department = 'Sales';

Regular index on department:

• Finds matching rows via index

• Must do bookmark lookup to get first_name and last_name from table

Covering index:

CREATE INDEX idx_dept_cover ON Employees(department, last_name, first_name);

• Index contains all needed columns (department, last_name, first_name)

• No bookmark lookup needed — all data is in the index leaf

• Query runs 2-5x faster (no extra I/O to fetch table rows)

A covering index satisfies the entire query from the index alone.
