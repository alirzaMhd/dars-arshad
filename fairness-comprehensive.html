TCP Fairness

Section 3.7.3 — Complete Guide for 20/20 Exam

AIMD Fairness

When K TCP connections share a bottleneck link of rate R bps, a fair congestion control mechanism gives each connection approximately R/K bandwidth — an equal share. TCP's Additive-Increase Multiplicative-Decrease (AIMD) algorithm provably converges to this equal share.

Fair Share Definition:
Fair Rate per Connection = R / K
K connections sharing a bottleneck link of rate R bps, each gets R/K on average

How AIMD Achieves Fairness

TCP's AIMD algorithm produces a characteristic "saw-tooth" pattern: the congestion window increases linearly by 1 MSS per RTT and is cut in half upon packet loss. Over time, competing connections converge to equal bandwidth shares.

AIMD Update Rules:
On ACK: cwnd ← cwnd + 1 MSS (Additive Increase)
On Loss: cwnd ← cwnd / 2 (Multiplicative Decrease)
Each connection increases by the same absolute amount per RTT and decreases by the same factor (2x) on loss

45-Degree Increase Line

In throughput space (connection 1 vs connection 2), the 45-degree line represents equal bandwidth share. AIMD always increases along this line because both connections add 1 MSS per RTT, maintaining equal absolute increment.

Multiplicative Decrease Toward Origin

On loss, both connections halve their windows, moving along a vector toward the origin. This preserves the ratio of their throughputs, so they stay on the equal-share trajectory.

Common Mistake: AIMD does NOT guarantee instant fairness — it converges over multiple cycles. Connections starting at different times or with different RTTs may temporarily get unequal shares.

Chiu & Jain Convergence Proof (Conceptual)

Chiu and Jain (1989) proved that AIMD converges to fairness regardless of starting point. The key insight: additive increase moves both connections along the 45-degree line (equal absolute increase), and multiplicative decrease preserves the ratio of their throughputs. Over repeated cycles, the operating point converges to the intersection of the equal-share line and full-utilization line.

AIMD Convergence (Two Connections): Initial state: (x, y) where x ≠ y Step 1: Both add 1 per RTT → (x+1, y+1) — moves toward 45° line Step 2: Loss occurs at (x', y') Step 3: Both halve → (x'/2, y'/2) — preserves ratio x'/y' Step 4: Repeat — over cycles, ratio approaches 1:1

Fairness Analysis

Consider two TCP connections sharing a single bottleneck link of rate R. Throughput space is visualized with Connection 1 on the x-axis and Connection 2 on the y-axis.

Convergence Cycle (Point A → B → C → D):
A → B: Both connections increase (45° line, total < R)
B → C: Both halve on loss (vector toward origin)
C → D: Both increase again (45° line, total < R)
The throughput oscillates along the equal-bandwidth share line over time

The Convergence Process

Point A

Underutilized: x + y < R. Both connections increase by 1 MSS/RTT → move along 45° line.

Point B

Loss Event: x + y > R, packet drops. Both immediately halve cwnd → move toward origin.

Point C

Underutilized again: At half the bandwidth, both start increasing linearly.

Point D

Loss Event: Repeat the cycle. Over multiple cycles, the trajectory converges to the equal share line.

RTT Bias

In practice, connections with smaller RTTs open their congestion windows faster and grab available bandwidth more aggressively.

Throughput with Different RTTs:
Throughput ≈ (1 / RTT) × f(cwnd)
A connection with half the RTT can achieve roughly double the throughput of a connection with the full RTT, given the same cwnd
FactorImpact on Fairness
Different RTTsSmaller RTT → higher throughput (unfair advantage)
Different Start TimesEarlier start → initially larger window
Different MSSLarger MSS → more data per ACK → faster increase
Number of ConnectionsMore connections per host → larger aggregate share
Warning: The idealized convergence assumes identical RTTs, identical MSS, and no UDP traffic. In real networks, these assumptions almost never hold, leading to significant unfairness.

UDP & Parallel TCP

UDP Unfairness

UDP has no built-in congestion control. A UDP application can send at any rate, for as long as it pleases, without throttling. Since TCP reduces its rate during congestion while UDP does not, UDP sources can easily crowd out TCP traffic on a shared bottleneck link.

Critical Exam Point: Multimedia applications (Internet phone, video conferencing) often choose UDP precisely because they do NOT want their transmission rate throttled — even if it means being "unfair" to TCP flows.

Parallel TCP Connections

Even among TCP-based applications, unfairness arises when applications use multiple parallel connections. Web browsers commonly open multiple parallel TCP connections to download page objects simultaneously.

Parallel TCP Bandwidth Formula:
Fraction of R for App = (n_parallel) / (N_total + n_parallel - 1)
App with n parallel connections among N total single-connection apps gets more than fair share

9 Apps × 1 Connection Each

Each gets R/10 ≈ 10% of bandwidth

New app with 1 connection: also R/10

Same 9 Apps + New App with 11 Connections

New app gets > R/2 (more than half!)

Each of the 9 others gets < R/18

Real-World Impact

Web browsers commonly use 6-30+ parallel TCP connections per page. This gives web traffic a disproportionate share of bottleneck bandwidth compared to non-browser applications. Some protocols (like HTTP/2 and HTTP/3) mitigate this through connection multiplexing.

Worked Examples

Example 1: AIMD Fairness Convergence

Problem: Two TCP connections share a bottleneck link of 100 Mbps. Connection A starts at cwnd = 10 MSS and Connection B starts at cwnd = 2 MSS. Assume MSS = 1,500 bytes and RTT = 100 ms for both. Show two AIMD cycles and compute the throughput after convergence.

Solution:

Cycle 1:
- Initial: A = 10 MSS, B = 2 MSS. Total = 12 MSS = 12 × 1500 × 8 = 144,000 bits
- AI (1 RTT): A = 11, B = 3. Total = 14 MSS
- AI (2 RTT): A = 12, B = 4. Total = 16 MSS = 192,000 bits = 1.92 Mbps
- Continue until total exceeds 100 Mbps bottleneck capacity
- Loss at ~84 RTTs: A ≈ 94, B ≈ 86. Total ≈ 180 MSS ≈ 216 Mbps. Halve: A = 47, B = 43

Cycle 2:
- A = 47, B = 43. Ratio ≈ 1.09:1 (much closer to equal)
- Increase until next loss, then halve again
- After several cycles: A ≈ B ≈ 50 MSS average → each gets ~50 Mbps

After convergence: Each connection ≈ 50 Mbps (R/2)

The ratio A:B converges from 5:1 toward 1:1 over successive cycles.

Example 2: RTT Bias Calculation

Problem: Two TCP connections share a bottleneck link of 10 Mbps. Connection X has RTT = 40 ms, Connection Y has RTT = 120 ms. Both have MSS = 1,500 bytes and the same congestion window size at steady state. Estimate the throughput ratio between X and Y.

Solution:

TCP throughput ≈ (cwnd × MSS) / RTT. At the same cwnd:

Throughput_X / Throughput_Y = RTT_Y / RTT_X = 120 / 40 = 3

Connection X gets approximately 3× the throughput of Y.

If fair share would be 5 Mbps each, actual allocation:

- Throughput_X = 3/4 × 10 Mbps = 7.5 Mbps

- Throughput_Y = 1/4 × 10 Mbps = 2.5 Mbps

This demonstrates why geographically distant connections (larger RTT) suffer throughput penalties compared to nearby connections.

Example 3: Parallel TCP Bandwidth Allocation

Problem: A bottleneck link of 1 Gbps carries traffic from 5 existing applications, each using 1 TCP connection. A new application arrives and opens 8 parallel TCP connections. What fraction of the bandwidth does the new application receive?

Solution:

Total connections: 5 (existing) + 8 (new) = 13 connections

Per-connection fair share: 1 Gbps / 13 ≈ 76.9 Mbps

New application total: 8 × 76.9 Mbps ≈ 615.4 Mbps (61.5%)

Each existing application: 76.9 Mbps (7.7%)

Compare: If the new app used 1 connection, it would get 1/6 ≈ 166.7 Mbps (16.7%). By using 8 parallel connections, it gets 3.7× more bandwidth.

Key Insight: Using 8 parallel connections gives the new app more than half the link bandwidth (61.5%), while each existing fair app suffers a 54% reduction (from 166.7 Mbps to 76.9 Mbps).
