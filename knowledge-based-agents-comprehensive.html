Knowledge-Based Agents

Artificial Intelligence — Logical Agents

What is a Knowledge-Based Agent?

A knowledge-based agent is an intelligent agent that uses an explicit knowledge base (KB) and reasoning to decide its actions. Unlike a purely reactive agent that maps percepts directly to actions, a knowledge-based agent maintains an internal representation of the world and uses logical inference to derive new facts and choose optimal behaviors.

Central Idea
Maintain a KB of sentences in a knowledge representation language; use TELL/ASK operations to reason
Key Benefit
Flexibility — can accept new tasks as goals, learn from new information, adapt to changing environments
Key Challenge
Designing a representation language and inference algorithms that are both expressive and tractable
Core Principle
Agent Behavior = f(Knowledge Base + Perception + Inference)
The agent's actions are determined by what it knows (KB), what it senses (percepts), and what it can derive (inference)
Important: A knowledge-based agent is NOT just a lookup table. It can combine general knowledge with current observations to infer hidden aspects of the world state before acting.

Why Knowledge-Based Agents?

Problem-solving agents (Chapter 3) work only in fully observable, deterministic environments where the agent knows the outcome of its actions. Knowledge-based agents overcome these limitations:

  • Partial observability: Combine general knowledge with observations to infer hidden state (e.g., a doctor diagnosing a disease before treatment)
  • Flexible knowledge: Chess programs can compute legal moves but don't know that a piece can't be in two squares at once — KB agents can represent such general knowledge
  • Composability: A mathematician proving theorems combines known facts with general axioms; a KB agent does the same
  • Adaptability: New tasks can be accepted as explicitly described goals; new knowledge can be added via TELL

Knowledge Base (KB)

A Knowledge Base is a set of sentences expressed in a knowledge representation language. Each sentence represents an assertion about the world.

Fundamental Operations

TELL
Add a new sentence to the knowledge base. This is how the agent learns new facts.
ASK
Query the knowledge base about the truth of a sentence. This may trigger inference.
Inference
Deriving new sentences from existing ones. The core reasoning mechanism.

Types of Knowledge in KB

TypeDescriptionExample
Background Knowledge Built-in facts about the environment, provided by the designer "Wumpus eats anyone who enters its room"
Percept Knowledge Facts derived from sensors (TELL what was perceived) "Stench detected at [1,2]"
Action Knowledge Recording that an action was performed "Agent moved Forward to [2,1]"
Derived Knowledge New facts inferred from existing sentences "Wumpus must be at [1,3]"
Key Insight: In logical agents, the answer returned by ASK must follow logically from what was previously TELL'd to the KB. The agent doesn't guess — it reasons.

KB-Agent Algorithm

The KB-Agent follows a simple but powerful loop. Each cycle, it receives a percept, updates its knowledge, consults its KB for the best action, and executes it.

KB-Agent Pseudocode
function KB-Agent(percept) returns action persistent: KB, a knowledge base t, a counter (0 initially) TELL(KB, Make-Percept-Sentence(percept, t)) action = ASK(KB, Make-Action-Query(t)) TELL(KB, Make-Action-Sentence(action, t)) t = t + 1 return action
The canonical knowledge-based agent algorithm (Russell & Norvig)

Step-by-Step Execution

StepOperationPurpose
1 Receive percept from environment Sense the current state
2 TELL KB what was perceived Update the agent's knowledge about the world
3 ASK KB what action to perform Query the KB — this may trigger extensive inference about current state, future states, etc.
4 TELL KB that action was performed Record the action so the KB knows it was actually executed
5 Execute the action Affect the environment
Example: Wumpus World Agent Trace

Percept: [None, None, None, None, None] at [1,1]

TELL: KB = KB ∪ {¬Stench₁,₁, ¬Breeze₁,₁, ¬Glitter₁,₁, ¬Bump₁,₁, ¬Scream₁,₁}

ASK: What action is safe? → Inference: adjacent rooms [1,2] and [2,1] have no pit and no wumpus → Safe to move

Action: Forward (to [2,1])

TELL: KB = KB ∪ {At[2,1]}

Note: The KB-Agent closely resembles the agent with internal state from Chapter 2, but TELL/ASK operations provide a cleaner, more principled framework for computing actions.

Knowledge Level vs Implementation Level

To verify the agent's behavior, we use a knowledge-level description: what does the agent know, and what are its goals? This is independent of the implementation level (how knowledge is actually stored).

Example: Autonomous Taxi Agent

Knowledge Level: The taxi knows it is in San Francisco, its passenger wants to go to Marin County, and the Golden Gate Bridge is the only connection between the two. Therefore, it should cross the Golden Gate Bridge.

Implementation Level: The geographical knowledge could be stored as an image, a linked list, a graph, or a set of logical sentences — the behavior is the same.

Declarative vs Procedural Approaches

There are two fundamental approaches to building intelligent systems:

DimensionDeclarative ApproachProcedural Approach
Definition Express knowledge as explicit sentences; system reasons using inference Encode desired behavior directly as executable code
Knowledge Representation Explicit, readable, modifiable sentences in a representation language Implicit in program logic and control flow
Flexibility High — easy to add new knowledge via TELL Low — changing behavior requires recoding
Efficiency Lower — inference can be slow Higher — direct execution, no reasoning overhead
Explainability High — can show the chain of reasoning Low — hard to explain why a decision was made
Learning Easy to integrate — new knowledge is just added Hard — learning requires code modification
Example Expert systems (MYCIN, DENDRAL) Traditional control systems, hardcoded robots
Best Practice: Hybrid Approach
Successful Agent = Declarative Knowledge + Procedural Efficiency
A successful agent uses both: declarative for what it knows, procedural for how it acts efficiently

Comparison Examples

Chess Playing

Declarative: Represent rules of chess as logical sentences (e.g., "a bishop moves diagonally", "a piece cannot occupy a square already occupied by a friendly piece"). The agent reasons about legal moves.

Procedural: Code legal-move generation functions directly in the programming language. Faster but harder to modify (e.g., adding "en passant" requires code changes).

Real systems: Use both — procedural for move generation, declarative for strategy knowledge.

Medical Diagnosis

Declarative: "If patient has fever AND rash AND joint pain THEN consider measles." New diseases are added as new sentences.

Procedural: A decision tree encoded as nested if-else statements. Adding a new disease requires restructuring the code.

Real systems: Modern AI uses declarative knowledge (medical ontologies) with procedural algorithms (inference engines).

Worked Examples

Example 1: Autonomous Taxi Agent

Scenario: A self-driving taxi must navigate from San Francisco Airport (SFO) to downtown San Francisco.

Background Knowledge (initial KB):

  • US-101 connects SFO to downtown SF
  • I-280 is an alternative route
  • Traffic on US-101 is heavy during rush hour (4-7 PM)
  • If traffic is heavy, the trip takes > 60 min

Percept: Current time = 5:30 PM, GPS position = SFO

TELL: Current time is 5:30 PM (rush hour)

Inference: Traffic on US-101 is heavy → US-101 will take > 60 min. I-280 is alternative.

ASK: What route minimizes travel time? → I-280

Action: Take I-280

Output: The agent chose I-280 because it inferred heavy traffic from the time of day.

Example 2: Smart Home Thermostat

Scenario: A thermostat agent controls heating based on knowledge about occupancy and temperature.

Background Knowledge:

  • If nobody is home AND temperature < 10°C, turn on heating to prevent pipes from freezing
  • If someone is home AND temperature < 18°C, turn on heating for comfort
  • If temperature > 28°C, turn on cooling

Percept: Temperature = 8°C, no motion detected

TELL: Temperature = 8°C, Occupancy = false

Inference: 8°C < 10°C and nobody is home → freeze protection needed

Action: Turn on heating (set to 12°C)

Output: Heating activated for freeze protection despite no occupants.

Example 3: Supply Chain Planner

Scenario: A warehouse robot must decide when to reorder inventory.

Background Knowledge:

  • Lead time for supplier A is 5 days
  • Lead time for supplier B is 2 days (but 20% more expensive)
  • Daily demand averages 100 units
  • Safety stock = 200 units
  • Reorder point = LeadTime × DailyDemand + SafetyStock

Percept: Current inventory = 350 units of item X

TELL: Inventory(X) = 350

Inference: Reorder point for supplier A = 5 × 100 + 200 = 700. 350 < 700 → reorder needed.

ASK: Which supplier? → If urgency (inventory < 300), use B; otherwise use A.

Action: Reorder from supplier A (cheaper, since inventory > 300)

Output: Placed order with supplier A for 500 units (5-day lead time).

Example 4: Email Spam Filter

Scenario: An email agent classifies messages as spam or legitimate.

Background Knowledge:

  • If email contains "free money" AND sender is unknown → spam (confidence 90%)
  • If email contains "meeting" AND sender is in contacts → legitimate
  • If email has multiple exclamation marks AND all caps subject → likely spam

Percept: Email from unknown sender, subject: "YOU WON!!! FREE IPHONE!!! Click now!"

TELL: Sender = unknown, Subject has "FREE", has "!!!", has all caps

Inference: Multiple spam indicators triggered → high probability of spam

Action: Move to spam folder

Output: Email classified as spam with confidence 95%.

Example 5: Robot Vacuum Cleaner

Scenario: A Roomba-like agent cleans rooms while avoiding obstacles and stairs.

Background Knowledge:

  • Stairs are dangerous — cliff sensors detect drop-offs
  • When battery < 15%, return to dock
  • A room is "clean" when the agent has traversed 90% of its area

Percept: Cliff sensor = activated (at edge of stairs), battery = 80%

TELL: CliffSensor = true at current position

Inference: Current position is adjacent to a drop-off. Back up and avoid this direction.

Action: Reverse, turn 45°, continue cleaning

Output: Avoided stairs, continued normal cleaning operation.

Complexity & Trade-offs

Inference Complexity

MethodTime ComplexitySpace ComplexityCompleteness
Model Checking (TT-Entails) O(2n) O(n) Complete (finite models)
Resolution (PL-RESOLUTION) O(2n) worst-case (NP-complete) O(2n) Refutation complete
Forward Chaining (Horn clauses) O(|KB|) linear O(|KB|) Complete for Horn KB
DPLL (SAT solving) O(2n) worst-case, often much faster O(n) Complete
Key Complexity Insight
Propositional entailment is CO-NP-Complete
All known algorithms for general propositional inference have worst-case exponential complexity. This is expected — no polynomial-time algorithm exists unless P = NP.

Trade-off Summary

Expressive Power
More expressive logic (e.g., first-order) allows more natural representation but inference becomes undecidable or very expensive
Inference Efficiency
Restricted languages (e.g., Horn clauses) allow linear-time inference but cannot express all knowledge
Knowledge vs Code
Declarative is flexible but slow; Procedural is fast but inflexible. Real systems balance both.
Practical Implication

For an agent with 100 propositional symbols, there are 2100 ≈ 1.27 × 1030 possible models — far too many to enumerate. Modern SAT solvers (DPLL, CDCL) use heuristics to handle millions of clauses efficiently, but worst-case remains exponential.

In practice, domain-specific knowledge and restricted representation languages (like Horn clauses) make many real-world inference problems tractable.
