Optimal Binary Search Tree (OBST)

Dynamic Programming — Algorithm Design (Hadi Yousefi)

Problem Definition

Given n keys k₁, k₂, ..., kₙ with search probabilities p₁, p₂, ..., pₙ (where Σ pᵢ = 1), construct a binary search tree that minimizes the expected search cost.

Why Does This Problem Matter?

In real-world applications like database indexing, dictionary lookups, and compiler symbol tables, we search for keys thousands of times per second. If we know that some keys are searched for much more frequently than others, we can organize the tree to place frequent keys near the root — reducing the average number of comparisons needed.

For example, in an English dictionary, words like "the" and "is" are searched far more often than "zyzzyva" or "quixotic". An optimal BST puts high-frequency words at shallower depths.

Expected Search Cost:
Cost(T) = Σ_{i=1}^{n} pᵢ · (depth(kᵢ) + 1)
Weighted sum of all key depths, where depth is the number of comparisons required to find the key.

Breaking down the formula:
• pᵢ = probability that key kᵢ is searched for (higher pᵢ means more frequent searches)
• depth(kᵢ) = number of edges from root to key kᵢ (root has depth 0)
• depth(kᵢ) + 1 = number of comparisons needed to find kᵢ (we compare at each level, including the root)
• pᵢ · (depth(kᵢ) + 1) = expected number of comparisons contributed by key kᵢ
• Sum over all keys = total expected search cost
⚠ High-probability keys should be near the root to minimize expected search cost!

Intuition: Why Does Placement Matter?

Consider two极端 cases:

Best Case

If the most probable key (p=0.9) is at the root, it costs only 0.9 × 1 = 0.9 expected comparisons.

The other 10% of searches go deeper, but the 90% are fast.

Worst Case

If the most probable key (p=0.9) is at depth 3, it costs 0.9 × 4 = 3.6 expected comparisons — 4× worse!

The 90% of searches now take 4 comparisons each.

BST Properties

In a BST, for any node: all keys in its left subtree are smaller, and all keys in its right subtree are larger. This ordering property is what makes BSTs efficient for search — we can eliminate half the remaining keys with each comparison.

The BST Ordering Constraint

When we choose a root, we split the remaining keys into two groups: those smaller go to the left subtree, those larger go to the right. This constraint means we cannot arbitrarily place keys — the structure is determined by which key we pick as root at each step.

This is why OBST is harder than just sorting keys by probability: we must respect the BST ordering while trying to minimize cost.

Understanding Dummy Keys (External Nodes)

In addition to real keys k₁...kₙ, we have n+1 dummy keys d₀, d₁, ..., dₙ representing the "gaps" between keys:

• d₀ = search for a value less than k₁ (left of the smallest key)

• d₁ = search for a value between k₁ and k₂

• dₙ = search for a value greater than kₙ (right of the largest key)

Each dummy key dᵢ has probability qᵢ — the probability that a search ends at that gap (unsuccessful search). These dummy keys become the leaves of the BST.

Total Probability Constraint:
Σᵢ pᵢ + Σⱼ qⱼ = 1
All searches must end somewhere — either at a real key (successful search) or at a dummy key (unsuccessful search).

Input

• n sorted keys k₁...kₙ

• Key probabilities p₁...pₙ

• Dummy probabilities q₀...qₙ

Output

• Minimum expected search cost

• The optimal BST structure (which key is root at each subtree)

Constraints

• BST ordering must hold (left < root < right)

• All probabilities sum to 1

• Each subtree must also be optimal

Dynamic Programming Solution

Why Dynamic Programming?

The OBST problem has optimal substructure: the optimal tree for keys k₁...kₙ must contain optimal subtrees for its left and right children. If we knew which key was the root, we could solve the left and right subproblems independently.

However, we don't know which key should be the root! So we try every possible root, and for each, we need the optimal cost of the left and right subtrees. This is where DP helps — we solve all smaller subproblems first and reuse their results.

Key insight: A subproblem is defined by a contiguous range of keys kᵢ...kⱼ. There are O(n²) such subproblems, and each takes O(n) time to solve (trying all possible roots). Total: O(n³).

Recurrence Relation

Define A[i][j] = minimum expected search cost for the subproblem with keys kᵢ...kⱼ (where i ≤ j).

Define R[i][j] = index of the root chosen for the optimal BST for keys kᵢ...kⱼ (used for reconstruction).

Base Case (single key):
A[i][i] = pᵢ   and   R[i][i] = i
A tree with one key has cost equal to its probability.

Why? If we have only key kᵢ, it becomes the root. The search cost for kᵢ is 1 comparison (just compare with root). The expected cost = pᵢ × 1 = pᵢ.

Note: The dummy keys (leaves) are not counted in this cost because they represent unsuccessful searches that end at external nodes.
Base Case (empty subtree):
A[i][i-1] = 0   and   A[n+1][n] = 0
An empty subtree (when i > j) has zero cost because there are no keys to search for.

Important: When we later include dummy keys q₀...qₙ in the weight calculation, we account for the cost of unsuccessful searches that end at these empty subtrees.
Recurrence (i < j):
A[i][j] = min_{i ≤ m ≤ j} ( A[i][m-1] + A[m+1][j] ) + Σ_{t=i}^{j} p_t
For each possible root m in keys i..j:
• A[i][m-1] = cost of left subtree (keys i..m-1)
• A[m+1][j] = cost of right subtree (keys m+1..j)
• Σ p_t = sum of probabilities for all keys in the range (the "weight penalty")

Why add Σ p_t? When we make key m the root, every other key in the subtree moves down by 1 level. This means each key's search cost increases by 1 comparison. The total extra cost = sum of all probabilities × 1 = Σ p_t.

If i > m-1 or m+1 > j: The empty subtree cost = 0 (no keys to search).
Final Answer:
A[1][n]
Minimum expected search cost for the complete set of n keys. This is the value we want to compute.

Understanding the Weight Term w[i][j]

Why w[i][j] = Σ p_t + Σ q_t?

The weight w[i][j] includes BOTH real key probabilities AND dummy key probabilities. This is because:

1. Real keys (pᵢ): When we add a root above, each real key's depth increases by 1, adding pᵢ to the expected cost.

2. Dummy keys (qⱼ): The dummy keys (leaves) also get pushed down by 1 level. A search that ends at dummy key dⱼ now takes 1 extra comparison, adding qⱼ to the expected cost.

Example: For subtree k₂...k₃ with p₂=0.3, p₃=0.2, q₁=0.1, q₂=0.05, q₃=0.05:

w[2][3] = p₂ + p₃ + q₁ + q₂ + q₃ = 0.3 + 0.2 + 0.1 + 0.05 + 0.05 = 0.7

Algorithm: Optimal BST DP

OPTIMAL-BST(p, n) let A[1..n+1][0..n], R[1..n][1..n] for i ← 1 to n A[i][i] ← p[i] // single key subtree R[i][i] ← i // root is the only key A[i][i-1] ← 0 // empty left subtree A[n+1][n] ← 0 // empty right subtree for last key for d ← 1 to n-1 // diagonal (subtree size - 1) for i ← 1 to n-d // starting index j ← i + d // ending index A[i][j] ← ∞ // initialize to infinity sumP ← Σ_{t=i}^{j} p[t] // weight of this subtree for m ← i to j // try each possible root cost ← A[i][m-1] + A[m+1][j] + sumP if cost < A[i][j] A[i][j] ← cost // found better root R[i][j] ← m // remember which root return A[1][n], R
How the Algorithm Works (Step by Step):

1. Initialize base cases: Fill A[i][i] = pᵢ for single keys, and A[i][i-1] = 0 for empty subtrees.

2. Process diagonals: Start with d=1 (pairs of adjacent keys), then d=2 (triples), ..., up to d=n-1 (all n keys).

3. For each subproblem (i,j): Try every possible root m from i to j. For each m, compute cost = left subtree cost + right subtree cost + weight penalty.

4. Keep the minimum: Store the best (minimum) cost and which root achieved it in R[i][j].

5. Build the tree: Use the R matrix to reconstruct the optimal tree by recursive subdivision.

Tree Reconstruction from R Matrix

BUILD-TREE(R, i, j) if i > j return null // empty subtree r ← R[i][j] // root of optimal BST for keys i..j node = new Node(key[r]) node.left = BUILD-TREE(R, i, r-1) // left subtree node.right = BUILD-TREE(R, r+1, j) // right subtree return node
Reconstruction Example:

For keys k₁, k₂, k₃ with R[1][3] = 2 (root is k₂):

• Root = k₂

• Left subtree: BUILD-TREE(R, 1, 1) → k₁

• Right subtree: BUILD-TREE(R, 3, 3) → k₃

Result: Tree with k₂ at root, k₁ as left child, k₃ as right child.

Worked Examples

How to Read These Examples:

Each example shows the complete DP computation step-by-step. We fill the A[i][j] table diagonal by diagonal:

• Diagonal d=0: Single keys (A[1][1], A[2][2], ..., A[n][n])

• Diagonal d=1: Pairs of adjacent keys (A[1][2], A[2][3], ...)

• Diagonal d=2: Triples (A[1][3], A[2][4], ...)

• Continue until we fill A[1][n] (the full range)

For each cell, we try every possible root and keep the minimum cost.

Complexity Analysis

Why O(n³) Time?

The algorithm has three nested loops:

1. Outer loop (diagonals): n-1 iterations (d = 1 to n-1)

2. Middle loop (starting index): Up to n iterations per diagonal

3. Inner loop (root choice): Up to n iterations per subproblem

Total: O(n) × O(n) × O(n) = O(n³)

Space: We store three n×n tables (A, w, R), so O(n²) space.

Time Complexity

O(n³)

For each of O(n²) subproblems, we try O(n) possible roots. Total O(n³) operations.

For n=100 keys, this is about 1 million operations — very fast.

Space Complexity

O(n²)

Two n×n tables: A for costs, R for roots.

For n=100, we need about 10,000 entries — trivial memory usage.

Knuth Optimization

For OBST, the root choice is monotonic: R[i][j-1] ≤ R[i][j] ≤ R[i+1][j]. This reduces to O(n²) by limiting root search range.

This optimization is possible because of the quadrangle inequality in the cost function.

Comparison with Brute Force:

Brute force: Try all possible BST structures. The number of distinct BSTs with n keys is the Catalan number C(n) = (2n)!/((n+1)!n!), which grows exponentially.

DP approach: O(n³) polynomial time — much more efficient!

For n=10: Brute force tries ~16,796 trees. DP does ~1,000 operations.

For n=20: Brute force tries ~6,564,120,420 trees. DP does ~8,000 operations.
