Coin Change Problem (Minimum Number of Coins)

What is the Coin Change Problem?

The coin change problem asks: Given a set of coin denominations and a target amount, what is the minimum number of coins needed to make that amount?

Think of it like this: You have coins of different values (like 1 cent, 5 cents, 10 cents, 25 cents) and you need to make change for a specific amount using the fewest coins possible. You have unlimited supply of each denomination.

This is a classic optimization problem that demonstrates why greedy algorithms don't always work and why dynamic programming is essential.

Problem Formulation:
Given: denominations D = {d1, d2, ..., dn}, target M
Find: min number of coins whose sum = M
Each coin can be used any number of times (unlimited supply)
Why "Unlimited Supply" Matters: This means if you have a coin of value 3, you can use it as many times as you want. This is different from problems where you have a limited number of each coin. The unlimited supply is what makes this an "unbounded" knapsack problem.

Input

  • Coin denominations: d1, d2, ..., dn
  • Target amount: M
  • Unlimited supply of each coin

Output

  • Minimum number of coins needed
  • Which coins to use (via backtracking)
  • If impossible, return infinity or -1

Real-World Applications

  • Cash register systems: Making change with minimum coins
  • Vending machines: Dispensing correct change efficiently
  • Currency exchange: Converting between denominations
  • Resource allocation: Distributing resources in optimal chunks
  • Packet switching: Breaking data into optimal-sized packets
Unbounded Knapsack Analogy:
This is the "unbounded knapsack" variant where each item (coin) can be taken unlimited times
Differs from 0/1 knapsack where each item can be taken at most once

0/1 Knapsack (Limited)

  • Each item can be used at most once
  • Recurrence uses c[i-1][j-w]
  • Example: Each coin type has limited quantity

Unbounded Knapsack (Coin Change)

  • Each item can be used unlimited times
  • Recurrence uses c[i][j-d] (same row!)
  • Example: Unlimited supply of each coin
CRITICAL WARNING: Greedy does NOT always give optimal solution for coin change!

Why greedy fails: Greedy always picks the largest coin first, but sometimes using a smaller coin now allows you to use larger coins later, resulting in fewer total coins.

Counter-example: For denominations {1, 3, 4} and amount 6:
• Greedy: 4 + 1 + 1 = 3 coins (picks 4 first, then fills with 1s)
• Optimal: 3 + 3 = 2 coins (uses two 3s)

The greedy approach "locks itself in" by picking the 4, forcing two small 1s. The DP approach considers all options and finds that two 3s is better.

Greedy vs DP Comparison — Detailed

Strategy Pick largest coin first, repeat Try all possibilities, build optimal solution bottom-up

What is a "Canonical" Coin System? A coin system is called "canonical" if the greedy algorithm always gives the optimal solution. The US coin system {1, 5, 10, 25} is canonical. However, most arbitrary coin systems are NOT canonical, which is why we need DP.

Dynamic Programming Solution — Detailed Explanation

Why Does DP Work Here?

Dynamic programming works because this problem has two key properties:

  • Optimal Substructure: The optimal solution to the main problem contains optimal solutions to subproblems. If the best way to make amount M uses a coin of value d, then the remaining M-d must also be made optimally.
  • Overlapping Subproblems: When solving recursively, we encounter the same subproblems many times. DP stores these solutions to avoid recomputation.

Understanding the Recurrence — Step by Step

Let c[i][j] = minimum number of coins needed to make amount j using the first i coin denominations.

For each cell c[i][j], we have exactly two choices:

  • Choice 1: Don't use coin i → Then c[i][j] = c[i-1][j] (use only coins 1 to i-1)
  • Choice 2: Use coin i → Then c[i][j] = c[i][j-di] + 1 (use coin i, and solve the remaining subproblem)

We take the minimum of these two choices because we want the fewest coins.

KEY INSIGHT: Notice that when we "use coin i", we write c[i][j-di] + 1, NOT c[i-1][j-di] + 1. This is because we have unlimited supply of coin i, so after using one coin i, we can still use more coins i in the future. This is what makes it "unbounded" — we stay on the same row i.
Recurrence Relation — Full Explanation:
c[i][j] = min(c[i-1][j], c[i][j-di] + 1)   if j ≥ di
c[i][j] = c[i-1][j]                          if j < di
Breaking it down:
• c[i-1][j] = best solution without using coin i at all
• c[i][j-di] + 1 = use one coin i, then optimally solve for remaining amount j-di
• If j < di, we can't use coin i, so only option is c[i-1][j]

Step-by-Step: Why c[i][j-di] and not c[i-1][j-di]?

Step 1: In 0/1 knapsack (limited items), after using item i, we can't use it again, so we look at row i-1.
Step 2: In unbounded knapsack (unlimited items), after using coin i, we CAN use it again, so we stay on row i.
Step 3: This is why we write c[i][j-di] instead of c[i-1][j-di]. The "i" (not "i-1") means "we can still use coin i in the future."

Base Cases — Detailed Explanation

Base Cases:
c[0][j] = ∞   for all j > 0
c[i][0] = 0   for all i
c[1][j] = j / d1   (if d1 = 1, or divisibility holds)
Why these base cases?
• c[0][j] = ∞: With 0 coins available, we can only make amount 0. Any positive amount is impossible (infinite coins needed).
• c[i][0] = 0: To make amount 0, we need 0 coins regardless of what coins are available.
• c[1][j]: With only the first coin denomination d1, we can only make amounts that are multiples of d1. If d1=1, we can make any amount j using j coins.

The Algorithm — Annotated

COIN-CHANGE(d, n, M): let c[0..n][0..M] be 2D array // BASE CASE: No coins available → can't make any positive amount for j = 1 to M: c[0][j] = ∞ // BASE CASE: Amount 0 needs 0 coins for i = 0 to n: c[i][0] = 0 // FILL TABLE: Consider coins one by one for i = 1 to n: // For each coin denomination for j = 1 to M: // For each amount from 1 to M if j < d[i]: // Can't use coin i (too big) c[i][j] = c[i-1][j] // Copy from row above else: // Take minimum of: not using coin i vs using coin i c[i][j] = min(c[i-1][j], // Don't use coin i c[i][j-d[i]] + 1) // Use coin i (+1 for this coin) return c[n][M] // Answer: min coins using all n denominations

Space-Optimized Version (1D Array) — Detailed

Why Can We Optimize to 1D?

Look at the recurrence: c[i][j] depends on:

  • c[i-1][j] — the cell directly above (previous row, same column)
  • c[i][j-di] — the cell in the same row, to the left

Since we only need the current row and the previous row, we can use a single 1D array and update it in place. When we compute dp[j], we only need dp[j] (from previous iteration) and dp[j-di] (already computed in current iteration).

COIN-CHANGE-1D(d, n, M): let dp[0..M] = ∞ // Initialize all to infinity dp[0] = 0 // Base case: 0 coins for amount 0 for i = 1 to n: // For each coin denomination for j = d[i] to M: // Start from d[i] (can't make amount < d[i]) // Same recurrence, but in 1D: // dp[j] = min(dp[j], dp[j-d[i]] + 1) dp[j] = min(dp[j], dp[j-d[i]] + 1) return dp[M]
IMPORTANT: In the 1D version, the inner loop goes from d[i] to M (left to right). This is correct for unbounded knapsack because we want to allow using the same coin multiple times. If we went right to left, it would be 0/1 knapsack (each coin used at most once).
Complexity Analysis:
Time: O(n × M) — fill n×M table cells
Space: O(M) with 1D optimization (was O(n×M) with 2D)
• n = number of coin denominations
• M = target amount
• Each cell takes O(1) time (just a comparison and assignment)

Coin Tracking (Backtracking) — Detailed

How to Find Which Coins Were Used?

After filling the DP table, we know the minimum number of coins, but not which coins. To find the actual coins, we need to backtrack through the table.

TRACK-COINS(c, d, n, M): i = n, j = M // Start from bottom-right corner coins = [] // List to store coins used while j > 0: if i == 0: break // Should not happen if solution exists if c[i][j] == c[i-1][j]: // We didn't use coin i, move up i = i - 1 else: // We used coin i, record it and move left coins.append(d[i]) j = j - d[i] // DON'T decrease i! We can use same coin again (unlimited) return coins

Backtracking Logic Explained:

Step 1: Start at c[n][M] (bottom-right of table)
Step 2: If c[i][j] == c[i-1][j], we didn't use coin i → move UP (i-1)
Step 3: If c[i][j] != c[i-1][j], we used coin i → record d[i], move LEFT (j - d[i])
Step 4: Repeat until j == 0

Worked Examples — Complete Step-by-Step

Example 1: Coins {1, 4, 6}, Amount = 8 — Greedy Fails

Understanding Why Greedy Fails Here

Greedy picks the largest coin first (6), leaving remainder 2. Then it fills with 1s (two of them). Total: 3 coins.

But if we use two 4s, we get 8 with only 2 coins. Greedy never considers this because it always commits to the largest coin immediately.

Greedy approach — Step by step:

Step 1: Largest coin ≤ 8 is 6. Use it. Remaining: 8 - 6 = 2
Step 2: Largest coin ≤ 2 is 1. Use it. Remaining: 2 - 1 = 1
Step 3: Largest coin ≤ 1 is 1. Use it. Remaining: 1 - 1 = 0
Result: 6 + 1 + 1 = 8 → 3 coins

DP approach — Building the table c[i][j]:

How to read this table: Row i means "using coins from d1 to di". Column j means "for amount j".

i\j012345678
0 (no coins)0∞∞∞∞∞∞∞∞
1 (d=1)012345678
2 (d=4)012312342
3 (d=6)012312122

How Each Row Is Computed:

Row 1 (d=1): With only coin 1, amount j needs j coins of 1. So c[1][j] = j.
Row 2 (d=4): Now we can also use coin 4. For each amount j:
• If j < 4: can't use coin 4, copy from row above
• If j ≥ 4: min(not using 4, using 4). For j=4: min(c[1][4]=4, c[2][0]+1=1) = 1
Row 3 (d=6): Now we can also use coin 6. For j=8:
• c[3][8] = min(c[2][8]=2, c[3][2]+1=2+1=3) = min(2, 3) = 2
• We don't use coin 6! Two 4s is better than one 6.

DP result: 2 coins (4 + 4) — better than greedy's 3 coins!

Key Insight from This Example

The DP table shows that at c[3][8], the optimal solution doesn't use the largest coin (6). Instead, it uses two coins of 4. The DP explores ALL possibilities and picks the best, while greedy commits to the first choice and misses better alternatives.

Example 2: Coins {1, 3, 4}, Amount = 6 — Full DP Table

Building the table step by step:

i\j0123456
1 (d=1)0123456
2 (d=3)0121232
3 (d=4)0121122

Detailed Computation for c[3][6]:

Step 1: c[3][6] = min(c[2][6], c[3][6-4] + 1) = min(c[2][6], c[3][2] + 1)
Step 2: c[2][6] = 2 (from row 2). c[3][2] = c[2][2] = 2 (since d3=4 > 2, can't use coin 4)
Step 3: c[3][6] = min(2, 2+1) = min(2, 3) = 2
Result: We don't use coin 4! The optimal is 2 coins from row 2.

Backtracking to Find the Coins:

Step 1: Start at c[3][6] = 2. Compare with c[2][6] = 2. They're equal → didn't use coin 4 → move to row 2.
Step 2: At c[2][6] = 2. Compare with c[1][6] = 6. Different! → used coin 3. Record "3". Move to c[2][3].
Step 3: At c[2][3] = 1. Compare with c[1][3] = 3. Different! → used coin 3. Record "3". Move to c[2][0].
Step 4: j = 0, done. Coins: [3, 3]

Result: 2 coins (3 + 3). Greedy would give 3 coins (4 + 1 + 1).

Why Backtracking Works

The backtracking works because each cell c[i][j] was computed as the minimum of two options. If c[i][j] equals c[i-1][j], we know we didn't use coin i. If not, we used coin i and can trace back to c[i][j-di].

When No Solution Exists

If the target amount cannot be made with the given denominations, the DP table will have ∞ at c[n][M]. This happens when:

  • No combination of the given coins sums to M
  • Example: Coins {2, 5} can only make even amounts or amounts ≥ 5 that are 5 + even

Exam Tips — Key Points to Remember:
• The recurrence c[i][j] = min(c[i-1][j], c[i][j-di] + 1) uses c[i][...] (same row) because of unlimited supply
• Unlike 0/1 knapsack where we use c[i-1][j-wi], unbounded knapsack uses c[i][j-di]
• Initialize with c[0][j] = ∞ for j > 0 and c[i][0] = 0 for all i
• When d1 = 1, all amounts are achievable, but the DP still finds the minimum
• Greedy fails for non-canonical coin systems — always use DP
• The 1D optimization reduces space from O(nM) to O(M)
• To find which coins were used, backtrack from c[n][M] using the comparison method

Deep Dive — Advanced Concepts

Optimal Substructure Property

A problem has optimal substructure if an optimal solution can be constructed from optimal solutions of its subproblems.

In coin change: If the optimal way to make amount M uses a coin of value d, then the remaining amount M-d must also be made optimally. If it weren't, we could improve the solution for M-d, which would improve the solution for M — contradicting optimality.

Overlapping Subproblems Property

When solving recursively, we encounter the same subproblems many times. For example, to make amount 10 with coins {1, 3, 4}, we might need to solve for amount 6 multiple times from different paths.

DP stores these solutions in a table so each subproblem is solved only once. This is what makes DP efficient compared to brute-force recursion.

Recursive Solution (Inefficient)

minCoins(amount): if amount == 0: return 0 result = ∞ for each coin d: if d <= amount: result = min(result, 1 + minCoins(amount - d)) return result

Time: O(nM) — exponential! Many repeated calculations.

DP Solution (Efficient)

minCoins(amount): dp[0] = 0 for j = 1 to amount: dp[j] = ∞ for each coin d: if d <= j: dp[j] = min(dp[j], dp[j-d] + 1) return dp[amount]

Time: O(n × M) — polynomial! Each subproblem solved once.

Why the 1D Array Works (Left-to-Right Update)

In the 1D version, when we process coin i, we update dp[j] from left to right (j = d[i] to M). This works because:

  • dp[j] depends on dp[j-d[i]], which was just updated in this iteration
  • This allows using the same coin multiple times (unbounded)
  • If we went right to left, dp[j-d[i]] would be from the previous coin's iteration, giving 0/1 knapsack behavior
Direction of 1D Update Matters:
Left to right (j = d[i] to M): Unbounded (unlimited coins) ← COIN CHANGE
Right to left (j = M to d[i]): 0/1 (each coin used at most once)
This is a crucial distinction that determines whether you get unbounded or 0/1 knapsack behavior.

Time and Space Complexity — Deep Analysis

  • Time O(nM): We have n coins and M amounts. Each cell in the DP table takes O(1) time to compute (just a min operation). Total: n × M cells.
  • Space O(M) (1D): We only need a 1D array of size M+1. The 2D version uses O(nM) space but can be optimized to O(M) because each row only depends on the previous row.
  • Space O(nM) (2D): If we need to backtrack to find which coins were used, we need the full 2D table or a separate tracking array.

Handling Edge Cases

  • Amount = 0: Return 0 coins (base case)
  • Amount < min coin: Return ∞ or -1 (impossible)
  • No coin of value 1: Some amounts may be impossible (shown as ∞ in table)
  • All coins > M: Return ∞ (can't make any positive amount ≤ M)
  • Duplicate denominations: Remove duplicates before processing (they don't help)

Variations of Coin Change Problem

  • Count number of ways: Instead of minimum coins, count how many ways to make amount M (different recurrence: sum instead of min)
  • Limited supply: Each coin has a limited count (becomes 0/1 knapsack or bounded knapsack)
  • Coin change II: Find all combinations that make amount M
  • Minimum cost: Each coin has a cost, minimize total cost instead of coin count
Connection to Other DP Problems: Coin change is a foundation for many DP problems. Understanding it helps with: unbounded knapsack, rod cutting, house robber, and many optimization problems that involve making choices with unlimited or limited resources.
Common Mistakes to Avoid:
• Using greedy instead of DP for non-canonical coin systems
• Confusing c[i][j-di] (unbounded) with c[i-1][j-di] (0/1)
• Forgetting to initialize c[0][j] = ∞ for j > 0
• Wrong loop direction in 1D version (must be left to right for unbounded)
• Not handling the case where dp[M] remains ∞ (impossible case)
• Off-by-one errors in array indexing
