Scheduling with Deadlines

Greedy Algorithms — Complete Guide with Worked Examples

Problem Definition

Imagine you run a factory with a single machine. Customers bring you jobs, and each job promises a certain profit if completed by a certain deadline. You cannot work on two jobs simultaneously, and each job takes exactly one hour (one time unit). Your goal: choose which jobs to accept so that you maximize your total profit while ensuring every accepted job finishes on time.

This is the Scheduling with Deadlines problem — a classic optimization problem in computer science and operations research. It appears in real-world scenarios such as task scheduling in operating systems, production planning in factories, CPU job scheduling in compilers, and project management where tasks have firm deadlines.

⚠ Important Assumption: Each job takes exactly 1 unit of time. This is a key constraint — without it, the greedy approach discussed here would not apply directly. If jobs had different processing times, the problem becomes significantly harder (NP-hard in general). The unit-time assumption is what makes the greedy strategy work perfectly.
Formal Definition
Given: J = { (d₁, p₁), (d₂, p₂), ..., (dₙ, pₙ) }
dᵢ = deadline (job must finish at or before time dᵢ)
pᵢ = profit (earned only if job completed by its deadline)
Each job requires 1 time unit. Find subset S ⊆ J maximizing Σpᵢ where S is feasible.

In mathematical terms, we have a set of n jobs. Job i has a deadline dᵢ (a positive integer representing the latest time unit by which it must finish) and a profit pᵢ (a positive number earned if and only if the job is scheduled and completes by its deadline). We must choose a subset of jobs and assign each chosen job to a distinct time slot (1, 2, 3, ...) such that no job is assigned to a slot later than its deadline. The objective is to maximize the total profit of all scheduled jobs.

Feasibility Condition

A set of jobs is feasible if there exists a schedule (ordering) such that every job finishes by its deadline. The key insight is this: since every job takes exactly 1 time unit, if we have k jobs to schedule, we need k distinct time slots. The question is whether we can assign these k jobs to slots 1 through k such that each job i is placed in a slot ≤ dᵢ.

The simplest way to check feasibility is to sort the jobs by their deadlines in ascending order and assign them greedily to slots 1, 2, 3, .... If at any position i, the i-th job (in deadline-sorted order) has a deadline less than i, then the set is infeasible — there simply aren't enough early slots to accommodate all the jobs with tight deadlines.

Feasibility Test
deadline(i) ≥ i   for all i = 1, 2, ..., k
Where jobs are sorted by ascending deadline and i is the position in the schedule. If this condition holds for every position, the set is feasible. If it fails at any position, no valid schedule exists for this set.

Why does sorting by deadline work? Suppose you have a feasible schedule. If any two adjacent jobs are out of deadline order (the later one has an earlier deadline), swapping them cannot make things worse — the job with the earlier deadline gets an earlier slot, which is better for it. By repeatedly swapping such inversions, you eventually reach the deadline-sorted order, which is also feasible. Therefore, if ANY schedule works, the deadline-sorted schedule works too.

Key Properties

Single Processor

Only one job at a time. No parallel execution. This models a real-world scenario where you have one machine, one worker, or one CPU core. The constraint means jobs must be serialized — each occupies the full time slot.

Unit Processing Time

Every job takes exactly 1 time unit, regardless of job. This simplification is crucial: it means time is divided into discrete slots (1, 2, 3, ...), and each job fills exactly one slot. Without this, we'd need to handle variable-length intervals, making the problem much harder.

Deadline Constraint

Job must complete at or before its deadline (time ≤ dᵢ). If a job with deadline 3 is assigned to slot 4, it fails — the deadline is violated and no profit is earned. The deadline is a hard constraint, not a soft preference.

Profit Maximization

Goal: maximize sum of profits of scheduled jobs. Not all jobs need to be scheduled — sometimes skipping a low-profit job allows fitting a higher-profit one. The challenge is choosing the right subset.

Optimal Substructure

The scheduling problem has optimal substructure, meaning: if J* is an optimal feasible set of jobs, then for any job j in J*, the set J* − {j} is an optimal feasible set for the remaining jobs (all jobs except j). This property is what makes greedy algorithms applicable — it means we can build the optimal solution incrementally by making locally optimal choices (picking the highest-profit feasible job) without worrying about future consequences.

More precisely, suppose J* = {j₁, j₂, ..., jₖ} is the optimal set. If we remove any job jᵢ from J*, the remaining k−1 jobs still form a feasible schedule (since removing a job can only make feasibility easier), and they are optimal for the subproblem consisting of all jobs except jᵢ. If there were a better feasible subset of the remaining jobs, we could combine it with jᵢ to get a better solution for the original problem — contradicting the optimality of J*.

Why Greedy Works Here

Not all optimization problems can be solved greedily. The scheduling problem has two key properties that enable a greedy approach:

  1. Greedy Choice Property: There exists an optimal solution that includes the locally optimal choice (the highest-profit job that can be feasibly added). We can safely make this choice without exploring alternatives.
  2. Optimal Substructure: After making the greedy choice, the remaining subproblem (scheduling the remaining jobs) has the same structure as the original problem.

Together, these properties mean: sort jobs by profit (descending), try each one in order, keep it if feasible, and the result is optimal. No backtracking, no recursion — just a single pass.

Real-World Analogy

Think of it like a freelance worker with 1-hour appointment slots. Clients offer different payments (profits) and have latest-available times (deadlines). The worker wants to maximize income. The strategy: always try to book the highest-paying client first, and if they fit into the schedule without conflicting with already-booked clients, accept them.

Greedy Algorithm with Feasibility Checking

Algorithm Overview

The greedy algorithm builds a feasible job set incrementally using a simple but powerful strategy: always try the most profitable job first. The intuition is straightforward — if you're going to skip any job, you'd rather skip a low-profit one than a high-profit one. So process jobs from highest to lowest profit, and for each job, check whether adding it to your current schedule would still keep everything feasible.

Here's the step-by-step logic:

  1. Sort all jobs by profit in decreasing order. This ensures we always consider the most valuable jobs first, giving them priority for the limited time slots.
  2. Start with an empty schedule. No jobs selected yet.
  3. For each job (in profit order):
    • Temporarily add it to the selected set.
    • Check if the resulting set is still feasible (can all selected jobs be scheduled by their deadlines?).
    • If feasible → keep it (permanently add to the set).
    • If infeasible → discard it (it would violate some deadline, so skip it).
  4. The final selected set is optimal. No other combination of jobs yields a higher total profit while respecting all deadlines.
Important: To check feasibility of a set, we only need to examine jobs sorted by ascending deadline. There is no need to check all possible permutations — the deadline-sorted order is the canonical feasible order. If the deadline-sorted order fails, no other order succeeds. This is a proven theorem, not just a heuristic.

Pseudocode

function SCHEDULE_WITH_DEADLINES(J, d, p):
   Sort jobs by decreasing profit → list L
   S ← ∅ ▷ Selected feasible set (initially empty)
   for each job j in L: ▷ Process highest-profit first
      S' ← S ∪ {j} ▷ Tentatively add job j
      if IS_FEASIBLE(S') then ▷ Can all jobs in S' meet deadlines?
         S ← S' ▷ Yes: permanently add j
      end if
   end for
   return S ▷ The optimal feasible set
 
function IS_FEASIBLE(S):
   Sort jobs in S by ascending deadline
   for i = 1 to |S|:
      if deadline(S[i]) < i then ▷ Job i can't fit in slot i
         return false ▷ Set is infeasible
      end if
   end for
   return true ▷ All jobs fit — set is feasible

Why Only One Feasibility Check?

A natural question: when we add a new job to the set, why do we need to check the entire set again? Why not just check if the new job fits? The answer is subtle but important:

When we add a new job j to an already feasible set S, the set S ∪ {j} might become infeasible not because of j itself, but because j displaces another job. The feasibility condition requires that ALL jobs in the set can be simultaneously scheduled. Adding a job pushes other jobs to later time slots, potentially violating their deadlines.

For example, suppose S = {A(d=2), B(d=3)} is feasible (schedule: A at t=1, B at t=2). If we add C(d=2), the set becomes {A(d=2), B(d=3), C(d=2)}. Sorted by deadline: A(d=2), C(d=2), B(d=3). Position 3: B's deadline 3 ≥ 3 ✓. But if C had deadline 1 instead, we'd have A(d=2), C(d=1), B(d=3) — position 2: A's deadline 2 ≥ 2 ✓, but position 1: C's deadline 1 ≥ 1 ✓. Actually this is feasible. The point is: adding ANY job can potentially break feasibility for OTHER jobs, not just the new one.

So we must re-verify the entire set. Fortunately, the check is fast: just sort by deadline and scan once.

Why Deadline-Sorted Order is the Canonical Check

For a given set of jobs, if any schedule orders them by deadline and this order is feasible, then the set is feasible. This is because:

  • If there exists some feasible schedule, sorting by deadlines always yields a feasible schedule
  • The deadline-sorted order minimizes the completion time of each job, giving the highest chance of feasibility
  • No other permutation can satisfy deadlines if the deadline-sorted order fails

Intuitively: if you put jobs with tight deadlines first, you give them the best chance. If even that fails, nothing works.

Step-by-Step Feasibility Check

Given a candidate set S, the feasibility check works as follows:

  1. Sort jobs in S by ascending deadline (earliest deadline first).
  2. Assign job[1] to time slot 1, job[2] to time slot 2, ..., job[k] to time slot k.
  3. Verify: if for any job[i], deadline[i] < i, the set is infeasible. This means job[i] would need to be scheduled at time i, but its deadline is earlier than i — it can't be completed on time.
  4. If all positions pass (deadline[i] ≥ i for all i), the set is feasible.
Feasibility Example — How the Check Works

Suppose S has jobs with deadlines {3, 1, 2}.

Step 1: Sort by deadline → [d=1, d=2, d=3]

Step 2: Assign to slots: job with d=1 → slot 1, job with d=2 → slot 2, job with d=3 → slot 3

Step 3: Verify each position:

Position 1: deadline 1 ≥ 1 ✓ (job with deadline 1 finishes at time 1 — on time)

Position 2: deadline 2 ≥ 2 ✓ (job with deadline 2 finishes at time 2 — on time)

Position 3: deadline 3 ≥ 3 ✓ (job with deadline 3 finishes at time 3 — on time)

→ Feasible ✓ All three jobs can be scheduled.

Infeasibility Example — When the Check Fails

Suppose S has jobs with deadlines {1, 1, 3}.

Step 1: Sort by deadline → [d=1, d=1, d=3]

Step 2: Assign to slots: job with d=1 → slot 1, job with d=1 → slot 2, job with d=3 → slot 3

Step 3: Verify each position:

Position 1: deadline 1 ≥ 1 ✓ (first job finishes at time 1 — on time)

Position 2: deadline 1 < 2 ✗ (second job would need to finish at time 2, but its deadline is 1 — TOO LATE!)

→ Infeasible ✗ We have two jobs with deadline 1 but only one time slot ≤ 1. One must be rejected.

Greedy Choice Property — Why This Works

The greedy algorithm works because of the greedy choice property: there exists an optimal solution that includes the highest-profit feasible job. Proof sketch:

  1. Let O* be an optimal solution (maximum profit feasible set).
  2. If the greedy choice g (highest-profit feasible job) is in O*, we're done.
  3. If g is NOT in O*, then O* contains some other job j with profit p(j) < p(g).
  4. Replace j with g in O*. Since g's deadline is at least as late as j's (g was feasible when considered), the set remains feasible.
  5. The new set has higher profit (p(g) > p(j)), contradicting O*'s optimality.
  6. Therefore, g must be in some optimal solution.

After fixing the greedy choice, the remaining problem (scheduling remaining jobs) has the same structure, so we can apply the same argument recursively.

Why Not Sort by Deadline Instead?

You might wonder: why not sort by deadline (earliest first) and schedule greedily? The reason is that this maximizes the NUMBER of jobs scheduled, not the TOTAL PROFIT. Consider jobs: A(p=100, d=2), B(p=1, d=1). Sorting by deadline gives: B at slot 1, A at slot 2 → total profit = 101. But sorting by profit gives: A first (feasible at slot 1), then B (also feasible at slot 2) → total profit = 101. Same result here, but consider: A(p=100, d=1), B(p=50, d=1). Sorting by deadline: only B fits (slot 1) → profit 50. Sorting by profit: A fits (slot 1) → profit 100. The profit-sorted approach correctly prioritizes high-value jobs.

Comparing All Approaches

There are three main ways to solve the scheduling-with-deadlines problem. Here's how they compare in terms of time, space, and practical usability:

ApproachTime ComplexitySpace ComplexityNotes
Brute Force (enumerate all subsets)O(2ⁿ · n)O(n)Try every possible subset of jobs, check feasibility of each, pick the one with maximum profit. Exponential time — only feasible for n ≤ 20.
Greedy (basic feasibility check)O(n²)O(n)Sort by profit, then for each job, re-sort and re-check the entire selected set. Simple to implement, easy to understand. Good for n ≤ 1,000.
Greedy + Union-FindO(n log n)O(m) where m = max deadlineSame greedy logic, but uses Union-Find to find free slots in nearly O(1). Best for large n (10,000+). Requires understanding of DSU.

Why not brute force? With n jobs, there are 2ⁿ possible subsets (each job is either included or not). For n = 20, that's about 1 million subsets. For n = 30, it's about 1 billion. For n = 40, it's about 1 trillion. The brute force approach is mathematically correct but computationally impossible for realistic problem sizes.

Why greedy works: The problem has the greedy choice property and optimal substructure, which together guarantee that the greedy approach finds the optimal solution. No need to explore alternatives.

Why Union-Find helps: The basic greedy algorithm wastes time re-checking feasibility from scratch each time. Union-Find remembers which slots are free, so each job's feasibility check is nearly instant.

Union-Find Optimization

Motivation — Why Do We Need This?

The basic greedy algorithm works correctly, but it has a performance problem. Each time we try to schedule a job, we must check whether the entire current set is still feasible. This feasibility check requires sorting the set by deadline and scanning through it — an O(k) operation where k is the number of currently selected jobs. Since we do this for each of the n jobs, the total time is O(n²).

For small n (say, n ≤ 1000), O(n²) is perfectly fine. But what if n = 100,000 or 1,000,000? Then n² = 10 billion operations — way too slow. We need a faster way to check feasibility.

The Union-Find (Disjoint Set Union) data structure solves this problem. Instead of re-checking the entire set each time, we maintain a clever data structure that tells us, in nearly O(1) time, whether there's a free time slot for a new job. The key insight: instead of asking "is the entire set feasible?", we ask the simpler question "is there a free slot ≤ this job's deadline?" — and Union-Find answers that almost instantly.

Core Idea — Finding Free Slots

Imagine time slots as a row of parking spaces numbered 1, 2, 3, ..., m (where m is the maximum deadline). Initially, all spaces are empty. When we assign a job to slot k, that slot becomes occupied. For a new job with deadline d, we need to find the latest free slot ≤ d. Why the latest? Because we want to leave earlier slots free for future jobs with tighter deadlines.

Without Union-Find, finding the latest free slot ≤ d requires scanning backwards from d to 1 until we find an empty slot — potentially O(m) per job. With Union-Find, we can find it in nearly O(1) amortized time.

Here's the trick: we maintain a parent array where parent[t] tells us "if slot t is occupied, the next candidate slot to try is parent[t]." Initially, parent[t] = t for all t (every slot points to itself, meaning it's free). When we occupy slot t, we set parent[t] = find(t-1), which means "slot t is taken; try the slot that t-1 points to."

  1. Find the latest free time slot ≤ deadline of the job. Call find(d[j]). If it returns 0, no free slot exists — reject the job. If it returns t > 0, slot t is free and we can schedule the job there.
  2. Assign the job to that slot. Record slot[t] = j.
  3. Merge the assigned slot with the slot before it. Set parent[t] = find(t-1). This "links" slot t to the previous slot, so future calls to find(t) will skip over the occupied slot and find the next available one.

The Union-Find Data Structure Explained

Union-Find (also called Disjoint Set Union or DSU) is a data structure that tracks elements partitioned into disjoint (non-overlapping) sets. It supports two main operations:

  • find(x): Returns the "representative" (root) of the set containing x. In our context, find(t) returns the latest free slot ≤ t.
  • union(x, y): Merges the sets containing x and y. In our context, after occupying slot t, we union(t, t-1) so that future lookups skip slot t.

The magic is in the path compression optimization: during find(x), after finding the root, we make every node on the path point directly to the root. This flattens the tree structure, making future find operations extremely fast.

Without path compression, find could take O(n) time in the worst case (a long chain). With path compression, each find takes amortized O(α(n)) time, where α is the inverse Ackermann function — a function that grows so slowly it's ≤ 5 for any practical input size (even n = 10^100).

Data Structure in Detail

We maintain an array parent[] where parent[t] points to the next available slot before t. Initially, parent[t] = t for all t. When slot t is occupied, we set parent[t] = find(t-1).

Union-Find Operations
find(t) = latest free slot ≤ t
If slot t is free, parent[t] = t, so find(t) returns t. If slot t is occupied, parent[t] points to some earlier slot, so find(t) recursively searches earlier slots until finding a free one. If no free slot exists (we reach 0), find returns 0.

After occupying slot t: union(t, t-1) sets parent[t] = find(t-1), so future calls to find(t) skip the occupied slot and find the next available one.

Visual example of parent array evolution:

Initial: parent = [0, 1, 2, 3] (slots 0-3, all free, each points to itself)

After occupying slot 2: parent[2] = find(1) = 1. Now parent = [0, 1, 1, 3].

After occupying slot 1: parent[1] = find(0) = 0. Now parent = [0, 0, 1, 3].

Now find(2) → parent[2] = 1 → parent[1] = 0 → returns 0 (no free slots ≤ 2).

But find(3) → parent[3] = 3 → returns 3 (slot 3 is still free).

Optimized Algorithm — Complete Pseudocode

function SCHEDULE_UF(J, d, p):
   Sort jobs by decreasing profit
   m ← max deadline among all jobs
   parent[0..m] initialized: parent[t] = t ▷ Each slot points to itself
   slot[1..m] ← empty ▷ Which job is assigned to each slot
   total_profit ← 0
 
   for each job j in sorted order:
      t ← find(min(d[j], m)) ▷ Find latest free slot ≤ deadline
      if t > 0: ▷ A free slot was found
         slot[t] ← j ▷ Assign job to slot t
         total_profit ← total_profit + p[j]
         parent[t] ← find(t - 1) ▷ Mark slot t as occupied; link to previous
      end if
   end for
   return slot[1..m], total_profit
 
function find(x):
   if parent[x] == x then return x ▷ x is free (root of its set)
   parent[x] ← find(parent[x]) ▷ Path compression: point directly to root
   return parent[x]

Path Compression — The Secret to Speed

Without path compression, if we repeatedly occupy consecutive slots, the parent array forms a long chain: parent[t] = t-1, parent[t-1] = t-2, ..., parent[1] = 0. A find(t) call would need to follow this entire chain — O(t) time.

Path compression fixes this: during find(x), after we find the root r, we update parent[x] = r (and similarly for every node on the path). This means future calls to find(x) jump directly to the root in O(1) time, without traversing the chain.

Example of path compression:

Before: parent = [0, 0, 1, 2, 3] (a chain: 4→3→2→1→0)

find(4) traverses: 4→3→2→1→0, returns 0

After path compression: parent = [0, 0, 1, 0, 0] (4 and 3 now point directly to 0)

Next find(4) returns 0 in just 1 step!

With path compression, each find operation runs in nearly O(1) time (amortized inverse Ackermann function α(n)). The entire scheduling becomes O(n log n + n α(m)) = O(n log n).

Why This Gives the Same Result as the Basic Algorithm

The Union-Find approach produces the exact same schedule as the basic greedy algorithm. Both process jobs in decreasing profit order and assign each to the latest available slot ≤ its deadline. The only difference is how they find the available slot: the basic algorithm re-sorts and re-checks the entire set, while Union-Find uses the parent array to jump directly to the answer.

The correctness proof is identical: the greedy choice property and optimal substructure still hold. The Union-Find is purely a performance optimization — it doesn't change the algorithm's logic, only its speed.

Complexity Analysis

Understanding the time and space complexity of both algorithms is essential for choosing the right one in practice. Let's break down exactly where the time goes in each approach.

Basic Greedy Algorithm — O(n²)

The basic greedy algorithm has two main phases: sorting and the main loop with feasibility checks.

Time Complexity: O(n²)
T(n) = O(n log n) + O(n²) = O(n²)
n log n for sorting jobs by profit + n jobs × O(k) for feasibility checks (k ≤ n). The sorting term is dominated by the quadratic feasibility checks.

Breaking it down step by step:

  • Sorting phase: We sort n jobs by decreasing profit. Any comparison-based sort (merge sort, quicksort, heapsort) takes O(n log n) time. This is a one-time cost.
  • Main loop: We iterate through all n jobs. For each job, we perform a feasibility check on the current selected set S.
  • Feasibility check: Given k jobs in S, we sort them by deadline (O(k log k)) and scan through them (O(k)). In total, this is O(k log k) per job.
  • Total for all feasibility checks: The sum of k log k over all iterations is bounded by O(n² log n) in the worst case, but practically O(n²) since the log factor is small. The dominant cost is the repeated sorting.

Union-Find Optimized Algorithm — O(n log n)

The Union-Find approach eliminates the repeated feasibility checks, reducing the per-job cost from O(n) to nearly O(1).

Time Complexity: O(n log n)
T(n) = O(n log n) + n × O(α(m)) = O(n log n)
n log n for sorting + n find/union operations, each amortized O(α(m)) ≈ O(1). The α(m) term is the inverse Ackermann function, which is effectively constant for any practical input.

Breaking it down step by step:

  • Sorting phase: Same as before — O(n log n). This is now the DOMINANT cost.
  • Initialization: Creating the parent array of size m (max deadline) takes O(m) time.
  • Main loop: We iterate through n jobs. For each job, we perform one find operation (to locate a free slot) and one union operation (to mark the slot as occupied).
  • Find/Union cost: Each operation is O(α(m)) amortized, where α is the inverse Ackermann function. In practice, α(m) ≤ 5 for all m ≤ 10^80 (more atoms than in the universe).
  • Total for all operations: n × O(α(m)) = O(n α(m)) ≈ O(n). This is negligible compared to the sorting cost.

Basic Algorithm: O(n)

We need O(n) space for the job list (deadlines and profits), plus O(k) for the selected set (k ≤ n). No additional data structures needed. Total: O(n).

When to Use Which Algorithm

  • Basic Greedy (O(n²)): Use when n ≤ 1,000, or when code simplicity matters more than performance. Also good for interviews where you need to explain the algorithm clearly. The O(n²) approach is easier to implement correctly and easier to debug.
  • Union-Find (O(n log n)): Use when n > 10,000, or when jobs have a wide range of deadlines (m ≈ n). Essential for competitive programming and production systems handling large datasets. The extra implementation complexity is worth it for the performance gain.
What is α(n)? α(n) is the inverse Ackermann function. The Ackermann function grows incredibly fast — faster than any exponential. Its inverse grows incredibly SLOWLY. For all practical values of n (even n up to 10^80, which is more than the number of atoms in the observable universe), α(n) ≤ 5. This means Union-Find operations are effectively O(1) — constant time — for any problem you'll ever encounter.

Proof of Optimality — Exchange Argument

The greedy algorithm is optimal for the scheduling-with-deadlines problem under the 1-unit time assumption. The standard proof technique is the exchange argument:

  1. Assume the contrary: Let G be the greedy solution and O be any optimal solution with O ≠ G. We'll show O can be transformed into G without decreasing profit.
  2. Find the first difference: Sort both sets by deadline. Let the first position where they differ be position k. At positions 1 through k-1, both sets have the same jobs. At position k, G has job g and O has job o, where p(g) > p(o) (greedy chose a higher-profit job).
  3. Exchange: Replace o with g in O. Since g's deadline ≥ o's deadline (g was feasible when considered by greedy), and o was at position k in the deadline-sorted order, g also fits at position k. The set remains feasible.
  4. Profit increases or stays same: The new set has profit(O) - p(o) + p(g) ≥ profit(O) since p(g) > p(o).
  5. Repeat: Continue finding differences and exchanging. Eventually O becomes identical to G.
  6. Conclusion: Since each exchange didn't decrease profit, and G is the final result, profit(G) ≥ profit(O). Since O was optimal, profit(G) = profit(O). Therefore G is optimal.
Exchange Argument Example

Greedy G = {A(p=50, d=2), B(p=40, d=1), D(p=20, d=3)} (profit=110)

Optimal O = {A(p=50, d=2), B(p=40, d=1), E(p=10, d=1)} (profit=100) — but wait, {A, B, E} is infeasible (B and E both deadline 1). So O can't contain E. This illustrates why the greedy choice is always part of some optimal solution.
