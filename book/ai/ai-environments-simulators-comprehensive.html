AI Environments & Simulators

Environment properties, RUN-EVAL framework, and classification table

Environment Properties

Different tasks impose different constraints on agent design. The standard axes below classify environments.

Fully Observable vs Partially Observable

  • Fully observable: Sensors report every aspect relevant to the action choice at every step.
  • Partially observable: Sensors miss information, requiring internal state.

Deterministic vs Stochastic

  • Deterministic: The next state is completely determined by the current state and chosen action.
  • Stochastic: Randomness or unpredictability from other agents/nature affects outcomes.

Episodic vs Sequential

  • Episodic: Agent experience is divided into separate episodes; later episodes depend only on earlier episodes.
  • Sequential: Current decision affects all future decisions.

Static vs Dynamic vs Semidynamic

  • Static: Environment does not change while the agent deliberates.
  • Dynamic: Environment changes during deliberation.
  • Semidynamic: Environment does not change during deliberation, but the performance score changes over time.

Discrete vs Continuous

  • Discrete: Limited number of percepts and actions at each step.
  • Continuous: Real-valued signals, positions, speeds.

Single-Agent vs Multi-Agent

  • Single-agent: Only one rational entity in the environment.
  • Multi-agent: Multiple agents; can be cooperative, competitive, or partially cooperative.
Environment Classification Formula:
E = (Observable, Deterministic, Episodic, Static, Discrete, Agents)
An environment can be fully specified by these six axes.
Strategic Environment:
Strategic = Deterministic for my actions AND Nondeterministic for other agents
Common in competitive multi-agent settings like chess.

Environment Simulator Programs

Most real development happens in a simulated environment before deploying agents in physical settings.

RUN-ENVIRONMENT

Procedure RUN-ENVIRONMENT(state, UPDATE-FN, agents, termination) repeat for each agent do PERCEPT[agent] ← GET-PERCEPT(agent, state) for each agent do ACTION[agent] ← PROGRAM[agent](PERCEPT[agent]) state ← UPDATE-FN(actions, agents, state) until termination(state)

RUN-EVAL-ENVIRONMENT

function RUN-EVAL-ENVIRONMENT(state, UPDATE-FN, agents, termination, PERFORMANCE-FN) return scores repeat for each agent do PERCEPT[agent] ← GET-PERCEPT(agent, state) for each agent do ACTION[agent] ← PROGRAM[agent](PERCEPT[agent]) state ← UPDATE-FN(actions, agents, state) scores ← PERFORMANCE-FN(scores, agents, state) until termination(state)

Important Distinction

The state variable in the simulator is not the same as the agent's internal state. Agents must construct state only from their percepts, never by peeking at simulator internals.

Notes and Common Pitfalls

Example 1 - Easy vs Hard Environments

The fully observable, deterministic, episodic, static, discrete, single-agent environment is easiest to design for. The taxi-driving task lies near the opposite end on most axes.

Example 2 - Strategic Environments

If an environment is deterministic for my agent's actions but not for opponent actions, call it strategic rather than fully deterministic.

Example 3 - Poker Special Case

If the agent keeps track of card order, poker becomes deterministic; otherwise it is nondeterministic. This causes classification ambiguity.
