Knowledge Engineering in First-Order Logic

Building Knowledge Bases for AI Systems

Overview: The Knowledge Engineering Process

Knowledge engineering is the systematic process of constructing a knowledge base that enables an AI agent to reason about a specific domain. The process involves six core steps, each critical to building a robust and effective knowledge base.

The knowledge engineering process is iterative—you may need to revisit earlier steps as you discover new requirements or problems.

Step 1: Identify the Task

Before writing any logic, clearly define what the knowledge base must accomplish.

What questions?
What can the KB answer?
What facts?
What information exists?
What reasoning?
What inferences are needed?
Key Questions to Ask
1. What agents will use the KB?
2. What tasks will they perform?
3. What information do they need?
Example: Family Relationships

Task: Determine family relationships between people.

Questions the KB should answer:

  • Is X the parent of Y?
  • Is X the sibling of Y?
  • Is X an ancestor of Y?
  • How are X and Y related?

Step 2: Assemble Relevant Knowledge

Gather knowledge from domain experts, textbooks, and other sources. This is called knowledge acquisition.

Common Mistake: Trying to capture ALL knowledge at once. Start with the most important concepts and expand gradually.
Expert Interviews
Talk to domain experts
Textbooks
Read reference materials
Observation
Watch how experts solve problems
Knowledge Sources
• Domain experts (primary source)
• Textbooks and manuals
• Existing databases
• Case studies and examples

Step 3: Decide on Vocabulary (Ontology)

Choose the predicates, functions, and constants that will represent your domain. This is the ontology of your knowledge base.

Vocabulary Components
Predicates: P(x), Q(x,y), R(x,y,z)
Functions: f(x), g(x,y)
Constants: a, b, c
Predicates express properties or relations. Functions map objects to objects. Constants name specific objects.
Example: Family Domain Vocabulary

Constants: John, Mary, Bob (specific people)

Predicates:

  • Person(x) — x is a person
  • Male(x) — x is male
  • Female(x) — x is female
  • Parent(x,y) — x is a parent of y
  • Child(x,y) — x is a child of y

Step 4: Encode General Knowledge

Write axioms that capture general truths about the domain. These are the rules that apply to all instances.

Universal Axiom Pattern
∀x (Condition(x) → Conclusion(x))
For all x, if x satisfies the condition, then x satisfies the conclusion.
Example: General Knowledge Axioms

Axiom 1: Every parent is a person

∀x (Parent(x,y) → Person(x))

Axiom 2: If x is a parent of y, then y is a child of x

∀x∀y (Parent(x,y) → Child(y,x))
Common Mistake: Writing too-specific axioms. General axioms should apply universally, not just to specific instances.

Step 5: Encode Specific Problem

Add atomic sentences that describe the specific situation or problem instance you want to reason about.

Specific Instance Pattern
Predicate(Constant1, Constant2, ...)
Ground facts about specific objects in the domain.
Example: Specific Family Facts
Person(John)
Person(Mary)
Person(Bob)
Male(John)
Female(Mary)
Parent(John, Bob)
Parent(Mary, Bob)

Step 6: Debug the Knowledge Base

Test the KB by asking questions and checking if the answers are correct. Find and fix missing or incorrect axioms.

Missing Axioms
KB can't prove things that should be provable
Incorrect Axioms
KB proves things that are wrong
Vague Predicates
Hard to define predicates completely
Debugging Process
1. Ask a question you know the answer to
2. Check if the KB gives the right answer
3. If wrong, find the faulty axiom
4. If no answer, find the missing axiom
5. Fix and re-test
Example: Debugging Session

Test: Is Bob a child of John?

Expected: Yes

KB Result: No (can't derive it)

Problem: Missing axiom Child(x,y) ↔ Parent(y,x)

Fix: Add the bidirectional axiom

What is an Ontology?

An ontology defines the vocabulary of a domain—the types of things that exist and how they relate to each other. It is the conceptual foundation of your knowledge base.

Ontology Definition
Ontology = {Types of objects, Properties, Relations, Functions}
The complete set of concepts and categories used to describe a domain.

Choosing Predicates

Predicates represent properties of objects or relations between objects. The choice of predicates determines what you can express.

Predicate Type Purpose Example
Unary (1-ary) Property of an object Person(x), Red(x)
Binary (2-ary) Relation between two objects Parent(x,y), Likes(x,y)
Ternary (3-ary) Relation among three objects Betwen(x,y,z)
n-ary Relation among n objects Give(x,y,z)
Design Principle: Keep predicates as general as possible. Avoid creating predicates that are too specific (e.g., IsTallJohn(x) instead of Tall(x)).

Functions vs. Predicates

Functions map objects to objects; predicates express true/false properties. The choice affects expressiveness.

Functions
Return objects
Father(x), Mother(x)
Age(x), Height(x)
Predicates
Return true/false
IsFather(x), IsMother(x)
IsOld(x), IsTall(x)
When to Use Which
Use a FUNCTION when:
• Each input maps to exactly one output
• You need to refer to the output

Use a PREDICATE when:
• You're asserting a property or relation
• The answer is yes/no
Example: Function vs Predicate

Using function: Father(John) = Bob (function returns an object)

Using predicate: Parent(John, Bob) (predicate is true)

Combining: Person(Father(John)) — function inside predicate

Constants and Objects

Constants name specific objects in the domain. Choose meaningful, consistent names.

Naming Conventions
• Use lowercase for variables: x, y, z
• Use uppercase for constants: John, Mary
• Use descriptive names: Parent, NotFriend
• Keep names consistent throughout
Common Mistake: Using the same name for different concepts. For example, using "Parent" to mean both "is a parent" and "is a father" creates ambiguity.

Ontology Engineering Principles

Completeness
Cover all relevant concepts
Consistency
No contradictory definitions
Minimalism
Don't include unnecessary concepts
Modularity
Organize into logical sections
Example: Good vs Bad Ontology

Bad: Too many specific predicates

IsParentOfJohn(x)
IsParentOfMary(x)
IsParentOfBob(x)

Good: One general predicate

Parent(x, y) — x is a parent of y

Why Debugging is Critical

A knowledge base with errors will produce wrong conclusions. Debugging is the process of finding and fixing these errors to ensure the KB behaves correctly.

Types of KB Errors
1. Missing Axioms — can't prove true things
2. Incorrect Axioms — prove false things
3. Vague Predicates — incomplete definitions
4. Contradictory Axioms — inconsistent KB

Missing Axioms

When the KB can't derive something that should be provable, an axiom is missing.

Example: Missing Symmetry Axiom

KB has: Parent(John, Bob) — "John is a parent of Bob"

KB needs: To derive Child(Bob, John) — "Bob is a child of John"

Missing axiom: ∀x∀y (Parent(x,y) → Child(y,x))

Without it: KB can't answer "Is Bob a child of John?"

Debugging Technique: Start with a simple question you know the answer to. Work backward to find what axioms are needed to derive that answer.

Incorrect Axioms

When the KB proves something that is false in the real world, an axiom is incorrect.

Example: Incorrect Axiom

Axiom: ∀x (Male(x) → Father(x))

Problem: This says all males are fathers, which is false!

Fix: ∀x∀y (Male(x) ∧ Parent(x,y) → Father(x,y))

Corrected: A male is a father only if he has a child

Finding Incorrect Axioms
1. Find a false conclusion
2. Trace back which axioms were used
3. Check each axiom for correctness
4. Fix or remove the faulty axiom

Vague Predicates

Some concepts are inherently difficult to define precisely. These vague predicates require careful handling.

Person(x)
When does a fetus become a person?
Tall(x)
How tall is "tall"?
Friend(x,y)
What makes someone a friend?
Strategies for Vague Predicates
1. Use operational definitions (measurable criteria)
2. Use context-dependent rules
3. Accept approximation (fuzzy logic)
4. Define relative to other predicates
Example: Defining "Tall"

Problem: Tall(x) is vague

Operational definition:

Tall(x) ↔ Height(x) > 180cm
Now "tall" has a measurable criterion.

Contradictory Axioms

When two axioms contradict each other, the KB becomes inconsistent and can prove anything.

Example: Contradiction

Axiom 1: ∀x (Student(x) → ¬Working(x))

Axiom 2: ∀x (Working(x) → Student(x))

Problem: Axiom 1 says students don't work. Axiom 2 says workers are students. Together: no one can be both!

Detecting Contradictions
1. Use a theorem prover to find inconsistencies
2. Test with known facts
3. Check for circular definitions
4. Verify axioms don't overlap incorrectly

Debugging Methodology

Step 1
Test with simple, known facts
Step 2
Check if derivations match expectations
Step 3
Isolate problematic axioms
Step 4
Fix and re-test incrementally

Example 1: Simple Family Domain

Complete Engineering Process

Step 1 - Identify Task: Answer questions about family relationships (parent, child, sibling, ancestor).

Step 2 - Assemble Knowledge: Interview family members, read genealogy records.

Step 3 - Ontology:

Constants: John, Mary, Bob, Alice
Predicates: Person(x), Male(x), Female(x), Parent(x,y)

Step 4 - General Axioms:

∀x (Parent(x,y) → Person(x))
∀x∀y (Parent(x,y) → Child(y,x))
∀x∀y∀z (Parent(x,y) ∧ Parent(x,z) → Sibling(y,z))

Step 5 - Specific Facts:

Person(John), Person(Mary), Person(Bob), Person(Alice)
Male(John), Male(Bob), Female(Mary), Female(Alice)
Parent(John, Bob), Parent(John, Alice), Parent(Mary, Bob), Parent(Mary, Alice)

Step 6 - Debug: Test: "Is Bob a sibling of Alice?" Should derive: Yes

Example 2: Animal Kingdom

Building an Animal Knowledge Base

Task: Classify animals and their properties.

Vocabulary:

Animal(x), Dog(x), Cat(x), Pet(x)
Loves(x,y), Fear(x,y)

General Axioms:

∀x (Dog(x) → Animal(x))
∀x (Cat(x) → Animal(x))
∀x∀y (Pet(x) ∧ Dog(y) → Loves(x,y))
∀x∀y (Cat(x) ∧ Dog(y) → Fear(y,x))

Specific Facts:

Dog(Rex), Cat(Whiskers), Pet(Tom)
→ Tom loves Rex (by Pet(Tom) ∧ Dog(Rex))
→ Rex fears Whiskers (by Dog(Rex) ∧ Cat(Whiskers))

Example 3: Shopping Domain

E-commerce Knowledge Base

Task: Determine if a customer can buy an item.

Vocabulary:

Customer(x), Product(y), InStock(y)
CanAfford(x,y), Wants(x,y), CanBuy(x,y)

General Axiom:

∀x∀y (Customer(x) ∧ Product(y) ∧ InStock(y) ∧ Wants(x,y) ∧ CanAfford(x,y) → CanBuy(x,y))

Specific Facts:

Customer(Alice), Product(Laptop)
InStock(Laptop), Wants(Alice, Laptop), CanAfford(Alice, Laptop)
→ Alice can buy the laptop

Example 4: Travel Domain

Travel Planning Knowledge Base

Task: Plan trips between cities.

Vocabulary:

City(x), Flight(x,y), Hotel(x), Booked(x,y)
CanTravel(x,y), NeedsHotel(x,y)

General Axioms:

∀x∀y (Flight(x,y) → CanTravel(x,y))
∀x∀y (City(x) ∧ City(y) ∧ ¬Flight(x,y) → ¬CanTravel(x,y))
∀x∀y (CanTravel(x,y) ∧ x ≠ y → NeedsHotel(x,y))

Specific Facts:

City(Paris), City(Tokyo), Flight(Paris, Tokyo)
→ CanTravel(Paris, Tokyo)
→ NeedsHotel(Paris, Tokyo)

Example 5: Debugging a Faulty KB

Finding and Fixing Errors

Original KB:

∀x (Student(x) → ¬PartTime(x))
∀x (PartTime(x) → Student(x))
Student(Bob), PartTime(Alice)

Problem: Axiom 1 says students can't be part-time. Axiom 2 says part-timers are students. Contradiction for Alice!

Debugging:

1. Test: Is Alice a student?
2. Derive: Yes (from PartTime(Alice) and Axiom 2)
3. Test: Is Alice part-time?
4. Derive: Yes (from PartTime(Alice))
5. Check: Can Alice be both? Axiom 1 says NO!
6. Contradiction found!

Fix: Remove or revise Axiom 1 to allow overlap.

Comparison: Well-Designed vs Poorly-Designed KB

Aspect Well-Designed Poorly-Designed
Predicates General and reusable Specific and duplicated
Axioms Complete and correct Missing or contradictory
Naming Consistent and descriptive Inconsistent and confusing
Structure Modular and organized Mixed and tangled
Testing Thorough with edge cases Minimal or no testing
