Avoiding Repeated States

Artificial Intelligence — Chapter 2: Problem Solving Using Search

The Problem of Repeated States

When a search algorithm revisits the same state multiple times, it causes exponential waste. In the worst case, a finite state space can produce an infinite search tree if repeated states are not detected.

Tree Search (no repeat detection)
States explored: O(bd)  —  but many are redundant!
Without memoization, the same state may be expanded exponentially many times

The Romanian Example

Romania's road map has only 20 cities (states). But a tree search starting from Arad and trying to reach Bucharest would generate an infinite tree by cycling between cities (Arad → Zerind → Arad → Zerind → ...). With repeat detection, only 20 states need to be explored.

Without Repeat Detection

• Infinite search tree from finite space

• Cycles cause infinite loops

• Same state expanded thousands of times

• DFS may never terminate

With Repeat Detection

• Graph search remembers visited states

• Each state expanded at most once

• Search terminates even with cycles

• Dramatically fewer nodes explored

Grid Example: Exponential Explosion

Tree Search on Grid (without repeats)
Nodes = O(4d)
Each step has ~4 moves (up, down, left, right), so branching factor = 4
Graph Search on Grid (with repeats)
Nodes ≈ πd²  (for a d × d reachable area)
Only unique grid cells are expanded — a quadratic number, not exponential!
⚠ Critical Insight

A finite state space can produce an infinite search tree when using tree search. Without repeated state detection, DFS can loop forever even when a solution exists at depth 1! Always use graph search for cyclic state spaces.

Graph Search: The Solution

Graph search maintains two data structures: the closed list (expanded nodes) and the open list (frontier). Before expanding a node, check if its state is already in the closed list.

Open List (Frontier)

Nodes discovered but not yet expanded. Also called the fringe or frontier.

Closed List (Explored)

Nodes that have been expanded. Typically implemented with a hash table for O(1) lookup.

Pseudocode: GRAPH-SEARCH

function GRAPH-SEARCH(problem) returns solution or failure closed ← empty set frontier ← {MAKE-NODE(problem.INITIAL-STATE)} loop do if EMPTY?(frontier) then return failure node ← POP(frontier) if problem.GOAL-TEST(node.STATE) then return SOLUTION(node) if node.STATE not in closed then add node.STATE to closed for each action in problem.ACTIONS(node.STATE) do child ← CHILD-NODE(problem, node, action) if child.STATE not in closed and child not in frontier then add child to frontier

Hash Table Implementation

The closed set is typically a hash table mapping state → best-known cost (or parent). This enables O(1) lookup to check if a state has been visited.

Space Overhead for Repeat Detection
|closed| ≤ |state space|
The closed list stores at most all unique states in the problem
Feature Tree Search Graph Search
Repeat detection No Yes (closed list)
Space complexity Lower (no closed list) Higher (stores all visited states)
Time in cyclic spaces Infinite (cycles) Finite
Optimality preservation N/A (may not find goal) Depends on search strategy
⚠ Trade-off Warning

Graph search trades space for time. By storing all visited states (potentially the entire state space), we save exponential time. For the Romania problem: 20 states stored vs infinite tree. For a 20×20 grid: 400 states stored vs 420 tree nodes.

Optimality Concerns with Graph Search

Graph search always keeps the first path discovered to each state. This is a problem because the first path to a state might not be the cheapest path.

Safe: BFS and UCS

For BFS (with uniform costs) and UCS (with non-negative costs), the first time a state is reached is via the shortest path. This is guaranteed by the order of expansion.

BFS/UCS: First Path = Optimal Path
If cost frontier is non-decreasing, first pop is optimal
BFS expands level by level, UCS expands in order of path cost

Danger: DFS and IDS

For DFS and IDS, the first path discovered to a state might be suboptimal. If we add the state to the closed list, we may miss a better path found later.

DFS/IDS Problem
First path to S (cost = 10): S is closed  →  Better path (cost = 3) rejected!
Once a state is closed, alternative paths are ignored — even if cheaper

Solutions for DFS/IDS

  • Compare costs: When a state is re-encountered, if the new path is cheaper, update the node and propagate the cost change to children
  • Accept suboptimality: In some problems, finding any solution quickly matters more than optimality
  • Don't use closed list: Let DFS/IDS run as tree search (may loop but IDS with cycles is complex)

The Space-Time Trade-off

Strategy Without Closed List With Closed List
BFS O(bd) time, O(bd) space Optimal + complete
UCS O(bC*/ε) time Optimal (with non-negative costs)
DFS O(bm) time, O(bm) space Space becomes O(state space), may lose optimality
IDS O(bd) time, O(bd) space Adding closed list makes space O(bd) — defeats purpose!
⚠ Key Understanding

Using a closed list with DFS/IDS converts their space complexity from O(bd) to O(|state space|). For DFS, this means the memory advantage over BFS is lost! There is no free lunch — you must choose between memory efficiency and repeat avoidance.

Worked Examples

Example 1: Tree Search vs Graph Search on a 3×3 Grid

Problem: Robot on 3×3 grid, start at (0,0), goal at (2,2). Can move up, down, left, right (staying within bounds). Depth to goal = 4 moves.

Tree Search (no repeat detection):

At each step, the robot can go to 2-4 neighbors. Some moves lead back to previous cells. Tree search visits (0,0) → (0,1) → (0,0) → (0,1) → ... creating cycles.

Total nodes generated (BFS tree): ~44 = 256 nodes (many repeats).

Graph Search (with closed list):

There are only 9 unique cells. The closed list stores all 9. Each cell expanded once.

Total nodes expanded: 9 unique cells vs 256 tree nodes.

Savings: 256/9 = 28x fewer nodes expanded!

Example 2: Romanian Route Finding

Problem: Find path from Arad to Bucharest in Romania road map (20 cities). Using DFS.

Tree Search: DFS goes Arad → Zerind → Oradea → Sibiu → Fagaras → Bucharest. But without repeat detection, DFS might go Arad → Sibiu → Arad → Sibiu → ... cycling forever. Or: Arad → Timisoara → Lugoj → Mehadia → Lugoj → Timisoara → Arad → ... infinite.

Graph Search: Closed list tracks which 20 cities have been visited. DFS with closed list: Arad → Sibiu → Fagaras → Bucharest. Found in 4 steps exploring only 4 of 20 cities. Total closed list size: 4 states.

Result: Without graph search, DFS on Romanian map can loop infinitely. With graph search, it terminates quickly.

Example 3: Suboptimal Path with DFS + Closed List

Problem: Graph with states A, B, C, D, E, F, G. Start = A, Goal = G.

Edges: A→B(1), A→C(10), B→D(1), D→E(1), E→C(1), C→F(1), F→G(1)

The optimal path is A→B→D→E→C→F→G with total cost 5.

DFS with closed list:

DFS explores: A → B → D → E → C → F → G

But wait — DFS first reaches C via path A→C (cost 10) and closes C. Later, when the optimal path A→B→D→E→C (cost 4) reaches C, C is already closed! The better path is rejected.

Result: DFS finds path A→C→F→G with cost 12, not optimal.

Fix: When re-reaching C, compare costs. If new cost (4) < old cost (10), update C's cost and revisit children.

Example 4: Exponential Reduction with Graph Search

Problem: 8-puzzle has 181,440 reachable states. A tree search for a solution at depth 20 would generate b20 nodes. Branching factor b ≈ 2-3 (depends on blank position).

Tree Search: ~320 = 3.4 billion nodes (many repeats)

Graph Search: At most 181,440 unique states expanded.

Savings: 3.4 billion / 181,440 = 18,900x fewer nodes!

This is why every practical 8-puzzle solver uses graph search with a closed list.

⚠ Exam Tip

When comparing tree search and graph search on an exam, always: (1) explain that tree search may explore the same state many times, (2) show the growth formula (bd for tree vs |states| for graph), (3) mention optimality concerns for DFS/IDS.
