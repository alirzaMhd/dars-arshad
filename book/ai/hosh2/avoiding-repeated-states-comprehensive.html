Avoiding Repeated States

AI Search - Complete Guide for 20/20 Exam

The Repeated State Problem

In state spaces with multiple paths to the same state, TREE-Search wastes time re-expanding identical states. A path like A→B→C→B creates a loop. Even without loops, different paths can reach the same state (e.g., A→B→D and A→C→D).

State Space Size vs Tree Size:
Tree size can be exponential or infinite even when state space is finite
In a grid with 800 distinct states, the tree of paths has 4^20 nodes at depth 20 - over a trillion nodes, all representing only 800 states.
Critical Issue: Repeated states can turn a solvable problem into an unsolvable one by causing infinite expansion. They can also increase complexity from polynomial to exponential.

Graph Search Algorithm

GRAPH-SEARCH maintains a closed list of all expanded states. Before expanding a node, it checks whether that state is already in the closed list. If so, the node is discarded.

function GRAPH-SEARCH(problem, fringe) returns solution or failure
closed ← empty set
fringe ← Insert(Make-Node(Initial-State[problem]), fringe)
loop do
if Empty?(fringe) then return failure
node ← Remove-First(fringe)
if Goal-Test[problem](State[node]) then return Solution(node)
if State[node] not in closed then
closed ← Add(State[node], closed)
fringe ← Insert-All(Expand(node, problem), fringe)

Open List

The fringe containing nodes that have been generated but not yet expanded.

Closed List

The set of states that have already been expanded. Prevents re-expansion.

Memory Requirement:
All expanded states must remain in closed
This is why GRAPH-SEARCH needs more memory than TREE-SEARCH: it stores every visited state, not just the frontier.

Optimality with Repeated States

When a repeated state is detected, GRAPH-SEARCH keeps only the first discovered path. This is safe for BFS and UCS, where the first path is always optimal. For DFS and IDS, a better path may be discovered later.

Strategy Repeated State Safe? Reason
BFS Yes First path is always shortest hop path
UCS Yes First path is always cheapest path
DFS No Later path may be cheaper or shallower
IDS No May find suboptimal path first
For DFS and IDS: A modified GRAPH-SEARCH must check if the new path is cheaper/shallower and update the node's children if so. This adds bookkeeping complexity.

Worked Examples

Example 1 - Infinite Tree from Finite Graph

Graph: A↔B, B↔C, C↔D. Tree from A: A→B→C→D, A→B→A→B→C→D, A→B→A→B→A→B→C→D, ... Infinite paths from finite 4-state graph.

GRAPH-SEARCH: Expands A, B, C, D once each. Stops. Total: 4 nodes.

Example 2 - Grid World

20x40 grid with 4 actions (up, down, left, right). Each state has 4 successors. Tree at depth 20 has 4^20 nodes. Graph has only 800 states. GRAPH-SEARCH needs ~800 expansions instead of trillions.

Example 3 - Two Paths to Same State

Paths to state D: Path1 (cost 5) found first, Path2 (cost 3) found later. BFS/UCB keeps Path1 because it was first. But Path1 is worse! For UCS, this cannot happen because UCS explores by cost. For BFS, it cannot happen in unweighted graphs.

Example 4 - Implementation with Hash Table

Store expanded states in a hash table. When a node is about to be expanded, hash its state and check table membership in O(1). This keeps the overhead of cycle detection low.
