Search Performance Evaluation

AI Problem Solving — Complete Guide

Four Evaluation Criteria

Every search algorithm is evaluated along four dimensions that determine its practical usefulness.

Criterion 1 — Completeness:
Does the algorithm guarantee finding a solution when one exists?
A complete algorithm always finds a solution if the state space contains one (assuming infinite time and memory).
Criterion 2 — Optimality:
Does the algorithm find the least-cost solution among all solutions?
An optimal algorithm returns the solution with minimum path cost, not just any solution.
Criterion 3 — Time Complexity:
How long does the algorithm take to find a solution?
Measured as the number of nodes expanded (or generated) during search.
Criterion 4 — Space Complexity:
How much memory is needed to perform the search?
Measured as the maximum number of nodes stored simultaneously (usually the fringe + visited set).

Completeness Examples

• BFS: Complete (finds solution if exists)

• DFS: Incomplete (may loop forever in infinite spaces)

• Iterative Deepening: Complete

• Greedy Best-First: Incomplete (can get stuck)

Optimality Examples

• BFS: Optimal (for uniform step costs)

• UCS: Optimal (any positive costs)

• DFS: Not optimal (finds any solution)

• A* with admissible heuristic: Optimal

Common Mistake: Confusing completeness with optimality. An algorithm can be complete (always finds a solution) but not optimal (solution may be expensive). Example: BFS is complete but only optimal when all step costs are equal.

Key Metrics: b, d, m

Three metrics characterize the search space and determine algorithm performance.

b — Branching Factor:
b = maximum number of successors generated per node
Upper bound on how many children each node can produce. For Romanian cities, b ≈ 3 (most cities connect to 2-4 others).
d — Depth of Shallowest Goal:
d = number of steps along the shortest path from initial state to any goal state
The minimum solution length. D determines the problem's inherent difficulty.
m — Maximum Depth:
m = length of the longest possible path in the state space
May be infinite if the state space has cycles. Finite for DAGs (directed acyclic graphs).

Warning: Exponential Complexity. Even moderate values of b and d produce astronomically large search trees. For b=10, d=15: 10¹⁵ nodes. At 10⁷ nodes/second, this takes 10⁸ seconds ≈ 3 years. Never underestimate exponential growth.

Total Cost

The total cost of solving a problem via search has two components that must be balanced.

Total Cost:
Total Cost = Search Cost + Path Cost
Search cost = time + memory used during search. Path cost = cost of traversing the solution.
Search Cost Components:
Time ≈ Number of nodes generated  |  Space ≈ Maximum number of nodes stored
Time measured in operations (or seconds), space measured in memory (bytes/megabytes).

Unit Conversion

Different cost types must be converted to a common unit for comparison. For example, converting path distance (km) to time (seconds) using average speed.

Cost Unit Conversion Example

Problem: A path costs 350 km. A search takes 2 seconds. The car travels at 70 km/h. Which dominates total cost in terms of time?

Solution:

Travel time = 350 km / 70 km/h = 5 hours = 18,000 seconds

Search time = 2 seconds

Total time = 18,002 seconds

Path cost dominates (99.99% of total time). Search time is negligible.

Trade-Offs

More search time can sometimes reduce path cost (e.g., A* finds shorter routes).

More memory can reduce search time (e.g., bidirectional search halves depth).

The best algorithm balances both costs for the specific problem.

When Search Cost Matters

• Real-time systems (self-driving cars)

• One-time search (trip planning)

• Repeated searches (game AI)

• Resource-constrained devices (robots with limited RAM)

Common Mistake: Ignoring one component of total cost. A search that finds the absolute shortest path but takes 3 hours to compute may be worse than one that finds a slightly longer path in 1 second. Always consider the combined total.

Worked Examples

Example 1: Calculate Total Nodes at Depth d

Problem: A search problem has branching factor b=4 and shallowest goal depth d=6. What is the maximum number of nodes BFS expands before finding the goal (in the worst case)?

Solution:

BFS expands all nodes at depths 0, 1, 2, ..., d−1 before reaching depth d.

Total nodes = Σᵢ₌₀ᵈ bⁱ = (bᵈ⁺¹ − 1) / (b − 1)

For b=4, d=6:

Total = (4⁷ − 1) / (4 − 1) = (16,384 − 1) / 3 = 16,383 / 3 = 5,461 nodes

The tree at depth 6 alone has 4⁶ = 4,096 nodes. Earlier depths contribute 1 + 4 + 16 + 64 + 256 + 1,024 = 1,365 nodes.

Example 2: Estimate Time to Complete Search

Problem: For a problem with b=3 and d=10, if each node expansion takes 0.1 milliseconds (10⁻⁴ s), how long will a complete BFS take?

Solution:

Total nodes to expand (worst-case) = (3¹¹ − 1) / (3 − 1) = (177,147 − 1) / 2 = 88,573

Time = 88,573 × 0.1 ms = 8,857.3 ms ≈ 8.86 seconds

Check memory: fringe at depth 10 = 3¹⁰ = 59,049 nodes

If each node uses 64 bytes: 59,049 × 64 ≈ 3.78 MB

Feasible! But for b=10, d=15: 10¹⁵ nodes → 10⁸ seconds ≈ 3.2 years. Completely infeasible.

Example 3: Completeness Check

Problem: Consider a search space with 5 states: A (initial), B, C, D, E (goal). Transitions: A→B, B→C, C→B, B→D, D→E. Depth-first search is used with a depth limit of 3. Is it complete?

Solution:

DFS exploration from A:

A (depth 0) → B (depth 1)
B (depth 1) → C (depth 2)
C (depth 2) → B (depth 3, but B is already in current path — cycle detected by some implementations, otherwise would recurse)
Back to B → D (depth 2)
D (depth 2) → E (depth 3) — Goal found!

DFS with depth limit 3 finds the solution. Complete for this case.

But if depth limit were 2: DFS would reach D at depth 2, then E requires depth 3. It would fail. Incomplete.

DFS with depth limit l is complete iff l ≥ d (depth of shallowest goal). Without a limit, DFS may loop forever in cyclic graphs.

Example 4: Optimality Comparison

Problem: Two paths exist from A to G: A→B→G (cost 5+1=6) and A→C→G (cost 2+2=4). Which search algorithms find the optimal solution?

Solution:

Example 5: Total Cost Trade-Off

Problem: Algorithm X finds a 300km path in 5 seconds. Algorithm Y finds a 280km path in 120 seconds. If driving at 60 km/h and time = search_time + travel_time, which is better?

Solution:

Algorithm X:

Travel time = 300 km / 60 km/h = 5 hours = 18,000 seconds

Total time = 5 + 18,000 = 18,005 seconds

Algorithm Y:

Travel time = 280 km / 60 km/h ≈ 4.667 hours = 16,800 seconds

Total time = 120 + 16,800 = 16,920 seconds

Algorithm Y is better by 1,085 seconds (~18 minutes) despite taking 24× longer to search!

The extra search time (115 seconds) saves 1,200 seconds of driving. Total cost is dominated by path cost in this case.
