IDA* — Iterative Deepening A*

Artificial Intelligence — Informed Search

Algorithm Overview

IDA* reduces A*'s exponential memory requirement by using iterative deepening on the f-cost instead of depth. It behaves like DFS but prunes branches whose f-cost exceeds a growing threshold.

f-limit (threshold)
f-limit = f(root) initially; incremented each iteration
Unlike IDDFS which limits depth, IDA* limits the f-cost, combining g(n) + h(n)

Pseudocode

function IDA*(problem) returns a solution root ← MAKE-NODE(INITIAL-STATE[problem]) f-limit ← f-COST(root) loop do solution, f-limit ← DFS-CONTOUR(root, f-limit) if solution is not null then return solution if f-limit = ∞ then return failure function DFS-CONTOUR(node, f-limit) returns solution and new limit if f-COST[node] > f-limit then return null, f-COST[node] if GOAL-TEST(STATE[node]) then return node, f-limit next-f ← ∞ for each s in SUCCESSORS(node) do solution, new-f ← DFS-CONTOUR(s, f-limit) if solution is not null then return solution, f-limit next-f ← MIN(next-f, new-f) return null, next-f

Properties

Complete
Yes — eventually f-limit reaches C* and the goal is found
Optimal
Yes — with admissible heuristic, first solution found is optimal
Space Complexity
O(bd) — linear with depth, like DFS. Worst case O(bδ) where δ = min action cost
Time Complexity
Depends on number of distinct f-values along paths. Can be much worse than A*

Walkthrough: Romania Problem

  Goal: Arad → Bucuresti (C* = 418 with straight-line heuristic)

  Iteration 1: f-limit = f(Arad) = 366
    └─ Arad (f=366)
       ├─ Sibiu (f=393) > 366 → cutoff, returns 393
       ├─ Timisoara (f=447) > 366 → cutoff, returns 447
       └─ Zerind (f=449) > 366 → cutoff, returns 449
    → New f-limit = min(393, 447, 449) = 393

  Iteration 2: f-limit = 393
    └─ Arad
       └─ Sibiu (f=393)
          ├─ Oradea (f=415) > 393 → cutoff, returns 415
          ├─ Rimnicu (f=413) > 393 → cutoff, returns 413
          └─ Fagaras (f=417) > 393 → cutoff, returns 417
    → New f-limit = min(415, 413, 417, 447, 449) = 413

  Iteration 3: f-limit = 413
    └─ Arad → Sibiu → Rimnicu (f=413)
       ├─ Craiova (f=526) > 413 → cutoff, returns 526
       ├─ Pitesti (f=417) > 413 → cutoff, returns 417
       └─ Sibiu again (already on path) → skip
    → New f-limit = min(415, 417, 417, 447, 449, 526) = 415

  Iteration 4: f-limit = 415
    └─ Arad → Sibiu → Oradea (f=415)
       └─ ... explores Oradea branch
    → New f-limit = min(417, ...) = 417

  Iteration 5: f-limit = 417
    └─ Arad → Sibiu → Fagaras (f=417) OR Rimnicu → Pitesti (f=417)
       At Fagaras: f=417 ≤ 417, expand
       └─ Bucuresti found! f=418 = 417+1
    → Solution found! Cost = 418 (optimal)
Key Observation: IDA* re-explores nodes in each iteration. Above, Arad and Sibiu are expanded 5 times, Rimnicu 2-3 times. This is the price of linear memory.

TSP Performance Issue

TSP Example: f-limit increments by 1 each iteration
For TSP with N cities, each iteration expands only one more node than the previous.
Iterations: 1, 2, 3, ..., N
Total expansions: 1 + 2 + 3 + ... + N = N(N+1)/2 = O(N²)
A* would expand N nodes total: O(N)

Solution: Increase f-limit by a larger increment ε each iteration.
Larger ε → fewer iterations, but may sacrifice optimality if ε is too large.

  │ 7 │ 6 │ 5 │                  │ 7 │ 6 │ 5 │
  └───┴───┴───┘                  └───┴───┴───┘

  Heuristic: Manhattan distance
  f(start) = 0 + 0 = 0 (already at goal? No — this example is already solved.
  Let's use a scrambled version.)

  Suppose start has f(start) = 6, and C* = 24.

  IDA* iterations:
    f-limit=6:  1 node expanded, cutoff at depth 1. New limit = 8
    f-limit=8:  5 nodes expanded, cutoff at depth 2. New limit = 10
    f-limit=10: 18 nodes expanded. New limit = 12
    f-limit=12: 55 nodes expanded. New limit = 14
    ...
    f-limit=24: ~5000 nodes expanded. Goal found!

  Total nodes expanded by IDA*: ~8,000
  A* would expand: ~3,000 (less re-expansion)
  IDA* memory: O(bd) ≈ 500 nodes at once
  A* memory: O(b^d) ≈ 3,000 nodes

ε must be small enough that the optimal path's f-cost is not skipped over. The heuristic guides this — if all paths have distinct f-costs, any ε < min difference works.
Example 3: Toy Tree — IDA* Contour Expansion
  Tree:
             A (f=5)
           /   \
      (f=7)B     C(f=8)
         / \     / \
     (9)D  E(10) F(9) G(12)

  C* = optimal path cost = A→C→F = 9

  IDA* Traces:
    Iter 1: f-limit=5
      A: f=5 ≤ 5, expand
      B: f=7 > 5, cutoff → return 7
      C: f=8 > 5, cutoff → return 8
      New f-limit = min(7,8) = 7

    Iter 2: f-limit=7
      A: f=5 ≤ 7, expand
      B: f=7 ≤ 7, expand
      D: f=9 > 7, cutoff → return 9
      E: f=10 > 7, cutoff → return 10
      C: f=8 > 7, cutoff → return 8
      New f-limit = min(8,9,10) = 8

    Iter 3: f-limit=8
      A: f=5 ≤ 8, expand
      B: f=7 ≤ 8, expand
      D: f=9 > 8, cutoff → return 9
      E: f=10 > 8, cutoff → return 10
      C: f=8 ≤ 8, expand
      F: f=9 > 8, cutoff → return 9
      G: f=12 > 8, cutoff → return 12
      New f-limit = min(9,9,10,12) = 9

    Iter 4: f-limit=9
      A: f=5 ≤ 9, expand
      B: f=7 ≤ 9, expand
      D: f=9 ≤ 9, expand — no children, backtrack
      E: f=10 > 9, cutoff
      C: f=8 ≤ 9, expand
      F: f=9 ≤ 9, expand — goal found!

  Nodes expanded: A(4×), B(3×), C(3×), D(2×), E(1×), F(1×), G(1×) = 15
  A* would expand: A, B, C, D, F = 5 nodes
Warning: In worst-case problems (like TSP with unit f-increments), IDA* can expand O(N²) nodes versus A*'s O(N). The re-expansion overhead makes it unsuitable when many distinct f-values exist along paths. Use ε-increments carefully — too large loses optimality, too small causes thrashing.
