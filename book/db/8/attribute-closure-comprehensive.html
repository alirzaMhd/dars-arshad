What is Attribute Closure?

The attribute closure of a set of attributes X, denoted X⁺, is the set of all attributes that are functionally determined by X under a given set of FDs F.

Definition
X⁺ = { A | X → A can be derived from F using Armstrong's Axioms }
X⁺ is the set of all attributes A such that X → A is in F⁺.

In other words, if we know the values of attributes in X, we can uniquely determine the values of all attributes in X⁺.

Key Properties

X ⊆ X⁺

Reflexivity

Every attribute determines itself (trivial FD)

X⁺ = (X⁺)⁺

Idempotence

Applying closure twice gives the same result

X ⊆ Y ⇒ X⁺ ⊆ Y⁺

Monotonicity

Larger attribute sets have larger closures

X → Y ⟺ Y ⊆ X⁺

FD Membership

X → Y holds iff Y ⊆ X⁺

Why Attribute Closure Matters

Attribute closure is the single most important computational tool for working with FDs. It enables us to:

  • Check if a given FD X → Y is implied by F
  • Determine if X is a superkey
  • Find candidate keys
  • Determine if two FD sets are equivalent
  • Check normalization conditions (BCNF, 3NF)
Mastering attribute closure is essential for solving normalization problems in exams!

Closure and F⁺

Relationship
F⁺ = { X → Y | X ⊆ R, Y ⊆ X⁺ }
The closure of FD set F can be computed by finding every possible X and its corresponding X⁺.

However, computing F⁺ explicitly is exponential. Attribute closure for specific X is much more efficient.

Algorithm to Compute X⁺

The attribute closure algorithm iteratively adds attributes to the closure set until no more attributes can be added.

Algorithm: Closure(X, F)
result := X
while (changes) do
  for each FD (Y → Z) in F do
    if Y ⊆ result then
      result := result ∪ Z
  end for
end while
return result
Repeatedly apply FDs whose LHS is contained in the current result set.

Step-by-Step Explanation

Initialize

Step 1

Set result = X (the starting attribute set)

Search

Step 2

Find an FD Y → Z where Y ⊆ result and Z ⊈ result

Add

Step 3

Set result = result ∪ Z (add new attributes)

Repeat

Step 4

Continue from Step 2 until no more attributes can be added

Complexity Analysis

PropertyValue
Time ComplexityO(|F| × |R|) in worst case
Space ComplexityO(|R|)
Number of iterationsAt most |R| iterations (each adds at least one attribute)
OptimizationTerminate early when result = R (all attributes)

Optimization Tips

  • If result ever becomes equal to R (all attributes), we can stop immediately — X is a superkey
  • Process FDs in any order — the final result is unique regardless of order
  • Multiple FDs may fire in one iteration — apply all applicable FDs
  • Skip FDs whose RHS is already in result to avoid redundant checks

Example 1: Basic Closure

R(A, B, C, D, E)   F = { A → BC, CD → E, B → D, E → A }

Compute A⁺

Step 1: Initialize → result = {A}

Step 2: Apply A → BC → result = {A, B, C}   (since A ⊆ result)

Step 3: Apply B → D → result = {A, B, C, D}   (since B ⊆ result)

Step 4: Apply CD → E → result = {A, B, C, D, E}   (since CD ⊆ result)

Step 5: No more FDs fire → result = {A, B, C, D, E}

A⁺ = ABCDE (all attributes — so A is a superkey!)

Example 2: Partial Closure

R(A, B, C, D)   F = { AB → C, C → D, D → A }

a) Compute B⁺

Step 1: result = {B}

Step 2: No FD has LHS ⊆ {B}. Stop.

B⁺ = B

b) Compute (BC)⁺

Step 1: result = {B, C}

Step 2: Apply C → D → result = {B, C, D}

Step 3: Apply D → A → result = {A, B, C, D}

Step 4: All attributes reached. Stop.

(BC)⁺ = ABCD — BC is a superkey!

Example 4: Finding Candidate Keys

R(A, B, C, D)   F = { A → BC, BC → D, D → A }

Find all candidate keys.

Compute A⁺: {A} → {A} → A→BC → {A,B,C} → BC→D → {A,B,C,D} ⇒ A⁺ = ABCD

Compute D⁺: {D} → D→A → {D,A} → A→BC → {D,A,B,C} ⇒ D⁺ = ABCD

Compute BC⁺: {B,C} → BC→D → {B,C,D} → D→A → {A,B,C,D} ⇒ BC⁺ = ABCD

Check minimality: B⁺ = B, C⁺ = C (not superkeys)

Candidate keys: {A}, {D}, {B, C}

Example 5: FD Membership Test

R(A, B, C, D, E)   F = { AB → C, C → D, D → E, A → B }

Question: Does AB → E hold?

Compute (AB)⁺:

result = {A, B}

Apply AB → C → result = {A, B, C}

Apply C → D → result = {A, B, C, D}

Apply D → E → result = {A, B, C, D, E}

Since E ⊆ (AB)⁺, we have AB → E. YES, it holds.

Question: Does A → E hold?

Compute A⁺:

result = {A}

Apply A → B → result = {A, B}

Apply AB → C → result = {A, B, C}

Apply C → D → result = {A, B, C, D}

Apply D → E → result = {A, B, C, D, E}

Since E ⊆ A⁺, A → E holds too! YES.

Applications of Attribute Closure

Attribute closure is used for several critical tasks in normalization and database design:

FD Membership

X → Y holds?

Check: Y ⊆ X⁺? If yes, FD is implied.

Superkey Test

Is X a superkey?

Check: X⁺ = R? If yes, X is a superkey.

Candidate Key

Find minimal superkeys

X is a candidate key if X⁺ = R and no proper subset of X has this property.

FD Equivalence

F ≡ G?

Check: For each FD in F, test membership in G and vice versa.

BCNF Check

Is R in BCNF?

For each FD X → Y, check if X is a superkey (X⁺ = R).

3NF Check

Is R in 3NF?

For each FD X → Y, either X is a superkey or each attribute in Y is part of a candidate key.

Use 1: FD Membership Test

To check if X → Y follows from F:

Membership Test
X → Y ∈ F⁺ ⟺ Y ⊆ X⁺
Compute X⁺ using the closure algorithm. If Y is a subset of X⁺, the FD holds.
Example

F = { A → B, AB → C, C → D }

Does A → D hold?

A⁺ = {A} → A→B → {A,B} → AB→C → {A,B,C} → C→D → {A,B,C,D}

D ⊆ A⁺, so A → D holds.

This is more efficient than computing the full F⁺.

Use 2: Superkey Test

To check if X is a superkey:

Superkey Test
X is a superkey ⟺ X⁺ = R
If the closure of X contains all attributes of R, then X is a superkey.
Example

R(A, B, C, D), F = { A → BC, B → D }

Is A a superkey? A⁺ = ABCD. Yes!

Is AB a superkey? (AB)⁺ = ABCD. Yes!

Is AD a superkey? (AD)⁺ = AD → A→BC → ABCD. Yes!

Is B a superkey? B⁺ = BD. No.

Use 3: Finding Candidate Keys

Algorithm to find all candidate keys:

1. For each singleton attribute A: if A⁺ = R, A is a candidate key

2. For each pair of attributes (A,B): if (AB)⁺ = R and no subset is a superkey, AB is a candidate key

3. Continue increasing the size of attribute sets until all attributes that are part of some candidate key are covered

Example

R(A, B, C, D), F = { B → C, C → A, A → B }

Singletons: A⁺ = ABC → ABCD? No (need D). B⁺ = ABC → No. C⁺ = CBA → No. D⁺ = D → No.

Pairs: (AD)⁺ = AD → A→B → ABD → B→C → ABCD. Yes! AD is a candidate key.

(BD)⁺ = BD → B→C → BCD → C→A → ABCD. Yes! BD is a candidate key.

(CD)⁺ = CD → C→A → ACD → A→B → ABCD. Yes! CD is a candidate key.

Candidate keys: {A,D}, {B,D}, {C,D}

Use 4: Checking BCNF

A relation is in BCNF if for every non-trivial FD X → Y, X is a superkey.

BCNF Condition
For each X → Y ∈ F (non-trivial): X⁺ = R
Every determinant must be a superkey.
Example

R(A, B, C), F = { A → B, B → C, C → A }

A⁺ = ABC → superkey. B⁺ = BCA → superkey. C⁺ = CAB → superkey.

R is in BCNF.

Use 5: Checking 3NF

A relation is in 3NF if for every non-trivial FD X → Y, either X is a superkey or each attribute in Y is part of some candidate key.

3NF Condition
∀ X → Y ∈ F: X⁺ = R OR each A ∈ Y is prime
If X is not a superkey, every attribute in Y must be part of a candidate key.
Example

R(A, B, C), F = { AB → C, C → B }

Candidate keys: AB and AC (since C→B, AC→AB, (AC)⁺=ABC)

Check FD C → B: C⁺ = CB ≠ ABC (C is not a superkey), but B is prime (part of candidate keys AB, AC).

R is in 3NF (but not BCNF).
