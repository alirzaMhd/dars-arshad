What is a Functional Dependency?

A Functional Dependency (FD) is a constraint between two sets of attributes in a relation. It is a fundamental concept in database normalization theory introduced by E.F. Codd.

Definition
X → Y
Read as: "X determines Y" or "Y is functionally dependent on X"

If two tuples have the same value for attributes in set X, they must have the same value for attributes in set Y.

Formal Definition
∀ t₁, t₂ ∈ R: t₁[X] = t₂[X] ⇒ t₁[Y] = t₂[Y]
For any two tuples t₁ and t₂ in relation R, if they agree on X, they must agree on Y.

Key Concepts

Determinant

Left-hand side (LHS)

The attribute set X that determines other attributes

Dependent

Right-hand side (RHS)

The attribute set Y that is determined by X

FD Constraint

Semantics of data

Not a logical deduction — it reflects real-world business rules

Key Concept

Normalization basis

FDs form the mathematical foundation of normalization

Real-World Meaning

Functional dependencies are semantic constraints — they reflect real-world rules, not mathematical derivations.

Example: Student Database

FD: StudentID → StudentName

Meaning: Each student ID uniquely identifies a student name. No two students can share the same ID but have different names.

This FD is a statement about the real world: "Student IDs are unique identifiers."

An FD is not a "proof" — it is an assumption about the semantics of the data that must hold for all valid instances of the relation.

Types of Functional Dependencies

Trivial FD

X → Y where Y ⊆ X

Always true, no real constraint

Non-Trivial FD

X → Y where Y ⊈ X

Actually constrains the data

Completely Non-Trivial

X ∩ Y = ∅

No overlap between sides

Full FD

X → Y, no subset X'→Y

Minimal determinant

Partial FD

X → Y where ∃ X' ⊂ X, X' → Y

Causes 2NF issues

Transitive FD

X → Y, Y → Z ⇒ X → Z

Causes 3NF issues

1. Trivial FD

An FD is trivial if the RHS set is a subset of the LHS set.

Trivial FD Condition
X → Y is trivial ⟺ Y ⊆ X
The dependent attributes are already contained in the determinant.
Examples of Trivial FDs

A → A (always holds)

AB → A (holds because A ⊆ AB)

ABC → AB (holds because AB ⊆ ABC)

Trivial FDs are always true and provide no real constraints. They are usually ignored in practice.

2. Non-Trivial FD

An FD is non-trivial if the RHS contains at least one attribute not in the LHS.

Non-Trivial FD Condition
X → Y is non-trivial ⟺ Y ⊈ X
At least one attribute on the RHS is not in the LHS.
Examples of Non-Trivial FDs

A → B (B is not in {A})

StudentID → Name (Name is not in {StudentID})

CourseID → Instructor (Instructor is not in {CourseID})

Completely Non-Trivial
X → Y is completely non-trivial ⟺ X ∩ Y = ∅
No overlap at all between LHS and RHS attributes.

3. Full FD vs Partial FD

Full FD: Y is fully functionally dependent on X if Y cannot be determined by any proper subset of X.

Partial FD: Y is partially functionally dependent on X if there exists a proper subset of X that determines Y.

Full FD Condition
X → Y is full ⟺ (∀X' ⊂ X, X' ↛ Y)
No proper subset of X determines Y.
Partial FD Condition
X → Y is partial ⟺ (∃X' ⊂ X, X' → Y)
Some proper subset of X determines Y.
Example: Full vs Partial

Schema: R(StudentID, CourseID, Grade, Instructor)

FDs:

• {StudentID, CourseID} → Grade — FULL FD (neither StudentID nor CourseID alone determines Grade)

• {StudentID, CourseID} → Instructor — PARTIAL FD (CourseID alone → Instructor)

Partial FDs cause Second Normal Form (2NF) violations. Eliminating partial FDs is the goal of 2NF normalization.

4. Transitive FD

A transitive dependency occurs when X → Y, Y → Z, and thus X → Z, but Y does not determine X.

Example: Transitive FD

Schema: R(StudentID, CollegeID, CollegeName)

FDs:

• StudentID → CollegeID

• CollegeID → CollegeName

• StudentID → CollegeName (transitive)

The transitive FD StudentID → CollegeName causes 3NF violations.

Transitive FDs cause Third Normal Form (3NF) violations. Eliminating transitive dependencies is the goal of 3NF normalization.

Properties of Functional Dependencies

Reflexivity

Trivial dependency

If Y ⊆ X, then X → Y

Augmentation

Add attributes

If X → Y, then XZ → YZ

Transitivity

Chain rule

If X → Y and Y → Z, then X → Z

Union

Combine RHS

If X → Y and X → Z, then X → YZ

Decomposition

Split RHS

If X → YZ, then X → Y and X → Z

Pseudo-Transitivity

Extended chain

If X → Y and YW → Z, then XW → Z

Armstrong's Axioms (Inference Rules)

These are sound and complete — they generate all possible implied FDs and no invalid ones.

Primary Rules (Armstrong's Axioms)
1. Reflexivity   2. Augmentation   3. Transitivity
These three rules are the foundation for reasoning about FDs.
Additional Rules (Derived)
4. Union   5. Decomposition   6. Pseudo-Transitivity
These rules can be proven using the primary axioms.

Soundness and Completeness

Soundness: Every FD derived using Armstrong's Axioms is logically implied by the original set F.

Completeness: Every FD that is logically implied by F can be derived using Armstrong's Axioms.

Closure of F
F⁺ = { X → Y | F ⊨ X → Y }
The set of all FDs implied by F is called the closure of F.
