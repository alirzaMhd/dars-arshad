NONCLUSTERED INDEX

Database Indexing — Complete Guide for 20/20 Exam

What is a Nonclustered Index?

Definition:
A nonclustered index is a separate structure from the data rows that contains the indexed column values and pointers to the actual data rows
Unlike clustered indexes, nonclustered indexes do not affect the physical storage order of data

Think of a nonclustered index like a book's index at the back. The index lists topics alphabetically with page numbers (pointers), but the actual book content is organized differently. To find a topic, you look it up in the index, get the page number, then go to that page to read the content.

KEY DIFFERENCE: A table can have MULTIPLE NONCLUSTERED INDEXES (up to 999 in SQL Server, 64 in MySQL). Each creates a separate structure pointing to the data.

Key Characteristic

• Separate structure from data

• Contains index key + row locator

• Multiple per table allowed

Row Locator

• Clustered table: uses clustered key

• Heap table: uses RID (Row ID)

• Extra indirection step

Nonclustered vs Clustered Index

Feature Clustered Index Nonclustered Index
Physical Order Determines data order No effect on data order
Leaf Level Contains full data rows Contains index keys + pointers
Quantity per Table Maximum 1 Multiple (up to 999)
Insert Performance Slower (maintain order) Faster (append to index)
Range Query Speed Very fast (sequential I/O) Slower (random I/O)
Storage Overhead Only B-tree structure B-tree + row locator storage

B-Tree Structure of Nonclustered Index

The nonclustered index uses a B-tree structure similar to clustered, but the leaf level is fundamentally different:

Root & Intermediate

• Same as clustered

• Contain index key values

• Point to lower level pages

Leaf Pages (Index Only)

• Contains index key values

• Contains row locators (pointers)

• Does NOT contain actual data

Visual: Nonclustered Index Structure
NONCLUSTERED INDEX on Email column: ROOT: [alice@ | bob@ | carol@] | | | INTER: [a-c] [d-f] [g-z] | | | LEAF: [alice@ → RID_101] [bob@ → RID_205] [carol@ → RID_178] [dave@ → RID_312] [eve@ → RID_089] ... (all sorted by Email, but NOT by table order)
Row Locator Types:
Clustered Table: Locator = Clustered Index Key
e.g., if PK=EmployeeID is clustered, nonclustered leaf contains EmployeeID value to find the row
Heap Table: Locator = RID (Row Identifier)
RID = File:Page:Slot number → direct physical address of the row

Key Lookup (Bookmark Lookup)

How Nonclustered Index Finds Data
Step 1: Search nonclustered index B-tree → Find matching index key value Step 2: Get row locator from leaf level → Either RID or clustered key Step 3: Go to actual data page → Key Lookup (if clustered) or RID Lookup (if heap) → Read the full data row TOTAL: 2 separate I/O operations minimum 1. Read nonclustered index pages 2. Read data page
Key Lookup Cost: Each key lookup requires an additional random I/O operation. If your query returns many rows, this can be very expensive. This is why nonclustered indexes are best for selective queries (returning few rows).

SQL Syntax for Nonclustered Index

Create Nonclustered Index:
CREATE NONCLUSTERED INDEX index_name ON table_name (column1, column2, ...);
Creates a nonclustered index (default type if CLUSTERED not specified)
-- Basic syntax CREATE NONCLUSTERED INDEX IX_Employees_Email ON Employees(Email); -- Multiple nonclustered indexes CREATE NONCLUSTERED INDEX IX_Employees_Dept ON Employees(Department); CREATE NONCLUSTERED INDEX IX_Employees_Name ON Employees(LastName, FirstName); -- Composite nonclustered index CREATE NONCLUSTERED INDEX IX_Orders_Cust_Date ON Orders(CustomerID, OrderDate); -- Covering index (INCLUDE) CREATE NONCLUSTERED INDEX IX_Orders_Cust ON Orders(CustomerID) INCLUDE (OrderDate, TotalAmount);
CREATE INDEX without CLUSTERED keyword creates nonclustered index by default in most RDBMS.

Worked Examples

Example 1: Create Nonclustered Index on Email
-- Table with clustered index on EmployeeID (PK) CREATE TABLE Employees ( EmployeeID INT PRIMARY KEY, -- clustered FirstName VARCHAR(50), LastName VARCHAR(50), Email VARCHAR(100), Department VARCHAR(50) ); -- Create nonclustered index on Email CREATE NONCLUSTERED INDEX IX_Emp_Email ON Employees(Email); -- Query using the index SELECT EmployeeID, FirstName, LastName, Email FROM Employees WHERE Email = 'alice@company.com'; -- Execution plan: -- 1. Index Seek on IX_Emp_Email → find Alice -- 2. Key Lookup on PK → get FirstName, LastName -- Total: 2 I/O operations
Example 2: Covering Index (Avoid Key Lookup)
-- Nonclustered index INCLUDES extra columns CREATE NONCLUSTERED INDEX IX_Emp_Email_Covering ON Employees(Email) INCLUDE (FirstName, LastName); -- Same query now uses covering index SELECT EmployeeID, FirstName, LastName, Email FROM Employees WHERE Email = 'alice@company.com'; -- Execution plan: -- Index Seek on IX_Emp_Email_Covering → done! -- All needed columns are in the index leaf level -- Total: 1 I/O operation (no key lookup!)
Example 3: Composite Nonclustered Index
-- Composite index on two columns CREATE NONCLUSTERED INDEX IX_Emp_Dept_Name ON Employees(Department, LastName); -- Query 1: Uses full index prefix SELECT * FROM Employees WHERE Department = 'CS' AND LastName = 'Smith'; -- Index Seek → efficient -- Query 2: Uses only first column SELECT * FROM Employees WHERE Department = 'CS'; -- Index Seek → still efficient (uses prefix) -- Query 3: Cannot use index effectively SELECT * FROM Employees WHERE LastName = 'Smith'; -- Index Scan → must scan entire index -- (LastName is not the first column)

Performance Analysis

Operation Time Complexity Description
Point Query O(log_b n + 1) B-tree traversal + 1 key lookup
Range Scan O(log_b n + k × L) Find start + k key lookups (L = lookup cost)
Insert O(log_b n) Add to index + add to heap/clustered
Delete O(log_b n) Remove from index + remove from heap/clustered
Update (non-key) O(1) No index change needed

Advantages

• Multiple indexes per table

• Faster inserts/updates than clustered

• Good for point queries

• Covering indexes eliminate lookups

Disadvantages

• Key lookups add overhead

• Range queries slower than clustered

• Extra storage for each index

• More indexes = slower writes

Covering Index Optimization

Why Covering Indexes Matter
Without Covering Index: Query: SELECT Name, Email FROM Users WHERE Age > 25 Plan: Index Scan on IX_Age → get RIDs For each RID: RID Lookup → read full row Filter: keep Name, Email Cost: O(n) lookups → SLOW! With Covering Index: CREATE INDEX IX_Age_Cover ON Users(Age) INCLUDE (Name, Email) Plan: Index Scan on IX_Age_Cover → read Name, Email directly No lookups needed! Cost: O(n) index reads → FAST! Speed improvement: 5-50x for large result sets
Covering Index Rule: Include all columns referenced in SELECT, WHERE, and JOIN clauses in the INCLUDE list. This eliminates key lookups entirely.

When to Use Nonclustered Index

Decision Tree:

1. Do you need to query on non-PK columns? → Yes → Create nonclustered index

2. Are queries returning few rows (point queries)? → Yes → Nonclustered index ideal

3. Do you need multiple search paths? → Yes → Create multiple nonclustered indexes

4. Is the table write-heavy? → Yes → Nonclustered faster for writes

USE Nonclustered When:

• Point queries on specific values

• Foreign key columns

• Frequently searched non-PK columns

• Need multiple index paths

AVOID Nonclustered When:

• Range queries on large result sets

• Very small tables (< 1000 rows)

• Columns rarely used in WHERE

• Too many indexes already
