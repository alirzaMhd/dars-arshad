COMPOSITE SEARCH KEY

Database Indexing — Complete Guide for 20/20 Exam

What is a Composite Search Key?

A composite search key (also called a compound key) is an index built on two or more columns of a table. Instead of indexing a single column, the index sorts rows by the first column first, then by the second column within each group of the first, and so on.

Definition:
Key = (Column₁, Column₂, ..., Columnₙ)
An ordered tuple of columns. The sort order is lexicographic: Column₁ is the primary sort key, Column₂ is secondary, etc.
Example 1 — Single vs Composite Key

Single-key index: INDEX(Name) — sorts by Name only.

Composite index: INDEX(Name, Age) — sorts by Name first, then by Age within matching Names.

Single Key INDEX(Name): Composite Key INDEX(Name, Age): ┌──────────────┐ ┌──────────────────────────────┐ │ Adams (25) │ │ Adams (25) │ │ Adams (30) │ │ Adams (30) │ │ Brown (22) │ │ Brown (22) │ │ Brown (28) │ │ Brown (28) │ │ Smith (20) │ │ Smith (20) │ │ Smith (35) │ │ Smith (35) │ └──────────────┘ └──────────────────────────────┘

Multi-Column Indexing

When you create an index on (Name, Age, Salary), the database builds a sorted structure that respects the column order. The first column provides the widest discrimination; each subsequent column refines the ordering.

Sort Order Principle:
Sort by Col₁ → break ties with Col₂ → break ties with Col₃ → ...
This is analogous to sorting a phone book by Last Name, then First Name.

Key Principle

• Column order matters

• (A, B) ≠ (B, A) as indexes

• Each column refines the sort

When to Use

• Queries filter on leading columns

• Multi-column WHERE clauses

• Covering index scenarios

⚠ Common Exam Pitfall: An index on (Name, Age) can serve queries that filter on Name alone, or Name + Age, but cannot efficiently serve queries that filter only on Age (without Name). The leading column rule is strict.

Composite Keys in B+ Trees

In a B+ Tree, composite keys are stored as ordered tuples. Each internal node contains key ranges that reflect the multi-column ordering. Leaf nodes store the actual data entries (or pointers) in composite-key sorted order.

B+ Tree Leaf Order (Composite Key):
(K₁ᵃ, K₂ᵃ) < (K₁ᵇ, K₂ᵇ) ⟺ K₁ᵃ < K₁ᵇ OR (K₁ᵃ = K₁ᵇ AND K₂ᵃ < K₂ᵇ)
Lexicographic comparison: compare first column; if equal, compare second column.
Example 3 — B+ Tree with INDEX(Name, Age)
┌─────────────────────────────┐ │ (Bob,28) | (Smith,25)│ ← Internal node └──────┬───────────────┬────┘ ┌───────────────┘ └───────────────┐ ┌──────────┴──────────┐ ┌────────────────┴──────────┐ │ Alice,25 → ptr │ │ Bob,30 → ptr │ │ Alice,30 → ptr │ │ Carol,27 → ptr │ │ Bob,25 → ptr │ │ Smith,20 → ptr │ └─────────────────────┘ │ Smith,35 → ptr │ Leaf Node 1 (lower half) └───────────────────────────┘ Leaf Node 2 (upper half) Leaf nodes are linked: Leaf1 → Leaf2 (for range scans)
Example 4 — Three-Column Composite Key B+ Tree

For INDEX(Name, Age, Salary), the internal node splits consider all three columns in order:

Internal: (Bob,28,6800) | (Smith,20,4500) Leaf 1: Leaf 2: ┌─────────────────────┐ ┌───────────────────────────┐ │ Alice,25,5000 → ptr │ │ Bob,30,6800 → ptr │ │ Alice,32,7500 → ptr │ │ Carol,27,5500 → ptr │ │ Bob,25,4200 → ptr │ │ Smith,20,4500 → ptr │ └─────────────────────┘ │ Smith,35,8200 → ptr │ └───────────────────────────┘

Notice: "Bob,25" comes before "Bob,30" (Age breaks tie). "Smith,20" comes before "Smith,35".

⚠ Internal Node Key Size: With composite keys, internal nodes must store full key prefixes. A 3-column composite index may have larger internal nodes than a single-column index, potentially increasing tree height and I/O cost.

Why Tree+ Structure?

The B+ Tree is ideal for composite keys because:

Sorted Order

Leaf-level linked list preserves composite-key order, enabling efficient range scans on leading columns.

Prefix Search

Traversing the tree with only the first column is valid — just compare on the leading prefix.

Balanced Height

Leaf nodes always at same depth ensures O(log n) lookup regardless of key dimensionality.

Range Scan

After locating the start of a range via tree traversal, follow leaf pointers — no need to re-traverse the tree.

Query Types on Composite Indexes

Not all queries benefit equally from a composite index. Understanding which queries can use the index is critical.

Query Type WHERE Clause Uses Index? Efficiency
Full Composite Lookup WHERE Name='Bob' AND Age=25 Yes — full key match FAST
Prefix Lookup WHERE Name='Bob' Yes — leading column only FAST
Left-Prefix + Range WHERE Name='Bob' AND Age>25 Yes — prefix + range on next col FAST
Non-Leading Column WHERE Age=25 No — skips leading column SLOW
Gap in Columns WHERE Name='Bob' AND Salary=5000 Partial — uses Name only MEDIUM
⚠ Leading Column Rule: For INDEX(A, B, C):
• WHERE A=... ✓ uses index
• WHERE A=... AND B=... ✓ uses index
• WHERE A=... AND B=... AND C=... ✓ full index
• WHERE B=... ✗ index skipped
• WHERE B=... AND C=... ✗ index skipped
• WHERE A=... AND C=... ⚠ only A portion used

SQL Syntax for Composite Indexes

-- Create composite index
CREATE INDEX idx_name_age ON employees(Name, Age);

-- Composite primary key
CREATE TABLE enrollments (
  student_id INT,
  course_id INT,
  enrollment_date DATE,
  PRIMARY KEY (student_id, course_id)
);

-- Three-column composite index
CREATE INDEX idx_name_age_salary ON employees(Name, Age, Salary);

-- Composite UNIQUE constraint
ALTER TABLE employees
  ADD CONSTRAINT uq_name_dept UNIQUE (Name, Department);
Example 5 — SQL Query Patterns

Given INDEX(Name, Age, Salary) on employees:

-- ✅ Full composite: uses full index efficiently
SELECT * FROM employees WHERE Name='Bob' AND Age=25 AND Salary=5000;

-- ✅ Prefix lookup: uses Name portion of index
SELECT * FROM employees WHERE Name='Bob';

-- ✅ Prefix + range: Name exact, Age range
SELECT * FROM employees WHERE Name='Bob' AND Age BETWEEN 25 AND 30;

-- ❌ Non-leading: cannot use composite index
SELECT * FROM employees WHERE Age=25;

-- ⚠ Partial: only Name portion used, Salary filter is post-index
SELECT * FROM employees WHERE Name='Bob' AND Salary=5000;

Performance Considerations

Index Selectivity:
Selectivity = (Number of distinct key values) / (Total number of rows)
Higher selectivity means the index is more effective at narrowing down results. Composite keys often have higher selectivity than individual columns.

Write Overhead

• Each INSERT/UPDATE must maintain all indexed columns

• More columns = more write cost

• Balance read speed vs write penalty

Storage Cost

• Composite index stores full key in every B+ Tree node

• Larger keys = fewer entries per page

• More disk pages = more I/O

Column Order Matters — Performance Comparison
Query PatternINDEX(Name,Age)INDEX(Age,Name)

WHERE Name='X' AND Age=25FAST ✓FAST ✓
WHERE Name='X' AND Age>25FAST ✓MEDIUM ⚠

The index that best matches your most frequent query pattern should have the most selective (discriminating) column first.

⚠ Rule of Thumb for Column Order:
1. Put the column used in equality conditions first.
2. Among equality columns, put the most selective one first.
3. Put range-scan columns after all equality columns.
4. Consider ORDER BY — the index column order should match the sort order.

Covering Index

A covering index includes all columns needed by a query. When the index "covers" the query, the database never needs to access the actual table — all data comes from the index.

Covering Index Example:
INDEX(Name, Age, Salary) covers: SELECT Name, Age, Salary FROM employees WHERE Name='Bob'
All requested columns exist in the index → no table lookup needed → single index scan.
Covering Index Benefit
MetricWithout Covering IndexWith Covering Index
Index scan1 (find row)1 (find row)
Table lookup1 per row (random I/O)0
Total I/O for 1000 rows~1001 page reads~5-10 page reads

Worked Example 1 — Full Composite Lookup

Given: INDEX(Name, Age) on employees table with 10,000 rows.

Query: SELECT * FROM employees WHERE Name='Smith' AND Age=30;

Steps:
1. Root: compare ('Smith',30) with root keys → go right
2. Internal: compare with (Bob,28), (Smith,25) → go right of (Smith,25)
3. Leaf: scan to ('Smith',30) → follow pointer → fetch row
Total I/O: ~3 page reads (tree height). No full scan needed.

Performance

Time: O(log n)

Space: O(k) per key

Result

Rows scanned: 1-2

Pages read: ~3

Worked Example 2 — Prefix Lookup

Same index: INDEX(Name, Age). Query: SELECT * FROM employees WHERE Name='Smith';

Steps:
1. Root: compare 'Smith' with root keys → go right
2. Internal: compare with (Bob,28), (Smith,25) → go right of (Smith,25)
3. Leaf: scan from first 'Smith' entry → follow leaf pointers until Name ≠ 'Smith'
Uses only the Name column. Scans all Smith entries in leaf chain.
Result

If there are 50 employees named 'Smith': pages read ≈ 3 (tree) + 2 (leaf scan) = ~5 pages.

Much faster than full table scan (10,000 pages).

Worked Example 3 — Non-Leading Column (Cannot Use Index)

Index: INDEX(Name, Age). Query: SELECT * FROM employees WHERE Age=25;

Why Index Fails:
B+ Tree is sorted by (Name, Age), not by Age alone.
Age=25 could be anywhere in the tree — Alice,25 and Bob,25 are far apart. Database must do a full table scan or use a different index.
⚠ Exam Answer: The composite index (Name, Age) cannot be used for a query that filters only on Age. The database must scan all leaf nodes or use another index on Age.

Worked Example 4 — Range on Second Column

Index: INDEX(Name, Age). Query: SELECT * FROM employees WHERE Name='Smith' AND Age BETWEEN 25 AND 30;

Steps:
1. Navigate to first 'Smith' entry via tree
2. Scan leaf: ('Smith',25), ('Smith',26), ('Smith',27), ('Smith',28), ('Smith',29), ('Smith',30)
3. Stop at ('Smith',31) or next non-Smith entry
The index handles the equality on Name and the range on Age efficiently.
Result

Pages read: ~4-5 (tree + partial leaf scan). Compare to full scan: 10,000 pages.

Worked Example 5 — Ordering by Composite Key

Index: INDEX(Name, Age). Query: SELECT * FROM employees ORDER BY Name, Age LIMIT 10;

Steps:
1. Go to leftmost leaf node
2. Read first 10 entries — they are already sorted by Name, Age!
3. Return immediately — no sort operation needed
The composite index provides the ORDER BY for free since the data is already in that order at the leaf level.

Without Index

1. Full table scan

2. Sort all rows by Name, Age

3. Return first 10

Time: O(n log n)

With Composite Index

1. Navigate to first leaf

2. Read 10 entries

3. Done!

Time: O(log n + 10)

Quick Reference — Composite Search Key

  • Definition: Index on 2+ columns, sorted lexicographically by column order
  • Key Rule: (A,B) ≠ (B,A) — column order matters!
  • Leading Column: First column must appear in WHERE to use index
  • Full Key Match: WHERE A=... AND B=... → fastest lookup O(log n)
  • Prefix Match: WHERE A=... → uses first column only
  • Range on 2nd Column: WHERE A=... AND B>... → works if A is equality
  • Non-Leading Query: WHERE B=... → index NOT used
  • Covering Index: Include all SELECT columns → no table access needed
  • Column Order Strategy: Equality columns first → most selective first → range columns → ORDER BY columns
  • Write Cost: More columns = higher INSERT/UPDATE overhead
  • Storage: Composite keys are larger → fewer entries per B+ Tree page
  • B+ Tree: Leaf linked list preserves composite order → efficient range scans
