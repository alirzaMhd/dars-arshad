HASH INDEX

Database Indexing — Complete Guide for 20/20 Exam

What is a Hash Index?

Definition:
A hash index uses a hash function to map index key values directly to bucket addresses, enabling O(1) average-case point queries
Instead of traversing a B-tree, the index computes where the data should be located

Imagine a row of mailboxes numbered 0-9. When you get mail for "Alice", you hash the name "Alice" to get a number (say 3), and go directly to mailbox #3. No searching needed — you know exactly where to look. That's how hash indexes work.

CRITICAL LIMITATION: Hash indexes are ONLY for exact match queries. They cannot support range queries (BETWEEN, >, <), ORDER BY, or JOIN operations efficiently.

Key Characteristic

• Uses hash function h(k)

• Direct bucket access

• No ordering maintained

Best Use Case

• Point queries (exact match)

• Equality comparisons (=)

• High-cardinality columns

Hash Index vs B-Tree Index

Feature Hash Index B-Tree Index
Point Query O(1) average O(log n)
Range Query NOT SUPPORTED O(log n + k)
ORDER BY NOT SUPPORTED Natural order
Partial Match NOT SUPPORTED Prefix matching
Storage Buckets + overflow chains B-tree pages
Worst Case O(n) all in one bucket O(log n) balanced

Hash Function Basics

Basic Hash Function:
h(k) = k mod m
Where k = key value, m = number of buckets (table size)
Example 1: Simple Modulo Hashing
Table size: m = 10 buckets (0-9) Keys to insert: 25, 37, 48, 16, 29, 55 h(25) = 25 mod 10 = 5 → Bucket 5 h(37) = 37 mod 10 = 7 → Bucket 7 h(48) = 48 mod 10 = 8 → Bucket 8 h(16) = 16 mod 10 = 6 → Bucket 6 h(29) = 29 mod 10 = 9 → Bucket 9 h(55) = 55 mod 10 = 5 → Bucket 5 ← COLLISION!
Good Hash Function Properties:
1. Deterministic: same key → same hash
2. Uniform: keys distribute evenly across buckets
3. Fast: O(1) computation
4. Minimize collisions: different keys → different buckets

Common Hash Functions

Division Method

h(k) = k mod m

• Simplest method

• m should be prime

• Avoid powers of 2

Multiplication Method

h(k) = ⌊m(kA mod 1)⌋

• A ≈ 0.618 (golden ratio)

• Works for any m

• Less sensitive to pattern

Mid-Square Method

h(k) = middle digits of k²

• Square the key

• Extract middle digits

• Good distribution

Example 2: Choosing Table Size
BAD choices for m (table size): - m = 10 (power of 10): multiples of 10 all go to bucket 0 - m = 16 (power of 2): only looks at last 4 bits - m = 100: keys ending in 00, 100, 200... all collide GOOD choices for m: - m = 11 (prime): better distribution - m = 13 (prime): even better - m = 7 (prime): small but effective Rule: Choose m as a prime number not close to powers of 2 or 10

Collision Resolution

When two different keys hash to the same bucket, we have a collision. There are several strategies to handle this:

Method 1: Separate Chaining (Open Hashing)
Each bucket contains a linked list of all keys that hash to it
Simple but uses extra memory for pointers
Separate Chaining Example
Hash function: h(k) = k mod 10 Insert: 25, 37, 48, 16, 29, 55 Bucket 0: [empty] Bucket 1: [empty] Bucket 2: [empty] Bucket 3: [empty] Bucket 4: [empty] Bucket 5: [25] → [55] ← chain Bucket 6: [16] Bucket 7: [37] Bucket 8: [48] Bucket 9: [29] To find 55: h(55)=5, go to bucket 5, traverse chain
Method 2: Open Addressing (Closed Hashing)
If bucket occupied, probe next bucket until empty one found
No extra pointers, but clustering can occur
Linear Probing Example
Hash function: h(k) = k mod 10 Insert: 25, 37, 48, 16, 29, 55 Step 1: h(25)=5, bucket 5 empty → insert 25 Step 2: h(37)=7, bucket 7 empty → insert 37 Step 3: h(48)=8, bucket 8 empty → insert 48 Step 4: h(16)=6, bucket 6 empty → insert 16 Step 5: h(29)=9, bucket 9 empty → insert 29 Step 6: h(55)=5, bucket 5 FULL → probe 6, FULL → probe 7, FULL → probe 8, FULL → probe 9, FULL → probe 0, EMPTY → insert 55 Problem: Primary clustering (consecutive occupied buckets)
Method 3: Double Hashing
h(k, i) = (h₁(k) + i × h₂(k)) mod m
Second hash function determines probe step size, reduces clustering

Separate Chaining

• Simple to implement

• No clustering problem

• Extra pointer storage

• Cache unfriendly

Open Addressing

• Better cache performance

• No extra pointers

• Clustering issues

• Must limit load factor

Load Factor

Load Factor Formula:
α = n / m
Where n = number of entries, m = number of buckets
Load Factor Impact
Example: 8 entries in 10 buckets α = 8 / 10 = 0.8 (80% full) Separate Chaining: - Average chain length = α = 0.8 - Average search: O(1 + α) = O(1.8) Open Addressing: - Average probes = 1/(1-α) = 1/(1-0.8) = 5 - Average search: O(1/(1-α)) = O(5) Keep α < 0.7 for good performance! When α > 0.75, resize hash table (rehash)
Rehashing: When load factor exceeds threshold (typically 0.75), create new table with double size, re-insert all entries. This is expensive but maintains O(1) performance.

SQL Syntax for Hash Index

MySQL Hash Index:
CREATE TABLE t (id INT, name VARCHAR(50), INDEX USING HASH (name)) ENGINE=MEMORY;
Hash indexes only supported in MEMORY engine (MySQL) or InnoDB adaptive hash index
-- MySQL MEMORY engine with hash index CREATE TABLE user_sessions ( session_id VARCHAR(64), user_id INT, created_at TIMESTAMP, INDEX USING HASH (session_id) ) ENGINE=MEMORY; -- PostgreSQL hash index CREATE INDEX idx_users_email_hash ON users USING hash (email); -- SQL Server: No direct hash index syntax -- But you can create indexed view with hash bucket
Database Support: Hash indexes have limited support. MySQL MEMORY engine, PostgreSQL 10+, and some NoSQL databases support them. SQL Server and Oracle use B-tree by default.

Worked Examples

Example 1: Session Lookup Table
-- Hash index perfect for session lookups CREATE TABLE sessions ( token VARCHAR(128) PRIMARY KEY, user_id INT NOT NULL, expires_at TIMESTAMP, INDEX USING HASH (token) ) ENGINE=MEMORY; -- Query: Exact match on session token SELECT user_id, expires_at FROM sessions WHERE token = 'abc123xyz789...'; -- Performance: O(1) average -- Hash(token) → direct bucket access -- No B-tree traversal needed
Example 2: When Hash Index Fails
-- Hash index on price column CREATE TABLE products ( product_id INT, name VARCHAR(100), price DECIMAL(10,2), INDEX USING HASH (price) ) ENGINE=MEMORY; -- Query 1: Works (exact match) SELECT * FROM products WHERE price = 29.99; -- O(1) ✓ -- Query 2: FAILS (range query) SELECT * FROM products WHERE price BETWEEN 20 AND 50; -- Hash index CANNOT help! -- Must scan entire table -- Query 3: FAILS (order by) SELECT * FROM products ORDER BY price; -- Hash index has no ordering! -- Must sort separately
Example 3: Hash Index with Collisions
-- Hash function: h(k) = k mod 10 -- Inserting user IDs: 101, 201, 301, 401, 501 h(101) = 101 mod 10 = 1 → Bucket 1 h(201) = 201 mod 10 = 1 → Bucket 1 (collision!) h(301) = 301 mod 10 = 1 → Bucket 1 (collision!) h(401) = 401 mod 10 = 1 → Bucket 1 (collision!) h(501) = 501 mod 10 = 1 → Bucket 1 (collision!) All keys collide! This is because: - All keys end in same digit - Hash function is poor for this data pattern Better hash function: h(k) = (k × 7 + 13) mod 10 h(101) = (101×7+13) mod 10 = 720 mod 10 = 0 h(201) = (201×7+13) mod 10 = 1420 mod 10 = 0 h(301) = (301×7+13) mod 10 = 2120 mod 10 = 0 Still collides! Need better distribution.

When to Use Hash Index

Decision Tree:

1. Do you ONLY need exact match queries (=)? → Yes → Hash index possible

2. Do you need range queries (BETWEEN, >, <)? → Yes → DO NOT use hash index

3. Is the column high-cardinality (many unique values)? → Yes → Hash index efficient

4. Is the table read-heavy with point lookups? → Yes → Hash index ideal

USE Hash Index When:

• Equality-only queries

• Session/token lookups

• Cache/mapping tables

• High-cardinality columns

AVOID Hash Index When:

• Any range queries needed

• ORDER BY required

• Partial matching (LIKE 'abc%')

• Low-cardinality columns
