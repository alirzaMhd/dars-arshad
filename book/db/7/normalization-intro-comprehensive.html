What is Normalization?

Normalization is a systematic process of organizing data in a database to minimize redundancy (duplication) and avoid anomalies (update, insert, delete problems). It involves decomposing tables into smaller, well-structured tables and defining relationships between them.

The process was first proposed by Edgar F. Codd in 1970 as part of the relational model. Normalization theory has since evolved through multiple "normal forms" (NF), each adding stricter constraints on table structure.

Why Normalization Matters

Without normalization, the same data is stored in multiple places — leading to inconsistencies, wasted storage, and complex maintenance. A normalized database is cleaner, faster to query correctly, and easier to update.

Core Objective of Normalization
Eliminate Redundancy → Eliminate Anomalies → Maintain Data Integrity
Each normal form addresses a specific class of redundancy and its associated anomalies.

Historical Context: Codd's Contribution

1970 — Codd's Paper

• "A Relational Model of Data for Large Shared Data Banks"

• Introduced 1NF, 2NF, 3NF

• Foundation of relational databases

1974 — Boyce-Codd

• Raymond Boyce & Edgar Codd

• Introduced BCNF (stronger than 3NF)

• Handles certain anomalies 3NF misses

Later Normal Forms

• 4NF (Multi-valued Dependencies)

• 5NF (Join Dependencies)

• DKNF (Domain-Key Normal Form)

The Normal Forms Hierarchy

Inclusion Property
1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF ⊃ 4NF ⊃ 5NF
Each normal form is a subset of the previous one. If a table satisfies 3NF, it automatically satisfies 2NF and 1NF.
Normal FormRequirementEliminates
1NFAtomic values, no repeating groupsNon-atomic data
2NF1NF + no partial dependenciesPartial dependency anomalies
3NF2NF + no transitive dependenciesTransitive dependency anomalies
BCNFEvery determinant is a candidate keyRemaining anomalies from 3NF
4NFNo multi-valued dependenciesMulti-valued dependency anomalies
5NFNo join dependenciesJoin dependency anomalies

Key Terminology

TermDefinition
Functional Dependency (FD)X → Y means X uniquely determines Y. If two rows have same X, they must have same Y.
Candidate KeyA minimal set of attributes that uniquely identifies each row.
Primary KeyOne chosen candidate key used to identify rows.
Prime AttributeAn attribute that is part of any candidate key.
Non-Prime AttributeAn attribute that is not part of any candidate key.
DeterminantThe left-hand side of a functional dependency (X in X → Y).
DecompositionSplitting a table into multiple tables to remove redundancy.
Exam Tip

Normalization questions are common in database exams. Always identify the functional dependencies first, then check which normal form is violated, and apply the correct decomposition algorithm.

What Are Anomalies?

Anomalies are problems that arise in poorly designed databases when performing insert, update, or delete operations. They are caused by data redundancy — the same information stored in multiple places.

Insert Anomaly

● Cannot insert data without also inserting unrelated data

● NULL values are forced into columns

Update Anomaly

● Same fact stored in multiple rows

● Must update ALL occurrences

Delete Anomaly

● Deleting data also deletes unrelated data

● Unintentional data loss

Notice: "Ali" appears twice (repeating student info), "Dr. Ahmadi" appears three times (repeating instructor info). This redundancy causes all three types of anomalies.

Insert Anomaly

Problem: Cannot insert a new course without a student

Suppose we want to add a new course "Networks" (CSE501) taught by Dr. Mohammadi. To insert this course, we must also provide a StudentID — because StudentID is part of the primary key.

-- We cannot do this: INSERT INTO Student_Course (CourseID, CourseName, Instructor) VALUES ('CSE501', 'Networks', 'Dr. Mohammadi'); -- ERROR: StudentID is NULL and part of PK! -- We are forced to use a dummy student: INSERT INTO Student_Course (StudentID, StudentName, CourseID, CourseName, Instructor) VALUES (NULL, NULL, 'CSE501', 'Networks', 'Dr. Mohammadi'); -- This creates NULL problems and wastes space

Update Anomaly

Problem: Changing a fact requires multiple updates

If Dr. Ahmadi changes her name to Dr. Ahmadi-Fard, we must update ALL rows where she appears as instructor:

-- Must update 3 rows (rows 1, 3, 6 in our table) UPDATE Student_Course SET Instructor = 'Dr. Ahmadi-Fard' WHERE Instructor = 'Dr. Ahmadi'; -- If we miss even one row → INCONSISTENCY!

This leads to update anomalies: some rows say "Dr. Ahmadi" while others say "Dr. Ahmadi-Fard". Which is correct?

Delete Anomaly

Problem: Deleting data removes unintended information

If student Reza (103) drops the only course he is taking (OS), deleting that row also deletes the fact that Dr. Rezaei teaches OS:

-- Delete Reza's enrollment: DELETE FROM Student_Course WHERE StudentID = 103; -- Now we LOST: Dr. Rezaei teaches OS! -- Even if we need this info, it's gone.

The instructor-course information is permanently lost — even though it has nothing to do with the deletion intent.

What is Data Redundancy?

Data redundancy means the same piece of data is stored in multiple places within the database. It is the root cause of all three types of anomalies (insert, update, delete).

Redundancy → Problems
Redundancy → Inconsistency + Wasted Storage + Anomalies
Normalization breaks tables apart to ensure each fact is stored exactly once.

Types of Redundancy

Direct Redundancy

• Same column value repeated across rows

• Example: "Ali" repeated for each course

• Fixed by 2NF (remove partial dependencies)

Transitive Redundancy

• Value determined through a chain

• Example: Instructor depends on CourseID, not directly on StudentID

• Fixed by 3NF (remove transitive dependencies)

Non-Atomic Redundancy

• Multiple values in a single cell

• Example: "DBMS, OS" in one cell

• Fixed by 1NF (atomic values)

Example: Identifying Redundancy

Look at the Student_Course table again:

Redundancy: StudentName is repeated for each course a student takes. Instructor and CourseName are repeated for each enrollment in that course.

Measuring Redundancy

Redundancy Ratio
RR = Total Rows / Unique Facts
If a fact appears N times, its redundancy ratio is N. Ideal = 1 (each fact stored once).
Redundancy Calculation Example

In our table, "Ali" appears 2 times but is the same person: RR = 2.

"Dr. Ahmadi" appears 3 times: RR = 3.

"DBMS" appears 3 times: RR = 3.

After normalization, each appears exactly once (RR = 1).

Quick Summary

Normalization is the process of organizing data to reduce redundancy and eliminate anomalies. The normal forms form a hierarchy where each level addresses a specific problem:

Normal FormFixesRule
1NFNon-atomic data, repeating groupsEach cell holds a single value
2NFPartial dependenciesAll non-key attributes depend on the full PK
3NFTransitive dependenciesNo non-key attribute depends on another non-key
BCNFNon-key determinantsEvery determinant must be a candidate key

Three Types of Anomalies

1. Insert Anomaly

Cannot insert without unrelated data being present. Caused by combining independent facts in one table.

2. Update Anomaly

Same fact appears in multiple rows. Changing it requires updating all occurrences.

3. Delete Anomaly

Deleting a row removes unrelated facts that should be preserved independently.

Key Takeaways

  • Redundancy is the root cause of all anomalies — normalization reduces redundancy
  • Functional Dependencies (FDs) are the mathematical foundation of normalization
  • Decomposition (splitting tables) is the primary tool for normalization
  • Lossless join and dependency preservation are critical properties of a good decomposition
  • Normalization is a top-down design approach — start with 1NF, progress upward
