What is BCNF?

Boyce-Codd Normal Form (BCNF) is a stricter version of 3NF. A table is in BCNF if and only if:

  • It is in 3NF
  • For every non-trivial functional dependency X → Y, X must be a superkey
BCNF Definition (Formal)
∀ (X → Y) ∈ F+, if Y ⊄ X, then X must be a superkey of R
Every determinant (left-hand side of an FD) must be a superkey. No exceptions.
BCNF is the Strongest Practical Normal Form

BCNF eliminates all redundancy based on functional dependencies. It is stronger than 3NF: every BCNF relation is in 3NF, but not every 3NF relation is in BCNF. For most practical database designs, BCNF is the target.

Key Insight: Determinant Must Be a Superkey

The fundamental rule of BCNF: Every determinant must be a candidate key.

Superkey

• A set of attributes that uniquely identifies all rows

• May contain extra attributes beyond a candidate key

• In BCNF, every LHS of every FD must be a superkey

Candidate Key

• A minimal superkey (no proper subset is a superkey)

• There can be multiple candidate keys

• BCNF: each FD's LHS must contain at least one candidate key

BCNF Violation

• An FD where the LHS is NOT a superkey

• Example: A → B where A is not a key

• Even if the relation satisfies 3NF!

BCNF Violation Example

Table: Student_Grade_Advisor (3NF but NOT BCNF)
StudentIDCourseIDGradeAdvisor

FDs: (StudentID, CourseID) → Grade, Advisor; Advisor → StudentID

Problem: Advisor → StudentID is a valid FD but Advisor is NOT a superkey (an advisor advises many students). This violates BCNF even though it satisfies 3NF (all attributes are prime since (StudentID, CourseID) and (Advisor, CourseID) are both keys).

Case Where 3NF Satisfies but BCNF Doesn't

Classic Example: R(A, B, C) with FDs {AB → C, C → B}
// Candidate keys: AB and AC // Prime attributes: A, B, C (all three are prime!) // Check 3NF: // AB → C: AB is a superkey → OK // C → B: C is not a superkey, BUT B is prime → OK for 3NF // R is in 3NF but NOT in BCNF! // Check BCNF: // C → B: C is NOT a superkey → VIOLATES BCNF // To achieve BCNF, we must decompose: // R1(A, C) and R2(C, B) or R1(A, B) and R2(C, B)

This is the textbook example of a relation in 3NF but not BCNF. Since all attributes are prime, 3NF is satisfied even with C → B. But BCNF requires C to be a superkey, which it is not.

Exam Tip: 3NF vs BCNF

To check if a 3NF relation is also BCNF: look for any FD where the LHS is not a superkey. If all FDs have superkey LHS, it is BCNF. If some FD has a non-superkey LHS but its RHS is a prime attribute, it is 3NF but not BCNF.

BCNF Decomposition Algorithm

The BCNF decomposition algorithm iteratively splits relations that violate BCNF until all relations satisfy BCNF.

Algorithm BCNFDecompose(R, FDs): // Input: Relation R, Set of FDs F // Output: Set of relations in BCNF result = {R} while ∃ Ri ∈ result that is not in BCNF: // Find a violating FD X → Y in Ri // X → Y violates BCNF if X is not a superkey of Ri violatingFD = findViolatingFD(Ri, FDs) // Decompose Ri into two relations R1 = (X ∪ Y) // Create relation from the violating FD R2 = (Ri − Y) // Remove only the dependent attributes // Note: R2 keeps X (the determinant) for rejoining result.remove(Ri) result.add(R1) result.add(R2) return result

Algorithm Walkthrough

BCNF Decomposition Step-by-Step
// Given: R(A, B, C, D) // FDs: AB → C, C → D, D → B // Candidate key: AB, AC, AD // Iteration 1: Check R(A, B, C, D) // C → D: C is not a superkey → VIOLATES BCNF! // Decompose: // R1(C, D) ← from violating FD C → D // R2(A, B, C) ← R - D + C (keep C for joining) // Iteration 2: Check R1(C, D) // C → D: C is a superkey of R1 → OK // R1 is in BCNF ✓ // Iteration 3: Check R2(A, B, C) // AB → C: AB is a superkey → OK // No other FDs violate BCNF // R2 is in BCNF ✓ // Final BCNF decomposition: R1(C, D), R2(A, B, C)

Algorithm Example with Non-Deterministic Choice

BCNF Decomposition May Have Multiple Valid Results
// Given: R(StudentID, Subject, Teacher) // FDs: (StudentID, Subject) → Teacher (PK) // Teacher → Subject // Violating FD: Teacher → Subject // Decompose: // Option 1: // R1(Teacher, Subject) Teacher is key here // R2(StudentID, Teacher) (StudentID, Teacher) is key here // Losses: (StudentID, Subject) → Teacher // Option 2 (if we choose differently): // R1(Teacher, Subject) Teacher is key here // R2(StudentID, Subject) (StudentID, Subject) is key here // Losses: Teacher → Subject // But preserves: (StudentID, Subject) → Teacher // The choice affects which FDs are preserved! // No BCNF decomposition can preserve all FDs in this case.

BCNF vs 3NF: Practical Trade-off

When BCNF decomposition loses functional dependencies, database designers often choose to stay at 3NF instead. Maintaining data integrity through FK constraints is more important than eliminating every last bit of redundancy.

BCNF Quick Reference

  • ▸ Rule: Every determinant must be a superkey
  • ▸ Stricter than 3NF: 3NF allows non-key det. if RHS is prime
  • ▸ Classic violation: A → B where A is not a key
  • ▸ Algorithm: iteratively decompose on violating FDs
  • ▸ Always lossless, but may not preserve FDs
  • ▸ 3NF is the fallback when BCNF loses FDs
  • ▸ Developed by Boyce and Codd (1974)
  • ▸ Check: compute closure of each FD's LHS
