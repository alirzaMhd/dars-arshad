NORMALIZATION PROCESS

Database Systems — Chapter 7: Normalization

What is Normalization?

Normalization is a systematic process of organizing data in a database to:

  • Eliminate redundancy (duplicate data)
  • Avoid anomalies (insertion, update, deletion problems)
  • Ensure data integrity and consistency
  • Simplify query processing and maintenance
Normalization Goal:
Unnormalized → 1NF → 2NF → 3NF → BCNF → 4NF → 5NF
Each step removes a specific type of redundancy and anomaly.

UNF

Unnormalized form

Contains repeating groups

1NF

Atomic values

No repeating groups

2NF

Full FD on key

No partial dependencies

3NF

No transitive dependencies

No non-key → non-key FDs

BCNF

Every FD key-based

No overlapping candidate keys

4NF

No MVDs

Independent multi-valued facts separated

5NF

No JDs

No lossless 3+ way decompositions

Why Normalize?

Without normalization, databases suffer from three types of anomalies:

AnomalyDescriptionExample
InsertionCannot insert data without including unrelated dataCannot add a new course without a student enrolled
UpdateChanging one value requires updating multiple rowsChanging a professor's office requires updating all rows for that professor
DeletionDeleting one fact unintentionally deletes anotherDeleting the last student in a course deletes the course info
Normalization Trade-off:

Higher normal forms reduce redundancy but may increase join operations, potentially degrading query performance. The optimal level depends on the specific application requirements.

Step-by-Step Normalization Process

Step 0: Start with Unnormalized Form (UNF)

A table with repeating groups, multi-valued attributes, or composite values.

Step 1: Convert to First Normal Form (1NF)

Action: Remove repeating groups by creating separate rows or separate tables.

Rule: Each cell must contain an atomic (indivisible) value.

Result: A table with atomic values, a primary key, no repeating groups.

Step 2: Convert to Second Normal Form (2NF)

Action: Remove partial dependencies — FDs where a non-key attribute depends on part of a composite key.

Rule: Must be in 1NF. Every non-key attribute must be fully functionally dependent on the entire primary key.

Result: Decompose table so each non-key attribute depends on the full key.

Step 3: Convert to Third Normal Form (3NF)

Action: Remove transitive dependencies — FDs where a non-key attribute depends on another non-key attribute.

Rule: Must be in 2NF. No non-key attribute should be transitively dependent on the primary key.

Result: Every non-key attribute depends on "the key, the whole key, and nothing but the key."

Step 4: Convert to Boyce-Codd Normal Form (BCNF)

Action: Remove remaining FDs where the determinant is not a candidate key.

Rule: Must be in 3NF. For every FD X → Y, X must be a superkey.

Result: Every functional dependency is key-based.

Step 5: Convert to Fourth Normal Form (4NF)

Action: Remove multi-valued dependencies (MVDs).

Rule: Must be in BCNF. No non-trivial MVDs where the determinant is not a superkey.

Result: Independent multi-valued facts are stored in separate tables.

Step 6: Convert to Fifth Normal Form (5NF)

Action: Remove join dependencies (JDs) not implied by candidate keys.

Rule: Must be in 4NF. Every join dependency must be implied by candidate keys.

Result: Relation cannot be losslessly decomposed further — the ultimate normal form.

Normalization Summary Decision Chart

UNF: Repeating groups exist? ├── Yes → Flatten into 1NF (atomic values, key identified) └── No → Already in 1NF 1NF: Partial dependencies exist? (non-key attr depends on part of key) ├── Yes → Decompose into 2NF └── No → Already in 2NF 2NF: Transitive dependencies exist? (non-key → non-key) ├── Yes → Decompose into 3NF └── No → Already in 3NF 3NF: Every FD determinant is a candidate key? ├── No → Decompose into BCNF └── Yes → Already in BCNF BCNF: Non-trivial MVDs with non-superkey determinant? ├── Yes → Decompose into 4NF └── No → Already in 4NF 4NF: Non-trivial JDs not implied by keys? ├── Yes → Decompose into 5NF └── No → Already in 5NF (end of process)

  • Course(CourseID, Dept)
  • Department(Dept, DeptPhone)
  • Enrollment(StudentID, CourseID, Instructor)

Step 4: Check BCNF

Action: Verify that every FD determinant is a candidate key.

Check each table:

  • Student: StudentID → StudentName. StudentID is the key. ✓
  • Course: CourseID → Dept. CourseID is the key. ✓
  • Department: Dept → DeptPhone. Dept is the key. ✓
  • Enrollment: (StudentID, CourseID, Instructor) is the key. No non-trivial FDs with non-key determinant. ✓

All tables are in BCNF!

Note: In some cases, the transition from 3NF to BCNF requires additional decomposition when there are overlapping candidate keys. For example:

BCNF Special Case

R(A, B, C) with FDs: AB → C and C → B

Candidate keys: AB and AC

This is in 3NF but NOT in BCNF because C → B and C is not a superkey.

Decompose: R₁(C, B), R₂(A, C). Now both are in BCNF.

Step 5: Check 4NF

Action: Check for multi-valued dependencies.

In our Enrollment table, a student might have multiple courses and each course might have multiple instructors. This could create MVDs.

Looking at the Enrollment table: (StudentID, CourseID, Instructor)

If courses and instructors are independent (all combinations valid), then:

  • StudentID →→ CourseID (each student can take many courses, independent of instructors)
  • StudentID →→ Instructor (each student can have many instructors, independent of courses)

If these MVDs exist, we would decompose:

  • EnrollCourse(StudentID, CourseID)
  • EnrollInstructor(StudentID, Instructor)

However, in our running example, the original data shows that Instructor is tied to Course (Dr.Smith teaches CS101, Dr.Lee teaches MATH101). So the MVDs do NOT hold, and the Enrollment table remains in 4NF.

Step 6: Check 5NF

Action: Check for join dependencies not implied by keys.

Our tables have simple key structures. No non-trivial join dependencies exist. All tables are in 5NF (PJNF).

Final Normalized Schema Summary

Student(StudentID PK, StudentName)

Course(CourseID PK, Dept)

Department(Dept PK, DeptPhone)

Enrollment(StudentID FK→Student, CourseID FK→Course, Instructor)

All tables in 5NF. Redundancy eliminated. Anomalies prevented.

Key Principle — "The Key, the Whole Key, and Nothing but the Key"

This famous maxim describes 3NF but extends in spirit to all normal forms: each table should represent one fact about one entity, identified by its key. Violating this at any level introduces redundancy.

When to Stop Normalizing?

Stop at 3NF

Most practical databases stop here. 3NF eliminates most anomalies while preserving dependencies.

Go to BCNF

When overlapping candidate keys exist, BCNF catches edge cases 3NF misses.

Consider 4NF/5NF

Only when MVDs or JDs are present. These are rare in practice.

Practical Normalization Guidelines
  • Almost always: normalize to 3NF or BCNF
  • For most business applications: 3NF is sufficient
  • When performance is critical: consider denormalization
  • 4NF/5NF: only for specialized cases with complex relationships
  • Remember: normalization is a bottom-up design approach (complements ER modeling)

Common Mistakes in Normalization

Over-normalization

Creating too many tables degrades performance. More joins = slower queries.

Under-normalization

Stopping too early leaves redundancy. More anomalies = data inconsistency.

Ignoring FDs

Not identifying all functional dependencies leads to incomplete normalization.

Skipping Steps

Going directly to 3NF from UNF without 1NF/2NF may miss important decompositions.
