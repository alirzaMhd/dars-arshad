Second Normal Form (2NF)

Database Normalization — دومین فرم نرمال | Complete Guide for 20/20 Exam

What is 2NF?

A table is in Second Normal Form (2NF) if and only if:

  • It is in 1NF
  • Every non-prime attribute is fully functionally dependent on the entire primary key

In simpler terms: No partial dependency on any part of a composite primary key.

2NF Condition
If PK = (A, B) and A → C, then C is partially dependent → Violates 2NF
A non-key attribute depends on only part of the primary key. This is called a partial functional dependency.
2NF Only Applies to Composite Keys

If a table has a single-attribute primary key, it is automatically in 2NF (provided it is in 1NF). Partial dependencies can only occur when the primary key consists of two or more attributes.

Key Concepts

Full Functional Dependency

Y is fully functionally dependent on X if:

• X → Y holds

• No proper subset of X determines Y

Example: (StudentID, CourseID) → Grade is full

Partial Functional Dependency

Y is partially dependent on X (a composite key) if:

• X → Y holds

• Some proper subset of X also determines Y

Example: (StudentID, CourseID) → StudentName is partial

Prime vs Non-Prime

Prime attribute: Part of any candidate key

Non-prime attribute: Not part of any candidate key

2NF only cares about non-prime attributes

2NF Violation Example

Table: Enrollment (in 1NF, but not 2NF)
StudentID (PK part)CourseID (PK part)StudentNameInstructorGrade
101CSE201AliDr. AhmadiA
101CSE301AliDr. RezaeiB
102CSE201SaraDr. AhmadiA

Functional Dependencies:

(StudentID, CourseID) → Grade // Full dependency (OK) StudentID → StudentName // Partial dependency (BAD!) CourseID → Instructor // Partial dependency (BAD!)

StudentName depends on only StudentID (part of PK). Instructor depends on only CourseID (part of PK). Both are partial dependencies → violates 2NF.

What is a Partial Dependency?

A partial dependency occurs when a non-prime attribute is functionally dependent on a proper subset of a composite candidate key, rather than on the entire key.

Partial Dependency Definition
(A, B) → C (FD holds), AND A → C (proper subset determines C)
C depends on only part of the key (A) rather than the full key (A, B). This is the signature of a 2NF violation.

Detecting Partial Dependencies

Algorithm to detect partial dependencies:

  1. Identify the primary key (composite or single)
  2. List all functional dependencies
  3. For each non-prime attribute Y, check if its determinant includes only part of the primary key
  4. If yes → partial dependency → violates 2NF
Partial Dependency Detection Example
Table: Order_Details PK = (OrderID, ProductID) FDs: 1. (OrderID, ProductID) → Quantity // Full → OK 2. OrderID → OrderDate // Partial → 2NF violation 3. ProductID → ProductName, Price // Partial → 2NF violation Conclusion: Table is NOT in 2NF

Why Partial Dependencies Are Bad

ProblemExample
Insert AnomalyCannot add a new course unless a student enrolls in it (need both parts of PK)
Update AnomalyChanging "Dr. Ahmadi" to "Dr. Ahmadi-Fard" requires updating multiple rows
Delete AnomalyDeleting the last enrollment in a course deletes the course information
RedundancyStudentName is repeated for every course a student takes
Partial Dependencies Cause Redundancy

Since StudentName depends only on StudentID, storing it alongside each course enrollment creates redundant copies. Same for Instructor depending only on CourseID.

Example 3: Composite Key without Partial Dependency

Consider a table where ALL non-key attributes depend on the FULL composite key:

Already in 2NF
StudentID (PK)CourseID (PK)GradeAttendance%
101CSE201A95
101CSE301B85
102CSE201A90

FDs: (StudentID, CourseID) → Grade, Attendance%

There is no StudentID → Grade (a student gets different grades in different courses). There is no CourseID → Attendance% (different students have different attendance).

This table is already in 2NF (assuming it's in 1NF).

2NF Decomposition Pattern

Decomposition Rule for 2NF
R(A, B, C, D) with PK=(A,B) and A→C
Split into: R1(A, C) and R2(A, B, D)

General pattern: For each partial dependency, extract the partially dependent attributes along with their determinant into a new table. The original table keeps only the fully dependent attributes plus the key.

2NF Normalization Algorithm

Step-by-step algorithm to normalize a table to 2NF:

Algorithm NormalizeTo2NF(R, FDs, PK): // Input: Relation R, Set of FDs, Primary Key PK // Output: Set of relations in 2NF // Step 1: Verify R is in 1NF if not isIn1NF(R): convertTo1NF(R) // Step 2: If PK is single attribute → already 2NF if size(PK) == 1: return {R} // Step 3: Find all partial dependencies partialFDs = {} for each FD: X → Y in FDs: if X ⊂ PK and Y is non-prime: partialFDs.add(X → Y) // Step 4: Decompose for each partial dependency result = {R} for each X → Y in partialFDs: R1 = (X ∪ Y) // Extract determinant + dependent R2 = R - Y + X // Remove dependent, keep determinant result.remove(R) result.add(R1) result.add(R2) return result

Algorithm Walkthrough

Applying the Algorithm
// Given: R = Enrollment(StudentID, CourseID, StudentName, Instructor, Grade) // PK = (StudentID, CourseID) // FDs: StudentID → StudentName, CourseID → Instructor // Step 1: Is R in 1NF? Yes (atomic values, PK defined) // Step 2: Is PK single? No (composite: StudentID + CourseID) // Step 3: Find partial FDs // StudentID → StudentName: StudentID ⊂ (StudentID, CourseID) ✓ Partial! // CourseID → Instructor: CourseID ⊂ (StudentID, CourseID) ✓ Partial! // Step 4: Decompose // For StudentID → StudentName: // R1 = (StudentID, StudentName) → Student table // R2 = (StudentID, CourseID, Instructor, Grade) → remaining // For CourseID → Instructor (in R2): // R2a = (CourseID, Instructor) → Course table // R2b = (StudentID, CourseID, Grade) → Enrollment table // Result: // Student(StudentID, StudentName) ← 2NF // Course(CourseID, Instructor) ← 2NF // Enrollment(StudentID, CourseID, Grade) ← 2NF

Checking if a Table is in 2NF

Quick checklist:

  1. Is the table in 1NF? (If no, fix 1NF first)
  2. Is the primary key a single attribute? (If yes, it's automatically 2NF)
  3. For composite PK: check each non-prime attribute
  4. Is any non-prime attribute determined by a subset of the PK?
  5. If yes → not 2NF. If no → it is 2NF.
Exam Tip

In exams, always write down all functional dependencies first. Then identify the PK. Then check each FD to see if it's a partial dependency. This systematic approach never fails.

2NF Quick Reference

  • ▸ Rule: 1NF + no partial dependencies on composite PK
  • ▸ Partial dependency: non-prime attribute depends on subset of PK
  • ▸ Single-attribute PK → automatically in 2NF
  • ▸ Fix: extract determinant + dependent into new table
  • ▸ Decomposition is lossless and dependency-preserving
  • ▸ Still may have transitive dependencies → need 3NF
  • ▸ Common FD sign: StudentID → Name in a table with (StudentID, CourseID) PK
