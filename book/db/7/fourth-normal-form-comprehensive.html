FOURTH NORMAL FORM (4NF)

Database Systems — Chapter 7: Normalization

What is Fourth Normal Form?

A relation is in Fourth Normal Form (4NF) if and only if:

  • It is in BCNF
  • It has no multi-valued dependencies (MVDs) that are not also functional dependencies
Formal Definition:
R is in 4NF ⇔ R is in BCNF ∧ ¬∃ non-trivial MVD X →→ Y
where X is not a superkey and Y is non-empty, and X ∩ Y = ∅
Key Insight:

4NF eliminates redundancy caused by multi-valued dependencies. A table that is in BCNF may still have redundancy if it contains multiple independent multi-valued facts.

4NF Checklist

✓ Relation is in BCNF

✓ Every non-trivial MVD X →→ Y has X as a superkey

✓ No independent multi-valued attributes are stored together

✓ All redundancy from MVDs is eliminated

Why 4NF?

BCNF handles functional dependencies well, but it does not handle multi-valued dependencies. Consider a table where an employee has multiple skills and multiple dependents. These two facts are independent, but storing them together causes redundancy.

BCNF is Not Enough

A table in BCNF can still have redundancy when it stores two independent multi-valued facts

MVDs Cause Spurious Tuples

When independent facts are stored together, every combination must be stored, leading to unnecessary rows

4NF Separates Concerns

4NF decomposes such tables so each independent fact is stored in its own relation

History and Motivation

4NF was introduced by Ronald Fagin in 1977. He recognized that BCNF was insufficient for relations containing multi-valued dependencies. The classic example is the Employee-Dependent-Skill problem, where an employee may have multiple dependents and multiple skills completely independently.

The Problem 4NF Solves

An employee John has skills {Java, Python} and dependents {Alice, Bob}. If stored in one table:

EmpSkillDependent
JohnJavaAlice
JohnJavaBob
JohnPythonAlice
JohnPythonBob

4 rows for just 1 employee! The MVD Emp →→ Skill creates a Cartesian product with Emp →→ Dependent.

Multi-valued Dependencies (MVDs)

A multi-valued dependency (MVD) is a constraint where the value of one attribute determines a set of values for another attribute, independently of other attributes.

MVD Notation:
X →→ Y
Read as: "X multi-determines Y" or "X determines a set of Y values"

Formal Definition

An MVD X →→ Y holds in relation R if, for any two tuples t₁ and t₂ in R with t₁[X] = t₂[X], there exists a tuple t₃ in R such that:

  • t₃[X] = t₁[X] = t₂[X]
  • t₃[Y] = t₁[Y]
  • t₃[Z] = t₂[Z] where Z = R − (X ∪ Y)
Example: Identifying an MVD

Consider Employee(EmpID, Skill, Dependent):

EmpIDSkillDependent
E1JavaAlice
E1PythonAlice
E1JavaBob
E1PythonBob

Here, EmpID →→ Skill holds because for each EmpID, the set of skills is independent of the dependents. Similarly EmpID →→ Dependent also holds.

Trivial vs Non-Trivial MVDs

Trivial MVD

X →→ Y is trivial if:

Y ⊆ X or X ∪ Y = R

Example: EmpID →→ EmpID

Non-Trivial MVD

X →→ Y is non-trivial if:

Y ⊄ X and X ∪ Y ≠ R

Example: EmpID →→ Skill

Properties of MVDs

1. MVD Implication (FD is a special case of MVD)

Every FD is an MVD:
If X → Y, then X →→ Y
But the converse is NOT true. An MVD is not necessarily an FD.

2. Complementation Rule

If X →→ Y, then:
X →→ (R − X − Y)
Where R − X − Y represents all attributes not in X or Y.

3. Augmentation Rule

If X →→ Y, then XZ →→ YZ

4. Transitivity Rule

If X →→ Y and Y →→ Z, then X →→ (Z − Y)
MVD Inference Example

If we know EmpID →→ Skill in relation R(EmpID, Skill, Dependent):

By complementation: EmpID →→ Dependent

MVDs always come in complementary pairs in a 3-attribute relation.

Important Distinction:

Unlike FDs, MVDs cannot be inferred from looking at a single instance. You need domain knowledge. The MVD EmpID →→ Skill means that for each employee, skills are independent of dependents.

Example 1: Employee Skills and Dependents

Problems:

  • Redundancy: Employee name repeated for every skill-dependent combination

4NF Decomposition:

Decompose into two relations:

R1(EmpID, Skill)

E1Alice
E1Bob

Now each relation stores only one independent multi-valued fact. Total rows: 4 (vs 4 in the original). Insertion/deletion is now straightforward.

4NF Decomposition Algorithm

4NF Decomposition Algorithm:
Given R and set of FDs and MVDs

Algorithm Steps:

  1. Start with relation R and find a non-trivial MVD X →→ Y that violates 4NF (X is not a superkey)
  2. Compute the closure of X with respect to both FDs and MVDs
  3. Decompose R into two relations:
    • R₁ = (X ∪ Y)
    • R₂ = (R − Y)
  4. Check each new relation for 4NF compliance
  5. Repeat until all relations are in 4NF
Important Property:

The 4NF decomposition is lossless-join. Natural join of R₁ and R₂ gives exactly R. It also preserves all MVDs.

Step-by-Step Decomposition Example

Complete Decomposition Walkthrough

Given: R(A, B, C, D) with MVD A →→ B and FD A → C

Step 1: Check 4NF

Is R in 4NF? No. A →→ B is a non-trivial MVD and A is not a superkey (A alone does not determine D).

Step 2: Compute X⁺

X = {A}. Using FD A → C, we get X⁺ = {A, C}.

Step 3: Decompose

R₁ = (A ∪ B) = R₁(A, B)

R₂ = (R − B) = R₂(A, C, D)

Step 4: Check 4NF for R₁

R₁(A, B) has MVD A →→ B, but this is trivial since A ∪ B = R₁. R₁ is in 4NF.

Step 5: Check 4NF for R₂

R₂(A, C, D) has FD A → C. A is the key. No non-trivial MVDs. R₂ is in 4NF.

Result:

R decomposed into R₁(A, B) and R₂(A, C, D), both in 4NF.

Lossless Join Property

Lossless Join Condition for MVDs:
R = R₁ ⨝ R₂ ⇔ R₁ ∩ R₂ →→ (R₁ − R₂) | R₂ − R₁
The intersection of the two decomposed relations must multi-determine the difference.

The 4NF decomposition algorithm guarantees lossless join because:

  • R₁ ∩ R₂ = X (the determinant of the MVD)
  • R₁ − R₂ = Y
  • R₂ − R₁ = R − (X ∪ Y) = Z
  • Since X →→ Y holds in R, the natural join of R₁ and R₂ is lossless
Verifying Lossless Join

Original: R(EmpID, Skill, Dependent) with EmpID →→ Skill

Decomposition: R₁(EmpID, Skill), R₂(EmpID, Dependent)

R₁ ∩ R₂ = {EmpID}

R₁ − R₂ = {Skill}

R₂ − R₁ = {Dependent}

Check: EmpID →→ Skill holds ✓ and EmpID →→ Dependent holds ✓

Natural join reconstructs the original exactly.
