Third Normal Form (3NF)

Database Normalization — سومین فرم نرمال | Complete Guide for 20/20 Exam

What is 3NF?

A table is in Third Normal Form (3NF) if and only if:

  • It is in 2NF
  • There are no transitive dependencies: no non-prime attribute is functionally dependent on another non-prime attribute
3NF Condition (Formal Definition)
For every FD X → A (where A is a single attribute):
Either (1) A ∈ X (trivial), or (2) X is a superkey, or (3) A is a prime attribute

In simpler terms: A non-key column cannot determine another non-key column.

3NF vs 2NF

2NF eliminates partial dependencies (non-key depends on part of PK). 3NF eliminates transitive dependencies (non-key depends on another non-key). A table in 2NF may still have transitive dependencies.

3NF Violation Example

Table: Employee_Department (2NF but NOT 3NF)
EmpID (PK)EmpNameDeptIDDeptNameDeptLocation
E01AliD10EngineeringBuilding A
E02SaraD10EngineeringBuilding A
E03RezaD20MarketingBuilding B

Functional Dependencies:

EmpID → EmpName, DeptID, DeptName, DeptLocation // PK determines all DeptID → DeptName, DeptLocation // TRANSITIVE! Non-key → non-key

DeptName and DeptLocation depend on DeptID, which is NOT a key (not a superkey). This is a transitive dependency: EmpID → DeptID → DeptName.

Anomalies in the Example

AnomalyExample
InsertCannot add a new department (D30, Sales, Building C) without an employee assigned to it
UpdateRenaming "Engineering" to "Engineering Dept" requires updating ALL employees in D10
DeleteDeleting the last employee in D20 deletes the Marketing department info
3NF Fix

Decompose into: Employee(EmpID, EmpName, DeptID) and Department(DeptID, DeptName, DeptLocation). Now DeptName depends on DeptID which IS the key of the Department table.

What is a Transitive Dependency?

A transitive dependency occurs when a non-prime attribute determines another non-prime attribute. Formally: if X → Y and Y → Z, then X → Z is a transitive dependency (where Y is not a superkey and Z is non-prime).

Transitive Dependency Pattern
X → Y (X is a key, Y is non-prime)
Y → Z (Y is non-prime, Z is non-prime)
∴ X → Z (transitive, violates 3NF)

Identifying Transitive Dependencies

Algorithm to detect transitive dependencies:

  1. Verify the table is in 2NF (no partial dependencies)
  2. List all functional dependencies (FDs)
  3. For each FD X → Y where X is NOT a superkey and Y is non-prime:
    • If X determines another non-prime attribute Z → transitive dependency
Transitive Dependency Detection
Table: Student_Advisor PK = StudentID FDs: StudentID → AdvisorID, AdvisorName, AdvisorPhone // PK FDs AdvisorID → AdvisorName, AdvisorPhone // Transitive! // AdvisorID is not a key of this table // AdvisorID → AdvisorName shows transitive dep: // StudentID → AdvisorID → AdvisorName Conclusion: Not in 3NF

3NF Synthesis Algorithm

The 3NF synthesis algorithm produces a dependency-preserving and lossless decomposition into 3NF.

Algorithm NormalizeTo3NF(R, F): // Input: Relation R, Set of FDs F // Output: Set of relations in 3NF // Step 1: Compute minimal cover of F F_min = minimalCover(F) // Step 2: Group FDs by left-hand side // For each unique LHS X in F_min: // Create relation with X ∪ all RHS attributes determined by X result = {} for each unique X in F_min: attrs = X ∪ closure(X, F_min) - X result.add(relation with attrs) // Step 3: If no relation contains a key of R, add a key relation if not containsKey(result, R): result.add(relation with a candidate key of R) // Step 4: Remove redundant relations for each Ri in result: if Ri ⊆ Rj for some j ≠ i: result.remove(Ri) return result

Algorithm Walkthrough

Step-by-Step: Student_Advisor → 3NF
// Given: R(StudentID, AdvisorID, AdvisorName, StudentName) // F: {StudentID → AdvisorID, AdvisorID → AdvisorName, StudentID → StudentName} // Step 1: Minimal cover // F_min = {StudentID → AdvisorID, AdvisorID → AdvisorName, StudentID → StudentName} // Step 2: Group by LHS // For X = StudentID: R1(StudentID, AdvisorID, StudentName) // For X = AdvisorID: R2(AdvisorID, AdvisorName) // Step 3: Check key containment // Candidate key of R: StudentID // StudentID is in R1 → OK // Step 4: Remove redundant // No redundancies // Final 3NF decomposition: // R1(StudentID, AdvisorID, StudentName) // R2(AdvisorID, AdvisorName)

3NF Decomposition by Transitive Dependency Removal

Simpler, more intuitive approach for exam purposes:

Algorithm Decompose3NF_Simple(R, FDs): // Step 1: Ensure R is in 2NF result = NormalizeTo2NF(R, FDs) // Step 2: For each relation in result, check transitive dependencies for each relation Ri in result: for each non-trivial FD X → Y in FDs on Ri: if X is not a superkey and Y is non-prime: // Transitive dependency found // Decompose: R1 = (X ∪ Y), R2 = (Ri - Y + X) R1 = (X ∪ Y) R2 = (Ri - Y + X) result.remove(Ri) result.add(R1) result.add(R2) return result

3NF vs BCNF: When 3NF is Not Enough

A relation that is 3NF but not BCNF
R(A, B, C) FDs: AB → C, C → B // Candidate keys: AB, AC // Prime attributes: A, B, C (all are prime!) // Since all attributes are prime, there are no partial // or transitive dependencies → 3NF is satisfied. // However, C → B violates BCNF because C is not a superkey // (C does not determine A).

This example shows that 3NF allows certain dependencies that BCNF forbids. When all attributes are prime, 3NF holds even if non-key determinants exist.

Minimal Cover for 3NF Synthesis

Minimal Cover Steps
1. Decompose RHS: Replace X → YZ with X → Y, X → Z
2. Remove extraneous attributes from LHS
3. Remove redundant FDs
Minimal Cover Example
// Original FDs: AB → C, A → B, B → C, AC → D // Step 1: Already decomposed (all single RHS) // Step 2: Check extraneous attributes // AC → D: Is A extraneous? Without A: C+ = {C, B, ...} no D → NO // Is C extraneous? Without C: A+ = {A, B, C} includes C → C extraneous! // So A → D (from AC → D) // Step 3: Remove redundant // B → C: B+ = {B, C} in others? A → B, A → C → B → C is redundant // Minimal cover: {AB → C, A → B, A → D}

3NF Quick Reference

  • ▸ Rule: 2NF + no transitive dependency (non-key → non-key)
  • ▸ Transitive pattern: PK → NonKey1 → NonKey2
  • ▸ Fix: Extract NonKey1 + NonKey2 into separate table
  • ▸ Synthesis algorithm: minimal cover → group by LHS → add key if needed
  • ▸ 3NF is always dependency-preserving (unlike BCNF)
  • ▸ 3NF allows non-key determinants when all attributes are prime
  • ▸ 3NF ⊃ BCNF (BCNF is stricter)
  • ▸ Most real-world databases aim for 3NF
