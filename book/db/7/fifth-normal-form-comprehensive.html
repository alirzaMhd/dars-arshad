FIFTH NORMAL FORM (5NF)

Database Systems — Chapter 7: Normalization

What is Fifth Normal Form?

A relation is in Fifth Normal Form (5NF), also called Project-Join Normal Form (PJNF), if and only if:

  • It is in 4NF
  • It has no join dependencies that are not implied by candidate keys
  • Every join dependency in R is implied by the candidate keys of R
Formal Definition:
R is in 5NF ⇔ ∀ JD ⋈(R₁, ..., Rₙ) in R, each Rᵢ is a superkey of R
A join dependency exists only if it comes from candidate key constraints.
Key Insight:

5NF addresses join dependencies — situations where a table can be losslessly decomposed into three or more tables, but cannot be decomposed into just two. This is the final normal form in classical normalization theory.

5NF Checklist

✓ Relation is in 4NF

✓ Every join dependency is implied by candidate keys

✓ No lossless decomposition into smaller tables is possible without losing FDs

✓ Every table represents one fact about one concept

Why 5NF?

Even after achieving 4NF (eliminating MVDs), some relations may still contain join dependencies — constraints that require the relation to be decomposable into three or more projections for lossless-join reconstruction.

Join Dependencies

A JD ⋈(R₁, R₂, R₃) means the relation can be losslessly decomposed into three projections

Beyond Binary Decompositions

While 4NF handles binary decompositions (splitting into 2 tables), 5NF handles n-ary decompositions (splitting into 3+ tables)

Ultimate Normalization

5NF represents the maximally normalized state. No further lossless decomposition is possible without losing information.

The Spurious Tuple Problem

Consider a relation Agent(AgentID, Company, Product) with the constraint that an agent sells products for a company, but only if that company makes that product. This is a ternary relationship that cannot be captured by binary projections alone.

If we decompose it into binary relations and join them back, we may get spurious tuples — rows that were not in the original.

Historical Context

5NF was introduced by Ronald Fagin in 1979 as the final step in the normalization hierarchy. It addresses constraints that are more subtle than FDs and MVDs — specifically, constraints that involve three or more relation variables.

In practice, most database designs stop at BCNF or 3NF. 5NF is primarily of theoretical interest, though it does occasionally arise in practice with ternary relationships.

Join Dependency (JD)

A join dependency (JD) is a constraint stating that a relation is equal to the natural join of its projections on certain subsets of its attributes.

Join Dependency Notation:
⋈(R₁, R₂, ..., Rₙ)
Read as: "R is the lossless join of its projections on attribute sets R₁, R₂, ..., Rₙ"

Formal Definition

A join dependency JD ⋈(R₁, R₂, ..., Rₙ) holds in relation R if:

R = π_{R₁}(R) ⨝ π_{R₂}(R) ⨝ ... ⨝ π_{Rₙ}(R)
The relation is exactly the natural join of all its projections on the specified attribute sets.
Example: Ternary Join Dependency

Consider R(A, B, C). If the JD ⋈(AB, BC, CA) holds, then:

R = π_{AB}(R) ⨝ π_{BC}(R) ⨝ π_{CA}(R)

This means the 3-way join of the three binary projections reconstructs R exactly, but no 2-way join does.

Trivial vs Non-Trivial JDs

Trivial JD

A JD is trivial if one of the projections Rᵢ equals all attributes of R

Example: ⋈(ABC, AB) is trivial because ABC covers all attributes.

Non-Trivial JD

A JD is non-trivial if no projection Rᵢ equals all attributes of R

Example: ⋈(AB, BC, CA) in a 3-attribute relation is non-trivial.

JD vs MVD vs FD

DependencyNotationArityEliminated by
Functional DependencyX → YBinary (one value determines another)BCNF
Multi-valued DependencyX →→ YBinary (one value determines a set)4NF
Join Dependency⋈(R₁, ..., Rₙ)n-ary (can involve 3+ projections)5NF
Relationship:
FD ⊂ MVD ⊂ JD
Every FD is an MVD, and every MVD is a binary JD.

An MVD X →→ Y is equivalent to the binary JD ⋈(XY, XZ) where Z = R − (X ∪ Y). So 4NF handles only binary JDs. 5NF handles all JDs, including n-ary ones.

Properties of Join Dependencies

1. Reflexivity

If R contains all attributes of R₁, then ⋈(R₁, R₂, ..., Rₙ) is trivial

2. Decomposition through Keys

If R has candidate key K, then ⋈(K, R₁, ..., Rₙ) is implied
A key determines all other attributes, so any JD involving the key is automatically satisfied.

3. Every MVD is a JD

If X →→ Y, then ⋈(XY, X(R−X−Y))
An MVD is exactly a binary JD.
Important:

Not every JD is an MVD. A JD can require three or more projections, which no MVD can capture. This is why 5NF is needed even after achieving 4NF.

Detailed Examples

Example 1: Agent-Company-Product (The Classic 5NF Example)

Consider R(Agent, Company, Product) with the constraint:

  • An agent sells products for a company
  • But only if that company actually manufactures that product

This is a ternary relationship. The relation cannot be decomposed into binary relations without losing information.

Sample Data:

AgentCompanyProduct
SmithFordCar
SmithGMTruck
JonesFordCar

Try Binary Decomposition:

R₁(Agent, Company), R₂(Agent, Product), R₃(Company, Product)

Joining R₁ ⨝ R₂ ⨝ R₃ gives:

AgentCompanyProduct
SmithFordCar
SmithFordTruck
SmithGMCar
SmithGMTruck
JonesFordCar

Spurious tuples! Smith-Ford-Truck and Smith-GM-Car appear but were not in the original. The binary join is lossy, so the JD ⋈(AgentCompany, AgentProduct, CompanyProduct) does NOT hold.

This relation is already in 5NF — it cannot be further decomposed losslessly.

Example 2: A Relation with a Join Dependency

Consider R(Student, Course, Instructor) where:

  • Each student takes multiple courses
  • Each course has multiple instructors
  • Each instructor teaches multiple students
  • All combinations are allowed (no ternary constraint)

Project-Join Normal Form (PJNF)

Project-Join Normal Form (PJNF) is synonymous with 5NF. A relation is in PJNF if every join dependency that holds in the relation is implied by the candidate keys.

PJNF Definition:
R is in PJNF ⇔ every JD ⋈(R₁, ..., Rₙ) in R is implied by the candidate keys of R
"Implied by candidate keys" means each Rᵢ is a superkey of R.
Important:

Some authors distinguish between 5NF and PJNF. In common usage they are the same. However, the original definition of PJNF required that every JD is a consequence of the candidate keys, making it slightly stronger than the standard 5NF definition.

When Does a JD Follow from Keys?

A JD ⋈(R₁, ..., Rₙ) is implied by candidate keys if every attribute set Rᵢ contains a candidate key. Since a key determines all attributes, any projection containing a key will reconstruct the full relation when joined.

5NF Decomposition Algorithm

Algorithm:

  1. Find a non-trivial JD ⋈(R₁, ..., Rₙ) that is not implied by candidate keys
  2. Decompose R into projections π_{R₁}(R), π_{R₂}(R), ..., π_{Rₙ}(R)
  3. Check each projection for 5NF compliance
  4. Repeat until all relations are in 5NF
5NF Decomposition Walkthrough

Given: R(A, B, C, D) with JD ⋈(ABC, BCD, CDA) and keys {AB, CD}

Step 1: Is R in 5NF?

Check: Does any projection contain a key?

  • ABC: does NOT contain AB (yes it does! A, B are in ABC)
  • BCD: does NOT contain key CD (yes! C, D are in BCD)... wait, BCD has C, D, yes.

Actually ABC contains {A,B} which is key. BCD contains {C,D} which is key. CDA contains... needs more analysis.

Let's assume the JD is not key-implied. Then we decompose:

R₁ = π_{ABC}(R), R₂ = π_{BCD}(R), R₃ = π_{CDA}(R)

The decomposition is lossless and all resulting projections are in 5NF.

Lossless Join Decomposition

Lossless Join Test:
R = ⋈(π_{R₁}(R), π_{R₂}(R), ..., π_{Rₙ}(R))
A decomposition is lossless iff the JD holds.

Testing for Lossless Join

To verify a decomposition is lossless, construct the chase matrix:

  1. Create a row for each projection with distinguished variables for attributes in that projection
  2. Apply FDs and JDs to generate new rows
  3. If a row with all distinguished variables appears, the join is lossless
Lossless Join Example

Given R(A, B, C) with JD ⋈(AB, BC, CA):

Original R: A B C a1 b1 c1 a1 b2 c2 a2 b1 c2 π_AB(R): A B a1 b1 a1 b2 a2 b1 π_BC(R): B C b1 c1 b2 c2 b1 c2 π_CA(R): C A c1 a1 c2 a1 c2 a2 Join all three — result equals R iff JD holds.

Chase Test Visualization

The chase algorithm determines whether a JD holds by attempting to prove that all tuples in the join are in the original relation. If the chase succeeds (produces a row with all distinguished variables), the JD holds and the decomposition is lossless.
