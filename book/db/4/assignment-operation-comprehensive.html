ASSIGNMENT OPERATION

Database Relational Algebra - Comprehensive Guide

What is Assignment Operation?

The assignment operation (← or GIVING) is a relational algebra operator that assigns the result of a relational expression to a temporary relation variable. It allows us to break complex queries into smaller, more manageable steps.

Assignment is not a fundamental operation like selection, projection, or join. Instead, it is a notational convenience that helps in writing clearer and more modular relational algebra expressions.

Key Characteristics

Temporary Storage
Stores intermediate results for reuse
Query Decomposition
Breaks complex queries into simpler steps
No New Data
Does not modify the original relations
Session Scope
Variable exists only during the query session

When to Use Assignment

  • When a query has multiple nested operations
  • When the same intermediate result is used multiple times
  • When you need to break down complex logic for clarity
  • When building incremental queries step by step

How Assignment Works

The assignment operation works by evaluating the expression on the right side and storing the result in the variable on the left side.

  1. Evaluate the expression: Compute the result of the relational algebra expression
  2. Store in variable: Assign the result to the named temporary relation
  3. Use in subsequent operations: Reference the variable in later expressions
  4. Final result: The last expression yields the final answer

Assignment vs Direct Expression

Aspect With Assignment Without Assignment
Readability Clear, step-by-step Complex nested expressions
Reusability Intermediate results reusable Must recompute each time
Debugging Easier to test each step Hard to isolate issues
Performance May materialize intermediate results Optimizer can choose strategy

Application in Updates

Assignment is also used in relational algebra to express updates to a relation. By assigning a new expression to an existing relation variable, we can model INSERT, DELETE, and MODIFY operations.

INSERT
R ← R ∪ NewTuples
DELETE
R ← R - TuplesToRemove
MODIFY
R ← (R - OldVersion) ∪ NewVersion

Assignment Notation

Basic Assignment
TempResult ← Expression
Assigns the result of Expression to the temporary variable TempResult
Assignment with GIVING keyword
GIVING TempResult = Expression
Alternative syntax used in some systems (e.g., Tutorial D)
Chained Assignment
T1 ← Expr1; T2 ← Expr2; Result ← T1 ⋈ T2
Multiple assignments can be chained to build complex queries step by step

Update Operations Using Assignment

INSERT Operation
R ← R ∪ {NewTuple1, NewTuple2, ...}
Add new tuples to relation R by taking the union with new data
DELETE Operation
R ← R - σcondition(R)
Remove tuples matching condition from R by subtracting selected tuples
MODIFY Operation
R ← (R - σold(R)) ∪ πschema(σold(R) ⋈ NewValues)
Replace old versions of tuples with updated values
DELETE with Condition
S ← S - σCity='C2'(S)
Delete all tuples where City equals 'C2' from relation S

Key Variable Definitions

R (Left side)
The variable being assigned (can be existing or new)
Expression (Right side)
Any valid relational algebra expression
TempResult
A temporary variable holding intermediate results
← (Arrow)
Assignment operator (direction: right to left)

Example 1: Multi-step Query

Problem: Find names of suppliers in cities that supply part P1

Given Relations:

SP (Supply)S (Suppliers)
S#P#QTYS#SnameCity
S1P1300S1SmithLondon
S1P2200S2JonesParis
S2P1400S3ClarkLondon
S2P3100S4AdamsAthens

Step-by-step with Assignment:

Step1 ← σP#='P1'(SP) -- Get all supplies of P1
Step2 ← πS#(Step1) -- Get supplier numbers for P1
Step3 ← S ⋈ Step2 -- Join with suppliers
Result ← πSname(Step3) -- Get supplier names
Result: {Smith, Jones} - Suppliers in cities that supply P1

Example 2: DELETE Operation

Problem: Delete all suppliers from city 'C2'

Given Relation S:

S#City
S1C1
S2C2
S3C2

Using Assignment:

TuplesToDelete ← σCity='C2'(S) -- Find tuples to delete
S ← S - TuplesToDelete -- Remove them from S

Result after assignment:

S#City
S1C1
S now contains only supplier S1 from city C1

Example 3: INSERT Operation

Problem: Add a new supply record (S2, P2, 40)

Given Relation SP:

S#P#QTY
S1P1300
S1P2200
S2P1400

Using Assignment:

NewTuple ← {(S2, P2, 40)} -- Create new tuple
SP ← SP ∪ NewTuple -- Add to existing relation

Result after assignment:

S#P#QTY
S1P1300
S1P2200
S2P1400
S2P240
SP now contains 4 tuples including the new one

Example 4: Complex Query with Multiple Assignments

Problem: Find suppliers who supply all parts in city C1

Step-by-step approach:

-- Step 1: Get parts supplied in C1
PartsInC1 ← πP#(σCity='C1'(SP ⋈ S))

-- Step 2: Get all supplier-part combinations
AllCombos ← πS#(S) × PartsInC1

-- Step 3: Get actual supplier-part pairs
ActualPairs ← πS#,P#(SP)

-- Step 4: Find suppliers missing any combination
MissingPairs ← AllCombos - ActualPairs

-- Step 5: Get suppliers not in missing list
Result ← πS#(S) - πS#(MissingPairs)
Result contains suppliers who supply ALL parts found in city C1

Example 5: MODIFY Operation

Problem: Change supplier S2's city from 'C2' to 'C3'

Using Assignment:

OldVersion ← σS#='S2'(S) -- Get old S2 tuple
NewVersion ← πS#,Sname(OldVersion) × {(C3)} -- Create new version
S ← (S - OldVersion) ∪ NewVersion -- Replace old with new
Supplier S2 now has City = 'C3' instead of 'C2'

Time Complexity

Assignment Itself
O(1) for pointer assignment
The assignment operation is essentially a pointer/reference assignment
Expression Evaluation
Depends on the expression
The complexity depends entirely on the relational algebra expression being evaluated
Materialization Cost
O(|Result|) if materialized
If the system materializes intermediate results, storage and I/O costs apply

Space Complexity

Temporary Storage
O(|IntermediateResult|)
Space needed to store each intermediate result

In practice, smart query optimizers may avoid materializing intermediate results by pipelining data through operations.

Optimization Considerations

Pipelining
Pass results directly between operations without storing
Materialization
Store intermediate results for reuse in multiple later operations
Lazy Evaluation
Compute results only when needed, not at assignment time
Caching
Cache frequently used intermediate results

Common Mistakes

Mistake 1: Overwriting Original Relations

When using assignment to update, you replace the entire relation. Be careful not to accidentally lose data by forgetting to include unchanged tuples.

Mistake 2: Forgetting Union for INSERT

To insert, you must use R ← R ∪ NewData. Using just R ← NewData would replace the entire relation with only the new data.

Mistake 3: Not Using Union for DELETE

To delete, use R ← R - TuplesToRemove. Using R ← TuplesToRemove would replace R with only the deleted tuples (opposite of intended).

Mistake 4: Schema Mismatch

The left side variable must have the same schema as the right side expression result. Mismatched schemas cause errors.

Mistake 5: Assuming Persistence

Assignment creates temporary variables that exist only during the query session. They are not saved to the database permanently unless explicitly designed that way.
