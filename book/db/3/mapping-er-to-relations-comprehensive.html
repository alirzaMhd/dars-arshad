MAPPING ER TO RELATIONS

Database Systems — Converting ER/EER Diagrams to Relational Schema for Exam Preparation

Overview of Mapping Process

Mapping ER/EER to Relations converts conceptual schema to logical/physical schema.

General Process:
Step 1: Map Strong Entities → Relations
Step 2: Map Weak Entities → Relations
Step 3: Map Relationships → Relations/FKs
Step 4: Map Specialization/Generalization
Step 5: Map Category (Union Type)
Each step follows specific rules based on entity/relationship type.

Mapping Strong Entities

Rule:
Strong Entity → Relation
Create a relation with the same name as the entity. All simple attributes become columns. The primary key becomes the PK of the relation.
Example 1: Strong Entity Mapping

Entity: EMPLOYEE with attributes {EmpID, Name, Address, Phone}

CREATE TABLE EMPLOYEE (
  EmpID INT PRIMARY KEY,
  Name VARCHAR(100),
  Address VARCHAR(200),
  Phone VARCHAR(20)
);
Example 2: Composite Attributes

Entity: STUDENT with composite attribute Name (FirstName, LastName)

CREATE TABLE STUDENT (
  StudentID INT PRIMARY KEY,
  FirstName VARCHAR(50),
  LastName VARCHAR(50)
);

Composite attributes are flattened into separate columns.

Mapping Weak Entities

Rule:
Weak Entity → Relation with Owner PK as FK
Create a relation with the weak entity's attributes plus the owner entity's PK as a foreign key. The PK is composite (owner PK + partial key).
Example 3: Weak Entity Mapping

Weak Entity: DEPENDENT of EMPLOYEE

Attributes: {Name (partial key), BirthDate, Relationship}

CREATE TABLE DEPENDENT (
  EmpID INT,
  DepName VARCHAR(50),
  BirthDate DATE,
  Relationship VARCHAR(20),
  PRIMARY KEY (EmpID, DepName),
  FOREIGN KEY (EmpID) REFERENCES EMPLOYEE(EmpID)
);

PK is composite: Owner PK (EmpID) + Partial Key (DepName).

Example 4: M:N Relationship Mapping

Relationship: ENROLLS_IN (M:N between Student and Course)

CREATE TABLE ENROLLS_IN (
  StudentID INT,
  CourseID INT,
  EnrollDate DATE,
  Grade CHAR(1),
  PRIMARY KEY (StudentID, CourseID),
  FOREIGN KEY (StudentID) REFERENCES STUDENT(StudentID),
  FOREIGN KEY (CourseID) REFERENCES COURSE(CourseID)
);

M:N relationships always require a junction table with composite PK.

Example 5: Relationship with Attributes

Relationship: WORKS_ON (M:N with attribute Hours)

CREATE TABLE WORKS_ON (
  EmpID INT,
  ProjID INT,
  Hours DECIMAL(5,2), -- Relationship attribute
  PRIMARY KEY (EmpID, ProjID),
  FOREIGN KEY (EmpID) REFERENCES EMPLOYEE(EmpID),
  FOREIGN KEY (ProjID) REFERENCES PROJECT(ProjID)
);

Mapping Specialization/Generalization

Option 8A: Multiple Relations

• One relation for superclass

• One relation for each subclass

• Subclass PK = Superclass PK + FK

Option 8B: Single Relation

• One relation with all attributes

• Add type discriminator column

• NULLs for irrelevant attributes

Example 6: Specialization Mapping

Superclass: EMPLOYEE, Subclasses: ENGINEER, MANAGER

-- Option 8A: Multiple Relations
CREATE TABLE EMPLOYEE (
  EmpID INT PRIMARY KEY,
  Name VARCHAR(100)
);

CREATE TABLE ENGINEER (
  EmpID INT PRIMARY KEY,
  EngType VARCHAR(50),
  FOREIGN KEY (EmpID) REFERENCES EMPLOYEE(EmpID)
);

CREATE TABLE MANAGER (
  EmpID INT PRIMARY KEY,
  MgmtLevel INT,
  FOREIGN KEY (EmpID) REFERENCES EMPLOYEE(EmpID)
);

Key Rules to Remember

✓ Strong entities → simple relation

✓ Weak entities → composite PK with owner FK

✓ 1:1 → FK on either side

✓ 1:N → FK on N side

✓ M:N → junction table required

✓ Composite attributes → flatten into columns
