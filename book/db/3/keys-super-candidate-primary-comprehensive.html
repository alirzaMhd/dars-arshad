KEYS - SUPER, CANDIDATE, PRIMARY

Database Systems — Keys and Constraints for Exam Preparation

Super Key

A super key is a set of attributes that can uniquely identify each tuple in a relation.

Definition:
K ⊆ R such that no two tuples t₁, t₂ have t₁[K] = t₂[K]
A super key K is a subset of relation R where the values of K uniquely identify each tuple.
Example 1: Finding Super Keys

Given Employee(EmpID, Name, Email, Phone, DeptID):

Super KeyWhy?
{EmpID}Unique per employee
{Email}Unique per employee
{EmpID, Name}EmpID already unique, adding Name still unique
{EmpID, Name, Phone}Still unique (superset of a super key)
{Email, Phone}Email is unique, so this combination is unique

A relation can have many super keys. The minimum super keys are called candidate keys.

Key Points:

• A super key can contain extra attributes beyond what's needed for uniqueness

• Every candidate key is a super key, but not every super key is a candidate key

• Number of possible super keys can be very large (2ⁿ - 1 for n attributes)

Candidate Key

A candidate key is a minimal super key — no proper subset of it is also a super key.

Definition:
K is a candidate key ⟺ K is a super key AND ∀K' ⊂ K, K' is NOT a super key
Minimal super key: removing any attribute would lose the uniqueness property.
Example 2: Candidate Keys

For Employee(EmpID, Name, Email, Phone, DeptID):

  • {EmpID} → Candidate Key (minimal, can't remove anything)
  • {Email} → Candidate Key (minimal, unique)
  • {EmpID, Name} → NOT candidate key (EmpID alone is sufficient)
Example 3: Composite Candidate Key

For Enrollment(StudentID, CourseID, Semester, Grade):

  • {StudentID, CourseID, Semester} → Candidate Key (composite)
  • No single attribute can uniquely identify an enrollment
  • All three attributes together are needed and minimal

Properties

• Must be minimal

• Can be composite (multiple attributes)

• A relation can have multiple candidate keys

Naming Convention

• Candidate keys are underlined in schema

• Also called: candidate key, alternate key

Primary Key

The primary key is the candidate key chosen by the database designer to be the main identifier.

Constraints:
PRIMARY KEY = NOT NULL + UNIQUE
Primary key values cannot be NULL and must be unique across all tuples.
Example 4: Choosing Primary Key
Candidate KeysSelected PKReason
{EmpID}, {Email}EmpIDSimpler, numeric, never changes
{S#}, {Sname}S#Short, standardized code
{StudentID, CourseID, Semester}CompositeNo single attribute is sufficient
Primary Key Rules:

1. Must be NOT NULL — every tuple must have a value

2. Must be UNIQUE — no two tuples can have the same PK value

3. Values should be stable — avoid attributes that change

4. Prefer simple values — short, numeric when possible

5. Only one primary key per relation

Alternate Key

Candidate keys that are NOT chosen as the primary key are called alternate keys.

Example 5: Alternate Keys

If EmpID is chosen as PK:

  • EmpID → Primary Key
  • Email → Alternate Key (still unique, but not PK)
  • Alternate keys can still have UNIQUE constraints

Worked Examples

Example 6: Complete Key Analysis

Given: Course(CourseID, CourseName, Instructor, Room, Time)

Assume: CourseID is unique, Instructor+Room+Time is also unique (one class per room at a time)

Super Keys:

{CourseID}, {Instructor, Room, Time}, {CourseID, CourseName}, {CourseID, Instructor}, ...

Candidate Keys:

{CourseID} — minimal, unique

{Instructor, Room, Time} — minimal, unique combination

Primary Key:

CourseID — chosen as PK (simpler)

Alternate Key:

{Instructor, Room, Time} — candidate key not chosen as PK

Example 7: Weak Entity Keys

For Dependent(EmpID, DependentName, Relationship, Age):

  • No single attribute is unique
  • {EmpID, DependentName} → Composite candidate key
  • EmpID is a partial key (distinguishes dependents of different employees)
  • DependentName is a discriminator (distinguishes dependents of same employee)
