RELATIONSHIP TYPES (CARDINALITY RATIOS)

Database Systems — Complete Guide for Exam Preparation

1. One-to-One (1:1) Relationship

Definition:
1 ---- 1
Each instance of entity A is associated with at most one instance of entity B, and vice versa. Neither side has more than one related record.

Notation

Written as:

1 ---- 1 or 1:1

Line with "1" on both ends

Reading direction:

Each A has exactly one B

Each B has exactly one A

ER Diagram Representation

PERSON
person_id, name, dob
1
has
1
PASSPORT
passport_no, issue_date

Real-World Examples

Person — Passport

One person holds exactly one passport

One passport belongs to exactly one person

Employee — Department (Manager)

One employee manages exactly one department

One department has exactly one manager

Student — Student_ID

One student is assigned exactly one ID

One ID belongs to exactly one student

Country — Capital

One country has one capital city

One capital serves one country

Conversion to Relational Model

Option 1: Merge into One Table
PERSON_PASSPORT(person_id, name, dob, passport_no, issue_date)

Best when relationship is total on both sides (every person has a passport, every passport has a person).

Option 2: Foreign Key with UNIQUE Constraint
PERSON(person_id, name, dob, passport_no UNIQUE)
PASSPORT(passport_no, issue_date)

The UNIQUE constraint on passport_no ensures each passport is linked to only one person.

Common Mistake

Do NOT forget the UNIQUE constraint when using a foreign key for 1:1 relationships. Without it, multiple persons could reference the same passport — making it 1:n by mistake.

2. One-to-Many (1:n) Relationship

Definition:
1 ---- n
Entity A can be associated with many instances of entity B, but each instance of B is associated with at most one instance of A.

Notation

Written as:

1 ---- n or 1:n

Line with "1" on one side, "n" on the other

Reading direction:

One A has many B's

Each B belongs to exactly one A

ER Diagram Representation

DEPARTMENT
dept_id, dept_name
1
employs
n
EMPLOYEE
emp_id, name, salary

Real-World Examples

Department — Employees

One department has many employees

Each employee belongs to one department

Customer — Orders

One customer places many orders

Each order belongs to one customer

Author — Books

One author writes many books

Each book has one author

Mother — Children

One mother has many children

Each child has one mother

Conversion to Relational Model

Foreign Key in the "Many" Side
DEPARTMENT(dept_id, dept_name)
EMPLOYEE(emp_id, name, salary, dept_id FK → DEPARTMENT)

Always place the foreign key in the table on the "n" side, referencing the primary key of the "1" side.

Another Example: Customer Orders
CUSTOMER(cust_id, name, email)
ORDER(order_id, order_date, amount, cust_id FK → CUSTOMER)

Each order stores which customer placed it via cust_id.

Common Mistake

Never put the foreign key in the "1" side table. That would create a 1:1 relationship instead of 1:n. The foreign key always goes in the "many" side.

Key Point: The most common relationship type in relational databases. Almost every database has multiple 1:n relationships.

3. Many-to-Many (m:n) Relationship

Definition:
m ---- n
Each instance of entity A can be associated with many instances of entity B, and each instance of B can be associated with many instances of A.

Notation

Written as:

m ---- n or m:n

Line with "m" on one side, "n" on the other

Reading direction:

One A has many B's

One B has many A's

ER Diagram Representation

STUDENT
student_id, name
m
enrolls
n
COURSE
course_id, title

Real-World Examples

Student — Course

A student enrolls in many courses

A course has many students

Doctor — Patient

A doctor treats many patients

A patient can see many doctors

Actor — Movie

An actor appears in many movies

A movie has many actors

Product — Supplier

A product comes from many suppliers

A supplier provides many products

Conversion to Relational Model

Create a Junction (Bridge) Table
STUDENT(student_id, name)
COURSE(course_id, title)
ENROLLMENT(student_id FK, course_id FK, enrollment_date, grade)

The junction table contains foreign keys to both entities. The primary key is typically the combination of both foreign keys.

Junction Table with Extra Attributes
DOCTOR(doctor_id, name, specialty)
PATIENT(patient_id, name, dob)
TREATMENT(doctor_id FK, patient_id FK, visit_date, diagnosis, treatment)

Junction tables can hold additional attributes that describe the relationship itself (e.g., diagnosis, grade).

Common Mistake

Never try to represent m:n relationships with a single foreign key. You MUST create a junction table. Without it, data duplication and anomalies will occur.

Exam Tip

When asked to convert an m:n relationship to relational model, always create a new table. Name it after the relationship (e.g., ENROLLMENT, TREATMENT, APPEARANCE).

Quick Decision Guide

Step 1: Identify the two entities
Step 2: Ask: Can one A be linked to multiple B's?
Step 3: Ask: Can one B be linked to multiple A's?
Both No → 1:1
Only one Yes → 1:n
Both Yes → m:n

Warning: Common Mistakes

Mistake 1: Confusing 1:n with 1:1

Just because one side has "many" possibilities doesn't mean it's 1:n. Check BOTH directions. If an employee can have only one department AND a department has only one employee, it's 1:1, not 1:n.

Mistake 2: Forgetting UNIQUE for 1:1

When using a foreign key for 1:1, always add UNIQUE constraint. Without it, the relationship accidentally becomes 1:n.

Mistake 3: Not creating junction table for m:n

You cannot represent m:n with a single foreign key. Always create a new bridge/junction table containing foreign keys to both entities.

Mistake 4: Placing FK in wrong table for 1:n

The foreign key goes in the "many" side, not the "one" side. Placing it in the "one" side creates 1:1 or causes data loss.

Exam Tips

Identify Cardinality

Always ask: "Can one A have multiple B's?" and "Can one B have multiple A's?" Both answers determine the type.

Relational Conversion

1:1 → merge or FK + UNIQUE
1:n → FK in "many" side
m:n → junction table

Total vs Partial

Total participation: every entity must participate (double line in ER)
Partial: optional participation (single line)

Look for Keywords

"each" → 1 side
"many / several / multiple" → n side
"one and only one" → 1 side
