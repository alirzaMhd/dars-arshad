DATABASE DESIGN OVERVIEW

Entity-Relationship Modeling — Complete Guide for Exam

Definition of Database Design

Database design is the process of producing a detailed data model of a database. It defines the structure, relationships, constraints, and security mechanisms that a database will use to store and manage data efficiently.

Core Principle
Good Design = Minimized Redundancy + Maximized Integrity + Optimized Performance
A well-designed database avoids duplication, ensures data accuracy, and supports fast queries.

Three-Level Schema Architecture

The ANSI/SPARC architecture defines three levels of database schema to separate user views from physical storage:

External Level (View Level)

Individual user views. Each user sees only the data relevant to them. Multiple external views can exist for one database.

Example: A student sees grades; a professor sees all student grades in their course.
Conceptual Level (Logical Level)

The entire database structure as understood by the database administrator. Defines all entities, attributes, relationships, and constraints.

Example: Tables for Students, Courses, Enrollments with all relationships.
Internal Level (Physical Level)

How data is actually stored on disk. Includes indexing, file organization, and storage structures.

Example: B-tree indexes on student IDs, hash indexes on names.
Schema Mapping
External → Conceptual → Internal
Each level is mapped to the next. Changes at one level do not affect other levels (data independence).

Purpose of Database Design

  • Minimize Redundancy: Avoid storing the same data in multiple places
  • Ensure Data Integrity: Maintain accuracy and consistency through constraints
  • Optimize Performance: Design for efficient querying and updates
  • Support Security: Control access to sensitive data
  • Enable Scalability: Allow the database to grow without major redesign

Design Phases

  1. Requirements Analysis — Gather what users need from the database. Identify data items, relationships, and constraints.
  2. Conceptual Design — Create an ER diagram that represents entities, attributes, and relationships at a high level.
  3. Logical Design — Convert the ER diagram into a relational schema (tables, primary keys, foreign keys).
  4. Physical Design — Define storage structures, indexes, and partitioning for the target DBMS.
Common Mistake
Skipping requirements analysis and jumping straight to tables. This leads to missing relationships, redundant data, and costly redesigns later.

What is the ER Model?

The Entity-Relationship (ER) model was introduced by Peter Chen in 1976. It provides a graphical method for conceptual database design using ER diagrams.

Key Property
ER Model is Implementation-Independent
It describes data at a high level without being tied to any specific DBMS (Oracle, MySQL, etc.).

Three Main Components of ER Model

Entities

Real-world objects or concepts that can be distinguished from other objects.

Represented by: RECTANGLES in ER diagrams

Types:

  • Strong Entity: Has its own primary key (e.g., Student)
  • Weak Entity: Depends on a strong entity (e.g., Dependent)
Attributes

Properties or characteristics that describe an entity.

Represented by: OVALS in ER diagrams

Types:

  • Simple: Cannot be divided (e.g., Age)
  • Composite: Can be divided (e.g., Name → First, Last)
  • Derived: Calculated from other attributes (e.g., Age from DOB)
  • Multivalued: Can have multiple values (e.g., Phone Numbers)
Relationships

Associations between two or more entities.

Represented by: DIAMONDS in ER diagrams

Types:

  • One-to-One (1:1): Each entity relates to at most one of the other
  • One-to-Many (1:N): One entity relates to many of the other
  • Many-to-Many (M:N): Many entities relate to many of the other

ER Diagram Notation Reference

Component Symbol Description
Strong Entity Rectangle Independent entity with its own key
Weak Entity Double Rectangle Depends on a strong entity
Attribute Oval Property of an entity
Key Attribute Oval (underlined) Unique identifier for an entity
Multivalued Attribute Double Oval Can hold multiple values
Derived Attribute Dashed Oval Calculated at runtime
Relationship Diamond Association between entities
Weak Relationship Double Diamond Relationship involving a weak entity
Participation Constraint Line style Total (double line) or Partial (single line)

Relationship Cardinalities

One-to-One (1:1)

Each record in Table A relates to at most one record in Table B, and vice versa.

Example: Person — Passport
One-to-Many (1:N)

One record in Table A can relate to many records in Table B, but each B record relates to only one A record.

Example: Department — Employees
Many-to-Many (M:N)

Records in both tables can relate to multiple records in the other table. Requires a junction table in relational design.

Example: Students — Courses (via Enrollments)
Common Mistake
Confusing primary keys with foreign keys in relationships. The primary key uniquely identifies a record; a foreign key references a primary key in another table.

Step-by-Step Database Design Process

  1. Gather Requirements from Users
    Interview stakeholders. Understand what data needs to be stored, who will use it, and what operations are needed. Document everything.
  2. Identify Entities and Their Attributes
    Determine the main objects (entities) and their properties (attributes). Identify which attribute is the primary key for each entity.
  3. Determine Relationships Between Entities
    Find how entities are connected. Define the cardinality (1:1, 1:N, M:N) and participation constraints (total vs. partial).
  4. Draw ER Diagram
    Use rectangles (entities), ovals (attributes), and diamonds (relationships) to create a visual model of the database.
  5. Verify with Users
    Review the ER diagram with stakeholders. Check for missing entities, incorrect relationships, or wrong attributes. Iterate until approved.
  6. Convert ER to Relational Schema
    Transform entities into tables, attributes into columns, and relationships into foreign keys. Handle M:N relationships with junction tables.
  7. Implement in DBMS
    Create the actual database tables using SQL CREATE TABLE statements. Apply constraints (PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE).

ER to Relational Schema Conversion Rules

ER Component Relational Schema Equivalent
Strong Entity Create a table with all simple attributes; composite attributes become separate columns
Weak Entity Create a table including the primary key of the identifying entity as a foreign key
1:1 Relationship Add foreign key to either table (preferably the one with total participation)
1:N Relationship Add foreign key to the "many" side table
M:N Relationship Create a new junction table with foreign keys from both entities
Multivalued Attribute Create a separate table with the attribute and the entity's primary key
Derived Attribute Do NOT store in the database; calculate when needed

Participation Constraints

Total Participation

Every entity instance MUST participate in the relationship. Shown with a double line in ER diagrams.

Example: Every Employee MUST belong to a Department.
Partial Participation

Some entity instances may or may not participate. Shown with a single line in ER diagrams.

Example: Not every Department has a Manager.
Common Mistake
Forgetting to convert M:N relationships into junction tables. Directly adding a foreign key in one of the entity tables will cause data duplication and anomalies.
Exam Tip
When converting a 1:N relationship, always place the foreign key on the "many" side. Placing it on the "one" side will result in null values and poor design.

Worked Examples

Example 1: University Enrollment System

Scenario: A university tracks students, courses, and enrollments. Each student has an ID, name, and email. Each course has a code, title, and credits. A student can enroll in many courses; a course can have many students.

Step 1: Identify Entities & Attributes

Student
  • PK Student_ID
  • First_Name
  • Last_Name
  • Email
  • Date_of_Birth
Course
  • PK Course_Code
  • Title
  • Credits
  • Department
Enrollment
  • FK Student_ID
  • FK Course_Code
  • Enrollment_Date
  • Grade

Step 2: Determine Relationships

Student
Enrolls
Course

M:N relationship — Requires junction table "Enrollment"

Step 3: Relational Schema

Student(Student_ID [PK], First_Name, Last_Name, Email, Date_of_Birth)
Course(Course_Code [PK], Title, Credits, Department)
Enrollment(Student_ID [FK], Course_Code [FK], Enrollment_Date, Grade)
PRIMARY KEY (Student_ID, Course_Code)
Example 2: Hospital Management System

Scenario: A hospital tracks doctors, patients, and appointments. Each doctor has an ID, name, and specialization. Each patient has an ID, name, and phone number. A doctor can see many patients; a patient can see many doctors. Appointments are scheduled between them.

ER Design

Doctor
Treats
Patient

M:N relationship via junction table "Appointment"

Relational Schema

Doctor(Doctor_ID [PK], Name, Specialization, Phone)
Patient(Patient_ID [PK], Name, Phone, Address)
Appointment(Doctor_ID [FK], Patient_ID [FK], Date, Time, Reason)
PRIMARY KEY (Doctor_ID, Patient_ID, Date)
Example 3: Company Employee Hierarchy

Scenario: A company has departments, employees, and projects. Each department has a name and budget. Employees work in one department and can work on multiple projects. Each project has a name and deadline.

ER Design

Department
Employs
Employee
Works_On
Project

1:N between Department and Employee; M:N between Employee and Project

Relational Schema

Department(Dept_ID [PK], Dept_Name, Budget)
Employee(Emp_ID [PK], Emp_Name, Salary, Dept_ID [FK])
Project(Project_ID [PK], Project_Name, Deadline)
Works_On(Emp_ID [FK], Project_ID [FK], Hours_Spent)
PRIMARY KEY (Emp_ID, Project_ID)
Example 4: Library System with Weak Entity

Scenario: A library tracks books, authors, and book copies. A book can have multiple authors (M:N). Each book can have multiple physical copies (weak entity — a copy cannot exist without a book record).

Entities

Book (Strong)
  • PK ISBN
  • Title
  • Publication_Year
Author (Strong)
  • PK Author_ID
  • Name
  • Nationality
Book_Copy (Weak)
  • Partial Key Copy_Number
  • FK ISBN
  • Condition

Relational Schema

Book(ISBN [PK], Title, Publication_Year)
Author(Author_ID [PK], Name, Nationality)
Written_By(ISBN [FK], Author_ID [FK]) -- M:N junction
Book_Copy(ISBN [FK], Copy_Number, Condition)
PRIMARY KEY (ISBN, Copy_Number)

Common Exam Pitfalls

Pitfall 1: Identifying Entities
Not every noun is an entity. If something has no attributes of its own, it might be a relationship, not an entity. Ask: "Does this need to be tracked independently?"
Pitfall 2: Composite vs. Simple Attributes
A composite attribute (like Address: Street, City, Zip) should be broken into simple attributes in the relational model. Do not store the composite as a single column.
Pitfall 3: Ignoring Constraints
Always define primary keys, foreign keys, NOT NULL, and UNIQUE constraints. A schema without constraints does not enforce data integrity.
Pitfall 4: M:N in Relational Model
You cannot directly implement M:N relationships in a relational database. You MUST use a junction (association) table.
