ATTRIBUTES IN DATABASE DESIGN

Properties & Characteristics of Entities — Comprehensive Guide

Definition

What is an Attribute?
An attribute is a property or characteristic that describes an entity. It represents a single data element within a record and defines what information is stored about each entity instance.

Every entity in a database has attributes that capture its relevant data. For example, a Student entity might have attributes like Name, Student_ID, Date_of_Birth, and GPA.

Attribute Types

1. Simple (Atomic) Attribute
Cannot be divided further

A basic attribute that holds a single indivisible value.

Student_ID → 10234
Age → 21
Gender → 'M'
2. Composite Attribute
Can be divided into sub-parts

An attribute composed of multiple sub-attributes.

Name → {First_Name, Last_Name}
Address → {Street, City, State, Zip}
3. Multi-valued Attribute
Can have multiple values

An attribute that can hold more than one value for a single entity instance.

Phone_Numbers → {555-1234, 555-5678}
Skills → {Java, Python, SQL}
4. Derived Attribute
Computed from other attributes

An attribute whose value is calculated from other stored attributes.

Age = Current_Year - Birth_Year
Total = Quantity × Price
5. Stored Attribute
Value stored explicitly

An attribute whose value is stored directly rather than derived. Often used to avoid repeated computation.

Date_of_Birth (stored)
→ Age (derived from DoB)
6. Key Attribute
Uniquely identifies an entity

An attribute whose value is unique for each entity instance and can be used to distinguish records.

Student_ID → 10234
SSN → 123-45-6789
7. Composite Key
Key made of multiple attributes

A key attribute formed by combining two or more attributes to uniquely identify an entity.

Course_Section = {Course_ID, Section_No}
Order_Line = {Order_ID, Product_ID}
Key Points to Remember
  • Every entity must have at least one key attribute
  • Composite attributes are flattened in relational tables (sub-parts become columns)
  • Multi-valued attributes require a separate table in relational design
  • Derived attributes are often not stored but computed on demand

Domain

Definition
A domain is the set of all allowed values that an attribute can take. It defines the data type, range, and format for an attribute.

Common Domain Types

INTEGER
Whole numbers (positive/negative)
Example: 1, 42, -5, 1000
VARCHAR / STRING
Variable-length text
Example: 'John', 'Database Design'
DATE
Calendar dates
Example: '2026-07-10', '1999-12-31'
BOOLEAN
True/False values
Example: TRUE, FALSE
DECIMAL / FLOAT
Decimal numbers
Example: 3.14, 99.99, -0.5
ENUMERATION
Predefined set of values
Example: {'Low','Medium','High'}

Domain Constraints

Constraints restrict the values that can be stored in attributes to maintain data integrity.

  • TYPE Data Type Constraint — Ensures only the correct data type is stored.
    Age: INTEGER (cannot store 'abc')
  • RANGE Range Constraint — Restricts values to a specific range.
    Age: 0-150 (values outside range rejected)
  • FORMAT Format Constraint — Enforces a specific format or pattern.
    Email: 'user@domain.com' (regex pattern)
  • NULL NULL Constraint — Determines if a value can be NULL (missing/unknown).
    Phone_Number: NULL (optional field)
  • NOT NULL NOT NULL Constraint — Ensures every record must have a value.
    Student_ID: NOT NULL (required field)
  • DEFAULT Default Value — Provides a default when no value is specified.
    Status: DEFAULT 'Active'

NULL Values Explained

What is NULL?
NULL represents a missing, unknown, or inapplicable value. It is NOT the same as zero (0) or an empty string ('').
NULL is appropriate when:
  • Information is unknown (employee's middle name)
  • Value will be provided later (order ship date)
  • Attribute doesn't apply (fax number for person without fax)
NULL is NOT appropriate when:
  • Value is zero (student with 0 credits)
  • Value is empty string (name field left blank)
  • Value is unknown but must be entered (age unknown → use estimated)
Common NULL Pitfalls
  • NULL comparisons return UNKNOWN, not TRUE or FALSE: NULL = NULL → UNKNOWN
  • Use IS NULL or IS NOT NULL for NULL checks
  • Aggregate functions like COUNT ignore NULLs
  • NULL in arithmetic operations results in NULL

Common Mistakes to Avoid

Mistake 1: Using Multi-valued Attribute Instead of Composite

If a student has one phone number, it's Simple. If they have multiple, it's Multi-valued (separate table needed). Don't confuse with composite.

Mistake 2: Storing Derived Attributes

If you store both Date_of_Birth and Age, you risk inconsistency when Age isn't updated. Store Date_of_Birth and derive Age.

Mistake 3: Not Identifying Key Attributes

Every entity must have at least one key attribute. Without it, you cannot uniquely identify records in the table.

Mistake 4: Flattening Composite Attributes Incorrectly

When converting composite attributes to relational tables, use the sub-part names as columns, not the parent name. Use First_Name, Last_Name — not Name.

Mistake 5: Using NULL Carelessly

Don't use NULL when a default or zero is appropriate. NULL means unknown or inapplicable, not "not provided".
