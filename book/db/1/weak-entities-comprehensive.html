WEAK ENTITIES

Database Design — Comprehensive Guide

Definition

A weak entity is an entity that cannot be uniquely identified by its own attributes alone. It depends on an identifying (owner) entity for its existence and identification.

Key Idea
Partial Key + Owner's PK = Full Identification
The weak entity's partial key combined with its owner's primary key uniquely identifies each weak entity instance.

Core Concepts

Partial Key (Discriminator)
An attribute that uniquely identifies weak entity instances within the same owner entity.

Shown with dashed underline in ER diagrams.

Identifying Relationship
The relationship connecting weak entity to its owner.

Represented by a double diamond in ER diagrams.

Owner Entity
The strong entity on which the weak entity depends.

Its primary key becomes part of the weak entity's identification.

Existence Dependency
Weak entity cannot exist without the owner entity.

If owner is deleted, all its weak entities are also deleted.

Classic Example: Employee → Dependent

Scenario

An Employee can have dependents (spouse, children) who receive benefits. A dependent is identified by their relationship to a specific employee.

Employee (Owner/Strong)
  • EmpID (PK)
  • Name
  • Department
Dependent (Weak)
  • EmpID (FK from Employee)
  • DependentName (Partial Key)
  • Relationship
  • BirthDate
Identification
(EmpID, DependentName) → Dependent
No two dependents of the same employee can share the same name, but two different employees can each have a dependent named "John".

Key Characteristics

No Primary Key of Its Own
Weak entity lacks a unique identifier using only its own attributes.
Partial Key (Discriminator)
Has an attribute that distinguishes instances within the same owner.

Shown with dashed underline in ER diagrams.

Existence Dependency
Cannot exist without the owner entity.

If owner is deleted, all its weak entities are also deleted.

Cascading Delete
Deletion of owner automatically deletes all associated weak entities.

Complete Identification

Primary Key of Weak Entity
PK(Owner) + Partial Key = Composite PK of Weak Entity
The weak entity's primary key is always a composite key combining the owner's primary key and its own partial key.
Example: Course → Section

Course (strong): CourseID (PK), CourseName

Section (weak): CourseID (FK) + SectionNum (Partial Key) → Composite PK

Section 1 of CS101 and Section 1 of CS202 are different sections — identified by (CourseID, SectionNum).

Key Takeaway

Golden Rule
Weak Entity = No PK + Existence Dependency + Partial Key
If an entity meets all three conditions, it is a weak entity that requires an owner entity for complete identification.

Worked Examples

Example 1: Employee → Dependent (Classic)

Employee (strong): EmpID (PK), EmpName, Salary

Dependent (weak): EmpID (FK), DepName (Partial Key), Relationship, BirthDate

Identification
PK = (EmpID, DepName)
Dependent cannot be identified by name alone — two employees can each have a "John". Must combine with EmpID.
Example 2: Course → Section

Course (strong): CourseID (PK), CourseName, Credits

Section (weak): CourseID (FK), SectionNum (Partial Key), Schedule, Room

Identification
PK = (CourseID, SectionNum)
Section 1 of CS101 ≠ Section 1 of CS202. Section number only meaningful within a course.
Example 3: Building → Room

Building (strong): BuildingID (PK), BuildingName, Address

Room (weak): BuildingID (FK), RoomNum (Partial Key), Capacity, Type

Identification
PK = (BuildingID, RoomNum)
Room 101 in Building A ≠ Room 101 in Building B. Room number is local to a building.
Example 4: Order → Order_Item

Order (strong): OrderID (PK), OrderDate, CustomerID

Order_Item (weak): OrderID (FK), ItemNum (Partial Key), ProductID, Quantity, Price

Identification
PK = (OrderID, ItemNum)
Item 1 in Order 1001 ≠ Item 1 in Order 1002. Item number is local to an order.
Example 5: Person → Passport (Conditional)

Person (strong): PersonID (PK), FullName, BirthDate

Passport (weak if no unique passport ID): PersonID (FK), PassportType (Partial Key), IssueDate

Note
If passport has its own unique ID → Strong Entity. If identified only by person → Weak Entity.
Whether Passport is weak depends on whether it has a globally unique identifier or not.

Relational Conversion

When converting weak entities to relational tables:

Conversion Rule
Weak Entity Table = Partial Key + Owner's PK (as FK) + Own Attributes
The owner's primary key becomes a foreign key AND part of the weak entity's composite primary key.
Relational Schema
-- Strong entity (Owner)
CREATE TABLE Employee (
  EmpID INT PRIMARY KEY,
  EmpName VARCHAR(100),
  Salary DECIMAL
);

-- Weak entity
CREATE TABLE Dependent (
  EmpID INT,
  DepName VARCHAR(100),
  Relationship VARCHAR(50),
  BirthDate DATE,
  PRIMARY KEY (EmpID, DepName),
  FOREIGN KEY (EmpID) REFERENCES Employee(EmpID)
    ON DELETE CASCADE
);
Note: ON DELETE CASCADE ensures that when an employee is deleted, all their dependents are automatically removed.

Common Mistakes

Mistake 1: Treating partial key as full primary key

Using only DepName as PK is wrong — two different employees can have dependents with the same name.

Mistake 2: Forgetting cascading delete

Always use ON DELETE CASCADE for weak entity foreign keys — weak entities cannot exist without their owner.

Mistake 3: Missing the identifying relationship

The double diamond (identifying relationship) is mandatory — it connects weak entity to its owner.

Mistake 4: Not using composite PK

The weak entity's primary key must be composite: Owner's PK + Partial Key. Never use just the partial key.

Exam Tips

  • Look for double rectangles and double diamonds — they signal weak entities.
  • Weak entities always have existence dependency — ask "can this exist without its owner?"
  • Partial key is dashed underline — it only distinguishes within the same owner.
  • In relational conversion, always include owner's PK as FK + part of composite PK.
  • Common weak entity patterns: Dependent, Section, Room, Order_Item, Chapter, Episode.
  • When in doubt: if entity needs another entity's ID to be unique → it's weak.
