ENTITIES IN DATABASE DESIGN

Comprehensive Guide to Entity Concepts in ER Modeling

Entity Definition

Definition
An entity is a thing or object in the real world that is distinguishable from all other objects.
Entities can be tangible (physical objects like students, cars) or intangible (abstract concepts like courses, bank accounts).

Every entity has a set of properties called attributes that describe it. For example, a Student entity might have attributes like Student_ID, Name, Age, and Major.

Entity vs Entity Type vs Entity Set

These three terms are often confused but have distinct meanings:

Entity

A single, specific instance of a real-world object.

Example: A particular student named "John Smith" with ID 12345.

Entity Type

Defines the collection (or set) of entities that share the same attributes. It is the blueprint or schema.

Example: The STUDENT entity type has attributes: Student_ID, Name, Age, Major.

Entity Set

The collection of all entities of a particular entity type at any point in time. It is the actual data instance.

Example: All students currently enrolled in the university.

Analogy

Think of it like this:

  • Entity Type = The concept of "Car" (make, model, year, color)
  • Entity = Your specific car (2024 Toyota Camry, blue)
  • Entity Set = All cars in the parking lot right now

Strong Entity

Strong Entity
An entity that can exist independently and has its own key attribute (primary key).
Strong entities do not depend on other entities for their identification. They can be uniquely identified by their own attributes.
Student
Key: Student_ID

Students exist independently. A Student can exist without being enrolled in any course.

Course
Key: Course_ID

Courses exist independently. A Course can exist even if no students are enrolled.

Employee
Key: Employee_ID

Employees exist independently. An Employee can exist without having dependents.

Department
Key: Dept_ID

Departments exist independently. A Department can exist even if it has no employees assigned yet.

Key Attributes

A key attribute is the attribute (or combination of attributes) that uniquely identifies each entity in an entity set.

Key Attribute Notation
EntityName( PrimaryKey, Attribute1, Attribute2, ... )
The underline indicates the key attribute in ER notation.
Examples of Key Attributes
  • Student( Student_ID, Name, Age, Major )
  • Course( Course_ID, Title, Credits, Department )
  • Employee( Employee_ID, Name, Salary, Hire_Date )
  • Account( Account_Number, Balance, Type, Open_Date )
Common Mistake

Do NOT use Name as a primary key. Names are not unique. Always use a surrogate key (like ID numbers) or a natural key (like SSN) that guarantees uniqueness.

Strong Entity

Strong Entity
Has its own primary key and can exist independently of other entities.
Strong entities are the foundation of an ER model. They represent the main objects of interest in the database.
Characteristics of Strong Entities
  • Has a primary key that uniquely identifies each instance
  • Can exist independently without depending on other entities
  • Represented by a single rectangle in ER diagrams
  • Has its own set of attributes
Student
Key: Student_ID

Can exist without being enrolled in any course or having any dependents.

Employee
Key: Emp_ID

Can exist without having any dependents or being assigned to any project.

Book
Key: ISBN

Can exist without being borrowed by any member.

Customer
Key: Customer_ID

Can exist without having any accounts or transactions.

Weak Entity

Weak Entity
Depends on a strong entity (owner entity) and does not have a complete key of its own.
A weak entity has a partial key (discriminator) that, combined with the owner entity's key, uniquely identifies it.
Characteristics of Weak Entities
  • Does NOT have a primary key of its own
  • Has a partial key (also called discriminator) - underlined with dashed line
  • Cannot exist without its owner entity
  • Connected to owner via an identifying relationship
  • Represented by a double rectangle in ER diagrams
Dependent
Owner: Employee

A dependent (child/spouse) of an employee. Cannot exist without the employee. Partial key: Name.

Section
Owner: Course

A section of a course. Cannot exist without the course. Partial key: Section_Number.

Room
Owner: Building

A room in a building. Cannot exist without the building. Partial key: Room_Number.

Item
Owner: Order

An item in an order. Cannot exist without the order. Partial key: Item_Number.

Identifying Relationship

Identifying Relationship
The relationship that connects a weak entity to its owner entity.
This is a special type of relationship that provides the missing key for the weak entity. Represented by a double diamond in ER diagrams.
Example: Identifying Relationship

Employee ——(Double Diamond: HAS)—— Dependent

Here, "HAS" is the identifying relationship. The Dependent entity cannot be uniquely identified by its partial key (Name) alone. It needs the Employee's key (Emp_ID) to form a complete identification.

Composite Key for Dependent: (Emp_ID, Name)

Key Concept

The primary key of a weak entity is formed by combining: Owner Entity's Key + Weak Entity's Partial Key. For example, Dependent's key = (Emp_ID + Dependent_Name).

When to Use Weak Entities

Use Weak Entities When:
  • The entity logically depends on another entity for its meaning
  • The entity cannot be uniquely identified by its own attributes alone
  • The entity has a natural owner that provides context
  • The entity should be deleted when the owner is deleted
Common Mistake

Do NOT create weak entities unnecessarily. If an entity can be uniquely identified by its own attributes and can exist independently, it should be a strong entity, not a weak one.

ER Diagram Symbols for Entities

Entity-Relationship (ER) diagrams use specific symbols to represent different types of entities and relationships:

Symbol Represents Description
▭ Strong Entity Single rectangle - represents an entity that can exist independently
▢▢ Weak Entity Double rectangle - represents an entity that depends on another entity
◇ Relationship Single diamond - represents a regular relationship between entities
◇◇ Identifying Relationship Double diamond - connects a weak entity to its owner

Attribute Notation

Attribute Type Notation Example
Simple Attribute Oval with attribute name Name, Age
Key Attribute Oval with underlined name Student_ID
Partial Key Oval with dashed underline Name (for Dependent)
Composite Attribute Oval connected to sub-ovals Address → (Street, City, Zip)
Multivalued Attribute Double oval Phone_Numbers
Derived Attribute Dashed oval Age (derived from Birth_Date)

Entity Naming Conventions

Best Practices for Naming Entities
  • Use singular nouns (Student, not Students)
  • Use PascalCase or snake_case consistently
  • Be descriptive (Employee, not Person)
  • Avoid abbreviations (Department, not Dept)
  • Use meaningful names that reflect the real-world concept

Worked Example 1: University System

Identify Entities in a University Database

Strong Entities:

  • Student - Key: Student_ID, Attributes: Name, Age, Major, Email
  • Course - Key: Course_ID, Attributes: Title, Credits, Department
  • Professor - Key: Prof_ID, Attributes: Name, Rank, Department, Salary

Weak Entities:

  • Section - Owner: Course, Partial Key: Section_Number, Attributes: Semester, Year, Room

A Section cannot exist without a Course. The same Section_Number can appear in different courses, so it's not globally unique.

Worked Example 2: Hospital System

Identify Entities in a Hospital Database

Strong Entities:

  • Patient - Key: Patient_ID, Attributes: Name, DOB, Gender, Phone
  • Doctor - Key: Doctor_ID, Attributes: Name, Specialty, Phone, Salary
  • Department - Key: Dept_ID, Attributes: Name, Location, Head_Doctor

Weak Entities:

  • Appointment - Owner: Patient, Partial Key: Appointment_Date, Attributes: Time, Purpose, Doctor

An Appointment cannot exist without a Patient. A patient can have multiple appointments, but each appointment is uniquely identified by (Patient_ID + Appointment_Date).

Worked Example 3: Company System

Identify Entities in a Company Database

Strong Entities:

  • Employee - Key: Emp_ID, Attributes: Name, Salary, Hire_Date, Job_Title
  • Project - Key: Project_ID, Attributes: Name, Budget, Start_Date, End_Date
  • Department - Key: Dept_ID, Attributes: Name, Location, Budget

Weak Entities:

  • Dependent - Owner: Employee, Partial Key: Name, Attributes: Relationship, Birth_Date, Gender

A Dependent cannot exist without an Employee. Two employees can have dependents with the same name, but within one employee's dependents, names must be unique.

Dependent's Primary Key
(Emp_ID, Dependent_Name)
Composite key: Owner's key + Partial key

Worked Example 4: Library System

Identify Entities in a Library Database

Strong Entities:

  • Book - Key: ISBN, Attributes: Title, Author, Publisher, Year
  • Member - Key: Member_ID, Attributes: Name, Address, Phone, Join_Date

Weak Entities:

  • Borrow - Owner: Book, Partial Key: Borrow_Date, Attributes: Return_Date, Member_ID

A Borrow record cannot exist without a Book. The same book can be borrowed multiple times, so we need (ISBN + Borrow_Date) to uniquely identify each borrow record.

Borrow's Primary Key
(ISBN, Borrow_Date)
If a book can be borrowed multiple times on the same day, add Member_ID to the key

Worked Example 5: Banking System

Identify Entities in a Banking Database

Strong Entities:

  • Account - Key: Account_Number, Attributes: Balance, Type, Open_Date
  • Customer - Key: Customer_ID, Attributes: Name, Address, Phone, SSN
  • Branch - Key: Branch_ID, Attributes: Name, Address, Phone

Weak Entities:

  • Transaction - Owner: Account, Partial Key: Transaction_ID, Attributes: Date, Amount, Type, Description

A Transaction cannot exist without an Account. Transactions are identified by (Account_Number + Transaction_ID).

Common Mistakes

Mistake 1: Using Names as Primary Keys

Names are not unique. Two people can have the same name. Always use a unique identifier like ID numbers.

Wrong: Student(Name, Age, Major)

Correct: Student(Student_ID, Name, Age, Major)

Mistake 2: Creating Weak Entities Unnecessarily

If an entity can be uniquely identified by its own attributes and can exist independently, it should be a strong entity.

Wrong: Making "Book" a weak entity of "Library"

Correct: Book is a strong entity with ISBN as its own key

Mistake 3: Confusing Entity Type with Entity Set

Entity Type is the blueprint (schema). Entity Set is the actual data (instance). Don't use them interchangeably.

Wrong: "The entity set has attributes Name and Age"

Correct: "The entity type has attributes Name and Age"

Mistake 4: Forgetting to Include Owner's Key in Weak Entity

The primary key of a weak entity is ALWAYS a composite key that includes the owner's primary key.

Wrong: Dependent(Name, Relationship, Birth_Date)

Correct: Dependent(Emp_ID, Name, Relationship, Birth_Date)

Mistake 5: Not Using Identifying Relationships

Weak entities MUST be connected to their owner entity via an identifying relationship (double diamond).

Wrong: Connecting weak entity with a regular relationship (single diamond)

Correct: Using double diamond for identifying relationship
