ANSI/SPARC Three-Schema Architecture

External, Conceptual, Internal Layers — Complete Guide for Exam Preparation

Three-Schema Architecture

The ANSI/SPARC architecture defines 3 layers (also called "views") that separate user views from physical data storage.

Architecture Layers
External Layer → Conceptual Layer → Internal Layer
Also called: Outer → Middle → Inner. Each layer provides data independence.

Architecture Diagram

┌─────────────────────────────────────────────────────────┐ │ EXTERNAL LAYER │ │ (User Views / Access Levels) │ │ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ │ │ User A │ │ User B │ │ User C │ │ User D │ │ │ │ View │ │ View │ │ View │ │ View │ │ │ └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘ │ ├───────┼────────────┼────────────┼────────────┼─────────┤ │ └────────────┼────────────┼────────────┘ │ │ ▼ ▼ │ ├─────────────────────────────────────────────────────────┤ │ CONCEPTUAL LAYER │ │ (Logical Design / ER Model) │ │ ┌─────────────────────────────────────────────────┐ │ │ │ Analysis Model (ER) → Design Model (Relational)│ │ │ └─────────────────────────────────────────────────┘ │ ├─────────────────────────────────────────────────────────┤ │ INTERNAL LAYER │ │ (Physical Storage / DDL) │ │ ┌─────────────────────────────────────────────────┐ │ │ │ Tables, Indexes, Files on Disk │ │ │ └─────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────┘

Layer Summary

Layer Synonym Purpose Audience
External Outer / View User-specific data views End Users
Conceptual Middle / Logical Entire database structure DBA, Designers
Internal Inner / Physical Physical storage details System Admin

External Layer (Outermost)

The external layer defines user-specific views of the database. Each user sees only the portion they need.

External Layer Purpose
User View = Only What You Need to See
Implements "need to know" principle — users access only relevant data.

Key Characteristics

User Views

Each user sees different portion of database

Need to Know

Only relevant data is visible

Outermost Layer

Closest to end users

Access Levels

Different permissions for different users

Example 3: SQL Views

Implementing External Layer with SQL Views
-- Create view for students (External Layer) CREATE VIEW StudentView AS SELECT StudentID, FirstName, LastName, Major FROM Students WHERE StudentID = CURRENT_USER_ID; -- Create view for professors CREATE VIEW ProfessorView AS SELECT s.StudentID, s.FirstName, s.LastName, c.CourseName, e.Grade FROM Students s JOIN Enrollments e ON s.StudentID = e.StudentID JOIN Courses c ON e.CourseID = c.CourseID WHERE c.ProfessorID = CURRENT_USER_ID; -- Student queries their view SELECT * FROM StudentView; -- Only sees their own information -- Professor queries their view SELECT * FROM ProfessorView; -- Only sees students in their courses
SQL Views implement the external layer by restricting what each user can see.

Example 4: Security Implementation

Access Control at External Layer
-- Different users, different views -- HR Manager sees everything CREATE VIEW HRView AS SELECT * FROM Employees; -- Department Manager sees own department CREATE VIEW DeptManagerView AS SELECT * FROM Employees WHERE DepartmentID = USER_DEPARTMENT; -- Employee sees only own info CREATE VIEW EmployeeView AS SELECT EmployeeID, FirstName, LastName, Email FROM Employees WHERE EmployeeID = CURRENT_USER_ID; -- Assign views to roles GRANT SELECT ON HRView TO 'hr_manager'; GRANT SELECT ON DeptManagerView TO 'dept_manager'; GRANT SELECT ON EmployeeView TO 'employee';

Conceptual Layer (Middle)

The conceptual layer contains two sub-layers: the analysis model and the design model.

Conceptual Layer Structure
Analysis Model → Design Model
Analysis = ER Model (general view) → Design = Relational Model (specific view)

Two Sub-Layers

Analysis Model
Conceptual Design

ER Model
General View
Independent of specific DBMS

Design Model
Logical Design

Relational Model
Specific View
Depends on chosen model

Analysis Model (ER Design)

ER Diagram for University
┌──────────┐ ┌──────────┐ │ Student │ │ Course │ ├──────────┤ ├──────────┤ │ ID │ │ Code │ │ Name │──M:N──▶│ Title │ │ Major │ │ Credits │ │ DOB │ │ Dept │ └──────────┘ └──────────┘ │ │ │ │ ▼ ▼ ┌─────────────────────────────────┐ │ Enrollment │ ├─────────────────────────────────┤ │ StudentID (FK) │ │ CourseCode (FK) │ │ Semester │ │ Grade │ └─────────────────────────────────┘ This is the CONCEPTUAL/GENERAL view. Independent of any specific database software.

Design Model (Relational)

Relational Tables Implementation
-- Design Model converts ER to Tables CREATE TABLE Students ( StudentID INT PRIMARY KEY, Name VARCHAR(50), Major VARCHAR(30), DOB DATE ); CREATE TABLE Courses ( CourseCode VARCHAR(10) PRIMARY KEY, Title VARCHAR(50), Credits INT, Department VARCHAR(30) ); CREATE TABLE Enrollments ( StudentID INT, CourseCode VARCHAR(10), Semester VARCHAR(10), Grade CHAR(2), PRIMARY KEY (StudentID, CourseCode, Semester), FOREIGN KEY (StudentID) REFERENCES Students(StudentID), FOREIGN KEY (CourseCode) REFERENCES Courses(CourseCode) ); This is the CONCEPTUAL/SPECIFIC view. Uses relational model (tables).

M:N Relationship → New table EmployeeProjects(EmpID, ProjID, Hours) Result: CREATE TABLE Department (...); CREATE TABLE Employee (...FOREIGN KEY...); CREATE TABLE EmployeeProjects (...);

Why Two Sub-Layers?

Internal Layer (Innermost/Physical)

The internal layer describes how data is physically stored on media. It deals with files, blocks, and storage allocation.

Internal Layer Purpose
Physical Storage = How Data Lives on Disk
Uses DDL for table creation, DML for query implementation. Manages actual file organization.

Internal Layer Components

File Organization

How data files are structured on disk

Index Structures

B-trees, hash indexes for fast access

Storage Allocation

Disk space management

Data Compression

Reducing storage requirements

Example 1: Physical Storage

How Tables Are Stored
Students Table on Disk: File: students.dat ┌─────────────────────────────────────────────────┐ │ Block 1: [S1|Smith|London|20][S2|Jones|Paris|10]│ │ Block 2: [S3|Blake|Paris|30][S4|Clark|London|20]│ │ Block 3: [S5|Adams|Athens|30] │ └─────────────────────────────────────────────────┘ Each block contains: - Header (block number, record count) - Data records (actual data) - Footer (next block pointer) Storage Details: - Block size: 4KB (typical) - Records per block: Varies - File extension: .dat, .dbf, .mdf

Example 2: Index Implementation

B-Tree Index on StudentID
B-Tree Index Structure: [S3] / \ [S1,S2] [S4,S5] / | \ / | \ [S1][S2] [S4][S5] Index File: students_idx.dat ┌─────────────────────────────────────┐ │ Key Value │ Block Number │ Record # │ ├─────────────────────────────────────┤ │ S1 │ 1 │ 1 │ │ S2 │ 1 │ 2 │ │ S3 │ 2 │ 1 │ │ S4 │ 2 │ 2 │ │ S5 │ 3 │ 1 │ └─────────────────────────────────────┘ Query: SELECT * FROM Students WHERE StudentID = 'S3' 1. Search index → Found at Block 2, Record 1 2. Go directly to Block 2 3. Retrieve record

Example 3: DDL in Internal Layer

Physical Implementation with DDL
-- DDL creates the physical structure CREATE TABLE Suppliers ( S# CHAR(5) NOT NULL, Sname CHAR(20), City CHAR(15), Status INT, PRIMARY KEY (S#) ); -- DBMS translates to physical storage: -- 1. Allocates disk space -- 2. Creates data file -- 3. Creates index on S# -- 4. Sets up row format -- 5. Initializes free space map -- DML implements queries SELECT * FROM Suppliers WHERE City = 'London'; -- DBMS translates to: -- 1. Check index (if exists on City) -- 2. Read relevant blocks -- 3. Filter records -- 4. Return results

Common File Organizations
Type Description Best For

Sequential Records in key order Range queries
Hash Records by hash of key Exact lookups
Clustered Related records together Joins

Example 5: Storage Optimization

Internal Layer Optimizations
Optimization Techniques: 1. Data Compression - Reduce storage space - Trade CPU for I/O 2. Denormalization - Duplicate data for speed - Trade storage for performance 3. Partitioning - Split large tables - Improve query performance 4. Archiving - Move old data offline - Keep active data fast Example: Partitioning by Year Orders_2022 (archived) Orders_2023 (archived) Orders_2024 (active)

Mapping Between Layers

Mapping between layers provides data independence. Changes in one layer don't affect others.

Data Independence Types
Logical Independence + Physical Independence
Logical: Conceptual changes don't affect External. Physical: Internal changes don't affect Conceptual.

Mapping Types

Mapping Between Independence Type Example Change
External ↔ Conceptual User views ↔ Database structure Logical Independence Add column to table
Conceptual ↔ Internal Database structure ↔ Physical storage Physical Independence Move files to new disk

Example 1: Logical Independence

Conceptual Change, External Unaffected
Before Change: Conceptual: Students(ID, Name, City) External: StudentView shows ID, Name After Change (Add Phone column): Conceptual: Students(ID, Name, City, Phone) External: StudentView STILL shows ID, Name StudentView definition didn't change! Student doesn't notice new column. This is LOGICAL DATA INDEPENDENCE.

Example 2: Physical Independence

Internal Change, Conceptual Unaffected
Before Change: Internal: Students stored on Disk1 Conceptual: Students table exists After Change (Move to SSD): Internal: Students stored on SSD Conceptual: Students table UNCHANGED The table structure didn't change! Queries work the same way. This is PHYSICAL DATA INDEPENDENCE.

Example 3: Mapping Diagram

Layer Interaction Flow
User Request Flow: End User → External Layer (view) ↓ External ↔ Conceptual Mapping ↓ Conceptual Layer (logical design) ↓ Conceptual ↔ Internal Mapping ↓ Internal Layer (physical storage) ↓ Data Retrieved ↓ Reverse path back to user Each mapping provides independence!
