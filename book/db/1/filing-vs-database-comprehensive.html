Filing System vs Database System

Database Systems — Complete Guide for Exam Preparation

Two Approaches to Data Management

Data can be managed using either a Filing System (traditional, procedural) or a Database System (modern, non-procedural). Understanding the differences is essential for exams.

Key Distinction
Filing System = Application-centric
Database System = Data-centric
Filing systems serve individual applications. Database systems serve all applications through centralized management.

The Castle Analogy

DBMS as a Castle

DBMS is like a castle that protects the data:

  • King = DBMS (controls everything)
  • Queen = Data (most important)
  • Princes = Tables, Views, Indexes
  • Guards = Security mechanisms
  • Walls = Access controls
  • Gate = SQL interface

The King (DBMS) controls who can access the Queen (data) and how. In a filing system, there is no king — everyone has their own copy of the queen!

Filing System — Characteristics

A filing system (also called file processing system) is a traditional approach where each application maintains its own data files.

1. Each Application Has Its Own Files

Example: Separate Files per Application
StudentApp/ → students.dat
AccountApp/ → accounts.dat
ExamApp/ → exams.dat

Each application stores its data in separate files. There is no sharing between applications.

2. Data is Redundant Across Applications

Example: Duplicated Student Data
StudentApp/students.dat ExamApp/exams.dat
101, Ahmed, CS 101, Ahmed, CS
102, Sara, CS 102, Sara, CS

Student name and department are stored in BOTH files — this is natural redundancy.

3. No Centralized Control

Each application manages its own data independently. There is no single authority overseeing all data.

Example: No Central Authority
  • StudentApp team can change student name format
  • ExamApp team doesn't know about the change
  • Data becomes inconsistent between applications

4. Program-Data Dependence

Programs are directly dependent on file structure. Changing file format requires changing all programs.

Example: File Structure Change
-- Original: students.dat (fixed-length records)
struct Student {
  int id; // 4 bytes
  char name[20]; // 20 bytes
}

-- If we add phone number (10 bytes):
-- ALL programs that read students.dat must be updated!

5. Security is Difficult

Each application implements its own security. There is no统一 access control.

Example: Security Issues
  • StudentApp allows read access to all staff
  • ExamApp allows read access to faculty only
  • No way to enforce consistent security policies

6. No Concurrent Access Support

Multiple users accessing the same file simultaneously can cause data corruption.

Example: Concurrent Access Problem
  • User A reads student record
  • User B reads same record
  • User A updates and saves
  • User B updates and saves — User A's changes are LOST!

Database System — Characteristics

A database system uses a DBMS (Database Management System) to centrally manage all data. It is the modern, non-procedural approach.

1. Centralized Data Storage via DBMS

Example: Centralized Storage
-- All applications access same data through DBMS
StudentApp ──┐
AccountApp ──┼──→ DBMS ──→ Database
ExamApp ─────┘

All applications connect to the DBMS, which manages a single copy of the data.

2. Data is Shared, Reduced Redundancy

Example: Single Source of Truth
Students Table (in DB)
101, Ahmed, CS
102, Sara, CS

All applications access the same Students table — no duplication.

3. DBMS Controls Access

Example: Centralized Security
-- DBMS enforces access control
GRANT SELECT ON Students TO student_app;
GRANT SELECT, UPDATE ON Grades TO exam_app;
REVOKE ALL ON Salary FROM public;

The DBMS acts as the gatekeeper — all access goes through it.

4. Data Independence

Programs are independent of data structure. Changing storage format doesn't affect programs.

Example: Logical Data Independence
-- Add new column to Students table
ALTER TABLE Students ADD Phone VARCHAR(15);

-- Existing programs still work!
-- They don't need to know about the Phone column

5. Security Through Access Levels

Example: Role-Based Access
Role Access Level
Admin Full access (CRUD)
Faculty Read/Write grades
Student Read own data only
Guest No access

6. Supports Concurrent Access

DBMS handles multiple users accessing data simultaneously through locking and transaction management.

Example: Concurrency Control
  • User A begins transaction
  • DBMS locks the record
  • User B must wait until A commits
  • Data integrity is maintained

Example 1: University Scenario

Filing System Approach
-- Student Affairs has its own file
student_affairs/students.txt

-- Registrar has its own copy
registrar/students.txt

-- Library has its own copy
library/members.txt

-- Same student data in 3 places!
Database System Approach
-- Single Students table
CREATE TABLE Students (
  ID INT PRIMARY KEY,
  Name VARCHAR(50),
  Dept VARCHAR(20)
);

-- All departments access same table
-- Student Affairs, Registrar, Library all query same DB

Example 2: Adding New Data Field

Filing System: Painful Change
  • Add "Phone" to student file format
  • Update Program 1 (student registration)
  • Update Program 2 (grade system)
  • Update Program 3 (library system)
  • Update Program 4 (report generator)
  • Test ALL programs
Database System: Simple Change
ALTER TABLE Students ADD Phone VARCHAR(15);
-- Done! Existing programs unaffected

Example 3: Multi-User Access

Filing System: Race Condition
  • Two staff update same student record
  • Staff A reads: GPA = 3.0
  • Staff B reads: GPA = 3.0
  • Staff A saves: GPA = 3.2
  • Staff B saves: GPA = 3.5 (overwrites A's change!)
  • Result: GPA should be 3.5, but A's update is lost
Database System: Transaction Control
BEGIN TRANSACTION;
SELECT GPA FROM Students WHERE ID = 101;
-- DBMS locks this row
UPDATE Students SET GPA = 3.2 WHERE ID = 101;
COMMIT;
-- Staff B must wait until A commits

Example 4: Security Comparison

Filing System: Inconsistent Security
  • File 1: Read access for all employees
  • File 2: Read access for managers only
  • File 3: No access control at all!
  • Each file has different security rules
Database System: Uniform Security
-- DBMS enforces consistent rules
CREATE VIEW student_public AS
SELECT ID, Name FROM Students;

GRANT SELECT ON student_public TO all_employees;
GRANT SELECT ON Students TO managers_only;

Example 5: Backup and Recovery

Filing System: Manual Backup
  • Copy each file manually
  • Store copies in different location
  • If backup forgotten → data lost forever
  • Recovery requires manual reconstruction
Database System: Automated Backup
-- DBMS handles backup automatically
BACKUP DATABASE UniversityDB TO DISK = 'backup.bak';

-- Recovery is automatic
RESTORE DATABASE UniversityDB FROM DISK = 'backup.bak';
