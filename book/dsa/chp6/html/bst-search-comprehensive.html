BST Search Algorithm

Data Structures — Complete Guide for 20/20 Exam

Iterative BST Search

INTERATIVE_SEARCH(x, k) while x ≠ NIL and k ≠ key[x] if k < key[x] x = left[x] else x = right[x] return x
How It Works:
Start at root, compare k with current node, go left or right
1. If k equals current node's key → found, return node
2. If k < current node's key → search left subtree
3. If k > current node's key → search right subtree
4. If we reach NIL → key not found
Example: Search for k=22
20 / \ 10 30 / \ / \ 5 15 25 35

Step 1: Compare 22 with 20 → 22 > 20, go RIGHT

Step 2: Compare 22 with 30 → 22 < 30, go LEFT

Step 3: Compare 22 with 25 → 22 < 25, go LEFT

Step 4: NIL reached → Key 22 NOT FOUND

Recursive BST Search

REC_SEARCH(x, k) if x = NIL or k = key[x] return x if k < key[x] return REC_SEARCH(left[x], k) else return REC_SEARCH(right[x], k)
Recursive Approach:
Same logic as iterative, but uses function calls
Base case: x = NIL or key found
Recursive case: call on left or right child
Stack Overflow Risk: For very deep trees, recursive version may cause stack overflow. Iterative version is safer for production code.

Iterative vs Recursive

• Iterative: Uses while loop

• Recursive: Uses function calls

• Both have same time complexity

When to Use Which

• Iterative: Large trees, production code

• Recursive: Simpler code, interviews

• Both return same result

Search Path Verification (Test 1 & 2)

Key Question:
Given a sequence of nodes, can it be a valid BST search path?
When searching for a key k, the path from root to the found/expected node must follow BST rules at every step
Test 1: Which sequence CANNOT be a search path for 363?

Given BST with root 925, and we want to search for 363:

Valid path must satisfy:

• After comparing with root, all subsequent nodes must be in the correct subtree

• If we go LEFT at a node, all later nodes must be < current node

• If we go RIGHT at a node, all later nodes must be > current node

Option 1: 925, 202, 911, 912

• 363 < 925 → go left ✓

• 363 > 202 → go right ✓

• 363 < 911 → go left ✓

• 363 < 912 → go left, but 912 is in LEFT subtree of 911 → INVALID!

912 > 911, so 912 should be in RIGHT subtree, not left!

Option 2: 925, 362, 258, 898, 244, 911, 220, 924

This path follows BST rules at each step → VALID

Test 2: Algorithm to verify search path
VERIFY_SEARCH_PATH(sequence, n) min = -∞, max = +∞ for i = 1 to n-1 if sequence[i] < sequence[i-1] max = sequence[i-1] else min = sequence[i-1] if sequence[n] < min OR sequence[n] > max return INVALID return VALID

How it works:

• Track the valid range [min, max] for the search key

• When going LEFT: update max = current node

• When going RIGHT: update min = current node

• At the end, check if the target key fits in the final range

Key Insight: A search path is valid if and only if at each step, the next node is in the correct subtree relative to ALL previous nodes on the path.

Path Element Property (Test 3)

BST Search Path Property:
For any search path from root to a node x:
• Elements on LEFT branch of path: all < root
• Elements on RIGHT branch of path: all > root
• Elements ON the path: can be in any order relative to each other
Example: Search for key 30 in this BST
60 / \ 20 70 / \ / \ 10 40 50 80

Search path for 30: 60 → 20 → 40 (not found)

Define sets:

• A = {elements on LEFT branch of path} = {10}

• B = {elements ON the path} = {60, 20, 40}

• C = {elements on RIGHT branch of path} = {70, 50, 80}

Which relationships always hold?

• Every element in A < every element in B? NOT necessarily (40 > 10)

• Every element in A < every element in C? YES, always

• Every element in B < every element in C? NOT necessarily

Correct Relationships:
A ≤ b ≤ C is NOT always true for all combinations
The correct relationships are:
• All elements in A are < all elements that come AFTER them on the path
• All elements in C are > all elements that come AFTER them on the path
• Elements in B (on path) have no fixed order relative to each other
Test 3 Example: Which is always true?

Given: A = left path elements, B = on-path elements, C = right path elements

• a ≤ b ≤ c (a∈A, b∈B, c∈C) → NOT always true

• a ≤ b and b ≤ c → NOT always true

• a ≤ c (a∈A, c∈C) → ALWAYS true

Answer: Only a ≤ c is guaranteed!

Time & Space Complexity

Best Case

Time: O(1)

Space: O(1)

When key is at root

Average Case

Time: O(lg n)

Space: O(1) iterative

When tree is balanced

Worst Case

Time: O(n)

Space: O(1) iterative

When tree is skewed

Complexity Formula:
Time = O(h), where h = height of tree
h ranges from ⌊lg n⌋ (balanced) to n-1 (skewed)
Key Insight: The search time depends entirely on the tree's height. This is why maintaining balance is crucial for BST performance.

Iterative Algorithm

while x ≠ NIL and k ≠ key[x] if k < key[x] x = left[x] else x = right[x] return x

Recursive Algorithm

if x = NIL or k = key[x] return x if k < key[x] return REC_SEARCH(left[x], k) else return REC_SEARCH(right[x], k)

Time Complexity

• Best: O(1)

• Average: O(lg n)

• Worst: O(n)

Space Complexity

• Iterative: O(1)

• Recursive: O(h) stack space

• h = height of tree

Remember: Search terminates when: (1) key is found, or (2) NIL pointer is reached (key not in tree).
