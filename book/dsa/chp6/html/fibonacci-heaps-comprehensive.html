Data Structures — Complete Guide for 20/20 Exam

Fibonacci Heap Definition

A Fibonacci heap is a collection of min-heap-ordered trees. The trees are rooted but not binomial trees. Fibonacci heaps are a refinement of binomial heaps that achieve better amortized time for several operations.

Formal Definition:
F(n) = collection of min-heap-ordered trees with n total nodes
Each tree satisfies: parent.key ≤ child.key for every parent-child pair. No structural constraints on the trees (unlike binomial heaps).
Key Distinction: Unlike binomial heaps where trees have a fixed structure (Binomial tree Bₖ has exactly C(n,k) nodes), Fibonacci heaps have NO structural constraints. Trees can be any shape, as long as the min-heap property holds.

Root List

min pointer →

• Circular doubly-linked list of tree roots

• Points to tree with minimum key

Tree Property

Min-Heap Ordered

• Parent ≤ Children

• No fixed structure

Node Structure

key, parent, child

• left, right (sibling list)

• degree, mark

Key Fields

n = total nodes

• min = pointer to min root

• degree(min) = number of children

Node Structure Detail

struct FibonacciNode { key // priority value (comparable) parent // pointer to parent node child // pointer to any one child left, right // pointers for circular doubly-linked list degree // number of children mark // boolean: has this node lost a child since // it became a child of its current parent? }
Circular Doubly-Linked List:
node.left.right == node && node.right.left == node
Siblings form a circular doubly-linked list. The root list and each child list use this structure. This allows O(1) insertion, deletion, and concatenation.

No Structural Constraints: Unlike binomial heaps, the trees can be different shapes. Node 3 has 2 children, node 7 has 1 child, node 5 has 2 children. There is no requirement that trees follow any particular pattern.
Key Property — Degree Bound:
degree(x) ≤ ⌊log_φ(n)⌋ where φ = (1+√5)/2 ≈ 1.618
The degree of any node is at most O(log n). This is proven using Fibonacci numbers, hence the name "Fibonacci heap." The mark field is crucial for maintaining this bound.

Node Fields Explained

key

The priority value. Used for comparisons. Must support <, ≤, = operations.

parent

Pointer to parent. NIL for root nodes. Used during cascading cut.

child

Pointer to any one child. Since children form a circular list, any child will do.

left / right

Circular doubly-linked list pointers. Connect siblings in root list or child list.

degree

Number of children. Updated during link operation. Used in consolidation.

mark

Critical for amortized analysis!

True if node lost a child since becoming a child of current parent. Enables cascading cut.

Lazy Merge Strategy

The fundamental insight of Fibonacci heaps: defer work as long as possible. Merging is done by simply concatenating root lists — actual tree restructuring is deferred.

Merge Operation:
MERGE(H₁, H₂): O(1) amortized
Just concatenate the two root lists. Update min pointer if needed. No tree restructuring!
MERGE(H₁, H₂): // Simply concatenate root lists — O(1)! concatenate root list of H₁ with root list of H₂ if H₁.min == NIL or (H₂.min ≠ NIL and H₂.min.key < H₁.min.key) H.min = H₂.min H.n = H₁.n + H₂.n
Why is this powerful? In binomial heaps, merge requires comparing and linking trees — O(log n). In Fibonacci heaps, merge is truly O(1) because we just splice two circular lists together. The actual "cleanup" (consolidation) is deferred to DELETE-MIN.

Lazy Operations Summary

INSERT — O(1)

Create new node, add to root list. Update min if needed. No restructuring.

→ Lazy: just add to root list

MERGE — O(1)

Concatenate root lists. Update min pointer. No tree linking.

→ Lazy: just splice lists

FIND-MIN — O(1)

Return min pointer value. Always valid since min is maintained.

→ Always O(1)

DECREASE-KEY — O(1)*

Cut node from parent, add to root list. Mark parent. Cascading cut if needed.

→ Cut + cascading cut

Amortized vs Actual Cost

The key insight: INSERT and MERGE have O(1) actual cost. DECREASE-KEY has O(1) amortized cost. The expensive CONSOLIDATE is paid for by the cheap operations — this is the power of potential function analysis.

INSERT Operation

INSERT(H, x): x.degree = 0 x.parent = NIL x.child = NIL x.mark = FALSE // Add x to root list — O(1) add x to root list of H if H.min == NIL or x.key < H.min.key H.min = x H.n = H.n + 1
Time Complexity:
INSERT: O(1) actual, O(1) amortized
Just create node and add to root list. No tree restructuring. The potential increases by 1 (one new tree), which is charged to the operation.

FIND-MIN Operation

FIND-MIN(H): return H.min
Time Complexity:
FIND-MIN: O(1) actual, O(1) amortized
The min pointer is always maintained. Simply return the pointer. This is one of the key advantages of Fibonacci heaps.

UNION (Merge) Operation

UNION(H₁, H₂): H = MAKE-FIB-HEAP() // Concatenate root lists — O(1) concatenate root list of H₁ with root list of H₂ if H₁.min == NIL or (H₂.min ≠ NIL and H₂.min.key < H₁.min.key) H.min = H₁.min else H.min = H₂.min H.n = H₁.n + H₂.n return H
Time Complexity:
UNION: O(1) actual, O(1) amortized
Simply splice two circular doubly-linked lists. No tree restructuring. This is the key advantage over binomial heaps (O(log n)).

EXTRACT-MIN Operation

The most complex operation — this is where consolidation happens.

EXTRACT-MIN(H): z = H.min if z ≠ NIL: // Add all children of z to root list for each child x of z: add x to root list of H x.parent = NIL // Remove z from root list remove z from root list of H if z == z.right: // z was only node H.min = NIL else: H.min = z.right // temporary CONSOLIDATE(H) // THE KEY STEP H.n = H.n - 1 return z
CONSOLIDATE — The expensive step: After removing min, we must merge trees of the same degree. This is where the O(log n) work happens. We use an array A[0..D(H.n)] where D(n) = ⌊log_φ(n)⌋.
CONSOLIDATE(H): let A[0..D(H.n)] be a new array, all entries NIL for each node x in root list of H: w = x d = w.degree while A[d] ≠ NIL: y = A[d] // another node with same degree if w.key > y.key: swap w and y // w always has smaller key LINK(y, w) // make y a child of w A[d] = NIL d = d + 1 A[d] = w // Rebuild root list from array A H.min = NIL for i = 0 to D(H.n): if A[i] ≠ NIL: add A[i] to root list of H if H.min == NIL or A[i].key < H.min.key: H.min = A[i]
LINK(y, x): // Make y a child of x remove y from root list of H make y a child of x x.degree = x.degree + 1 y.mark = FALSE
Time Complexity:
EXTRACT-MIN: O(log n) amortized
Adding children to root list is O(log n) total. CONSOLIDATE processes each node once. The potential decreases, paying for the work. Actual cost can be O(n) but amortized is O(log n).

DECREASE-KEY Operation

The operation that gives Fibonacci heaps their advantage over other priority queues.

DECREASE-KEY(H, x, k): if k > x.key: error "new key is greater than current key" x.key = k y = x.parent if y ≠ NIL and x.key < y.key: CUT(H, x, y) CASCADING-CUT(H, y) if x.key < H.min.key: H.min = x
CUT(H, x, y): remove x from child list of y y.degree = y.degree - 1 add x to root list of H x.parent = NIL x.mark = FALSE
CASCADING-CUT(H, y): z = y.parent if z ≠ NIL: if y.mark == FALSE: y.mark = TRUE // first child lost else: CUT(H, y, z) // second child lost → cut! CASCADING-CUT(H, z) // recurse up
Time Complexity:
DECREASE-KEY: O(1) amortized
The cut is O(1). Cascading cut may do multiple cuts, but each cut removes a marked node, reducing the potential by at least 1. The potential function accounts for all the work.
The Mark Field is Critical: Without the mark field and cascading cut, a node could accumulate too many children, violating the degree bound. The mark ensures each node loses at most one child before being cut itself, keeping degrees at O(log n).

DELETE Operation

DELETE(H, x): DECREASE-KEY(H, x, -∞) // make it the minimum EXTRACT-MIN(H) // remove it
Time Complexity:
DELETE: O(log n) amortized
Combine DECREASE-KEY (O(1) amortized) with EXTRACT-MIN (O(log n) amortized). The -∞ trick forces the node to the root, then it is extracted.

Amortized Analysis — Potential Function

Fibonacci heaps are analyzed using the potential method of amortized analysis. The potential function captures the "stored credit" from cheap operations.

Potential Function Φ(H):
Φ(H) = t(H) + 2·m(H)
where:
• t(H) = number of trees in the root list
• m(H) = number of marked nodes in the heap
• Φ(H) ≥ 0 always (empty heap: Φ = 0)
Critical Insight: The potential function is always non-negative. Each INSERT adds a tree (t increases by 1 → Φ increases by 1). Each cascading cut removes a marked node (m decreases → Φ decreases). The potential "pays" for expensive operations.

Amortized Cost Derivations

INSERT Amortized Cost:
â(INSERT) = 1 + ΔΦ = 1 + 1 = O(1)
Actual cost = 1 (add to root list). ΔΦ = +1 (new tree). Amortized = 1+1 = O(1).
FIND-MIN Amortized Cost:
â(FIND-MIN) = 0 + ΔΦ = 0 + 0 = O(1)
Actual cost = 0 (just return pointer). ΔΦ = 0. Amortized = O(1).
MERGE Amortized Cost:
â(MERGE) = 1 + ΔΦ = 1 + t₂ = O(1)*
Actual cost = 1 (splice lists). ΔΦ = t₂ (new trees from H₂). If we define MERGE's amortized cost as 1 + t₂, it's O(1) when t₂ is small. In practice, MERGE is O(1) because t₂ is bounded by the number of distinct degrees.
EXTRACT-MIN Amortized Cost:
â(EXTRACT-MIN) = O(t + D(n)) + ΔΦ = O(log n)
Actual cost = O(t + D(n)) where t = trees before, D(n) = ⌊log_φ(n)⌋. After consolidation, we have at most D(n)+1 trees. ΔΦ = -t + D(n) + 1 - 2m' (potential decreases). Amortized = O(D(n)) = O(log n).
DECREASE-KEY Amortized Cost:
â(DECREASE-KEY) = c + ΔΦ = O(1)
Actual cost c = 1 + number of cascading cuts. Each cascading cut removes one marked node. ΔΦ = 1 - 2·(number of cascading cuts). So â = c + 1 - 2c = 1 - c ≤ O(1). The potential "pays" for all the cuts!

The Magic of DECREASE-KEY

When DECREASE-KEY does cascading cuts, it removes marked nodes. Each removed marked node decreases Φ by 2, but the cut costs only 1. So each cascading cut actually has a NET NEGATIVE amortized cost — it "earns" credit! This is why DECREASE-KEY can be O(1) amortized despite doing potentially many cuts.

Graph Algorithm Applications

The primary motivation for Fibonacci heaps: optimizing graph algorithms that make many DECREASE-KEY calls.

Dijkstra's Shortest Path:
With Fibonacci Heap: O(V lg V + E)
With Binary Heap: O((V + E) lg V). The improvement comes from DECREASE-KEY being O(1)* instead of O(lg n). For dense graphs where E ≈ V², this is a significant improvement.
DIJKSTRA(G, w, s): initialize single source(G, s) S = ∅ Q = V[G] // Q is a Fibonacci heap while Q ≠ ∅: u = EXTRACT-MIN(Q) // O(lg V)* amortized S = S ∪ {u} for each vertex v ∈ Adj[u]: RELAX(u, v, w) // calls DECREASE-KEY RELAX(u, v, w): if d[v] > d[u] + w(u, v): d[v] = d[u] + w(u, v) π[v] = u DECREASE-KEY(Q, v, d[v]) // O(1)* amortized!
Prim's MST Algorithm:
With Fibonacci Heap: O(E + V lg V)
Same advantage as Dijkstra. Each edge may trigger a DECREASE-KEY. With binary heap: O(E lg V). With Fibonacci heap: O(E) for all DECREASE-KEY operations combined.

Complexity Comparison: Graph Algorithms

Algorithm Binary Heap Binomial Heap Fibonacci Heap
Dijkstra O((V+E) lg V) O((V+E) lg V) O(V lg V + E)
Prim O(E lg V) O(E lg V) O(E + V lg V)
When does Fibonacci heap help?
• Dense graphs: E ≈ V² → Dijkstra becomes O(V²) vs O(V² lg V) with binary heap
• Sparse graphs: E ≈ V → Both are O(V lg V), no advantage
• The advantage grows with the ratio E/V (edge density)
Why the Improvement?
Dijkstra: V × EXTRACT-MIN + E × DECREASE-KEY
Binary Heap: V·O(lg V) + E·O(lg V) = O((V+E) lg V)
Fibonacci: V·O(lg V)* + E·O(1)* = O(V lg V + E)
The E × DECREASE-KEY term drops from O(E lg V) to O(E)!

Worked Example 1: Insert and Extract-Min

Step-by-step: Insert 3, 7, 1, 5 then EXTRACT-MIN

Step 1: INSERT(3)

Root list:  [3]   ← min = 3

Step 2: INSERT(7)

Root list:  [3] ←→ [7]   ← min = 3

Step 3: INSERT(1)

Root list:  [3] ←→ [7] ←→ [1]   ← min = 1

Step 4: INSERT(5)

Root list:  [3] ←→ [7] ←→ [1] ←→ [5]   ← min = 1

Step 5: EXTRACT-MIN() — remove node 1

  Node 1 has no children → root list becomes [3] ←→ [7] ←→ [5]

  CONSOLIDATE: process nodes by degree
  - Node 3: degree 0 → A[0] = 3
  - Node 7: degree 0 → A[0] occupied! LINK(7, 3)
    → Node 3 now has child 7, degree 1 → A[1] = 3
  - Node 5: degree 0 → A[0] = 5

  After consolidation:
  A[0] = [5], A[1] = [3]←[7]

  Rebuild root list: [5] ←→ [3]←[7]   ← min = 5

Result: EXTRACT-MIN returns 1. Heap now has 3 nodes, min = 5.

Worked Example 2: Decrease-Key with Cascading Cut

Step-by-step: Cascading cut scenario

Initial Heap:

         1 ← min
        / \
       3   2
      / \   \
     7   5   8
    /
   12

DECREASE-KEY(12, 0): — reduce key 12 to 0

  1. Node 12 has key 0 now. Parent is 7.
     0 < 7 → CUT needed!

  2. CUT: Remove 12 from children of 7
     - 7.degree: 1 → 0
     - Add 12 to root list
     - 12.parent = NIL, 12.mark = FALSE

  3. CASCADING-CUT on 7:
     - 7.parent = 3 (not NIL)
     - 7.mark = FALSE → set 7.mark = TRUE
     - (No more cuts — first child lost)

  Result:
         1 ← min
        / \   \
       3   2   0  ← NEW ROOT (was 12)
      / \   \
     7   5   8
    (mark = TRUE)

Now DECREASE-KEY(8, 4): — reduce key 8 to 4

  1. Node 8 has key 4. Parent is 2.
     4 < 2? NO → no cut needed.

  2. Check min: 4 > 1, no update to min.

  Result: no change to structure

Now DECREASE-KEY(7, 0): — reduce key 7 to 0

  1. Node 7 has key 0. Parent is 3.
     0 < 3 → CUT needed!

  2. CUT: Remove 7 from children of 3
     - 3.degree: 2 → 1
     - Add 7 to root list
     - 7.parent = NIL, 7.mark = FALSE (reset)

  3. CASCADING-CUT on 3:
     - 3.parent = 1 (not NIL)
     - 3.mark = FALSE → set 3.mark = TRUE

  4. Update min: 0 < 1 → min = 7 (key 0)

  Result:
         1
        / \   \
       3   2   0
        \   \
         5   8
   (mark=TRUE)

   Root list: [1] ←→ [0] ←→ [0]  ← min = 0

Key Observation: Cascading cut prevented node 3 from accumulating too many children. The mark field ensures each node loses at most one child before being cut itself.

Worked Example 3: Full Dijkstra with Fibonacci Heap

Dijkstra on a 4-vertex graph
Graph:
    A ---4--- B
    |       / |
    2     1   7
    |   /     |
    C ---3--- D

Edges: (A,B,4), (A,C,2), (B,C,1), (B,D,7), (C,D,3)
Source: A

Initialize: d[A]=0, d[B]=∞, d[C]=∞, d[D]=∞

Fibonacci Heap after init:

Q = [(A,0)] ←→ [(B,∞)] ←→ [(C,∞)] ←→ [(D,∞)]
min = A (key = 0)

Iteration 1: EXTRACT-MIN → A(0)

  Relax edges from A:
  - (A,B,4): d[B] = ∞ > 0+4 = 4 → d[B] = 4, DECREASE-KEY(B, 4)
  - (A,C,2): d[C] = ∞ > 0+2 = 2 → d[C] = 2, DECREASE-KEY(C, 2)

  Q = [(C,2)] ←→ [(B,4)] ←→ [(D,∞)]
  min = C (key = 2)

Iteration 2: EXTRACT-MIN → C(2)

  Relax edges from C:
  - (C,B,1): d[B] = 4 > 2+1 = 3 → d[B] = 3, DECREASE-KEY(B, 3)
  - (C,D,3): d[D] = ∞ > 2+3 = 5 → d[D] = 5, DECREASE-KEY(D, 5)

  Q = [(B,3)] ←→ [(D,5)]
  min = B (key = 3)

Iteration 3: EXTRACT-MIN → B(3)

  Relax edges from B:
  - (B,D,7): d[D] = 5 > 3+7 = 10 → NO UPDATE

  Q = [(D,5)]
  min = D (key = 5)

Iteration 4: EXTRACT-MIN → D(5)

  No outgoing edges to relax.

  Q = [] (empty)

Final distances:

  d[A] = 0  (source)
  d[B] = 3  (A→C→B)
  d[C] = 2  (A→C)
  d[D] = 5  (A→C→D)

Operation counts:

  INSERT:       4 times → O(4) actual
  EXTRACT-MIN:  4 times → O(4 lg 4)* amortized
  DECREASE-KEY: 3 times → O(3) amortized

  Total with Fibonacci: O(V lg V + E) = O(4 lg 4 + 5)
  Total with Binary Heap: O((V+E) lg V) = O(9 lg 4)

Worked Example 4: Consolidation Detail

Full consolidation with 8 trees of degree 0

Scenario: After removing min from a heap with 8 nodes all as separate trees (degree 0).

CONSOLIDATE with A[0..D(8)] where D(8) = ⌊log_φ(8)⌋ = ⌊4.09⌋ = 4

Processing nodes (keys: 3, 7, 1, 5, 8, 12, 2, 9):

Step 1: Node(3), d=0 → A[0] = 3
  A = [3, _, _, _, _]

Step 2: Node(7), d=0 → A[0] occupied!
  LINK(7, 3): 7 becomes child of 3, degree=1
  A[1] = 3, A[0] = _
  A = [_, 3, _, _, _]

Step 3: Node(1), d=0 → A[0] = 1
  A = [1, 3, _, _, _]

Step 4: Node(5), d=0 → A[0] occupied!
  LINK(5, 1): 5 becomes child of 1, degree=1
  A[1] occupied! LINK(1, 3): 1 becomes child of 3
  A[2] = 3, A[1] = _, A[0] = _
  A = [_, _, 3, _, _]

Step 5: Node(8), d=0 → A[0] = 8
  A = [8, _, 3, _, _]

Step 6: Node(12), d=0 → A[0] occupied!
  LINK(12, 8): 12 becomes child of 8, degree=1
  A[1] = 8, A[0] = _
  A = [_, 8, 3, _, _]

Step 7: Node(2), d=0 → A[0] = 2
  A = [2, 8, 3, _, _]

Step 8: Node(9), d=0 → A[0] occupied!
  LINK(9, 2): 9 becomes child of 2, degree=1
  A[1] occupied! LINK(2, 8): 2 becomes child of 8
  A[2] occupied! LINK(8, 3): 8 becomes child of 3
  A[3] = 3, A[2] = _, A[1] = _, A[0] = _
  A = [_, _, _, 3, _]

FINAL: Only A[3] = 3 (single tree of degree 3)

Result: 8 trees of degree 0 consolidated into 1 tree of degree 3

    3 ← min (key=3)
   /|\
  1  8  7
 /|  |\
5 12 2  9

This demonstrates how consolidation reduces many small trees into fewer larger trees.

INSERT(H, x): x.degree=0; x.parent=NIL; x.child=NIL; x.mark=FALSE add x to root list of H if H.min==NIL or x.key < H.min.key: H.min = x H.n++ FIND-MIN(H): return H.min UNION(H₁, H₂): concatenate root lists; update min; H.n = H₁.n + H₂.n EXTRACT-MIN(H): z = H.min add all children of z to root list remove z from root list CONSOLIDATE(H) H.n--; return z CONSOLIDATE(H): A[0..D(n)] = all NIL for each x in root list: w = x; d = w.degree while A[d] ≠ NIL: y = A[d]; if w.key > y.key: swap LINK(y,w); A[d]=NIL; d++ A[d] = w rebuild root list from A; update min LINK(y, x): remove y from root list make y child of x; x.degree++ y.mark = FALSE DECREASE-KEY(H, x, k): x.key = k; y = x.parent if y ≠ NIL and x.key < y.key: CUT(H,x,y); CASCADING-CUT(H,y) if x.key < H.min.key: H.min = x CUT(H, x, y): remove x from y's children; y.degree-- add x to root list; x.parent=NIL; x.mark=FALSE CASCADING-CUT(H, y): z = y.parent if z ≠ NIL: if y.mark == FALSE: y.mark = TRUE else: CUT(H,y,z); CASCADING-CUT(H,z) DELETE(H, x): DECREASE-KEY(H, x, -∞) EXTRACT-MIN(H)

Key Formulas

Golden Ratio:
φ = (1+√5)/2 ≈ 1.618
Degree Bound:
D(n) = ⌊log_φ(n)⌋
Fibonacci Numbers:
F(k+2) = 1 + Σᵢ₌₀ᵏ F(i)
Dijkstra Complexity:
O(V lg V + E)

Critical Warnings for Exam

1. Fibonacci heap is NOT a binomial heap. Trees have no fixed structure.
2. O(1) for DECREASE-KEY is AMORTIZED, not worst-case.
3. The mark field is essential — without it, degree bound fails.
4. CONSOLIDATE is the expensive step in EXTRACT-MIN.
5. Practical performance often worse than binary heap due to constants.
