هشدار امنیتی: SNMPv1 و v2c رشته‌های community (رمزهای عبور) را به صورت متن ساده روی شبکه می‌فرستند. همیشه از SNMPv3 با احراز هویت و رمزنگاری در محیط‌های تولید استفاده کنید، یا از شبکه‌های مدیریت جداگانه استفاده کنید.

SNMP روی UDP — ملاحظات قابلیت اطمینان

حمل غیرقابل اعتماد

PDU SNMP معمولاً در بار UDP حمل می‌شود. از آنجا که UDP غیرقابل اعتماد است، هیچ تضمینی برای رسیدن درخواست یا پاسخ وجود ندارد.

فیلد شناسه درخواست

فیلد شناسه درخواست در PDU درخواست‌ها را از مدیر به عامل شماره‌گذاری می‌کند. پاسخ عامل این شناسه را کپی می‌کند و به مدیر اجازه می‌دهد درخواست‌ها یا پاسخ‌های گمشده را تشخیص دهد.

ارسال مجدد "مسئولانه"

استاندارد SNMP روش‌های ارسال مجدد خاص را الزام نمی‌کند. این فقط نیاز دارد سرور مدیریت کننده "باید در رابطه با فرکانس و مدت ارسال مجدد مسئولانه عمل کند."

SNMPv3 = SNMPv2 + امنیت

همانطور که در [RFC 3410] ذکر شد، "SNMPv3 را می‌توان به عنوان SNMPv2 با قابلیت‌های امنیتی و اداری اضافی در نظر گرفت." فقدان امنیت کافی در v1/v2c استفاده از SNMP را عمدتاً به پایش محدود کرد تا کنترل (SetRequest به ندرت در SNMPv1 استفاده می‌شد).

پایگاه اطلاعات مدیریت (MIB)

MIB یک پایگاه داده سلسله‌مراتبی و درختی از اشیاء مدیریت‌شده است. هر شیء با یک شناسه شیء (OID) مشخص می‌شود و دارای نحو، سطح دسترسی و وضعیت تعریف‌شده است.

ساختار OID:
1.3.6.1.2.1.2.2.1.10.1 ← ifInOctets روی رابط 1
iso(1) . org(3) . dod(6) . internet(1) . mgmt(2) . mib-2(1) . interfaces(2) . ifTable(2) . ifEntry(1) . ifInOctets(10) . instance(1)

مثال: شیء Counter32 از MIB IP [RFC 4293]

ipSystemStatsInDelivers OBJECT-TYPE SYNTAX Counter32 MAX-ACCESS read-only STATUS current DESCRIPTION "تعداد کل دیتاگرام‌هایی که با موفقیت به پروتکل‌های کاربر IP (شامل ICMP) تحویل داده شده‌اند. هنگام ردیابی آمار رابط، شمارنده رابطی که این دیتاگرام‌ها به آن آدرس داده شده‌اند، افزایش می‌یابد. این رابط ممکن است برای برخی از دیتاگرام‌ها همان رابط ورودی نباشد. ناپیوستگی‌ها در مقدار این شمارنده می‌تواند در راه‌اندازی مجدد سیستم مدیریت و در زمان‌های دیگر که توسط مقدار ipSystemStatsDiscontinuityTime نشان داده شده، رخ دهد." ::= { ipSystemStatsEntry 18 }

منبع: [RFC 4293] ماژول MIB IP. سایر ماژول‌های MIB شامل [RFC 4022] برای TCP و [RFC 4113] برای UDP هستند.

SMI (ساختار اطلاعات مدیریت)

SMI زبان توصیف داده [RFC 2578; RFC 2579; RFC 2580] است که برای تعریف اشیاء MIB استفاده می‌شود. یک زبان تعریف رسمی تضمین می‌کند نحو و معنای داده مدیریت به خوبی تعریف شده و بدون ابهام است. اشیاء MIB مرتبط در ماژول‌های MIB جمع‌آوری می‌شوند — تا اواخر 2019، بیش از 400 RFC مرتبط با MIB و بسیاری ماژول‌های MIB فروشنده-خاص (خصوصی) وجود دارد. انواع داده کلیدی عبارتند از:

انواع پایه

Integer32 — عدد صحیح 32 بیتی

OctetString — رشته بایتی

ObjectIdentifier — OID

IpAddress — آدرس IPv4 4 بایتی

شمارنده / سنجه

Counter32/64 — در 2^32 / 2^64 بازنشانی می‌شود

Gauge32 — در حداکثر می‌ماند، بازنشانی نمی‌شود

TimeTicks — صدم ثانیه

انواع جدول

SEQUENCE — تعریف ردیف

SEQUENCE OF — جدول ردیف‌ها

Index — کلید منحصر به فرد به ازای هر ردیف

مثال‌های حل شده

مثال 1: پرس و جوهای SNMP — پایش ترافیک رابط

سناریو: یک مدیر می‌خواهد ترافیک ورودی روی رابط GigabitEthernet0/1 یک مسیریاب (ifIndex = 2) را پایش کند. آنها ifInOctets را هر 60 ثانیه بازیابی می‌کنند و استفاده از پهنای باند را محاسبه می‌کنند.

# پرس و جوی OID ifInOctets برای شاخص رابط 2 $ snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.10.2 IF-MIB::ifInOctets.2 = Counter32: 1523456789 # 60 ثانیه صبر کنید و دوباره پرس و جو کنید $ snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.10.2 IF-MIB::ifInOctets.2 = Counter32: 1524567890 # محاسبه: delta = 1524567890 - 1523456789 = 1111101 بایت در 60 ثانیه # نرخ بیت = 1111101 * 8 / 60 = 148,146.8 bps ≈ 148 Kbps # استفاده روی پیوند 1 گیگابیت = 148 Kbps / 1,000,000 Kbps = 0.0148%

تحلیل:

  • ifInOctets یک Counter32 است — به طور یکنواخت افزایش می‌یابد تا زمانی که در 2^32 (4,294,967,296) بازنشانی شود
  • برای محاسبه استفاده، مدیر باید دوبار poll کند و تفاوت را محاسبه کند
  • اگر شمارنده بین pollها بازنشانی شود، مدیر باید آن را تشخیص دهد: new < old ← (2^32 - old) + new
  • فاصله poll مهم است: بیش از حد طولانی باعث از دست دادن بازنشانی شمارنده می‌شود؛ بیش از حد کوتاه باعث ترافیک اضافی می‌شود
مثال 2: MIB Object Walk — کشف رابط‌ها

سناریو: یک مدیر می‌خواهد تمام رابط‌های یک دستگاه و وضعیت عملیاتی آنها را با استفاده از SNMP walk کشف کند.

$ snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.2 IF-MIB::ifDescr.1 = STRING: GigabitEthernet0/0 IF-MIB::ifDescr.2 = STRING: GigabitEthernet0/1 IF-MIB::ifDescr.3 = STRING: Serial0/0/0 IF-MIB::ifDescr.4 = STRING: Loopback0 $ snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.8 IF-MIB::ifOperStatus.1 = INTEGER: up(1) IF-MIB::ifOperStatus.2 = INTEGER: up(1) IF-MIB::ifOperStatus.3 = INTEGER: down(2) IF-MIB::ifOperStatus.4 = INTEGER: up(1) $ snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.16 IF-MIB::ifOutOctets.1 = Counter32: 985642135 IF-MIB::ifOutOctets.2 = Counter32: 2145789632 IF-MIB::ifOutOctets.3 = Counter32: 0 IF-MIB::ifOutOctets.4 = Counter32: 123456789

تحلیل:

  • walk از GetNextRequest به طور مکرر برای پیمایش زیردرخت MIB استفاده می‌کند
  • رابط 3 (Serial0/0/0) ifOperStatus = down(2) و صفر بایت خروجی را نشان می‌دهد — این رابط احتمالاً پایین است یا به طور مدیریتی غیرفعال شده است
  • مدیر می‌تواند ارجاع متقاطع بزند: ifDescr.3 → ifOperStatus.3 → ifOutOctets.3 تا یک موجودی کامل رابط بسازد
مثال 3: سناریوی Trap SNMP — هشدار قطع پیوند

سناریو: رابط یک مسیریاب قطع می‌شود. عامل SNMP یک trap به سرور مدیریت می‌فرستد. NMS هشدار را دریافت و پردازش می‌کند.

جریان Trap:
مسیریاب قطع پیوند را تشخیص می‌دهد ← عامل SNMPv2-Trap می‌فرستد ← NMS در UDP 162 دریافت می‌کند ← NMS ثبت/هشدار می‌دهد
# جزئیات Trap ضبط شده در NMS دریافت SNMPv2-Trap از UDP: [192.168.1.1]:161 sysUptime.0 = 123456789 (14 روز، 6 ساعت) snmpTrapOID.0 = ifDown ifIndex.3 = 3 ifAdminStatus.3 = up(1) ifOperStatus.3 = down(2) ifDescr.3 = Serial0/0/0 # قانون همبستگی NMS: # رابط Serial0/0/0 از up به down تغییر کرد # شدت: بحرانی # اقدام: ایجاد تیکت + اطلاع به مهندس کشیک

تحلیل:

  • Traps بدون تأیید هستند — اگر NMS trap را از دست بدهد، رویداد گم می‌شود (مگر اینکه از InformRequest استفاده شود)
  • SNMPv2-Trap شامل snmpTrapOID برای شناسایی نوع رویداد (linkDown, authenticationFailure, و غیره) است
  • Trap شامل variable bindings با اطلاعات زمینه (کدام رابط، وضعیت فعلی) است
  • بهترین روش: از traps SNMPv3 با احراز هویت و رمزنگاری استفاده کنید. همچنین مقاصد trap اضافی پیکربندی کنید.
مثال 4: عملیات Set SNMP — غیرفعال کردن یک رابط

سناریو: یک مدیر از راه دور یک رابط نادرست پیکربندی شده را با استفاده از SNMP SetRequest غیرفعال می‌کند.

# بررسی وضعیت admin فعلی: ifAdminStatus.2 = 1 (up) $ snmpget -v2c -c private 192.168.1.1 1.3.6.1.2.1.2.2.1.7.2 IF-MIB::ifAdminStatus.2 = INTEGER: up(1) # تنظیم وضعیت admin به down (2) $ snmpset -v2c -c private 192.168.1.1 1.3.6.1.2.1.2.2.1.7.2 integer 2 IF-MIB::ifAdminStatus.2 = INTEGER: down(2) # تأیید تغییر $ snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.7.2 IF-MIB::ifAdminStatus.2 = INTEGER: down(2)
مهم: عملیات Set از رشته community "private" (خواندن-نوشتن) استفاده می‌کند. استفاده از SNMP برای تغییرات پیکربندی به دلیل فقدان تضمین‌های تراکنشی عموماً به نفع NETCONF/YANG توصیه نمی‌شود.
مثال 5: تشخیص بازنشانی شمارنده

سناریو: مقدار Counter32 بازنشانی می‌شود. NMS باید تشخیص دهد و تفاوت را به درستی محاسبه کند.

# Poll 1: شمارنده نزدیک حداکثر است ifInOctets.2 = Counter32: 4294967290 # Poll 2 (60 ثانیه بعد): شمارنده بازنشانی شده است ifInOctets.2 = Counter32: 5000 # محاسبه صحیح تفاوت: delta = (2^32 - 4294967290) + 5000 = 6 + 5000 = 5006 بایت # محاسبه نادرست (بدون تشخیص بازنشانی): delta = 5000 - 4294967290 = -4289962290 (اشتباه!) # نرخ بیت = 5006 * 8 / 60 = 667.5 bps

راه حل: تا حد امکان از Counter64 (ifHCInOctets) استفاده کنید، یا اطمینان حاصل کنید فواصل poll به اندازه کافی کوتاه هستند که شمارنده‌ها نمی‌توانند بیش از یک بار بین pollها بازنشانی شوند.
