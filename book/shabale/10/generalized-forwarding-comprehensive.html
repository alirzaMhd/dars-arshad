ارسال عمومی و OpenFlow

شبکه‌های کامپیوتری (کروس و راس) — فصل ۴: لایه شبکه: سطح داده

پارادایم تطبیق-به-علاوه-اقدام

مسیریاب‌های سنتی بر اساس یک فیلد واحد (IP مقصد) ارسال می‌کنند. ارسال عمومی روی چندین فیلد سرآیند در چندین لایه پروتکل تطبیق داده و یک یا چند اقدام را اجرا می‌کند. این کار سطح کنترل را از سطح داده جدا کرده و پایه شبکه‌سازی نرم‌افزارمحور (SDN) است. پروتکل OpenFlow [McKeown 2008, ONF 2020, Casado 2014, Tourrilhes 2014] پیاده‌سازی استاندارد ارسال عمومی است و از انقلاب گسترده‌تر SDN [Feamster 2013] پدید آمده است.

ساختار جدول جریان

یک ورودی جدول جریان از سه مؤلفه تشکیل شده است:

ورودی جدول جریان = (فیلدهای سرآیند، شمارنده‌ها، اقدامات)
فیلدهای سرآیند — الگوی تطبیق با wildcardها؛ شمارنده‌ها — بسته‌ها/بایت‌های مطابقت‌یافته؛ اقدامات — کاری که در صورت تطبیق انجام شود

الگوریتم تطبیق-به-علاوه-اقدام (OpenFlow)

for each packet received: for each flow table entry (in priority order): if match(packet.headerFields, entry.pattern): entry.counters.packets++ entry.counters.bytes += packet.size execute(entry.actions) break if no match found: send packet to controller (or drop)
اشتباه رایج: فرض اینکه ورودی‌های جریان به هر ترتیبی بررسی می‌شوند. ورودی‌ها دارای مقادیر اولویت صریح هستند — ورودی‌های با اولویت بالاتر ابتدا تطبیق داده می‌شوند. وقتی اولویت‌ها برابرند، خاص‌ترین (کمترین wildcard) ورودی برنده است.

مثال‌های عملی — تطبیق-به-علاوه-اقدام

مثال ۱: ارسال ساده IP از طریق جدول جریان

یک سوئیچ دارای یک جدول جریان با دو ورودی است. یک بسته با IP مقصد = 10.1.2.3 روی پورت ۲ می‌رسد.

ورودی ۱: match(IP dst = 10.1.1.*, priority=10) → forward(پورت ۳)
ورودی ۲: match(IP dst = 10.1.2.*, priority=10) → forward(پورت ۴)

نتیجه: بسته با ورودی ۲ مطابقت دارد (10.1.2.* شامل 10.1.2.3 می‌شود). از پورت ۴ ارسال می‌شود.

مثال ۲: رفع ابهام اولویت

یک بسته دارای IP src = 192.168.1.5, IP dst = 10.0.0.1, TCP dst port = 80 است.

ورودی A: match(IP dst = 10.0.0.*, priority=5) → forward(پورت ۱)
ورودی B: match(IP src = 192.168.1.*, IP dst = 10.0.0.1, TCP dst=80, priority=20) → drop

نتیجه: ورودی B اولویت بالاتری دارد (۲۰ > ۵). بسته حتی اگر هر دو مطابقت داشته باشند، رها می‌شود.

مثال ۳: پردازش چند-اقدامی

یک بسته با VLAN ID = 100 می‌رسد. ورودی مطابقت‌یافته دو اقدام را مشخص می‌کند.

ورودی: match(VLAN ID = 100) → [strip_vlan, forward(پورت ۵)]
اقدام ۱: برچسب VLAN را از سرآیند بسته حذف کن.
اقدام ۲: بسته اصلاح‌شده را از پورت ۵ ارسال کن.

نتیجه: برچسب VLAN حذف می‌شود و فریم Ethernet ساده از پورت ۵ خارج می‌شود.

فیلدهای تطبیق OpenFlow 1.0

OpenFlow 1.0 ۱۲ فیلد تطبیق را تعریف می‌کند که لایه فیزیکی (پورت)، لایه پیوند (Ethernet)، لایه شبکه (IP) و لایه انتقال (TCP/UDP) را پوشش می‌دهند. هر فیلد می‌تواند به یک مقدار دقیق یا یک wildcard تنظیم شود.

OpenFlow 1.0 Flow Match Structure (12 fields): ┌─────────────────────────────────────────────┐ │ Ingress Port │ Physical port of arrival │ │ Ethernet src │ 48-bit MAC address │ │ Ethernet dst │ 48-bit MAC address │ │ Ethernet Type │ 0x0800 (IPv4), 0x0806...│ │ VLAN ID │ 12-bit VLAN identifier │ │ VLAN Priority │ 3-bit 802.1p priority │ │ IP src │ 32-bit IPv4 address+mask │ │ IP dst │ 32-bit IPv4 address+mask │ │ IP Protocol │ TCP=6, UDP=17, ICMP=1 │ │ IP ToS │ 8-bit Type of Service │ │ TCP/UDP src port│ 16-bit transport src │ │ TCP/UDP dst port│ 16-bit transport dst │ └─────────────────────────────────────────────┘
اشتباه رایج: اشتباه گرفتن تطبیق wildcard با تطبیق زیرشبکه CIDR. در OpenFlow، فیلدهای IP مبدأ و مقصد از یک bitmask استفاده می‌کنند (نه طول پیشوند CIDR). برای مثال، 10.1.0.0/255.255.0.0 معادل طول پیشوند ۱۶ بیتی است.

Wildcardها و Bitmaskها

هر فیلد در یک ورودی جریان می‌تواند یک مقدار دقیق یا یک مقدار wildcard باشد. برای فیلدهای IP، یک bitmask مشخص می‌کند کدام بیت‌ها باید مطابقت داشته باشند. فیلد اولویت تعارضات را وقتی چندین ورودی مطابقت دارند حل می‌کند.

معناشناسی Wildcard:
match(header, pattern) = (header & mask) == (value & mask)
یک فیلد مطابقت دارد اگر بیت‌های سرآیند (ماسک‌شده) برابر بیت‌های الگو (ماسک‌شده) باشند. ماسک ۰ به معنای "wildcard" است (با هر چیزی مطابقت دارد).

تکامل فیلدهای تطبیق OpenFlow

در حالی که OpenFlow 1.0 ۱۲ فیلد تطبیق را تعریف کرد، نسخه‌های جدیدتر مشخصات OpenFlow این مجموعه را به ۴۱ فیلد تطبیق افزایش داده‌اند [Bosshart 2014]. این گسترش نشان‌دهنده تقاضا برای کنترل دقیق‌تر بر ترافیک شبکه با بالغ شدن استقرارهای SDN است.

محدودیت‌های طراحی: چرا برخی فیلدها نمی‌توانند تطبیق داده شوند

ممکن است تعجب کنید چرا برخی فیلدهای سرآیند — مانند فیلد TTL (Time-to-Live) یا طول دیتاگرام — در میان فیلدهای قابل تطبیق گنجانده نشده‌اند. پاسخ در مصالحه اساسی بین عملکرد و پیچیدگی نهفته است. "هنر" در انتخاب یک انتزاع برای ارسال عمومی، ارائه عملکرد کافی برای مفید بودن بدون بارگذاری بیش از حد انتزاع با جزئیات زیاد است که عملکرد را به خطر می‌اندازد یا رابط را پیچیده می‌کند.

این فلسفه طراحی به خوبی توسط معمار کامپیوتر Butler Lampson بیان شده است:

اصل انتزاع Lampson [Lampson 1983]:
"یک کار را در یک زمان انجام بده، و آن را خوب انجام بده. یک رابط باید حداقل essentials یک انتزاع را捕获 کند. تعمیم نده؛ تعمیم‌ها معمولاً اشتباه هستند."

در زمینه OpenFlow، طراحان عمداً فیلدهای تطبیق را به مفیدترین مجموعه متداول — که L2 تا L4 را پوشش می‌دهد — محدود کردند، به جای تلاش برای نمایش هر فیلد سرآیند ممکن. افزودن تطبیق TTL یا طول دیتاگرام به سخت‌افزار سوئیچ و رابط کنترلر با سود عملی محدود پیچیدگی می‌افزاید، زیرا آن فیلدها به ندرت در سیاست‌های ارسال ظاهر می‌شوند.

مثال‌های عملی — فیلدهای تطبیق

مثال ۱: فیلتر سطح MAC

یک ورودی جریان پیکربندی کنید که با همه بسته‌های ARP (EtherType = 0x0806) از یک MAC مبدأ خاص مطابقت داشته باشد.

Eth Type = 0x0806, Eth src = AA:BB:CC:DD:EE:FF, همه فیلدهای دیگر = wildcard
اقدام: ارسال به کنترلر

نتیجه: فقط بسته‌های ARP از AA:BB:CC:DD:EE:FF رهگیری می‌شوند؛ بقیه ترافیک عادی ادامه می‌یابد.

مثال ۲: تطبیق ترافیک زیرشبکه

همه ترافیک به یا از زیرشبکه 10.10.0.0/16 با پورت مقصد TCP 443 (HTTPS) را تطبیق بده.

IP src = 10.10.0.0/255.255.0.0, IP dst = 10.10.0.0/255.255.0.0
IP proto = 6 (TCP), TCP dst port = 443

نتیجه: هر جلسه HTTPS شامل زیرشبکه 10.10.x.x مطابقت داده می‌شود.

مثال ۳: ارسال آگاه از VLAN

همه بسته‌های با VLAN ID = 200 و اولویت = 5 (بالاترین) از یک پورت ورودی خاص را تطبیق بده.

پورت ورودی = ۳, VLAN ID = 200, اولویت VLAN = ۵
همه فیلدهای دیگر = wildcard

نتیجه: ترافیک با اولویت بالا VLAN 200 که روی پورت ۳ می‌رسد برای پردازش ویژه ایزوله می‌شود.

اقدامات OpenFlow

وقتی یک بسته با یک ورودی جریان مطابقت دارد، سوئیچ مجموعه اقدام مرتبط را اجرا می‌کند. اقدامات تعیین می‌کنند چه اتفاقی برای بسته می‌افتد — ممکن است ارسال، رها، اصلاح یا به کنترلر فرستاده شود.

انواع اقدام

اقدامتوضیحاتمورد استفاده
Forward(port)ارسال بسته از یک پورت فیزیکی خاصمسیریابی/سوئیچینگ عادی
Floodارسال به همه پورت‌ها به جز پورت ورودیBroadcast، سوئیچ یادگیرنده
Dropرها کردن بی‌صدا بستهفایروال، کنترل دسترسی
Modify-Fieldبازنویسی یک فیلد سرآیند (مثلاً MAC, IP, VLAN)NAT, تونل‌زنی, برچسب‌زنی
Send-to-Controllerکپسوله‌سازی و ارسال به کنترلر SDNمدیریت بسته اول، سیاست
Enqueue(port, queue)قرار دادن در صف QoS خاصشکل‌دهی ترافیک, QoS
اشتباه رایج: فرض اینکه forward و flood یکسان هستند. Forward(port) به دقیقاً یک پورت ارسال می‌کند. Flood به همه پورت‌ها به جز پورتی که بسته روی آن آمده ارسال می‌کند. Flood کردن بدون جلوگیری از حلقه می‌تواند باعث طوفان broadcast شود.

اجرای مجموعه اقدام

یک ورودی جریان می‌تواند یک لیست از اقدامات را مشخص کند که به ترتیب اجرا می‌شوند. ترتیب مهم است — یک اقدام modify-field که به دنبال آن forward می‌آید، بسته را قبل از ارسال تغییر می‌دهد.

Action Set Processing: for each action in entry.actions: switch action.type: case FORWARD: output packet to specified port case DROP: discard packet (stop processing) case MODIFY_FIELD: packet.header[field] = newValue case SEND_TO_CONTROLLER: encapsulate and send via OpenFlow protocol case FLOOD: output to all ports except ingress case ENQUEUE: place packet on QoS queue

مثال‌های عملی — اقدامات

مثال ۱: DNAT از طریق Modify-Field

MAC و IP مقصد را برای ترافیکی که روی پورت ۲ به یک IP مجازی می‌رسد بازنویسی کن.

تطبیق: ingress=2, IP dst=10.0.0.100
لیست اقدام: [modify_field(IP dst → 10.0.0.50), modify_field(Eth dst → 00:11:22:33:44:55), forward(پورت ۵)]

نتیجه: IP مقصد بسته به 10.0.0.50 بازنویسی می‌شود، MAC آن بازنویسی می‌شود و از پورت ۵ ارسال می‌شود.

مثال ۲: آینه‌سازی ترافیک از طریق چند اقدام

ترافیک عادی را ارسال کن در حالی که یک کپی به پورت نظارت ارسال می‌شود.

تطبیق: IP dst = 10.1.1.0/24, TCP dst = 80
لیست اقدام: [forward(پورت ۳), forward(پورت ۱۰)] // پورت ۱۰ = نظارت

نتیجه: ترافیک HTTP به 10.1.1.x به طور عادی ارسال می‌شود (پورت ۳) و یک کپی به مانیتور می‌رود (پورت ۱۰).

مثال ۳: رها کردن ترافیک مشکوک

همه ترافیک از یک IP منبع حمله شناخته‌شده قبل از رسیدن به سرورهای داخلی رها می‌شود.

تطبیق: IP src = 198.51.100.5
اقدام: drop

نتیجه: هر بسته از 198.51.100.5 بی‌صدا رها می‌شود. هیچ ورودی دیگری بعد از drop بررسی نمی‌شود.

کارت مرجع سریع

Forward: ارسال به یک یا چند پورت فیزیکی

Drop: رها کردن بی‌صدا — به عنوان قانون فایروال عمل می‌کند

Modify-Field: بازنویسی هر فیلد سرآیند

Send-to-Controller: ارتقا به کنترلر SDN برای تصمیم سیاست

شمارنده‌ها: ردیابی بسته‌ها، بایت‌ها و مدت به ازای هر ورودی

مثال‌های کاربردی شبکه

این مثال‌ها نشان می‌دهند که چگونه ورودی‌های جدول جریان OpenFlow فیلدهای تطبیق و اقدامات را برای پیاده‌سازی کارکردهای واقعی شبکه ترکیب می‌کنند.

مثال A: ارسال ساده لایه ۳

دو سوئیچ (s1، s2) بسته‌ها را بر اساس زیرشبکه IP مقصد ارسال می‌کنند. میزبان‌های h1 و h2 در زیرشبکه‌های مختلف پشت s1 و s2 قرار دارند.

Network topology: h1 (10.3.0.1) ── port 1 ─ [s1] ── port 4 ── [s2] ── port 2 ── h2 (10.2.0.1) Flow table for s1 (highest priority first): Priority Entry Pattern Action 20 ingress=1, IP src=10.3.*.*, IP dst=10.2.*.* forward(4) 15 IP dst=10.2.*.* forward(4) 10 ingress=4, IP src=10.2.*.*, IP dst=10.3.*.* forward(1) 5 (table-miss, all wildcards) send_to_controller
مثال ۱: h1 به h2 ارسال می‌کند

بسته: IP src=10.3.0.1, IP dst=10.2.0.1، روی پورت ۱ s1 می‌رسد.

ورودی با اولویت ۲۰ مطابقت دارد (ingress=1, IP src=10.3.*.*, IP dst=10.2.*.*).

نتیجه: از پورت ۴ به سمت s2 ارسال می‌شود.

مثال ۲: h2 به h1 ارسال می‌کند

بسته: IP src=10.2.0.1, IP dst=10.3.0.1، روی پورت ۴ s1 می‌رسد.

ورودی با اولویت ۱۰ مطابقت دارد (ingress=4, IP src=10.2.*.*, IP dst=10.3.*.*).

نتیجه: از پورت ۱ به سمت h1 ارسال می‌شود.

مثال B: توازن بار

یک سوئیچ OpenFlow ترافیک HTTP ورودی را بین دو استخر سرور بر اساس پورت TCP 80 توزیع می‌کند. پورت ورودی تعیین می‌کند کدام استخر سرور درخواست را مدیریت می‌کند.

Load balancer flow table on s1: Priority Entry Pattern Action 30 ingress=1, TCP dst=80 forward(2) → Server Pool A 30 ingress=2, TCP dst=80 forward(3) → Server Pool B 20 TCP dst=80 forward(2) → default to Pool A 10 (table-miss) send_to_controller
مثال ۳: درخواست HTTP از لینک خارجی

بسته: TCP dst=80، روی پورت ۱ (uplink خارجی) می‌رسد.

ورودی اولویت ۳۰ مطابقت دارد: ingress=1, TCP dst=80 → forward(2).

نتیجه: به استخر سرور A (پورت ۲) ارسال می‌شود.

مثال ۴: درخواست HTTP از شبکه داخلی

بسته: TCP dst=80، روی پورت ۲ می‌رسد.

ورودی اولویت ۳۰ مطابقت دارد: ingress=2, TCP dst=80 → forward(3).

نتیجه: به استخر سرور B (پورت ۳) ارسال می‌شود. ترافیک بر اساس منبع توازن می‌شود.

مثال C: فایروال حالت‌مند

یک سوئیچ فایروال فقط به ترافیک از منابع مورد اعتماد خاص اجازه می‌دهد و بقیه ترافیک را رها می‌کند. کنترلر قوانین را به صورت پویا نصب می‌کند.

Firewall flow table on s1: Priority Entry Pattern Action 100 IP src=203.0.113.0/24, TCP dst=443 forward(4) 100 IP src=203.0.113.0/24, TCP dst=80 forward(4) 50 IP dst=10.0.0.0/8 drop 10 (table-miss) send_to_controller
مثال ۵: ترافیک مجاز

بسته: IP src=203.0.113.5, TCP dst=443.

ورودی اولویت ۱۰۰ مطابقت دارد (IP src در 203.0.113.0/24, TCP dst=443).

نتیجه: از پورت ۴ به شبکه داخلی ارسال می‌شود.

مثال ۶: ترافیک مسدودشده

بسته: IP src=198.51.100.99, IP dst=10.0.0.5.

ورودی اولویت ۵۰ مطابقت دارد (IP dst در 10.0.0.0/8).

نتیجه: بسته رها می‌شود. توجه: قوانین ارسال خاص‌تر مطابقت ندارند زیرا IP src در 203.0.113.0/24 نیست.

مثال D: شبکه‌های مجازی با جداول جریان

در مسائل تمرینی، دانشجویان بررسی می‌کنند که چگونه جداول جریان می‌توانند برای ایجاد شبکه‌های مجازی استفاده شوند — دو یا چند شبکه منطقی جداگانه (هرکدام با رفتار ارسال مستقل و مجزای خود) که از مجموعه فیزیکی یکسانی از سوئیچ‌ها و لینک‌های بسته استفاده می‌کنند. این یک کاربرد مستقیم از انتزاع ارسال عمومی است: با نصب ورودی‌های جریان متفاوت برای مستأجران مختلف، یک بافت سوئیچ فیزیکی واحد می‌تواند چندین شبکه مجازی ایزوله را میزبانی کند.

مثال ۷: دو شبکه مجازی که یک سوئیچ را به اشتراک می‌گذارند

یک سوئیچ فیزیکی s1 را در نظر بگیرید که باید از دو شبکه مجازی، قرمز و آبی پشتیبانی کند. بسته‌های هر شبکه مجازی با پورت ورودی و برچسب VLAN آنها شناسایی می‌شوند. هر شبکه مجازی باید رفتار ارسال مستقل داشته باشد — یعنی یک بسته در شبکه قرمز نمی‌تواند به شبکه آبی نشت کند.

قرمز مجازی: پورت‌های ورودی {1,2}, VLAN ID = 10 → ارسال بر اساس جدول مسیریابی قرمز
آبی مجازی: پورت‌های ورودی {3,4}, VLAN ID = 20 → ارسال بر اساس جدول مسیریابی آبی
ترافیک بین شبکه‌ای مجازی به طور ضمنی رها می‌شود زیرا هیچ ورودی جریانی با ترافیک قرمز مقصد پورت‌های آبی مطابقت ندارد و بالعکس.

نتیجه: دو شبکه مجازی مستقل روی همان سوئیچ فیزیکی کار می‌کنند، هرکدام با معناشناسی ارسال خود.

فراتر از OpenFlow: P4 — قابلیت برنامه‌ریزی غنی‌تر

جداول جریان تطبیق-به-علاوه-اقدام OpenFlow یک شکل محدود از برنامه‌پذیری را نشان می‌دهند — کنترلر می‌تواند جفت‌های (تطبیق، اقدام) دلخواه نصب کند، اما مجموعه فیلدهای قابل تطبیق و مجموعه اقدامات ممکن توسط مشخصات ثابت شده است. P4 (Programming Protocol-independent Packet Processors) [P4 2020, Bosshart 2014] زبانی است که برنامه‌پذیری حتی غنی‌تری را فراهم می‌کند که به طور خاص برای پردازش دیتاگرام در نرخ خط طراحی شده است:

  • متغیرها — نگهداری حالت در بین بسته‌ها
  • محاسبات عمومی — محاسبه مقادیر فیلدهای سرآیند
  • عملیات بولی — منطق تطبیق شرطی پیچیده
  • توابع — بلوک‌های پردازش قابل استفاده مجدد
  • عبارات شرطی — انشعاب if/else در سطح داده
  • فرمت‌های سرآیند سفارشی — تجزیه هر پروتکل، نه فقط Ethernet/IP/TCP
  • اقدامات سفارشی — اولیه‌های پردازش تعریف‌شده توسط برنامه‌نویس

در حالی که OpenFlow فیلدهای تطبیق و اقدامات از پیش تعریف‌شده را ثابت می‌کند، P4 به برنامه‌نویس اجازه می‌دهد کل خط لوله پردازش بسته — شامل تجزیه‌گر، جداول تطبیق و منطق اقدام — را تعریف کند، همه در حالی که عملکرد نرخ خط را روی سخت‌افزار هدف حفظ می‌کند.

کارت مرجع سریع

ارسال ساده: تطبیق زیرشبکه IP مقصد → ارسال به پورت گام بعدی

توازن بار: تطبیق پورت ورودی + پورت TCP → استخرهای سرور مختلف

فایروال: تطبیق IPهای منبع مورد اعتماد → ارسال؛ تطبیق مقصد داخلی → رها

P4: خط لوله تطبیق-اقدام کاملاً قابل برنامه‌ریزی؛ سرآیندها و اقدامات سفارشی

جدول جریان = API: کنترلر رفتار سوئیچ را از راه دور برنامه‌ریزی می‌کند

اشتباه رایج: فکر کردن اینکه OpenFlow و P4 فناوری‌های رقیب هستند. OpenFlow یک پروتکل برای رابط سطح کنترل-داده است. P4 یک زبان برای برنامه‌ریزی خود سطح داده است. آن‌ها می‌توانند با هم استفاده شوند — P4 برای پیاده‌سازی یک خط لوله سازگار با OpenFlow.
