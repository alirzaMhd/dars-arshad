ساختار سرآیند دیتاگرام IPv4

دیتاگرام IPv4 بسته لایه شبکه است که توسط پروتکل اینترنت استفاده می‌شود. سرآیند استاندارد ۲۰ بایت است (بدون گزینه‌ها). هر فیلد نقش خاصی در مسیریابی، قطعه‌قطعه‌سازی و تشخیص خطا دارد.

اندازه سرآیند استاندارد (بدون گزینه):
Header = 20 bytes
سرآیند دیتاگرام IP دارای بخش ۲۰ بایتی ثابت است زمانی که هیچ گزینه‌ای وجود نداشته باشد
حداکثر اندازه دیتاگرام:
Max Size = 216 - 1 = 65,535 bytes
فیلد Total Length ۱۶ بیتی، دیتاگرام‌ها را به 65,535 بایت کل (سرآیند + بار) محدود می‌کند
سربار سرآیند + TCP:
IP Header (20) + TCP Header (20) = 40 bytes
هر segment TCP متحمل ۴۰ بایت سربار لایه شبکه+انتقال می‌شود

مثال‌های عملی

مثال ۱: محاسبه اندازه بار

یک دیتاگرام IPv4 دارای Total Length = 1200 بایت و HLEN = 5 است. اندازه بار چقدر است؟

گام ۱: HLEN = 5 یعنی سرآیند = 5 × 4 = 20 بایت
گام ۲: بار = Total Length - Header = 1200 - 20 = 1180 بایت

مثال ۲: تفسیر فیلد پروتکل

یک مسیریاب یک دیتاگرام IPv4 با فیلد Protocol = 6 دریافت می‌کند. چه پروتکل لایه انتقالی باید بار را در مقصد دریافت کند؟

شماره پروتکل 6 مربوط به TCP است. لایه IP میزبان مقصد، بار دیتاگرام را به ماژول TCP برای پردازش تحویل می‌دهد. اگر Protocol = 17 بود، به UDP تحویل داده می‌شد.

مثال ۳: TTL و طول سرآیند

یک دیتاگرام ضبط‌شده دارای ۲۰ بایت هگز اول است: 45 00 00 3C 1C 46 40 00 40 06 B1 E6 C0 A8 00 01 C0 A8 00 02. نسخه، طول سرآیند و TTL را تعیین کنید.

بایت ۱ (0x45):
  نیم‌بایت بالا = 4 → IPv4
  نیم‌بایت پایین = 5 → سرآیند = 5 × 4 = ۲۰ بایت
بایت ۹ (0x40): TTL = ۶۴ (دهدهی)
بایت ۱۰ (0x06): پروتکل = 6 (TCP)

قطعه‌قطعه‌سازی IP

وقتی یک دیتاگرام IP بزرگتر از حداکثر واحد انتقال (MTU) لینک خروجی است، مسیریاب آن را به قطعات کوچک‌تر تقسیم می‌کند. قطعات در میزبان مقصد بازسازی می‌شوند، نه در مسیریاب‌های میانی.

رمزگذاری افست قطعه:
Offset (bytes) = Fragment Offset field value × 8
فیلد افست ۱۳ بیتی موقعیت تقسیم بر ۸ را ذخیره می‌کند (زیرا افست باید روی مرزهای ۸ بایتی باشد)
تعداد قطعات:
N = ceil( (Payload Length) / (MTU - Header Length) )
هر قطعه سرآیند IP خود را حمل می‌کند (معمولاً ۲۰ بایت)
حداکثر داده به ازای هر قطعه:
Max Data per Fragment = (MTU - Header) rounded down to nearest multiple of 8
بار قطعات باید مضرب ۸ بایت باشد (به جز آخرین قطعه)

فیلدهای قطعه‌قطعه‌سازی

فیلدبیتنقش در قطعه‌قطعه‌سازی

بار قطعات (به جز آخرین) MUST مضرب ۸ بایت باشد. اگر بار محاسبه‌شده شما مضرب ۸ نیست، آن را به نزدیک‌ترین مضرب پایین گرد کنید. آخرین قطعه می‌تواند هر اندازه‌ای باشد.

مثال‌های عملی

مثال ۱: قطعه‌قطعه‌سازی پایه

یک دیتاگرام IP 4000 بایتی (سرآیند ۲۰ بایت، بار 3980 بایت) باید از لینکی با MTU = 1500 بایت عبور کند. چند قطعه و افست آن‌ها چیست؟

حداکثر داده به ازای هر قطعه: floor((1500 - 20) / 8) × 8 = floor(1480/8) × 8 = 185 × 8 = 1480 بایت
قطعه ۱: offset = 0, data = 1480 بایت, MF=1
قطعه ۲: offset = 185 × 8 = 1480, data = 1480 بایت, MF=1
قطعه ۳: offset = 370 × 8 = 2960, data = 3980 - 2960 = 1020 بایت, MF=0
مجموعاً ۳ قطعه. همه از Identification = مقدار یکسان استفاده می‌کنند.

مثال ۲: پرچم DF تنظیم شده

یک میزبان یک دیتاگرام 2000 بایتی (شامل سرآیند) با DF=1 روی لینک Ethernet (MTU=1500) ارسال می‌کند. چه اتفاقی می‌افتد؟

دیتاگرام (2000 بایت) از MTU (1500 بایت) فراتر می‌رود. از آنجا که DF=1 (Don't Fragment)، مسیریاب دیتاگرام را رها می‌کند و یک پیام خطای ICMP "Fragmentation Needed" به مبدأ ارسال می‌کند.

مثال ۳: بازسازی افست‌ها

سه قطعه با مقادیر افست و MF زیر به مقصد می‌رسند: (offset=0, MF=1), (offset=185, MF=1), (offset=370, MF=0). اندازه کل بار بازساخته‌شده چقدر است؟

قطعه ۱: بایت‌های 0-1479 (1480 بایت)
قطعه ۲: بایت‌های 1480-2959 (1480 بایت)
قطعه ۳: از 370 × 8 = 2960 شروع می‌شود. از آنجا که MF=0، این آخرین است.
برای یافتن اندازه بار قطعه ۳، به فیلد Total Length نیاز داریم. اگر Total Length = 1040، آنگاه بار = 1040 - 20 = 1020 بایت.
کل بار بازساخته‌شده = 1480 + 1480 + 1020 = 3980 بایت

Header Checksum

checksum سرآیند IPv4 فقط از سرآیند محافظت می‌کند (نه بار). باید در هر گام دوباره محاسبه شود زیرا فیلد TTL تغییر می‌کند. الگوریتم Internet checksum است: جمع متمم ۱ همه کلمات ۱۶ بیتی در سرآیند.

الگوریتم Internet Checksum:
Checksum = ~( ∑ (header 16-bit words in 1s complement) )
checksum متمم ۱ جمع متمم ۱ همه کلمات ۱۶ بیتی در سرآیند است (فیلد checksum خود در طول محاسبه صفر در نظر گرفته می‌شود)

شبه‌کد محاسبه Checksum

// Input: array of 16-bit words representing IP header (checksum field = 0) // Output: 16-bit Internet checksum function computeInternetChecksum(words[]): sum = 0 for each word in words: sum = sum + word // ordinary binary addition if sum > 0xFFFF: // carry-out detected sum = (sum & 0xFFFF) + 1 // wrap-around (end-around carry) checksum = ~sum & 0xFFFF // ones' complement return checksum // Verification at receiver: // Compute checksum over entire header INCLUDING checksum field // If result == 0, no error detected
Checksum IP فقط سرآیند HEADER را پوشش می‌دهد، نه بار را. TCP و UDP checksumهای خود را دارند که کل segment را پوشش می‌دهند. checksum IP باید در هر مسیریاب دوباره محاسبه شود زیرا TTL تغییر می‌کند. این یک هزینه پردازش قابل توجه است — به همین دلیل IPv6 checksum سرآیند را به طور کلی حذف کرد.

مثال‌های عملی

مثال ۱: محاسبه ساده Checksum

با فرض سه کلمه ۱۶ بیتی سرآیند: 0x4500، 0x003C، 0x1C46. checksum را محاسبه کنید.

جمع: 0x4500 + 0x003C = 0x453C
افزودن بعدی: 0x453C + 0x1C46 = 0x6182 (بدون نقلی)
متمم ۱: ~0x6182 = 0x9E7D
(برای یک سرآیند کامل، همه ۱۰ کلمه سرآیند ۲۰ بایتی جمع می‌شدند)

مثال ۲: نقلی انتها-به-انتها

دو کلمه ۱۶ بیتی را جمع کنید: 0xFFFF + 0x0001.

جمع معمولی: 0xFFFF + 0x0001 = 0x10000 (این ۱۷ بیت است)
نقلی انتها-به-انتها: 0x0000 + 1 = 0x0001
این جمع متمم ۱ است. متمم ۱ (~0x0001) = 0xFFFE به عنوان checksum ذخیره می‌شود.

مثال ۳: تأیید در گیرنده

در مقصد، کل سرآیند (شامل فیلد checksum) پردازش می‌شود. جمع متمم ۱ محاسبه‌شده همه کلمات = 0xFFFF. این به چه معناست؟

اگر جمع کل سرآیند (شامل checksum) = 0xFFFF باشد، پس از گرفتن متمم ۱، ~0xFFFF = 0x0000 را می‌گیریم. نتیجه 0 نشان می‌دهد هیچ خطایی تشخیص داده نشده است. هر نتیجه غیرصفر به معنای تشخیص خطای بیتی است و دیتاگرام معمولاً دور ریخته می‌شود.

فیلد Time-to-Live (TTL)

فیلد ۸ بیتی TTL از چرخش بی‌نهایت دیتاگرام‌ها در شبکه جلوگیری می‌کند. هر مسیریاب TTL را ۱ واحد کاهش می‌دهد. وقتی TTL به ۰ می‌رسد، مسیریاب دیتاگرام را رها کرده و یک پیام ICMP Time Exceeded به مبدأ ارسال می‌کند.

رفتار TTL:
TTLnew = TTLold - 1   (if TTLold > 0 → forward; if TTLold = 0 → drop)
دقیقاً یک بار در هر گام مسیریاب کاهش می‌یابد
برخی سیستم‌های عامل TTL اولیه را ۶۴ (Linux)، ۱۲۸ (Windows) یا ۲۵۵ (Solaris) تنظیم می‌کنند. هنگام تحلیل ردپای شبکه، TTL اولیه منهای TTL فعلی برابر با تعداد گام‌های مسیریاب طی‌شده است.

مثال‌های عملی

مثال ۱: تعداد گام‌ها از TTL

یک میزبان Linux بسته‌ای با TTL اولیه=64 ارسال می‌کند. بسته با TTL=51 به مقصد می‌رسد. چند مسیریاب را طی کرده است؟

گام‌ها = TTL اولیه - TTL ورود = 64 - 51 = ۱۳ مسیریاب

مثال ۲: انقضای TTL

یک دیتاگرام با TTL=1 به مسیریاب A می‌رسد. پس از کاهش، چه اتفاقی می‌افتد؟

مسیریاب A TTL را از 1 به 0 کاهش می‌دهد. مسیریاب دیتاگرام را رها می‌کند و یک پیام ICMP "Time Exceeded" (Type 11) به آدرس IP مبدأ ارسال می‌کند.

مثال ۳: مکانیزم Traceroute

Traceroute بسته‌هایی با TTL=1، سپس TTL=2، سپس TTL=3 و غیره ارسال می‌کند. در هر گام چه اتفاقی می‌افتد؟

TTL=1: اولین مسیریاب به 0 کاهش می‌دهد، رها می‌کند، ICMP Time Exceeded ارسال می‌کند. مبدأ RTT و IP مسیریاب A را ثبت می‌کند.
TTL=2: اولین مسیریاب ارسال می‌کند (TTL 2→1)، دومین مسیریاب به 0 کاهش می‌دهد، رها می‌کند، ICMP ارسال می‌کند. مبدأ IP مسیریاب B را ثبت می‌کند.
TTL=N: نهایتاً به مقصد می‌رسد. مقصد ICMP Port Unreachable (یا پاسخ برنامه) ارسال می‌کند. مبدأ اکنون کل مسیر و RTT هر گام را می‌داند.

کپسوله‌سازی در IPv4

فیلد بار دیتاگرام IP معمولاً یک segment لایه انتقال (TCP یا UDP) را حمل می‌کند. فیلد ۸ بیتی Protocol به میزبان مقصد می‌گوید کدام پروتکل لایه بالایی باید داده‌های خارج‌شده از کپسول را دریافت کند.

نگاشت شماره پروتکل:
Protocol Number = 6 → TCP  |  Protocol Number = 17 → UDP
شماره پروتکل در IP نقشی مشابه شماره پورت در لایه انتقال ایفا می‌کند — لایه شبکه را به لایه انتقال بالای خود متصل می‌کند
نسبت سربار IPv4 + TCP:
Overhead % = 40 / (40 + Application Data) × 100%
برای پیام‌های کوچک برنامه (مثلاً ۴۰ بایت)، سربار = 40/(40+40) = 50%

مثال ۱: محاسبه سربار

یک برنامه هر ۱۰ میلی‌ثانیه ۱۰۰ بایت داده تولید می‌کند که در TCP و سپس IP کپسوله می‌شود. درصد سربار سرآیند چقدر است؟

سرآیند IP: ۲۰ بایت
سرآیند TCP: ۲۰ بایت
کل سرآیند: ۴۰ بایت
کل دیتاگرام: 40 + 100 = ۱۴۰ بایت
درصد سربار: 40/140 × 100 = 28.57%

مثال ۲: شناسایی پروتکل

یک دیتاگرام IP ضبط‌شده نشان می‌دهد بایت ۱۰ سرآیند (شمارش از ۱) = 0x11. چه پروتکل انتقالی حمل می‌شود؟

فیلد Protocol در بایت ۱۰ سرآیند IP قرار دارد. 0x11 = 17 دهدهی. شماره پروتکل 17 = UDP. بنابراین بار یک segment UDP است.

مثال ۳: انتقال IPv6 — تونل‌زنی

دو مسیریاب IPv6 از طریق یک شبکه فقط-IPv4 ارتباط برقرار می‌کنند. یک دیتاگرام IPv6 (سرآیند 40B + بار 100B) باید تونل‌زنی شود. اندازه کل دیتاگرام IPv4 حمل‌کننده آن چقدر است؟

سرآیند IPv4: ۲۰ بایت
بار IPv4 (کل دیتاگرام IPv6): 40 + 100 = ۱۴۰ بایت
کل دیتاگرام IPv4: 20 + 140 = ۱۶۰ بایت
فیلد Protocol IPv4 برابر ۴۱ خواهد بود که نشان می‌دهد بار یک دیتاگرام IPv6 است.
