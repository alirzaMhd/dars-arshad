مرور ICMP

پروتکل پیام کنترل اینترنت (ICMP) یک پروتکل اصلی در مجموعه پروتکل اینترنت است. توسط دستگاه‌های شبکه، از جمله مسیریاب‌ها، برای ارسال پیام‌های خطا و اطلاعات عملیاتی که موفقیت یا شکست در ارتباط با یک آدرس IP دیگر را نشان می‌دهد، استفاده می‌شود.

مدیریت گزینه‌های ناشناخته

مهم: ICMP باعث可靠 شدن IP نمی‌شود. فقط خطاها را گزارش می‌کند — پروتکل لایه بالاتر (مثلاً TCP) باید بازیابی را مدیریت کند.

برای پیام‌های گزارش خطا، بار ICMP شامل 8 بایت اول دیتاگرام IP خطا (هدر IP + 8 بایت اول هدر حمل) است تا به فرستنده کمک کند مشخص کند کدام بسته باعث خطا شده است.

• مقصد غیرقابل دسترس (3/*)

• Source Quench (4/0)

• زمان تجاوز شد (11/*)

• مشکل پارامتر (12/0)

همیشه شامل 8 بایت اول دیتاگرام خطا هستند

هشدار: Source Quench (نوع 4) به ندرت در عمل استفاده می‌شود. هدف اصلی آن کنترل ازدحام بود، اما TCP مکانیزم کنترل ازدحام خود را در لایه حمل دارد و بیت‌های ECN (اعلان ازدحام صریح) می‌توانند ازدحام را در لایه شبکه علامت دهند.

قوانین پیام خطای ICMP

پیام‌های خطای ICMP هرگز در پاسخ به موارد زیر تولید نمی‌شوند:

  • یک پیام خطای ICMP دیگر (جلوگیری از حلقه‌های بی‌نهایت)
  • دیتاگرام‌های broadcast یا multicast IP
  • دیتاگرام‌هایی با آدرس مبدأ که unicast نیست
  • قطعات به غیر از اولین قطعه

Ping

Ping از پیام‌های درخواست Echo و پاسخ Echo ICMP برای تست دسترس‌پذیری و اندازه‌گیری زمان رفت و برگشت استفاده می‌کند.

مکانیزم Ping:
میزبان A نوع 8، کد 0 ICMP می‌فرستد ← میزبان B نوع 0، کد 0 ICMP پاسخ می‌دهد
زمان رفت و برگشت = زمان بین درخواست و پاسخ

پیاده‌سازی

سرور ping مستقیماً در هسته سیستم عامل پیاده‌سازی می‌شود، نه به عنوان یک فرآیند سطح کاربر

برنامه کلاینت به سیستم عامل دستور می‌دهد پیام‌های ICMP نوع 8 کد 0 تولید کند

درصد از دست دادن بسته

مثال خروجی Ping
$ ping -c 4 8.8.8.8 PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data. 64 bytes from 8.8.8.8: icmp_seq=1 ttl=118 time=12.3 ms 64 bytes from 8.8.8.8: icmp_seq=2 ttl=118 time=11.8 ms 64 bytes from 8.8.8.8: icmp_seq=3 ttl=118 time=12.1 ms 64 bytes from 8.8.8.8: icmp_seq=4 ttl=118 time=11.9 ms --- 8.8.8.8 ping statistics --- 4 packets transmitted, 4 received, 0% packet loss, time 3005ms rtt min/avg/max/mdev = 11.827/12.025/12.300/0.176 ms

میزبان درخواست Echo ICMP (8/0) می‌فرستد و پاسخ Echo (0/0) دریافت می‌کند. TTL = 118 یعنی بسته 256 - 118 = 138 هاپ (یا 64 - 48 = 16 بسته به TTL اولیه) را طی کرده است.

Traceroute

Traceroute مسیر بسته‌ها از مبدأ تا مقصد را با بهره‌برداری از فیلد TTL نقشه‌برداری می‌کند.

مکانیزم Traceroute:
ارسال بسته‌ها با TTL افزایشی (1، 2، 3، ...) به یک پورت UDP غیرمحتمل
هر مسیریاب TTL را کاهش می‌دهد؛ وقتی TTL=0، مسیریاب ICMP Time Exceeded (11/0) می‌فرستد. traceroute استاندارد 3 بسته به ازای هر مقدار TTL می‌فرستد و 3 اندازه‌گیری RTT به ازای هر هاپ فراهم می‌کند.
گامTTLعملپاسخ ICMP
11اولین مسیریاب TTL را کاهش می‌دهد ← 0، بسته را می‌اندازدTime Exceeded (11/0) از مسیریاب 1
22مسیریاب 1 ارسال می‌کند، مسیریاب 2 TTL را کاهش می‌دهد ← 0Time Exceeded (11/0) از مسیریاب 2
33به مقصد می‌رسد، اما پورت استفاده نشده استPort Unreachable (3/3) از مقصد

روش UDP

بسته‌ها به پورت UDP بالای غیرمحتمل فرستاده می‌شوند

Traceroute می‌فهمد به مقصد رسیده است

روش ICMP

برخی پیاده‌سازی‌ها از درخواست Echo ICMP استفاده می‌کنند

مقصد با پاسخ Echo (0/0) پاسخ می‌دهد

روش TCP

از بسته‌های SYN به پورت 80 استفاده می‌کند

مقصد با SYN/ACK پاسخ می‌دهد

مفید وقتی فایروال‌ها ICMP را مسدود می‌کنند

توجه: بسیاری از مسیریاب‌ها و فایروال‌ها طوری پیکربندی شده‌اند که پیام‌های Time Exceeded ICMP را نفرستند و باعث می‌شوند traceroute "* * *" را برای آن هاپ‌ها نشان دهد.

مثال‌های حل شده

مثال 1: استفاده از Ping برای تست دسترس‌پذیری

سناریو: یک مدیر شبکه باید تأیید کند که یک سرور راه دور در 203.0.113.50 قابل دسترس است و زمان پاسخ را اندازه‌گیری کند.

$ ping -c 5 203.0.113.50 PING 203.0.113.50 (203.0.113.50) 56(84) bytes of data. 64 bytes from 203.0.113.50: icmp_seq=1 ttl=64 time=45.2 ms 64 bytes from 203.0.113.50: icmp_seq=2 ttl=64 time=44.8 ms 64 bytes from 203.0.113.50: icmp_seq=3 ttl=64 time=46.1 ms 64 bytes from 203.0.113.50: icmp_seq=4 ttl=64 time=45.5 ms 64 bytes from 203.0.113.50: icmp_seq=5 ttl=64 time=44.9 ms --- 203.0.113.50 ping statistics --- 5 packets transmitted, 5 received, 0% packet loss, time 4005ms rtt min/avg/max/mdev = 44.800/45.300/46.100/0.504 ms

تحلیل:

  • 0% از دست دادن بسته — همه بسته‌ها به مقصد رسیدند و پاسخ‌ها برگشتند
  • میانگین RTT: 45.3 ms — قابل قبول برای یک سرور راه دور
  • TTL = 64 نشان می‌دهد میزبان مقصد از TTL اولیه پیش‌فرض 64 استفاده می‌کند (رایج در سیستم‌های لینوکس) و مستقیماً قابل دسترس است
  • mdev پایین (0.504 ms) نشان‌دهنده مسیر شبکه پایدار با نوسان حداقل است
مثال 2: تحلیل خروجی Traceroute

سناریو: کاربران از اتصالات کند به یک سرور وب در 198.51.100.20 گزارش می‌دهند. مدیر traceroute را اجرا می‌کند تا تنگنا را پیدا کند.

$ traceroute 198.51.100.20 traceroute to 198.51.100.20 (198.51.100.20), 30 hops max 1 10.0.0.1 (10.0.0.1) 0.5 ms 0.4 ms 0.4 ms 2 172.16.1.1 (172.16.1.1) 2.1 ms 2.0 ms 2.0 ms 3 192.168.20.1 (192.168.20.1) 15.3 ms 15.1 ms 15.2 ms 4 203.0.113.1 (203.0.113.1) 45.8 ms 125.3 ms 46.1 ms 5 198.51.100.20 (198.51.100.20) 48.2 ms 48.0 ms 48.1 ms

تحلیل:

  • هاپ 4 تنوع قابل توجهی نشان می‌دهد: یک بسته 125.3 ms در مقابل ~46 ms برای بقیه — این نشان‌دهنده ازدحام یا یک مسیریاب کند است
  • تنگنا در هاپ 4 (203.0.113.1) است، احتمالاً یک مسیریاب تجمیع ISP تحت بار
  • تأخیر سرتاسری: ~48 ms — مناسب برای یک سرور راه دور
  • توصیه: مسیریاب در 203.0.113.1 را برای ازدحام بررسی کنید یا بررسی کنید آیا مسیر جایگزینی موجود است
مثال 3: سناریوی خطای ICMP — قطعه‌بندی لازم است

سناریو: یک میزبان یک بسته 2000 بایتی به مقصدی در آن سوی یک پیوند با MTU 1500 می‌فرستد. پرچم DF (قطعه‌بندی نکن) تنظیم شده است. مسیریاب با یک خطای ICMP پاسخ می‌دهد.

پیام ICMP تولید شده:
نوع: 3 • کد: 4 • مقصد غیرقابل دسترس (قطعه‌بندی لازم است اما DF تنظیم شده)
مسیریاب 8 بایت اول دیتاگرام خطا (هدر IP + شروع هدر TCP/UDP) را شامل می‌کند

توالی رویدادها:

  1. میزبان دیتاگرام IP با طول کل 2000، DF=1 می‌فرستد
  2. مسیریاب دیتاگرام را دریافت می‌کند، نیاز به ارسال روی پیوند با MTU 1500 دارد
  3. مسیریاب نمی‌تواند قطعه‌بندی کند (DF=1) و نمی‌تواند بسته بیش از اندازه بزرگ را ارسال کند
  4. مسیریاب ICMP نوع 3، کد 4 تولید می‌کند و MTU هاپ بعدی را در پیام قرار می‌دهد
  5. میزبان خطای ICMP را دریافت می‌کند و MTU کاهش‌یافته را برای آن مقصد کش می‌کند (کشف MTU مسیر)
  6. میزبان با اندازه بسته کوچکتر (≤ 1500 بایت) دوباره ارسال می‌کند

این اساس کشف MTU مسیر (PMTUD) است که به ICMP برای تعیین پویای حداکثر اندازه بسته قابل عبور از مسیر بدون قطعه‌بندی متکی است.

مثال 4: حمله تغییر مسیر ICMP (امنیتی)

سناریو: یک مهاجم یک پیام جعلی تغییر مسیر ICMP می‌فرستد تا ترافیک را از طریق دستگاه خود هدایت کند.

مهاجم می‌فرستد: ICMP نوع 5، کد 1 (تغییر مسیر میزبان) IP مبدأ: جعل شده به عنوان دروازه (192.168.1.1) IP هدف: میزبان قربانی (192.168.1.100) دروازه جدید: IP مهاجم (192.168.1.200) شامل: 8 بایت اول دیتاگرام خطا (برای تطبیق با جریان موجود)

دفاع:

  • سیستم‌عامل‌های مدرن پیام‌های تغییر مسیر ICMP را به طور پیش‌فرض نادیده می‌گیرند
  • مسیریاب‌ها فقط برای ترافیک واقعاً ارسال‌شده توسط خودشان تغییر مسیر می‌فرستند
  • از IPsec برای احراز هویت پیام‌های ICMP استفاده کنید
  • پذیرش تغییر مسیر ICMP را غیرفعال کنید: sysctl net.ipv4.conf.all.accept_redirects=0
مثال 5: ICMPv6 Packet Too Big — کشف MTU مسیر

سناریو: یک میزبان IPv6 یک بسته 2000 بایتی می‌فرستد. یک پیوند میانی دارای MTU 1280 است. از آنجا که مسیریاب‌های IPv6 قطعه‌بندی نمی‌کنند، مسیریاب ICMPv6 Packet Too Big می‌فرستد.

پیام ICMPv6:
ICMPv6 نوع: 2 • کد: 0 • Packet Too Big
شامل MTU پیوند محدودکننده (1280 بایت) در بدنه پیام است
