کنترل جریان TCP

شبکه‌های کامپیوتری — راهنمای جامع برای آزمون ۲۰/۲۰

مبانی کنترل جریان

کنترل جریان یک سرویس تطبیق سرعت است — از سرریز شدن بافر گیرنده توسط فرستنده جلوگیری می‌کند.

⚠ تمایز مهم: کنترل جریان ≠ کنترل ازدحام. کنترل جریان از overwhelmed شدن گیرنده (بافر دریافت) جلوگیری می‌کند. کنترل ازدحام از overwhelmed شدن شبکه (بافرهای مسیریاب) جلوگیری می‌کند.

بافر دریافت

LastByteRead

آخرین بایت در جریان که توسط برنامه از بافر خوانده شده است.

LastByteRcvd

آخرین بایت در جریان که از شبکه رسیده و در بافر قرار گرفته است.

RcvBuffer

اندازه کل بافر دریافت اختصاص داده شده برای اتصال.

محدودیت سرریز بافر
LastByteRcvd - LastByteRead ≤ RcvBuffer
مقدار داده خوانده‌نشده در بافر نباید از ظرفیت بافر تجاوز کند.

برنامه داده را با سرعت خود از بافر می‌خواند. اگر فرستنده سریع‌تر از خواندن برنامه ارسال کند، بافر پر می‌شود. کنترل جریان از این سرریز جلوگیری می‌کند.

⚠ فرض کلیدی: در طول این بحث فرض می‌کنیم گیرنده TCP سگمنت‌های خارج‌ازترتیب را دور می‌ریزد. پیاده‌سازی‌های مدرن TCP اغلب داده‌های خارج‌ازترتیب را بافر می‌کنند، اما برای درک اصول کنترل جریان، فرض می‌کنیم سگمنت‌های خارج‌ازترتیب دور ریخته می‌شوند.

مکانیزم پنجره دریافت (rwnd)

تعریف

پنجره دریافت (rwnd)
rwnd = RcvBuffer - (LastByteRcvd - LastByteRead)
مقدار فضای خالی در بافر دریافت. پویا — با رسیدن داده و خواندن برنامه تغییر می‌کند.
محدودیت فرستنده
LastByteSent - LastByteAcked ≤ rwnd
مقدار داده تأییدنشده نباید از پنجره اعلام‌شده گیرنده تجاوز کند.

نحوه عملکرد

۱. میزبان B مقدار rwnd جاری خود را در فیلد پنجره دریافت هر سگمنتی که به A می‌فرستد قرار می‌دهد.

۲. در ابتدا، میزبان B rwnd = RcvBuffer تنظیم می‌کند.

۳. میزبان A دو متغیر را دنبال می‌کند:

LastByteSent

آخرین بایت ارسال شده به اتصال.

LastByteAcked

آخرین بایت تأیید شده.

۴. میزبان A تضمین می‌کند: LastByteSent - LastByteAcked ≤ rwnd

نمودار بافر دریافت (شکل ۳.۳۸)

بافر دریافت (RcvBuffer) به صورت زیر可视سازی می‌شود:

+--------------------------------------------+
| RcvBuffer |
|---------------------------------------------|
| TCP data in buffer (rwnd used) | Spare room |
|<-- LastByteRcvd - LastByteRead -->|<-- rwnd ->|
+--------------------------------------------+
↑ LastByteRead ↑ LastByteRcvd ↑ end

متغیر rwnd = RcvBuffer - (LastByteRcvd - LastByteRead). با خواندن داده توسط برنامه، LastByteRead جلو می‌رود و rwnd افزایش می‌یابد. با رسیدن داده جدید، LastByteRcvd جلو می‌رود و rwnd کاهش می‌یابد.

از آنجا که TCP تمام‌دوطرفه است، فرستنده در هر طرف اتصال یک پنجره دریافت مجزا نگهداری می‌کند. میزبان A rwnd خود را (برای داده ورودی) دنبال می‌کند و همچنین به rwnd اعلام‌شده توسط میزبان B (برای داده خروجی) احترام می‌گذارد.

// بررسی کنترل جریان در سمت فرستنده if ((NextSeqNum - SendBase) < rwnd_received) { // ارسال سگمنت جدید مجاز است send segment; } else { // باید صبر کند — بافر گیرنده پر است buffer data for later; }
⚠ اشتباه رایج: فیلد "پنجره دریافت" در هدر TCP، پنجره دریافت فرستنده (فضای خالی بافر گیرنده) را حمل می‌کند. هر طرف rwnd خود را به طرف دیگر اعلام می‌کند.

مشکل پنجره صفر

مشکل

اگر بافر دریافت میزبان B پر شود، rwnd = 0 اعلام می‌کند. میزبان A ارسال داده را متوقف می‌کند. اما اگر B داده‌ای برای ارسال به A نداشته باشد چه؟

B نمی‌تواند فقط برای اعلام مقدار جدید rwnd یک سگمنت بفرستد — TCP فقط زمانی سگمنت می‌فرستد که داده‌ای برای ارسال یا ACK برای بازگشت وجود داشته باشد.

اگر برنامه B بافر را خالی کند، B چیزی برای ارسال به A ندارد، بنابراین A هرگز از فضای تازه آزاد شده مطلع نمی‌شود. بن‌بست!

راه‌حل: سگمنت‌های کاوشگر ۱-بایتی

قانون مشخصات TCP

وقتی rwnd = 0، فرستنده باید به ارسال سگمنت‌هایی با ۱ بایت داده ادامه دهد.

پاسخ گیرنده

گیرنده این کاوشگرهای ۱-بایتی را تأیید می‌کند و ACK مقدار rwnd به‌روز شده (اکنون > ۰) را حمل می‌کند.

چرا UDP کنترل جریان ندارد

UDP هیچ کنترل جریانی فراهم نمی‌کند. در یک پیاده‌سازی UDP معمولی، UDP سگمنت‌ها را به یک بافر با اندازه محدود که قبل از سوکت متناظر قرار دارد اضافه می‌کند. فرایند هر بار یک سگمنت کامل را از بافر می‌خواند. اگر فرایند به اندازه کافی سریع نخواند، بافر سرریز می‌شود و سگمنت‌ها رها می‌شوند.

// مکانیزم کاوشگر پنجره صفر if (rwnd == 0) { // ارسال دوره‌ای سگمنت‌های کاوشگر ۱-بایتی send segment with 1 byte of new data; // پاسخ ACK حاوی rwnd به‌روز شده خواهد بود }
⚠ اشتباه رایج: کاوشگر ۱-بایتی یک ارسال مجدد نیست — یک بایت داده جدید است که به طور خاص برای دریافت ACK با اطلاعات rwnd تازه فرستاده می‌شود.

مثال‌های عملی و مقایسه

مثال ۱: محاسبه پایه بافر

تنظیمات: RcvBuffer = 4096 بایت. برنامه ۵۰۰ بایت/ثانیه می‌خواند. فرستنده با ۱۰۰۰ بایت/ثانیه ارسال می‌کند.

حالت اولیه: LastByteRcvd = 0, LastByteRead = 0, rwnd = 4096.

بعد از ۱ ثانیه: LastByteRcvd = 1000 (فرستنده ۱۰۰۰ بایت فرستاد), LastByteRead = 500 (برنامه ۵۰۰ خواند).

داده خوانده‌نشده = 1000 - 500 = 500 بایت.

rwnd = 4096 - 500 = 3596 بایت.

بعد از ۵ ثانیه: LastByteRcvd = 5000, LastByteRead = 2500.

داده خوانده‌نشده = 5000 - 2500 = 2500 بایت.

rwnd = 4096 - 2500 = 1596 بایت.

بعد از ۸ ثانیه: LastByteRcvd = 8000, LastByteRead = 4000.

داده خوانده‌نشده = 8000 - 4000 = 4000 بایت.

rwnd = 4096 - 4000 = 96 بایت (بافر تقریباً پر).

بعد از ~۸.۲ ثانیه: rwnd به ۰ می‌رسد. فرستنده باید متوقف شود (یا کاوشگرهای ۱-بایتی بفرستد).

مثال ۲: کنترل جریان در عمل با نرخ خواندن متغیر برنامه

تنظیمات: RcvBuffer = 8192 بایت. فرستنده هر ثانیه ۲۰۰۰ بایت می‌فرستد.

توجه کنید حتی اگر فرستنده می‌خواهد ۲۰۰۰ بایت/ثانیه ارسال کند، محدودیت rwnd ارسال واقعی را محدود می‌کند. فرستنده هرگز از ظرفیت بافر گیرنده تجاوز نمی‌کند.

مثال ۳: پنجره صفر و بازیابی کاوشگر

تنظیمات: RcvBuffer = 2048 بایت. در ابتدا خالی.

فاز ۱ — پر شدن بافر: فرستنده به سرعت ۲۰۴۸ بایت می‌فرستد. LastByteRcvd=2048. برنامه هنوز نخوانده. rwnd=0.

فاز ۲ — گرفتاری: فرستنده نمی‌تواند داده بیشتری بفرستد. B داده‌ای برای ارسال به A ندارد.

فاز ۳ — کاوشگر: A یک کاوشگر ۱-بایتی می‌فرستد (seq=2049). B آن را تأیید می‌کند (ack=2050, rwnd=0 همچنان).

فاز ۴ — برنامه می‌خواند: برنامه ۱۰۲۴ بایت می‌خواند. LastByteRead = 1024. rwnd = 2048 - 1024 = 1024.

فاز ۵ — ACK با rwnd جدید: B ACK=2049 (برای کاوشگر) با rwnd=1024 می‌فرستد.

فاز ۶ — از سرگیری: A ارسال را از سر می‌گیرد (تا ۱۰۲۴ بایت تأییدنشده).

مکانیزم کاوشگر ۱-بایتی برای شکستن بن‌بست پنجره صفر ضروری است.
