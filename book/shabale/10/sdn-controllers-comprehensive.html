کنترلرهای SDN — OpenDaylight و ONOS

لایه شبکه — معماری‌های مدرن کنترلر SDN برای امتحان

کنترلر OpenDaylight (ODL)

OpenDaylight (ODL) یک کنترلر SDN متن‌باز است که با مشارکت بنیاد لینوکس توسعه یافته است. این کنترلر حمایت صنعتی قابل توجهی پیدا کرده و یکی از پراستقرارترین کنترلرهای SDN است.

شکل 5.17: معماری OpenDaylight

معماری لایه‌ای ODL (شکل 5.17):
ارکستریشن و برنامه‌های شبکه (لایه بالایی)
↗ REST/RESTCONF/NETCONF APIs ↖
لایه انتزاع سرویس (SAL) — مرکز عصب
↗ [پیام‌رسانی] [ذخیره داده پیکربندی و عملیاتی] ↖
پروتکل‌های جنوبی: OpenFlow | NETCONF | SNMP | OVSDB
SAL یک رابط انتزاعی یکنواخت برای همه پروتکل‌های جنوبی فراهم می‌کند

لایه انتزاع سرویس (SAL)

SAL مرکز عصب کنترلر است. این لایه فراهم می‌کند:

قابلیت‌های SAL

• فراخوانی سرویس — مؤلفه‌ها سرویس‌های یکدیگر را فراخوانی می‌کنند

• دسترسی به داده — خواندن/نوشتن داده پیکربندی و عملیاتی

• اشتراک رویداد — اشتراک در رویدادهای تولیدشده توسط مؤلفه‌ها

• انتزاع پروتکل — رابط یکنواخت برای پروتکل‌های جنوبی

پروتکل‌های جنوبی پشتیبانی‌شده

• OpenFlow — مدیریت جدول جریان

• NETCONF — پروتکل پیکربندی شبکه

• SNMP — پروتکل ساده مدیریت شبکه

• OVSDB — پروتکل پایگاه داده Open vSwitch

توابع پایه شبکه ODL مربوط به قابلیت‌های مدیریت حالت در سطح شبکه هستند. اینها عبارتند از:

AD-SAL در مقابل MD-SAL

ODL دو رویکرد برای تعامل برنامه‌ها با سرویس‌های کنترلر فراهم می‌کند:

جنبهAD-SAL (API-Driven)MD-SAL (Model-Driven)
رویکردبرنامه‌ها مستقیماً از REST API استفاده می‌کنندمدل‌های YANG ساختار داده را تعریف می‌کنند
معرفی شدهنسخه‌های اولیه ODLنسخه‌های بعدی ODL
پروتکلREST روی HTTPNETCONF (مدل‌های تعریف‌شده با YANG)
انعطاف‌پذیریکمتر انعطاف‌پذیر، تغییرات API نیاز به بروزرسانی دارندانعطاف‌پذیرتر، مدل‌ها قابل توسعه هستند
موارد استفادهبرنامه‌های ساده، یکپارچه‌سازی سریعمدیریت پیکربندی پیچیده
مدل‌سازی داده YANG: YANG (RFC 6020) یک زبان مدل‌سازی داده است که برای تعریف ساختار داده پیکربندی و حالت عملیاتی استفاده می‌شود. در MD-SAL، دستگاه‌ها با دستکاری این مدل‌های تعریف‌شده با YANG با استفاده از NETCONF پیکربندی و مدیریت می‌شوند. این قابل توسعه‌تر از APIهای سخت‌کد شده است.

سرویس‌های پیشرفته

در بالای توابع پایه شبکه، ODL سرویس‌های پیشرفته فراهم می‌کند:

نمونه سرویس‌های پیشرفته

• مهندسی ترافیک — بهینه‌سازی انتخاب مسیر

• فایروال — اجرای سیاست امنیتی

• متوازن‌سازی بار — توزیع ترافیک بین سرورها

دسترسی شمالی

برنامه‌ها به سرویس‌های پیشرفته از طریق:

• REST/RESTCONF (AD-SAL)

• NETCONF (MD-SAL)

کنترلر ONOS

ONOS (سیستم عامل شبکه باز) یک کنترلر SDN متن‌باز است که با مشارکت بنیاد لینوکس توسعه یافته است. مانند ODL، دارای معماری لایه‌ای است اما با انتخاب‌های طراحی متمایز.

شکل 5.18: معماری ONOS

معماری سه لایه ONOS (شکل 5.18):
برنامه‌های کنترل شبکه (چارچوب Intent، REST API)
↕ انتزاعات و پروتکل‌های شمالی
هسته توزیع‌شده ONOS (متمرکز منطقاً)
↕ انتزاعات و پروتکل‌های جنوبی
دستگاه‌ها، پیوندها، میزبان‌ها، قوانین جریان، آمار
ONOS به عنوان یک سرویس توزیع‌شده روی سرورهای متصل اجرا می‌شود؛ هر سرور نرم‌افزار یکسانی اجرا می‌کند

لایه 1: انتزاعات و پروتکل‌های شمالی

لایه شمالی انتزاعاتی برای برنامه‌های کنترل شبکه فراهم می‌کند. ویژگی‌های کلیدی:

  • چارچوب Intent: برنامه‌ها سرویس‌های سطح بالا را بدون جزئیات پیاده‌سازی درخواست می‌کنند (مثلاً "میزبان A را به میزبان B متصل کن" بدون مشخص کردن VLANها، مسیرها، یا پروتکل‌ها)
  • دسترسی همزمان: از طریق پرس‌وجو (REST API)
  • دسترسی ناهمزمان: از طریق فراخوان‌های listener مطلع از تغییرات حالت شبکه
مثال چارچوب Intent ONOS:
Intent: "ارتباط بین میزبان A و میزبان B را مجاز کن"
Intent: "ارتباط میزبان A با میزبان C را مسدود کن"
چارچوب intent این سیاست‌های سطح بالا را به ورودی‌های جریان خاص ترجمه می‌کند

لایه 2: هسته توزیع‌شده

هسته توزیع‌شده قلب ONOS است. این هسته حالت شبکه را نگهداری می‌کند و انتزاع یک سرویس متمرکز منطقاً را فراهم می‌کند. هسته توزیع‌شده مکانیزم‌هایی برای تکرار سرویس و هماهنگی بین نمونه‌ها فراهم می‌کند و به برنامه‌های بالا و دستگاه‌های شبکه پایین، انتزاع یک کنترلر واحد، سازگار و متمرکز منطقاً را می‌دهد.

حالت نگهداری‌شده در هسته

• میزبان‌ها — موقعیت و هویت

• مسیرها — مسیرهای سرتاسری موجود

• توپولوژی — ساختار گراف شبکه

• دستگاه‌ها — موجودی سوییچ/مسیریاب

• پیوندها — وضعیت اتصال

• قوانین جریان — ورودی‌های ارسال نصب‌شده

• آمار — اندازه‌گیری‌های ترافیک

معماری توزیع‌شده

• روی یک خوشه سرور اجرا می‌شود

• هر سرور نرم‌افزار ONOS یکسانی اجرا می‌کند

• ظرفیت با سرورهای بیشتر مقیاس می‌شود

• تکرار سرویس برای تحمل خطا

• هماهنگی بین نمونه‌ها از طریق پروتکل‌های توزیع‌شده

لایه 3: انتزاعات و پروتکل‌های جنوبی

لایه جنوبی ONOS ناهمگنی دستگاه‌های شبکه زیرین را می‌پوشاند.

مزایای انتزاع جنوبی:
"مستقل از دستگاه و پروتکل" — هسته به انواع دستگاه خاص وابسته نیست
پلاگین‌های پروتکل: OpenFlow, NETCONF, OVSDB
رابط جنوبی ONOS منطقاً بالاتر از کنترلر متعارف (شکل 5.15) به دلیل این لایه انتزاع است

انتزاعات جنوبی فراهم می‌کنند:

  • انتزاع دستگاه: رابط یکنواخت برای همه انواع سوییچ
  • انتزاع پیوند: نمایش پیوند سازگار صرف‌نظر از پروتکل
  • انتزاع میزبان: ردیابی میزبان استاندارد
  • انتزاع قانون جریان: برنامه‌ریزی جریان مستقل از پروتکل
  • انتزاع بسته: رابط پردازش بسته یکنواخت
تفاوت معماری کلیدی: ONOS لایه انتزاع خود را بالای پلاگین‌های پروتکل قرار می‌دهد (بین پلاگین‌ها و هسته توزیع‌شده). SAL در ODL در همان سطح پلاگین‌های پروتکل است. این یعنی هسته ONOS نسبت به پروتکل خنثی‌تر از ODL است.

مقایسه معماری: SAL در مقابل انتزاعات

ODL: SAL-محور

SAL در مرکز معماری است.

فراهم می‌کند: پیام‌رسانی، ذخیره داده (پیکربندی + عملیاتی)، و مسیریابی سرویس.

پلاگین‌های پروتکل (OpenFlow, NETCONF, و غیره) در SAL ثبت می‌شوند.

برنامه‌ها سرویس‌ها را از طریق SAL از طریق REST یا مدل‌های YANG فراخوانی می‌کنند.

ONOS: انتزاع-محور

انتزاعات در مرکز هستند.

شمالی: انتزاعات Intent، دستگاه، میزبان، پیوند.

هسته توزیع‌شده در سطح انتزاع کار می‌کند، نه سطح پروتکل.

جنوبی: فراهم‌کننده‌ها انتزاعات را برای پروتکل‌های خاص پیاده‌سازی می‌کنند.

مثال‌های حل شده

مثال 1: اتصال مبتنی بر Intent با ONOS

سناریو: یک اپراتور شبکه می‌خواهد اتصال بین دو سرور برقرار کند: سرور A (MAC=00:00:00:00:00:01، متصل به سوییچ s1 پورت 1) و سرور B (MAC=00:00:00:00:00:02، متصل به سوییچ s4 پورت 2).

استفاده از چارچوب Intent ONOS:

// ONOS Intent API — Java Intent intent = HostToHostIntent.builder() .appId(appId) .one(connectPoint("s1", 1)) // موقعیت سرور A .two(connectPoint("s4", 2)) // موقعیت سرور B .build(); intentService.submit(intent);

آنچه درون کنترلر رخ می‌دهد:

  1. چارچوب intent ONOS intent سطح بالا را دریافت می‌کند: "A را به B متصل کن".
  2. کامپایلر intent آن را به موارد زیر ترجمه می‌کند: پیدا کردن مسیر از s1 به s4، تعیین اینکه کدام سوییچ‌ها به ورودی جریان نیاز دارند.
  3. کامپایلر با هسته توزیع‌شده تعامل می‌کند تا توپولوژی، مسیرهای موجود و ظرفیت پیوندها را دریافت کند.
  4. چندین کاندیدای مسیر ارزیابی می‌شوند؛ بهترین مسیر انتخاب می‌شود (مثلاً s1→s2→s3→s4).
  5. چارچوب intent قوانین جریان را روی s1, s2, s3, و s4 با استفاده از فراهم‌کننده‌های جنوبی (OpenFlow) نصب می‌کند.
  6. ورودی‌های جریان: s1: dst=00:00:00:00:00:02 ← خروجی به s2; s2: dst=00:00:00:00:00:02 ← خروجی به s3; و غیره.

مزیت SDN: اپراتور مشخص می‌کند چه چیزی می‌خواهد، نه چگونه. ONOS همه جزئیات سطح پایین محاسبه مسیر و نصب جریان را مدیریت می‌کند.

مثال 2: زنجیره سرویس MD-SAL OpenDaylight

سناریو: یک شرکت می‌خواهد همه ترافیک HTTP قبل از رسیدن به سرور وب از فایروال عبور کند. ترافیک باید هدایت شود: کلاینت ← سوییچ A ← فایروال ← سوییچ B ← سرور وب.

استفاده از OpenDaylight MD-SAL:

  1. زنجیره سرویس را با استفاده از یک مدل داده YANG تعریف کنید:
// service-chain.yang module service-chain { yang-version 1.1; namespace "urn:example:service-chain"; prefix sc; list service-chain { key "name"; leaf name { type string; } list classifier { leaf dst-port { type uint16; } leaf protocol { type uint8; } } list service-function { ordered-by user; leaf type { type enumeration { enum firewall; enum DPI; enum lb; } } leaf device-ip { type inet:ipv4-address; } } } }
  1. MD-SAL این مدل را ذخیره می‌کند. یک برنامه هدایت ترافیک مدل را می‌خواند و آن را به ورودی‌های جریان ترجمه می‌کند.
  2. از طریق NETCONF، برنامه دستگاه فایروال را با قوانین مناسب پیکربندی می‌کند.
  3. از طریق OpenFlow، ورودی‌های جریان روی سوییچ A (تغییر مسیر HTTP به فایروال) و سوییچ B (پذیرش از فایروال) نصب می‌شوند.
ورودی جریان سوییچ A: match: dst-port=80, proto=TCP actions: خروجی به پورت فایروال ورودی جریان سوییچ B: match: in_port=فایروال, dst-port=80, proto=TCP actions: خروجی به پورت سرور وب

مزیت MD-SAL: مدل YANG یک منبع حقیقت واحد برای کل پیکربندی زنجیره سرویس فراهم می‌کند. تغییرات با بروزرسانی نمونه مدل از طریق NETCONF اعمال می‌شوند.

مثال 3: بازیابی خرابی هسته توزیع‌شده ONOS

سناریو: یک خوشه ONOS دارای 5 سرور است. یک سرور (نمونه 3) خراب می‌شود. شبکه دارای 50 سوییچ متصل به خوشه است.

آنچه رخ می‌دهد:

فازعمل
تشخیصپروتکل عضویت خوشه تشخیص می‌دهد نمونه 3 غیرقابل دسترس است (انقضای heartbeat)
انتخاب مجددپروتکل اجماع RAFT یک رهبر جدید از بین 4 نمونه باقی‌مانده انتخاب می‌کند
تخصیص مجدد سوییچسوییچ‌هایی که به نمونه 3 متصل بودند، از دست رفتن اتصال را از طریق انقضای echo OpenFlow تشخیص می‌دهند
اتصال مجددسوییچ‌ها با استفاده از لیست IP کنترلر از پیش پیکربندی‌شده به نمونه‌های پشتیبان متصل می‌شوند
بازیابی حالتهسته توزیع‌شده (گراف DB Titan) قبلاً حالت را بین نمونه‌ها تکرار کرده است؛ رهبر توپولوژی کامل دارد
نصب مجدد جریاننمونه‌های کنترلر جدید جداول جریان را در سوییچ‌های اختصاص‌یافته تأیید می‌کنند؛ ورودی‌های گمشده را دوباره نصب می‌کنند

نتیجه: عملیات شبکه بدون از دست دادن بسته ادامه می‌یابد. ورودی‌های جریان موجود در سوییچ‌ها باقی می‌مانند و به ارسال ادامه می‌دهند. فقط درخواست‌های جریان جدید به طور مختصر در طول اتصال مجدد تأخیر دارند.

اصل طراحی کلیدی: سوییچ‌ها "کش صفحه داده" هستند — آنها برای هر بسته به کنترلر وابسته نیستند. کنترلر فقط برای رویدادهای عدم تطبیق جدول مشورت می‌شود.

مثال 4: برنامه مهندسی ترافیک الهام‌گرفته از B4

سناریو: یک کنترلر SDN سراسری پیوندهای WAN بین مراکز داده را مدیریت می‌کند. سه کلاس برنامه: ترافیک تعاملی کاربر (اولویت 1)، تحلیل نزدیک به زمان واقعی (اولویت 2)، و تکرار حجیم (اولویت 3). استفاده از پیوند باید به حداکثر برسد.

راه‌حل (الهام‌گرفته از B4):

// شبه-کد برای برنامه TE function computeAllocation(demands, links, priorities): // 1. پهنای باند را برای جریان‌های با اولویت بالا رزرو کن for each interactive_flow: path = shortest_path(flow.src, flow.dst) allocate(path, flow.demand) // 2. اولویت متوسط را روی ظرفیت باقی‌مانده تخصیص بده for each analytics_flow: path = path_with_available_bw(flow.src, flow.dst, flow.demand) if path exists: allocate(path, flow.demand) else: queue for later // 3. ظرفیت باقی‌مانده را با ترافیک حجیم پر کن for each replication_flow: path = path_with_available_bw(flow.src, flow.dst) allocate(path, min(flow.demand, available_bw)) // قابل توقف — می‌تواند برای اولویت بالاتر رها شود

نتایج به‌دست‌آمده توسط B4: 70% استفاده متوسط از پیوند (در مقابل 30-40% معمولی)، 2-3 برابر بهبود. کنترلر SDN دید سراسری دارد و می‌تواند همزمان در همه جریان‌ها بهینه‌سازی کند.

مثال 5: یکپارچه‌سازی دستگاه چند فروشنده از طریق انتزاعات جنوبی

سناریو: یک شبکه دارای سوییچ‌هایی از سه فروشنده است: Cisco (سیستم عامل اختصاصی)، Juniper (JunOS)، و یک سوییچ white-box که Open vSwitch اجرا می‌کند.

بدون SDN: اپراتورهای شبکه باید سه نحو CLI مختلف و پروتکل‌های مدیریت را یاد بگیرند. خودکارسازی در همه دستگاه‌ها نیاز به اسکریپت‌های سفارشی برای هر فروشنده دارد.

با انتزاعات جنوبی ONOS:

// انتزاع دستگاه — API یکنواخت صرف‌نظر از فروشنده DeviceId ciscoId = DeviceId.deviceId("netconf:10.0.0.1:830"); DeviceId juniperId = DeviceId.deviceId("netconf:10.0.0.2:830"); DeviceId ovsId = DeviceId.deviceId("openflow:10.0.0.3:6653"); // نصب همان قانون جریان روی هر سه دستگاه FlowRule rule = DefaultFlowRule.builder() .forDevice(ciscoId) // فراهم‌کننده ONOS ترجمه Cisco←NETCONF را انجام می‌دهد .withSelector(matchDst(IP4Prefix.valueOf("10.0.0.0/8"))) .withTreatment(DefaultTrafficTreatment.builder() .setOutput(PortNumber.port(3)) .build()) .build(); flowRuleService.applyFlowRules(rule); // همان فراخوانی برای Juniper flowRuleService.applyFlowRules(rule.forDevice(juniperId)); // همان فراخوانی برای OVS flowRuleService.applyFlowRules(rule.forDevice(ovsId));

مزیت انتزاع: هسته توزیع‌شده ONOS نیازی ندارد بداند که آیا یک دستگاه OpenFlow، NETCONF، یا یک پروتکل اختصاصی صحبت می‌کند. فراهم‌کننده‌های جنوبی ترجمه را انجام می‌دهند.
