مرور NETCONF

NETCONF (پروتکل پیکربندی شبکه) یک پروتکل استاندارد IETF برای نصب، دستکاری و حذف پیکربندی دستگاه‌های شبکه است. این پروتکل از پارادایم RPC با پیام‌های رمزگذاری شده با XML روی یک جلسه امن و اتصال گرا مانند TLS (امنیت لایه حمل) روی TCP استفاده می‌کند.

پشته NETCONF:
حمل: TCP/TLS/SSH • رمزگذاری: XML • پارادایم: RPC
IETF RFC 6241 — جایگزین SNMP برای مدیریت پیکربندی

لایه حمل

SSH (RFC 6242) — رایج‌ترین

TLS (RFC 7589) — امنیت لایه حمل روی TCP

TCP (خام, RFC 5539)

اتصال گرا و قابل اعتماد

ویژگی‌های کلیدی

تراکنشی — commit/rollback

پیکربندی کاندیدا — ویرایش بدون تأثیر

فیلتر کردن — زیردرخت، XPath

اعلان‌ها — جریان رویداد

تراکنش‌های اتمی چند-دستگاهی [RFC 3535] — عملیاتی که به صورت اتمی در مجموعه‌ای از دستگاه‌ها کامل می‌شوند یا کاملاً معکوس می‌شوند

در مقابل SNMP

TCP در مقابل UDP

XML در مقابل BER/DER

جریان جلسه NETCONF (شکل 5.22)

کلاینت (NMS) سرور (دستگاه) | | |--- <hello> (قابلیت‌ها) --------------> | |<--- <hello> (قابلیت‌ها) ---------------| برقراری جلسه | | |--- <rpc> (<get-config/>) ------------> | |<--- <rpc-reply> (داده) ---------------| تبادل RPC | | |--- <rpc> (<edit-config>) -----------> | |<--- <rpc-reply> (<ok/>) -------------| تغییر پیکربندی | | |<--- <notification> (رویداد) ----------| اعلان ناهمزمان | | |--- <rpc> (<close-session/>) --------> | |<--- <rpc-reply> (<ok/>) -------------| بستن جلسه
فازجهتپیامهدف
1. Helloهر دو<hello>تبادل قابلیت‌ها (ماژول‌های YANG، نسخه‌های NETCONF)
2. RPCکلاینت ← سرور<rpc>فراخوانی عملیات با پارامترها
3. پاسخسرور ← کلاینت<rpc-reply>بازگرداندن داده یا <ok/> در صورت موفقیت، <rpc-error> در صورت شکست
4. اعلانسرور ← کلاینت<notification>رویداد ناهمزمان (نیاز به create-subscription دارد)
5. بستنکلاینت ← سرور<close-session>خاتمه جلسه NETCONF
نکته کلیدی: NETCONF از یک تبادل قابلیت در فاز <hello> استفاده می‌کند. کلاینت و سرور هر کدام ماژول‌های YANG و قابلیت‌های پروتکلی را که پشتیبانی می‌کنند اعلام می‌کنند. عملیاتی که توسط هر دو طرف پشتیبانی نمی‌شوند قابل استفاده نیستند.

عملیات NETCONF (جدول 5.3)

NETCONF مجموعه‌ای از عملیات پایه را تعریف می‌کند که پایه و اساس مدیریت دستگاه را تشکیل می‌دهند. این عملیات را می‌توان به تراکنش‌های پیچیده چند-دستگاهی تبدیل کرد که یا به صورت اتمی و با موفقیت کامل می‌شوند یا کاملاً معکوس می‌شوند — دستگاه‌ها را در حالت قبل از تراکنش باقی می‌گذارند. این رویکرد "شبکه به عنوان یک کل" یک نیاز مهم اپراتور از [RFC 3535] بود.

عملیاتتوضیحورودیخروجی
get-configبازیابی همه یا بخشی از یک ذخیره داده پیکربندیsource, filterداده پیکربندی XML
getبازیابی هر دو داده پیکربندی و وضعیتfilterداده XML پیکربندی + وضعیت
edit-configتغییر یک ذخیره داده پیکربندیtarget, config, operation<ok/> یا <rpc-error>; در صورت خطا، پیکربندی می‌تواند به حالت قبلی بازگردد
lockقفل کردن یک ذخیره داده پیکربندی (جلوگیری از ویرایش‌های همزمان)target<ok/> یا خطای lock-denied
unlockآزاد کردن یک قفل قبلاً اخذ شدهtarget<ok/>
create-subscriptionاشتراک در اعلان‌های رویدادstream, filterجریان اعلان شروع می‌شود
notification(طرف سرور) ارسال یک اعلان رویدادداده رویدادنامعتبر (ناهمزمان)
close-sessionبستن صحیح جلسه NETCONFهیچ<ok/>
kill-sessionخاتمه اجباری جلسه دیگرsession-id<ok/>

مثال‌های پیام XML از کتاب درسی

دستور <get/> — بازیابی وضعیت کامل دستگاه
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <get/> </rpc>

عملیات <get/> هر دو داده پیکربندی و وضعیت عملیاتی را از دستگاه برمی‌گرداند.

<edit-config> — تنظیم MTU روی یک رابط
<rpc message-id="102" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <edit-config>     <target><running/></target>     <config>       <top xmlns="http://example.com/ns/example">         <interfaces>           <interface>             <name>GigabitEthernet0/1</name>             <mtu>1500</mtu>           </interface>         </interfaces>       </top>     </config>   </edit-config> </rpc>

عملیات پیش‌فرض merge است (اگر وجود نداشته باشد ایجاد می‌کند، اگر وجود داشته باشد بروزرسانی می‌کند). سایر عملیات: replace, create, delete, remove.

<rpc-reply> — پاسخ موفقیت
<rpc-reply message-id="102" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <ok/> </rpc-reply>

یک عنصر <ok/> نشان می‌دهد عملیات با موفقیت کامل شده است. پاسخ‌های خطا شامل <rpc-error> با error-type، error-tag و error-message هستند.

عملیات ویرایش:
merge • replace • create • delete • remove
از طریق ویژگی 'operation' روی عناصر پیکربندی مشخص می‌شود

معنای عملیات

merge — ایجاد یا بروزرسانی

replace — جایگزینی موجود

create — اگر وجود داشته باشد شکست می‌خورد

delete — اگر موجود نباشد شکست می‌خورد

remove — اگر وجود داشته باشد حذف می‌کند

ذخیره‌های پیکربندی

<candidate> — ویرایش بدون تأثیر روی پیکربندی در حال اجرا

<running> — پیکربندی فعال فعلی

<commit> — کپی candidate → running

<discard-changes> — بازگردانی candidate

زبان مدل‌سازی داده YANG

YANG (نسل بعدی دیگر) زبان مدل‌سازی داده برای NETCONF است. ساختار، محدودیت‌ها و معنای داده پیکربندی و وضعیت را تعریف می‌کند. مشابه SMI برای SNMP، اما برای دنیای XML-based NETCONF ساخته شده است.

هدف YANG:
تعریف مدل‌های داده برای پیکربندی NETCONF و وضعیت عملیاتی
ماژول‌های YANG ساختار، انواع و محدودیت‌های داده مبادله‌شده از طریق NETCONF را تعریف می‌کنند

ساختار ماژول YANG

module example-interface {   yang-version 1.1;   namespace "http://example.com/ns/example-interface";   prefix exif;   import ietf-yang-types { prefix yang; }   import ietf-inet-types { prefix inet; }   container interfaces {     list interface {       key "name";       leaf name {         type string;       }       leaf description {         type string;       }       leaf mtu {         type uint16 {           range "68..9216";         }         default 1500;       }       leaf enabled {         type boolean;         default true;       }     }   } }

محدودیت‌های YANG

محدوده

type uint16 { range "68..9216"; }

مقادیر معتبر: 68 تا 9216

طول

type string { length "1..255"; }

طول رشته: 1 تا 255 کاراکتر

الگو

type string { pattern "[0-9a-fA-F]*"; }

محدودیت regex روی رشته

اجباری

leaf name { mandatory true; }

باید در داده وجود داشته باشد

نکته کلیدی: YANG به مدل‌سازان داده اجازه می‌دهد محدودیت‌هایی را که پیکربندی‌ها باید برآورده کنند (محدوده، طول، الگو، اجباری) بیان کنند. این یک کمک قدرتمند در تضمین این است که پیکربندی‌های NETCONF محدودیت‌های صحت و سازگاری مشخص شده را برآورده می‌کنند. YANG همچنین برای مشخص کردن اعلان‌های NETCONF استفاده می‌شود.

تبدیل YANG به XML

نگاشت:

مثال‌های حل شده

مثال 1: بازیابی پیکربندی با <get-config>

سناریو: یک NMS می‌خواهد پیکربندی رابط فعلی را از یک دستگاه برای ساختن موجودی بازیابی کند.

<rpc message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <get-config>     <source><running/></source>     <filter type="subtree">       <interfaces xmlns="http://example.com/ns/example-interface">         <interface>           <name/>           <mtu/>         </interface>       </interfaces>     </filter>   </get-config> </rpc>

پاسخ:

<rpc-reply message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <data>     <interfaces xmlns="http://example.com/ns/example-interface">       <interface>         <name>GigabitEthernet0/0</name>         <mtu>1500</mtu>       </interface>       <interface>         <name>GigabitEthernet0/1</name>         <mtu>9000</mtu>       </interface>     </interfaces>   </data> </rpc-reply>

تحلیل:

  • فیلتر زیردرختی پاسخ را فقط به <name> و <mtu> هر رابط محدود می‌کند
  • رابط GigabitEthernet0/1 دارای MTU 9000 (jumbo frames فعال) — NMS این را برای موجودی علامت‌گذاری می‌کند
  • پاسخ در <data> پیچیده شده است تا پیکربندی را از وضعیت عملیاتی متمایز کند
مثال 2: پیکربندی رابط با <edit-config>

سناریو: یک مدیر یک رابط VLAN جدید روی یک سوییچ پیکربندی می‌کند. پیکربندی باید به صورت اتمی اعمال شود.

<rpc message-id="202" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <edit-config>     <target><candidate/></target>     <config>       <interfaces xmlns="http://example.com/ns/example-interface">         <interface operation="create">           <name>Vlan100</name>           <description>VLAN مدیریت</description>           <mtu>1500</mtu>           <ipv4 xmlns="http://example.com/ns/example-ip">             <address>               <ip>192.168.100.1</ip>               <prefix-length>24</prefix-length>             </address>           </ipv4>         </interface>       </interfaces>     </config>   </edit-config> </rpc> # commit پیکربندی کاندیدا <rpc message-id="203" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <commit/> </rpc> <rpc-reply message-id="203" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <ok/> </rpc-reply>

تحلیل:

  • ویرایش روی پیکربندی <candidate> انجام می‌شود — هیچ تأثیری روی دستگاه در حال اجرا ندارد
  • operation="create" تضمین می‌کند رابط از قبل وجود ندارد (در صورت تکراری شکست می‌خورد)
  • <commit/> همه تغییرات را به صورت اتمی اعمال می‌کند — اگر هر اعتبارسنجی شکست بخورد، کل تراکنش بازگردانی می‌شود
  • اگر پیکربندی خطا داشته باشد، دستگاه <rpc-error> برمی‌گرداند و پیکربندی کاندیدا بدون تغییر می‌ماند
مثال 3: کشف قابلیت دستگاه از طریق <hello>

سناریو: یک NMS به یک دستگاه جدید متصل می‌شود و قابلیت‌های آن را از طریق تبادل <hello> NETCONF کشف می‌کند.

# NMS قابلیت‌های خود را می‌فرستد <hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <capabilities>     <capability>urn:ietf:params:netconf:base:1.1</capability>     <capability>urn:ietf:params:netconf:capability:writable-running:1.0</capability>     <capability>urn:ietf:params:netconf:capability:candidate:1.0</capability>     <capability>urn:ietf:params:netconf:capability:validate:1.0</capability>     <capability>http://example.com/ns/example-interface?module=example-interface&amp;revision=2024-01-01</capability>   </capabilities> </hello> # دستگاه با قابلیت‌های خود پاسخ می‌دهد <hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <capabilities>     <capability>urn:ietf:params:netconf:base:1.1</capability>     <capability>urn:ietf:params:netconf:capability:candidate:1.0</capability>     <capability>urn:ietf:params:netconf:capability:rollback-on-error:1.0</capability>     <capability>urn:ietf:params:netconf:capability:notification:1.0</capability>     <capability>http://example.com/ns/example-interface?module=example-interface&amp;revision=2024-01-01</capability>     <capability>http://example.com/ns/example-routing?module=example-routing&amp;revision=2024-03-01</capability>   </capabilities> </hello>

تحلیل:

  • هر دو طرف از NETCONF 1.1 (base:1.1) پشتیبانی می‌کنند — RPCهای درهم و قاب‌بندی تکه‌ای را فعال می‌کند
  • دستگاه از candidate پشتیبانی می‌کند اما از writable-running پشتیبانی نمی‌کند — NMS باید از الگوی candidate/commit استفاده کند
  • دستگاه از rollback-on-error پشتیبانی می‌کند — اگر تغییر پیکربندی شکست بخورد، دستگاه به طور خودکار بازگردانی می‌کند
  • دستگاه از notification پشتیبانی می‌کند — NMS می‌تواند در جریان‌های رویداد مشترک شود
  • ماژول‌های YANG اعلام شده: example-interface + example-routing — NMS دقیقاً می‌داند کدام مدل‌های داده توسط دستگاه پشتیبانی می‌شوند
مثال 4: تراکنش Commit با اعتبارسنجی

سناریو: یک مدیر چندین تغییر را روی پیکربندی کاندیدا اعمال می‌کند، آنها را اعتبارسنجی می‌کند، سپس commit می‌کند. یک تغییر در اعتبارسنجی شکست می‌خورد و باعث ابطال تراکنش می‌شود.

# گام 1: قفل کردن ذخیره داده کاندیدا <rpc message-id="301"><lock><target><candidate/></target></lock></rpc> <rpc-reply message-id="301"><ok/></rpc-reply> # گام 2: اعمال تغییرات پیکربندی روی کاندیدا <rpc message-id="302"><edit-config><target><candidate/></target>...</edit-config></rpc> <rpc-reply message-id="302"><ok/></rpc-reply> # گام 3: اعتبارسنجی پیکربندی کاندیدا <rpc message-id="303"><validate><source><candidate/></source></validate></rpc> <rpc-reply message-id="303">   <rpc-error>     <error-type>application</error-type>     <error-tag>bad-element</error-tag>     <error-severity>error</error-severity>     <error-message>مقدار MTU 10000 از حداکثر 9216 بیشتر است</error-message>     <error-info>       <bad-element>mtu</bad-element>     </error-info>   </rpc-error> </rpc-reply> # گام 4: کنار گذاشتن تغییرات ناموفق و باز کردن قفل <rpc message-id="304"><discard-changes/></rpc> <rpc-reply message-id="304"><ok/></rpc-reply> <rpc message-id="305"><unlock><target><candidate/></target></unlock></rpc> <rpc-reply message-id="305"><ok/></rpc-reply>

نکته کلیدی: مدل تراکنشی NETCONF (candidate ← validate ← commit) از رسیدن پیکربندی‌های نادرست به دستگاه در حال اجرا جلوگیری می‌کند. این یک مزیت اساسی نسبت به SNMP است، جایی که یک عملیات Set می‌تواند فوراً به اتصال آسیب برساند.

مثال 5: اعلان رویداد — تغییر حالت پیوند

سناریو: NMS در اعلان‌های تغییر وضعیت رابط مشترک می‌شود. وقتی یک پیوند قطع می‌شود، دستگاه یک اعلان می‌فرستد.

# گام 1: اشتراک در اعلان‌ها <rpc message-id="401" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">   <create-subscription xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">     <stream>interface-state</stream>   </create-subscription> </rpc> # گام 2: دستگاه به صورت ناهمزمان اعلان می‌فرستد <notification xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">   <eventTime>2024-10-15T14:30:00Z</eventTime>   <interface-state-change xmlns="http://example.com/ns/example-interface">     <name>GigabitEthernet0/1</name>     <admin-status>up</admin-status>     <oper-status>down</oper-status>     <reason>link-failure</reason>   </interface-state-change> </notification>

اعلان‌های NETCONF ناهمزمان هستند — NMS آنها را در زمان واقعی پس از اشتراک دریافت می‌کند. برخلاف traps SNMP، اعلان‌ها روی همان جلسه TCP تحویل می‌شوند و تحویل قابل اعتماد و مرتب را فراهم می‌کنند.
