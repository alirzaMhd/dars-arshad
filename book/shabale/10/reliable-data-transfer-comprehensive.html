اصول انتقال داده قابل اعتماد

شبکه‌های کامپیوتری — راهنمای کامل برای امتحان ۲۰/۲۰

rdt1.0 — کانال کاملاً قابل اعتماد

ساده‌ترین حالت: کانال زیرین کاملاً قابل اعتماد است. بدون خطای بیتی، بدون فقدان، بدون تغییر ترتیب. هم فرستنده و هم گیرنده فقط یک حالت دارند.

rdt1.0 Sender (FSM):
State: Wait for call from above
Event: rdt_send(data)
Action: packet = make_pkt(data); udt_send(packet)

rdt1.0 Receiver (FSM):
State: Wait for call from below
Event: rdt_rcv(packet)
Action: extract(packet, data); deliver_data(data)
rdt1.0 کانال کامل را فرض می‌کند — بدون بررسی خطا، بدون ACK، بدون NAK، بدون شماره ترتیب. این کاملاً نظری است; کانال‌های واقعی خطاهای بیتی و فقدان دارند.

rdt2.0 — کانال با خطاهای بیتی

سه قابلیت اضافه می‌کند (ARQ — درخواست تکرار خودکار):

تشخیص خطا

بیت‌های checksum به بسته اضافه می‌شوند. گیرنده بیت‌های خراب را تشخیص می‌دهد.

بازخورد گیرنده

بسته‌های ACK (تأیید مثبت) و NAK (تأیید منفی) از گیرنده به فرستنده ارسال می‌شوند.

ارسال مجدد

فرستنده بسته‌های دریافت شده با خطا را مجدداً ارسال می‌کند. این یک پروتکل stop-and-wait است — فرستنده قبل از ارسال بسته بعدی منتظر ACK/NAK می‌ماند.

نقص مهلک: بسته‌های ACK/NAK خودشان می‌توانند خراب شوند! فرستنده نمی‌تواند بداند آیا گیرنده آخرین بسته را به درستی دریافت کرده است یا خیر.

سه رویکرد برای ACK/NAK خراب

۱. "چه گفتی؟"

اضافه کردن یک بسته جدید از فرستنده به گیرنده که از گیرنده می‌خواهد پاسخ خود را تکرار کند. اما آن بسته جدید نیز می‌تواند خراب شود — منجر به یک حلقه بی‌نهایت از سؤالات فراعلاقه.

۲. بیت‌های checksum کافی

اضافه کردن بیت‌های checksum کافی به فرستنده اجازه می‌دهد نه تنها تشخیص دهد بلکه بازیابی از خطاهای بیتی را بدون ارسال مجدد انجام دهد. برای خرابی کار می‌کند اما برای فقدان بسته نه.

۳. ارسال مجدد + شماره ترتیب

به سادگی بسته داده فعلی را وقتی یک ACK/NAK خراب دریافت می‌شود دوباره ارسال کنید. این بسته‌های تکراری را معرفی می‌کند که شماره‌های ترتیب آنها را مدیریت می‌کنند. این رویکرد تقریباً در همه پروتکل‌های موجود از جمله TCP اتخاذ شده است.

rdt2.1 — شماره ترتیب به کمک می‌آید

یک شماره ترتیب ۱-بیتی (۰ یا ۱) به بسته‌های داده اضافه می‌کند. اکنون گیرنده می‌تواند داده جدید را از ارسال‌های مجدد تشخیص دهد. فرستنده ۴ حالت دارد (منتظر فراخوانی ۰/۱، منتظر ACK/NAK ۰/۱).

rdt2.1 Sender (key additions):
- Packet numbered: make_pkt(seq#, data, checksum)
- On corrupted ACK/NAK: retransmit current packet (doesn't advance seq#)
- On valid ACK: advance to next seq# (flip 0↔1)

rdt2.1 Receiver (key additions):
- Tracks expected sequence number (0 or 1)
- If out-of-order seq# received: send ACK for expected packet (duplicate)
- If corrupted: send NAK

rdt2.2 — پروتکل بدون NAK

بسته‌های NAK را کاملاً حذف می‌کند. در عوض، گیرنده یک ACK برای آخرین بسته به درستی دریافت شده ارسال می‌کند. یک فرستنده که ACKهای تکراری دریافت می‌کند می‌فهمد که بسته بعدی به درستی دریافت نشده است.

نوآوری کلیدی rdt2.2:
ACKهای تکراری جایگزین NAK می‌شوند
گیرنده ACK با شماره ترتیب آخرین بسته به درستی دریافت شده درون‌ترتیبی را ارسال می‌کند.
دو ACK برای یک seq# → فرستنده می‌داند که باید بسته بعدی را مجدداً ارسال کند.

rdt3.0 — کانال با فقدان و خطاهای بیتی

اکنون کانال می‌تواند بسته‌ها را نیز گم کند (نه فقط آنها را خراب کند). این نیاز به یک زمان‌سنج شمارش معکوس برای تشخیص و بازیابی از بسته‌های گمشده دارد.

مکانیسم‌های کلیدی

  • زمان‌سنج: وقتی بسته‌ای ارسال می‌شود شروع می‌شود. اگر قبل از دریافت ACK زمانش تمام شود ← ارسال مجدد
  • مدت زمان: حداقل RTT + زمان پردازش تنظیم می‌شود. در عمل، از یک تخمین محافظه‌کارانه استفاده می‌شود
  • شماره ترتیب: ۱-بیت متناوب (۰, ۱, ۰, ۱...) — به عنوان پروتکل بیت متناوب شناخته می‌شود
rdt3.0 Sender FSM (simplified):
State: Wait for call 0 from above
├─ rdt_send(data) → make_pkt(0,data,chk), start_timer
└─ goto: Wait for ACK 0

State: Wait for ACK 0
├─ rcv ACK(0) → stop_timer, goto: Wait for call 1
├─ timeout → resend pkt0, start_timer
└─ rcv corrupt/ACK(1) → do nothing (wait)

عملکرد Stop-and-Wait

استفاده از فرستنده:
Usender = (L/R) / (RTT + L/R)
L = اندازه بسته (بیت), R = نرخ انتقال (bps), RTT = زمان رفت و برگشت (ثانیه)
مثال: مشکل عملکرد Stop-and-Wait

داده شده: R = 1 Gbps, L = 1000 بایت (8000 بیت), RTT = 30 ms

dtrans = L/R = 8000 / 109 = ۸ میکروثانیه

Usender = 0.008 / (30 + 0.008) = 0.00027 = 0.027%

توان عملیاتی مؤثر = 0.00027 × 1 Gbps = 267 kbps — برای یک لینک ۱ Gbps وحشتناک است!

فرستنده فقط ۲.۷ صدم درصد از زمان مشغول بود. این انگیزه‌ای برای پایپلاینینگ است.

حاصلضرب پهنای باند-تأخیر (BDP)
BDP = پهنای باند × RTT
با R = 1 Gbps, RTT = 30 ms: BDP = 10⁹ × 0.03 = 30,000,000 بیت = 3.75 MB
این تعداد بایت‌هایی است که می‌توانند قبل از بازگشت اولین ACK "در پرواز" باشند.
برای استفاده کامل از لینک، پنجره باید حداقل BDP / MSS ≈ 3750 بسته ۱۰۰۰ بایتی باشد.

چهار سناریو (شکل ۳.۱۶)

(a) بدون فقدان — عملکرد عادی

(b) بسته داده گم شد → وقفه → ارسال مجدد

(c) ACK گم شد → وقفه → ارسال مجدد (تکراری در گیرنده)

(d) وقفه زودهنگام → ACK تکراری دریافت شد

ارسال مجدد = نوش‌درمان

فرستنده نمی‌داند آیا DATA گم شده، ACK گم شده یا فقط تأخیر داشته است. در همه موارد: ارسال مجدد. شماره‌های ترتیب موارد تکراری را مدیریت می‌کنند.

پایپلاینینگ و Go-Back-N (GBN)

پروتکل‌های stop-and-wait خیلی کند هستند. پایپلاینینگ به فرستنده اجازه می‌دهد بدون انتظار برای تأیید، چندین بسته را ارسال کند. این "خط لوله" را پر می‌کند و استفاده را به طور چشمگیری بهبود می‌بخشد.

استفاده پایپلاین شده:
Upipelined ≈ N × (L/R) / (RTT + L/R)
N = تعداد بسته‌های در پرواز. با N به اندازه کافی بزرگ، U → 1 (استفاده کامل).

Go-Back-N (GBN)

فرستنده مجاز است تا N بسته تأیید نشده در خط لوله داشته باشد. فضای شماره ترتیب: [0, 2k - 1].

متغیرهای فرستنده

base: شماره ترتیب قدیمی‌ترین بسته تأیید نشده

nextseqnum: کوچکترین شماره ترتیب استفاده نشده

پنجره: [base, base+N-1] برای بسته‌های در حال انتقال

رویدادهای فرستنده

1. از بالا: اگر پنجره پر نیست، ارسال کن; در غیر این صورت رد کن

2. دریافت ACK: ACK تجمعی; پنجره را بلغزان

3. وقفه: همه بسته‌ها از base تا nextseqnum-1 را مجدداً ارسال کن

GBN Sender Pseudocode:
rdt_send(data):
  if nextseqnum < base + N:
    sndpkt[nextseqnum] = make_pkt(nextseqnum, data, checksum)
    udt_send(sndpkt[nextseqnum])
    if base == nextseqnum: start_timer
    nextseqnum++
  else: refuse_data(data)

rdt_rcv(rcvpkt) && notcorrupt:
  base = getacknum(rcvpkt) + 1
  if base == nextseqnum: stop_timer else: start_timer

timeout:
  start_timer
  for i in [base, nextseqnum-1]: udt_send(sndpkt[i])

گیرنده GBN

گیرنده فقط expectedseqnum را نگه می‌دارد. این:

  • ✓ فقط بسته‌های درون‌ترتیبی را می‌پذیرد (شماره ترتیب == expectedseqnum)
  • ✗ همه بسته‌های خارج از ترتیب را دور می‌ریزد (به درستی دریافت شده اما خارج از ترتیب دور ریخته می‌شوند!)
  • ✓ ACK تجمعی برای بالاترین بسته متوالی دریافت شده ارسال می‌کند
GBN بسته‌های خارج از ترتیب که به درستی دریافت شده‌اند را دور می‌ریزد! این به نظر اسراف می‌رسد، اما گیرنده بافری برای آنها ندارد — آنها به هر حال وقتی بسته گمشده زمانش تمام شود مجدداً ارسال می‌شوند. این ضعف اصلی عملکرد GBN است.

انتخابی (Selective Repeat - SR)

Selective Repeat با ارسال مجدد فقط بسته‌های گمشده/خراب به جای کل پنجره، GBN را بهبود می‌بخشد. این از مشکل "ارسال‌های مجدد غیرضروری" GBN وقتی بسته‌های زیادی در خط لوله هستند جلوگیری می‌کند.

فرستنده SR

• پنجره‌ای از N شماره ترتیب

• زمان‌سنج‌های جداگانه برای هر بسته (زمان‌سنج منطقی)

• فقط بسته زمان‌سنج شده را مجدداً ارسال کنید

• ACK دریافت شد → بسته را به عنوان دریافت شده علامت بزن

• پنجره زمانی جلو می‌رود که send_base تأیید شود

گیرنده SR

• هر بسته به درستی دریافت شده را تأیید می‌کند (ACKهای جداگانه)

• بسته‌های خارج از ترتیب را بافر می‌کند

• دسته‌ای از بسته‌های متوالی را به ترتیب وقتی شکاف پر شد تحویل می‌دهد

• ACK مجدد برای بسته‌های در محدوده [rcv_base-N, rcv_base-1]

SR Receiver Events:

1. Packet seq in [rcv_base, rcv_base+N-1] received correctly:
  → Send selective ACK; buffer if not already received
  → If seq == rcv_base: deliver consecutive run, advance window

2. Packet seq in [rcv_base-N, rcv_base-1] received correctly:
  → Send ACK (re-acknowledge — critical!)

3. Otherwise: ignore

محدودیت حیاتی: اندازه پنجره

محدودیت اندازه پنجره SR:
اندازه پنجره ≤ (حداکثر شماره ترتیب + 1) / 2
با شماره ترتیب k-بیتی: N ≤ 2k-1. در غیر این صورت فرستنده و گیرنده ممکن است در مورد اینکه بسته جدید است یا ارسال مجدد اختلاف داشته باشند.
مثال: چرا اندازه پنجره باید ≤ نصف فضای شماره ترتیب باشد

داده شده: شماره ترتیب ۰,۱,۲,۳ (فیلد ۲-بیتی، حداکثر=۴). اندازه پنجره N=3.

سناریوی A: بسته‌های ۰,۱,۲ ارسال شدند. ACKها گم شدند. فرستنده ۰,۱,۲ را مجدداً ارسال می‌کند. گیرنده فکر می‌کند ۰ یک ارسال مجدد از داده قدیمی است.

سناریوی B: همان بسته‌ها، ACKها دریافت شدند. فرستنده بسته‌های جدید ۳,۰,۱ را ارسال می‌کند. بسته ۰ می‌رسد — گیرنده seq=0 را می‌بیند.

مسئله: گیرنده نمی‌تواند سناریوی A (ارسال مجدد) را از سناریوی B (داده جدید با seq=0) تشخیص دهد!

راه حل: N ≤ 4/2 = 2. با اندازه پنجره ۲، ابهام از بین می‌رود.

SR پیچیده است زیرا پنجره‌های فرستنده و گیرنده همگام نیستند. فرستنده نمی‌داند گیرنده کدام بسته‌ها را بافر کرده است. به همین دلیل ارسال مجدد ACK برای بسته‌های در [rcv_base-N, rcv_base-1] ضروری است — از توقف پنجره فرستنده جلوگیری می‌کند.

مثال‌های عملی: مکانیسم‌های RDT

مثال ۱: لغزش پنجره GBN

داده شده: N=4, base=2, nextseqnum=5. بسته‌های ۲,۳,۴ در پرواز هستند.

ACK برای بسته ۲ می‌رسد.

اقدام: base = 2+1 = 3. پنجره اکنون [3, 6] را پوشش می‌دهد. فرستنده می‌تواند بسته ۵ را ارسال کند (اگر داده موجود باشد).

قبل: پنجره [2,3,4,5]. بعد: پنجره [3,4,5,6]. به اندازه ۱ به جلو لغزید.

مثال ۲: وقفه GBN — "Go-Back-N" در عمل

داده شده: N=5, فرستنده بسته‌های ۰ تا ۴ را ارسال کرده است. بسته ۲ گم شده است.

گیرنده دریافت می‌کند: pkt0 ✓ (ACK0 ارسال شد), pkt1 ✓ (ACK1 ارسال شد).

گیرنده دریافت می‌کند: pkt3 ✗ (خارج از ترتیب — دور ریخته شد), pkt4 ✗ (دور ریخته شد).

فرستنده ACK0, ACK1 را دریافت می‌کند. زمان‌سنج برای قدیمی‌ترین تأیید نشده (pkt2) در نهایت منقضی می‌شود.

فرستنده مجدداً ارسال می‌کند: بسته‌های ۲, ۳, ۴ (همه از base تا nextseqnum-1).

بسته‌های ۳ و ۴ به درستی دریافت شده بودند اما دور ریخته شدند و مجدداً ارسال شدند — این ضعف GBN است!

مثال ۳: بازیابی SR — ارسال مجدد فردی

داده شده: N=4, فضای شماره ترتیب [0..7]. فرستنده pkts 0,1,2,3 را ارسال می‌کند. pkt2 گم می‌شود.

گیرنده: pkt0 ✓ → ACK0; pkt1 ✓ → ACK1; pkt3 ✓ → ACK3 (بافر شده).

فرستنده ACK0, ACK1, ACK3 را دریافت می‌کند. فقط زمان‌سنج pkt2 فعال می‌ماند.

زمان pkt2 تمام می‌شود. فرستنده فقط pkt2 را مجدداً ارسال می‌کند.

گیرنده pkt2 ✓ را دریافت می‌کند → pkt2 و pkt3 بافر شده را به لایه بالایی تحویل می‌دهد. هر دو پنجره جلو می‌روند.

SR در مقایسه با GBN N-1 = 3 ارسال مجدد غیرضروری را ذخیره می‌کند!

مثال ۴: rdt3.0 — وقفه زودهنگام

سناریو: فرستنده pkt0 را ارسال می‌کند. بسته و ACK هر دو سالم هستند (بدون فقدان)، اما ACK تأخیر دارد (ازدحام).

زمان‌سنج قبل از رسیدن ACK منقضی می‌شود → فرستنده pkt0 را مجدداً ارسال می‌کند (تکراری).

گیرنده دوباره seq=0 را می‌بیند → تکراری را از طریق seq# تشخیص می‌دهد → دوباره ACK0 ارسال می‌کند (ACK تکراری).

ACK0 اصلی (تأخیری) می‌رسد → فرستنده نادیده می‌گیرد (آیا قبلاً جلو رفته؟ خیر, rdt3.0 stop-and-wait است).

رفتار صحیح: هر دو ACK یکسان هستند (seq#0). فرستنده اولین ACK را دریافت می‌کند، به seq#1 می‌رود. ACK0 دوم تکراری است و نادیده گرفته می‌شود (فرستنده rdt3.0 ACK با seq# اشتباه را دور می‌ریزد).

مثال ۵: محاسبه استفاده از فرستنده

داده شده: R = 10 Mbps, L = 2000 بایت (16000 بیت), RTT = 100 ms.

dtrans = L/R = 16000 / 107 = 0.0016 s = 1.6 ms

Stop-and-wait: U = 1.6 / (100 + 1.6) = 0.0157 → 1.57%

پایپلاین شده با N=10: U ≈ 10 × 0.0157 = 0.157 → 15.7%

N مورد نیاز برای استفاده ۱۰۰٪: N ≥ (RTT + L/R) / (L/R) = 101.6 / 1.6 ≈ ۶۴ بسته

جدول خلاصه: مکانیسم‌های RDT

مکانیسم هدف مورد استفاده در
Checksum تشخیص خطاهای بیتی در بسته ارسالی rdt2.0, rdt2.1, rdt2.2, rdt3.0, GBN, SR, TCP
زمان‌سنج وقفه/ارسال مجدد وقتی بسته یا ACK گم می‌شود rdt3.0, GBN (تک زمان‌سنج), SR (زمان‌سنج هر بسته), TCP
شماره ترتیب تشخیص بسته‌های گمشده (شکاف‌ها)، تشخیص موارد تکراری rdt2.1, rdt2.2, rdt3.0, GBN, SR, TCP
ACK به فرستنده بگو بسته(ها) به درستی دریافت شده‌اند rdt2.0+, GBN (تجمعی), SR (فردی), TCP (تجمعی)
NAK به فرستنده بگو بسته به اشتباه دریافت شده است rdt2.0, rdt2.1 (در rdt2.2+ با ACKهای تکراری حذف شد)
پنجره / پایپلاینینگ اجازه دادن به چندین بسته تأیید نشده; بهبود استفاده GBN (اندازه N), SR (اندازه N), TCP (تطبیقی)

ارسال مجدد در فقدان همه بسته‌های تأیید نشده را مجدداً ارسال می‌کند فقط بسته گمشده را مجدداً ارسال می‌کند
بافر گیرنده هیچ (بسته‌های خارج از ترتیب را دور می‌ریزد) بسته‌های خارج از ترتیب را بافر می‌کند
نوع ACK تجمعی فردی (انتخابی)
زمان‌سنج تک زمان‌سنج برای قدیمی‌ترین بسته زمان‌سنج منطقی هر بسته
محدودیت اندازه پنجره N ≤ 2k - 1 N ≤ 2k-1 (نصف فضای شماره ترتیب)
حافظه در فرستنده بافر N بسته بافر N بسته
حافظه در گیرنده هیچ (فقط expectedseqnum) بافر تا N بسته
مناسب برای نرخ خطای کم، پیاده‌سازی ساده نرخ خطای بالا، حاصلضرب پهنای باند-تأخیر بزرگ

خلاصه تکامل RDT

rdt1.0: کانال کامل (بدون خطا)

rdt2.0: +ACK/NAK (خطاهای بیتی)

rdt2.1: +شماره ترتیب (ACK/NAK خراب)

rdt2.2: -NAK (ACKهای تکراری)

rdt3.0: +زمان‌سنج (فقدان بسته)

GBN: +پایپلاینینگ, ACK تجمعی

SR: +ارسال مجدد انتخابی

اشتباهات رایج امتحان

• اشتباه گرفتن رفتار ارسال مجدد GBN و SR

• فراموش کردن محدودیت اندازه پنجره SR (≤ نصف)

• سوءتفاهم ACK تجمعی در مقابل فردی

• فکر کردن rdt2.2 از NAK استفاده می‌کند (نمی‌کند!)

• پیچیدن نکردن سرریز در محاسبه checksum
