DHCP (Dynamic Host Configuration Protocol)

شبکه‌های کامپیوتری — کروس و راس فصل ۴ | راهنمای جامع

DHCP چیست؟

DHCP (Dynamic Host Configuration Protocol) یک پروتکل اتصال و راه‌اندازی خودکار (zeroconf) است که به یک میزبان اجازه می‌دهد هنگام اتصال به شبکه، به طور خودکار یک آدرس IP دریافت کند. مدیر شبکه سرور DHCP را پیکربندی می‌کند تا هر میزبان بدون نیاز به پیکربندی دستی، یک آدرس IP از مجموعه آدرس‌های سرور دریافت کند.

اصل اصلی:
پیکربندی خودکار IP = شبکه‌سازی اتصال و راه‌اندازی خودکار
میزبان همه چیز مورد نیاز برای ارتباط را دریافت می‌کند — بدون نیاز به تنظیمات دستی

DHCP آدرس‌های IP را به طور دائم تخصیص نمی‌دهد. در عوض، آن‌ها را برای مدت زمان محدودی (ساعت‌ها یا روزها) اجاره می‌دهد. هنگامی که اجاره منقضی می‌شود، میزبان باید تمدید کند یا یک آدرس جدید دریافت کند. این امکان استفاده کارآمد از فضای محدود آدرس IPv4 را فراهم می‌کند.

معماری کلاینت-سرور DHCP

DHCP از مدل کلاینت-سرور پیروی می‌کند. کلاینت (میزبانی که به شبکه می‌پیوندد) ارتباط با سرور DHCP را آغاز می‌کند. سرور مجموعه‌ای از آدرس‌ها را مدیریت کرده و آن‌ها را درخواست تخصیص می‌دهد.

اشتباه رایج: DHCP یک پروتکل مسیریابی نیست

DHCP فقط تخصیص آدرس IP را انجام می‌دهد، نه مسیریابی را. میزبانی که از طریق DHCP یک IP جدید دریافت می‌کند، همچنان برای ارتباط خارج از زیرشبکه به دروازه پیش‌فرض (که توسط DHCP نیز ارائه می‌شود) وابسته است.

مثال‌های عملی

مثال ۱: اتصال جدید به شبکه

یک لپ‌تاپ به شبکه Wi-Fi دانشگاه متصل می‌شود. سرور DHCP دارای مجموعه‌ای از ۲۵۴ آدرس (192.168.10.1/24) است. سرور آدرس 192.168.10.42 را با اجاره ۲۴ ساعته تخصیص می‌دهد.

نتیجه: لپ‌تاپ می‌تواند از طریق دروازه 192.168.10.1 به اینترنت دسترسی داشته باشد، نام‌ها را از طریق DNS 8.8.8.8 حل کند، همه اینها بدون نیاز به پیکربندی دستی.

مثال ۲: اتمام مجموعه آدرس‌ها

یک شبکه کنفرانس با مجموعه DHCP شامل ۱۰۰ آدرس (192.168.50.100–199) دارای ۱۰۰ میزبان متصل است. یکصد و یکمین میزبان یک پیام Discover ارسال می‌کند.

نتیجه: سرور هیچ آدرس در دسترسی برای ارائه ندارد. میزبان هیچ Offer دریافت نمی‌کند و نمی‌تواند به شبکه بپیوندد. راه‌حل: کاهش مدت اجاره یا گسترش مجموعه آدرس‌ها.

DHCP دارای صف داخلی نیست — درخواست در صورت نبود آدرس آزاد به سادگی نادیده گرفته می‌شود.
مثال ۳: زمان‌بندی تمدید اجاره

یک تلفن IP 10.0.0.77 را با اجاره ۸ ساعته در ساعت ۸:۰۰ صبح دریافت کرد. طبق RFC 2131، کلاینت باید تمدید را در ۵۰٪ زمان اجاره (T1 = ۴ ساعت) و سپس اتصال مجدد را در ۸۷٫۵٪ (T2 = ۷ ساعت) امتحان کند.

در ساعت ۱۲:۰۰ (T1): کلاینت یک Request یونیکست به سرور اصلی ارسال می‌کند. اگر تا ساعت ۱۵:۰۰ (T2) پاسخی دریافت نشود: کلاینت به هر سروری broadcast می‌کند. اگر اجاره در ساعت ۱۶:۰۰ بدون تمدید منقضی شود: کلاینت باید استفاده از آدرس را متوقف کند.

هشدار: مشکل تحرک در زیرشبکه

وقتی یک میزبان به زیرشبکه جدیدی منتقل می‌شود (مثلاً از خانه به کافه)، DHCP یک آدرس IP جدید تخصیص می‌دهد. هرگونه ارتباط TCP فعال که از IP قدیمی استفاده می‌کند قطع می‌شود — ارتباطات TCP با (IP مبدأ، پورت مبدأ، IP مقصد، پورت مقصد) شناسایی می‌شوند. میزبان باید تحت IP جدید ارتباطات را برقرار کند. این یک محدودیت اساسی تحرک مبتنی بر DHCP است.

فرمت پیام DHCP و گزینه‌ها

پیام‌های DHCP درون دیتاگرام‌های UDP حمل می‌شوند. این فرمت از BOOTP تکامل یافته و ساختار پایه یکسانی دارد. فیلدهای کلیدی شامل کد عملیات (1=درخواست، 2=پاسخ)، نوع سخت‌افزار، شناسه تراکنش (xid)، آدرس IP کلاینت (ciaddr)، آدرس IP شما (yiaddr)، آدرس IP سرور (siaddr)، آدرس IP دروازه (giaddr)، آدرس سخت‌افزاری کلاینت (chaddr) و گزینه‌های با طول متغیر است.

کوکی جادویی و گزینه‌ها

هر پیام DHCP شامل یک کوکی جادویی ۴ بایتی (0x63825363) است که نشان می‌دهد گزینه‌های DHCP به دنبال می‌آیند. فیلد گزینه‌ها با طول متغیر است و از ساختار Type-Length-Value (TLV) استفاده می‌کند. گزینه‌های رایج عبارتند از: ماسک زیرشبکه (type 1)، مسیریاب (type 3)، DNS (type 6)، زمان اجاره IP (type 51)، نوع پیام DHCP (type 53) و شناسه سرور (type 54). لیست گزینه‌ها با یک بایت ۲۵۵ خاتمه می‌یابد.

مثال ۴: رمزگشایی گزینه‌های DHCP

یک پیام DHCP Offer شامل: Option 53 = 2 (Offer)، Option 1 = 255.255.255.0 (ماسک زیرشبکه)، Option 3 = 192.168.1.1 (دروازه)، Option 51 = 43200 (اجاره ۱۲ ساعته بر حسب ثانیه)، Option 54 = 192.168.1.10 (شناسه سرور).

کلاینت اکنون IP پیشنهادی، مرزهای شبکه، محل ارسال ترافیک خارج از زیرشبکه، مدت اعتبار اجاره و سروری که باید با آن تمدید کند را می‌داند.

فرآیند چهار مرحله‌ای DHCP (DORA)

پروتکل DHCP از یک دست‌دهی چهار پیامه استفاده می‌کند که با مخفف DORA شناخته می‌شود: Discover، Offer، Request، Acknowledge. کلاینت از حالت INIT (بدون IP) شروع کرده و پس از تکمیل موفقیت‌آمیز به حالت BOUND (دارای اجاره معتبر) منتقل می‌شود.

INIT (بدون IP) → DHCP Discover (broadcast) → DHCP Offer (broadcast) → DHCP Request (broadcast) → DHCP ACK (broadcast) → BOUND (دارای IP)

شبه‌کد الگوریتم

CLIENT BEHAVIOR (DHCP Client State Machine): State: INIT → Broadcast DHCPDISCOVER to 255.255.255.255:67 → Source IP: 0.0.0.0, Source Port: 68 → Set xid = random transaction ID → Transition to SELECTING state State: SELECTING → Wait for DHCPOFFER messages (timeout = T) → Collect offers from 0 or more servers → Select one offer (usually first received) → Broadcast DHCPREQUEST containing: • Option 54: selected server identifier • Option 50: requested IP address → Transition to REQUESTING state State: REQUESTING → Wait for DHCPACK (or DHCPNAK) → If DHCPACK received: • Configure interface with offered IP • Set lease timer = offered lease time • Set T1 = 0.5 × lease, T2 = 0.875 × lease → Transition to BOUND state → If DHCPNAK received or timeout: → Restart from INIT State: BOUND (normal operation) → At T1 (50% lease): unicast DHCPREQUEST to server → If ACK received: reset lease timer, stay BOUND → At T2 (87.5% lease): broadcast DHCPREQUEST → If ACK received: reset lease timer, stay BOUND → If lease expires: → transition to INIT SERVER BEHAVIOR (simplified): On receiving DHCPDISCOVER: → If pool has available IP: • Select IP from pool • Create binding entry (IP + client MAC) • Broadcast DHCPOFFER with yiaddr = proposed IP • Include options: mask, gateway, DNS, lease, server ID → Else: silently drop On receiving DHCPREQUEST: → If requested IP is still available: • Commit binding (reserve IP permanently for lease) • Broadcast DHCPACK with yiaddr = confirmed IP → Else: • Broadcast DHCPNAK (negative acknowledgment)

شکست گام به گام

گام ۱: DHCP Discover (کلاینت ← سرور)

میزبان تازه متصل شده هیچ آدرس IP ندارد، بنابراین یک پیام DHCP Discover را به 255.255.255.255 (broadcast محدود) با IP مبدأ 0.0.0.0 ارسال می‌کند. پیام از طریق UDP روی پورت 67 (سرور) ارسال می‌شود. هر دستگاه در زیرشبکه این broadcast را دریافت می‌کند، اما فقط سرورهای DHCP آن را پردازش می‌کنند.

کلید: منبع = 0.0.0.0:68 مقصد = 255.255.255.255:67 Broadcast

گام ۲: DHCP Offer (سرور ← کلاینت)

یک یا چند سرور DHCP با یک پیام Offer پاسخ می‌دهند، که معمولاً نیز broadcast است (مگر اینکه کلاینت پرچم broadcast را روی 0 تنظیم کرده باشد). Offer شامل یک آدرس IP پیشنهادی (yiaddr)، ماسک زیرشبکه، دروازه پیش‌فرض، سرور DNS، زمان اجاره و شناسه سرور است. کلاینت ممکن است چندین Offer دریافت کند.

yiaddr = IP پیشنهادی Option 54 = شناسه سرور زمان اجاره = Option 51

گام ۳: DHCP Request (کلاینت ← سرور)

کلاینت یک Offer را انتخاب کرده و یک پیام DHCP Request را broadcast می‌کند. این broadcast است تا همه سرورهای DHCP در زیرشبکه بدانند کدام Offer پذیرفته شده است (سرورهای انتخاب‌نشده می‌توانند IPهای پیشنهادی خود را به مجموعه بازگردانند). Request شامل شناسه سرور انتخاب‌شده (Option 54) و IP درخواستی (Option 50) است.

Option 50 = IP درخواستی Option 54 = سرور انتخاب‌شده هنوز broadcast!

گام ۴: DHCP ACK (سرور ← کلاینت)

سرور انتخاب‌شده تخصیص را با یک پیام DHCP ACK تأیید می‌کند. آن اتصال (binding) را در پایگاه داده خود ثبت می‌کند. کلاینت رابط شبکه خود را با IP تخصیص‌یافته پیکربندی کرده و تایمرهایی برای تمدید تنظیم می‌کند. کلاینت اکنون در حالت BOUND قرار دارد و می‌تواند در شبکه ارتباط برقرار کند.

سرور binding را ثبت می‌کند کلاینت رابط را پیکربندی می‌کند حالت BOUND

مثال‌های عملی

مثال ۱: چرخه کامل DORA

یک میزبان جدید با آدرس MAC AA:BB:CC:DD:EE:FF به یک شبکه Ethernet با یک سرور DHCP (192.168.1.1) متصل می‌شود. مجموعه آدرس‌های سرور از 192.168.1.100 تا 192.168.1.200 است.

  1. Discover: میزبان از 0.0.0.0:68 به 255.255.255.255:67 با xid=0x1234، chaddr=AA:BB:CC:DD:EE:FF broadcast می‌کند.
  2. Offer: سرور با yiaddr=192.168.1.100، mask=255.255.255.0، gateway=192.168.1.1، DNS=8.8.8.8، lease=86400s، server ID=192.168.1.1 پاسخ می‌دهد.
  3. Request: میزبان با Option 50=192.168.1.100، Option 54=192.168.1.1، همان xid=0x1234 broadcast می‌کند.
  4. ACK: سرور با yiaddr=192.168.1.100، همان پارامترهای پیکربندی تأیید می‌کند. میزبان رابط را پیکربندی می‌کند.

میزبان 192.168.1.100 اکنون با دسترسی کامل به شبکه عملیاتی است. زمان کل: معمولاً کمتر از ۱ ثانیه.

مثال ۲: چندین سرور DHCP

یک زیرشبکه دارای دو سرور DHCP است: سرور A (مجموعه: ۱۰.۰.۰.۱۰–۵۰) و سرور B (مجموعه: ۱۰.۰.۰.۵۱–۱۰۰). یک کلاینت یک Discover broadcast می‌کند.

  1. هر دو سرور Discover را دریافت کرده و هر کدام یک Offer ارسال می‌کنند: سرور A آدرس ۱۰.۰.۰.۱۰ و سرور B آدرس ۱۰.۰.۰.۵۱ را پیشنهاد می‌دهد.
  2. کلاینت Offer سرور A را می‌پذیرد (اولین دریافت‌شده). یک Request با Option 54 = شناسه سرور A (10.0.0.1) broadcast می‌کند.
  3. سرور A ACK ارسال می‌کند. سرور B Request را می‌بیند (که آن را انتخاب نکرده) و ۱۰.۰.۰.۵۱ را به مجموعه آزاد خود بازمی‌گرداند.

Request دقیقاً broadcast می‌شود تا همه سرورها بدانند کدام Offer پذیرفته شده و بتوانند پیشنهادهای انتخاب‌نشده را بازپس بگیرند.

مثال ۳: سناریوی DHCPNAK

یک کلاینت سعی می‌کند IP 10.0.0.5 (آدرس قبلی خود از یک زیرشبکه متفاوت) را درخواست کند. سرور DHCP مجموعه خود را بررسی کرده و می‌بیند 10.0.0.5 در هیچ محدوده پیکربندی‌شده‌ای نیست.

سرور DHCPNAK ارسال می‌کند. کلاینت باید از حالت INIT دوباره شروع کند (Discover جدید). این کار از تخصیص خودسرانه IPهای نامعتبر توسط کلاینت‌ها جلوگیری کرده و یکپارچگی مجموعه را حفظ می‌کند.

DHCPNAK همچنین می‌تواند رخ دهد اگر IP درخواستی قبلاً به میزبان دیگری اجاره داده شده باشد (که از طریق تشخیص تداخل یا جستجوی پایگاه داده binding شناسایی می‌شود).
اشتباه رایج: Broadcast در گام ۳

دانشجویان اغلب می‌پرسند: "چرا کلاینت Request را در گام ۳ broadcast می‌کند به جای اینکه به صورت یونیکست به سرور انتخاب‌شده ارسال کند؟" پاسخ: broadcast تضمین می‌کند که همه سرورهای DHCP در زیرشبکه بدانند کدام Offer پذیرفته شده است. سرورهای انتخاب‌نشده می‌توانند بلافاصله IP پیشنهادی را به مجموعه بازگردانند. اگر Request یونیکست بود، سرورهای انتخاب‌نشده فقط پس از یک timeout IP را بازپس می‌گرفتند که باعث هدررفت موقت آدرس‌ها می‌شود.

نمودار انتقال حالت DHCP

+-----------+ | INIT | <-- (lease expires or NAK) +-----------+ | (broadcast Discover) | v +-----------+ | SELECTING | <-- collects Offers +-----------+ | (broadcast Request) | v +-----------+ | REQUESTING| <-- waits for ACK/NAK +-----------+ | | (ACK) | | (NAK/timeout) v v +--------+ +-------+ | BOUND | | INIT | +--------+ +-------+ | (T1 timer: 50% lease) | v +-----------+ | RENEWING | -- unicast Request to server -- +-----------+ | (ACK or T2 timer) | +------+------+ | | (ACK) (T2: 87.5%) | | v v +--------+ +-----------+ | BOUND | | REBINDING | -- broadcast Request -- +--------+ +-----------+ | | (ACK) | | (lease expires) v v +--------+ +-------+ | BOUND | | INIT | +--------+ +-------+

خلاصه حالت‌ها

INIT: بدون IP، بدون اجاره

SELECTING: در انتظار پیشنهادها

REQUESTING: در انتظار ACK

BOUND: اجاره معتبر، عملیات عادی

RENEWING: تلاش برای تمدید یونیکست در T1

REBINDING: تلاش broadcast در T2

تایمرهای مهم

T1: ۵۰٪ اجاره (تمدید)

T2: ۸۷٫۵٪ اجاره (اتصال مجدد)

انقضای اجاره: ۱۰۰٪

دوره مهلت: ندارد

عامل رله DHCP

در بسیاری از شبکه‌های واقعی، یک سرور DHCP به چندین زیرشبکه سرویس می‌دهد. از آنجایی که پیام‌های DHCP Discover broadcast هستند (محدود به زیرشبکه)، نمی‌توانند به طور پیش‌فرض از مسیریاب‌ها عبور کنند. عامل رله DHCP (معمولاً درون مسیریاب) این مشکل را حل می‌کند.

نحوه کار رله DHCP

عامل رله پیام‌های broadcast DHCP را در یک زیرشبکه گرفته و آن‌ها را به صورت یونیکست به یک سرور DHCP شناخته‌شده در زیرشبکه دیگر ارسال می‌کند. فیلد giaddr (آدرس IP دروازه) را به IP خود در زیرشبکه کلاینت تنظیم می‌کند، تا سرور بداند کلاینت در کدام زیرشبکه قرار دارد و بتواند یک IP مناسب از مجموعه صحیح تخصیص دهد.

RELAY AGENT BEHAVIOR: On receiving DHCPDISCOVER (broadcast, port 67): → Set giaddr = IP of receiving interface → Forward as unicast to configured DHCP server → Note: do not modify chaddr, xid, or options On receiving DHCPOFFER/ACK (from server): → Remove giaddr (set to 0) → Forward as broadcast or unicast (per flags) to client's subnet → Use ARP or switching table to deliver to client
مثال ۱: رله DHCP در سراسر زیرشبکه‌ها

توپولوژی شبکه: زیرشبکه A (192.168.1.0/24) و زیرشبکه B (10.0.0.0/24) که توسط یک مسیریاب متصل شده‌اند. سرور DHCP در زیرشبکه A در آدرس 192.168.1.10 قرار دارد. یک میزبان به زیرشبکه B می‌پیوندد.

  1. میزبان در زیرشبکه B یک Discover در 10.0.0.0/24 broadcast می‌کند.
  2. مسیریاب (عامل رله) آن را روی رابط 10.0.0.1 خود دریافت کرده، giaddr=10.0.0.1 تنظیم می‌کند و به صورت یونیکست به 192.168.1.10:67 ارسال می‌کند.
  3. سرور giaddr=10.0.0.1 را می‌بیند، می‌داند کلاینت در 10.0.0.0/24 است و IP را از مجموعه مربوط به آن زیرشبکه انتخاب می‌کند.
  4. سرور پاسخ (Offer/ACK) را به رله در 10.0.0.1 ارسال می‌کند که آن را به کلاینت در زیرشبکه B ارسال می‌کند.

یک سرور DHCP به هر دو زیرشبکه سرویس می‌دهد. بدون رله، یک سرور DHCP جداگانه در هر زیرشبکه مورد نیاز بود.

مثال ۲: شبکه شرکتی با ۱۰ زیرشبکه

یک شرکت دارای ۱۰ VLAN (یکی برای هر دپارتمان) است و می‌خواهد یک سرور DHCP واحد در اتاق سرور داشته باشد. رابط مسیریاب هر VLAN به عنوان یک رله DHCP پیکربندی شده است که به 10.0.0.10:67 اشاره می‌کند.

سرور DHCP ۱۰ مجموعه مجزا را نگهداری می‌کند. فیلد giaddr مشخص می‌کند از کدام مجموعه استفاده شود. مدیریت کل: یک سرور به جای ده سرور. افزونگی سخت‌افزاری از دست نمی‌رود — یک سرور دوم می‌تواند برای failover اضافه شود.

اشتباه رایج: رله در مقابل پراکسی

رله DHCP اغلب با پراکسی DHCP اشتباه گرفته می‌شود. یک رله پیام‌ها را بدون تغییر ارسال می‌کند (به جز تنظیم giaddr). یک پراکسی مکالمه DHCP را خاتمه داده و یک مکالمه جدید از طرف کلاینت ایجاد می‌کند. رله‌ها شفاف هستند؛ پراکسی‌ها به عنوان واسطه عمل می‌کنند. اکثر مسیریاب‌ها رله را پیاده‌سازی می‌کنند، نه پراکسی را.

تمدید اجاره و آزادسازی

اجاره‌های DHCP برای استفاده کارآمد از آدرس طراحی شده‌اند. یک میزبان یک IP را برای همیشه نگه نمی‌دارد — باید به صورت دوره‌ای تمدید کند. فرآیند تمدید از دو تایمر (T1 و T2) محاسبه‌شده از مدت اجاره استفاده می‌کند.

تایمرهای اجاره (RFC 2131):
T1 = 0.5 × Lease_Time  |  T2 = 0.875 × Lease_Time
T1: تلاش برای تمدید یونیکست. T2: اگر پاسخی نیامد، تلاش برای اتصال مجدد broadcast.
LEASE RENEWAL ALGORITHM: State: BOUND → Wait for T1 timer to fire State: RENEWING → Unicast DHCPREQUEST to original server (ciaddr = current IP) → Include Option 53 = 3 (Request) → If DHCPACK received before T2: • Reset lease timer = lease time from ACK • Reset T1, T2 timers → Return to BOUND → If DHCPNAK received: → Transition to INIT (must get new IP) State: REBINDING (T2 fired, no ACK yet) → Broadcast DHCPREQUEST (ciaddr = current IP) → Any server on subnet can respond → If DHCPACK received: • Reset all timers → Return to BOUND → If DHCPNAK received: → Transition to INIT → If lease expires: → Transition to INIT (must stop using IP) GRACEFUL RELEASE (client-initiated): → Send DHCPRELEASE to server → Include Option 53 = 7 (Release) → Server marks IP as free → Client transitions to INIT
مثال ۳: تمدید اجاره با راه‌اندازی مجدد سرور

یک میزبان دارای اجاره ۲۴ ساعته روی IP 172.16.0.50 است. در T1 (۱۲ ساعت)، میزبان تلاش تمدید یونیکست می‌کند اما سرور DHCP به طور موقت برای تعمیرات از کار افتاده است.

  1. T1 (۱۲ ساعت): Request یونیکست → بدون پاسخ. میزبان به استفاده از IP ادامه می‌دهد.
  2. T2 (۲۱ ساعت): Request broadcast → سرور دوباره فعال شده است. سرور با ACK، همان IP، با اجاره ۲۴ ساعته تازه پاسخ می‌دهد.
  3. میزبان تایمرها را بازنشانی کرده، در حالت BOUND باقی می‌ماند. هیچ وقفه‌ای در سرویس شبکه ایجاد نمی‌شود.

تمدید دو سطحی (یونیکست سپس broadcast) مقاومت در برابر قطعی‌های کوتاه سرور را فراهم می‌کند. میزبان ۸۷٫۵٪ از زمان اجاره را برای مدیریت خرابی‌ها قبل از نیاز به یافتن IP جدید دارد.

اشتباه رایج: DHCPRELEASE الزامی نیست

یک کلاینت می‌تواند به سادگی استفاده از IP خود را متوقف کند (مثلاً خاموش شدن) بدون ارسال DHCPRELEASE. سرور آدرس را هنگام انقضای اجاره بازپس می‌گیرد. با این حال، ارسال release برای دستگاه‌های همراه که ممکن است قبل از انقضای اجاره بازنگردند، یک روش خوب است — این امکان استفاده مجدد فوری از آدرس را فراهم می‌کند.

ISC DHCP و استقرار عملی

Internet Systems Consortium (ISC) پرکاربردترین پیاده‌سازی منبع‌باز DHCP را ارائه می‌دهد. ISC DHCP در اکثر سیستم‌های یونیکس‌مانند اجرا می‌شود و از هر دو عملکرد سرور و رله پشتیبانی می‌کند.

مثال پیکربندی ISC DHCP

# /etc/dhcp/dhcpd.conf — ISC DHCP Server Configuration default-lease-time 86400; # 24 hours in seconds max-lease-time 172800; # 48 hours maximum subnet 192.168.1.0 netmask 255.255.255.0 { range 192.168.1.100 192.168.1.200; option routers 192.168.1.1; option subnet-mask 255.255.255.0; option domain-name-servers 8.8.8.8, 8.8.4.4; option domain-name "example.local"; } # Static reservation for a printer host printer1 { hardware ethernet AA:BB:CC:11:22:33; fixed-address 192.168.1.10; }

• پشتیبانی از عامل رله

• کنترل دسترسی مبتنی بر نقش

ملاحظات امنیتی DHCP

• سرور DHCP مخرب: یک مهاجم در زیرشبکه می‌تواند پیکربندی‌های IP مخرب ارائه دهد (مثلاً یک دروازه جعلی برای MITM).

• تشخیص DHCP: ویژگی سوئیچ که پیام‌های DHCP غیرقابل اعتماد را فیلتر می‌کند و فقط به سرورهای مجاز اجازه می‌دهد.

• حمله گرسنگی: مهاجم پیام‌های Discover را با MACهای جعلی flood می‌کند تا مجموعه آدرس را خالی کند (DoS).

• کاهش: استفاده از DHCP snooping، امنیت پورت و محدودسازی نرخ در پورت‌های دسترسی.

مثال ۴: رزرو ایستا در مقابل مجموعه پویا

یک مدیر شبکه یک سرور DHCP را با یک مجموعه پویا (192.168.1.100–200) و یک رزرو ایستا برای سرور فایل (MAC: AA:BB:CC:DD:EE:FF → IP: 192.168.1.5) پیکربندی می‌کند.

سرور فایل همیشه 192.168.1.5 را دریافت می‌کند (مفید برای رکوردهای DNS A، قوانین فایروال). سایر میزبان‌ها آدرس‌های پویا از مجموعه دریافت می‌کنند. اگر سرور فایل از MAC متفاوتی استفاده کند (مثلاً تعویض NIC)، IP متفاوتی دریافت خواهد کرد مگر اینکه رزرو به‌روزرسانی شود — یک دام عملیاتی رایج.

مثال ۵: DHCP از طریق Wi-Fi (802.11)

یک گوشی هوشمند به Wi-Fi کافه متصل می‌شود. نقطه دسترسی کلاینت بی‌سیم را به زیرشبکه سیمی پل می‌کند. تبادل DHCP دقیقاً مانند Ethernet انجام می‌شود، اما ارتباط اولیه (احراز هویت/همراهی 802.11) ابتدا انجام می‌شود.

گوشی هوشمند IP 10.0.0.42 را با اجاره ۱ ساعته دریافت می‌کند. پس از ۳۰ دقیقه، کاربر به کافه دیگری می‌رود. اجاره قدیمی نهایتاً منقضی می‌شود و گوشی در مکان جدید یک IP جدید دریافت می‌کند. هر تماس VoIP یا جریان پخش‌موسیقی که از IP قدیمی استفاده می‌کند قطع می‌شود — به همین دلیل پروتکل‌های تحرک مانند MIPv6 یا تحویل بدون وقفه در لایه بالایی مورد نیاز است.

مهم: DHCPv6 با DHCPv4 یکسان نیست

در IPv6، میزبان‌ها می‌توانند آدرس IP خود را از طریق SLAAC (پیکربندی خودکار آدرس بدون حالت) بدون هیچ سرور DHCP پیکربندی کنند. DHCPv6 اختیاری است و معمولاً برای ارائه آدرس‌های سرور DNS و سایر پارامترهای پیکربندی که از Router Advertisements در دسترس نیستند استفاده می‌شود. فرآیند چهار پیامه DORA به یک فرآیند چهار پیامه در DHCPv6 تبدیل می‌شود: Solicit ← Advertise ← Request ← Reply.

نکته امتحانی: نکات کلیدی کروس و راس

به خاطر بسپارید: DHCP یک پروتکل اتصال و راه‌اندازی خودکار است (بخش ۴.۲.۵ در کروس و راس ویرایش ۸). مراحل DORA، رفتار broadcast (255.255.255.255، 0.0.0.0، UDP 67/68)، مفهوم اجاره و این واقعیت که DHCP فقط برای پیکربندی آدرس است — نه مسیریابی — را بدانید. آماده باشید توضیح دهید چرا ارتباطات TCP وقتی یک میزبان زیرشبکه را تغییر می‌دهد قطع می‌شوند (چهارتایی (IP مبدأ، پورت مبدأ، IP مقصد، پورت مقصد) تغییر می‌کند). همچنین مورد استفاده عامل رله برای محیط‌های چند زیرشبکه‌ای را درک کنید.
