Link-State Routing Overview

Link-State (LS) routing is a centralized routing algorithm that uses complete, global knowledge about the network. Each node has identical and complete information about the network topology and all link costs.

Key Properties

• Global — complete topology known

• Centralized — all computation at one node

• Uses Dijkstra's algorithm

• Also called LS algorithm

Information Required

• Set of all nodes N

• Set of all edges E

• Cost c(x,y) for each edge

• Complete map of network

Real-World Usage

• OSPF (Open Shortest Path First)

• IS-IS (Intermediate System-Intermediate System)

• Used in intra-AS routing

Algorithm Classification

Routing algorithms can be classified along three broad dimensions:

Centralized vs Decentralized

Centralized (LS): Complete global knowledge — all link costs known. Computation in one location (central controller or replicated at each router).

Decentralized (DV): Iterative, distributed calculation. Each node knows only its own directly attached link costs.

Static vs Dynamic

Static: Routes change slowly (often via human manual intervention).

Dynamic: Routes change in response to traffic loads or topology changes. Can be periodic or event-driven. More responsive but can cause loops and oscillations.

Load-Sensitive vs Load-Insensitive

Load-sensitive: Link costs vary with congestion level. Early ARPAnet was load-sensitive [McQuillan 1980], but difficulties were encountered [Huitema 1998].

Load-insensitive: Link costs do NOT reflect current congestion. Today's Internet routing (RIP, OSPF, BGP) is load-insensitive — a design choice that avoids oscillation problems.

Key Distinction: LS algorithms require global state information and complete knowledge of all link costs. Each node broadcasts link-state packets (LSPs) containing its directly connected link costs to ALL other nodes, ensuring every node has an identical view of the network. In practice (e.g., with OSPF), this is accomplished by a link-state broadcast algorithm [Perlman 1999].

Dijkstra's Algorithm — Pseudocode

Dijkstra's algorithm computes the least-cost path from a source node u to all other nodes in the network. It is iterative and has the property that after the k-th iteration, the least-cost paths are known to k destination nodes, and among the least-cost paths to all destination nodes, these k paths will have the k smallest costs. A closely related algorithm is Prim's algorithm for minimum spanning trees; see [Cormen 2001] for a general discussion of graph algorithms.

Notation: D(v) = current cost from source to node v p(v) = predecessor node along path from source to v N' = set of nodes whose least-cost path is known Algorithm for source node u: 1 Initialization: 2 N' = {u} 3 for all nodes v: 4 if v is neighbor of u: 5 D(v) = c(u, v) 6 else: 7 D(v) = ∞ 8 9 Loop: 10 find w not in N' such that D(w) is minimum 11 add w to N' 12 update D(v) for each neighbor v of w not in N': 13 D(v) = min( D(v), D(w) + c(w, v) ) 14 until N' = N
Core Update Rule:
D(v) = min( D(v), D(w) + c(w, v) )
New cost to v = min(old cost, cost to w + cost from w to v)

Forwarding Table Construction

After running Dijkstra's algorithm, each node constructs a forwarding table that maps each destination to the next-hop router on the least-cost path.

The next-hop is determined by the predecessor information p(v) from Dijkstra's output.

Step-by-Step Explanation

Step 0 (Initialization): N' = {u}. Direct neighbors: v (cost 2), x (cost 1), w (cost 5). Others set to ∞. Node x has minimum cost (1), so it is selected.

Step 1 (ux): N' = {u, x}. Update via x: D(v) = min(2, 1+1) = 2 (no change); D(w) = min(5, 1+3) = 4 (improved!); D(y) = min(∞, 1+2) = 3 → actually x to y is 2, so D(y) = 1+2 = 2. D(z) = ∞ (x is not connected to z). Now y has cost 2, tied with v — we pick y (arbitrary tie-break).

Step 2 (uxy): N' = {u, x, y}. Update via y: D(v) = min(2, 2+∞) = 2 (no change; y not connected to v); D(w) = min(4, 2+1) = 3 (improved!); D(z) = min(∞, 2+4) = 6 → wait, y to z is 4, so actually D(z) = min(∞, 2+4) = 6. Computational Complexity

Naive Implementation

Time: O(n²)

Space: O(n)

n = number of nodes (excluding source)

With Heap (Priority Queue)

Time: O((n + e) log n)

Space: O(n + e)

e = number of edges

Message Complexity

O(|N| × |E|)

Each node broadcasts LS packet

Each packet reaches all nodes

Complexity Derivation (Naive):
Total comparisons = n + (n-1) + (n-2) + ... + 1 = n(n+1)/2
First iteration: check n nodes, second: n-1, third: n-2, etc. ⇒ O(n²)

Improved implementation: Using a heap data structure to find the minimum in line 9 of the algorithm reduces finding the minimum from O(n) to O(log n) per iteration, giving O((n+e) log n) overall.

Oscillation Problem

When link costs are congestion-sensitive (i.e., costs reflect current traffic load), LS algorithms can cause oscillations — routing paths continuously flip-flop between alternatives.

Warning: Oscillations occur when link costs depend on traffic load. As routers all compute and switch to the "best" path simultaneously, the load shifts, making the previously worse path now better — leading to a cycle.
Oscillation Scenario

Consider a network with nodes x, y, z, w where link costs equal the traffic load carried. Initially (Figure 5.5a), traffic is distributed. After LS runs:

Phase 1: y and x detect clockwise paths are cheaper → all route clockwise (Figure 5.5b).

Phase 2: All detect zero-cost counterclockwise paths → all route counterclockwise (Figure 5.5c).

Phase 3: All detect clockwise is better again → switch back (Figure 5.5d).

This cycle repeats indefinitely.

Self-Synchronization [Floyd 1994]: Researchers have found that routers in the Internet can self-synchronize among themselves. Even though they initially execute the LS algorithm with the same period but at different instants of time, the algorithm execution instance can eventually become, and remain, synchronized at the routers. This self-synchronization worsens the oscillation problem by ensuring all routers switch paths simultaneously.

Solutions to Oscillation

Solution 1: Fixed Costs

Mandate that link costs do NOT depend on traffic load. But this defeats the purpose of congestion-aware routing.

Solution 2: Randomization

Ensure routers do not run LS at the same time. Each router randomizes the time it sends link advertisements to break synchronization [Floyd Synchronization 1994].

Solution 3: Periodic Updates

Use fixed periodic updates rather than event-driven updates tied to cost changes, reducing feedback loops.

Important: Internet routing protocols (OSPF, RIP, BGP) are load-insensitive — link costs do NOT explicitly reflect current congestion levels. This design choice avoids oscillation problems.

Example 4: Effects of Link Cost Changes

In the original 6-node network from Tab 2, suppose c(v,w) changes from 3 to 10. Recompute least-cost paths from u.

Without the cheap v-w link, the path u→v→w is now 2+10=12. The path u→x→y→w is 1+2+1=4. So D(w) becomes:

• Initial: D(w) = min(5, 2+10, 1+3) → wait, through v: 2+10=12, through x: 1+3=4

So D(w) = 4 via x.

Result: The path u→w stays at cost 4 via x-y, and u→z stays at 4 via y-w-z (or could change if w-z link cost changes).
