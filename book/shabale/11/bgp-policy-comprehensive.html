BGP Route Selection and Policy

BGP (Border Gateway Protocol) is the de facto inter-AS routing protocol for the Internet. Unlike intra-AS protocols (OSPF, RIP) that optimize for performance, BGP is fundamentally policy-driven. Policy can override all other routing considerations including shortest AS path or hot potato routing.

BGP Route Selection Algorithm

When a router has two or more routes to the same prefix, BGP uses the following ordered rules:

BGP Route Selection Priority (highest to lowest):
1. Local Preference (highest wins)
2. Shortest AS-PATH
3. Closest NEXT-HOP (hot potato routing)
4. BGP Identifier (lowest wins, tiebreak)
Routes with the highest local preference are always chosen first, enforcing AS policy before any performance metrics
Warning: BGP is NOT a shortest-path algorithm. Policy trumps path length. A route through 10 ASes with high local preference will be chosen over a 2-AS path with default preference.

BGP Attributes

Every BGP route advertisement includes attributes that influence route selection:

AttributeTypePurpose
Local PreferenceMandatoryIndicates preferred exit point for an AS; set by AS policy
AS-PATHMandatorySequence of ASes traversed; used for loop detection and path length
NEXT-HOPMandatoryIP address of next-hop router toward the prefix
MED (Multi-Exit Discriminator)OptionalSuggested entry point into an AS when multiple links exist
CommunityOptionalTag for group policy actions (prepend, filter, prefer)

Local Preference in Detail

The local preference attribute is attached to routes within an AS and is never passed to neighboring ASes. It allows an AS to specify which egress point is preferred for a given destination. Higher values (default 100) indicate greater preference.

Key Concepts

• Local preference is intra-AS only

• Default value is 100

• Range: 0 to 2^32 - 1

• Policy can be set per prefix, per neighbor, or per AS

BGP Message Types

• OPEN: Establish connection

• UPDATE: Advertise/withdraw routes

• NOTIFICATION: Error reporting

• KEEPALIVE: Maintain session

Quick Reference Card: BGP Route Selection

1. Highest LOCAL_PREF (policy first!) 2. Shortest AS_PATH length 3. Lowest MED (if same AS) 4. eBGP learned > iBGP learned 5. Closest IGP neighbor (hot potato) 6. Lowest BGP Router ID

Customer/Provider Relationships

In the Internet hierarchy, ISPs form customer-provider relationships. The commercial relationship dictates how routes are advertised and what traffic is carried.

Selective Route Advertisement: Stub Networks

An access ISP like X in Figure 5.13 is connected to two providers (B and C). To function as a stub network (only sourcing/sinking its own traffic), X must selectively advertise its routes. Specifically, X will function as an access ISP network if it advertises to its neighbors B and C that it has no paths to any other destinations except itself.

Even though X may know a path X→C→Y to reach network Y, X will not advertise this path to B. Since B is unaware that X can reach Y, B will never forward traffic destined to Y through X. This prevents X from becoming a transit network between B and C.

Warning: If a multi-homed stub AS advertises routes learned from one provider to another, it becomes a transit AS and must carry other networks' traffic — likely violating its commercial agreement and incurring unexpected costs.

Multi-Homed Access ISP Behavior

A multi-homed access ISP (like X) connects to two or more providers for redundancy. Key behaviors:

Benefits

• Redundancy if one link fails

• Load balancing across links

• Better performance via best exit selection

Requirements

• Must not leak routes between providers

• Must use its own public prefix

• Typically sets local pref per provider

Example: Provider Route Advertisement Decision

Consider provider B in Figure 5.13. B learns path A→W from A. B installs AW and advertises it to customer X. Should B advertise BAW to C?

No. If B advertises BAW to C, traffic from C to W would flow through B, making B carry transit traffic between A and C. B has no incentive to carry this traffic without payment. The rule of thumb: traffic on a backbone must have source or destination in a customer of that ISP; otherwise, the traffic would be getting a free ride on the ISP's network. Individual peering agreements governing such questions are typically negotiated between ISPs and are often confidential [Huston 1999a; Huston 2012]. For a detailed description of how routing policy reflects commercial relationships among ISPs, see [Gao 2001; Dimitropoulos 2007]. For a discussion of BGP routing policies from an ISP standpoint, see [Caesar 2005b].

Peering Agreements and Transit Traffic

Peering is a business arrangement where two ISPs agree to exchange traffic between their networks without charging each other. Understanding peering vs. transit is critical for BGP policy design.

Peering vs. Transit

AspectPeeringTransit
PaymentSettlement-free (no money exchanged)Customer pays provider
Route scopeOnly routes from peer's customersFull Internet routing table
Traffic typeTraffic between peers' customers onlyAll destinations reachable
RelationshipMutually beneficialHierarchical
AgreementTypically negotiated, often confidentialStandard contract

Peering Traffic Rules

In a peering agreement, an ISP typically:

  • Advertises to the peer only routes from its own customer networks (not routes learned from other peers or providers)
  • Does NOT carry transit traffic between the peer and other networks
  • Does NOT advertise the peer's routes to other peers or providers
Peering Route Flow Rule:
Peer → Advertise to peer only: own prefixes + customer prefixes
Peer → Do NOT advertise: other peers' routes, providers' routes
This ensures that peering traffic stays between the two peers' customer cones

Transit Traffic Prevention

Transit traffic through a backbone ISP means packets traverse the ISP's network where neither source nor destination is a customer of that ISP. This is prevented by:

Prevention Mechanisms

• Filtering — Do not advertise peer routes to other peers

• Local preference — Prefer routes from customers

• AS_PATH prepending — Make path through you look longer

• Community tagging — Mark routes for specific treatment

Consequences of Leaking

• Free transit — Other ISPs get free bandwidth

• Cost increase — You pay for transit traffic

• Relationship damage — Peers may terminate peering

• Reputation loss — Prefix hijack or misconfiguration

Peering Agreement Confidentiality

Peering agreements between ISPs are typically confidential. They govern questions such as which routes are exchanged, traffic volume commitments, and geographic scope. The lack of standardization means BGP policy configuration must be carefully customized per peering relationship.

Why Inter-AS vs. Intra-AS Differ

Three fundamental reasons explain why different protocols are used for inter-AS and intra-AS routing:

ConsiderationInter-AS (BGP)Intra-AS (OSPF, RIP)
PolicyPolicy dominates; routes selected based on commercial relationshipsSingle administrative domain; policy is less important
ScaleMust handle Internet-scale routing (900K+ prefixes); data structures must scale to large numbers of networksLimited to single AS; can split into OSPF areas for hierarchy, or divide one AS into two ASs
PerformanceSecondary concern; policy often selects longer pathsPrimary concern; cost metrics optimize performance
Key Insight: BGP is policy-first, performance-second. Intra-AS protocols like OSPF and RIP are performance-first. This is why the Internet needs both types of protocols operating together.

Worked Examples

Example 1: Multi-Homed Stub Route Advertisement

Scenario: AS X is multi-homed to providers B and C (Figure 5.13). X has learned route X→C→Y to reach AS Y's prefix.

Question: Should X advertise this route to B? Why or why not?

Solution: No. If X advertises X→C→Y to B, then B will install path B→X→C→Y and may forward traffic to Y through X. This makes X a transit AS between B and C. X's traffic must be solely its own (source/destination within X).

Implementation: X advertises only its own prefix to B and C. X does not re-advertise routes learned from one provider to the other. This is enforced via outbound route filters.

prefix-list X-OWN permit 192.0.2.0/24 route-map TO-B permit 10 match ip address prefix-list X-OWN neighbor 203.0.113.1 route-map TO-B export
Example 2: Provider Transit Traffic Prevention

Scenario: Backbone ISP B has learned path A→W from peer A and path C→Y from peer C. B also has customer X.

Question: Should B advertise route B→A→W to C? What would happen if it did?

Analysis: If B advertises BAW to C, then traffic from C's customer Y destined to W would flow as Y→C→B→A→W. B carries this traffic even though neither source (Y) nor destination (W) is B's customer. B gets no revenue for this transit.

Solution: B should advertise BAW only to its customer X, not to peer C. B applies the rule: "Traffic flowing across my backbone must have a source or destination in a customer network."

Example 3: Local Preference for Exit Selection

Scenario: Multi-homed AS X connects to provider B and provider C. X learns the same prefix 203.0.113.0/24 from both. The link to B is 1 Gbps (cheaper), the link to C is 10 Gbps (more expensive per-GB).

Question: How does X prefer the cheaper link while keeping the faster link as backup?

Solution: Set local preference higher on routes learned from the preferred provider.

route-map FROM-B permit 10 set local-preference 150 route-map FROM-C permit 10 set local-preference 100 neighbor 203.0.113.2 route-map FROM-B import neighbor 203.0.113.6 route-map FROM-C import

Result: All routes from B have local pref 150, all from C have 100. Traffic exits via B unless B's link fails. If B goes down, routes from B disappear and traffic shifts to C automatically.

Example 4: AS_PATH Prepending for Traffic Engineering

Scenario: AS X has two links to provider B. X wants to use one link as primary and the other as backup for incoming traffic.

Solution: Prepend AS_PATH on the backup link to make it appear longer.

route-map TO-B-PRIMARY permit 10 set as-path prepend 64500 route-map TO-B-BACKUP permit 10 set as-path prepend 64500 64500 64500

Result: Primary link advertises path "64500", backup advertises "64500 64500 64500". Incoming traffic prefers the shorter path (primary) because AS_PATH length is the second criterion in BGP selection.

Example 5: BGP Policy Conflict Resolution

Scenario: AS X receives two routes to prefix 10.0.0.0/16:

Route 1: AS-PATH {B, A, Z}, NEXT-HOP 192.0.2.1, Local Pref 100

Route 2: AS-PATH {C, Z}, NEXT-HOP 198.51.100.1, Local Pref 200

Question: Which route is selected and why?

Answer: Route 2 is selected. Even though Route 1 has a shorter AS_PATH (3 vs 2? Actually Route 2 has shorter AS_PATH {C,Z} = 2 hops vs {B,A,Z} = 3 hops), the local preference criterion comes FIRST. Route 2 with Local Pref 200 wins regardless of path length. If both had same local pref, Route 2 would still win on shorter AS_PATH.

Moral: Local preference can override any other routing consideration — it is the policy hammer.
