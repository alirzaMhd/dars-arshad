OpenDaylight (ODL) Controller

OpenDaylight (ODL) is an open-source SDN controller developed in partnership with the Linux Foundation. It has found considerable industry support and is one of the most widely deployed SDN controllers.

Figure 5.17: OpenDaylight Architecture

ODL Layered Architecture (Figure 5.17):
Network Orchestrations & Applications (Top Layer)
↗ REST/RESTCONF/NETCONF APIs ↖
Service Abstraction Layer (SAL) — THE NERVE CENTER
↗ [messaging] [config & operational data store] ↖
Southbound Protocols: OpenFlow | NETCONF | SNMP | OVSDB
SAL provides a uniform abstract interface to all southbound protocols

Service Abstraction Layer (SAL)

The SAL is the controller's nerve center. It provides:

SAL Capabilities

• Service invocation — Components invoke each other's services

• Data access — Read/write configuration and operational data

• Event subscription — Subscribe to events generated by components

• Protocol abstraction — Uniform interface to southbound protocols

Southbound Protocols Supported

• OpenFlow — Flow table management

• NETCONF — Network Configuration Protocol

• SNMP — Simple Network Management Protocol

• OVSDB — Open vSwitch Database Protocol

Basic Network Functions (ODL Core)

ODL's Basic Network Functions correspond to the network-wide state management capabilities. These include:

AAAAuthentication, Authorization, Accounting

AD-SAL vs. MD-SAL

ODL provides two approaches for applications to interact with controller services:

AspectAD-SAL (API-Driven)MD-SAL (Model-Driven)
ApproachApplications use REST API directlyYANG models define data structures
IntroducedInitial ODL releasesLater ODL releases
ProtocolREST over HTTPNETCONF (YANG-defined models)
FlexibilityLess flexible, API changes require updatesMore flexible, models are extensible

YANG Data Modeling: YANG (RFC 6020) is a data modeling language used to define the structure of configuration and operational state data. In MD-SAL, devices are configured and managed by manipulating these YANG-defined models using NETCONF. This is more extensible than hard-coded APIs.

Enhanced Services

Above the Basic Network Functions, ODL provides Enhanced Services:

Enhanced Service Examples

• Traffic Engineering — Optimize path selection

• Firewalling — Security policy enforcement

• Load Balancing — Distribute traffic across servers

Northbound Access

Applications access enhanced services via:

• REST/RESTCONF (AD-SAL)

• NETCONF (MD-SAL)

ONOS Controller

ONOS (Open Network Operating System) is an open-source SDN controller, also developed in partnership with the Linux Foundation. Like ODL, it features a layered architecture but with distinct design choices.

Figure 5.18: ONOS Architecture

ONOS Three-Layer Architecture (Figure 5.18):
Network-Control Apps (Intent Framework, REST API)
↕ Northbound Abstractions & Protocols
ONOS Distributed Core (Logically Centralized)
↕ Southbound Abstractions & Protocols
Devices, Links, Hosts, Flow Rules, Statistics
ONOS runs as a distributed service on interconnected servers; each server runs identical software

Layer 1: Northbound Abstractions and Protocols

The northbound layer provides abstractions for network-control applications. Key features:

  • Intent Framework: Applications request high-level services without implementation details (e.g., "connect Host A to Host B" without specifying VLANs, paths, or protocols)
  • Synchronous access: Via query (REST API)
  • Asynchronous access: Via listener callbacks notified on network state changes
ONOS Intent Framework Example:
Intent: "Allow connectivity between Host A and Host B"
Intent: "Block Host A from communicating with Host C"
The intent framework translates these high-level policies into specific flow entries

Layer 2: Distributed Core

The distributed core is the heart of ONOS. It maintains the network's state and provides the abstraction of a logically centralized service. The distributed core provides mechanisms for service replication and coordination among instances, giving the applications above and the network devices below the abstraction of a single, consistent logically centralized controller.

State Maintained in Core

• Hosts — Location and identity

• Paths — Available end-to-end routes

• Topology — Network graph structure

• Devices — Switch/router inventory

• Links — Connection status

• Flow rules — Installed forwarding entries

• Statistics — Traffic measurements

Distributed Architecture

• Runs on a cluster of servers

• Each server runs identical ONOS software

• Capacity scales with more servers

• Service replication for fault tolerance

• Coordination among instances via distributed protocols

Layer 3: Southbound Abstractions and Protocols

ONOS's southbound layer masks the heterogeneity of underlying network devices.

Southbound Abstraction Benefits:
"Device and protocol agnostic" — core does not depend on specific device types
Protocol plugins: OpenFlow, NETCONF, OVSDB
ONOS's southbound interface is logically higher than the canonical controller (Figure 5.15) due to this abstraction layer

The southbound abstractions provide:

  • Device abstraction: Uniform interface for all switch types
  • Link abstraction: Consistent link representation regardless of protocol
  • Host abstraction: Standardized host tracking
  • Flow rule abstraction: Protocol-independent flow programming
  • Packet abstraction: Uniform packet processing interface
Key Architectural Difference: ONOS places its abstraction layer above the protocol plugins (between plugins and the distributed core). ODL's SAL is at the same level as the protocol plugins. This means ONOS's core is more protocol-agnostic than ODL's.

Architectural Comparison: SAL vs. Abstractions

ODL: SAL-Centric

SAL is at the center of the architecture.

It provides: messaging, data store (config + operational), and service routing.

Protocol plugins (OpenFlow, NETCONF, etc.) register with SAL.

Apps invoke services through SAL via REST or YANG models.

ONOS: Abstraction-Centric

Abstractions are at the center.

Northbound: Intent, Device, Host, Link abstractions.

Distributed core works at abstraction level, not protocol level.

Southbound: providers implement abstractions for specific protocols.

Worked Examples

Example 1: Intent-Based Connectivity with ONOS

Scenario: A network operator wants to establish connectivity between two servers: Server A (MAC=00:00:00:00:00:01, attached to switch s1 port 1) and Server B (MAC=00:00:00:00:00:02, attached to switch s4 port 2).

Using ONOS Intent Framework:

// ONOS Intent API — Java Intent intent = HostToHostIntent.builder() .appId(appId) .one(connectPoint("s1", 1)) // Server A location .two(connectPoint("s4", 2)) // Server B location .build(); intentService.submit(intent);

What happens internally:

  1. ONOS's intent framework receives the high-level intent: "Connect A to B".
  2. The intent compiler translates this into: find a path from s1 to s4, determine which switches need flow entries.
  3. The compiler interacts with the distributed core to get topology, available paths, and link capacities.
  4. Multiple path candidates are evaluated; the best path is selected (e.g., s1→s2→s3→s4).
  5. The intent framework installs flow rules on s1, s2, s3, and s4 using the southbound providers (OpenFlow).
  6. Flow entries: s1: dst=00:00:00:00:00:02 → output to s2; s2: dst=00:00:00:00:00:02 → output to s3; etc.

SDN advantage: The operator specifies what they want, not how. ONOS handles all the low-level details of path computation and flow installation.

Example 2: OpenDaylight MD-SAL Service Chain

Scenario: An enterprise wants all HTTP traffic to pass through a firewall before reaching the web server. Traffic must be steered: Client → Switch A → Firewall → Switch B → Web Server.

Using OpenDaylight MD-SAL:

  1. Define the service chain using a YANG data model:
// service-chain.yang module service-chain { yang-version 1.1; namespace "urn:example:service-chain"; prefix sc; list service-chain { key "name"; leaf name { type string; } list classifier { leaf dst-port { type uint16; } leaf protocol { type uint8; } } list service-function { ordered-by user; leaf type { type enumeration { enum firewall; enum DPI; enum lb; } } leaf device-ip { type inet:ipv4-address; } } } }
  1. The MD-SAL stores this model. A traffic steering application reads the model and translates it into flow entries.
  2. Via NETCONF, the application configures the firewall device with appropriate rules.
  3. Via OpenFlow, flow entries are installed on Switch A (redirect HTTP to firewall) and Switch B (accept from firewall).
Switch A flow entry: match: dst-port=80, proto=TCP actions: output to firewall port Switch B flow entry: match: in_port=firewall, dst-port=80, proto=TCP actions: output to web server port

MD-SAL advantage: The YANG model provides a single source of truth for the entire service chain configuration. Changes are made by updating the model instance via NETCONF.

Example 3: ONOS Distributed Core Failure Recovery

Scenario: An ONOS cluster has 5 servers. One server (instance 3) fails. The network has 50 switches connected to the cluster.

What happens:

PhaseAction
DetectionCluster membership protocol detects instance 3 is unreachable (heartbeat timeout)
Re-electionRAFT consensus protocol elects a new leader among remaining 4 instances
Switch reassignmentSwitches that were connected to instance 3 discover connection loss via OpenFlow echo timeout
ReconnectionSwitches connect to backup instances using pre-configured controller IP list
State recoveryDistributed core (Titan graph DB) already replicated state across instances; leader has complete topology
Flow re-installationNew controller instances verify flow tables on assigned switches; re-install any missing entries

Result: Network operation continues with no packet loss. Existing flow entries remain in switches and continue forwarding. Only new flow requests are briefly delayed during reconnection.

Key design principle: Switches are the "data plane cache" — they do not depend on the controller for every packet. The controller is only consulted for table-miss events.

Example 4: B4-Inspired Traffic Engineering Application

Scenario: A global SDN controller manages inter-data-center WAN links. Three application classes: interactive user traffic (priority 1), nearline analytics (priority 2), and bulk replication (priority 3). Link utilization should be maximized.

Solution (B4-inspired):

// Pseudo-code for TE app function computeAllocation(demands, links, priorities): // 1. Reserve bandwidth for highest priority flows for each interactive_flow: path = shortest_path(flow.src, flow.dst) allocate(path, flow.demand) // 2. Allocate medium priority on remaining capacity for each analytics_flow: path = path_with_available_bw(flow.src, flow.dst, flow.demand) if path exists: allocate(path, flow.demand) else: queue for later // 3. Fill remaining capacity with bulk traffic for each replication_flow: path = path_with_available_bw(flow.src, flow.dst) allocate(path, min(flow.demand, available_bw)) // Preemptible — can be dropped for higher priority

Results achieved by B4: 70% average link utilization (vs. 30-40% typical), 2-3x improvement. The SDN controller has a global view and can optimize across all flows simultaneously.

Example 5: Multi-Vendor Device Integration via Southbound Abstractions

Scenario: A network has switches from three vendors: Cisco (proprietary OS), Juniper (JunOS), and a white-box switch running Open vSwitch.

Without SDN: Network operators must learn three different CLI syntaxes and management protocols. Automating across all devices requires custom scripts for each vendor.

With ONOS southbound abstractions:

// Device abstraction — uniform API regardless of vendor DeviceId ciscoId = DeviceId.deviceId("netconf:10.0.0.1:830"); DeviceId juniperId = DeviceId.deviceId("netconf:10.0.0.2:830"); DeviceId ovsId = DeviceId.deviceId("openflow:10.0.0.3:6653"); // Install same flow rule on all three devices FlowRule rule = DefaultFlowRule.builder() .forDevice(ciscoId) // ONOS provider handles Cisco→NETCONF translation .withSelector(matchDst(IP4Prefix.valueOf("10.0.0.0/8"))) .withTreatment(DefaultTrafficTreatment.builder() .setOutput(PortNumber.port(3)) .build()) .build(); flowRuleService.applyFlowRules(rule); // Same call for Juniper flowRuleService.applyFlowRules(rule.forDevice(juniperId)); // Same call for OVS flowRuleService.applyFlowRules(rule.forDevice(ovsId));

Abstraction benefit: The ONOS distributed core does not need to know whether a device speaks OpenFlow, NETCONF, or a proprietary protocol. The southbound providers handle the translation.
