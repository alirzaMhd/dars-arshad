SNMP & MIB

Simple Network Management Protocol & Management Information Base

Network Management Framework (Figure 5.20)

A network management system consists of five key components that work together to monitor, control, and manage network devices.

Definition of Network Management [Saydam 1996]:
Network management includes the deployment, integration, and coordination of the hardware, software, and human elements to monitor, test, poll, configure, analyze, evaluate, and control the network and element resources to meet real-time, operational performance, and QoS requirements at a reasonable cost.
Five Components of Network Management:
Managing Server • Managed Device • Agent • Data • Protocol
The protocol (SNMP, NETCONF) enables communication between the managing server and the agent

SNMP Protocol Details

SNMP (Simple Network Management Protocol) defines how management information is exchanged between network management systems and agents.

SNMPv3 PDU Types (Table 5.2)

PDU TypeDirectionDescription
GetRequestManager → AgentRetrieve value of one or more MIB objects
GetNextRequestManager → AgentRetrieve the next object in the MIB tree (used for walking)
GetBulkRequestManager → AgentRetrieve large blocks of data efficiently (SNMPv2+)
SetRequestManager → AgentModify the value of a MIB object (write configuration)
InformRequestManager → ManagerNotify another managing server of MIB values remote to its access (SNMPv2+)
ResponseAgent → ManagerResponse to Get/Set requests; includes error status
SNMPv2-TrapAgent → ManagerUnsolicited notification of an event (unacknowledged)

Security Warning: SNMPv1 and v2c send community strings (passwords) in cleartext over the network. Always use SNMPv3 with authentication and encryption in production environments, or use isolated management networks.

SNMP over UDP — Reliability Considerations

Unreliable Transport

SNMP PDU is typically carried in UDP payload. Since UDP is unreliable, there is no guarantee a request or response will arrive.

Request ID Field

The Request ID field in the PDU numbers requests from manager to agent. The agent's response copies this ID, allowing the manager to detect lost requests or replies.

"Responsible" Retransmission

The SNMP standard does not mandate specific retransmission procedures. It only requires the managing server "needs to act responsibly in respect to the frequency and duration of retransmissions."

SNMPv3 = SNMPv2 + Security

As noted in [RFC 3410], "SNMPv3 can be thought of as SNMPv2 with additional security and administration capabilities." The lack of adequate security in v1/v2c limited SNMP primarily to monitoring rather than control (SetRequest was rarely used in SNMPv1).

Management Information Base (MIB)

The MIB is a hierarchical, tree-structured database of managed objects. Each object is identified by an Object Identifier (OID) and has a defined syntax, access level, and status.

OID Structure:
1.3.6.1.2.1.2.2.1.10.1 → ifInOctets on interface 1
iso(1) . org(3) . dod(6) . internet(1) . mgmt(2) . mib-2(1) . interfaces(2) . ifTable(2) . ifEntry(1) . ifInOctets(10) . instance(1)

SMI (Structure of Management Information)

SMI is the data description language [RFC 2578; RFC 2579; RFC 2580] used to define MIB objects. A formal definition language ensures the syntax and semantics of management data are well-defined and unambiguous. Related MIB objects are gathered into MIB modules — as of late 2019, there are over 400 MIB-related RFCs and many more vendor-specific (private) MIB modules. Key data types include:

Base Types

Integer32 — 32-bit integer

OctetString — byte string

ObjectIdentifier — OID

IpAddress — 4-byte IPv4 addr

Counter / Gauge

Counter32/64 — wraps at 2^32 / 2^64

Gauge32 — stays at max, doesn't wrap

TimeTicks — hundredths of a second

Table Types

SEQUENCE — row definition

SEQUENCE OF — table of rows

Index — unique key per row

Worked Examples

Example 1: SNMP Queries — Monitoring Interface Traffic

Scenario: An administrator wants to monitor the incoming traffic on interface GigabitEthernet0/1 of a router (ifIndex = 2). They retrieve ifInOctets every 60 seconds and calculate the bandwidth utilization.

# Query the ifInOctets OID for interface index 2
$ snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.10.2
IF-MIB::ifInOctets.2 = Counter32: 1523456789

# Wait 60 seconds and query again
$ snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.10.2
IF-MIB::ifInOctets.2 = Counter32: 1524567890

# Calculate: delta = 1524567890 - 1523456789 = 1111101 bytes in 60 seconds
# Bit rate = 1111101 * 8 / 60 = 148,146.8 bps ≈ 148 Kbps
# Utilization on 1 Gbps link = 148 Kbps / 1,000,000 Kbps = 0.0148%

Analysis:

  • ifInOctets is a Counter32 — it monotonically increases until it wraps at 2^32 (4,294,967,296)
  • To calculate utilization, the manager must poll twice and compute the delta
  • If the counter wraps between polls, the manager must detect it: new < old → (2^32 - old) + new
  • Polling interval matters: too long and you miss counter wraps; too short and you generate excessive traffic
Example 2: MIB Object Walk — Discovering Interfaces

Scenario: An administrator wants to discover all interfaces on a device and their operational status using SNMP walk.

$ snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.2
IF-MIB::ifDescr.1 = STRING: GigabitEthernet0/0
IF-MIB::ifDescr.2 = STRING: GigabitEthernet0/1
IF-MIB::ifDescr.3 = STRING: Serial0/0/0
IF-MIB::ifDescr.4 = STRING: Loopback0

$ snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.8
IF-MIB::ifOperStatus.1 = INTEGER: up(1)
IF-MIB::ifOperStatus.2 = INTEGER: up(1)
IF-MIB::ifOperStatus.3 = INTEGER: down(2)
IF-MIB::ifOperStatus.4 = INTEGER: up(1)

$ snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.16
IF-MIB::ifOutOctets.1 = Counter32: 985642135
IF-MIB::ifOutOctets.2 = Counter32: 2145789632
IF-MIB::ifOutOctets.3 = Counter32: 0
IF-MIB::ifOutOctets.4 = Counter32: 123456789

Analysis:

  • The walk uses GetNextRequest repeatedly to traverse the MIB subtree
  • Interface 3 (Serial0/0/0) shows ifOperStatus = down(2) and zero outbound octets — this interface is likely down or administratively disabled
  • The administrator can cross-reference: ifDescr.3 → ifOperStatus.3 → ifOutOctets.3 to build a complete interface inventory
Example 3: SNMP Trap Scenario — Link Down Alert

Scenario: A router's interface goes down. The SNMP agent sends a trap to the management server. The NMS receives and processes the alert.

Trap Flow:
Router detects link down → Agent sends SNMPv2-Trap → NMS receives on UDP 162 → NMS logs/ alarms
# Trap details captured at NMS
Received SNMPv2-Trap from UDP: [192.168.1.1]:161
sysUptime.0 = 123456789 (14 days, 6 hours)
snmpTrapOID.0 = ifDown
ifIndex.3 = 3
ifAdminStatus.3 = up(1)
ifOperStatus.3 = down(2)
ifDescr.3 = Serial0/0/0

# NMS correlation rule:
# Interface Serial0/0/0 changed from up to down
# Severity: Critical
# Action: Generate ticket + page on-call engineer

Analysis:

  • Traps are unacknowledged — if the NMS misses the trap, the event is lost (unless InformRequest is used)
  • SNMPv2-Trap includes snmpTrapOID to identify the event type (linkDown, authenticationFailure, etc.)
  • The trap includes variable bindings with contextual information (which interface, current status)
  • Best practice: Use SNMPv3 traps with authentication and encryption. Also configure redundant trap destinations.
Example 4: SNMP Set Operation — Disabling an Interface

Scenario: An administrator remotely disables a misconfigured interface using SNMP SetRequest.

# Check current admin status: ifAdminStatus.2 = 1 (up)
$ snmpget -v2c -c private 192.168.1.1 1.3.6.1.2.1.2.2.1.7.2
IF-MIB::ifAdminStatus.2 = INTEGER: up(1)

# Set admin status to down (2)
$ snmpset -v2c -c private 192.168.1.1 1.3.6.1.2.1.2.2.1.7.2 integer 2
IF-MIB::ifAdminStatus.2 = INTEGER: down(2)

# Verify the change
$ snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.7.2
IF-MIB::ifAdminStatus.2 = INTEGER: down(2)
Important: The Set operation uses the "private" community string (read-write). Using SNMP for configuration changes is generally discouraged in favor of NETCONF/YANG due to SNMP's lack of transactional guarantees.
Example 5: Counter Wrap Detection

Scenario: A Counter32 value wraps around. The NMS must detect and correctly compute the delta.

# Poll 1: Counter is near maximum
ifInOctets.2 = Counter32: 4294967290

# Poll 2 (60 seconds later): Counter has wrapped
ifInOctets.2 = Counter32: 5000

# Correct delta calculation:
delta = (2^32 - 4294967290) + 5000 = 6 + 5000 = 5006 bytes
# Incorrect calculation (no wrap detection):
delta = 5000 - 4294967290 = -4289962290 (WRONG!)

# Bit rate = 5006 * 8 / 60 = 667.5 bps

Solution: Use Counter64 (ifHCInOctets) wherever possible, or ensure poll intervals are short enough that counters cannot wrap more than once between polls.
