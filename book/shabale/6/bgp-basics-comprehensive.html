BGP — Border Gateway Protocol (Basics & Route Advertisement)

Computer Networks — Inter-AS Routing & Path Vector Protocol

The Role of BGP in the Internet

Border Gateway Protocol (BGP) is the de facto inter-AS routing protocol that glues the Internet together. While intra-AS protocols (OSPF, RIP) handle routing within an organization, BGP handles routing between Autonomous Systems.

BGP is a decentralized and asynchronous protocol in the vein of distance-vector routing (Section 5.2.2). It is arguably the most important Internet protocol after IP itself — the protocol that glues the thousands of ISPs together [RFC 4271].

BGP: Path Vector Protocol
Route = Prefix + Path Attributes
Path = Sequence of AS Numbers (AS-PATH)
Decision = Based on policies, not just shortest path
BGP is a path-vector protocol — it advertises not just destinations, but the complete path of ASs to reach them.

Key Characteristics

• Inter-AS: Connects different organizations

• Policy-Driven: Operators control route selection

• CIDR Support: Advertises prefixes with subnet masks

• Loop-Free: AS-PATH prevents loops by design

BGP vs OSPF

Scope: Inter-AS vs Intra-AS

Metric: Policy + Path vs Cost

Convergence: Slower vs Fast

Transport: TCP (179) vs IP (89)

Scale: Global Internet vs Enterprise

CIDRized Prefixes as Destinations

In BGP, packets are not routed to a specific destination address but to CIDRized prefixes. A router's forwarding table contains entries of the form (x, I), where x is a prefix (e.g., 138.16.68/22 covering 1024 addresses) and I is the outgoing interface number.

BGP advertises CIDRized IP prefixes (e.g., 128.119.0.0/16) rather than individual IP addresses or classful networks. This enables:

  • Route aggregation: A single prefix can represent millions of hosts.
  • Classless addressing: Variable-length subnet masks allow efficient address space usage.
  • Supernetting: Multiple smaller networks can be summarized into one larger prefix.
CIDR Advertisement Example

A university with IP blocks 128.119.0.0/24 through 128.119.255.0/24 can advertise a single aggregate route 128.119.0.0/16. This reduces the global routing table size.

BGP is often called the "glue of the Internet." Without BGP, the ~100,000+ ASs would have no way to exchange routing information, and inter-network communication would be impossible.

eBGP Connections

eBGP operates between routers in different ASs. Key characteristics:

  • Typically runs between directly connected border routers.
  • Uses TCP port 179 for reliable session establishment.
  • When advertising a route, the router prepends its own AS number to the AS-PATH.
  • TTL is set to 1 by default (prevents spoofed BGP sessions from non-adjacent routers).

iBGP Connections

iBGP operates between routers within the same AS. Key characteristics:

  • Used to distribute external routes learned via eBGP to internal routers.
  • iBGP connections create a mesh of TCP connections within each AS — every iBGP speaker peers with every other iBGP speaker. This is because iBGP does not re-advertise routes learned from other iBGP peers (loop prevention rule).
  • Does not modify the AS-PATH attribute.
  • May be multiple hops away within the AS (TTL = 255).
  • Note that iBGP connections do not always correspond to physical links — they are logical TCP sessions.
iBGP Full Mesh Rule
If a route is learned via iBGP, do NOT advertise it to another iBGP peer.
This prevents routing loops within the AS but requires all N routers to have N(N-1)/2 peerings. Route reflectors or confederations can reduce this complexity.
eBGP+iBGP Peering Setup

Consider AS 100 with two border routers (R1, R2) and one internal router (R3). AS 200 has one border router (R4).

  • eBGP: R1 ↔ R4 (AS 100 ↔ AS 200)
  • iBGP: R1 ↔ R2, R1 ↔ R3, R2 ↔ R3 (full mesh within AS 100)

R4 (AS 200) advertises prefix 10.1.0.0/16 to R1 via eBGP. R1 then advertises this to R2 and R3 via iBGP. R2 and R3 can now reach 10.1.0.0/16 through R1.

iBGP full mesh scales poorly. In an AS with 1000 iBGP speakers, you would need 499,500 TCP sessions. Route reflectors or BGP confederations are used to solve this.

BGP Path Attributes

BGP routes carry attributes that influence path selection and enforce routing policies. The two most fundamental attributes for inter-AS loop prevention and path selection are AS-PATH and NEXT-HOP.

AS-PATH Attribute

The AS-PATH is a sequence of AS numbers that a route has traversed. When a BGP router advertises a route via eBGP, it prepends its own AS number to the AS-PATH.

AS-PATH Format
AS_PATH = { AS1, AS2, AS3, ... }
Example: AS_PATH = "701 1239 3549"
The path is read left-to-right: the most recent AS prepends to the beginning.

AS-PATH: Loop Prevention

When a BGP router receives an UPDATE, it checks if its own AS number is already in the AS-PATH. If it is, the route is rejected (loop detected). This is BGP's primary loop prevention mechanism.

AS-PATH: Path Selection

Among routes with the same local preference, BGP prefers the shorter AS-PATH (fewer AS hops). This is not the same as router hops — it counts ASs traversed.

AS-PATH in Action

AS 100 advertises prefix 10.1.0.0/16 to AS 200. AS 200's border router receives the UPDATE with AS-PATH = [100]. AS 200 then advertises to AS 300 with AS-PATH = [200, 100].

Now AS 300 advertises to AS 100. AS 100 sees AS-PATH = [300, 200, 100]. Since AS 100's own AS number is in the path, the route is rejected — loop prevented.

NEXT-HOP Attribute

The NEXT-HOP attribute is the IP address of the router interface that should be used as the next hop to reach the advertised prefix. For eBGP, the NEXT-HOP is set to the IP address of the eBGP peer's interface.

NEXT-HOP Behavior
eBGP advertisement: NEXT-HOP = eBGP peer's interface IP
iBGP advertisement: NEXT-HOP = unchanged (preserved from eBGP)
If the NEXT-HOP is not reachable via the IGP, the route is considered invalid and not installed.
A common BGP troubleshooting scenario: a route is learned via iBGP but not installed because the NEXT-HOP is not in the routing table. This happens when the IGP does not have a route to the NEXT-HOP address.

Route Advertisement Flow

The flow of BGP route advertisements follows a 3-AS topology where each AS runs both iBGP (internally) and eBGP (between ASs). Understanding how routes propagate through this topology is essential for the exam.

Gateway Router vs Internal Router

In each AS, routers are classified into two roles:

  • Gateway router: A router on the edge of an AS that directly connects to one or more routers in other ASs (e.g., 1c, 1d in AS1; 2a, 2c in AS2; 3a in AS3).
  • Internal router: A router that connects only to hosts and routers within its own AS (e.g., 1a, 1b in AS1).

Figure 5.8 / 5.9 Classic 3-AS Topology

Consider three ASs: AS1, AS2, AS3. Each has multiple routers:

  • AS1: Routers 1a, 1b, 1c, 1d (1c = gateway to AS2, 1d = gateway to AS3)
  • AS2: Routers 2a, 2b, 2c (2c = gateway to AS1, 2a = gateway to AS3)
  • AS3: Routers 3a, 3b (3a = gateway to AS2)
Route Advertisement Sequence (AS3 advertises a prefix)
Step 1: 3a (eBGP) → 2c "AS3 x" [AS-PATH: 3]
Step 2: 2c (iBGP) → 2a, 2b "AS3 x" [AS-PATH: 3]
Step 3: 2a (eBGP) → 1c "AS2 AS3 x" [AS-PATH: 2, 3]
Step 4: 2b (eBGP) → 1d "AS2 AS3 x" [AS-PATH: 2, 3]
Step 5: 1c,1d (iBGP) → 1a,1b "AS2 AS3 x" [AS-PATH: 2, 3]
Each eBGP hop prepends the AS number to the message notation. iBGP does not modify AS-PATH. In BGP notation, "AS3 x" means "prefix x is in AS3"; "AS2 AS3 x" means "reach x by passing through AS2 then AS3."
Example 1: Route Propagation Across 3 ASs

Initial setup: AS3 originates prefix 10.3.0.0/16 on router 3a.

  1. 3a → 2c (eBGP): 3a sends UPDATE to 2c with prefix 10.3.0.0/16 and AS-PATH = [3]. NEXT-HOP = 3a's interface IP.
  2. 2c → 2a, 2b (iBGP): 2c floods the route internally. AS-PATH stays [3]. NEXT-HOP stays as 3a's IP.
  3. 2a → 1c (eBGP): 2a prepends AS 2. AS-PATH = [2, 3]. NEXT-HOP = 2a's interface IP to AS1.
  4. 2b → 1d (eBGP): Same prefix, same AS-PATH [2, 3]. NEXT-HOP = 2b's interface IP.
  5. 1c,1d → 1a,1b (iBGP): Internal distribution within AS1. AS-PATH stays [2, 3].

Result: All routers in AS1 know that 10.3.0.0/16 is reachable via AS2 → AS3. Router 1a has two potential next-hops: 1c (via AS2) or 1d (via AS2 as well — actually via AS3 passing through AS2 depending on eBGP peer). The BGP decision process (including hot potato routing) will select one.

Example 2: Two Paths to the Same Destination

AS1 learns about prefix 10.3.0.0/16 from two different entry points:

  • Entry via 1c: AS-PATH = [2, 3], learned from AS2's 2a
  • Entry via 1d: AS-PATH = [2, 3], learned from AS2's 2b

Since both paths have the same AS-PATH length (2), router 1b applies hot potato routing: it picks the entry point closest to itself (lowest IGP cost to NEXT-HOP).

If 1b is closer to 1c (cost 2) than to 1d (cost 10), the route via 1c → 2a → 3a is selected.

Example 3: AS-PATH Loop Prevention in Multi-AS Topology

Four ASs: AS100, AS200, AS300, AS400. AS100 advertises 172.16.0.0/16.

  • AS200 learns from AS100: AS-PATH = [100]
  • AS300 learns from AS200: AS-PATH = [200, 100]
  • AS400 learns from AS300: AS-PATH = [300, 200, 100]

Now, if AS200 also peers with AS400, AS400 advertises the route back to AS200. AS200 receives UPDATE with AS-PATH = [400, 300, 200, 100]. Since AS200 = 200 is in the AS-PATH, the route is rejected.

Without this check, AS200 would re-learn its own route through AS400 → AS300 → AS200, creating a cycle.

BGP UPDATE Message Format

The BGP UPDATE message is used to advertise or withdraw routes. It contains:

  • Withdrawn Routes: Prefixes being removed.
  • Path Attributes: AS-PATH, NEXT-HOP, ORIGIN, LOCAL_PREF, etc.
  • Network Layer Reachability Information (NLRI): The prefixes being advertised.
UPDATE message:
 Withdrawn Routes Length: 0
 Withdrawn Routes: (none)
 Path Attributes:
  ORIGIN: IGP
  AS_PATH: [100, 200]
  NEXT_HOP: 192.0.2.1
 NLRI: 10.1.0.0/16
