IP-Anycast — One IP, Many Servers

Computer Networks — BGP-Based Anycast Routing & Applications

IP-Anycast: Concept

IP-Anycast is a networking technique where the same IP address is assigned to multiple geographically distributed servers. Internet routers use BGP to direct each client to the "closest" server (according to the BGP route selection algorithm). This allows replicating the same content on servers in many different countries while having each user access the content from the nearest server.

IP-Anycast Definition
One IP address ← multiple physical servers in different locations
Client → Routers → "Closest" server (as determined by BGP)
Different clients (or the same client at different times) may reach different servers. The network decides which server handles the request.

Unicast vs. Anycast vs. Multicast vs. Broadcast

Why Use IP-Anycast?

Low Latency

Clients are automatically routed to the nearest server, reducing round-trip times.

Load Distribution

Different clients reach different servers, spreading the load across multiple data centers.

DDoS Resilience

Attack traffic is distributed across many servers. Individual servers see less impact. Attackers cannot target a single IP (it belongs to everyone).

High Availability

If one server fails, BGP withdraws its route. Traffic is automatically redirected to the next-closest server.

IP-anycast is NOT a transport-layer feature — it is an IP/BGP layer feature. The client has no idea it is talking to different servers. The same TCP connection cannot survive being redirected to a different server.

How BGP Implements IP-Anycast

IP-anycast leverages BGP's route selection process to route clients to the nearest server. Here is how it works:

Anycast via BGP — The Mechanism
Step 1: Server A (New York) advertises 192.0.2.0/24 via BGP
Step 2: Server B (Tokyo) advertises 192.0.2.0/24 via BGP
Step 3: Internet routers receive both advertisements
Step 4: Each router selects the "best" route using the 4-rule algorithm
Step 5: Client in London reaches the server that BGP selects as closest
Each server independently originates the same IP prefix. The Internet's BGP routers choose which server to send traffic to based on their local BGP decision.

BGP Route Selection in Anycast

When a router receives two BGP advertisements for the same anycast prefix from different servers, it applies the standard 4-route selection algorithm:

  1. LOCAL_PREF: Usually identical for both (set by the ISP's policy).
  2. AS-PATH: Tends to be shorter for the geographically closer server.
  3. Hot Potato: The exit point closest to the client wins.
  4. Router ID: Tie-breaker if all else is equal.
Anycast Route Selection

A router in London receives two BGP advertisements for 192.0.2.0/24:

  • From Server A (New York): AS-PATH = [AS701, AS1239], NEXT-HOP = 10.1.1.1 (IGP cost = 30)
  • From Server B (Tokyo): AS-PATH = [AS2914, AS1239, AS701], NEXT-HOP = 10.2.2.2 (IGP cost = 120)

Decision: Rule 1 (LOCAL_PREF) ties. Rule 2 (AS-PATH): path to New York = 2, path to Tokyo = 3. New York wins — the client in London reaches the New York server.

BGP does not measure actual geographic distance or real-time latency. It uses BGP attributes (AS-PATH length, IGP cost). The "closest" server by BGP metrics may not be the geographically closest or the one with lowest actual latency.

IP-Anycast Use Cases

1. DNS Root Server System

The DNS root server system is the classic example of IP-anycast. There are only 13 root server IP addresses (a.root-servers.net through m.root-servers.net). Corresponding to each of these IP addresses, there are multiple DNS root servers, with some addresses having over 100 DNS root servers scattered over all corners of the world.

DNS Anycast Statistics
13 Root Server IP Addresses → Over 100 Physical Servers Per Address → 1000+ Total Globally
Each root server IP address is anycasted from dozens to hundreds of locations. For example, the K-root server (operated by RIPE NCC) is deployed in over 50 locations. When a DNS query is sent to one of these 13 IP addresses, IP anycast routes it to the nearest of the DNS root servers responsible for that address [Li 2018].

DNS Anycast Benefits

• Low latency: Each client reaches a nearby root server.

• DDoS resilience: Attack traffic spreads across hundreds of instances.

• High availability: Multiple redundant instances per IP.

Root Server Instances

• A-root: ~200 instances (Verisign)

• K-root: ~50 instances (RIPE NCC)

• L-root: ~190 instances (ICANN)

• M-root: ~200 instances (WIDE Project)

2. Content Delivery Networks (CDNs)

CDNs like Cloudflare, Akamai, and Fastly use IP-anycast to deliver content from thousands of edge servers worldwide. A CDN may replicate videos and other objects on servers in different countries. Figure 5.12 in the textbook illustrates how a CDN uses anycast to serve a user from the nearest data center.

In practice, CDNs generally choose not to use IP-anycast for TCP-based content delivery because BGP routing changes can result in different packets of the same TCP connection arriving at different server instances. IP-anycast is more extensively used by the DNS system (UDP-based) than by CDNs for this reason.
Anycast CDN (Figure 5.12)

A CDN deploys servers at multiple locations (New York, London, Tokyo, Sydney), all advertising the same IP prefix (e.g., 203.0.113.0/24).

  • A user in Berlin reaches the London server (shortest AS-PATH from Berlin to London).
  • A user in Seoul reaches the Tokyo server.
  • If the London server crashes, BGP withdraws its route. Users in Berlin are redirected to the next-closest server (e.g., New York).

CDN Anycast Benefits

• Automatic failover — no DNS TTL delays

• Global load distribution

• Attack mitigation — absorbs DDoS at the edge

CDN Anycast vs DNS-based

DNS-based CDN: Directs clients via DNS resolution (per-request granularity, but slow failover).

Anycast-based: Directs via BGP (fast failover, but less granular).

3. DDoS Mitigation Services

DDoS protection providers (Cloudflare, Akamai Prolexic, AWS Shield) use anycast to scrub attack traffic. When a customer's site is attacked, traffic is redirected to anycast-scrubbing centers that filter malicious packets before forwarding clean traffic to the origin server.

Anycast DDoS Scrubbing
Attack traffic → Anycast IP → Distributed across N scrubbing centers
Each scrubbing center sees 1/N of the attack → Filters → Forwards clean traffic
By spreading the attack across many data centers, anycast makes volumetric DDoS attacks much harder to execute.

Worked Examples: Anycast Routing Decisions

Example 1: DNS Anycast — Client in Brazil Reaching Root Server

Setup: The F-root server IP (192.5.5.241) is anycasted from 200+ locations worldwide. A DNS resolver in Sao Paulo, Brazil, needs to resolve www.example.com.

Anycast decision:

  • F-root instance in Miami: AS-PATH = [AS1239, AS3549] (2 AS hops from Brazil)
  • F-root instance in London: AS-PATH = [AS6762, AS1299, AS1239, AS3549] (4 AS hops)
  • F-root instance in Los Angeles: AS-PATH = [AS6461, AS2914, AS3549] (3 AS hops)

Decision: Rule 1 (LOCAL_PREF) ties (all transit ASs have default). Rule 2 (AS-PATH): Miami (2) < LA (3) < London (4). Miami wins.

Result: The Brazilian resolver queries the F-root server in Miami — the closest instance according to BGP.

The actual DNS resolution takes ~20ms (to Miami) instead of ~120ms (to London).
Example 2: CDN Anycast — Video Streaming

Setup: A video streaming CDN uses anycast IP 203.0.113.1, deployed at three data centers:

  • Ashburn, VA: AS-PATH from client = [AS701, AS1239]
  • Dallas, TX: AS-PATH from client = [AS209, AS1239]
  • San Jose, CA: AS-PATH from client = [AS6461, AS1239]

Client location: The client is in Chicago. IGP costs from the Chicago router to each peer:

  • To Ashburn NEXT-HOP: cost 20
  • To Dallas NEXT-HOP: cost 15
  • To San Jose NEXT-HOP: cost 50

Decision process:

  1. LOCAL_PREF: All = 100 → tie.
  2. AS-PATH: All = 2 → tie.
  3. Hot Potato (Rule 3): Dallas (cost 15) < Ashburn (20) < San Jose (50). Dallas wins.

Result: The client streams from the Dallas data center, which has the lowest IGP cost to the exit point.

Example 3: TCP Connection Issues with Anycast

Setup: A client in Berlin establishes a TCP connection to an anycast IP (192.0.2.1) served by two CDN nodes: London and Frankfurt.

Initial connection: BGP selects the London node (shorter AS-PATH from Berlin at the time). The TCP three-way handshake completes with London.

Mid-session route change: The BGP route to London's prefix is withdrawn (e.g., link failure between Berlin and London). BGP re-converges and now selects the Frankfurt node.

Problem:

  • The client's TCP packets now arrive at the Frankfurt server.
  • Frankfurt has no knowledge of the TCP connection state (sequence numbers, window size, buffers).
  • Frankfurt sends a TCP RST (reset) packet, terminating the connection.

Result: The TCP connection is broken. The client must re-establish a new TCP connection.

TCP connections are stateful — the server maintains per-connection state. Anycast can redirect mid-connection to a new server that lacks this state. This is why anycast works best for stateless protocols (DNS over UDP) or with state-sharing mechanisms between anycast nodes.
Example 4: Anycast DDoS Mitigation in Action

Setup: A website protected by a DDoS mitigation service uses anycast IP 104.16.0.1. The service has scrubbing centers in Los Angeles, Chicago, New York, London, Frankfurt, and Singapore.

Attack scenario: A botnet launches a 500 Gbps DDoS attack from compromised IoT devices worldwide.

Anycast absorption:

  • Attack traffic from Asia hits the Singapore scrubbing center (~150 Gbps).
  • Attack traffic from Europe hits London and Frankfurt (~200 Gbps combined).
  • Attack traffic from the Americas hits LA, Chicago, and New York (~150 Gbps combined).

Each scrubbing center sees only a fraction of the total attack. It filters malicious traffic and forwards only clean traffic to the origin server (which sees only ~1 Gbps of legitimate traffic).

The website remains operational. Without anycast, the origin server's single IP would be overwhelmed by the full 500 Gbps attack.

Example 5: When Anycast Fails — BGP Hijacking

Setup: A legitimate AS (AS 200) advertises anycast prefix 203.0.113.0/24 for a CDN. A malicious AS (AS 666) also advertises the same prefix.

Normal operation:

  • AS 200's route: AS-PATH = [200], originating from legitimate servers.
  • AS 666's route: AS-PATH = [666], originating from hijack servers.

If AS 666's route propagates with a shorter AS-PATH or higher LOCAL_PREF:

  • Traffic destined to 203.0.113.0/24 is routed to AS 666's hijack servers.
  • This is a BGP hijack — the anycast IP is "stolen."

Mitigation: RPKI (Resource Public Key Infrastructure) and BGP filtering prevent unauthorized prefix advertisements.

RPKI Route Origin Authorization (ROA) ensures only AS 200 can legitimately advertise 203.0.113.0/24.
