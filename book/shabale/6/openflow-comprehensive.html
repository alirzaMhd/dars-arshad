OpenFlow Protocol

SDN Southbound Protocol — Match + Action Forwarding for 20/20 Exam

OpenFlow Protocol Overview

OpenFlow [OpenFlow 2009, ONF 2020] is the earliest and most widely deployed southbound protocol for SDN. It operates between an SDN controller and an SDN-controlled switch or device implementing the OpenFlow API.

OpenFlow Transport:
Protocol: TCP
Default Port: 6653
OpenFlow messages are sent over a TCP connection between controller and switch

Match + Action Paradigm

OpenFlow uses a "match + action" abstraction where incoming packets are matched against flow table entries, and matching entries specify what actions to perform.

Flow Table Entry Structure

Header Fields (Match)

• Ingress Port

• Ether src/dst

• Ether type

• VLAN ID / priority

• IP src/dst

• IP protocol

• IP ToS bits

• TCP/UDP src/dst port

Counters

• Per-table: packets, bytes, duration

• Per-flow: packets, bytes, duration

• Per-port: rx/tx packets, rx/tx bytes

• Per-queue: tx packets, tx bytes

Actions

• Forward to port(s)

• Drop the packet

• Modify-field (rewrite headers)

• Send to controller (Packet-In)

• Enqueue to QoS queue

OpenFlow 1.0: 11 Header Fields

OpenFlow 1.0 allows matching on 11 header fields, enabling fine-grained flow classification:

LayerFields
PhysicalIngress Port
L2 (Ethernet)Source MAC, Destination MAC, EtherType, VLAN ID, VLAN Priority
L3 (IP)Source IP, Destination IP, IP Protocol, IP ToS
L4 (TCP/UDP)Source Port, Destination Port
Key Insight: Traditional routers match only on destination IP. OpenFlow matches on 11+ fields, enabling per-flow forwarding decisions based on application, user, or any combination of header values. This is what makes SDN "software-defined."

Flow Table Processing Pipeline

Packet arrives on port → Lookup in flow table (match against entries) → Match found: execute actions (forward, drop, modify, etc.) → No match: send Packet-In to controller → Controller decides and installs flow entry → Subsequent packets match and are forwarded at line rate

The first packet of a flow triggers a controller interaction; subsequent packets are handled entirely in the switch data plane.

Additional OpenFlow messages are defined in [OpenFlow 2009, ONF 2020]. The OpenFlow protocol specification is maintained by the Open Networking Foundation (ONF).

Controller-to-Switch Messages

The SDN controller sends these important message types to the controlled switch:

Four Controller→Switch Message Types:
1. Configuration
2. Modify-State
3. Read-State
4. Send-Packet

1. Configuration Message

Allows the controller to query and set a switch's configuration parameters.

ParameterDescription
Switch capabilitiesQuery what features the switch supports
Flow table configurationSet table miss behavior (send to controller, drop)
Port configurationEnable/disable ports, set rate limits
Datapath IDSet or verify switch identifier

2. Modify-State Message

Used to add, delete, or modify entries in the switch's flow table, and to set switch port properties.

Modify-State Command Types: OFPFC_ADD → Add new flow entry OFPFC_MODIFY → Modify matching flow entry OFPFC_DELETE → Delete matching flow entry Example: Add flow entry (dest IP=10.0.0.0/8 → output port 3) match: {nw_dst: 10.0.0.0/8} actions: [OUTPUT: 3] priority: 100 idle_timeout: 30

Modify-State Sub-commands

• Add — Insert new flow entry

• Modify — Update existing entry

• Delete — Remove entry

• Modify-Strict — Strict match modification

• Delete-Strict — Strict match deletion

Timers on Flow Entries

• idle_timeout — Remove if no match for N seconds

• hard_timeout — Remove after N seconds regardless

• Value 0 = permanent entry

• Expired entries trigger Flow-Removed message

3. Read-State Message

Used by the controller to collect statistics and counter values from the switch's flow table and ports.

Statistics TypeData Returned
Flow statisticsPer-flow: packet count, byte count, duration
Aggregate statisticsAggregated across all flows
Port statisticsPer-port: rx/tx packets, bytes, drops, errors
Queue statisticsPer-queue: tx packets, bytes, drops
Table statisticsPer-table: active entries, matches, lookups

4. Send-Packet Message

Used by the controller to send a specific packet out of a specified port on the controlled switch. The packet itself is contained in the message payload.

Send-Packet: buffer_id: (none - packet in payload) data: [raw packet bytes] actions: [OUTPUT: port_number] in_port: OFPP_CONTROLLER

This is used when the controller itself needs to inject a packet into the network — for example, sending an ARP reply, DHCP offer, or LLDP discovery packet.

Switch-to-Controller Messages

The SDN-controlled switch sends these messages to the controller to report events and deliver unmatched packets:

Three Switch→Controller Message Types:
1. Flow-Removed
2. Port-Status
3. Packet-In

1. Flow-Removed Message

Informs the controller that a flow table entry has been removed, either due to:

  • Timeout — idle_timeout expired (no matching packets) or hard_timeout expired (absolute time elapsed)
  • Controller request — Modify-State delete command
  • Flow eviction — switch resource constraints
Flow-Removed: match: (original match fields) cookie: (opaque controller identifier) priority: 100 reason: OFPRR_IDLE_TIMEOUT duration_sec: 45 idle_timeout: 30 packet_count: 142 byte_count: 18907

The message includes counters so the controller can update its state even after a flow is removed.

2. Port-Status Message

Used by a switch to inform the controller of a change in port status.

ReasonDescription
OFPPR_ADDPort was added (cable plugged, link came up)
OFPPR_DELETEPort was removed (cable unplugged, link down)
OFPPR_MODIFYPort configuration changed (rate, duplex, etc.)

Port-status messages are critical for the controller to maintain an accurate network topology view. They trigger the link-state update mechanism.

3. Packet-In Message

This is one of the most important OpenFlow messages. A packet arriving at a switch port that does not match any flow table entry is sent to the controller for processing.

Packet-In Triggers:
Table miss (no matching flow entry)
Flow entry action = "send to controller"
Flow entry action = "send to controller with buffer"
The controller decides what to do and can install a flow entry for subsequent packets
Important: The Packet-In mechanism is how the controller learns about new flows and installs forwarding rules. The first packet of a flow suffers the controller round-trip delay; subsequent packets are forwarded at wire speed. This is the "slow path" vs. "fast path" tradeoff.

Packet-In Delivery Modes

ModeDescriptionUse Case
Buffer (with buffer_id)Switch buffers the packet, sends only header to controllerDefault; saves bandwidth
No buffer (packet in payload)Entire packet sent to controllerWhen buffer unavailable or packet is small

Message Flow Summary

Controller → Switch: Configuration: "Set your miss-send-length to 128 bytes" Modify-State: "Add flow: TCP 10.0.0.1:80 → 10.0.0.2:1234 → forward port 4" Read-State: "Send me port 3 statistics" Send-Packet: "Send this ARP reply out port 2" Switch → Controller: Flow-Removed: "Flow entry timed out: 142 packets were forwarded" Port-Status: "Port 5 link is DOWN" Packet-In: "New packet, no match found: here's the header, what should I do?"

Worked Examples

Example 1: New Flow Setup (Packet-In → Flow Installation)

Scenario: Host A (10.0.0.1) sends first TCP SYN to Host B (10.0.0.2) through OpenFlow switch s1. No flow entry exists.

Message Exchange:

  1. Host A sends TCP SYN (src=10.0.0.1:4000, dst=10.0.0.2:80) to switch s1 on port 1.
  2. s1 performs flow table lookup — no matching entry → Packet-In message sent to controller.
  3. Packet-In: buffer_id: 256 in_port: 1 data: [TCP SYN: 10.0.0.1:4000→10.0.0.2:80] reason: OFPR_NO_MATCH
  4. Controller's routing app determines path: forward out port 3 to reach Host B.
  5. Controller sends Modify-State (OFPFC_ADD) to install flow entry:
  6. Modify-State ADD: match: in_port=1, nw_src=10.0.0.1, nw_dst=10.0.0.2, tp_src=4000, tp_dst=80, proto=TCP actions: [OUTPUT: 3] priority: 100, idle_timeout: 60
  7. Controller sends Packet-Out with the buffered SYN packet and action [OUTPUT: 3].
  8. Switch forwards the SYN packet out port 3. All subsequent packets in this TCP flow match the new entry and are forwarded at line rate.
Example 2: Link Failure Detection and Recovery

Scenario: Link between switch s2 and s4 fails. The controller must be notified and update flow tables.

Message Exchange:

  1. Switch s2 detects link loss on port 5 (connected to s4).
  2. s2 sends Port-Status message to controller:
  3. Port-Status: reason: OFPPR_DELETE port_no: 5 port_config: 0 state: OFPPS_LINK_DOWN
  4. Controller's link-state manager updates the network graph: link s2-s4 removed.
  5. Routing application (Dijkstra) is notified, recomputes paths.
  6. Controller sends Modify-State DELETE for flow entries using s2→s4.
  7. Controller sends Modify-State ADD for new flow entries with alternate paths.
  8. OLD: match: dst=10.0.0.0/24 → actions: [OUTPUT: 5] (direct to s4) NEW: match: dst=10.0.0.0/24 → actions: [OUTPUT: 3] (via s3→s4)

Result: Traffic is rerouted around the failed link. In SDN, this happens centrally; in traditional networks, OSPF must converge across all routers.

Example 3: Flow Removed Due to Idle Timeout

Scenario: A flow entry for SSH traffic (TCP port 22) between two hosts was installed with idle_timeout=300 seconds (5 minutes). No SSH traffic has been seen for 5 minutes.

Message Exchange:

  1. Switch counts 300 seconds since last packet matched the flow entry.
  2. Switch removes the flow entry from its flow table.
  3. Switch sends Flow-Removed to controller with final statistics:
Flow-Removed: match: nw_src=10.0.0.1, nw_dst=10.0.0.2, tp_dst=22, proto=TCP priority: 100 reason: OFPRR_IDLE_TIMEOUT duration_sec: 784 idle_timeout: 300 packet_count: 14582 byte_count: 21873000

Controller action: The controller records the statistics for billing/accounting purposes. The flow entry is removed from its state database. If a new SSH packet arrives, a new Packet-In → Modify-State cycle begins.

Why timeouts matter: Idle timeout removes unused flow entries, conserving switch TCAM memory (expensive, power-hungry). Hard timeout ensures flows are periodically refreshed, preventing stale entries.

Example 4: Controller-Initiated Packet Injection (Send-Packet)

Scenario: An SDN controller wants to discover network topology using LLDP (Link Layer Discovery Protocol). The controller needs to send LLDP packets out of all switch ports.

Message Exchange:

  1. Controller constructs an LLDP packet with chassis ID = switch dpid, port ID = port number.
  2. For each switch and port, controller sends Send-Packet:
Send-Packet (s1, port 1): buffer_id: OFP_NO_BUFFER data: [LLDP: chassis=00:00:00:00:00:01, port=1] actions: [OUTPUT: 1] in_port: OFPP_CONTROLLER Send-Packet (s1, port 2): data: [LLDP: chassis=00:00:00:00:00:01, port=2] actions: [OUTPUT: 2] in_port: OFPP_CONTROLLER
  1. Neighboring switches receive the LLDP packets. If no flow entry matches, they send Packet-In to controller.
  2. Controller learns: "s1 port 2 → s2 port 3" from the received LLDP, building the network topology.
Example 5: Read-State for Traffic Engineering

Scenario: A traffic engineering application runs every 60 seconds to check link utilization and decide if flows need rerouting.

Message Exchange:

  1. Controller sends Read-State request for port statistics on all switches:
Read-State: type: OFPST_PORT match: (all ports)
  1. Each switch responds with:
Reply (s1): port_no: 3 rx_packets: 45891324 tx_packets: 51234891 rx_bytes: 38917000345 tx_bytes: 41234905123 rx_dropped: 234 tx_dropped: 15 duration_sec: 3600
  1. TE app computes: utilization = (tx_bytes / duration) / link_speed = 41234905123 / 3600 / 1.25e9 ≈ 91.6%. Link is congested!
  2. TE app computes new paths for some flows to balance load.
  3. Controller sends Modify-State to install new flow entries with different paths.

SDN advantage: Centralized visibility enables global traffic engineering impossible in traditional hop-by-hop routing.
