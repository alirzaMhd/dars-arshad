SDN Architecture & Controller

Network Layer — Software-Defined Networking Control Plane for 20/20 Exam

Four Key Characteristics of SDN Architecture

SDN (Software-Defined Networking) represents a fundamental shift in how networks are designed and operated. The following four characteristics define SDN [Kreutz 2015]:

1. Flow-Based Forwarding

Packet forwarding can be based on any combination of transport-layer, network-layer, or link-layer header fields.

OpenFlow 1.0 allows matching on 11 header fields.

Contrasts with traditional routers that forward based only on destination IP.

2. Separation of Planes

Data plane = switches with flow tables executing "match + action".

Control plane = servers + software that compute and manage flow tables.

These are physically separate in SDN.

3. External Control Functions

Control plane software runs on servers remote from switches.

Two components: SDN controller + network-control applications.

Controller maintains network state; apps use APIs to program network.

4. Programmable Network

Network is programmable through software applications.

Apps are the "brains" — routing, access control, load balancing.

Example: routing app runs Dijkstra on controller's link-state DB.

SDN as "Unbundling" of Networks

SDN represents a significant unbundling of network functionality, analogous to the evolution from mainframes (single-vendor hardware + software + apps) to PCs (separate hardware, OS, applications):

AspectTraditional RouterSDN
Data planeIntegrated in routerCommodity switches
Control planeEmbedded in routerSeparate servers
Forwarding logicFixed (destination IP)Programmable (any header)
Vendor lock-inSingle vendorMulti-vendor ecosystem
Innovation speedSlow (hardware cycles)Fast (software updates)
Warning: SDN's "logically centralized" controller is NOT a single physical server. In practice it is a distributed system of multiple servers for fault tolerance and scalability. Do not confuse logical centralization with physical centralization.

SDN Controller: Three Functional Layers

Figure 5.15 shows a generic SDN controller architecture. The controller's functionality is organized into three layers:

Layer 1: Communication Layer (Southbound)

The lowest layer handles communication between the controller and controlled network devices. This crosses the southbound interface.

ProtocolPurposeCharacteristics
OpenFlowFlow table managementMatch + action, default port 6653
SNMPDevice monitoringQuery/response for stats, traps for events
NETCONFDevice configurationYANG data models, XML-based

This layer sends events to the controller (link up/down, device join, heartbeat) providing an up-to-date network view.

Layer 2: Network-Wide State Management Layer

The middle layer maintains distributed state about the network. This is the controller's "database".

State Information Maintained

• Link-state info — status of all links

• Host info — connected hosts and their locations

• Switch info — device capabilities and status

• Statistics — flow table counters, port stats

• Flow tables — installed forwarding rules

Implementation Challenges

• Consistency — maintaining logical time ordering

• Consensus — agreement among controller replicas

• Fault tolerance — surviving server failures

• Scalability — handling increasing network size

Layer 3: Northbound Interface Layer

The top layer provides APIs for network-control applications to interact with the controller.

Northbound API Types:
RESTful API: Request-response over HTTP (JSON/XML)
Intent Framework: Declarative high-level policies
Applications read/write network state, register for event notifications

Applications can:

  • Read/write network state and flow tables
  • Register for state-change event notifications
  • Take actions in response to device events

NOX Controller Comparison

The three-layer SDN controller architecture depicted in Figure 5.15 closely resembles the architecture of the originally proposed NOX controller from 2008 [Gude 2008]. NOX was the first SDN controller and established the component-based architecture that modern controllers such as OpenDaylight and ONOS still follow today. The communication layer, network-wide state management, and northbound API structure originated with NOX.

Data and Control Plane Interaction: Link-State Change

Figure 5.16 illustrates a complete 6-step interaction when a link fails between two SDN-controlled switches. This example uses Dijkstra's algorithm for shortest-path routing implemented as a network-control application.

Key Differences from Traditional Per-Router Control

SDN vs. Traditional per-router control:
1. Dijkstra runs as a separate app outside switches
2. Switches send link updates to controller, not to each other
This centralizes the routing computation and simplifies switch hardware

The 6-Step Interaction (Figure 5.16)

Scenario: Link between switch s1 and s2 goes down. Shortest path routing is implemented. Flows at s1, s3, s4 are affected; s2 unchanged.

Step 1

Switch s1 detects link failure to s2.

Sends OpenFlow port-status message to controller.

Step 2

Controller receives OpenFlow message.

Notifies link-state manager which updates the link-state database.

Step 3

Routing app (Dijkstra's link-state) registered for link-state change events.

Receives notification of the change.

Step 4

Routing app queries updated link-state from manager.

Computes new least-cost paths using Dijkstra's algorithm.

Step 5

Routing app interacts with flow table manager.

Determines which flow tables need updating.

Step 6

Flow table manager uses OpenFlow to update:

• s1: route to s2 via s4 (not direct)

• s4: forward packets from s1 to s2

Important Contrast: In a traditional per-router network, every router runs Dijkstra's algorithm and floods link-state updates to all other routers. In SDN, only the controller runs Dijkstra, and switches send updates only to the controller. This dramatically simplifies switches.

Implications of SDN Control

Since the controller tailors flow tables as it pleases, it can implement any forwarding behavior simply by changing application software. An ISP can easily switch from least-cost routing to a custom approach without updating firmware on every router. In traditional networks, software on all routers (from multiple vendors) must be changed.

Google B4 Case Study

Google's B4 network is a private WAN connecting its data centers worldwide. It is a landmark SDN deployment that drove WAN links to near 70% utilization (2-3x improvement over typical WANs).

SDN: Past and Future

Although intense interest in SDN is recent, the technical roots of data/control plane separation go back considerably further. In 2004, [Feamster 2004, Lakshman 2004, RFC 3746] argued for separation of the network's data and control planes. [van der Merwe 1998] described a control framework for ATM networks with multiple controllers.

The Ethane Project [Casado 2007]

Ethane pioneered the notion of a network of simple flow-based Ethernet switches with match-plus-action flow tables, a centralized controller managing flow admission and routing, and forwarding of unmatched packets from switches to the controller. A network of more than 300 Ethane switches was operational in 2007. Ethane quickly evolved into the OpenFlow project.

Network Functions Virtualization (NFV)

A generalization of SDN known as network functions virtualization (NFV) similarly aims at the disruptive replacement of sophisticated middleboxes (with dedicated hardware and proprietary software for media caching, firewalling, etc.) with simple commodity servers, switching, and storage. While SDN separates the data and control planes of packet forwarding, NFV extends this separation to network functions and middleboxes.

Inter-AS SDN Research

A second area of important research seeks to extend SDN concepts from the intra-AS setting to the inter-AS setting [Gupta 2014]. This would enable policy-driven, programmable control across autonomous system boundaries, potentially transforming how ISPs negotiate and implement inter-domain routing policies.

Worked Examples

Example 1: New Host Join Event

Scenario: A new host with MAC address AA:BB:CC:DD:EE:FF connects to switch s3 on port 5. The SDN controller needs to learn about this host and install forwarding rules.

Step-by-step:

  1. Switch s3 receives a packet from the new host on port 5. No flow table match exists, so s3 sends an OpenFlow Packet-In message to the controller containing the packet.
  2. The controller's communication layer receives the Packet-In and passes it to the host tracker module in the state management layer.
  3. The host tracker updates its database: host AA:BB:CC:DD:EE:FF is reachable via s3, port 5.
  4. The routing application (registered for host events) receives notification. It computes paths to the new host from all other switches.
  5. The routing app instructs the flow table manager to install forwarding rules on switches s1, s2, s3, s4 pointing to the new host via s3.
  6. The controller sends OpenFlow Modify-State messages to install flow entries: "If dest MAC = AA:BB:CC:DD:EE:FF, forward to s3's port 5".
Packet-In (s3, port 5, src=AA:BB:CC:DD:EE:FF) → Host Tracker updates DB → Routing App computes paths → Modify-State (s1: dest=AA:BB:CC:DD:EE:FF → out s3) → Modify-State (s2: dest=AA:BB:CC:DD:EE:FF → out s3) → Modify-State (s4: dest=AA:BB:CC:DD:EE:FF → out s3)
Example 2: Traffic Engineering with Flow Priorities

Scenario: A network has two paths between s1 and s4: direct (10 Gbps, high latency) and via s2-s3 (1 Gbps, low latency). The controller wants video traffic on the high-bandwidth path and interactive traffic on the low-latency path.

Solution using SDN:

Flow Entry 1 (high priority): Match: dest IP=10.0.0.0/24, protocol=UDP, port=554 (RTSP) Action: output port 3 (direct to s4) Priority: 100 Flow Entry 2 (low priority): Match: dest IP=10.0.0.0/24 Action: output port 2 (via s2-s3) Priority: 1

Result: Video traffic follows the high-bandwidth path; all other traffic uses the low-latency path. This fine-grained control is impossible in traditional destination-only forwarding.

SDN advantage: The traffic engineering app simply installs different flow entries. No router configuration changes needed — just a software update to the app.

Example 3: Distributed Firewall with SDN

Scenario: An enterprise wants to block all SSH traffic (TCP port 22) from the guest network (10.0.100.0/24) to the server farm (10.0.200.0/24), while allowing all other traffic.

Traditional approach: Configure ACLs on every router along the path. Error-prone and difficult to maintain.

SDN approach: The access control application installs a single flow entry at the edge switch connecting guest to core:

Flow Entry (block SSH): Match: in_port=guest, src=10.0.100.0/24, dst=10.0.200.0/24, TCP, dst_port=22 Action: drop Priority: 100 Flow Entry (allow all): Match: in_port=guest, dst=10.0.200.0/24 Action: normal forwarding Priority: 1

Result: SSH traffic is dropped at the edge switch. If the policy changes (e.g., allow SSH from engineering subnet), the access control app updates the flow entry — instant policy change across the entire network.

Example 4: B4-Style Application-Aware Routing

Scenario: An SDN-controlled WAN connects 4 data centers. Three traffic classes exist: bulk replication (elastic, can wait), user-facing (latency-sensitive), and control (must get through). Links are near capacity.

Solution (B4-inspired):

Traffic ClassPriorityBandwidth GuaranteeAction under Congestion
ControlHighest10% minimumAlways forwarded
User-facingMedium60% fair shareUses shortest path
Bulk replicationLowBest effort (elastic)Deferred, uses alternate paths

Result: WAN links achieve ~70% utilization (vs. typical 30-40%) because the traffic engineering app can fill leftover capacity with bulk traffic and preempt it when higher-priority traffic appears.

Example 5: Controller Failure Recovery

Scenario: A 5-server distributed SDN controller cluster experiences one server failure. Switches are connected to multiple controller instances.

What happens:

  1. Switch detects loss of OpenFlow connection to failed controller via heartbeat timeout.
  2. Switch establishes connection to another controller instance (pre-configured backup).
  3. Remaining controller instances use Paxos (or similar consensus protocol) to agree on the current network state.
  4. The failed server's state is recovered from replicas in the distributed state management layer.
  5. Ongoing flow operations continue uninterrupted because flow tables are stored in switches.

Key insight: SDN's distributed core provides fault tolerance. The switch's flow table is the "cache" — if controller is temporarily unavailable, switches continue forwarding based on existing entries.
