ICMP Protocol

Internet Control Message Protocol — Network Management Guide

ICMP Overview

The Internet Control Message Protocol (ICMP) is a core protocol in the Internet protocol suite. It is used by network devices, including routers, to send error messages and operational information indicating success or failure when communicating with another IP address.

Key Facts:
ICMP is part of IP • Protocol Number: 1
ICMP messages are carried inside IP datagrams (encapsulated, not layered above)

Encapsulation

ICMP messages are carried in IP datagrams

IP header protocol field = 1

Purpose

Error reporting & diagnostic functions

Not for reliable data transport

ICMPv4 vs ICMPv6

ICMPv6 includes Packet Too Big

Handles unrecognized options

Important: ICMP does not make IP reliable. It only reports errors — the higher-layer protocol (e.g., TCP) must handle recovery.

ICMP Message Format

OffsetFieldSizeDescription
0Type1 byteIdentifies the ICMP message type
1Code1 byteFurther qualifies the message type
2-3Checksum2 bytesChecksum covering the ICMP message
4+Rest of HeaderVariableDepends on type/code; often includes first 8 bytes of offending datagram

For error-reporting messages, the ICMP payload includes the first 8 bytes of the offending IP datagram (IP header + first 8 bytes of transport header) to help the sender identify which packet caused the error.

• Parameter Problem (12/0)

Always include first 8 bytes of offending datagram

Warning: Source Quench (Type 4) is seldom used in practice. Its original purpose was congestion control, but TCP has its own congestion-control mechanism at the transport layer, and Explicit Congestion Notification (ECN) bits can signal congestion at the network layer.

ICMP Error Message Rules

ICMP error messages are never generated in response to:

  • Another ICMP error message (prevets infinite loops)
  • IP broadcast or multicast datagrams
  • Datagrams with a source address that is not a unicast address
  • Fragments other than the first fragment

Ping

Ping uses ICMP Echo Request and Echo Reply messages to test reachability and measure round-trip time.

Ping Mechanism:
Host A sends ICMP Type 8, Code 0 → Host B replies ICMP Type 0, Code 0
Round-trip time = time between request and reply

Implementation

The ping server is implemented directly in the operating system kernel, not as a user-level process

The client program instructs the OS to generate ICMP Type 8 Code 0 messages

Request

Type: 8

Code: 0

Includes identifier + sequence number

Reply

Type: 0

Code: 0

Echoes back the payload data

Output Fields

TTL — remaining hop count

time — RTT in ms

Packet loss percentage

Ping Output Example
$ ping -c 4 8.8.8.8
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=118 time=12.3 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=118 time=11.8 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=118 time=12.1 ms
64 bytes from 8.8.8.8: icmp_seq=4 ttl=118 time=11.9 ms

--- 8.8.8.8 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
rtt min/avg/max/mdev = 11.827/12.025/12.300/0.176 ms

The host sends ICMP Echo Request (8/0) and receives Echo Reply (0/0). TTL = 118 means the packet has traversed 256 - 118 = 138 hops (or 64 - 48 = 16 depending on initial TTL).

Traceroute

Traceroute maps the path packets take from source to destination by exploiting the TTL field.

Traceroute Mechanism:
Send packets with incrementing TTL (1, 2, 3, ...) to an unlikely UDP port
Each router decrements TTL; when TTL=0, router sends ICMP Time Exceeded (11/0). Standard traceroute sends 3 packets per TTL value, providing 3 RTT measurements per hop.
StepTTLActionICMP Response
11First router decrements TTL → 0, drops packetTime Exceeded (11/0) from Router 1
22Router 1 forwards, Router 2 decrements TTL → 0Time Exceeded (11/0) from Router 2
33Reaches destination, but port is unusedPort Unreachable (3/3) from Destination

UDP Method

Packets sent to unlikely high UDP port

Destination replies with Port Unreachable (3/3)

Traceroute knows it reached the destination

ICMP Method

Some implementations use ICMP Echo Request

Destination replies with Echo Reply (0/0)

TCP Method

Uses SYN packets to port 80

Destination replies with SYN/ACK

Useful when firewalls block ICMP

Note: Many routers and firewalls are configured to not send ICMP Time Exceeded messages, causing traceroute to show "* * *" for those hops.

Worked Examples

Example 1: Using Ping to Test Reachability

Scenario: A network administrator needs to verify that a remote server at 203.0.113.50 is reachable and measure response time.

$ ping -c 5 203.0.113.50
PING 203.0.113.50 (203.0.113.50) 56(84) bytes of data.
64 bytes from 203.0.113.50: icmp_seq=1 ttl=64 time=45.2 ms
64 bytes from 203.0.113.50: icmp_seq=2 ttl=64 time=44.8 ms
64 bytes from 203.0.113.50: icmp_seq=3 ttl=64 time=46.1 ms
64 bytes from 203.0.113.50: icmp_seq=4 ttl=64 time=45.5 ms
64 bytes from 203.0.113.50: icmp_seq=5 ttl=64 time=44.9 ms

--- 203.0.113.50 ping statistics ---
5 packets transmitted, 5 received, 0% packet loss, time 4005ms
rtt min/avg/max/mdev = 44.800/45.300/46.100/0.504 ms

Analysis:

  • 0% packet loss — all packets reached the destination and replies returned
  • Average RTT: 45.3 ms — acceptable for a remote server
  • TTL = 64 suggests the destination host is using a default initial TTL of 64 (common for Linux systems) and is directly reachable
  • Low mdev (0.504 ms) indicates stable network path with minimal jitter
Example 2: Analyzing Traceroute Output

Scenario: Users report slow connections to a web server at 198.51.100.20. The administrator runs traceroute to find the bottleneck.

$ traceroute 198.51.100.20
traceroute to 198.51.100.20 (198.51.100.20), 30 hops max
1 10.0.0.1 (10.0.0.1) 0.5 ms 0.4 ms 0.4 ms
2 172.16.1.1 (172.16.1.1) 2.1 ms 2.0 ms 2.0 ms
3 192.168.20.1 (192.168.20.1) 15.3 ms 15.1 ms 15.2 ms
4 203.0.113.1 (203.0.113.1) 45.8 ms 125.3 ms 46.1 ms
5 198.51.100.20 (198.51.100.20) 48.2 ms 48.0 ms 48.1 ms

Analysis:

  • Hop 4 shows significant variation: one packet took 125.3 ms vs ~46 ms for others — this indicates congestion or a slow router
  • The bottleneck is at hop 4 (203.0.113.1), likely an ISP aggregation router under load
  • End-to-end latency: ~48 ms — reasonable for a remote server
  • Recommendation: Investigate the router at 203.0.113.1 for congestion or check if an alternative path is available
Example 3: ICMP Error Scenario — Fragmentation Needed

Scenario: A host sends a 2000-byte packet to a destination across a link with MTU 1500. The DF (Don't Fragment) flag is set. The router responds with an ICMP error.

ICMP Message Generated:
Type: 3 • Code: 4 • Destination Unreachable (Fragmentation Needed but DF Set)
The router includes the first 8 bytes of the offending datagram (IP header + TCP/UDP header start)

Sequence of Events:

  1. Host sends IP datagram with total length 2000, DF=1
  2. Router receives datagram, needs to forward over link with MTU 1500
  3. Router cannot fragment (DF=1) and cannot forward the oversized packet
  4. Router generates ICMP Type 3, Code 4 and includes next-hop MTU in the message
  5. Host receives ICMP error and caches the reduced MTU for that destination (Path MTU Discovery)
  6. Host retransmits with smaller packet size (≤ 1500 bytes)

This is the foundation of Path MTU Discovery (PMTUD), which relies on ICMP to dynamically determine the maximum packet size that can traverse the path without fragmentation.

Example 4: ICMP Redirect Attack (Security)

Scenario: An attacker sends a fake ICMP Redirect message to redirect traffic through their machine.

Attacker sends: ICMP Type 5, Code 1 (Host Redirect)
Source IP: spoofed as the gateway (192.168.1.1)
Target IP: victim host (192.168.1.100)
New Gateway: attacker's IP (192.168.1.200)
Included: first 8 bytes of the offending datagram (to match existing flow)

Defense:

  • Modern OSes ignore ICMP Redirect messages by default
  • Routers only send redirects for traffic actually forwarded by them
  • Use IPsec to authenticate ICMP messages
  • Disable ICMP redirect acceptance: sysctl net.ipv4.conf.all.accept_redirects=0
Example 5: ICMPv6 Packet Too Big — Path MTU Discovery

Scenario: An IPv6 host sends a 2000-byte packet. An intermediate link has MTU 1280. Since IPv6 routers do not fragment, the router sends ICMPv6 Packet Too Big.

ICMPv6 Message:
ICMPv6 Type: 2 • Code: 0 • Packet Too Big
Includes the MTU of the constricting link (1280 bytes) in the message body
