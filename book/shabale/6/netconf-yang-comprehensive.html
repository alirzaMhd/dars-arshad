NETCONF & YANG

Network Configuration Protocol & Data Modeling Language

NETCONF Overview

NETCONF (Network Configuration Protocol) is an IETF-standardized protocol for installing, manipulating, and deleting the configuration of network devices. It uses an RPC paradigm with XML-encoded messages over a secure, connection-oriented session such as TLS (Transport Layer Security) over TCP.

NETCONF Stack:
Transport: TCP/TLS/SSH • Encoding: XML • Paradigm: RPC
IETF RFC 6241 — replaces SNMP for configuration management

Transport Layer

SSH (RFC 6242) — most common

TLS (RFC 7589) — Transport Layer Security over TCP

TCP (raw, RFC 5539)

Connection-oriented & reliable

Key Features

Transactional — commit/rollback

Candidate config — edit without impact

Filtering — subtree, XPath

Notifications — event streaming

Multi-device atomic transactions [RFC 3535] — operations that complete atomically across a set of devices or are fully reversed

vs SNMP

TCP vs UDP

XML vs BER/DER

RPC vs Get/Set

Transactional vs atomic

NETCONF Session Flow (Figure 5.22)

Client (NMS) Server (Device)
| |
|--- <hello> (capabilities) -----------> |
|<--- <hello> (capabilities) ------------| Session Establishment
| |
|--- <rpc> (<get-config/>) ------------> |
|<--- <rpc-reply> (data) ---------------| RPC Exchange
| |
|--- <rpc> (<edit-config>) -----------> |
|<--- <rpc-reply> (<ok/>) -------------| Configuration Change
| |
|<--- <notification> (event) -----------| Async Notification
| |
|--- <rpc> (<close-session/>) --------> |
|<--- <rpc-reply> (<ok/>) -------------| Session Close
PhaseDirectionMessagePurpose
1. HelloBoth<hello>Exchange capabilities (YANG modules, NETCONF versions)
2. RPCClient → Server<rpc>Invoke operation with parameters
3. ReplyServer → Client<rpc-reply>Return data or <ok/> on success, <rpc-error> on failure
4. NotificationServer → Client<notification>Asynchronous event (requires create-subscription)
5. CloseClient → Server<close-session>Terminate the NETCONF session
Key Point: NETCONF uses a capability exchange during the <hello> phase. The client and server each advertise which YANG modules and protocol capabilities they support. Operations not supported by both sides cannot be used.

NETCONF Operations (Table 5.3)

NETCONF defines a set of base operations that form the foundation of device management. These operations can be composed into sophisticated multi-device transactions that either complete atomically and successfully, or are fully reversed — leaving devices in their pre-transaction state. This "network as a whole" approach was an important operator requirement from [RFC 3535].

OperationDescriptionInputOutput
get-configRetrieve all or part of a configuration datastoresource, filterXML config data
getRetrieve both configuration and state datafilterXML config + state data
edit-configModify a configuration datastoretarget, config, operation<ok/> or <rpc-error>; on error, config can be rolled back to previous state
lockLock a configuration datastore (prevent concurrent edits)target<ok/> or lock-denied error
unlockRelease a previously acquired locktarget<ok/>
create-subscriptionSubscribe to event notificationsstream, filterNotification stream starts
notification(Server side) Send an event notificationevent dataN/A (async)
close-sessionGracefully close the NETCONF sessionNone<ok/>
kill-sessionForcefully terminate another sessionsession-id<ok/>

XML Message Examples from the Textbook

<get/> Command — Retrieve Full Device State
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get/>
</rpc>

The <get/> operation returns both configuration and operational state data from the device.

<edit-config> — Setting MTU on an Interface
<rpc message-id="102" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><running/></target>
    <config>
      <top xmlns="http://example.com/ns/example">
        <interfaces>
          <interface>
            <name>GigabitEthernet0/1</name>
            <mtu>1500</mtu>
          </interface>
        </interfaces>
      </top>
    </config>
  </edit-config>
</rpc>

The default operation is merge (creates if not exist, updates if exists). Other operations: replace, create, delete, remove.

<rpc-reply> — Successful Response
<rpc-reply message-id="102" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <ok/>
</rpc-reply>

An <ok/> element indicates the operation completed successfully. Error responses include <rpc-error> with error-type, error-tag, and error-message.

Edit Operations:
merge • replace • create • delete • remove
Specified via the 'operation' attribute on configuration elements

Operation Semantics

merge — create or update

replace — replace existing

create — fail if exists

delete — fail if missing

remove — delete if exists

Configuration Stores

<candidate> — edit without affecting running config

<running> — currently active config

<commit> — copy candidate → running

<discard-changes> — revert candidate

YANG Data Modeling Language

YANG (Yet Another Next Generation) is the data modeling language for NETCONF. It defines the structure, constraints, and semantics of configuration and state data. Similar to SMI for SNMP, but built for NETCONF's XML-based world.

YANG Purpose:
Define data models for NETCONF configuration and operational state
YANG modules define the structure, types, and constraints of data exchanged via NETCONF

YANG Module Structure

module example-interface {
  yang-version 1.1;
  namespace "http://example.com/ns/example-interface";
  prefix exif;

  import ietf-yang-types { prefix yang; }
  import ietf-inet-types { prefix inet; }

  container interfaces {
    list interface {
      key "name";
      leaf name {
        type string;
      }
      leaf description {
        type string;
      }
      leaf mtu {
        type uint16 {
          range "68..9216";
        }
        default 1500;
      }
      leaf enabled {
        type boolean;
        default true;
      }
    }
  }
}

YANG Constraints

Range

type uint16 { range "68..9216"; }

Valid values: 68 through 9216

Length

type string { length "1..255"; }

String length: 1 to 255 chars

Pattern

type string { pattern "[0-9a-fA-F]*"; }

Regex constraint on string

Mandatory

leaf name { mandatory true; }

Must be present in data

Key Point: YANG allows data modelers to express constraints that configurations must satisfy (range, length, pattern, mandatory). This is a powerful aid in ensuring NETCONF configurations satisfy specified correctness and consistency constraints. YANG is also used to specify NETCONF notifications.

Worked Examples

Example 1: Configuration Retrieval with <get-config>

Scenario: An NMS wants to retrieve the current interface configuration from a device to build an inventory.

<rpc message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
    <filter type="subtree">
      <interfaces xmlns="http://example.com/ns/example-interface">
        <interface>
          <name/>
          <mtu/>
        </interface>
      </interfaces>
    </filter>
  </get-config>
</rpc>

Response:

<rpc-reply message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <data>
    <interfaces xmlns="http://example.com/ns/example-interface">
      <interface>
        <name>GigabitEthernet0/0</name>
        <mtu>1500</mtu>
      </interface>
      <interface>
        <name>GigabitEthernet0/1</name>
        <mtu>9000</mtu>
      </interface>
    </interfaces>
  </data>
</rpc-reply>

Analysis:

  • The subtree filter limits the response to only the <name> and <mtu> of each interface
  • Interface GigabitEthernet0/1 has MTU 9000 (jumbo frames enabled) — the NMS flags this for the inventory
  • The response is wrapped in <data> to distinguish configuration from operational state
Example 2: Interface Configuration with <edit-config>

Scenario: An administrator configures a new VLAN interface on a switch. The configuration must be applied atomically.

<rpc message-id="202" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><candidate/></target>
    <config>
      <interfaces xmlns="http://example.com/ns/example-interface">
        <interface operation="create">
          <name>Vlan100</name>
          <description>Management VLAN</description>
          <mtu>1500</mtu>
          <ipv4 xmlns="http://example.com/ns/example-ip">
            <address>
              <ip>192.168.100.1</ip>
              <prefix-length>24</prefix-length>
            </address>
          </ipv4>
        </interface>
      </interfaces>
    </config>
  </edit-config>
</rpc>
# Commit the candidate configuration
<rpc message-id="203" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit/>
</rpc>
<rpc-reply message-id="203" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <ok/>
</rpc-reply>

Analysis:

  • The edit is performed on the <candidate> config — no impact on the running device
  • The operation="create" ensures the interface doesn't already exist (fail if duplicate)
  • <commit/> atomically applies all changes — if any validation fails, the entire transaction is rolled back
  • If the configuration has errors, the device returns <rpc-error> and the candidate config is unchanged
Example 3: Device Capability Discovery via <hello>

Scenario: An NMS connects to a new device and discovers its capabilities through the NETCONF <hello> exchange.

# NMS sends its capabilities
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:writable-running:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:candidate:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:validate:1.0</capability>
    <capability>http://example.com/ns/example-interface?module=example-interface&amp;revision=2024-01-01</capability>
  </capabilities>
</hello>
# Device responds with its capabilities
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:candidate:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:rollback-on-error:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:notification:1.0</capability>
    <capability>http://example.com/ns/example-interface?module=example-interface&amp;revision=2024-01-01</capability>
    <capability>http://example.com/ns/example-routing?module=example-routing&amp;revision=2024-03-01</capability>
  </capabilities>
</hello>

Analysis:

  • Both sides support NETCONF 1.1 (base:1.1) — enables interleaved RPCs and chunked framing
  • The device supports candidate but not writable-running — the NMS should use candidate/commit pattern
  • The device supports rollback-on-error — if a configuration change fails, the device automatically rolls back
  • The device supports notification — the NMS can subscribe to event streams
  • YANG modules advertised: example-interface + example-routing — the NMS knows exactly which data models the device supports
Example 4: Transactional Commit with Validation

Scenario: An administrator applies multiple changes to the candidate config, validates them, then commits. One change fails validation, causing the transaction to abort.

# Step 1: Lock the candidate datastore
<rpc message-id="301"><lock><target><candidate/></target></lock></rpc>
<rpc-reply message-id="301"><ok/></rpc-reply>

# Step 2: Apply config changes to candidate
<rpc message-id="302"><edit-config><target><candidate/></target>...</edit-config></rpc>
<rpc-reply message-id="302"><ok/></rpc-reply>

# Step 3: Validate the candidate configuration
<rpc message-id="303"><validate><source><candidate/></source></validate></rpc>
<rpc-reply message-id="303">
  <rpc-error>
    <error-type>application</error-type>
    <error-tag>bad-element</error-tag>
    <error-severity>error</error-severity>
    <error-message>MTU value 10000 exceeds maximum 9216</error-message>
    <error-info>
      <bad-element>mtu</bad-element>
    </error-info>
  </rpc-error>
</rpc-reply>

# Step 4: Discard the failed changes and unlock
<rpc message-id="304"><discard-changes/></rpc>
<rpc-reply message-id="304"><ok/></rpc-reply>
<rpc message-id="305"><unlock><target><candidate/></target></unlock></rpc>
<rpc-reply message-id="305"><ok/></rpc-reply>

Key takeaway: NETCONF's transactional model (candidate → validate → commit) prevents misconfigurations from ever reaching the running device. This is a fundamental advantage over SNMP, where a Set operation can immediately damage connectivity.

Example 5: Event Notification — Link State Change

Scenario: The NMS subscribes to interface state change notifications. When a link goes down, the device sends a notification.

# Step 1: Subscribe to notifications
<rpc message-id="401" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <create-subscription xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">
    <stream>interface-state</stream>
  </create-subscription>
</rpc>
# Step 2: Device sends notification asynchronously
<notification xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">
  <eventTime>2024-10-15T14:30:00Z</eventTime>
  <interface-state-change xmlns="http://example.com/ns/example-interface">
    <name>GigabitEthernet0/1</name>
    <admin-status>up</admin-status>
    <oper-status>down</oper-status>
    <reason>link-failure</reason>
  </interface-state-change>
</notification>

NETCONF notifications are asynchronous — the NMS receives them in real time after subscribing. Unlike SNMP traps, notifications are delivered over the same TCP session, providing reliable, in-order delivery.
