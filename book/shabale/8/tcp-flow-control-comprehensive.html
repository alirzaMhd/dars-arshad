TCP Flow Control

Computer Networking — Comprehensive Guide for 20/20 Exam

Flow Control Basics

Flow control is a speed-matching service — it prevents the sender from overflowing the receiver's buffer.

⚠ Important Distinction: Flow control ≠ Congestion control. Flow control prevents sender from overwhelming receiver (receive buffer). Congestion control prevents sender from overwhelming the network (router buffers).

The Receive Buffer

LastByteRead

Last byte in stream read by the application from the buffer.

LastByteRcvd

Last byte in stream that has arrived from the network and been placed in the buffer.

RcvBuffer

Total size of the receive buffer allocated for the connection.

Buffer Overflow Constraint
LastByteRcvd - LastByteRead ≤ RcvBuffer
The amount of unread data in the buffer must not exceed the buffer capacity.

The application reads data from the buffer at its own pace. If the sender sends faster than the application reads, the buffer fills up. Flow control prevents this overflow.

⚠ Key Assumption: Throughout this discussion we assume the TCP receiver discards out-of-order segments. Modern TCP implementations often buffer out-of-order data, but for understanding flow control fundamentals, we assume out-of-order segments are discarded.

The Receive Window (rwnd) Mechanism

Definition

Receive Window (rwnd)
rwnd = RcvBuffer - (LastByteRcvd - LastByteRead)
Amount of free space in the receive buffer. Dynamic — changes as data arrives and the application reads.
Sender Constraint
LastByteSent - LastByteAcked ≤ rwnd
The amount of unacknowledged data must not exceed the receiver's advertised window.

How It Works

1. Host B places its current rwnd value in the Receive Window field of every segment it sends to A.

2. Initially, Host B sets rwnd = RcvBuffer.

3. Host A tracks two variables:

LastByteSent

Last byte sent into the connection.

LastByteAcked

Last byte acknowledged.

4. Host A ensures: LastByteSent - LastByteAcked ≤ rwnd

The variable rwnd = RcvBuffer - (LastByteRcvd - LastByteRead). As the application reads data, LastByteRead advances and rwnd grows. As new data arrives, LastByteRcvd advances and rwnd shrinks.

Because TCP is full-duplex, the sender at each side of the connection maintains a distinct receive window. Host A tracks its own rwnd (for incoming data) and also respects the rwnd advertised by Host B (for outgoing data).

// Sender-side flow control check if ((NextSeqNum - SendBase) < rwnd_received) { // OK to send new segment send segment; } else { // Must wait — receiver's buffer is full buffer data for later; }
⚠ Common Mistake: The "receive window" field in the TCP header carries the sender's receive window (the receiver's free buffer space). Each side advertises its own rwnd to the other.

Zero Window Problem

The Problem

If Host B's receive buffer becomes full, it advertises rwnd = 0. Host A stops sending data. But what if B has no data to send to A?

B cannot send a segment just to advertise a new rwnd value — TCP only sends segments when there is data to send or an ACK to return.

If B's application empties the buffer, B has nothing to send A, so A never learns about the newly freed space. Deadlock!

The Solution: 1-Byte Probe Segments

TCP Specification Rule

When rwnd = 0, the sender must continue sending segments with 1 data byte.

Receiver's Response

The receiver acknowledges these 1-byte probes, and the ACK carries the updated rwnd value (now > 0).

Why UDP Has No Flow Control

UDP provides no flow control. For a typical UDP implementation, UDP appends the segments to a finite-sized buffer that precedes the corresponding socket. The process reads one entire segment at a time from the buffer. If the process does not read fast enough, the buffer overflows and segments are dropped.

// Zero-window probe mechanism if (rwnd == 0) { // Send 1-byte probe segments periodically send segment with 1 byte of new data; // The ACK response will carry updated rwnd }
⚠ Common Mistake: The 1-byte probe is not a retransmission — it's a new data byte sent specifically to elicit an ACK with fresh rwnd information.

Worked Examples & Comparison

Example 1: Basic Buffer Calculation

Setup: RcvBuffer = 4096 bytes. Application reads 500 bytes/sec. Sender sends at 1000 bytes/sec.

Initial state: LastByteRcvd = 0, LastByteRead = 0, rwnd = 4096.

After 1 second: LastByteRcvd = 1000 (sender sent 1000 bytes), LastByteRead = 500 (app read 500).

Unread data = 1000 - 500 = 500 bytes.

rwnd = 4096 - 500 = 3596 bytes.

After 5 seconds: LastByteRcvd = 5000, LastByteRead = 2500.

Unread data = 5000 - 2500 = 2500 bytes.

rwnd = 4096 - 2500 = 1596 bytes.

After 8 seconds: LastByteRcvd = 8000, LastByteRead = 4000.

Unread data = 8000 - 4000 = 4000 bytes.

rwnd = 4096 - 4000 = 96 bytes (buffer nearly full).

After ~8.2 seconds: rwnd reaches 0. Sender must stop (or send 1-byte probes).

Example 3: Zero Window and Probe Recovery

Setup: RcvBuffer = 2048 bytes. Initially empty.

Phase 1 — Buffer fills: Sender sends 2048 bytes quickly. LastByteRcvd=2048. App hasn't read yet. rwnd=0.

Phase 2 — Stuck: Sender cannot send more data. B has no data to send to A.

Phase 3 — Probe: A sends a 1-byte probe (seq=2049). B ACKs it (ack=2050, rwnd=0 still).

Phase 4 — App reads: Application reads 1024 bytes. LastByteRead = 1024. rwnd = 2048 - 1024 = 1024.

Phase 5 — ACK with new rwnd: B sends ACK=2049 (for the probe) with rwnd=1024.

Phase 6 — Resume: A resumes sending (up to 1024 unacknowledged bytes).

The 1-byte probe mechanism is essential to break the zero-window deadlock.

FeatureFlow ControlCongestion Control
PurposePrevent receiver buffer overflowPrevent network overload
Constrained byReceiver's rwndNetwork's cwnd (congestion window)
ScopeEnd-to-end (sender ↔ receiver)Network-wide (all senders sharing links)
SignalExplicit: rwnd in TCP headerImplicit: loss / delay / ECN
