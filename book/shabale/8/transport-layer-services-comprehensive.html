Transport Layer Services Overview

The transport layer provides logical communication between application processes running on different hosts. It extends the network layer's host-to-host delivery into process-to-process delivery. Transport protocols can offer different service models to applications.

Household Analogy: Different Service Models

Ann and Bill are responsible cousins: they pick up and drop off mail frequently, never lose letters. They provide reliable service.

Susan and Harvey are younger cousins: they pick up and drop off mail less frequently, occasionally lose letters (sometimes chewed by the family dog). They provide an unreliable service model.

Just as different cousin pairs provide different service levels, different transport protocols (TCP vs UDP) offer different service models to applications. The services they can provide are constrained by the underlying "postal service" (network layer).

Key Principle:
Transport Service = f(Network Layer Constraints, Protocol Design)
Transport services are constrained by the network layer below, but can add capabilities (e.g., reliability over unreliable IP)

Possible Transport Services

Reliable Data Transfer

Guarantees delivery without errors, in order, with no duplicates

Provided by: TCP

Delay Guarantees

Bounds on end-to-end delivery time

Constrained by network layer

Bandwidth Guarantees

Minimum throughput assurance

Constrained by network layer

Security

Encryption, data confidentiality

Added at transport (e.g., TLS)

Relationship with Network Layer

The services a transport protocol can provide are often constrained by the service model of the underlying network-layer protocol. If the network layer cannot provide delay or bandwidth guarantees, neither can the transport layer for those specific guarantees.

However, transport can offer services the network layer does not:

  • Reliable transfer over unreliable IP (checksums, ACKs, timers)
  • Encryption even when network layer lacks confidentiality
  • In-order delivery even with out-of-order IP delivery
Just because a transport protocol CAN provide a service doesn't mean it always does. UDP provides NO reliability, even though TCP does — the choice depends on the application's needs.

Internet Transport Protocols: UDP vs TCP Overview

The Internet makes two distinct transport-layer protocols available: UDP (User Datagram Protocol) and TCP (Transmission Control Protocol). Both run on top of IP, which provides best-effort service — no guarantees on delivery, order, or integrity.

IP Service Model:
Best-Effort Delivery — No Guarantees
IP does not guarantee delivery, orderly delivery, or data integrity

• Reliable data transfer

• Flow control

• Congestion control

• In-order delivery

How TCP Achieves Reliability

TCP converts IP's unreliable service into reliable data transport using four key techniques:

Flow Control

Prevents sender from overwhelming receiver's buffer

Sequence Numbers

Number bytes (not packets) to detect loss, reorder, duplicates

Acknowledgments

Cumulative ACKs tell sender what has been received

Timers

Timeout triggers retransmission of lost segments

TCP Congestion Control — For the Common Good

TCP congestion control prevents any one connection from swamping routers with excessive traffic. It strives to give each connection traversing a congested link an equal share of the link bandwidth. Unlike UDP (which is unregulated), TCP's sending rate is governed by detected congestion.

UDP traffic is unregulated. An application using UDP can send at any rate, for as long as it pleases. This can crowd out TCP sessions and cause network congestion collapse.

Chapter Approach

This chapter alternates between basic principles and the TCP protocol. We first discuss reliable data transfer in a general setting (rdt protocols), then examine how TCP specifically implements it. Similarly, we cover congestion control principles, then TCP's specific mechanisms.

Terminology Note

We refer to transport-layer packets as segments for both TCP and UDP. However, Internet RFCs often call UDP packets datagrams (and reserve "datagram" for the network-layer packet too). For clarity, this guide uses "segment" for both transport protocols.

Worked Examples: TCP vs UDP Scenarios

Example 1: Web Browsing

Scenario: A user wants to download a webpage with text content, images, and CSS files. Reliability is critical — a corrupted character could break the layout.

Analysis: Web browsing requires reliable, ordered delivery of all page elements. Lost data would result in broken pages.

Choice: TCP — HTTP runs over TCP to ensure all data arrives correctly and in order.

Note: HTTP/3 uses QUIC over UDP, but QUIC implements its own reliability at the application layer.

Example 2: DNS Query

Scenario: A client queries a DNS server to resolve "www.example.com". The query is a single small message; a quick response is desired.

Analysis: DNS queries are tiny (typically < 512 bytes). Connection setup overhead would dominate. If the query is lost, the application can simply retry.

Choice: UDP — No connection establishment delay. Fast, simple, application handles retransmission if needed.

TCP's three-way handshake would add 1 RTT before any data exchange — unacceptable for latency-sensitive queries.

Example 3: Streaming Video (Live)

Scenario: A live video stream is being broadcast. The application can tolerate small amounts of packet loss but needs a consistent sending rate.

Analysis: Real-time video is delay-sensitive. TCP's congestion control would throttle the rate when packets are lost, causing buffering and playback delays. A few lost pixels are acceptable.

Choice: UDP — Application gets finer control over sending rate; occasional loss is acceptable.

Example 4: File Transfer (FTP)

Scenario: A 2GB file must be transferred from a server to a client. Any single bit error could corrupt the entire file.

Analysis: File transfer requires 100% reliable delivery. Every byte must arrive correctly, in order, with no gaps.

Choice: TCP — FTP uses TCP. The reliability guarantees are essential; throughput is prioritized over latency.

Quick Reference Cards

Use UDP When:

• Finer app-level control over sending

• No connection establishment delay

• No connection state (more clients)

• Small header overhead (8 bytes)

• Can tolerate some loss

Use TCP When:

• Reliability is essential

• In-order delivery required

• Congestion control needed

• Flow control needed

• Cannot tolerate data loss
