Multiplexing & Demultiplexing

Computer Networking — Complete Guide for 20/20 Exam

Multiplexing and Demultiplexing Concepts

The transport layer extends host-to-host delivery (provided by the network layer) to process-to-process delivery. This is accomplished through two complementary operations:

Demultiplexing

Delivering data in a transport-layer segment to the correct socket at the receiving host. The transport layer examines header fields (port numbers) to identify the receiving socket.

Multiplexing

Gathering data chunks from different sockets at the source host, encapsulating each with header info, and passing segments to the network layer.

Port Number Specification:
16-bit number → Range: 0 to 65535
Well-known ports: 0-1023 (reserved, e.g., HTTP:80, FTP:21, DNS:53)
Registered ports: 1024-49151
Dynamic/private ports: 49152-65535
Real-World Example: Multiple Apps on One Host

Suppose you are downloading Web pages while running one FTP session and two Telnet sessions. You have four network application processes running. When the transport layer receives data from the network, it must direct each incoming segment to the correct one of these four processes — this is demultiplexing in action.

Household Analogy: Multiplexing & Demultiplexing

When Bill receives a batch of mail from the mail carrier, he performs demultiplexing — observing to whom the letters are addressed and hand-delivering them to his brothers and sisters.

Ann performs multiplexing — collecting letters from her brothers and sisters and giving the collected mail to the mail person.

How Demultiplexing Works

Each socket is assigned a port number. When a segment arrives, the transport layer examines the destination port number and directs the segment to the corresponding socket. The segment's data then passes through the socket into the attached process.

// Creating a UDP socket in Python with explicit port binding
clientSocket = socket(AF_INET, SOCK_DGRAM)
clientSocket.bind(('', 19157)) # assigns port 19157
The transport layer delivers to sockets, not directly to processes. A process can have multiple sockets, each acting as a separate "door" for data.

UDP vs TCP Socket Identification

Connectionless (UDP) Demultiplexing

UDP Socket Identifier:
(Dest IP, Dest Port) — 2-tuple
Segments with different source IP/port but same dest IP + dest port go to the SAME socket

A UDP socket is fully identified by a 2-tuple: (destination IP address, destination port number). If two UDP segments have different source IPs or source ports but the same destination IP and port, they are both directed to the same socket.

The source port number serves as a return address — when the receiver wants to send a response, it uses the source port as the destination port in the reply.

Connection-Oriented (TCP) Demultiplexing

TCP Socket Identifier:
(Src IP, Src Port, Dest IP, Dest Port) — 4-tuple
Each unique combination identifies a distinct connection socket

A TCP socket is identified by a 4-tuple: (source IP address, source port number, destination IP address, destination port number). Two arriving TCP segments with different source IPs or source ports will be directed to different sockets.

Property UDP TCP
Socket identifier 2-tuple: (dest IP, dest port) 4-tuple: (src IP, src port, dest IP, dest port)
Connection type Connectionless Connection-oriented
Multiple clients on same port All go to same socket Each gets a unique connection socket
Server socket creation Single socket for all clients Welcoming socket + per-connection sockets
Source port purpose Return address Part of connection identifier

Port Scanning and Web Servers

How Web Servers Use Ports

A Web server typically listens on port 80 (for HTTP) or port 443 (for HTTPS). When clients send segments, all have destination port 80. The server distinguishes different clients using source IP addresses and source port numbers.

Persistent vs Non-Persistent HTTP Sockets

Feature Persistent HTTP Non-Persistent HTTP
Socket lifetime Same socket for multiple requests New socket per request
Connection overhead Low (one connection) High (frequent create/close)
Performance Better (reuses TCP connection) Worse (TCP handshake per object)
Modern usage HTTP/1.1 and later HTTP/1.0 (legacy)

Port Scanning with nmap

nmap is a port scanner that determines which applications are listening on which ports. It sequentially scans ports looking for accepting TCP connections or UDP ports that respond.

nmap Outcome Meaning Security Implication
Open Port accepts connections / responds Application is listening — potential attack surface
Closed No application listening on that port Host responds (e.g., RST for TCP) — host is reachable
Unreachable Host does not respond at all Host may be down, firewalled, or filtered

Web Server Architecture: Process vs Thread

There is not always a one-to-one correspondence between connection sockets and processes. Today's high-performing Web servers often use only one process and create a new thread with a new connection socket for each new client connection. A thread is a lightweight subprocess. At any given time, there may be many connection sockets attached to the same process.

The well-known port list is maintained in RFC 1700 and updated at iana.org [RFC 3232]. Ports 0-1023 are reserved for well-known application protocols (HTTP:80, FTP:21, DNS:53).

Port scanning is a double-edged sword. System administrators use it to verify their own networks, but attackers use it to find vulnerable services. The Slammer worm exploited SQL Server on UDP port 1434 via a buffer overflow.

Worked Examples: Multiplexing & Demultiplexing

Example 1: UDP — Multiple Clients, Same Server

Scenario: Client A (IP: 10.0.0.1, port: 55000) and Client B (IP: 10.0.0.2, port: 55001) both send UDP segments to Server S (IP: 192.168.1.1, port: 161 — SNMP).

Demultiplexing behavior: Both segments have dest IP=192.168.1.1 and dest port=161. Since UDP uses a 2-tuple, both are delivered to the same socket.

Result: Server uses recvfrom() to extract the source port from each segment when sending replies.

Example 2: TCP — Multiple Clients, Same Server

Scenario: Client A (IP: 10.0.0.1, port: 45000) and Client B (IP: 10.0.0.2, port: 45001) both connect to Web Server S (IP: 192.168.1.1, port: 80).

Demultiplexing behavior: TCP uses a 4-tuple. The two connections are:

• Connection 1: (10.0.0.1, 45000, 192.168.1.1, 80)

• Connection 2: (10.0.0.2, 45001, 192.168.1.1, 80)

Result: Two different sockets are created. Each client's data goes to its own connection socket.

Example 3: TCP — Same Source Port, Different Source IPs

Scenario: Client A (IP: 10.0.0.1, port: 26145) and Client C (IP: 10.0.0.3, port: 26145) both connect to Server B (IP: 192.168.1.1, port: 80).

Problem: Both clients happen to use the same source port number 26145.

Result: This is not a problem! The 4-tuples differ because source IPs differ:

• (10.0.0.1, 26145, 192.168.1.1, 80) — different from

• (10.0.0.3, 26145, 192.168.1.1, 80)

Server B correctly demultiplexes them to two separate sockets.

Example 4: UDP Source Port as Return Address

Scenario: Host A sends a DNS query to DNS server at IP 8.8.8.8, port 53. Host A's UDP socket is on port 34000.

Step 1: A creates segment: src port=34000, dst port=53, data=query

Step 2: DNS server receives, sees dst port=53, delivers to DNS application

Step 3: DNS server creates response: src port=53, dst port=34000 (taken from query's src port!)

Step 4: Host A receives response, sees dst port=34000, delivers to waiting socket

Result: The source port in the query becomes the destination port in the response — clean round-trip routing!

Key Takeaways

• UDP: 2-tuple → All clients share one socket

• TCP: 4-tuple → Each client gets unique socket

• Port range: 0-65535 (16-bit)

• Well-known: 0-1023

Common Exam Mistakes

• Thinking TCP uses only dest port

• Forgetting source port = return address

• Confusing persistent vs non-persistent sockets

• Misidentifying nmap outcomes
