IPv6 — Internet Protocol Version 6

Computer Networking (Kurose & Ross) — Chapter 4: The Network Layer

Why IPv6? — Address Exhaustion

The Internet Engineering Task Force (IETF) foresaw that the 32-bit address space of IPv4 would eventually be exhausted. By February 3, 2011, IANA allocated the last remaining /8 IPv4 address block, marking a critical milestone. IPv6 was designed as the long-term solution.

What Happened to IPv5?

An often-asked question is what happened to IPv5? It was initially envisioned that the ST-2 protocol would become IPv5, but ST-2 was later dropped.

Address Space Comparison
IPv4: 232 ≈ 4.3 × 109 addresses
IPv6: 2128 ≈ 3.4 × 1038 addresses
IPv6 provides approximately 7.9 × 1028 times more address space than IPv4.
Address Density Comparison
IPv4 density: ~8.4 addresses per km2 of Earth's surface
IPv6 density: ~6.6 × 1023 addresses per km2 of Earth's surface
Every square meter of Earth can have ~6.6 × 1017 IPv6 addresses.

Addressing the Planet

IPv6 is designed so that "every grain of sand on the planet can be IP-addressable." With 2128 addresses, there are enough to assign an IPv6 address to every atom on Earth's surface many times over.

New Address Type: Anycast

IPv6 introduces a new type of address, called an anycast address, that allows a datagram to be delivered to any one of a group of hosts. For example, an HTTP GET request can be sent to the nearest of a number of mirror sites, providing automatic failover and load distribution.

Exhaustion Predictions & Adoption

[Solensky 1996] estimated IPv4 exhaustion would occur around 2008 and 2018 — predictions that proved remarkably accurate. IANA allocated the last IPv4 pool in February 2011. [Richter 2015] provided a survey of address-space exhaustion, and [Huston 2019] offered ongoing analysis of the remaining address pool.

Adoption of IPv6 has steadily accelerated. NIST [NIST IPv6 2020] reports more than a third of US government second-level domains are IPv6-enabled. Google reports about 25% of clients accessing Google services via IPv6 [Google IPv6 2020]. Measurements by [Czyz 2014] confirm that adoption is accelerating. Europe's 3GPP has specified IPv6 as the standard addressing scheme for mobile multimedia.

Worked Examples

Example 1: Address Density Calculation

Earth's surface area is approximately 5.1 × 108 km2. How many addresses per km2 does each protocol offer?

Solution:

IPv4: 232 / (5.1 × 108) = 4.29 × 109 / 5.1 × 108 ≈ 8.4 addresses/km2

IPv6: 2128 / (5.1 × 108) = 3.4 × 1038 / 5.1 × 108 ≈ 6.7 × 1029 addresses/km2

IPv6 offers 1029 addresses per km2, enough to assign trillions of addresses to every grain of sand on Earth.

Example 2: Subnet Allocation

An ISP is allocated a /32 IPv6 prefix. How many /48 customer prefixes can it support?

Solution:

Number of prefix bits available = 48 − 32 = 16 bits.

Number of /48 subnets = 216 = 65,536 customer prefixes.

Each /48 prefix provides 280 addresses per customer, equivalent to 248 IPv4 Internet-sized address spaces per customer.

Example 3: IPv4 Exhaustion Impact

A company in 2016 requires 8000 public IP addresses. Their RIR has run out of IPv4. What options exist?

Solution:

Option A: Use NAT with private addresses (RFC 1918) — limited scalability, breaks peer-to-peer applications.

Option B: Purchase IPv4 addresses on the transfer market — costly (~$30 per IP in 2021).

Option C: Deploy IPv6 with a /48 prefix — provides 280 addresses at negligible cost. Recommended.

Quick Reference: IPv4 Exhaustion

• IANA exhaustion: 3 February 2011

• IPv4 address size: 32 bits (4 bytes)

• IPv6 address size: 128 bits (16 bytes)

• Lesson: Network-layer changes are extremely difficult to deploy — requires global coordination across all Internet players

Why Not a "Flag Day"?

A flag day involving billions of devices is even more unthinkable today. Even in the early days of the Internet [RFC 801], when the network was tiny, a flag day (turning off all machines for upgrade) was not possible. Deploying a new network-layer protocol requires gradual coexistence, not a coordinated cutover.

Analogy: Introducing new protocols into the network layer is like replacing the foundation of a house — it affects everything built on top. Introducing new application-layer protocols, by contrast, is like adding a new layer of paint: far less disruptive and much easier to deploy.
Common Mistake: Address Representation

IPv4 addresses use dotted-decimal (e.g., 192.0.2.1). IPv6 uses colon-hexadecimal (e.g., 2001:db8::1). Both are valid only in their respective protocol — never mix notations in production configurations.

IPv6 Datagram Format

IPv6 introduces a simplified, fixed-length 40-byte header for faster router processing. No more variable-length Options field or fragmentation support at intermediate routers.

IPv6 Fixed Header (40 bytes)
Header size = 40 bytes (vs. 20–60 bytes for IPv4)
Fixed-size header enables O(1) hardware processing in routers.

Header Fields

FieldSize (bits)Description
Version4Always 6 for IPv6
Traffic Class8Similar to IPv4 TOS — QoS/differentiation
Flow Label20Identifies flows for QoS without deep-packet inspection
Payload Length16Length of the payload (data following the 40-byte header)
Next Header8Type of next header (TCP: 6, UDP: 17, ICMPv6: 58, etc.)
Hop Limit8TTL replacement — decremented by each router; dropped at 0
Source Address128IPv6 address of the sender
Destination Address128IPv6 address of the receiver
Total Header Bit Count
4 + 8 + 20 + 16 + 8 + 8 + 128 + 128 = 320 bits = 40 bytes
All fields are mandatory and fixed-width, simplifying router logic.

Worked Examples

Example 1: Flow Label for QoS

A VoIP call sends packets between two hosts every 20 ms. The router sees packets with the same (Source, Dest, Flow Label). How does this improve QoS compared to IPv4?

Solution:

IPv6 Flow Label (20 bits) lets the sender tag packets belonging to a flow. The router identifies the flow without parsing higher-layer headers (TCP/UDP ports).

The router maintains a flow cache keyed by (Src, Dst, Flow Label). Processing becomes O(1) per packet after the first lookup, eliminating the 5-tuple parsing overhead of IPv4.

Example 2: Next Header Chaining

An IPv6 packet has Next Header = 44 (Fragment Header), and the Fragment Header's Next Header = 6 (TCP). Draw the packet structure.

Solution:

Packet layout (read left to right):

IPv6 Header (40 B) NH=44 → Fragment Header (8 B) NH=6 → TCP Segment

This chaining replaces the IPv4 Options field. Routers only process headers they understand (if NH=44, and the router supports fragmentation, it processes it; otherwise it skips).

Each extension header has its own Next Header field, forming a linked list of headers.

Example 3: Payload Length Calculation

An IPv6 packet carries a 40-byte TCP header and 1460 bytes of data. What is the Payload Length field value?

Solution:

Payload Length = data after the 40-byte IPv6 header.

Payload = TCP header (40) + data (1460) = 1500 bytes. Payload Length = 1500.

Note: IPv6 Payload Length does NOT include the 40-byte IPv6 header (unlike IPv4 Total Length which includes the header).

Common Mistake: Payload Length vs Total Length

IPv6 Payload Length excludes the 40-byte base header. IPv4 Total Length includes the IP header. When migrating, always check which field is being used.

Quick Reference: IPv6 Header

• Version: 4 bits, value = 6

• Flow Label: 20 bits — new in IPv6, enables per-flow QoS

• Next Header: 8 bits — identifies extension or upper-layer protocol

• Hop Limit: 8 bits — replaces IPv4 TTL

• Header size: 40 bytes fixed (no padding needed)

IPv4 vs IPv6 — Key Differences

IPv6 is not backward-compatible with IPv4. Several IPv4 header fields were removed or reworked, and new capabilities were added.

Fields Removed from IPv4

Fragmentation Fields

ID, Flags, Fragment Offset removed. Fragmentation is end-to-end only (source host fragments; routers do not).

Header Checksum

Removed because link layers (Ethernet, WiFi) and transport layers (TCP/UDP) already provide error detection. Saves router processing time.

Options Field

Replaced by extension headers chained via Next Header. Only headers of interest are parsed.

Worked Examples

Example 1: No Header Checksum Impact

An IPv6 packet traverses a router. Why is it safe to omit the header checksum even though IPv4 had one?

Solution:

Three reasons: (1) Ethernet frames carry a CRC that detects bit errors before the packet reaches the IP layer. (2) TCP/UDP checksums cover the entire segment, including source/destination IPs (via pseudo-header). (3) Removing checksum reduces per-hop processing, improving router throughput by roughly 5–10% per router.

Example 2: End-to-End Fragmentation

An IPv6 host wants to send a 4000-byte payload across a path with MTU 1500. Fragmentation is not allowed at routers. What happens?

Solution:

The host must perform Path MTU Discovery (PMTUD). It sends a 1500-byte probe and receives ICMPv6 Packet Too Big messages if the packet exceeds the path MTU. The host fragments the 4000-byte payload into three fragments:

Fragment 1: 1448 bytes data + Fragment Header + IPv6 header

Fragment 2: 1448 bytes data + Fragment Header + IPv6 header

Fragment 3: 1104 bytes data + Fragment Header + IPv6 header

Total: 3 packets instead of 1, but intermediate routers forward them at full speed without reassembly.

Example 3: Extension Header Overhead

Compare the overhead of option handling in IPv4 vs IPv6 for a security option that adds 24 bytes. The path has 8 routers. Assume the option is examined by each router in IPv4 but only processed at destination in IPv6 (Routing Extension Header).

Solution:

IPv4: The Options field is parsed by every router. Total processing overhead = 8 routers × 24 bytes = 192 bytes of option processing.

IPv6: The option is encoded as a Destination Options Extension Header — intermediate routers skip it (Next Header simply points past it). Only the destination processes it. Overhead = 0 bytes at intermediate routers.

This is why IPv6 extension headers are more efficient for options meant only for the end host.

Quick Reference: What Changed?

• Removed: IHL, ID, Flags, Fragment Offset, Checksum, Options, Padding

• Renamed: TOS → Traffic Class, TTL → Hop Limit, Protocol → Next Header

• New: Flow Label (20 bits)

• Scaled: Addresses 32 → 128 bits

Common Mistake: Assuming Routers Fragment

IPv6 routers NEVER fragment packets. If an IPv6 packet exceeds the outgoing link MTU, the router drops it and sends an ICMPv6 "Packet Too Big" message back to the source. The source must fragment or reduce path MTU.

Transition Mechanism — Tunneling

The Internet cannot switch from IPv4 to IPv6 overnight. Tunneling allows IPv6 islands to communicate across an IPv4-only infrastructure by encapsulating IPv6 datagrams inside IPv4 datagrams.

Tunneling Concept

Tunneling Encapsulation
IPv4 header (Protocol = 41) | IPv6 datagram (original)
Protocol number 41 in the IPv4 header indicates that the payload is an IPv6 datagram.

Algorithm: IPv6 Tunneling across IPv4 Network

Algorithm TUNNEL_IPv6_over_IPv4(Src: Node B, Dst: Node E, Path: B→R1→R2→R3→E) // B and E are IPv6-capable // R1, R2, R3 are IPv4-only routers // The tunnel is between B and E through the IPv4 cloud Input: IPv6 datagram D from B to E Output: D delivered to E 1. BEGIN 2. // B creates an IPv6 datagram for E 3. D.ver := 6 4. D.src := B_IPv6 5. D.dst := E_IPv6 6. 7. // B encapsulates D inside an IPv4 datagram 8. outer.ver := 4 9. outer.src := B_IPv4 10. outer.dst := E_IPv4 11. outer.protocol := 41 // indicates IPv6 payload 12. outer.payload := D 13. 14. // Forward across IPv4 cloud 15. FOR each router R in {R1, R2, R3} 16. R reads IPv4 header only 17. R checks outer.dst, decrements outer.TTL 18. R forwards outer packet via IPv4 routing 19. END FOR 20. 21. // E receives the IPv4 packet 21. IF outer.protocol == 41 THEN 22. D := outer.payload // decapsulate IPv6 datagram 23. Process D as IPv6 datagram // read src/dst IPv6 addresses 24. END IF 25. END

Network Topology Example (B → E via IPv4 Cloud)

[ B ] ---- [ R1 ] ---- [ R2 ] ---- [ R3 ] ---- [ E ] IPv6 node IPv4 rtr IPv4 rtr IPv4 rtr IPv6 node IPv6 datagram inside IPv4 datagram: +--------+-----------------+--------+ | IPv4 | IPv6 | Upper | | hdr | datagram | layer | | proto= | (inner) | data | | 41 | | | +--------+-----------------+--------+ <--- outer (IPv4) ---> <------- payload (IPv6) -------->

Worked Examples

Example 1: Tunneling Overhead Calculation

An IPv6 datagram (40-byte header + 100-byte payload) is tunneled across an IPv4 network. What is the total bytes transmitted?

Solution:

Inner: IPv6 header (40) + payload (100) = 140 bytes

Outer: IPv4 header (20 bytes, no options) + protocol 41

Total on wire = 20 (outer IPv4) + 140 (inner IPv6 + payload) = 160 bytes

Overhead percentage = (160 − 140) / 140 ≈ 14.3%. This is the cost of backward compatibility.

Example 2: Dual Routing Tables

Node B has both an IPv4 address (192.0.2.1) and an IPv6 address (2001:db8::1). Node E has IPv4 (198.51.100.1) and IPv6 (2001:db8::2). B sends an IPv6 datagram through the tunnel. Which addresses appear in the outer IPv4 header?

Solution:

Outer IPv4 header contains:

src = 192.0.2.1 (B's IPv4 address)

dst = 198.51.100.1 (E's IPv4 address)

The inner IPv6 datagram has:

src = 2001:db8::1, dst = 2001:db8::2

IPv4 routers forward based solely on outer IPv4 addresses. Only E (both IPv4/IPv6) strips the outer header and processes the inner IPv6 datagram.

Example 3: Protocol Number Verification

An engineer captures a tunneled packet with Wireshark. The IPv4 Protocol field shows 0x29 (decimal 41). What is the payload, and what should the decapsulating host do?

Solution:

Protocol = 41 = IPv6 encapsulation (IANA-assigned).

The receiving host should: (1) strip the IPv4 header, (2) pass the remaining bytes to the IPv6 processing stack, (3) verify IPv6 version (4-bit field = 6), (4) forward the inner datagram to the destination IPv6 address.

Other common protocol numbers: TCP=6, UDP=17, ICMP=1, GRE=47.

Quick Reference: Tunneling

• Purpose: Connect IPv6 islands across IPv4 infrastructure

• Protocol number: 41 = IPv6 in IPv4

• Outer header: IPv4 (20 bytes)

• Inner header: IPv6 (40 bytes) + payload

• Key hosts: Tunnel entry/exit nodes must be dual-stack (IPv4 + IPv6)

Common Mistake: Protocol Number Confusion

When building tunnels, Protocol = 41 in the outer IPv4 header (not Protocol = 6 for TCP, not EtherType 0x86DD). If you configure a firewall to allow tunneled traffic, allow IP protocol 41, not TCP/UDP port 41.

Common Mistake: MTU Issues in Tunnels

Tunneling adds 20 bytes of IPv4 overhead. If the path MTU to E is 1500 bytes, the largest IPv6 datagram B can send is 1500 − 20 = 1480 bytes. Sending a full 1500-byte IPv6 datagram would cause fragmentation at the IPv4 layer or ICMPv6 Packet Too Big responses.
