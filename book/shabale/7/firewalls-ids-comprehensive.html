Firewalls & Intrusion Detection Systems

Computer Networking (Kurose & Ross) — Chapter 4: Network Layer Security

What is a Firewall?

A firewall is a hardware or software device placed at the boundary between an internal network and the Internet. It inspects datagram and segment headers of all incoming and outgoing traffic, and denies suspicious packets based on a configured rule set.

Core Principle:
Firewall(inspect headers) → { ALLOW if match-rule, DENY otherwise }
Every packet is evaluated against an ordered rule list; the first matching rule determines action.

Key Functions

• Inspect IP/TCP/UDP/ICMP headers

• Filter by src IP, dst IP, port, protocol

• Track connection state

• Block malformed packets

Placement

Network boundary between

internal LAN and external

Internet (WAN)

Common Filter Actions

ALLOW — permit packet

DENY — drop packet silently

REJECT — drop + send ICMP

Packet Filtering Rules

A firewall rule typically contains: Action, Protocol, Source IP, Source Port, Destination IP, Destination Port. Rules are evaluated top-to-bottom.

Rule Format

Action : ALLOW | DENY | REJECT

Proto : TCP | UDP | ICMP

Src : IP address / subnet mask

Dst : IP address / subnet mask

Port : number or range

Default Policies

Default-allow: permit unless denied

Default-deny: block unless explicitly allowed

Default-deny is more secure

Example 1: Ping Sweep Prevention

Scenario: Attacker sends 1000 ICMP echo requests to 192.168.1.0/24 to discover live hosts.

Step 1: Firewall receives ICMP packet with type=8 (echo request).

Step 2: Rule B matches — ICMP, dst 192.168.1.0/24, action DENY.

Step 3: Packet is dropped. No reply sent. Attacker sees no responses.

Step 4: Attacker cannot distinguish dead hosts from firewalled ones.

Result: Ping sweep fails. Internal network topology remains hidden.

Example 2: Port Scan Filtering

Scenario: Attacker probes TCP ports 1–1024 on 192.168.1.5 from 203.0.113.5.

Step 1: Probe to port 22 → Rule D matches (external src, dst port 22) → DENY.

Step 2: Probe to port 80 → No explicit rule allows inbound TCP/80 to 192.168.1.5. Default-deny drops it.

Step 3: Only port 443 matches Rule C if dst=192.168.1.10 — but dst is 192.168.1.5, so no match, DENY.

Step 4: Attacker receives no SYN-ACK from any port — all ports appear closed/filtered.

Result: Port scan reveals no open ports. Scanning effort wasted.

Example 3: Stateful Connection Tracking

Scenario: Internal host 192.168.1.20 makes HTTP request to 93.184.216.34:80.

Step 1: Outbound SYN packet (src:192.168.1.20:40000, dst:93.184.216.34:80) → Rule A matches → ALLOW. Firewall creates state entry.

Step 2: Response SYN-ACK (src:93.184.216.34:80, dst:192.168.1.20:40000) — matches state table entry → ALLOW.

Step 3: Unsolicited SYN (src:5.5.5.5:9999, dst:192.168.1.20:40000) — no state entry → DENY.

Result: Stateful firewall prevents external hosts from injecting unsolicited packets into established connection flows.

Common Mistake: Placing allow rules before deny rules for the same traffic. If a broad ALLOW rule precedes a specific DENY rule, the deny never triggers. Always order from most-specific to least-specific.

Common Mistake: Blocking only inbound ICMP echo requests but forgetting to block outbound echo requests. An internal compromised host can still participate in DDoS attacks. Also, ICMP unreachable messages (Type 3) are needed for Path MTU Discovery — blind blocking can break connectivity.

Firewall Rule Design Principles

Principle 1: Default-Deny

Start with a blanket deny-all rule at the bottom. Only explicitly allow necessary traffic. This minimizes attack surface.

Principle 2: Least Privilege

Allow only the minimal set of ports, protocols, and IPs required for legitimate operation. Deny everything else.

Principle 3: Rule Ordering

Place specific rules before general rules. More frequently matched rules should be higher in the list for performance.

ALLOW outbound TCP/80 (web browsing)
ALLOW outbound TCP/443 (HTTPS)
ALLOW outbound UDP/53 (DNS to trusted server)
DENY inbound ICMP echo-request
DENY inbound TCP ports <1024 (well-known port scans)
DENY any (default catch-all)
↑ Typical small-office firewall rule set (ordered top-to-bottom)

Intrusion Detection Systems (IDS)

Unlike firewalls that only inspect packet headers, an IDS performs deep packet inspection (DPI) — examining both headers AND payloads. The IDS compares packet contents against a signature database of known attack patterns.

IDS Operation:
Score(packet) = max { match(packet, signature_i) } for i in database
If Score ≥ threshold → ALERT. If Score < threshold → PASS.

Signature Matching

Each signature is a pattern (regex, byte sequence, or heuristic) that identifies malicious traffic. Common sources: Snort, Suricata rule sets.

Placement

IDS is deployed out-of-band via a network tap or port mirroring (SPAN). It does not block traffic inline — only monitors and alerts.

Alert Types

True Positive — real attack detected

False Positive — benign traffic flagged

False Negative — attack missed (worst case)

Signature-Based Detection — Worked Examples

Example 1: SQL Injection Detection

Packet Payload: GET /login.php?user=' OR 1=1 -- HTTP/1.1

Step 1: IDS reads HTTP request payload from TCP stream.

Step 2: Signature database contains pattern: ' OR 1=1 --

Step 3: The payload matches the SQL injection signature.

Step 4: IDS generates alert: HIGH priority — SQL Injection attempt to /login.php from 10.0.0.5.

Result: Administrator receives alert. Even if firewall allows HTTP traffic, IDS catches the malicious payload inside.

Example 2: Port Scan Detection

Scenario: Host 203.0.113.50 sends TCP SYN to 10 ports on 192.168.1.1 within 200ms.

Step 1: IDS monitors all connections via SPAN port.

Step 2: Signature: "More than 5 SYN packets to different ports from same source within 1 second" → port scan.

Step 3: IDS counts SYNs per source IP. 203.0.113.50 exceeds threshold.

Step 4: Alert: MEDIUM — Horizontal port scan from 203.0.113.50 targeting 192.168.1.1.

Result: Port scan behavior detected even though firewall might block the scans silently.

Example 3: Malware C2 Beacon Detection

Scenario: Internal host 192.168.1.77 sends 1KB HTTP POST to 198.51.100.99 every 60 seconds, with payload containing encoded data.

Step 1: IDS sees periodic outbound HTTP POSTs to same external IP.

Step 2: Signature: "Regular HTTP POST to unknown IP with entropy > 0.8" matches.

Step 3: Payload decoded — contains base64-encoded system information.

Step 4: Alert: HIGH — C2 beacon detected. 192.168.1.77 likely compromised.

Result: Botnet beaconing is identified despite looking like normal HTTPS traffic to the firewall.

Common Mistake: Relying only on signature-based detection. Zero-day attacks (no existing signature) will produce false negatives. Signature databases must be updated continuously — stale signatures miss modern threats.

IDS Limitations

• Cannot inspect encrypted payloads (TLS)

• High false-positive rate

• Needs regular signature updates

• No protection for zero-day exploits

IPS Advantages

• Blocks attacks in real time

• Inline deployment stops traffic

• Can reassemble fragmented packets

IPS Disadvantages

• Can drop legitimate traffic (FP)

• Requires careful tuning

• Single point of failure

• Adds latency

Anomaly-Based Detection

Beyond signatures, modern IDS/IPS uses anomaly detection: establishing a baseline of "normal" traffic and flagging deviations. This can detect novel attacks but produces more false positives.

Statistical Anomaly

Baseline: avg 100 connections/min. Spike to 10,000/min → alert. Detects DDoS, worm propagation.

Protocol Anomaly

Malformed TCP headers, unusual flag combinations (e.g., SYN-FIN set simultaneously) → alert.

Behavioral Anomaly

User logging in from 2 geographic locations in 5 minutes → alert. Detects credential theft.

Defense-in-Depth: Layered Security Architecture

No single security device is sufficient. A comprehensive network defense combines firewall, IDS/IPS, and other controls in a layered architecture.

Internet → Router → Firewall → IPS (inline) → Switch → IDS (passive via SPAN) → Internal LAN
↑ Typical enterprise network security architecture

Layer 1: Perimeter Firewall

Blocks unwanted protocols, ports, IPs. First line of defense. Filters bulk of malicious traffic (90%+).

Layer 2: IPS (Inline)

Inspects payloads and blocks known attacks in real-time. Catches what the firewall misses (application-layer attacks).

Layer 3: IDS (Passive)

Monitors for anomalies, unknown attacks, and policy violations. Provides forensic data and post-incident analysis.

Common Mistake: Deploying only a firewall and believing the network is secure. Firewalls cannot inspect payload — malware in HTTPS traffic, SQL injection in HTTP POST bodies, and zero-day exploits all bypass simple firewalls. IDS/IPS is essential.

Use Cases — Worked Examples

Example 1: Blocking Malware Download

Scenario: User on 192.168.1.50 clicks a phishing link and browser requests GET /malware.exe from evil.com.

Step 1: Firewall sees TCP/443 (HTTPS) to evil.com — outbound HTTPS is allowed by rule. Passes.

Step 2: IPS inspects TLS handshake — evil.com certificate is self-signed and known-bad in threat intel feed → BLOCK.

Step 3: Even if IPS misses (e.g., trusted CA), the downloaded file passes through IDS which runs file hash against malware signature database.

Step 4: IDS matches hash → ALERT. File is quarantined by endpoint protection.

Result: Defense-in-depth catches the malware at multiple layers. No single point of failure.

Example 2: Preventing Internal Reconnaissance

Scenario: Attacker compromises 192.168.1.100 and scans internal subnet 10.0.0.0/8.

Step 1: Firewall has no rule against internal-to-internal traffic — it passes.

Step 2: IDS on internal SPAN port sees 192.168.1.100 sending SYN packets to 10.0.0.0/8 ports 22, 80, 443.

Step 3: IDS triggers anomaly alert: "Internal host scanning private ranges — possible lateral movement."

Step 4: SOC isolates 192.168.1.100. The compromised host is contained before data exfiltration.

Result: Internal IDS detects lateral movement invisible to perimeter firewall. Incident response triggers containment.

Example 3: DNS Tunneling Detection

Scenario: Compromised host encodes stolen data into DNS queries: base64encodeddata.evil.com

Step 1: Firewall allows UDP/53 (DNS) to external servers — legitimate business need.

Step 2: IDS monitors DNS query lengths. Normal DNS queries: 20–50 chars. These queries: 200+ chars.

Step 3: Signature: "DNS query length > 100 chars with high subdomain entropy" → data exfiltration.

Step 4: Alert: CRITICAL — DNS tunneling detected. Source 192.168.1.77 exfiltrating data to evil.com.

Result: Data exfiltration via DNS tunnel (invisible to firewall) is caught by IDS signature analysis.

Common Mistake: Failing to monitor internal traffic. Many organizations focus all security at the perimeter and assume internal traffic is safe. Once an attacker breaches the perimeter, lateral movement goes undetected if internal monitoring is absent. Always deploy IDS on internal segments too.

Limitations of Firewalls and IDS

Cannot Stop Everything

New attacks with no signatures bypass IDS entirely. Firewalls cannot block attacks on allowed ports (e.g., SQL injection on TCP/80).

Encrypted Traffic Blindness

With ubiquitous TLS, firewalls and IDS cannot inspect payload contents without SSL/TLS interception (MITM proxy), which raises privacy concerns.

Resource Constraints

Deep packet inspection requires significant CPU/memory. At 10Gbps+ line rates, many IDS/IPS devices cannot keep up and may drop packets.

Best Practices Quick Reference

Firewall Best Practices

• Default-deny policy

• Block ICMP echo inbound/outbound

• Restrict high ports (>1023)

• Log denied traffic for analysis

• Review rules quarterly

IDS/IPS Best Practices

• Update signatures daily

• Tune rules to reduce FPs

• Deploy both inline + passive

• Monitor internal segments too

• Correlate with firewall logs

General Security

• Defense-in-depth is essential

• Encrypt everything (TLS 1.3)

• Segment network (VLANs)

• Automate incident response

• Conduct regular penetration tests

Incident Response Flow:
Firewall log: blocked inbound SYN to port 445 from 5.5.5.5
→ IDS log: same source scanned 50 hosts in 3 seconds
→ Correlation: automated block rule added for 5.5.5.0/24
→ Alert sent to SOC: "WannaCry-style worm activity detected and blocked"
→ Forensic packet capture saved for post-mortem
