Router Architecture

Computer Networking (Kurose & Ross) — Chapter 4: The Network Layer

Input Ports — Functions and Architecture

An input port performs the physical and data-link layer termination of an incoming link. It also executes the lookup function, consulting the forwarding table to decide which output port a datagram should be sent to. Input ports are typically implemented on line cards — hardware boards that plug into the router chassis.

  Incoming Link
       |
  [Physical Layer Termination]   →  Optical/electrical signal decoding
       |
  [Link-Layer Processing]       →  Ethernet / PPP frame extraction
       |
  [Lookup / Forwarding Table]   →  Longest prefix match on destination IP
       |
  [Queuing / Switching Fabric]  →  Datagram sent into the switching fabric

Quick Reference: Input Port

Key Lookup function uses destination IP address to search forwarding table via longest prefix matching.

HW Implemented in hardware (TCAM — Ternary Content-Addressable Memory) for nanosecond-speed lookups.

Perf At 100 Gbps with 64-byte datagrams: 5.12 ns per datagram processing budget.

Common Mistake: Confusing forwarding table with routing table. The routing table is built by the routing processor; the forwarding table is a compact, hardware-optimized copy used by input ports for per-datagram lookup. They are NOT the same structure.
Terminology Warning: The term port in router architecture (input/output ports) refers to physical network interfaces — the hardware connectors where links are attached. These are completely different from the software ports (TCP/UDP port numbers) used by network applications and socket APIs, as discussed in Chapters 2 and 3. A single router input port handles traffic for thousands of application-layer ports simultaneously; the "port" concept at these layers operates at entirely different levels of the protocol stack.
Local Forwarding via Table Distribution: The forwarding table is computed by the routing processor and then copied to each line card over a separate control bus (e.g., a PCI bus). This allows each input port to make forwarding decisions locally without consulting the centralized routing processor for every datagram. The line card stores its own copy of the forwarding table (often in TCAM or SRAM) and performs lookups entirely in hardware at line rate. The routing processor is only involved when routes change — it updates the copies on the line cards via the bus.

Forwarding Table Lookup

The forwarding table maps destination IP prefixes to output port numbers. Lookups must occur at line rate — every 5–50 nanoseconds depending on link speed. TCAM hardware can compare an IP against all prefixes in a single clock cycle.

Processing Budget Formula:
Tbudget = (L + H) × 8 ÷ R
Where L = payload size (bytes), H = header size (bytes), R = link rate (bps)
For 64 B datagram on 100 Gbps link: (64+0) × 8 ÷ 100 × 109 = 5.12 ns

Input Port Components

• Physical layer termination (fiber/copper)

• Link-layer processing (framing, CRC)

• Forwarding table lookup (TCAM)

• Switching fabric interface

Key Metrics

Lookup speed: <10 ns

Forwarding table size: up to 1M+ entries

Line rate: 10–800 Gbps per port

Worked Examples

Example 1: Processing Budget Calculation

A router receives 1500-byte datagrams on a 40 Gbps link. What is the per-datagram processing budget?

Solution:

Tbudget = 1500 × 8 ÷ (40 × 109) = 12000 ÷ 4×1010 = 300 ns

This means the input port must complete physical reception, link-layer validation, lookup, and forwarding within 300 ns per packet.

Example 2: TCAM Lookup Efficiency

A TCAM has 524,288 entries. It performs lookups in 5 ns regardless of table size. Compare this to a binary search on a sorted table that takes log2(N) × 2 ns per comparison.

Solution:

TCAM lookup: 5 ns (constant time)

Binary search: log2(524288) × 2 = 19 × 2 = 38 ns

TCAM is 7.6x faster, essential for high-speed links.

Example 3: Head-of-Line (HOL) Blocking

Input port 1 has two datagrams: first destined for output port 2, second for output port 3. The switching fabric is busy transferring a datagram from input port 2 to output port 2. Explain HOL blocking.

Solution:

The first datagram (to port 2) waits because the fabric is busy with port 2. The second datagram (to port 3, which is free) is blocked behind the first. This is HOL blocking — a queued datagram cannot bypass an earlier one even if its destination output is available. This motivates input port queuing architectures like Virtual Output Queuing (VOQ).

Example 4: Longest Prefix Match

Given forwarding table entries: 128.0.0.0/8 → Port 0, 128.10.0.0/16 → Port 1, 128.10.4.0/24 → Port 2. Where is destination 128.10.4.15 forwarded?

Solution:

128.10.4.15 matches all three prefixes. The longest prefix is /24 (128.10.4.0/24), so the datagram goes to Port 2. If only /8 matched, it would go to Port 0.

Switching Fabric — Moving Datagrams Between Ports

The switching fabric connects input ports to output ports. It is completely contained within the router and is responsible for transferring datagrams from ingress to egress at line rate. The fabric is the router's internal network — its capacity determines the router's aggregate throughput.

  +----------+          +-----------+
  | Input 1  |--------->| Output 1  |
  +----------+          +-----------+
       |                      ^
       |   [Switching Fabric]  |
       v                      |
  +----------+          +-----------+
  | Input 2  |--------->| Output 2  |
  +----------+          +-----------+
       |                      ^
       |    (Crossbar / Bus    |
       v     / Interconnect)   |
  +----------+          +-----------+
  | Input N  |--------->| Output N  |
  +----------+          +-----------+

Quick Reference: Switching Fabric

Types Three major types: Memory-based, Bus-based, Crossbar / Interconnection Network.

Perf Switching capacity must equal or exceed sum of all line rates to avoid internal blocking.

Example Juniper MX2020: 800 Tbps switching capacity across 800 × 100 Gbps ports.

Common Mistake: Thinking switching fabric speed only needs to match a single port's line rate. In reality, the fabric must support all ports simultaneously. If N ports each run at R, the fabric needs N × R / 2 (bidirectional) capacity.
Implementation Options: Forwarding hardware can be built using either custom designs developed by the router vendor (e.g., Cisco's Silicon One, Juniper's Trio chipset), or constructed using merchant-silicon chips purchased from commercial suppliers (e.g., Intel, Broadcom). The merchant-silicon approach is common in white-box and open networking switches, where vendors like Broadcom provide off-the-shelf switching ASICs (e.g., Tomahawk, Trident series) that implement the entire switching fabric and forwarding pipeline. Custom designs offer differentiation and optimization for a vendor's specific architecture, while merchant silicon provides faster time-to-market and lower development costs.

Three Switching Fabric Types

1. Memory-Based

Early routers used a CPU with shared memory. Input port copies datagram to system memory; CPU looks up forwarding info and copies to output. Limited to ~2 Gbps due to memory bandwidth bottleneck.

2. Bus-Based

A shared bus connects all ports. Only one transfer at a time. Limited to ~32 Gbps (e.g., 32-bit PCI at 33 MHz = 1 Gbps aggregate; modern busses up to ~100 Gbps).

3. Crossbar / Interconnection

Multiple simultaneous transfers between non-conflicting input-output pairs. Full crossbar allows any input to reach any output simultaneously. Used in all high-end routers (Cisco CRS, Juniper MX/T Series).

Worked Examples

Example 1: Memory-Based Switching Bottleneck

A router has 4 input ports at 1 Gbps each. The shared memory bus runs at 800 MB/s. Can this router support line-rate forwarding?

Solution:

Total input rate: 4 × 1 Gbps = 4 Gbps = 500 MB/s
Memory bus: 800 MB/s × 2 (read + write) = 1600 MB/s theoretical
But each datagram requires two memory transfers (input→memory, memory→output).
Effective capacity: 800 MB/s ÷ 2 = 400 MB/s = 3.2 Gbps.
Needed: 4 Gbps. Line rate NOT supported - the memory bus is the bottleneck.

Example 2: Crossbar Scheduling — Matching Inputs to Outputs

At a given time, input ports 1, 2, 3 have datagrams for outputs 3, 1, 2 respectively. Show a valid crossbar configuration.

Solution:

This is a permutation matching: Input 1 → Output 3, Input 2 → Output 1, Input 3 → Output 2. All inputs and outputs are distinct, so the crossbar can establish 3 simultaneous connections — full throughput.

If two inputs both wanted the same output, only one would be served; the other would be queued (contention).

Example 3: Scaling to Large Systems

The Juniper MX2020 supports 800 ports of 100 Gbps. What switching capacity is required if each port operates at full duplex?

Solution:

Unidirectional: 800 × 100 Gbps = 80,000 Gbps = 80 Tbps
Bidirectional (full duplex): 2 × 80 Tbps = 160 Tbps of fabric capacity needed.
Juniper MX2020 delivers 800 Tbps — a 5x overspeed factor to accommodate bursty traffic and internal overhead.

Example 4: Knockout Switch Principle

In a large crossbar switch with N inputs, all sending to the same output, only one can succeed per time slot. If the fabric runs S times faster than line rate, how many packets reach the output per slot?

Solution:

With an N×N crossbar running at speed S × line rate, at most S packets can be delivered to the same output per time slot. The remaining N−S packets must be buffered or dropped. This is why switches use speedup (fabric running faster than line rate) to reduce contention.

Output Ports — Buffering and Transmission

Output ports receive datagrams from the switching fabric and transmit them on the outgoing link. They perform the inverse operations of input ports: link-layer framing, physical layer encoding, and signal transmission. Output ports must buffer datagrams when the switching fabric delivers them faster than the link can transmit.

  From Switching Fabric
       |
  [Output Port Buffer]   →  FIFO / priority queue of datagrams
       |
  [Link-Layer Encoding]  →  Add frame header, CRC
       |
  [Physical Layer]       →  Signal encoding, modulation
       |
  Outgoing Link

Quick Reference: Output Port

Queuing Output buffering required when arrival rate > transmission rate. Buffer size follows the B × RTT rule-of-thumb.

Scheduling FIFO is simplest; WFQ (Weighted Fair Queuing) provides QoS.

Drop Policy Tail-drop, RED (Random Early Detection), or WRED.

Common Mistake: Assuming larger buffers are always better. Large buffers cause bufferbloat — increased latency without improved throughput. The recommended buffer size is B = RTT × C / √N (for N TCP flows), not blindly large memory.

Buffer Sizing Formulas

Rule-of-Thumb Buffer Size:
B = RTT × C
C = link capacity, RTT = average round-trip time of TCP flows
For a 10 Gbps link with 250 ms RTT: B = 0.25 × 10×109 = 2.5 Gb = ~312 MB
Modern Rule (Stanford Router Buffering):
B = (RTT × C) ÷ √N
N = number of active TCP flows (typically 1000s). With N=1000, √N≈32, so B is reduced by ~32x

Worked Examples

Example 1: Output Buffer Occupancy

An output port has a 10 Gbps link. Packets arrive from the fabric at 12 Gbps for 100 ms. How much buffer is needed to avoid drops?

Solution:

Excess rate = 12 − 10 = 2 Gbps
Burst duration = 0.1 s
Buffer needed = 2 × 109 × 0.1 = 200 Mb = 25 MB

If the output port buffer is smaller than 25 MB, packets will be dropped during this burst.

Example 2: RED Drop Probability

A router uses RED with minth = 40 KB, maxth = 80 KB, and maxp = 0.1. Current average queue length is 60 KB. What is the drop probability?

Solution:

RED drop probability P = maxp × (avglen − minth) ÷ (maxth − minth)
P = 0.1 × (60 − 40) ÷ (80 − 40) = 0.1 × 20 ÷ 40 = 0.1 × 0.5 = 0.05 (5%)

Each arriving packet has a 5% chance of being marked/dropped, providing early congestion notification.

Example 3: Weighted Fair Queuing (WFQ)

Three flows share a 1 Gbps output link with weights 2:1:1 (flows A:B:C). Flow A sends at 600 Mbps, B at 300 Mbps, C at 400 Mbps. What bandwidth does each receive?

Solution:

Total weight = 2 + 1 + 1 = 4
Guaranteed rates: A = 2/4 × 1 Gbps = 500 Mbps, B = 250 Mbps, C = 250 Mbps
Since A sends 600 Mbps but is guaranteed 500 Mbps: A gets 500 Mbps
B sends 300 Mbps but is guaranteed 250 Mbps: B gets 250 Mbps (bottleneck)
C sends 400 Mbps but is guaranteed 250 Mbps: C gets 250 Mbps (bottleneck)
Excess bandwidth (remaining) is redistributed proportionally.

Example 4: Bufferbloat Calculation

A home router has a 64 MB buffer on a 20 Mbps link with 100 ms base RTT. How much does bufferbloat increase latency under full load?

Solution:

Time to drain full buffer: 64 MB × 8 ÷ 20 Mbps = 512 Mb ÷ 20 Mbps = 25.6 seconds
RTT under load = base RTT + buffer drain time = 100 ms + 25.6 s = 25.7 seconds
Latency increased by 256x due to bufferbloat.

Routing Processor — The Control Plane Brain

The routing processor handles all control-plane functions: it executes routing protocols (OSPF, BGP, RIP), computes forwarding tables, manages router configuration, and handles network management (SNMP, ICMP error messages). Unlike the data plane (hardware, nanosecond scale), the control plane runs in software at millisecond-to-second timescales.

  [Routing Processor]  ← Software, general-purpose CPU
       |
       ├── OSPF (link-state routing)     →  Builds LSDB → Dijkstra → forwarding table
       ├── BGP (path-vector / inter-AS)   →  Builds AS-path table → policies → forwarding table
       ├── ICMP (error / control messages) →  TTL expired, destination unreachable
       ├── SNMP (network management)       →  Statistics, configuration
       └── Router CLI / Management         →  Human operator interface
       |
  [Forwarding Table]  →  Downloaded to line cards (data plane)

Quick Reference: Routing Processor

Data Plane Hardware-based, nanosecond processing, per-datagram forwarding.

Control Plane Software-based, millisecond-to-second processing, topology discovery and route computation.

Line Card A line card typically hosts both the input port and output port for one or more links. The routing processor is a separate card or integrated into the supervisor module.

Common Mistake: Thinking the routing processor is involved in every datagram forwarding decision. In hardware-based routers, the routing processor only updates the forwarding table when routes change. Per-datagram forwarding is done entirely in hardware on the line cards.
Roundabout Analogy: A router is like a traffic roundabout. The routing processor is the city planning office that decides which routes to build (control plane). The input ports are the entrance ramps where cars look at signs to decide their exit. The switching fabric is the roundabout itself — moving cars from entrances to exits. The output ports are the exit ramps onto the outgoing roads. The planning office doesn't direct each individual car; it just updates the signs when road conditions change.
SDN Routers — Remote Controller: In Software-Defined Networking (SDN) architectures, the routing processor's role changes significantly. Instead of running distributed routing protocols locally, the routing processor is responsible for communicating with a remote SDN controller (e.g., via OpenFlow or similar protocol). The remote controller computes all forwarding table entries based on global network view and policies. The routing processor on each router receives these entries from the controller and installs them into the input ports' forwarding tables. This decouples control logic from the forwarding hardware, enabling centralized network management and programmatic traffic engineering.

Worked Examples

Example 1: OSPF Convergence Time

An OSPF domain has 200 routers. Each router floods a new LSA upon detecting a link failure. LSAs propagate in 10 ms per hop. A reconverged Dijkstra computation takes 50 ms per router. What is the total convergence time assuming a diameter of 6 hops?

Solution:

LSA propagation: 6 × 10 ms = 60 ms
Dijkstra computation (can start as LSA propagates, but worst-case): 50 ms
Total convergence: propagation + computation = 110 ms (≈ 0.1 seconds)

During this 110 ms, routers may have stale forwarding tables, causing temporary black holes or loops.

Example 2: BGP Route Processing Scalability

A core router receives 900,000 BGP routes, each costing 1 μs to process during initialization. The routing processor has 4 cores at 2 GHz. How long does initial BGP table processing take?

Solution:

Single-core time: 900,000 × 1 μs = 900 ms
With 4 cores (ideal parallelism): 900 ms ÷ 4 = 225 ms

In practice, BGP processing involves more than table insertion — policy checks, best-path selection, and adjacency maintenance add significant overhead (seconds to minutes).

Example 3: CPU Utilization During Route Instability

A router's routing processor handles 500 route updates per second, each taking 200 μs. What is the CPU utilization? How many updates per second would saturate the CPU?

Solution:

CPU time per second: 500 × 200 μs = 100,000 μs = 100 ms
Utilization: 100 ms / 1000 ms = 10%

Saturation point: 1 second / 200 μs = 5000 updates/second

During route flapping, update rates can spike to 10,000+/s, causing 200%+ CPU demand and rendering the router unable to converge. This is why route flap dampening is critical.

Example 4: Forwarding Table Update Latency

A routing processor computes a new forwarding table entry and needs to update 16 line cards. Each line card takes 100 μs to acknowledge the update. What is the total update latency for all 16 line cards if updates are sent in parallel? Sequentially?

Solution:

Parallel: All without simultaneous. Max latency = 100 μs
Sequential: 16 × 100 μs = 1.6 ms

Modern routers use parallel updates to minimize the window where forwarding tables are inconsistent across line cards.
