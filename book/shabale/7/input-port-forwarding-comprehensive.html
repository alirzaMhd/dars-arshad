Input Port Processing & Destination-Based Forwarding

Computer Networking: A Top-Down Approach (Kurose & Ross) — Chapter 4

Input Port Processing Overview

When a packet arrives at a router's input port, three sequential functions execute at the physical, link, and network layers before the packet can be forwarded.

Input Port Pipeline:
Line Termination → Link-Layer Processing → Lookup (Forwarding)
Each stage must complete before the next begins; lookup is the bottleneck.

Stage-by-Stage Breakdown

StageFunctionKey Detail
1. Line TerminationReceive bits from physical mediumClock recovery, signal decoding
2. Link-Layer ProcessingVerify frame integrity, extract IP datagramCRC check, remove Ethernet header
3. Lookup (Forwarding)Query forwarding table using dest IPUses longest prefix match; outputs port

Shadow Copy Mechanism

The routing processor computes the forwarding table in software. A shadow copy is pushed to each line card so lookups occur at line rate without involving the central processor.

Routing Processor

Computes forwarding table via routing protocols (OSPF, BGP) interacting with other routers

Or receives forwarding rules from a remote SDN controller

Pushes shadow copy to line cards

Line Card (Input Port)

Stores local forwarding table

Hardware lookup (TCAM/SRAM)

≪ 1 μs per lookup

Fast Lookup Memory Considerations

⚡ Memory Access Times:

Forwarding lookups must complete within nanoseconds to keep pace with line rates. Routers use on-chip DRAM and faster SRAM (employed as a DRAM cache) to store forwarding tables and enable rapid lookups. Special attention must be paid to memory access times — a single DRAM access (~50 ns) can consume most of the lookup budget at high line rates. SRAM caches mitigate this by caching frequently matched prefixes. For a survey of fast lookup algorithms, see [Gupta 2001, Ruiz-Sanchez 2001].

Example 2: Routing Table Update Propagation

A BGP update arrives at the routing processor, changing the next-hop for prefix 200.23.18.0/23.

Time t=0: Routing processor recomputes forwarding table.

Time t=2 ms: New shadow copy pushed to all 8 line cards.

Time t=2.5 ms: Line card begins using updated table. In-flight lookups finish with old table.

Example 3: Brute-Force Impracticality

Example 3: Why 232 Entries Fails

A naive forwarding table listing one entry per IP address would contain 4,294,967,296 entries.

At 1 Gbps line rate with 64-byte packets (~1.49 Mpps), the lookup budget is 672 ns per packet.

A linear scan of 4 billion entries at 10 ns per entry would take ~43 seconds — 64 million times too slow.

Solution: Prefix-based aggregation reduces the table to ~900K entries (BGP full table).

⚠ Common Mistake:

Students often think the routing processor performs per-packet lookups. In practice, the routing processor only computes the table; lookups happen on line cards via shadow copies.

⚡ Quick Reference: Input Port Processing

Pipeline: Line Termination → Link-Layer → Lookup

Shadow Copy: Forwarding table replicated to line cards; central CPU not in data path

Lookup Budget: ~1 μs per packet at 10 Gbps line rate

Prefix Table Size: ~900K–1M entries (vs. 4B brute-force)

Longest Prefix Matching (LPM)

When multiple forwarding table prefixes match a destination address, the router selects the entry with the longest subnet mask (most specific match).

Longest Prefix Matching Rule:
output = argmax ( mask_leni ) over i where addr & maski = prefixi
Among all matching entries, pick the one with the greatest prefix length.

Forwarding Table Example (4 Entries)

PrefixBinary PrefixMask LengthOutput Port
200.23.16.0/2011001000.00010111.0001201
200.23.18.0/2311001000.00010111.00010010232
200.23.18.0/2411001000.00010111.00010010.0243
0.0.0.0/0(no bits)04 (default)

LPM Algorithm Pseudocode

Algorithm LongestPrefixMatch(FIB table T, IP address D): best_len = -1 best_port = null for each entry E = (prefix, mask_len, port) in T: // Apply mask: keep only first mask_len bits if (D AND generate_mask(mask_len)) == prefix: if mask_len > best_len: best_len = mask_len best_port = port if best_len == -1: return default_port return best_port Function generate_mask(len): if len == 0: return 0 return (~0) << (32 - len)

The default route 0.0.0.0/0 matches every address. It is only selected when no other entry matches.

TCAM — Constant-Time Lookup

Ternary Content-Addressable Memories (TCAMs) compare a search key against all entries in parallel. Each TCAM cell stores 0, 1, or X (don't care). Longest prefix is resolved by ordering entries by prefix length.

TCAM vs. SRAM

TCAM: O(1) lookup, higher power, ~$350/Mb

SRAM + Algorithm: O(log N), lower power

Cisco Catalyst: up to 1M TCAM entries

TCAM Ordering Constraint

Entries must be stored longest-prefix-first

First match = longest prefix

No mask computation needed

⚠ Common Mistake:

LPM does NOT pick the numerically "largest" matching address; it picks the entry with the longest mask. A /24 always wins over a /20, even if the /20's address range includes more addresses.

⚡ Quick Reference: Longest Prefix Matching

Rule: Among matches, longest mask wins

Implementations: Binary trie (O(32)), TCAM (O(1))

TCAM capacity: up to 1M entries (Cisco Catalyst)

Default route: 0.0.0.0/0 matches all (length 0 — lowest priority)

Match-Plus-Action Abstraction

Modern routers generalize forwarding beyond simple destination-based lookups. The match-plus-action paradigm decouples pattern matching from the operations performed on matching packets.

Match-Plus-Action Model:
∀ packet p : (matchi(p)) ⇒ actioni(p)
If packet p satisfies match condition i, execute the associated action set.

Generalized Forwarding Table

Match ConditionActionsUse Case
Dest IP = 200.23.18.0/24Forward(port 3), DecTTLStandard forwarding
Src IP = 10.0.0.0/8DropACL / Firewall
Dest Port = 80NAT(translate addr), Forward(port 2)NAT gateway
Protocol = TCP & Flags = SYNCount++, Forward(port 1)Traffic monitoring

Additional Actions (Beyond Forwarding)

Checksum Check

Verify IP header checksum; if invalid, drop packet

Header checksum recomputed at each hop

TTL Decrement

Time-to-Live field reduced by 1

If TTL = 0 after decrement, send ICMP TTL exceeded

Prevents infinite loops

Counter Updates

Byte counters, packet counters per flow

Used for accounting, SNMP, NetFlow

Critical for network monitoring

Additional Input Processing Actions

Beyond forwarding decisions, input processing encompasses several mandatory actions applied to every arriving packet:

Physical & Link-Layer Processing

Line termination, clock recovery, signal decoding

Frame integrity verification (CRC), header extraction

Version, Checksum & TTL Checks

Packet's IP version number and checksum are verified

TTL field is checked (decrement to 0 → drop)

Checksum and TTL are rewritten before forwarding

Network Management Counters

Counters such as number of IP datagrams received must be updated

Used for SNMP, NetFlow, accounting

Essential for monitoring and debugging

⚠ Common Mistake:

Match-plus-action is not limited to destination IP. The match condition can inspect L2 (MAC), L3 (IP, protocol), L4 (ports, flags), or even L7 fields. Thinking "match = dest IP only" misses the generality of the abstraction.

⚡ Quick Reference: Match-Plus-Action

Match: Any combination of header fields (IP, TCP/UDP ports, protocol, flags)

Action: Forward, Drop, TTL-decrement, Checksum-recalc, Count, NAT, Mirror

Applications: Firewalls, NAT, load balancers, SDN (OpenFlow), traffic engineering

Key advantage: Single unified pipeline for all packet processing
