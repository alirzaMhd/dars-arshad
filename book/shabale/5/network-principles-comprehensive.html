Computer Networking: A Top-Down Approach — Kurose & Ross, Ch. 2

Client-Server Architecture

A central always-on server (fixed, well-known IP address) handles requests from many clients. Clients never communicate directly with each other — all traffic goes through the server.

Server Characteristics

• Always-on host

• Permanent IP address

• Scales poorly under flash crowds

• Requires data center infrastructure

Client Characteristics

• Communicate with server only

• May have dynamic IP addresses

• Do not communicate peer-to-peer

• May be intermittently connected

Example — Web Server Under Load

A news website (server) runs on a dedicated machine at IP 192.0.2.10. When a breaking story hits, 100,000 users open the site simultaneously. The server must handle all 100,000 requests. To cope, the company adds a load balancer and 20 back-end server replicas in a data center — this is costly and requires active management.

Key insight: In client-server, all processing burden falls on the server. Scaling requires provisioning more server capacity.

Peer-to-Peer (P2P) Architecture

There is no always-on server. Peers (end-user devices) communicate directly with each other. Peers both consume and provide content. The architecture is self-scaling — each new peer adds both demand and capacity.

P2P Characteristics

• No always-on server

• Peers communicate directly

• Self-scaling (peers = servers)

• Highly resilient to failure

P2P Challenges

• Not ISP-friendly (traffic patterns)

• Security concerns (no central authority)

• Flash crowd handling is complex

• Incentive mechanisms needed

Example — BitTorrent File Sharing

Alice wants to download a large Linux ISO file. She joins a swarm via a tracker. The file is split into 256 KB chunks. Alice downloads chunk 3 from Bob, chunk 7 from Carol, and chunk 12 from Dave — all simultaneously. Meanwhile, other peers download chunks they lack from Alice. As more peers join, the total upload capacity of the swarm grows, so download speeds do not degrade.

Key insight: In P2P, the system capacity grows with the number of participants — no data center needed.

Self-Scalability of P2P: One of the most compelling features of P2P architectures is their self-scalability. In a P2P file-sharing system, each peer generates workload by requesting files, but each peer also adds service capacity by uploading files to other peers. This means that as more peers join the system, the total system capacity grows proportionally — unlike client-server architectures where all burden falls on the server.

RFC vs Proprietary Protocols

Application-layer protocols fall into two categories regarding their specification:

RFC (Public Domain)

Protocols like HTTP are specified in Request for Comments (RFC) documents published by the IETF. Because the specification is publicly available, any browser that follows the RFC rules will work correctly with any server that follows the same rules. This interoperability is a cornerstone of the Internet's success.

Examples: HTTP (RFC 7230), SMTP (RFC 5321), DNS (RFC 1035)

Proprietary Protocols

Some applications use proprietary protocols — the protocol specification is not publicly available. Only the developer's software implements the protocol correctly. This creates vendor lock-in and limits interoperability.

Example: Skype uses a proprietary protocol — its message formats and communication rules are not published in any RFC.

Processes

A process is a program running on an end system. When two processes on different hosts want to communicate, they exchange messages across the network. The sending process generates messages; the receiving process consumes them.

Client Process

• Initiates communication

• Sends request first

• Usually ephemeral port

Server Process

• Waits for contact

• Listens at well-known port

• Typically always running

Example — Web Browser & Web Server

Firefox (client process) on your laptop initiates a connection to an Apache HTTP Server (server process) running on a remote host. Firefox sends an HTTP GET request; Apache processes it and returns the requested HTML page. Firefox is the client because it initiates the exchange, even though the server sends data back.

Interprocess Communication vs Network Communication

It is important to distinguish between two forms of process communication:

Interprocess Communication (IPC)

Processes running on the same host communicate via rules governed by the operating system (e.g., pipes, shared memory, message queues, loopback sockets).

Network Communication

Processes running on different hosts communicate by exchanging messages across the network. The sending process creates a message and pushes it into the network; the receiving process consumes it. This is the primary focus of Chapter 2 of the textbook.

Sockets: The API Between Application and Transport

A socket is the software interface through which an application process sends and receives messages from the network layer below. Think of it as a door: the application pushes data out one side of the door; the transport layer picks it up on the other side and delivers it to the destination socket on the remote host.

// Socket API pseudocode — client sending a message sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, server_address, server_port); send(sock, "Hello, server!", 14, 0); recv(sock, buffer, sizeof(buffer), 0); close(sock);
// Socket API pseudocode — server receiving sock = socket(AF_INET, SOCK_STREAM, 0); bind(sock, local_address, port_80); listen(sock, 5); while (true) { client_sock = accept(sock, client_addr, &client_len); recv(client_sock, buffer, sizeof(buffer), 0); send(client_sock, response, response_len, 0); close(client_sock); }
Common Mistake: The socket is NOT the transport protocol itself. A socket is the interface that the application uses to access transport-layer services. TCP or UDP operate beneath the socket, transparent to the application code (aside from the socket type chosen).

Application Developer's Control Over the Socket

When writing a network application, the developer controls everything on the application-layer side of the socket — what data is sent, when it is sent, and how it is formatted. However, the developer has little control on the transport-layer side of the socket:

  • The developer can choose which transport protocol to use (TCP or UDP) by selecting the socket type
  • The developer can set some parameters such as buffer sizes, maximum segment sizes, and timeout values
  • Beyond that, the transport-layer behavior (retransmission, congestion control, flow control, etc.) is handled entirely by the operating system and is largely opaque to the application

This separation of concerns is by design — the application developer should focus on application logic, not on the details of reliable data transfer or congestion control.

Your browser wants to fetch a video from YouTube. The DNS lookup resolves youtube.com to IP 142.250.80.46. The browser opens a TCP socket to (142.250.80.46, port 443). Socket Selection — The Transport Layer's Decision

When a TCP segment arrives at a host, the transport layer examines the destination IP and destination port to route the data to the correct socket. With UDP, the socket is identified by destination IP + destination port only. With TCP, the socket is identified by all four values (source IP, source port, dest IP, dest port) — this is why TCP can handle multiple concurrent connections to the same server port from different clients.

TCP Socket Identifier:
socket = (src_IP, src_port, dest_IP, dest_port)
All four values must match for data to reach the correct socket

Application-Layer Protocol Definition

An application-layer protocol defines the rules for communication between processes on different hosts. Specifically, it specifies:

Types of Messages

What kinds of messages are exchanged — for example, request messages (client asking for something) and response messages (server replying).

Message Syntax

The structure of each message type — what fields are present (e.g., status code, headers, body) and how the fields are delineated (e.g., carriage return and line feed (CRLF) in HTTP, or fixed-length fields in binary protocols).

Message Semantics

The meaning of each field — for example, what does a "404 Not Found" status code mean? What does the "Content-Type" header indicate?

Rules for Timing and Actions

When and how processes send messages — for example, "a server must not send a response before receiving a request" or "a client must wait for an acknowledgement before sending the next message."

Network Application vs Application-Layer Protocol

There is an important distinction between a network application and an application-layer protocol:

Example: HTTP is the application-layer protocol used by the Web. But the Web application is much broader — it includes HTML (the markup language for web pages), web browsers (like Chrome, Firefox), web servers (like Apache, Nginx), the document retrieval model (URLs, hyperlinks), and the entire ecosystem around it. HTTP is just one piece — the protocol that governs how browsers and servers exchange messages.

Similarly, SMTP is the application-layer protocol for electronic mail, but the email application also includes mail user agents (Outlook, Gmail), mail servers, message stores, and spam filters.

RFC and Proprietary Application-Layer Protocols

Some application-layer protocols are specified in RFCs (public domain) — for example, HTTP, SMTP, and DNS are all defined in RFC documents that anyone can read and implement. Any browser following the HTTP RFC will interoperate with any server following the same RFC. Other protocols are proprietary — the protocol specification is a company secret, and only the company's software implements it correctly. Skype is a well-known example of a proprietary protocol.

Four Dimensions of Transport Services

When choosing a transport protocol, applications evaluate four key service dimensions. Not all applications need all four — the trade-off is between functionality and overhead.

1. Reliable Data Transfer

Guarantees that data is delivered correctly and completely — no bits flipped, no data lost, no duplicates, in the right order.

Essential for: file transfer, email, web pages

2. Throughput

The rate (bits/sec) at which the network can deliver data. Some apps need a guaranteed minimum; others are elastic and use whatever is available.

Essential for: streaming video, voice calls

3. Timing

Guarantees on delay — e.g., "every bit arrives within 150 ms." Interactive real-time apps have strict timing requirements.

Essential for: telephony, gaming, video conferencing

4. Security

Encryption (no eavesdropping), data integrity (no tampering), and endpoint authentication (verifying who you are talking to).

Essential for: e-commerce, banking, private messaging

Example — Elastic vs Rate-Sensitive Applications

Scenario A: You are downloading a large update for your operating system via a background updater. If the network is congested, the download slows down, but the download still eventually finishes. The application does not need a minimum throughput — it is elastic.

Scenario B: You are on a Zoom video call. If the network throughput drops below ~1 Mbps, the video becomes pixelated, freezes, or drops entirely. The application needs a guaranteed minimum throughput — it is rate-sensitive.

Example — Timing Requirements in Practice

A VoIP call (Skype, WhatsApp voice) typically requires one-way delay < 150 ms. Beyond 150 ms, the conversation feels unnatural — speakers start talking over each other or there are awkward pauses. In contrast, loading a Wikipedia article can tolerate 2–3 seconds of delay without the user noticing.

Security Requirements

Security in transport-layer services covers three dimensions:

  • Encryption: Data is transformed so that an eavesdropper cannot read it.
  • Data integrity: The receiver can detect if data was modified in transit.
  • Endpoint authentication: The receiver can verify the sender's identity.

Neither TCP nor UDP provides any of these natively. Security must be layered on top (e.g., TLS for TCP, DTLS for UDP, or application-layer encryption).

Warning: An application can require reliable data transfer AND not use TCP. Reliability (ACKs, retransmissions, checksums) can be implemented at the application layer over UDP. Similarly, an application can use TCP but still have no security — TCP alone does not encrypt anything.

TCP (Transmission Control Protocol)

TCP is the Internet's workhorse transport protocol. It provides a connection-oriented, reliable byte-stream service between two processes.

  • Connection-oriented: Before data exchange, client and server perform a three-way handshake to establish state.
  • Reliable data transfer: Uses sequence numbers, ACKs, retransmissions, and checksums to guarantee delivery.
  • Congestion control: TCP dynamically adjusts its sending rate based on network conditions — it slows down when the network is congested.
  • Flow control: The receiver tells the sender how much data it can accept, preventing buffer overruns.
  • Full-duplex: Both sides can send and receive simultaneously over the same connection.
TCP Segment Structure (simplified):
[src_port(16) | dst_port(16) | seq_num(32) | ack_num(32) | flags(9) | window(16) | checksum(16) | payload]
Minimum header = 20 bytes, maximum = 60 bytes

TCP Connection Establishment — Three-Way Handshake

Client Server | | |------- SYN (seq=x) --------------->| |<---- SYN-ACK (seq=y, ack=x+1) ----| |------- ACK (seq=x+1, ack=y+1) ---->| | | | <-------- Data Exchange ---------> |
Example — TCP Overhead

A small monitoring application sends a 10-byte sensor reading every second. Over TCP, each segment adds 20 bytes of TCP header + 20 bytes of IP header = 40 bytes of overhead for 10 bytes of data (80% overhead). If the sensor sends 86,400 readings per day, the overhead alone is 3.4 MB of wasted bandwidth per day. For IoT devices on metered connections, this is significant.

UDP (User Datagram Protocol)

UDP is a connectionless, unreliable transport protocol. It offers the bare minimum: multiplexing/demultiplexing plus a lightweight integrity check.

  • Connectionless: No handshake — the sender just pushes datagrams out.
  • No reliability: Datagrams may be lost, duplicated, or delivered out of order. The application must handle this if needed.
  • No congestion control: UDP can send at any rate — it does not slow down when the network is congested.
  • Low overhead: Only 8 bytes of header.
  • No delivery guarantee: UDP does not even guarantee that a datagram will reach its destination.
UDP Segment Structure:
[src_port(16) | dst_port(16) | length(16) | checksum(16) | payload]
Header is only 8 bytes (vs 20+ for TCP)
Example — DNS over UDP

A DNS query is typically a single small packet (under 512 bytes). The client sends a UDP datagram to port 53 of the DNS server. The server replies with a single datagram. If the reply is lost, the DNS client simply retransmits after a short timeout. The simplicity of UDP avoids the TCP handshake overhead — a TCP DNS lookup would take 3 extra round trips (SYN, SYN-ACK, ACK) before even sending the query.

DNS chooses UDP because: low latency, one-query-one-response pattern, and loss is cheaply handled by retransmission.

TLS (Transport Layer Security)

Important: TLS is not a third transport protocol. It is an enhancement layer that sits between the application and TCP. Applications that use TLS (e.g., HTTPS) first establish a TCP connection, then perform a TLS handshake within that connection to negotiate encryption keys and authenticate the server.

// TLS handshake (simplified) — occurs AFTER TCP handshake Client Server | | | <-- (TCP 3-way handshake completes) --> | | | |--- ClientHello (ciphers, TLS version) ->| |<--- ServerHello (chosen cipher, cert) ---| |<--- ServerCertificate (X.509 chain) -----| |<--- ServerHelloDone ---------------------| |--- ClientKeyExchange (pre-master) ------>| |--- [ChangeCipherSpec] ----------------->| |--- Finished (encrypted) --------------->| |<--- [ChangeCipherSpec] -----------------| |<--- Finished (encrypted) ----------------| | | | <-------- Encrypted Data ------------> |

TLS Services

• Encryption (AES, ChaCha20)

• Data integrity (HMAC)

• Server authentication (X.509 certs)

• Optional client authentication

TLS Overhead

• 2 extra RTT for handshake

• TLS 1.3 reduces to 1 RTT

• ~5–15% CPU overhead

• Additional bytes per record

Warning: Neither TCP nor UDP provides security! Data sent over plain TCP is transmitted in cleartext — anyone on the path can read it. TLS is what adds encryption. Always use TLS (TLS 1.2+) for any application that handles sensitive data. UDP also has no security — if you need secure UDP, use DTLS (Datagram TLS).

Example — Why HTTP/3 Switched to UDP

HTTP/2 over TCP suffers from head-of-line blocking: if a TCP packet is lost, all subsequent streams (even unrelated ones) are blocked until the lost packet is retransmitted. HTTP/3 runs over QUIC, which is built on UDP. QUIC implements its own reliability and multiplexing at the application layer, so a lost packet only blocks the affected stream — other streams continue unaffected. This switch trades TCP's reliable in-order delivery for better multiplexing performance.

Example 1: Web Browsing — End-to-End Flow

Follow the path of a single HTTP request from a browser to a web server and back, from socket to physical wire.

Example 1 — Fetching a Web Page

You type http://example.com/index.html into your browser. Here is the step-by-step flow:

1. Browser (process) creates a TCP socket: socket(AF_INET, SOCK_STREAM, 0) 2. Browser resolves "example.com" to IP via DNS (UDP query to port 53) 3. TCP 3-way handshake to (93.184.216.34, port 80) 4. Browser sends HTTP GET /index.html through the socket 5. Socket passes data to TCP → TCP segments (seq=1, ack=1, ...) 6. TCP passes segments to IP → IP packets (src=192.168.1.5, dst=93.184.216.34) 7. IP passes to link layer → Ethernet frames (src MAC, dst MAC = next-hop router) 8. Router forwards packets across the Internet (routing table lookups) 9. Server's NIC receives frames → link layer strips Ethernet header 10. Server's IP layer reassembles packets → TCP layer reassembles segments 11. Server passes HTTP request to Apache (process) via its socket 12. Apache reads index.html from disk, sends HTTP 200 OK + content back 13. Reverse path: server socket → TCP → IP → link → routers → browser 14. Browser's TCP delivers data to browser process via socket 15. Browser renders the HTML page

Example 2: File Transfer — TCP vs UDP

Example 2 — Why File Transfer Needs TCP

A museum wants to transfer a 500 MB digitized painting (bitmap) from its on-site server to a cloud backup. The file is mission-critical — a single corrupted pixel could affect the artwork's archival value.

Over UDP: The application sends 500,000 KB of UDP datagrams. On a network with 0.1% packet loss, ~500 KB of data will be lost. The receiving application must detect every loss and request retransmission manually. If datagrams arrive out of order, the application must reassemble them. The application essentially needs to reimplement TCP's reliability logic at the application layer.

Over TCP: The application calls a single send() for the file data. TCP handles segmentation, retransmission of lost segments, in-order delivery, and flow control automatically. The receiving application simply calls recv() and gets the complete, correct file.

Verdict: TCP is the clear choice for file transfer — it provides reliability "for free" via the transport layer.

Example 3 — Internet Telephony: Why UDP Is Preferred

Alice and Bob are on a WhatsApp voice call. The audio codec produces a 160-byte packet every 20 ms (64 Kbps stream).

Over TCP: If a TCP segment carrying 20 ms of audio is lost, TCP will retransmit it. But retransmission takes at least one RTT (maybe 100–200 ms). By the time the retransmitted segment arrives, that 20 ms of audio is already 100+ ms late — it is useless. The user hears a glitch anyway. Meanwhile, TCP's congestion control may reduce the sending rate, causing even more delay for subsequent packets.

Over UDP: If a UDP datagram is lost, the receiver simply plays silence or uses packet loss concealment (PLC) to mask the gap. The next datagram (20 ms later) arrives on time. The user may not even notice a single lost packet. No retransmission overhead, no head-of-line blocking.

Verdict: UDP wins for real-time voice — a small amount of loss is acceptable; delay is not.

Audio packet size calculation:
Packet rate = 1 / 0.020 s = 50 packets/sec
Bandwidth needed = 160 bytes × 50 = 8,000 bytes/sec = 64 Kbps
Before including IP/UDP/RTP headers (additional ~40 bytes/packet)

  • The server sees the player's new position 100 ms after the move
  • The other players see the update after another 100 ms
  • By the time everyone agrees on the position, the player has already moved again
  • Result: the game shows the player teleporting or rubber-banding

This is why competitive games invest heavily in edge servers and low-latency routing.

Example 5: Total Response Time Calculation

Example 5 — Non-Persistent HTTP Response Time

Consider a web page with 1 base HTML file and 4 referenced images. Assume non-persistent HTTP (each object requires a separate TCP connection). Given:

  • RTT between client and server = 50 ms
  • Each object size = 100 KB
  • Link transmission rate = 10 Mbps
Transmission time for one object:
T_trans = object_size / link_rate = (100 × 8 × 10^3) / (10 × 10^6) = 0.08 s = 80 ms
Time for 1st object (base HTML) with non-persistent HTTP:
T_1 = 2 RTT + T_trans = 2(50) + 80 = 180 ms
2 RTT: one for TCP handshake (SYN, SYN-ACK, ACK) + one for HTTP request/response

For each of the 4 images, a new TCP connection is opened (2 RTT + T_trans each):

Total response time (serial, non-persistent):
T_total = (2 RTT + T_trans) + 4 × (2 RTT + T_trans) = 5 × (100 + 80) = 900 ms

With persistent HTTP (reuse same TCP connection):

Total response time (persistent HTTP):
T_total(persistent) = 2 RTT + 5 × T_trans = 100 + 5(80) = 500 ms
Only one TCP handshake; all 5 objects requested sequentially on the same connection

With parallel TCP connections (say browser opens 6 connections):

Total response time (parallel, all 5 objects sent concurrently):
T_total(parallel) ≈ 2 RTT + T_trans = 100 + 80 = 180 ms
All 5 objects transmitted simultaneously (limited by link rate sharing)

Key takeaway: Non-persistent HTTP is slow because of the per-object handshake overhead. Persistent and parallel connections significantly improve performance.

Key Formula Reference

Round Trip Time (RTT):
RTT = time for small packet to travel client → server → client
Typically 10–200 ms for terrestrial links; includes propagation delay, queuing delay, processing delay
Traffic Intensity:
Traffic intensity = (λ × L) / R
where λ = request arrival rate (req/sec), L = average object size (bits), R = link bandwidth (bps)
Note: If traffic intensity > 1, the queue grows without bound (infinite queuing delay). For good performance, traffic intensity should stay well below 1 (typically < 0.8).
Total Response Time (Non-Persistent HTTP):
T_total ≈ 2 × RTT + (file_size / link_rate)
For a single object. Each additional object on a new connection adds another 2 RTT + transmission time.

RTT Components

• Processing delay (router)

• Queuing delay (buffer wait)

• Transmission delay (link speed)

• Propagation delay (distance/speed of light)

Bandwidth vs Latency

Bandwidth: bits per second (throughput)

Latency: seconds per trip (delay)

For small transfers, latency dominates

For large transfers, bandwidth dominates

If your app needs... Choose... Because...
100% reliable file transfer TCP Built-in ACK/retransmission, ordering, flow control
Real-time voice/video UDP (+application-layer loss mitigation) Low delay, no head-of-line blocking, loss tolerance

Exam Tip: A common exam question asks "Why does Netflix use TCP for video streaming when video is loss-tolerant?" Answer: (1) TCP's congestion control is fair to other traffic, (2) HTTP-based delivery over TCP works through firewalls/NATs easily, (3) buffering at the client (seconds of video) hides TCP's delay variability, and (4) TCP's reliability means no visual artifacts from lost data.
