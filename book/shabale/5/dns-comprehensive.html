DNS — The Internet's Directory Service

Computer Networking: Kurose & Ross — Chapter 2 Complete Guide

The Core Problem: Names vs. Numbers

Humans identify hosts by memorable names like www.google.com, but network-layer routers require fixed-length IP addresses like 121.7.106.83 to forward packets. A translation service is essential to bridge this gap.

Fundamental Mapping:
Hostname (www.example.com) ↔ IP Address (192.0.2.1)
DNS translates human-friendly names to machine-friendly addresses and vice versa.

What is DNS?

DNS (Domain Name System) is two things in one:

  • A distributed database — stores resource records hierarchically across millions of servers worldwide
  • An application-layer protocol — allows clients and servers to query and update this database. DNS runs over UDP using port 53 (TCP is used for zone transfers and large responses)

Primary Service: Hostname-to-IP Translation

When a user types www.google.com into a browser, the following steps occur:

  1. The browser extracts the hostname from the URL
  2. The client-side DNS application (resolver) sends a UDP query to port 53
  3. The DNS protocol returns one or more IP addresses for www.google.com
  4. The browser initiates a TCP connection to the returned IP address on port 80/443
gethostbyname() — The Application Interface

Applications do not invoke DNS directly. Instead, they call the gethostbyname() function provided by the operating system. On many UNIX-based machines, this library function triggers the DNS resolution process:

  1. The calling application calls gethostbyname("www.google.com")
  2. The resolver code on the client side forms a DNS query and sends it via UDP to the local DNS server
  3. The resolver waits for the response and returns the resolved IP address to the calling application

The gethostbyname() function is deprecated in modern systems in favor of getaddrinfo() (which supports both IPv4 and IPv6), but the resolution workflow remains the same.

Additional Services

Host Aliasing

Hosts with complex canonical names can have simple aliases. For example, enterprise.example.com might be an alias for relay1.west-coast.example.com. DNS returns the canonical hostname when queried for the alias, along with the IP address via a CNAME record.

Mail Server Aliasing (MX Records)

MX records allow a company's mail server to use the same domain name as its web server while pointing to a different host. For example, example.com MX record points to mail.example.com, while the A record for example.com might point to a web server at a different IP.

Load Distribution

Popular sites like google.com replicate content across hundreds of servers. The same hostname maps to multiple IP addresses in the DNS database. DNS servers rotate through these addresses in round-robin fashion, distributing traffic across replicas.

Key Properties

• Distributed — no single point of failure

• Hierarchical — three-tier authority

• Cache-friendly — TTL-based caching

• Extensible — new record types

Transport

Default: UDP port 53

Fallback: TCP port 53

Packet < 512 bytes UDP

EDNS0: up to 4096 bytes

⚠ Design Philosophy: Complexity at the Edge

DNS is a prime example of the Internet's "edge" design philosophy. The critical name-to-address translation is not performed by a centralized core network component. Instead, it is implemented using DNS clients and servers that operate at the edge of the network — on end systems and organization-managed servers. This keeps the network core simple and places intelligence and complexity at the edges, a recurring theme in Internet architecture.

⚠ DNS is not just for web browsing

Every Internet application that uses hostnames relies on DNS — email (SMTP), file transfers (FTP), SSH, VoIP, streaming media, and virtually everything else.

Why Hierarchy? The Failure of Centralized Design

A single DNS server handling all queries would be catastrophic:

  • Single point of failure — if it crashes, the entire Internet stops working
  • Traffic volume — billions of devices generate trillions of daily queries; one server could never cope
  • Distant database — a client in Australia querying a server in New York suffers hundreds of milliseconds of latency
  • Maintenance nightmare — every new host requires updating a central database

The solution is a distributed, hierarchical database with three classes of DNS servers.

The Three Server Classes

1. Root DNS Servers

• 13 root server types labeled A through M

• 1000+ physical instances worldwide (anycast)

• Managed by 12 independent organizations

• Coordinated through IANA (Internet Assigned Numbers Authority)

• Provide IP addresses of TLD servers

2. TLD Servers

• Handle top-level domains: .com, .org, .net, .edu, .gov

• Also country TLDs: .uk, .fr, .jp, .ir

• Verisign manages .com

• Educause manages .edu

3. Authoritative Servers

• Organization's own DNS server

• Stores authoritative resource records

• Can be maintained internally or by a provider

• Example: dns1.networkutopia.com

BIND Software

DNS servers throughout the hierarchy commonly run BIND (Berkeley Internet Name Domain) software [BIND 2020]. Originally developed at the University of California, Berkeley, BIND is the most widely used DNS server software, implementing the DNS protocol and providing both authoritative and recursive resolution services.

Local DNS Server (The Essential Proxy)

Though not strictly part of the hierarchy, every ISP provides a local DNS server (also called a default name server). When a host makes a DNS query:

  • The query goes first to the local DNS server
  • The local server acts as a proxy, forwarding queries to the hierarchy on behalf of the requesting host
  • The local server caches results aggressively to speed up future queries
  • Example: dns.nyu.edu for NYU's campus network

Recursive vs. Iterative Queries

Two fundamental query modes exist. Most practical DNS resolution uses a hybrid: the client-to-local-DNS query is recursive, while the local-to-hierarchy queries are iterative.

Property Recursive Query Iterative Query
Who does the work? The receiving server The requesting server
Server load Higher (server must resolve fully) Lower (server returns referrals)
Response Final answer or error Answer or referral to next server
Cache benefit Intermediate servers can cache Client caches at each step
Messages for depth-3 6 messages (3 queries + 3 replies) 8 messages (4 queries + 4 replies)

Step-by-Step: Resolving gaia.cs.umass.edu from cse.nyu.edu

Iterative Query Flow (8 messages total)
Host (cse.nyu.edu) Local DNS (dns.nyu.edu) | | |--- (1) Query gaia.cs.umass.edu ------>| | |--- (2) Query --> Root Server | |<-- (3) Referral to .edu TLD ---| | | | |--- (4) Query --> .edu TLD | |<-- (5) Referral to umass.edu ---| | | | |--- (6) Query --> dns.umass.edu | |<-- (7) Answer 128.119.40.3 ----| | | |<-- (8) Answer 128.119.40.3 ----------| Legend: (1) = Recursive (host to local) (2-7) = Iterative (local to hierarchy)

All-Recursive Query Mode (Figure 2.20)

In the all-recursive alternative, every server in the chain recursively queries the next level on behalf of the requesting server:

  • The root server recursively queries the TLD server
  • The TLD server recursively queries the authoritative server
  • Each response propagates back down the same chain
Message Count (all-recursive, 3 levels):
5 queries + 5 replies = 10 total messages
Query chain: Host → Local → Root → TLD → Authoritative (4) + response chain back (4) + host-to-local response carries final answer = 10 messages total through 3 hierarchy levels.

In practice, the hybrid approach (recursive from host to local DNS, iterative from local DNS upward through the hierarchy) is the most common deployment. It balances the caching benefits of recursion with the low server load of iteration at the upper levels.

DNS Caching

DNS servers cache query results to improve performance and reduce load on the hierarchy.

  • Each mapping has a TTL (Time To Live) — typically 2 days
  • When cached, subsequent queries are answered directly without hierarchy traversal
  • Root servers are often bypassed entirely because TLD server addresses are cached by local DNS servers
  • Cache entries are not authoritative — they are "non-authoritative" answers
Caching Benefit Example

Host A queries www.google.com. Local DNS server resolves it (8 messages), caching the result. 30 seconds later, Host B queries the same name. The local DNS server responds immediately from cache — 0 hierarchy messages, only 1 reply.

Algorithm: Iterative DNS Resolution

ALGORITHM: resolve(hostname, type) ---------------------------------------- Input: hostname (e.g., "gaia.cs.umass.edu") record_type (e.g., "A") Output: IP address or error 1. IF hostname in local cache AND TTL valid THEN 2. return cached result (non-authoritative) 3. END IF 4. 5. current_server ← default_root_server 6. WHILE IP not found DO 7. send_query(current_server, hostname, type) 8. response ← receive_response() 9. 10. IF response contains answer THEN 11. cache(hostname, response.answer, response.TTL) 12. return response.answer 13. ELSE IF response contains referral THEN 14. current_server ← referral_server 15. CONTINUE // follow referral 16. ELSE 17. return "HOST NOT FOUND" error 18. END IF 19. END WHILE

In practice, the root server address is built into the DNS resolver software (a "hint file").

⚠ DNS Vulnerability: Cache Poisoning

An attacker can inject forged DNS records into a resolver's cache. When the cache stores the fake mapping, all subsequent clients are redirected to a malicious server. Mitigation: DNSSEC (DNS Security Extensions) cryptographically signs DNS responses.

Resource Records (RR)

Every DNS server stores data as resource records. Each record is a 4-tuple:

Resource Record Format:
(Name, Value, Type, TTL)
Name and Value semantics depend on Type; TTL is the time-to-live in seconds

Registrar and Domain Registration

Before a domain can be used on the Internet, it must be registered through an ICANN-accredited registrar. ICANN (Internet Corporation for Assigned Names and Numbers) coordinates the global DNS system and accredits organizations authorized to sell domain registrations.

  • Prior to 1999, Network Solutions held a monopoly on .com, .net, and .org registrations
  • Today, hundreds of ICANN-accredited registrars compete (e.g., GoDaddy, Namecheap, Google Domains)
  • The registrar verifies the domain name's uniqueness, collects registration fees, and enters NS and A (glue) records into the TLD DNS database

Registration example — networkutopia.com:

Step 1: Network Utopia Inc. selects a registrar and requests "networkutopia.com" Step 2: Registrar checks uniqueness (no other "networkutopia.com" exists) Step 3: Registrar inserts NS and A glue records into the .com TLD database: (networkutopia.com, dns1.networkutopia.com, NS) (networkutopia.com, dns2.networkutopia.com, NS) (dns1.networkutopia.com, 212.212.212.1, A) (dns2.networkutopia.com, 212.212.212.2, A) Step 4: Network Utopia configures authoritative DNS servers with additional A, MX, CNAME records as needed

Dynamic DNS Updates

Until recently, DNS records were configured statically from configuration files — adding, deleting, or modifying a record required manually editing a zone file and restarting the server. The UPDATE option (defined in RFC 2136 and RFC 3007) changes this:

  • Allows dynamic addition and deletion of resource records using DNS messages themselves
  • Enables clients to automatically update their DNS records when their IP address changes
  • Critical for mobile and home devices that receive dynamic IPs via DHCP
  • UPDATE messages follow the same DNS message format as standard queries and responses

DNS Message Format

There are only two message types: query and reply. Both share the exact same format.

DNS Message Structure (12-byte header + 4 variable sections)
+-------------------------------+ <-- 12 bytes fixed | Header (12 bytes) | | ID (16 bits) | Flags (16) | | QDCOUNT | ANCOUNT | | NSCOUNT | ARCOUNT | +-------------------------------+ | Question Section | <-- variable length | (the query being asked) | +-------------------------------+ | Answer Section | <-- variable length | (resource records for query) | +-------------------------------+ | Authority Section | <-- variable length | (records of authoritative | | servers) | +-------------------------------+ | Additional Section | <-- variable length | (helpful extra records) | +-------------------------------+ Header Field Details: +--------+--------+--------+--------+ | ID (identification) | <-- 16-bit random number +--------+--------+--------+--------+ matching query & reply | QR| OPCODE |AA|TC|RD|RA| Z |RCODE| +--------+--------+--------+--------+ QR: 0=query, 1=response OPCODE: 0=standard, 1=inverse, 2=server status AA: authoritative answer TC: truncated (UDP, >512 bytes) RD: recursion desired RA: recursion available RCODE: 0=OK, 3=name error (NXDOMAIN) QDCOUNT: number of questions (typically 1) ANCOUNT: number of answers NSCOUNT: number of authority records ARCOUNT: number of additional records

Question Section

+-------------------------------+ | QNAME (variable) | <-- sequence of labels | e.g., 3www6google3com0 | (length-byte prefixed) +-------------------------------+ | QTYPE (16 bits) | <-- 1=A, 15=MX, etc. +-------------------------------+ | QCLASS (16 bits) | <-- 1=Internet (IN) +-------------------------------+

nslookup — Platform Availability and Advanced Usage

The nslookup tool is available on most Windows and UNIX platforms. For systems without a command-line interface, web-based nslookup sites provide the same functionality through a browser. Advanced usage allows querying specific DNS servers directly:

$ nslookup -type=A www.google.com a.root-servers.net # query root directly $ nslookup -type=NS google.com a.gtld-servers.net # query TLD directly $ nslookup -type=MX gmail.com dns.google # use Google's resolver

This flexibility allows network administrators to troubleshoot exactly which level of the hierarchy returns a given response.

Additional Section in Action

When a DNS server returns MX records for example.com, it often includes the Additional Section with the corresponding A records:

;; ANSWER SECTION: example.com. IN MX 10 mail.example.com. ;; ADDITIONAL SECTION: mail.example.com. IN A 93.184.216.34 <-- saves an extra lookup!

This optimization eliminates the need for a separate A-record query for the mail server.

⚠ DDoS Amplification Attack

Attackers send DNS queries with a spoofed source IP (the victim's address) to open DNS resolvers. The response (which can be much larger than the query) is sent to the victim. A 60-byte query can trigger a 4000-byte response — a 66x amplification factor. Mitigation: disable open recursion on DNS servers.

DNS Security — Attack History and Defenses

⚠ October 21, 2002 — Root Server DDoS Attack

Attackers used a botnet to launch ICMP ping floods against all 13 root server IP addresses simultaneously. The attack caused minimal damage because:

  • Root servers had ICMP packet filters that dropped the attack traffic
  • Local DNS servers cache TLD server IPs, so most queries never reach the root servers
⚠ October 21, 2016 — Dyn DDoS Attack

The Mirai botnet, consisting of approximately 100,000 compromised IoT devices (printers, IP cameras, baby monitors, etc.), launched a massive DDoS attack against Dyn, a major DNS provider. The attack affected: Amazon, Twitter, Netflix, GitHub, Spotify, and many other services for nearly a full day. This attack demonstrated the vulnerability of DNS infrastructure to large-scale botnets.

⚠ Man-in-the-Middle Attack

An attacker intercepts DNS queries between a client and a DNS server, then returns bogus replies pointing to malicious IP addresses. The client unknowingly connects to attacker-controlled servers.

⚠ DNS Poisoning Attack

An attacker sends forged DNS replies to a DNS server, tricking it into caching bogus resource records. Once cached, all subsequent clients querying that server receive incorrect IP addresses. This attack can propagate through cache sharing.

⚠ DNSSEC — DNS Security Extensions [RFC 4033]

DNSSEC provides cryptographic signing of DNS responses. Using public-key cryptography, a DNS resolver can verify that a response is authentic and has not been tampered with. DNSSEC does not encrypt DNS data — it provides data integrity and origin authentication, ensuring returned records are exactly what the authoritative source published.

Example 1: Full Resolution Trace for www.amazon.com

Scenario: A host on the NYU campus (cse.nyu.edu) types www.amazon.com in a browser. No cached entries exist.

Step 1: Host sends query to local DNS (dns.nyu.edu) Q: "What is the IP of www.amazon.com?" Step 2: Local DNS queries root server (e.g., a.root-servers.net) R: "I don't know. Ask .com TLD at a.gtld-servers.net" [Local DNS caches .com TLD server address] Step 3: Local DNS queries .com TLD server Q: "What is the IP of www.amazon.com?" R: "I don't know. Amazon's authoritative DNS is dns.amazon.com (NS record)" [Local DNS caches amazon.com NS record] Step 4: Local DNS queries dns.amazon.com Q: "What is the IP of www.amazon.com?" R: "www.amazon.com is an alias (CNAME) for www.amazon.com.akadns.net" [Local DNS caches CNAME] Step 5: Local DNS follows CNAME and queries dns.amazon.com Q: "What is the IP of www.amazon.com.akadns.net?" R: "Answer: www.amazon.com.akadns.net A 205.251.242.103" [Local DNS caches final A record] Step 6: Local DNS returns 205.251.242.103 to the host Response: "www.amazon.com IP = 205.251.242.103" Total messages: 10 (5 queries + 5 replies) Cache entries created: 3 (.com TLD, NS for amazon.com, A record)

Example 3: Interpreting Resource Records — A Practical Exercise

Scenario: You are a network administrator examining your zone file. Interpret each of the following records:

Record 1: (www.mycompany.com, 198.51.100.10, A, 3600) Interpretation: www.mycompany.com has IPv4 address 198.51.100.10. TTL = 3600 seconds (1 hour). Record 2: (mycompany.com, dns1.mycompany.com, NS, 86400) Interpretation: The authoritative DNS server for the mycompany.com domain is dns1.mycompany.com. TTL = 1 day. Record 3: (mail.mycompany.com, 198.51.100.20, A, 3600) (shop.mycompany.com, 198.51.100.10, A, 3600) (www.mycompany.com, server1.mycompany.com, CNAME, 7200) Interpretation: Mail and web traffic go to different IPs. www is an alias; its canonical name is server1. To resolve www, first get server1's A record. Record 4: (mycompany.com, mail.mycompany.com, MX, 86400) Interpretation: Email sent to user@mycompany.com is delivered to the mail server at mail.mycompany.com.

FOR EACH ns_record IN records WHERE type == "NS" DO 5. // Cache the delegation as well 6. cache[ns_record.Value] ← { ... } 7. END FOR 8. 9. // Cache glue records in additional section 10.
