Electronic Mail & SMTP

Computer Networking (Kurose & Ross, Ch. 2) — Complete Study Guide

Three Major Components

E-mail systems are built from three core components:

  1. User Agents (UA) — the client software that lets users compose, read, reply to, and forward messages.
  2. Mail Servers — the always-on infrastructure that stores mailboxes and manages message queues.
  3. SMTP (Simple Mail Transfer Protocol) — the application-layer protocol used to transfer messages between mail servers.

User Agents

Common user agents include Microsoft Outlook, Gmail (web-based), and Apple Mail. Their primary functions:

  • Compose new messages
  • Read incoming messages from the mailbox
  • Reply to messages
  • Forward messages to other recipients

Mail Servers

Mail servers form the core of the e-mail infrastructure. Each recipient has a mailbox on a mail server where incoming messages are stored. The sender's mail server maintains a message queue for messages that cannot yet be delivered. Failed deliveries are retried every 30 minutes; if delivery still fails after several days, the server removes the message and notifies the sender.

E-mail Address Anatomy
alice@crepes.fr
The part after "@" identifies the destination mail server's hostname. "alice" is the mailbox name.

The flow proceeds as follows:

  1. Alice's UA sends the message to her mail server (crepes.fr) using SMTP.
  2. Alice's mail server places the message in its outgoing queue and then uses SMTP to send it to Bob's mail server (hamburger.edu).
  3. Bob's mail server places the message into Bob's mailbox.
  4. Bob retrieves the message from his mailbox using an access protocol (IMAP or HTTP).
⚠ SMTP is a PUSH protocol. The sending mail server pushes the message to the receiving mail server. This is fundamentally different from HTTP, which is a pull protocol where the client requests data from the server. Because SMTP uses push, a dedicated access protocol is needed for reading mail.

HTTP/IMAP (Pull) — client initiates connection and requests/pulls data from server

Historical Context

SMTP is much older than HTTP — its original RFC (RFC 821) dates back to 1982, when the Internet was still in its infancy. E-mail was the most popular Internet application during this early period [Segaller 1998], and it remains one of the most widely used services today.

A defining characteristic of e-mail is that it is asynchronous communication — the sender composes and sends a message at their convenience, and the recipient reads it at theirs. Unlike instant messaging or the request-response pattern of HTTP, there is no expectation that both parties are simultaneously connected.

SMTP Overview

SMTP (Simple Mail Transfer Protocol) is the standard protocol for transferring e-mail between mail servers. It is defined in RFC 5321.

⚠ SMTP uses only 7-bit ASCII! Binary attachments (images, videos) must be encoded using Base64 or quoted-printable before transmission. The mail server cannot handle raw binary data.

Why 7-bit ASCII? Historical Context

The 7-bit ASCII restriction was entirely sensible in the early 1980s when SMTP was designed. At that time, transmission capacity was scarce, and most network traffic was text-based. Restricting messages to 7-bit ASCII kept the protocol simple and compatible with the limited character encodings of the era.

In today's multimedia era, this restriction poses a clear challenge. Binary data such as images, videos, and documents cannot be transmitted as-is through SMTP. Instead, they must be encoded into ASCII using schemes like Base64 or quoted-printable before transmission. The receiving end decodes them back into binary form.

This stands in stark contrast to HTTP, which has no such restriction — HTTP can transmit arbitrary binary data directly using MIME types and Content-Type headers. The design difference reflects the eras in which each protocol was born: SMTP in the text-centric 1980s, HTTP in the more multimedia-aware 1990s.

Protocol Roles

The client side of SMTP runs on the sender's mail server. The server side runs on the receiver's mail server. There is a direct TCP connection between the two — no intermediate mail servers participate in the SMTP exchange.

This direct server-to-server model means that even if the two mail servers are on opposite sides of the world — say, from Hong Kong to St. Louis — the SMTP connection is established directly between them. There are no intermediate relay servers that store and forward the message.

If Bob's mail server is temporarily down, the message does not get stored on some intermediate server. Instead, it remains in Alice's mail server's message queue. Alice's server will periodically retry delivery (every ~30 minutes) until Bob's server accepts it or the attempt is abandoned after several days.

Three Phases of SMTP

1. Handshake Phase

The client establishes a TCP connection and the two sides identify themselves:

  • C: HELO — Client identifies itself with its domain name
  • S: 250 Hello — Server acknowledges
  • C: MAIL FROM: — Identifies the sender
  • S: 250 OK — Sender accepted
  • C: RCPT TO: — Identifies each recipient (one per command)
  • S: 250 OK — Recipient accepted

2. Transfer Phase

  • C: DATA — Client signals it is ready to send the message body
  • S: 354 Start mail input — Server is ready
  • C: Sends message (header lines + blank line + body)
  • C: . — A single period on a line by itself marks the end of message
  • S: 250 OK — Message accepted

3. Closure Phase

  • C: QUIT — Client terminates the session
  • S: 221 Bye — Server closes connection

SMTP uses persistent connections: multiple messages can be sent over the same TCP connection without re-establishing the handshake.

Persistent Connections — Multiple Messages

When a sending mail server has multiple messages destined for the same receiving mail server, all of them are transmitted over the same TCP connection. This avoids the overhead of repeatedly setting up and tearing down TCP connections.

For each individual message, the client begins with a new MAIL FROM command and ends with the single-period terminator (CRLF.CRLF). The QUIT command is only sent after all messages have been transferred. A single TCP connection may thus carry many back-to-back SMTP transactions.

SMTP Communication Pseudocode

// SMTP Client (sender's mail server) function sendMail(sender, recipients, message): TCP_connect(server, port=25) recv() // 220 ready send("HELO " + myDomain) // identify recv() // 250 OK send("MAIL FROM: <" + sender + ">") recv() for each recipient in recipients: send("RCPT TO: <" + recipient + ">") recv() send("DATA") recv() // 354 start send(message) send(".") // end marker recv() // 250 OK send("QUIT") TCP_close()

Extended SMTP (ESMTP)

ESMTP (Extended SMTP), defined in RFC 5321, extends the original SMTP protocol with additional capabilities. The telnet example in the Examples tab shows ESMTP in action — note the enhanced status codes such as 2.1.0, 2.1.5, and 2.0.0 in the server responses. These structured codes provide more detailed delivery information than the basic numeric codes.

Key ESMTP extensions include:

  • SMTP-AUTH — authentication mechanism for verifying client identity
  • STARTTLS — upgrades an insecure connection to a TLS-encrypted one
  • PIPELINING — allows multiple commands to be sent without waiting for each response
  • SIZE — lets the server advertise a maximum message size
  • DSN (Delivery Status Notification) — delivery receipts

ESMTP is identified by the server greeting that includes "ESMTP" (e.g., 220 mail.hamburger.edu ESMTP Sendmail ready), and clients use EHLO instead of HELO to request extended capabilities.

RFC 5322 — Internet Message Format

E-mail messages are defined by RFC 5322. A message consists of two parts separated by a blank line:

  1. Header lines — metadata about the message
  2. Body — the actual content (ASCII text)

⚠ Important distinction: SMTP commands (MAIL FROM, RCPT TO) operate at the protocol level — they are exchanged between mail servers during SMTP communication. The message headers (From:, To:, Subject:) are part of the message itself, transmitted inside the DATA block. They serve different purposes: SMTP commands route the message through the network; headers are displayed to the user.

Bcc: (Blind Carbon Copy) — Envelope vs. Headers

The Bcc: (Blind Carbon Copy) header demonstrates a key distinction between the SMTP envelope and the message headers. Recipients listed in the Bcc: field are included in the SMTP envelope via RCPT TO commands, so the mail server delivers the message to them. However, the Bcc: recipients are not listed in the message headers transmitted inside the DATA block. As a result, the primary (To:) and carbon copy (Cc:) recipients have no way of knowing that Bcc: recipients also received the message.

This illustrates a broader principle: the envelope (MAIL FROM, RCPT TO) governs actual delivery, while the headers (From:, To:, Cc:, Bcc:) govern what is displayed to the user. They can, and sometimes do, differ.

The Problem: SMTP is Push-Only

SMTP is a push protocol — it pushes messages from sender to receiver. But reading mail requires a pull operation: the recipient must fetch messages from their mailbox to their local device.

⚠ Bob cannot run a mail server on his laptop. Mail servers must be always on and always connected to the Internet. A typical user's device (laptop, phone) is not suitable. Instead, Bob's mail server at hamburger.edu runs 24/7 and stores his mail; Bob pulls messages from it using an access protocol.

IMAP (RFC 3501)

Internet Mail Access Protocol (IMAP) is a pull protocol that allows users to manage their e-mail on a remote server. Key features:

  • Messages remain on the server — the client views/manipulates them remotely
  • Supports folder hierarchies (Inbox, Sent, custom folders)
  • Allows partial retrieval (e.g., fetch headers without bodies)
  • Keeps state across sessions (read/unread flags, message deletions)
  • Runs over TCP, typically port 143 (or 993 for IMAPS)

Worked Examples

Example 1: Complete SMTP Dialogue — Alice to Bob

Scenario: Alice (alice@crepes.fr) sends a message to Bob (bob@hamburger.edu) about their networking project. The connection is established between crepes.fr (client) and hamburger.edu (server).

S: 220 hamburger.edu SMTP service ready C: HELO crepes.fr S: 250 Hello crepes.fr, pleased to meet you C: MAIL FROM: <alice@crepes.fr> S: 250 OK C: RCPT TO: <bob@hamburger.edu> S: 250 OK C: DATA S: 354 Start mail input; end with <CRLF>.<CRLF> C: From: alice@crepes.fr C: To: bob@hamburger.edu C: Subject: Project update C: C: Hi Bob, C: C: I have finished the network topology C: diagram. Let me know if you have any C: suggestions. C: C: Best, C: Alice C: . S: 250 OK, message accepted for delivery C: QUIT S: 221 hamburger.edu closing connection

Analysis: The client sends 4 commands (HELO, MAIL FROM, RCPT TO, DATA) before the message, the message body with 10 header/body lines, a dot terminator, and QUIT. This entire exchange uses a single persistent TCP connection.

Example 2: Telnet into an SMTP Server

Scenario: A user manually uses telnet to connect to an SMTP server and send an e-mail. This demonstrates the raw protocol without a client.

Example 3: Web-based E-mail — Full Journey

Scenario: Alice sends an e-mail from her Gmail account (alice@gmail.com) to Bob, who reads it using an IMAP client (Apple Mail). Trace the full protocol chain.

Step 1: Alice composes in browser at mail.google.com │ │ HTTP POST (TLS encrypted) ▼ Step 2: Gmail server receives message │ │ SMTP over TCP (port 25 or 587) ▼ Step 3: Gmail's mail server → gmail-smtp.google.com │ resolves MX record for hamburger.edu │ connects to bob's mail server ▼ Step 4: SMTP handshake (HELO, MAIL FROM, RCPT TO) │ message transferred inside DATA ▼ Step 5: Bob's mail server (hamburger.edu) │ places message in bob's mailbox │ │ IMAP (port 143) — Bob's client connects ▼ Step 6: Apple Mail on Bob's MacBook │ IMAP SELECT INBOX │ IMAP FETCH (retrieves message) ▼ Step 7: Bob reads the message in Apple Mail

Protocols used: HTTP (composition), SMTP (server-to-server), IMAP (retrieval). This shows that SMTP is only part of the chain — it handles the push between servers.
