Peer-to-Peer File Distribution

Computer Networking — Kurose & Ross Ch.2 — Interactive Study Guide

Architecture Comparison

In a client-server architecture, an always-on infrastructure server transmits a complete copy of the file to each requesting peer individually. The server bears the entire burden of upload bandwidth.

In a peer-to-peer (P2P) architecture, there is minimal (or no) reliance on always-on infrastructure servers. Instead, the participating peers — intermittently connected hosts such as PCs, laptops, and smartphones — communicate directly with one another. Each peer can re-distribute the portions of the file it has already received to other peers.

Client-Server

✗ Server sends N copies (once per peer)

✗ Upload capacity fixed at server

✗ Scales poorly with N

✗ Single point of failure

Peer-to-Peer

✓ Each peer redistributes received chunks

✓ Peers contribute their own upload capacity

✓ Self-scaling — more peers = more capacity

✓ No single point of failure

Core Insight:
Self-Scalability Property
In P2P, each peer that joins not only consumes service (downloads) but also adds service capacity (uploads). This is the fundamental architectural advantage over client-server, where only the server provides capacity.
⚠ Warning: P2P faces security, performance, and reliability challenges. Malicious peers can distribute corrupted content or poison the DHT with fake records. Peers can leave at any moment (churn), causing data loss if rare chunks disappear. NAT/firewall traversal adds significant complexity to peer discovery and connectivity. P2P traffic is also not ISP-friendly due to unpredictable bandwidth consumption and cross-continental traffic patterns. Designers must carefully weigh these challenges against P2P's scalability benefits.

How Peers Interact

Peers are intermittently connected — a laptop user may join the swarm from a coffee shop, download some chunks, close the lid, and continue later from a different IP address. The P2P protocol must handle this churn gracefully. Peers can also change IP addresses between sessions, requiring tracker-based discovery each time they rejoin.

Distribution Time: Mathematical Model

We model the file distribution problem for a file of size F bits, distributed from a single server to N peers.

Variables

FFile size (bits)
usServer upload rate (bits/sec)
uiUpload rate of peer i (bits/sec)
diDownload rate of peer i (bits/sec)
dminMinimum download rate across all peers = min(d1, d2, ..., dN)
NNumber of peers
Client-Server Distribution Time:
Dcs = max( N · F / us , F / dmin )
The server must upload N copies (one per peer). The bottleneck is either the server's upload capacity (N·F/us) or the slowest peer's download rate (F/dmin).
P2P Distribution Time:
DP2P = max( F / us , F / dmin , N · F / (us + Σui) )
The server uploads only once. The other N−1 copies are uploaded by peers. The total upload capacity is us + Σui. For large N, the third term dominates.

Client-Server Scaling

Dcs ∝ N

Doubling the number of peers roughly doubles the distribution time (when server upload is the bottleneck).

P2P Scaling

DP2P grows slowly with N

Since Σui grows with N, the denominator keeps the distribution time bounded. This is the self-scaling property.

Why P2P Is Self-Scaling — Intuition

Imagine 10 friends at a party. One friend (the server) knows a song. In client-server mode, the server sings the song to each friend individually — 10 performances. In P2P mode, the server sings it once. The first two friends who learned it can each sing it to two others. Those four can sing to four more, and so on. The more friends arrive, the more "singers" there are to help. This logarithmic spread is the intuition behind P2P's self-scaling property.

⚠ Key Exam Point: For client-server, Dcs grows linearly with the number of peers N. For P2P, DP2P is approximately proportional to 1/(us + Σui), which for large N means the distribution time remains bounded as long as average peer upload rates stay constant.

The BitTorrent Protocol

BitTorrent is the most widely deployed P2P file distribution protocol. It organizes participating peers into a structured system for efficient, decentralized file sharing.

History

BitTorrent was originally developed by Bram Cohen. Just as there are many browser clients conforming to the HTTP protocol, there are many different independent BitTorrent clients conforming to the BitTorrent protocol. The protocol's open design has led to a rich ecosystem of interoperable clients.

Key Concepts

Torrent

A torrent is the collection of all peers participating in the distribution of a particular file. A .torrent metadata file contains information about the file structure and the tracker address.

Chunks

Files are divided into chunks, typically 256 KB each. Chunks are the fundamental unit of data exchange. A peer must have the complete chunk before it can upload it to others.

Tracker

An infrastructure node that tracks which peers are currently participating in the torrent. The tracker keeps track of peers that are participating in the torrent. When a peer joins, it registers itself with the tracker and periodically informs the tracker it is still in the torrent. When a new peer contacts the tracker, it receives a list of 50 random peer IP addresses. A torrent may have fewer than ten or more than a thousand peers at any instant.

Peer Joining Process

  1. User obtains a .torrent file (or magnet link) pointing to the tracker.
  2. Client contacts the tracker; tracker responds with 50 randomly selected peer IPs.
  3. Client attempts TCP connections with all peers on the list. Those with successful TCP connections become neighboring peers. Over time, some leave and others join, so neighboring peers fluctuate.
  4. Client exchanges have messages to learn which chunks each neighbor possesses.
  5. Client requests chunks using a rarest-first strategy.

Chunk Exchange Details

Once neighboring peers are established, Alice asks each neighbor for a list of chunks they have (over TCP). She obtains L lists (one per neighbor), which she uses to build a complete picture of chunk availability. She then requests chunks she does not yet have. This involves two key decisions: which chunks to request first and which neighbors to send chunks to (the latter is governed by tit-for-tat).

Rarest-First Chunk Selection:
request(chunks) = argminc countneighbors(c)
A peer requests the chunk that has the fewest copies among its neighbors. This ensures rare chunks spread quickly, improving overall swarm resilience.

Detailed Strategy Descriptions

Rarest first: A peer determines the rarest chunks among its neighbors and requests those first. This ensures rare chunks spread quickly, improving overall swarm resilience.

Random first selection: New peers who have no chunks yet request a random chunk. This lets them quickly obtain their first complete chunk and begin contributing to the swarm.

Endgame mode: When a peer has all but the last few chunks, it requests these remaining chunks from all neighbors simultaneously. This avoids a single slow peer from bottlenecking the completion of the download.

Pipelining: Multiple chunk requests can be sent over a single TCP connection without waiting for each reply. This keeps the connection fully utilized and improves throughput.

Peer Departure

Once a peer has obtained the entire file, it has two options:

  • Altruistic stay: Remain in the swarm and continue uploading to others, helping the system.
  • Selfish leave: Depart immediately after completing the download (a free-rider behavior).

Because peers may leave at any time and rejoin later (possibly with different IPs), the protocol must be robust to churn. The tracker periodically checks in with peers to maintain an up-to-date membership list.

Additional BitTorrent Mechanisms

Pieces (mini-chunks): Chunks are further divided into smaller sub-units called pieces (typically 16 KB). This allows finer-grained exchange — a peer can request a single piece rather than an entire chunk, reducing waste if a transfer is interrupted.

Anti-snubbing: If a peer finds that it is choked by all of its top uploaders (i.e., none of them are sending data to it), it concludes it has been "snubbed." In response, it stops uploading to those peers. This prevents a peer from being exploited by uploaders who accept data but never reciprocate.

Distributed Hash Table (DHT)

A Distributed Hash Table (DHT) is a simple database distributed over the peers in a P2P system. It has been widely implemented — notably in BitTorrent — and has been the subject of extensive research. DHT enables trackerless torrents: peers can find each other without relying on a central tracker. Instead of contacting a single tracker to get peer IPs, the DHT stores mappings from info-hashes to peer addresses across the swarm itself. This removes the central point of failure and makes the system more resilient against tracker takedowns.

Tit-for-Tat: Incentive Mechanism

Tit-for-tat is BitTorrent's core trading incentive. Without it, peers would have no reason to upload — everyone would free-ride. Tit-for-tat ensures that peers who contribute more get better service.

How It Works

  1. Alice measures the download rates she receives from each of her neighbors.
  2. She ranks the neighbors by their contributed download rate.
  3. The top 4 uploaders are unchoked — Alice will upload chunks to them.
  4. All other neighbors are choked — they receive no chunks from Alice.
  5. Every 30 seconds, Alice performs optimistic unchoking: she randomly selects one additional (currently choked) peer and unchokes it.
Tit-for-Tat Decision Rule:
unchoked = topK(neighbors, rate_to_us, k=4) ∪ { random_other_neighbor }
A peer uploads to the 4 neighbors that send data fastest, plus one random additional peer (optimistic unchoke) every 30 seconds.

Algorithm: BitTorrent Tit-for-Tat

FUNCTION TitForTat(neighbors): // neighbors = set of connected peers // each neighbor has a measured download rate FOR each neighbor n IN neighbors: measure download_rate[n] // bytes/sec from n // Sort by rate descending sorted = sort(neighbors, key=download_rate, order=descending) // Unchoke top 4 uploaders top4 = sorted[0:4] FOR n IN top4: unchoke(n) // Choke everyone else FOR n IN neighbors \ top4: choke(n) // Optimistic unchoke every 30 seconds IF timer_elapsed >= 30_000 ms: candidate = random_select(neighbors \ top4) unchoke(candidate) reset_timer() // Reciprocation: only upload to those who upload to us

Optimistic Unchoking

Every 30 seconds, a random choked peer is unchoked. This allows new peers who have nothing to trade to obtain their first chunk. Once they have a chunk, they can begin reciprocating with others.

Rate Compatibility

Peers with compatible upload/download rates naturally cluster. A peer with a fast connection will be unchoked by others with fast connections, creating a "fast lane" where high-speed peers trade among themselves.

Tit-for-Tat in Action

Bob has 10 neighbors. He measures download rates (in KB/s): A=120, B=95, C=80, D=75, E=60, F=45, G=30, H=20, I=10, J=5. Bob unchokes A, B, C, D (top 4). After 30 seconds, Bob randomly picks H (from the 6 choked peers) and gives H one chunk. Now H has something to trade with other peers. If H later uploads fast to Bob, H may enter the top 4 on the next round.

⚠ Without Tit-for-Tat: In a system with no reciprocity enforcement, rational peers would never upload. Every peer would download then leave. The system would collapse — no peer would have anything to share, and the file would never be distributed beyond the initial seed. Tit-for-tat solves this by aligning individual incentives with system-wide efficiency.

The Free-Riding Problem

Without tit-for-tat (or a similar incentive mechanism), the majority of users would become free-riders — they would download the file and immediately leave without uploading to anyone else. A study by Saroiu et al. [Saroiu 2002] showed that this behavior would cause the system to collapse: as more peers free-ride, fewer uploaders remain, download speeds drop, and eventually no peer can complete a download. As the textbook notes: "If BitTorrent had been designed without tit-for-tat (or a variant), but otherwise exactly the same, BitTorrent would likely not even exist now." Tit-for-tat solves this by creating a direct incentive to upload: a peer who does not upload will be choked by others and will experience poor download speeds.

Game Theory Perspective

Tit-for-tat is a well-studied strategy in repeated Prisoner's Dilemma games. It is:

  • Nice: Starts by cooperating (optimistic unchoke gives first chunk)
  • Retaliatory: Chokes peers who do not upload (reciprocates defection)
  • Forgiving: If a choked peer starts uploading again, it can re-enter the top 4
  • Clear: The rule is simple and easy for peers to follow

Worked Examples

Example 1: Client-Server Distribution Time

Given: N = 100 peers, F = 1 GB (8 × 109 bits), us = 10 Mbps (107 bps), dmin = 5 Mbps (5 × 106 bps).

Compute Dcs:

Term 1: N · F / us = (100 × 8 × 109) / 107 = 8 × 1011 / 107 = 80,000 sec ≈ 22.22 hours

Term 2: F / dmin = (8 × 109) / (5 × 106) = 1,600 sec ≈ 26.67 min

Dcs = max(80000, 1600) = 80,000 sec ≈ 22.22 hours

The server's upload capacity is the bottleneck. The server must upload 100 copies.

Example 2: P2P Distribution Time

Given: Same parameters as Example 1, with Σui = 50 Mbps (5 × 107 bps) total upload capacity from all peers.

Compute DP2P:

Term 1: F / us = (8 × 109) / 107 = 800 sec ≈ 13.33 min

Term 2: F / dmin = (8 × 109) / (5 × 106) = 1,600 sec ≈ 26.67 min

Term 3: N · F / (us + Σui) = (100 × 8 × 109) / (107 + 5 × 107) = (8 × 1011) / (6 × 107) ≈ 13,333 sec ≈ 3.70 hours

DP2P = max(800, 1600, 13333) ≈ 13,333 sec ≈ 3.70 hours

P2P completes the distribution in 3.70 hours vs. 22.22 hours for client-server — a 6× improvement. As N grows, P2P's advantage widens.

Example 4: BitTorrent — Alice Joins a Torrent

Scenario: Alice wants to download "linux.iso". She joins a torrent with 200 existing peers.

Step-by-step flow:

  1. Alice opens the .torrent file, revealing the tracker URL and file hash.
  2. Alice's client contacts the tracker with a GET request announcing her presence and capabilities.
  3. The tracker responds with a list of 50 randomly selected peer IP addresses (e.g., Bob, Carol, Dave, ...).
  4. Alice's client opens TCP connections to these peers. Not all may accept — some may be behind restrictive NATs.
  5. Alice sends have messages (she has nothing initially) and receives have messages from neighbors.
  6. Using rarest-first, Alice identifies that chunk #42 is held by only 2 of 50 neighbors, while most chunks are held by 10+. She requests chunk #42 first.
  7. Bob sends Alice chunk #42. Alice verifies its hash, stores it, and now sends have(42) to all her neighbors.
  8. Other peers (who need chunk #42) can now request it from Alice. Alice has become a provider!
  9. Alice continues until she has all chunks, then decides to stay as a seed (altruist).
