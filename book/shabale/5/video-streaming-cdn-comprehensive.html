Video Streaming & Content Distribution Networks

Computer Networking (Kurose & Ross, Ch. 2) — Exam Study Guide

Fundamentals of Internet Video

Video is the dominant traffic type on the Internet today, accounting for over 80% of all consumer traffic. Understanding how video is compressed, transmitted, and rendered is essential to grasp modern networking challenges.

Streaming Video Traffic Statistics

Cisco 2020 Estimate

Streaming video accounts for approximately 80% of all Internet traffic (Cisco 2020 estimate). The three major streaming video services are Netflix, YouTube, and Amazon Prime Video.

Video Representation

A video is a sequence of images (frames) displayed at a constant rate. Each image is a rectangular array of pixels, and each pixel is represented by a number of bits encoding luminance (brightness) and chrominance (color).

Video Bit Rate Formula:
Bit Rate = Frame Rate × Resolution × Bits Per Pixel × Compression Ratio
The actual bit rate depends heavily on the compression algorithm and content complexity

Frame Rates

• 24 fps — Film standard

• 30 fps — NTSC TV standard

• 60 fps — High-motion / sports

Typical Bit Rates

• Low quality: 100 kbps

• SD (480p): 1-2 Mbps

• HD (1080p): 4-8 Mbps

• 4K UHD: 10-20+ Mbps

Key Insight

A 67-minute video at 2 Mbps requires roughly 1 GB of storage.

⚠ Warning: Without sufficient average end-to-end throughput (≥ video bit rate), video streaming suffers freezing delays, rebuffering events, and poor user experience.

Compression Trade-offs

Compression reduces bit rate by exploiting redundancy between frames (temporal compression) and within frames (spatial compression). Higher compression means lower quality. Content providers create multiple versions of the same video at different bit rates — for example, at 300 kbps, 1 Mbps, and 3 Mbps — to serve diverse network conditions.

⚠ Warning: A video encoded at too low a bit rate will appear blocky and pixelated. There is no free lunch — bit rate and visual quality are fundamentally traded off.

Streaming Performance Metric

The key performance measure is whether average end-to-end throughput meets or exceeds the video bit rate. If throughput drops below the encoding bit rate, the playback buffer drains, causing stalls.

Condition for Smooth Playback:
Average Throughput ≥ Video Encoding Bit Rate
If this condition holds over the duration of playback, the user experiences no rebuffering

HTTP Streaming

In traditional HTTP streaming, the video is stored as a regular file on an HTTP server. The client downloads it as quickly as the network allows, buffering the received data. Playback begins once a minimum threshold of data (say, 10 seconds worth) has been buffered.

⚠ Problem: In simple HTTP streaming, all clients receive the same encoded video regardless of their available bandwidth. A user on a 50 Mbps connection gets the same low-bit-rate file as a user on a 1 Mbps connection.

Limitations of Simple HTTP Streaming

Issue 1: No Adaptation

Every client gets the same encoding. Mobile users with fluctuating bandwidth suffer, while high-bandwidth users waste capacity.

Issue 2: Buffer Bloat

The client downloads faster than playback, filling the buffer. But if bandwidth drops late in the session, the buffer drains and the user sees a freeze.

DASH — Dynamic Adaptive Streaming over HTTP

DASH solves the limitations of simple HTTP streaming by encoding the video into multiple versions at different bit rates. A manifest file (MPD — Media Presentation Description) lists the URLs for each version along with the bit rate and resolution information.

How DASH Works

1. Video is encoded into chunks (2-10 seconds each) at multiple quality levels.

2. A manifest file tells the client where to find each chunk.

3. The client measures its current bandwidth.

4. The client requests the next chunk from the appropriate quality level.

5. If bandwidth drops, the client switches to a lower bit rate; if it improves, it switches up.

DASH Client Bitrate Selection Algorithm (Pseudocode)

algorithm DASH_AdaptiveBitrateSelection
  // called before requesting the next chunk
  input: available_rates[] ← list of bit rates from manifest
  input: buffer_level ← current playback buffer (seconds)
  input: throughput_estimate ← estimated current throughput

  if buffer_level < BUFFER_LOW_THRESHOLD then
    selected_rate ← min(available_rates) // play it safe
  else if buffer_level > BUFFER_HIGH_THRESHOLD then
    selected_rate ← max(available_rates) // take advantage
  else
    // pick highest rate that throughput can support
    selected_rate ← max{ r ∈ available_rates | r ≤ throughput_estimate × SAFETY_FACTOR }
  end if
  return selected_rate

Adaptation Benefits

• Mobile users maintain playback under fluctuating wireless conditions

• High-bandwidth users get the best available quality

• No single encoding for all — truly personalized streaming

Chunk Duration

Typical chunk sizes: 2-10 seconds

Netflix uses ~4-second chunks

Shorter chunks = more responsive adaptation but more overhead

Manifest File (MPD) — Detailed Role

The MPD (Media Presentation Description) is the manifest file that serves as the roadmap for DASH streaming. It provides the URL for each version (bit rate and resolution) of the video content. The client workflow is:

  1. The client first requests the manifest file from the server and learns about all available versions (bit rates, resolutions, chunk URLs).
  2. The client then selects chunks one at a time, specifying both the URL and the exact byte range for the desired chunk within the file.

HTTP Byte-Range Requests

Both Netflix and YouTube use HTTP byte-range requests for efficient video delivery. A byte-range request allows the client to request a specific range of bytes from a resource rather than downloading the entire file. This is essential for:

  • Seeking: When a user skips to the middle of a video, only the bytes for that segment are fetched rather than the entire video file.
  • DASH chunk selection: Multiple video chunks can be stored in a single file, and the client requests only the byte range corresponding to the desired chunk and quality level.

HTTP byte-range requests are implemented using the Range header (e.g., Range: bytes=1048576-2097151). The server responds with 206 Partial Content and delivers only the requested bytes.

Why CDNs?

A single data center serving video to the entire world suffers from three critical problems:

Problem 1: Distance

Users far from the data center experience high latency, packet loss, and reduced throughput, making high-quality streaming impossible.

Problem 2: Repeated Traffic

The same popular video is transmitted across the same long-haul links millions of times, wasting backbone capacity.

Problem 3: Single Point of Failure

If the data center goes down, the entire service goes down. A hardware failure or DDoS attack takes everything offline.

CDN Definition

A Content Distribution Network (CDN) manages geographically distributed servers that store copies of content. When a user requests a video, the CDN directs them to the best server — typically the closest one with available capacity.

Two Placement Philosophies

1. Enter Deep (Akamai's approach)

Deploy server clusters deep within access ISPs — thousands of locations worldwide, often inside the ISP's own facilities. Servers are very close to end users, minimizing the last-mile distance.

  • Thousands of locations
  • Very close to end users (low latency)
  • High maintenance and deployment cost
  • Complex management — negotiating with each ISP individually

2. Bring Home (Limelight's approach)

Build large, powerful clusters at Internet Exchange Points (IXPs) where multiple ISPs interconnect. Fewer locations, typically tens of clusters, each serving a wider region.

  • Tens of locations
  • Higher latency per user compared to Enter Deep
  • Lower maintenance and deployment cost
  • Easier to manage — fewer peering agreements needed

Content Replication Strategies

Pull Caching (On-Demand)

When a user requests content not currently stored at a CDN node, the node fetches it from the origin server and caches it. Subsequent requests for the same content are served locally. Cache replacement policies (LRU, LFU) manage storage.

Push Caching (Pre-positioning)

Content is proactively pushed to CDN servers during off-peak hours (e.g., 2 AM). This is ideal for popular content with predictable demand, like Netflix's latest original series.

How CDNs Direct Clients to Servers

The fundamental question: when a user clicks "Play" on a video, how does the CDN decide which of its thousands of servers should serve that user?

DNS Redirect — The Key Mechanism

CDNs use the Domain Name System to steer clients to the optimal server. Here is the step-by-step flow:

[User] clicks link to http://video.NetCinema.com/6Y7u2p1
  ↓
[Client] sends DNS query for video.NetCinema.com
  ↓
[NetCinema authoritative DNS] responds with CNAME: video.NetCinema.com → a790.kingcdn.com
  ↓
[Client] sends DNS query for a790.kingcdn.com
  ↓
[KingCDN authoritative DNS] returns IP address of optimal CDN server
  ↓
[Client] connects directly to that CDN server and requests the video over HTTP

DNS Redirect Summary

1. Content provider's DNS returns a CNAME pointing to the CDN's domain.

2. The client then resolves the CDN's hostname.

3. The CDN's DNS returns the "best" server IP for that client.

4. The client connects directly to that server.

Cluster Selection Strategies

The CDN's DNS must decide which server IP to return. Two main approaches:

1. Geographically Closest

Use geo-location databases (Quova, MaxMind) to map the client's LDNS IP address to a geographic location. Return the server closest to that location.

Pro: Simple, no extra probing traffic.

Con: Client's LDNS may be far from the client itself (e.g., a corporate DNS server in another city).

2. Real-Time Measurements

CDN periodically probes the LDNS servers of major ISPs to measure RTT and loss rates. When a request arrives from an LDNS, the CDN uses the most recent probe results to select the best server.

Pro: Reflects actual network conditions.

Con: Requires ongoing probing; may not capture transient congestion.

⚠ Pitfall: Some clients use remotely located LDNS servers (e.g., a user in Europe with their company's DNS server in the US). In this case, geo-location based on the LDNS IP would select a server in the US — the opposite of what is optimal.

Netflix

Netflix is the world's leading streaming service, accounting for a significant fraction of North American Internet traffic. Its architecture has evolved over time to handle massive scale.

Architecture Overview

  • Cloud processing: Netflix uses Amazon Web Services (AWS) for video ingestion, encoding, and content management. Raw studio content is uploaded to AWS, processed into multiple bit rate versions, and packaged into DASH-compatible chunks (~4 seconds each).
  • Open Connect (private CDN): Netflix built its own CDN called Open Connect, deployed in 200+ IXPs and hundreds of ISP facilities. This gives Netflix full control over the delivery infrastructure.
  • Push caching: During off-peak hours, Netflix pushes its most popular content to Open Connect appliances located inside ISP networks. The ISP serves content locally rather than fetching it from Netflix's origin every time.
  • Proprietary DASH: Netflix uses a custom DASH implementation with ~4-second chunks. The client adaptively selects bit rates based on throughput measurements.
  • Server selection: The server selection logic runs in Amazon cloud software. When a client starts a session, cloud software determines which Open Connect appliance should serve that user, considering location, load, and content availability.

Netflix CDN History

When Netflix first rolled out video streaming in 2007, it relied on three third-party CDN companies (Akamai, Limelight, and Level-3) to deliver its content. However, as Netflix grew to become one of the largest sources of Internet traffic, the cost of third-party CDN services became prohibitive. Netflix developed its own private CDN called Open Connect. Today, Netflix streams all of its video content from its own private CDN infrastructure.

Open Connect Hardware Details

Netflix's Open Connect servers are deployed as server racks installed in Internet Exchange Points (IXPs) and within residential ISP networks:

  • 200+ IXP locations — Netflix has racks of servers in over 200 IXPs worldwide
  • Hundreds of ISP locations — Netflix racks are embedded inside residential ISP networks
  • Network connectivity: Each server has several 10 Gbps Ethernet ports
  • Storage capacity: Each server has over 100 terabytes of storage
  • IXP clusters: IXP installations often have tens of servers storing the entire Netflix library
  • ISP hosting: ISPs host Netflix racks for free because it saves them significant transit costs — content is served locally rather than traversing the public Internet

Push Caching — Scheduling Detail

Netflix uses push caching (not pull caching) to populate its CDN servers. Content is pushed to Open Connect appliances during off-peak hours, typically late at night when network utilization is low. For IXP and ISP locations that cannot hold the entire Netflix library (limited storage), only the most popular videos are pushed to those servers. Popularity is determined on a day-to-day basis — the set of videos stored at each location is updated daily based on changing viewing patterns.

Server Selection — Detailed Flow

When a user selects a movie or TV show, the following detailed process takes place:

  1. Netflix software running in the Amazon cloud (AWS) first determines which CDN servers have copies of the requested content.
  2. Among the servers that have the content, the software determines the "best" server for that particular client.
  3. Decision rule: If the client's ISP is a residential ISP that hosts a Netflix rack, that rack is selected. Otherwise, a nearby IXP server is selected.
  4. The client receives the IP address of the specific server along with a manifest file containing the URLs and bit rate information for the video chunks.

YouTube (Google)

YouTube is the largest video-sharing platform, serving billions of users with content ranging from 240p user-uploaded clips to 4K professional content.

Architecture Overview

  • Three-tier private CDN: Google operates a massive private CDN with three tiers:
    • Tier 1: Mega data centers (origin storage)
    • Tier 2: IXP clusters (regional caches)
    • Tier 3: Enter-deep caches (inside ISP networks, similar to Akamai)
  • Pull caching: YouTube CDN nodes pull content on demand. If a video is not cached at a nearby node, it is fetched from the next tier or the origin.
  • DNS redirect: Google uses DNS to direct users to the nearest YouTube cache. The DNS response varies based on the user's geographic region and the load on available caches.
  • HTTP streaming (traditional approach): YouTube primarily served video using progressive HTTP download for many years. The user manually selects the quality (e.g., 720p, 1080p) rather than automatic adaptation.
  • HTTP byte-range requests: To save bandwidth, YouTube supports byte-range requests — if a user seeks to the middle of a video, only the requested byte range is fetched rather than the entire file.

Google's Network Infrastructure

Google operates a massive private network infrastructure consisting of three tiers:

  • Mega data centers: Approximately 19 locations worldwide, each containing ~100,000 servers. These serve as the origin storage and processing hubs.
  • IXP clusters: Approximately 90 clusters located at Internet Exchange Points, each with hundreds of servers. These cache content closer to regional populations.
  • Enter-deep clusters: Hundreds of smaller clusters (tens of servers each) located deep within ISP networks, similar to Akamai's approach.

All three tiers are connected via Google's own private network, not the public Internet. A single user request for a YouTube page may pull different components from different tiers: the YouTube video may come from a bring-home (IXP) cache, the Web page HTML from an enter-deep cache, and advertisements from a data center. Except for the connection to the local ISP, Google's cloud services are largely independent of the public Internet. Google's enter-deep servers also perform TCP splitting, terminating the client TCP connection and maintaining a separate optimized connection to Google's internal network.

YouTube Upload Process

Millions of videos are uploaded to YouTube every day. The upload process works as follows:

  • Videos are uploaded over HTTP from the client to YouTube's servers.
  • YouTube converts each uploaded video to the YouTube format (e.g., VP9 or H.264 codecs).
  • Multiple bit rate versions are created from each upload to support different connection speeds and device capabilities.
  • All processing — conversion, encoding, and bit rate ladder generation — takes place entirely within Google's data centers.

Worked Examples

Example 1: Storage Calculation for a Movie

Problem: Calculate the storage needed to store a 90-minute movie encoded at 3 Mbps (megabits per second).

Given: Duration = 90 min = 90 × 60 = 5,400 seconds. Bit rate = 3 Mbps = 3 × 106 bits/second.

Step 1: Total bits = 5,400 s × 3 × 106 bits/s = 16.2 × 109 bits.

Step 2: Convert to bytes: 16.2 × 109 / 8 = 2.025 × 109 bytes.

Step 3: Convert to gigabytes: 2.025 × 109 / (109) = 2.025 GB.

Answer: Approximately 2.03 GB of storage is needed for one 90-minute movie at 3 Mbps.

Note: If Netflix stores 10,000 titles with 5 quality versions each, total storage ≈ 10,000 × 5 × 2.03 GB ≈ 101,500 GB ≈ 101.5 TB just for the video files.

Example 2: DASH Adaptation in Action

Scenario: A user starts watching a video on their phone while on a 4G connection. The available bit rates in the manifest are: 300 kbps (360p), 1 Mbps (720p), 3 Mbps (1080p).

Time t=0: The client measures throughput at 600 kbps. It selects the 300 kbps stream (below throughput × 0.85 safety factor = 510 kbps, cannot support 1 Mbps). Playback starts at 360p.

Time t=15s: The user enters a building with weaker signal. Throughput drops to 200 kbps. The client switches to 300 kbps — but even this is above throughput. The buffer starts draining.

Time t=25s: Buffer is critically low. The client either continues at 300 kbps with rebuffering, or the player may need to pause and re-buffer.

Time t=40s: The user moves near a window. Throughput climbs to 2.5 Mbps. The client detects this and switches to 1 Mbps (720p) for the next chunk.

Time t=60s: Throughput reaches 5 Mbps. The client switches to 3 Mbps (1080p). Smooth playback at highest quality.

Key insight: DASH allows the quality to follow the available bandwidth dynamically. Without DASH, the user would be stuck at a single quality — either too low (wasting capacity at t=60) or too high (causing constant rebuffering at t=15).

Example 3: CDN DNS Redirect — Trace the Flow

Scenario: A user in Paris, France, wants to watch a video from NetCinema, which uses KingCDN as its third-party CDN.

Step 1: User clicks http://video.NetCinema.com/movie1.mp4.

Step 2: User's browser sends DNS query for video.NetCinema.com to the local DNS resolver (LDNS) provided by their ISP, say dns.francetelecom.fr.

Step 3: The LDNS resolver queries the root and .com DNS servers, eventually reaching NetCinema's authoritative DNS server.

Step 4: NetCinema's DNS returns a CNAME record: video.NetCinema.com → cdn.kingcdn.com.

Step 5: The LDNS resolver now queries KingCDN's authoritative DNS for cdn.kingcdn.com.

Step 6: KingCDN's DNS sees the query comes from dns.francetelecom.fr. Using geo-location (MaxMind), it knows this DNS server is in Paris. It checks which of its European servers has the lowest load and returns the IP 92.128.4.77 — a KingCDN server in Frankfurt with available capacity.

Step 7: The user's browser connects directly to 92.128.4.77 and requests the video via HTTP. The Frankfurt server has the content cached (pushed during off-peak hours) and serves it directly.

End result: The user in Paris is served from Frankfurt (~800 km away) instead of from a server in Virginia, USA (~6,200 km away). Latency drops from ~80 ms to ~15 ms.

DASH Algorithm Summary

1. Fetch manifest (MPD file) → get list of available bit rates and chunk URLs.

2. Measure recent throughput (e.g., weighted moving average of last 5 chunk downloads).

3. Check buffer level: if low, step down; if high, step up.

4. Select the highest bit rate ≤ throughput × safety factor (typically 0.75-0.90).

5. Request next chunk at selected quality. Repeat from step 2.

⚠ Common Exam Mistake: Students confuse push caching (proactive, scheduled) with pull caching (reactive, on-demand). Remember: Netflix pushes to Open Connect; YouTube pulls into its caches. The choice depends on content predictability.
