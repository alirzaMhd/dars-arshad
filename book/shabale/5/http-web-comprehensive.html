HTTP — The Web Protocol

Kurose & Ross · Computer Networking · Chapter 2 — Complete Study Guide

What is HTTP?

HyperText Transfer Protocol (HTTP) is the Web's application-layer protocol. It defines how messages are formatted and transmitted between Web browsers (clients) and Web servers.

Core Definition

• HTTP = HyperText Transfer Protocol

• Application-layer protocol for the Web

• Client-server architecture

• Uses TCP as its transport protocol

Key Properties

• Stateless — server remembers nothing

• Default port: 80

• Text-based (human-readable headers)

• Extensible via headers

Web Pages & Objects

A web page consists of a base HTML file and several referenced objects. Each object is addressable by a URL (Uniform Resource Locator).

URL Structure:
URL = hostname + path name
Example: http://www.example.com/images/photo.jpg → hostname = www.example.com, path = /images/photo.jpg

Client-Server Architecture

Client = Web browser (Chrome, Firefox, Safari) that initiates HTTP requests. Server = Web server (Apache, Nginx, IIS) that stores objects and sends responses.

HTTP REQUEST / RESPONSE FLOW: ────────────────────────────────────── 1. Client establishes TCP connection to server (port 80) 2. Client sends HTTP request message over TCP 3. Server processes request 4. Server sends HTTP response message (with requested object) 5. TCP connection may close or remain open (see Tab 2)
HTTP is stateless! If a client requests the same object twice, the server does not remember having seen that client before. State is maintained via cookies (Tab 4).

Non-Persistent vs Persistent Connections

HTTP can operate over non-persistent or persistent TCP connections. HTTP/1.0 used non-persistent by default; HTTP/1.1 uses persistent by default.

Non-Persistent Connections

Each request/response pair uses a separate TCP connection.

NON-PERSISTENT HTTP STEPS (for 1 object): ────────────────────────────────────────────── 1. Client opens TCP connection to server:port 2. Client sends HTTP request message 3. Server sends HTTP response message 4. Server closes TCP connection 5. Client reads full response 6. Repeat for each object in the page
Total Delay per Object (Non-Persistent):
Total Response Time = 2 × RTT + File Transmission Time
RTT = Round-Trip Time (time for a small packet to travel client → server → client).
1 RTT to establish TCP (SYN + SYN-ACK), then 1 RTT for request + response, then file transmission.
For a page with N objects, non-persistent HTTP requires N separate TCP connections. This means N × 2 RTT just for connection overhead! Modern browsers open 5–10 parallel connections to mitigate this.

Persistent Connections

Multiple objects are sent over the same TCP connection. HTTP/1.1 default mode.

PERSISTENT HTTP WITH PIPELINING: ────────────────────────────────────── 1. Client opens TCP connection 2. Client sends request for base HTML 3. Server responds 4. Client sends requests for all referenced objects (back-to-back, without waiting) 5. Server responds to each request in order 6. Connection remains open for future requests
Total Delay with Persistent Pipelining:
Total ≈ 1 × RTT (setup) + 1 × RTT (base) + 1 × RTT (all objects)
Only 1 TCP setup RTT total, then requests and responses overlap maximally.

Comparison: Non-Persistent vs Persistent

Feature Non-Persistent Persistent (HTTP/1.1)
TCP connections per page N (one per object) 1
RTT overhead (N objects) 2N × RTT ~3 × RTT (with pipelining)
Server memory load Lower (connections closed fast) Higher (keep-alive state)
Default in HTTP/1.0 HTTP/1.1
Pipelining support No Yes
Even with persistent connections, HTTP/1.1 suffers from Head-of-Line (HOL) blocking: a large object can delay small objects behind it. HTTP/2 solves this (see Tab 5).

HTTP/1.1 Parallel Connections

To circumvent HOL blocking, HTTP/1.1 browsers typically open up to 6 parallel TCP connections to the same server. This allows multiple requests to be processed concurrently.

Because TCP congestion control gives each connection approximately 1/nth of the available bandwidth, opening more parallel connections allows the client to grab a larger portion of the link's bandwidth. This effectively "cheats" the congestion control mechanism to improve performance.

HTTP Request Message

An HTTP request message has three parts: a request line, one or more header lines, and an optional entity body.

Request Message Format:
request line:   METHOD   URL   HTTP_VERSION
header lines:   HeaderName: value
    ...
(blank line)
entity body   (POST data, etc.)

HTTP Methods

Method Description Has Body? Idempotent?
GET Request an object No Yes
POST Submit data (form, etc.) Yes No
HEAD Request headers only (no body) No Yes
PUT Upload object to server Yes Yes
DELETE Delete object from server No Yes
Method Details:
• HEAD works like GET but returns only the response headers (no body) — used for debugging and checking resource existence without transferring the full object.
• PUT uploads an object to a specific path on the server (often used for REST APIs).
• DELETE removes an object from the server.
• HTML forms typically use GET or POST. With GET, form data is appended to the URL: www.somesite.com/animalsearch?monkeys&bananas

Example: HTTP Request

Example Request — Fetching a Web Page from a News Server
GET /sports/scores.html HTTP/1.1 Host: www.news-example.com User-Agent: Mozilla/5.0 (X11; Linux x86_64) Accept: text/html,application/xhtml+xml Accept-Language: en-US,en;q=0.5 Accept-Encoding: gzip, deflate Connection: keep-alive

Explanation:
• GET → request method (retrieve object)
• /sports/scores.html → path name (URL without hostname)
• HTTP/1.1 → protocol version
• Host: → required in HTTP/1.1 (enables virtual hosting)
• User-Agent: → browser identification
• Accept: → MIME types the client can process
• Accept-Language: → language preference (quality values)
• Connection: keep-alive → persistent connection requested

Request Headers — Important Details

Connection: close

Tells the server to close the TCP connection after sending the response (disables persistent connections).

User-Agent

Identifies the browser type. Servers can send different versions of the same object to different browsers based on this header.

Accept-Language

Enables content negotiation. The server can return a French version of the page if one is available, for example.

Host

The Host header is required in HTTP/1.1. It is needed by Web proxy caches and enables virtual hosting (multiple websites on one server).

HTTP Response Message

A response has a status line, header lines, and an entity body.

Response Message Format:
status line:   HTTP_VERSION   STATUS_CODE   PHRASE
header lines:   HeaderName: value
    ...
(blank line)
entity body   (requested object data)

HTTP Status Codes — Quick Reference Card

Example: HTTP Response

Example Response — Server Responds to the Above Request
HTTP/1.1 200 OK Date: Mon, 07 Jul 2025 14:30:22 GMT Server: Apache/2.4.57 (Ubuntu) Last-Modified: Sun, 06 Jul 2025 09:15:00 GMT Content-Length: 4820 Content-Type: text/html; charset=UTF-8 <!DOCTYPE html> <html> <head><title>Sports Scores</title></head> <body> <h1>Today's Scores</h1> <!-- ... 4820 bytes of HTML ... --> </body> </html>

Explanation:
• 200 OK → request succeeded
• Date: → server's clock when response generated
• Last-Modified: → used for conditional GET caching
• Content-Length: → exact byte count of entity body
• Content-Type: → MIME type of the returned object

Response Headers — Important Details

Server

Analogous to User-Agent on the request side. Indicates the server software, e.g., Apache/2.2.3.

Date

Represents the time when the HTTP response was created and sent by the server — not when the object was last modified.

Last-Modified

Indicates when the object was last changed on the server. Used by conditional GET for caching decisions.

Content-Type

Specifies the MIME type of the returned object (e.g., text/html). The type is officially indicated by this header, not by the file extension.

Content-Length

The number of bytes in the entity body. The client uses this to know when it has received the complete object.

Cookies — Maintaining State Over Stateless HTTP

Since HTTP is stateless, cookies allow servers to track user identity across requests. There are four components.

4 Cookie Components

1. Set-cookie header in HTTP response

2. Cookie header in HTTP request

3. Cookie file on client (managed by browser)

4. Back-end database on server

Common Uses

• Shopping cart 🛒

• User session identification

• Personalized content

• Tracking / analytics

COOKIE FLOW (First Visit): ───────────────────────────── 1. Browser sends GET /index.html 2. Server generates cookie-id "abc123" 3. Server sends: HTTP/1.1 200 OK Set-Cookie: session-id=abc123 4. Browser stores "abc123" in cookie file (domain: shop-example.com) 5. On subsequent requests, browser includes: Cookie: session-id=abc123 → Server looks up "abc123" in database → finds user's cart
Cookies are stored on the client but controlled by the server. Third-party cookies (from embedded content on a different domain) are used for cross-site tracking and are increasingly restricted by modern browsers.

Web Caching (Proxy Servers)

A web cache (proxy server) sits between client and origin server. It stores copies of recently requested objects. Caches reduce response time and decrease traffic on the access link.

Average Delay with Web Cache:
Avg Delay = hit_rate × LAN_delay + (1 − hit_rate) × (LAN_delay + Internet_delay)
hit_rate = fraction of requests served from cache (typically 0.2 to 0.7)
LAN_delay = delay between client and cache (e.g., 0.01 s)
Internet_delay = delay between cache and origin server (e.g., 2.0 s)
Example Calculation — Cache Performance

Given: LAN delay = 0.01 s, Internet delay = 2.0 s, hit rate = 0.4
With cache miss: total delay = 0.01 + 2.0 = 2.01 s
With cache hit: total delay = 0.01 s (just the LAN)
Average delay = 0.4 × 0.01 + 0.6 × (0.01 + 2.0)
                    = 0.004 + 0.6 × 2.01
                    = 1.210 s
Compared to 2.01 s without a cache — a 40% reduction!

Web Cache Operation — Step by Step

WEB CACHE OPERATION: ───────────────────────────── When a request arrives at the cache: 1. Cache checks its local storage for the requested object 2. If the object is found (cache hit): → Cache returns the object directly to the client → No traffic to the origin server 3. If the object is NOT found (cache miss): → Cache opens a TCP connection to the origin server → Cache sends an HTTP request for the object → Origin server responds with the object → Cache stores a copy in its local storage → Cache forwards the response to the client 4. Cache is both a server (to the requesting client) and a client (to the origin server)
When the cache acts as a client to the origin server, it must include the Host header (required in HTTP/1.1). This is why the Host header is essential for proxy caches to work correctly.

Conditional GET — Keeping the Cache Fresh

A conditional GET prevents the cache from sending stale objects. The cache includes an If-Modified-Since header with the timestamp of its stored copy.

CONDITIONAL GET FLOW: ───────────────────────────── Cache has "page.html" (Last-Modified: Mon, 07 Jul 2025 10:00:00 GMT) 1. Client requests page.html → Cache has copy, but may be stale 2. Cache sends to origin server: GET /page.html HTTP/1.1 If-Modified-Since: Mon, 07 Jul 2025 10:00:00 GMT 3. Server checks: has page changed since that date? a. If NOT modified → Server responds: HTTP/1.1 304 Not Modified (empty body — cache uses its copy) b. If modified → Server responds: HTTP/1.1 200 OK (full body with new object) 4. Cache forwards result to client
The 304 Not Modified response has an empty entity body. This saves bandwidth because the object itself is not retransmitted. The cache simply refreshes the timestamp of its stored copy.

HTTP/2 — Improving Performance

HTTP/2 (RFC 7540, 2015) was designed to address HTTP/1.1 performance limitations while maintaining full semantic compatibility with HTTP/1.1 (same methods, status codes, header fields, and URLs).

HTTP/2 Goals

• Reduce latency through multiplexing

• Request prioritization

• Server push

• Header compression (HPACK)

HOL in HTTP/1.1

On a single persistent TCP connection:

• Request 1 (large image) blocks

• Request 2 (small CSS file) behind it

• Result: unnecessary delay

HTTP/2 Framing Sublayer — The Key Innovation

HTTP/2 breaks messages into frames and interleaves them on a single TCP connection. This eliminates HOL blocking at the application layer.

HTTP/1.1 (serial on one connection): ────────────────────────────────────── [ REQUEST 1 → full response ⟶ ... ⟶ ] [ REQUEST 2 → full response ] ↑ large image delays CSS HTTP/2 (framed multiplexing): ────────────────────────────────────── [ REQ1-frame1 │ REQ2-frame1 │ REQ1-frame2 │ REQ2-frame2 │ ... ] ↑ both streams interleaved — no blocking

Binary Framing

HTTP/2 uses binary encoding of frames rather than HTTP/1.1's text-based format. Binary encoding is more efficient to parse, produces smaller frames, and is less error-prone than textual protocols.

Message Prioritization & Dependency

HTTP/2 allows the client to indicate the relative importance of each message:

Weight (1–256)

The client assigns a weight between 1 and 256 to each message. A higher weight means higher priority — the server should allocate more resources to it.

Message Dependency

The client can state that a message depends on another message by specifying the other message's stream ID. The dependent message should not be sent until its parent is complete.

HPACK Header Compression

HTTP/2 uses HPACK to compress header fields, significantly reducing overhead. Header compression is critical for performance because headers like Cookie and User-Agent are sent on every request and can be hundreds of bytes.

Server Push

The server can send additional objects without waiting for explicit requests. For example, when a client requests an HTML page, the server can push the CSS and JavaScript files that it knows the page will need.

SERVER PUSH EXAMPLE: ───────────────────────────── Client: GET /index.html Server: ← 200 OK (index.html body) Server: ← PUSH /styles.css (no request needed!) Server: ← PUSH /app.js (no request needed!)
Server push must be used carefully. If the client already has the pushed object cached, the push wastes bandwidth. HTTP/2 includes a RST_STREAM frame to cancel unnecessary pushes, but the bandwidth may already be consumed.

HTTP/3 — Over QUIC (UDP)

HTTP/3 (RFC 9114, 2022) replaces TCP with QUIC, which runs over UDP. QUIC addresses TCP-level HOL blocking and reduces connection establishment latency.

QUIC Protocol Details

Transport Layer

QUIC runs over UDP and is implemented in the application layer (not in the OS kernel like TCP). This allows for faster deployment of new features.

Message Multiplexing

Multiple streams are truly independent — a lost packet on one stream does not block other streams, eliminating TCP-level HOL blocking entirely.

Per-Stream Flow Control

QUIC provides per-stream flow control, allowing each stream to have its own flow control limits independent of other streams.

Low-Latency Establishment

QUIC supports 0-RTT connection establishment for clients that have previously connected, dramatically reducing handshake latency.

QPACK Header Compression

HTTP/3 uses QPACK for header compression, an evolution of HPACK designed to work efficiently with QUIC's stream-based multiplexing. Unlike HPACK (which relies on ordered TCP delivery), QPACK handles out-of-order delivery that can occur with QUIC streams.

Comparison: HTTP/1.1 vs HTTP/2 vs HTTP/3

Feature HTTP/1.1 HTTP/2 HTTP/3
Transport TCP TCP QUIC (UDP)
Multiplexing No (serial) Yes (frames) Yes (frames)
HOL blocking At HTTP + TCP level Only at TCP level None
Header compression No HPACK QPACK
Server push No Yes Yes
Connection setup 2 RTT (TCP + TLS) 2 RTT (TCP + TLS) ~0 RTT (QUIC 0-RTT)
Why HTTP/3 Matters — The HOL Problem at TCP Level

Even with HTTP/2's framing, if a TCP packet is lost, all streams on that connection are blocked until the lost packet is retransmitted. This is TCP-level HOL blocking.

HTTP/3 over QUIC eliminates this because:

  • QUIC runs over UDP (no TCP retransmission delay for all streams)
  • Each stream is independent — a lost packet on stream 1 does not block stream 2
  • Connection setup = 1 RTT or even 0 RTT (if client has previously connected)

Worked Examples

Example 1 — Non-Persistent vs Persistent: Total Delay Calculation

Scenario: A web page consists of a base HTML file + 5 images. RTT between client and server = 50 ms. File transmission time per object = 10 ms (negligible difference between objects).

Non-Persistent HTTP

Each object: 2 × RTT + transmission = 2(50) + 10 = 110 ms
6 objects → 6 × 110 = 660 ms

Persistent HTTP with Pipelining

TCP setup: 1 × RTT = 50 ms
Request base HTML: 1 × RTT + transmission = 60 ms
Request all 5 images (back-to-back): 1 × RTT + 5 × transmission = 50 + 50 = 100 ms
Total = 50 + 60 + 100 = 210 ms

Persistent pipelining is 3.1× faster than non-persistent (660 vs 210 ms).

Example 2 — Reading an HTTP Request Message
GET /products/search?q=laptop&sort=price HTTP/1.1 Host: www.shop-example.com User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8 Accept-Language: fr-FR,fr;q=0.9,en;q=0.5 Accept-Encoding: gzip, deflate, br Connection: keep-alive If-Modified-Since: Tue, 06 Jul 2025 08:30:00 GMT

Breakdown:
• GET → method (retrieve resource)
• /products/search?q=laptop&sort=price → URL with query string (parameters start after ?)
• Host: www.shop-example.com → virtual hosting (required HTTP/1.1)
• Accept: */*;q=0.8 → wildcard fallback with quality factor 0.8
• Accept-Language: fr-FR,fr;q=0.9,en;q=0.5 → French preferred, then English
• Accept-Encoding: gzip, deflate, br → client supports compressed responses
• If-Modified-Since → conditional GET (cache check)
Key insight: this is a search query (note the ?q=laptop in the URL). The server would use these parameters to generate a dynamic response.

Example 3 — Reading an HTTP Response Message
HTTP/1.1 301 Moved Permanently Date: Mon, 07 Jul 2025 15:00:00 GMT Server: Apache/2.4.57 (Ubuntu) Location: https://www.shop-example.com/products/laptops Content-Length: 212 Content-Type: text/html; charset=UTF-8 <html> <head><title>Moved</title></head> <body> <h1>The resource has moved</h1> <p>Please update your bookmarks to <a href="https://www.shop-example.com/products/laptops">this URL</a>.</p> </body> </html>

Breakdown:
• 301 Moved Permanently → the object has a new permanent URL
• Location: https://www.shop-example.com/products/laptops → the new URL where the resource now lives
• The body contains a minimal HTML page with a link (so users who follow the old link manually can click through)
Key insight: browsers receiving a 301 automatically follow the Location URL without user intervention. The 212-byte body is for human readers who might see the raw response.

Example 4 — Cookie Flow: First Visit vs Second Visit to an E-Commerce Site

First Visit

REQUEST: GET /store/index.html HTTP/1.1 Host: www.books-example.com RESPONSE: HTTP/1.1 200 OK Set-Cookie: session-id=7b3e9f1a; Max-Age=3600 Set-Cookie: cart=empty (body: HTML page)

Browser stores session-id=7b3e9f1a and cart=empty in its cookie jar. Server stores session-id 7b3e9f1a in its back-end database with an empty cart.

User navigates to /books/python.html

REQUEST: GET /books/python.html HTTP/1.1 Host: www.books-example.com Cookie: session-id=7b3e9f1a; cart=empty RESPONSE: HTTP/1.1 200 OK Set-Cookie: cart=python-book%3A1 (body: book page)

Server sees session-id=7b3e9f1a, looks up the cart, sees it was empty, and now updates it with "python-book × 1". The Set-Cookie with the updated cart value replaces the old one in the browser.

Second Visit (next day)

REQUEST: GET /store/index.html HTTP/1.1 Host: www.books-example.com Cookie: session-id=7b3e9f1a; cart=python-book%3A1 RESPONSE: HTTP/1.1 200 OK (body: personalized page showing "Welcome back! Your cart has 1 item")

Key insight: The server recognizes the returning user through the Cookie header and can restore their cart, offer personalized recommendations, etc. Without cookies, every visit would start from scratch.

Example 5 — Web Cache Performance: Should We Install a Proxy?

Scenario: A university has 500 students accessing the Web. Without a cache:

  • Average request rate: λ = 100 requests/second
  • Average object size: L = 250,000 bytes (250 KB)
  • Access link bandwidth: R = 10 Mbps
Traffic Intensity (without cache):
Traffic Intensity = (λ × L) / R = (100 × 250,000 × 8) / 10,000,000 = 20
20 >> 1 → The link is severely overloaded! Delay approaches infinity.

With a Web Cache (hit rate = 0.6)

Only 40% of requests go to the Internet. Effective request rate to the access link:

Traffic Intensity (with cache):
Effective λ = 100 × (1 − 0.6) = 40 req/s
Traffic Intensity = (40 × 250,000 × 8) / 10,000,000 = 8
8 >> 1 — still overloaded! We need a higher hit rate or a faster link.

With Cache hit rate = 0.85

Traffic Intensity (hit rate 0.85):
Effective λ = 100 × 0.15 = 15 req/s
Traffic Intensity = (15 × 250,000 × 8) / 10,000,000 = 3

Still high, but manageable with queuing. Key lesson: A cache reduces traffic, but if the initial load is extremely high, you may need a cache and a larger access link.

With a 60% cache hit rate, traffic drops from 20 → 8 (60% reduction). With 85% hit rate, traffic drops to 3 (85% reduction).

Additional Formulas — Quick Summary

Non-Persistent Total Delay (N objects):
Total = N × (2 × RTT + Tfile)
N objects, each requiring a separate TCP connection
Persistent Pipelined Total Delay:
Total = 2 × RTT + (N + 1) × Tfile
1 RTT for TCP + 1 RTT for responses + transmission times
Average Delay with Cache:
Avg Delay = h × DLAN + (1 − h) × (DLAN + DInternet)
h = hit rate, DLAN = LAN delay, DInternet = Internet delay
