UDP Sockets — Connectionless Transport

UDP (User Datagram Protocol) provides a connectionless, unreliable, packet-based service. Two processes communicate by sending discrete packets called datagrams — no handshake is required.

UDP Characteristics

• Connectionless: No handshake before data transfer

• Unreliable: Packets may be lost or reordered

• Packet-based: Message boundaries preserved

• No congestion control: Sends at application rate

Socket API Methods

socket() — create endpoint

sendto() — send datagram

recvfrom() — receive datagram

close() — release socket

How Addressing Works

Before sending a UDP packet, the destination address (IP + port number) must be explicitly attached to each packet. The source address (the sender's IP + port) is automatically attached by the operating system. The receiving process extracts the source address from recvfrom() to know where to reply.

UDP Packet Delivery Model
sendto(data, (destIP, destPort))  →  OS attaches (srcIP, srcPort) automatically
Each datagram is self-contained; the receiver uses recvfrom to get both data and sender address

Socket Creation: UDP

from socket import * clientSocket = socket(AF_INET, SOCK_DGRAM)

The AF_INET parameter indicates the address family (IPv4). SOCK_DGRAM specifies a UDP datagram socket. No port is bound explicitly — the OS assigns an ephemeral port automatically.

Communication Flow

CLIENT  →  SERVER
# No connection setup needed!
1. Create socket (AF_INET, SOCK_DGRAM)
2. (Client only) Get user input
3. sendto(data, serverAddr) →→ Server
4. Server calls recvfrom()  ← receives datagram
5. Server processes, calls sendto(response, clientAddr)
6. Client calls recvfrom()  ← receives response
7. Close socket
⚠ WARNING: UDP packets may be lost or arrive out of order! There is no retransmission, no acknowledgment, and no flow control. Applications must handle reliability themselves if needed.

Choosing the right port number depends on the type of application you are developing:

Port range 0–1023 is reserved for well-known system services. Using them requires root privileges and risks conflicts with standard services.

UDP Client — Complete Code Walkthrough

Below is a complete UDP client (based on Section 2.7.1 of Kurose & Ross). The client sends a message to a server, receives the modified response, and prints it.

UDPClient.py

Python 3 — UDP Client
from socket import * # Import all socket symbols serverName = '127.0.0.1' # Server IP address (localhost) serverPort = 12000 # Server port number # Create UDP socket (AF_INET = IPv4, SOCK_DGRAM = UDP) clientSocket = socket(AF_INET, SOCK_DGRAM) message = input('Input lowercase sentence: ') # Get user input # Send packet: encode string to bytes, attach server address clientSocket.sendto(message.encode(), (serverName, serverPort)) # Receive response (2048 = max bytes to read) modifiedMessage, serverAddress = clientSocket.recvfrom(2048) # Decode bytes back to string and print print(modifiedMessage.decode()) clientSocket.close() # Close the socket

Line-by-Line Explanation

Line 1: Import

from socket import *

Imports all symbols from Python's socket module: socket(), AF_INET, SOCK_DGRAM, sendto(), recvfrom(), etc. The * is a convenience used in textbook code so all names are available without prefixing with socket..

Lines 3-4: Server Address

serverName = '127.0.0.1'
serverPort = 12000

serverName is either a hostname (e.g., 'host.example.com') or an IP address string. The client does not need a port of its own — the OS provides an ephemeral port automatically. serverPort must match the port the server has bound to.

Line 7: Create Socket

clientSocket = socket(AF_INET, SOCK_DGRAM)

AF_INET indicates the address family for IPv4. SOCK_DGRAM selects UDP datagram service. This returns a socket descriptor (an integer file descriptor wrapped in a Python object).

Line 9: User Input

message = input('Input lowercase sentence: ')

Standard Python input() blocks until the user types a line and presses Enter. The return value is a Python string.

Line 12: Send Datagram

clientSocket.sendto(message.encode(), (serverName, serverPort))

This is the core UDP send operation. Two things happen:

• message.encode() converts the Python string into bytes using the default UTF-8 encoding. Sockets transmit raw bytes, not strings.

• (serverName, serverPort) is the destination address attached to this specific packet. The OS automatically attaches the source address (client's IP + ephemeral port).

Line 15: Receive Response

modifiedMessage, serverAddress = clientSocket.recvfrom(2048)

recvfrom(2048) blocks until a datagram arrives. 2048 is the buffer size — the maximum number of bytes to receive. Returns a tuple: (bytes_data, (host, port)). The second element tells us who sent the response (the server's address).

ℹ BUFFER SIZE: 2048 is the maximum number of bytes to receive at once. For UDP, this buffer should be larger than the maximum expected datagram size. A value of 2048 bytes works well for most purposes — it is large enough for typical messages but small enough to be memory-efficient.
Line 18: Decode & Print

print(modifiedMessage.decode())

.decode() converts the received bytes back into a Python string. Without this, you'd see something like b'HELLO' instead of HELLO.

Line 20: Close

clientSocket.close()

Releases the socket and the ephemeral port back to the OS. In Python, sockets are also reclaimed when the variable goes out of scope, but explicit close is best practice.

ℹ KEY INSIGHT: encode() and decode() are essential! Network sockets transmit bytes, not strings. Always convert strings → bytes before sending, and bytes → strings after receiving.

Pseudocode: UDP Client Algorithm

1. Import socket module
2. Set serverName and serverPort
3. Create UDP socket: socket(AF_INET, SOCK_DGRAM)
4. Read user input into 'message' (a string)
5. encode() message to bytes
6. sendto(bytes, (serverName, serverPort))
7. recvfrom(bufferSize) → modifiedMessage, serverAddress
8. decode() modifiedMessage back to string
9. Print decoded message
10. Close socket

UDP Server — Complete Code Walkthrough

The UDP server (from Kurose & Ross Section 2.7.1) listens on a fixed port, receives client messages, converts them to uppercase, and sends them back.

UDPServer.py

Python 3 — UDP Server
from socket import * serverPort = 12000 # Create UDP socket serverSocket = socket(AF_INET, SOCK_DGRAM) # Bind socket to local port 12000 ('' means all interfaces) serverSocket.bind(('', serverPort)) print('The server is ready to receive') while True: # Receive client packet and source address message, clientAddress = serverSocket.recvfrom(2048) # Decode bytes to string, convert to uppercase, encode back modifiedMessage = message.decode().upper().encode() # Send response back to the same client serverSocket.sendto(modifiedMessage, clientAddress)

Line-by-Line Explanation

Line 5: Create Socket

serverSocket = socket(AF_INET, SOCK_DGRAM)

Identical to the client — creates a UDP datagram socket. One socket handles all clients (unlike TCP).

Line 8: Bind to Port

serverSocket.bind(('', serverPort))

This is the critical difference from the client. The server must explicitly bind to a well-known port so clients know where to send datagrams. '' means "accept packets from any network interface." The client does not call bind() — it gets an ephemeral port from the OS automatically.

Line 12: Infinite Loop

while True:

The server runs forever, processing one client request per iteration. For UDP, this means one datagram per iteration. The server does not maintain per-client state.

Line 14: Receive

message, clientAddress = serverSocket.recvfrom(2048)

recvfrom() extracts both the data and the sender's address. message is raw bytes. clientAddress is a tuple (IP, port) — the server uses this to reply.

ℹ BUFFER SIZE: The 2048 argument in recvfrom(2048) is the maximum number of bytes to receive per datagram. For UDP, the buffer must be larger than the maximum expected datagram size; otherwise the datagram will be truncated. A buffer of 2048 bytes is sufficient for most textbook and practical applications.
Line 17: Process

modifiedMessage = message.decode().upper().encode()

A chain of three operations:

• .decode() → bytes to string

• .upper() → string to uppercase

• .encode() → string back to bytes

Line 20: Send Reply

serverSocket.sendto(modifiedMessage, clientAddress)

Uses the clientAddress extracted from recvfrom(). The same socket is used for all clients — the server doesn't create per-client sockets (unlike TCP).

⚠ WARNING: The UDP server must be running before any client tries to send data. If no server is listening, the client's packet is silently dropped — UDP has no connection establishment to detect this.

UDP Server State Model

1. Create socket: socket(AF_INET, SOCK_DGRAM)
2. Bind to fixed port: bind(('', serverPort))
3. # Server is now reachable at (thisHost, serverPort)
4. loop:
5.   Wait for packet: recvfrom(bufSize) → data, clientAddr
6.   Process data
7.   Send response: sendto(result, clientAddr)
8. end loop

TCP Sockets — Connection-Oriented Transport

TCP (Transmission Control Protocol) provides a connection-oriented, reliable, stream-based service. A connection must be established via the three-way handshake before any data can be exchanged.

TCP Characteristics

• Connection-oriented: Three-way handshake required

• Reliable: All data arrives, in order, without gaps

• Stream-based: No message boundaries (byte stream)

• Congestion control: Adapts to network conditions

Socket API Methods

socket() — create endpoint

connect() — establish connection (client)

listen() — mark as passive (server)

accept() — accept connection (server)

send() — send data

recv() — receive data

close() — terminate connection

Two Types of Server Sockets

A major conceptual difference from UDP: a TCP server uses two distinct sockets.

SocketPurposeMethodsScope
Welcoming SocketListens for new connection requestssocket(), bind(), listen(), accept()One per server, persists forever
Connection SocketExchanges data with one clientsend(), recv(), close()One per client, closed when done
TCP Connection Establishment (Three-Way Handshake)
Client → Server: SYN    Server → Client: SYN-ACK    Client → Server: ACK
The connect() call triggers this handshake. When accept() returns, the handshake is complete and the connection is ready.

Socket Creation: TCP

from socket import * clientSocket = socket(AF_INET, SOCK_STREAM)

The only code-level difference from UDP is SOCK_STREAM instead of SOCK_DGRAM. This tells the OS to create a TCP socket.

Reliable Byte Stream

Unlike UDP, TCP guarantees that all bytes sent will arrive in the order they were sent, without gaps or duplicates. However, there are no message boundaries — a single send() may be split across multiple recv() calls, and multiple send() calls may be combined into one recv().

ℹ KEY INSIGHT: Because TCP is a byte-stream protocol, the application layer must define its own message boundaries (e.g., using fixed-length messages, special delimiters, or prepending message lengths).
⚠ WARNING: TCP server must be running before client! The client's connect() will fail with ConnectionRefusedError if no server is listening on the target port.

Open vs Proprietary Applications

Network applications can be classified based on who defines the protocol:

Open Applications

The protocol rules are specified in an RFC standard (Request for Comments). Any developer can create an independent client or server implementation as long as it conforms to the RFC rules. These independently developed programs can interoperate.

Example: An HTTP client (e.g., Chrome browser) communicating with an HTTP server (e.g., Apache web server) — both are built by different organizations but work together because both follow the HTTP RFC.

Proprietary Applications

Both the client and server are created by the same developer or organization, giving them complete control over the protocol design. No published standard exists for the protocol.

Other developers cannot create interoperable clients or servers for a proprietary application because the protocol specification is not publicly documented.

TCP Byte Stream — No Message Boundaries

TCP is a stream-oriented protocol, not a message-oriented protocol. This has important consequences:

PropertyExplanation
No 1:1 mappingA single send() call may be split across multiple recv() calls by TCP.
MergingMultiple send() calls may be combined into a single recv() call.
App-layer framing requiredThe application must define its own message boundaries using one of these techniques: fixed-length messages, delimiter-based framing (e.g., newline \n), or length-prefix framing (prepend each message with its byte count).
⚠ WARNING: Never assume recv(N) will return exactly N bytes or match a single send() call! Always handle partial receives by looping until the expected amount of data is received.

TCP Client — Complete Code Walkthrough

Based on Kurose & Ross Section 2.7.2. The TCP client establishes a connection (three-way handshake), sends a message, and receives the uppercase response.

TCPClient.py

Python 3 — TCP Client
from socket import * serverName = '127.0.0.1' serverPort = 12000 # Create TCP socket (SOCK_STREAM instead of SOCK_DGRAM) clientSocket = socket(AF_INET, SOCK_STREAM) # Initiate TCP connection (three-way handshake happens here) clientSocket.connect((serverName, serverPort)) sentence = input('Input lowercase sentence: ') # Send data over connection (no destination address needed!) clientSocket.send(sentence.encode()) # Receive modified sentence modifiedSentence = clientSocket.recv(1024) print('From Server: ', modifiedSentence.decode()) clientSocket.close() # Close TCP connection

Line-by-Line Explanation

Line 8: Create TCP Socket

clientSocket = socket(AF_INET, SOCK_STREAM)

SOCK_STREAM selects TCP. This creates the client endpoint that will participate in the connection.

Line 11: Connect — The Handshake

clientSocket.connect((serverName, serverPort))

This single line triggers the entire three-way handshake:

• Client sends TCP SYN segment

• Server responds with SYN-ACK

• Client sends ACK

After connect() returns, the connection is fully established and ready for data. The client's ephemeral port is assigned during this process.

Line 15: Send Data (No Address)

clientSocket.send(sentence.encode())

Unlike UDP's sendto(), TCP's send() takes only the data. No destination address is needed because the connection (which includes the remote endpoint) was established in connect().

Line 17: Receive (No Address)

modifiedSentence = clientSocket.recv(1024)

TCP's recv() returns only the data bytes (no address tuple). If the TCP connection is closed by the server, recv() returns empty bytes (b''), which signals end-of-stream.

ℹ BUFFER SIZE: The 1024 argument in recv(1024) is the maximum number of bytes to receive at once. For TCP, this can be any size — the application may need multiple recv() calls to retrieve the full message because TCP is a stream protocol with no 1:1 relationship between send() and recv() calls.
Line 21: Close

clientSocket.close()

Sends FIN segment to perform TCP's connection termination (four-way handshake). After this, the socket cannot be used.

Pseudocode: TCP Client Algorithm

1. Import socket module
2. Set serverName and serverPort
3. Create TCP socket: socket(AF_INET, SOCK_STREAM)
4. connect((serverName, serverPort)) # block until handshake done
5. Read user input into 'sentence'
6. encode() to bytes
7. send(bytes) # no destination needed!
8. recv(bufSize) → modifiedSentence
9. decode() and print
10. Close socket
ℹ IMPORTANT: A TCP client does not call bind(). The OS assigns the client's IP and an ephemeral port as part of connect(). The client's port is released when the connection closes.

TCP Server — Complete Code Walkthrough

Based on Kurose & Ross Section 2.7.2. The TCP server creates a welcoming socket, listens for connections, and spawns dedicated connection sockets per client.

TCPServer.py

Python 3 — TCP Server
from socket import * serverPort = 12000 # Create welcoming socket (TCP) serverSocket = socket(AF_INET, SOCK_STREAM) # Bind to well-known port serverSocket.bind(('', serverPort)) # Listen for incoming connections (1 = max queued connections) serverSocket.listen(1) print('The server is ready to receive') while True: # Accept a connection: blocks until client connects # Returns a NEW socket dedicated to this client connectionSocket, addr = serverSocket.accept() # Receive data from client over the connection socket sentence = connectionSocket.recv(1024).decode() # Convert to uppercase and encode back capitalizedSentence = sentence.upper().encode() # Send result back over the same connection socket connectionSocket.send(capitalizedSentence) # Close the connection socket (NOT the welcoming socket!) connectionSocket.close()

Line-by-Line Explanation

Lines 6-8: Welcoming Socket Setup

serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))

Creates the welcoming socket. This socket is dedicated to listening for new connection requests. It does not exchange data with clients. bind() fixes it to port 12000 on all interfaces.

Line 11: Listen

serverSocket.listen(1)

Marks the socket as passive — ready to accept incoming connection requests. The parameter 1 is the backlog: the maximum number of queued but not-yet-accepted connections. The OS will reject additional connections (or hold them pending, depending on the platform) if the queue is full.

Line 17: Accept Connection

connectionSocket, addr = serverSocket.accept()

This is a blocking call. When a client's SYN arrives and the handshake completes, accept() returns a brand new socket (connectionSocket) that is specifically connected to that client. The original serverSocket remains untouched and ready to accept the next client.

Line 20: Receive Data

sentence = connectionSocket.recv(1024).decode()

Reads data from the connection socket (not the welcoming socket). recv(1024) returns up to 1024 bytes. Because TCP is a byte stream, the message boundaries may not align with send boundaries.

ℹ BUFFER SIZE: The 1024 in recv(1024) is the maximum bytes to receive in one call. For TCP, the buffer can be any size — there is no guarantee that one send() corresponds to one recv(). Applications should be prepared for partial reads and may need a loop to assemble the complete message.
Lines 23-26: Process and Reply

capitalizedSentence = sentence.upper().encode()
connectionSocket.send(capitalizedSentence)

Processes the data and sends it back over the same connection socket. The server knows who the client is because this socket is connected to exactly one client.

Line 29: Close Connection

connectionSocket.close()

Closes only this client's connection socket, performing TCP's connection termination. The serverSocket stays open to accept new clients. In a production server, you would iterate again and call accept() on the welcoming socket.

TCP Server Socket Model Visualized

# Welcoming socket (persistent):
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', port))
serverSocket.listen(backlog)

loop:
  # Block until a new client arrives
  connectionSocket, clientAddr = serverSocket.accept()
  # connectionSocket is now dedicated to this client
  data = connectionSocket.recv(bufSize)
  connectionSocket.send(response)
  connectionSocket.close()
end loop

ℹ KEY INSIGHT: The welcoming socket and each connection socket have different port numbers! The welcoming socket uses the well-known port (e.g., 12000). Each connection socket gets a distinct ephemeral port from the OS. This is how the server distinguishes between multiple simultaneous clients — the (clientIP, clientPort, serverIP, serverPort) 4-tuple is unique per connection.

Port Number Selection for TCP Servers

When implementing a TCP server:

  • If your protocol is defined by an RFC standard, use the well-known port specified in that RFC (e.g., port 12000 in Kurose & Ross examples).
  • If you are developing a proprietary application, avoid well-known ports (0–1023). Use ports above 49152 (ephemeral range) or registered ports (1024–49151) instead.

Each connection socket gets a different ephemeral port from the welcoming socket, allowing the server to handle multiple simultaneous clients. The 4-tuple (srcIP, srcPort, dstIP, dstPort) uniquely identifies each connection.

Examples & Applications

Example 1: UDP Ping Application

A simple ping application: client sends a message, server echoes the exact same message back (no transformation).

UDP Ping Client
from socket import * serverName = '127.0.0.1' serverPort = 12000 clientSocket = socket(AF_INET, SOCK_DGRAM) message = input('Ping message: ') clientSocket.sendto(message.encode(), (serverName, serverPort)) response, addr = clientSocket.recvfrom(2048) print('Response:', response.decode()) # Check if response matches original if response.decode() == message: print('Ping SUCCESS - message preserved') else: print('Ping FAIL - message modified') clientSocket.close()
UDP Ping Server
from socket import * serverPort = 12001 serverSocket = socket(AF_INET, SOCK_DGRAM) serverSocket.bind(('', serverPort)) print('Ping server ready on port', serverPort) while True: message, clientAddr = serverSocket.recvfrom(2048) print('Received:', message.decode(), 'from', clientAddr) # Echo the message back unchanged serverSocket.sendto(message, clientAddr)

Example 2: TCP Echo — Multiple Lines

This example shows that the same TCP connection can be reused for multiple send/recv exchanges.

TCP Echo Client (multi-line)
from socket import * serverName = '127.0.0.1' serverPort = 12002 clientSocket = socket(AF_INET, SOCK_STREAM) clientSocket.connect((serverName, serverPort)) # Send multiple messages over same connection messages = ['Hello', 'World', 'TCP', 'Echo', 'exit'] for msg in messages: clientSocket.send(msg.encode()) response = clientSocket.recv(1024) print(f'Sent: {msg} | Echo: {response.decode()}') clientSocket.close()
TCP Echo Server (multi-line)
from socket import * serverPort = 12002 serverSocket = socket(AF_INET, SOCK_STREAM) serverSocket.bind(('', serverPort)) serverSocket.listen(1) print('TCP Echo server ready on port', serverPort) connectionSocket, addr = serverSocket.accept() print('Connected by', addr) while True: data = connectionSocket.recv(1024) if not data: break # Empty data means client closed connection connectionSocket.send(data) # Echo back print('Echoed:', data.decode()) connectionSocket.close()
ℹ KEY: In the TCP echo server, empty bytes from recv() signals that the client closed its end of the connection. The server then breaks out of the loop and closes the connection socket.
Understanding Empty Bytes — TCP Connection Close

When a TCP peer calls close(), the remote side's recv() returns empty bytes (b''). This is the TCP end-of-stream signal — it indicates that no more data will arrive on this connection.

The server should check for this condition and break out of the receive loop, then close the connection socket:

while True: data = connectionSocket.recv(1024) if not data: # Empty bytes = connection closed break # Exit receive loop # Process data... connectionSocket.close() # Close this client's connection

TCP Byte Stream — Message Boundaries

Because TCP is a stream protocol, the application layer must define its own message boundaries. Common approaches include:

TechniqueDescriptionExample
Fixed-length messagesEvery message has the same pre-agreed sizeProtocol defines 1024-byte messages; read exactly 1024 bytes
Delimiter-based framingUse a special marker (e.g., newline \n) to separate messagesHTTP uses \r\n\r\n to mark end of headers
Length-prefix framingPrepend each message with its length (e.g., 4-byte integer)Send 4-byte length + data; receiver reads length first, then data
⚠ WARNING: TCP does not preserve message boundaries. A single send() may be split across multiple recv() calls, and multiple send() calls may be combined into one recv(). Always use application-level framing to handle this correctly.

Example 4: UDP Server — Count Character Occurrences

A modification of the Kurose & Ross UDP server. Instead of converting to uppercase, count how many times a specific character appears in the message.

Custom UDP Client (count)
from socket import * serverName = '127.0.0.1' serverPort = 12003 clientSocket = socket(AF_INET, SOCK_DGRAM) message = input('Enter a sentence: ') char = input('Character to count: ') # Send both message and target char payload = message + '|' + char clientSocket.sendto(payload.encode(), (serverName, serverPort)) response, addr = clientSocket.recvfrom(2048) print('Server response:', response.decode()) clientSocket.close()
Custom UDP Server (count)
from socket import * serverPort = 12003 serverSocket = socket(AF_INET, SOCK_DGRAM) serverSocket.bind(('', serverPort)) print('Char-count server ready') while True: data, clientAddr = serverSocket.recvfrom(2048) decoded = data.decode() # Parse payload: "message|char" parts = decoded.split('|') message = parts[0] target = parts[1] if len(parts) > 1 else '' count = message.count(target) response = f'Character "{target}" appears {count} time(s) in "{message}"' serverSocket.sendto(response.encode(), clientAddr)

Example 5: Tracing the Three-Way Handshake & Socket Creation

This example illustrates exactly what happens at the socket API level vs what happens at the TCP protocol level when a TCP client connects to a TCP server.

TIME CLIENT      SERVER

t0   socket(AF_INET, SOCK_STREAM) socket(AF_INET, SOCK_STREAM)
t1    bind(('', 12000))
t2    listen(1)
t3   connect(('127.0.0.1', 12000))
t4        ---- SYN ---->
t5        <-- SYN-ACK ---- accept() returns new connectionSocket
t6        ---- ACK ---->
t7   connect() returns (ready)
t8   send(data)  ==== data ====> recv()
t9   recv(response) <== response ==== send()
t10   close()     ---- FIN ----> close()
What happens at each step:

t0-t2: Both sides create sockets. The server binds to port 12000 and calls listen() to indicate it's ready to accept connections.

t3: Client calls connect() — this is the trigger for the handshake.

t4: Client's TCP sends a SYN segment to the server's IP:port 12000.

t5: Server's TCP receives SYN, sends back SYN-ACK. The server's OS also creates a new socket for this connection and accept() returns it.

t6-t7: Client receives SYN-ACK, sends ACK, and connect() returns. Connection is now ESTABLISHED.

t8-t9: Data flows over the connection. TCP handles segmentation, acknowledgment, retransmission, and ordering.

t10: Either side calls close(), triggering the four-way connection termination (FIN exchange).

⚠ WARNING: The client's connect() call returns after the three-way handshake completes (step t7). However, the server's accept() may return as early as step t5 (after receiving the SYN), depending on the OS implementation. This means accept() can return before the handshake is fully complete.

s = socket(AF_INET, SOCK_DGRAM)
s.bind(('', port))
data, addr = s.recvfrom(buf)
s.sendto(response, addr)
One socket handles all clients. Must bind to well-known port.
TCP Client Skeleton
s = socket(AF_INET, SOCK_STREAM)
s.connect((host, port))
s.send(data.encode())
data = s.recv(buf)
s.close()
connect() establishes connection. No address needed in send().
TCP Server Skeleton
s = socket(AF_INET, SOCK_STREAM)
s.bind(('', port)); s.listen(n)
conn, addr = s.accept()
data = conn.recv(buf)
conn.send(response)
conn.close()
Welcoming socket (s) + per-client connection sockets (conn).

Common Pitfalls to Avoid in Exams

PitfallWhy it's wrongCorrect approach
Calling send() on UDP socketUDP uses sendto() because each datagram needs a destinationUse sendto() with address argument
Calling connect() on UDP socketUDP is connectionless; connect() is TCP-onlyNo connection setup for UDP
Forgetting bind() on server socketServer port must be known to clients; without it, OS assigns ephemeral portAlways call bind(('', port)) on server
Calling bind() on client socket unnecessarilyClients get ephemeral ports from OS; explicit bind is unusualOnly bind on client when you need a specific source port
Forgetting listen() on TCP serverWithout listen(), accept() will failAlways call listen() before accept()
Closing welcoming socket instead of connection socketClosing serverSocket prevents new connectionsOnly close connectionSocket; keep serverSocket alive
Not checking for empty recv() in TCPEmpty bytes means connection closed; ignoring it causes infinite loopCheck if not data: break in TCP receive loop
Assuming one send() = one recv() in TCPTCP is a byte stream; messages can be split or combinedUse application-level framing (delimiters, length prefixes)
