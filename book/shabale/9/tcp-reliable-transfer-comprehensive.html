TCP Sender — Three Major Events

TCP creates a reliable data transfer service on top of IP's unreliable best-effort service. The sender manages two key variables:

SendBase

Sequence number of the oldest unacknowledged byte. SendBase - 1 is the last byte confirmed received in order.

NextSeqNum

Sequence number of the next byte to be sent.

Three Events (Simplified TCP Sender)

EventAction
1. Data from application above Create segment with seq = NextSeqNum; if timer not running, start it; pass to IP; NextSeqNum += length(data)
2. Timeout Retransmit oldest unacknowledged segment; restart timer
3. ACK received (value y) If y > SendBase: SendBase = y; if unacknowledged segments remain, restart timer

Sender Pseudocode

NextSeqNum = InitialSeqNumber; SendBase = InitialSeqNumber; loop forever { switch (event) { case data from application: create segment with seq = NextSeqNum; if (timer not running) start timer; pass segment to IP; NextSeqNum += length(data); break; case timeout: retransmit oldest unacknowledged segment; start timer; break; case ACK received (value y): if (y > SendBase) { SendBase = y; if (unacknowledged segments remain) start timer; } break; } }
⚠ Key Point: TCP uses a single timer for the oldest unacknowledged segment, not one timer per segment. This simplifies timer management.

Retransmission Scenarios

Scenario 1: Lost ACK

Host A sends seq=92 (8 bytes). Segment arrives, but B's ACK=100 is lost.

Action: Timeout occurs. A retransmits seq=92. B receives duplicate, discards it, re-sends ACK=100.

No harm — duplicate detection via sequence numbers prevents data corruption.

Scenario 2: Cumulative ACK Prevents Unnecessary Retransmissions

Host A sends two segments: seq=92 (8 bytes) and seq=100 (20 bytes).

Both arrive at B. B sends ACK=100 and ACK=120.

ACK=100 is lost, but before timeout, A receives ACK=120.

Action: Since ACK=120 > SendBase=92, SendBase = 120. No retransmission needed!

Cumulative ACKs provide robustness: a later ACK implicitly acknowledges all earlier data.

Scenario 3: Doubling Timeout Interval

Exponential Backoff Rule
On timeout: TimeoutInterval = TimeoutInterval × 2
Each successive timeout doubles the interval: 0.75s → 1.5s → 3.0s → 6.0s

This provides a limited form of congestion control. Timeout likely means congestion; persistent retransmission would worsen it.

Fast Retransmit

Timeout periods can be relatively long. The sender can detect packet loss sooner by noticing duplicate ACKs.

How Duplicate ACKs Arise

When a receiver detects a gap (out-of-order segment), it sends a duplicate ACK for the last in-order byte received.

EventReceiver Action [RFC 5681]
In-order segment arrives, no pending ACKDelayed ACK (wait up to 500 ms for next segment)
In-order segment arrives, one pending ACKImmediately send cumulative ACK
Out-of-order segment (gap detected)Immediately send duplicate ACK (seq of next expected byte)
Segment fills gap partially/completelyImmediately send ACK (lower end of gap)

Fast Retransmit Algorithm

event: ACK received, value y if (y > SendBase) { SendBase = y; if (unacknowledged segments remain) start timer; } else { // duplicate ACK dupACKcount[y]++; if (dupACKcount[y] == 3) { // 3 duplicate ACKs → fast retransmit resend segment with seq = y; } }
⚠ Why 3 duplicate ACKs? A single duplicate ACK could be caused by packet reordering, not loss. Three duplicate ACKs strongly suggest the segment is lost.

In the fast retransmit diagram (Figure 3.37), segment seq=100 is lost. The sender receives 4 ACKs for seq=100 (one original + three duplicates), triggering retransmission of seq=100 before its timer expires.

GBN vs SR in TCP

TCP is neither purely GBN nor purely SR — it's a hybrid that combines features of both.

FeatureGo-Back-NSelective RepeatTCP

Retransmit on timeoutAll unacknowledged packetsOnly lost packetOnly oldest unacknowledged (SR-like)

Why TCP is a Hybrid

GBN-like Features

• Cumulative ACKs — one ACK covers all prior bytes

• Single timer for oldest unacknowledged segment

• SendBase + NextSeqNum window management

SR-like Features

• Buffers out-of-order segments (modern implementations)

• Retransmits only one segment on timeout (not all N)

• Selective ACK (SACK, RFC 2018) adds explicit selective acknowledgment

TCP's error-recovery mechanism is best categorized as a hybrid of GBN and SR protocols. SACK [RFC 2018] makes TCP even more SR-like by allowing receivers to acknowledge out-of-order segments selectively.

Worked Examples

Example 1: Timeout and Retransmission

Setup: Host A sends segment seq=500 (100 bytes). TimeoutInterval = 200 ms.

Sequence:

t=0 ms: A sends seq=500, starts timer.

t=10 ms: Segment arrives at B. B sends ACK=600.

t=20 ms: ACK=600 is lost (router buffer overflow).

t=200 ms: Timer fires (no ACK received). A retransmits seq=500, restarts timer (doubled to 400 ms).

t=210 ms: Retransmitted segment arrives. B sees seq=500 (duplicate), discards data, sends ACK=600.

t=220 ms: ACK=600 arrives at A. SendBase = 600. Timer stopped.

Total delay due to loss: ~220 ms (including retransmission and propagation).

Example 2: Cumulative ACK Avoiding Retransmission

Setup: A sends seq=200 (50 bytes) and seq=250 (60 bytes).

Sequence:

t=0: Send seq=200. t=1: Send seq=250.

t=10: B receives seq=200, sends ACK=250.

t=12: B receives seq=250, sends ACK=310.

t=20: ACK=250 is lost. t=22: ACK=310 arrives.

A checks: ACK=310 > SendBase(200). SendBase = 310. Timer stopped.

Even though ACK=250 was lost, no retransmission needed because ACK=310 acknowledges all data up to byte 310.

Example 3: Fast Retransmit Detection

Setup: A sends 4 segments: seq=1000 (100B), seq=1100 (100B), seq=1200 (100B), seq=1300 (100B).

Loss: Segment seq=1100 is dropped at a router.

Receiver events:

• Receives seq=1000 → ACK=1100

• Receives seq=1200 (out of order) → duplicate ACK=1100 (gap still at 1100)

• Receives seq=1300 (out of order) → duplicate ACK=1100

Sender events:

• Receives ACK=1100 (original) → SendBase = 1100

• Receives dup ACK=1100 (from seq=1200) → dupCount=1

• Receives dup ACK=1100 (from seq=1300) → dupCount=2

• Receives dup ACK=1100 (from seq=1400, if sent) → dupCount=3 → fast retransmit seq=1100!

Fast retransmit avoids waiting for the timeout (which could be hundreds of ms).

Example 4: Duplicate ACK from Packet Reordering

Setup: A sends seq=500 (80B), seq=580 (80B), seq=660 (80B).

Network reorders: seq=580 arrives before seq=500 (unusual but possible).

Receiver:

• Receives seq=580 first (out of order, expecting 500) → duplicate ACK=500

• Receives seq=500 (in order now) → delivers bytes 500-579, ACK=660 (cumulative)

• Receives seq=660 → ACK=740

Sender: Receives one duplicate ACK=500 but not three. No fast retransmit triggered.

TCP tolerates packet reordering — one duplicate ACK is not enough to trigger retransmission. This prevents unnecessary retransmission when packets are merely delayed/reordered.

Example 5: GBN vs TCP Behavior with Multiple Losses

Setup: Window of 5 segments sent: seq=1,2,3,4,5. Segment 2 is lost.

GBN behavior: When sender times out on segment 2, it retransmits all unacknowledged segments: 2,3,4,5.

TCP behavior: When timeout occurs, TCP retransmits only segment with smallest sequence number (seq=2).

Segments 3,4,5 may already be buffered at receiver. When ACKs for 3,4,5 arrive (possibly after retransmission of 2), they are used to advance SendBase.

TCP is more bandwidth-efficient than pure GBN; it avoids retransmitting segments already received.
