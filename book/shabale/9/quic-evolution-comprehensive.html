QUIC & Transport Evolution

Section 3.8 — Complete Guide for 20/20 Exam

QUIC Overview

QUIC (Quick UDP Internet Connections) is an application-layer protocol designed from the ground up to improve the performance of secure HTTP. It uses UDP as its underlying transport protocol and implements transport-layer functionality — reliability, congestion control, security, and connection management — at the application layer.

QUIC Protocol Stack:
Application Layer: HTTP/3 (or slimmed HTTP/2)
↕ QUIC (RDT + Congestion Control + Encryption)
↕ UDP (Unreliable Datagram Service)
↕ IP
QUIC replaces the traditional TCP + TLS stack with a single application-layer protocol over UDP

Key Features

Connection-Oriented & Secure

QUIC uses connection IDs (source and destination) to maintain connection state. All packets are encrypted by default — unlike TCP where encryption is optional (TLS layer).

Faster Handshake

QUIC combines connection establishment + TLS handshake into a single round-trip (0-RTT for repeat connections). Traditional TCP+TLS requires 2-3 RTTs.

Deployed at Scale

Google has deployed QUIC on public-facing Web servers, YouTube, Chrome browser, and Android Google Search. Over 7% of Internet traffic was QUIC by 2017.

Application-Update Timescales

Because QUIC runs at the application layer, changes can be deployed much faster than TCP or UDP updates (which require OS kernel updates).

Standardization Status: QUIC is still in the process of being standardized as an Internet RFC [QUIC 2020]. The core transport specification and the HTTP/3 mapping are both at the Proposed Standard level within the IETF.

Important: QUIC is not a replacement for TCP at the transport layer — it runs over UDP. The "transport-layer functionality" is implemented in user space at the application layer. This design choice enables rapid innovation.

Streams in QUIC

A stream is an abstraction for reliable, in-order bi-directional delivery of data between two QUIC endpoints. Multiple streams can be multiplexed through a single QUIC connection, and new streams can be added quickly after connection establishment.

QUIC Connection & Stream IDs:
Connection ID: identifies the QUIC connection between endpoints
Stream ID: identifies a specific stream within a connection
Both IDs are carried in the QUIC packet header. Data from multiple streams may be packed into a single QUIC segment over UDP.

Head-of-Line (HOL) Blocking Avoidance

This is QUIC's most significant advantage. In HTTP/1.1 over TCP, all HTTP requests share a single byte stream. If a segment carrying bytes from one request is lost, all subsequent requests are blocked until retransmission — the HOL blocking problem.

HTTP/1.1 + TCP (HOL Blocked)

One TCP connection → one byte stream

Lost packet at byte 500 blocks bytes 500+ from all pending HTTP requests, even if they belong to different resources.

HTTP/3 + QUIC (No HOL)

One QUIC connection → multiple independent streams

Each stream has its own byte-stream numbering and reliability context. A lost packet only affects the specific stream(s) whose data was in that segment — other streams deliver data immediately to the application without waiting.

QUIC packets can carry data from multiple streams in a single UDP datagram. The per-stream framing allows the receiver to reassemble and deliver each stream independently.

SCTP: The Predecessor

The Stream Control Transmission Protocol (SCTP) [RFC 4960] pioneered the notion of multiplexing multiple application-level streams through a single connection. SCTP is message-oriented (preserving message boundaries) rather than byte-stream-oriented like TCP. QUIC adopts a similar multi-stream model. SCTP is used in 4G/5G cellular control plane protocols.

Exam Tip: The key distinction for HOL blocking: TCP delivers bytes in order on a single stream → one loss blocks all streams. QUIC delivers per-stream in order → one loss blocks only that stream.

QUIC Reliable Transfer

QUIC provides reliable data transfer to each stream separately using acknowledgment mechanisms similar to TCP's [RFC 5681]. This means a lost UDP segment only impacts streams whose data was in that segment.

QUIC Reliability Model:
Per-Stream: Reliable, in-order delivery
Cross-Stream: No ordering guarantees
Stream A can deliver data to the application even while Stream B is waiting for retransmission

Congestion Control

QUIC's congestion control is based on TCP NewReno [RFC 6582], a slight modification of TCP Reno. The QUIC recovery draft [QUIC-recovery 2020] explicitly states that algorithms parallel well-known TCP ones. Key mechanisms:

QUIC Congestion Control (based on TCP NewReno): - Slow Start: Exponential growth (double cwnd per RTT) - Congestion Avoidance: Additive increase (1 MSS per RTT) - Fast Recovery: Halve cwnd on triple duplicate ACK - Loss Detection: Retransmission timer per packet - SACK-based: Selective ACK for efficient recovery

Per-Stream RDT

Each stream has its own reliable in-order delivery. QUIC maintains stream-level sequence numbers for ordering within the stream, plus packet-level sequence numbers for loss detection.

Faster Deployment

Because QUIC is at the application layer, updates can happen at "application-update timescales" — weeks or days instead of years for kernel-level TCP changes. This allows rapid iteration on new congestion control algorithms.

Common Confusion: QUIC's congestion control is TCP-friendly — it is based on TCP NewReno, so it competes fairly with TCP flows in the network. Despite running over UDP, QUIC does NOT behave like a UDP source (which has no congestion control).

Worked Examples

Example 1: HOL Blocking — HTTP/1.1 vs HTTP/3

Problem: A web page contains 4 objects (index.html, style.css, script.js, image.jpg). Each object fits in one TCP/UDP segment. The segment carrying style.css is lost. Compare the delivery delay of the remaining objects under HTTP/1.1 over TCP vs HTTP/3 over QUIC. Assume RTT = 100 ms, retransmission timeout = 200 ms.

Solution:

HTTP/1.1 over TCP (single connection):

Segments arrive in order: [index.html] [style.css] [script.js] [image.jpg]

style.css is lost. TCP delivers bytes in order → script.js and image.jpg are buffered at receiver, not delivered to application until style.css is retransmitted.

Delivery timeline: index.html at t=0, style.css at t=200ms, script.js at t=200ms, image.jpg at t=200ms

Total blocking delay for last object: 200 ms

HTTP/3 over QUIC (4 streams):

Each object in its own stream. style.css is lost, but index.html, script.js, and image.jpg are in separate streams.

Delivery timeline: index.html at t=0, script.js at t=0, image.jpg at t=0, style.css at t=200ms

Total blocking delay for last object: 0 ms (3 of 4 delivered immediately)

QUIC saves 200 ms of HOL blocking delay compared to TCP.

Example 2: QUIC Handshake vs TCP+TLS Handshake RTT Comparison

Problem: A client in New York connects to a server in London (RTT = 80 ms). Calculate the total handshake time before the client can send the first HTTP request for: (a) TCP + TLS 1.3, (b) QUIC initial connection, (c) QUIC repeat connection.

Solution:

(a) TCP + TLS 1.3:

TCP 3-way handshake: 1 RTT = 80 ms

TLS 1.3 handshake: 1 RTT = 80 ms (ClientHello → ServerHello+Done, then client sends Finished)

Total: 160 ms before first HTTP request

(b) QUIC initial connection:

Combined connection + TLS handshake: 1 RTT = 80 ms

Total: 80 ms (50% reduction)

(c) QUIC repeat connection (0-RTT):

Client sends cached credentials + first HTTP request immediately

Total: 0 ms — data sent in the first flight

Exam Point: The 0-RTT feature of QUIC is only possible for repeat connections to the same server where cached session credentials are available. Initial connections always require 1 RTT.
Example 3: Multi-Stream Multiplexing Efficiency

Problem: A QUIC connection carries 5 streams. Each stream sends 10 KB of data. The path has a loss rate of 2%. How many bytes (on average) must be retransmitted if a lost segment carries data from 1 stream vs all 5 streams? Assume MSS = 1,500 bytes.

Solution:

Total data: 5 × 10 KB = 50 KB ≈ 34 segments (at ~1,500 bytes each)

Expected losses: 34 × 0.02 ≈ 0.68 segments (approximately 1 segment lost)

Case 1: Each segment carries data from 1 stream only (QUIC optimal):

Lost segment = 1,500 bytes from stream X. Only stream X waits for retransmission = 1,500 bytes retransmitted.

Other 4 streams: unaffected — 40 KB delivered immediately.

Case 2: One segment carries data from all 5 streams (packed):

Lost segment affects all 5 streams. All 5 streams stall until retransmission.

Bytes retransmitted: 1,500 bytes (same), but impacted streams = 5.

QUIC's per-stream reliability means only the affected stream(s) wait for retransmission. The key benefit is reduced application-level delay, not reduced bandwidth overhead.
