Generalized Forwarding & OpenFlow

Computer Networking (Kurose & Ross) — Chapter 4: Network Layer: Data Plane

The Match-Plus-Action Paradigm

Traditional routers forward based on a single field (destination IP). Generalized forwarding matches over multiple header fields spanning multiple protocol layers and executes one or more actions. This decouples the control plane from the data plane and is the foundation of Software-Defined Networking (SDN). The OpenFlow protocol [McKeown 2008, ONF 2020, Casado 2014, Tourrilhes 2014] is the canonical implementation of generalized forwarding, and emerged from the broader SDN revolution [Feamster 2013].

Traditional Forwarding

• Match: destination IP only

• Action: forward to next hop

• Fixed function per device

Rigid, vendor-specific

Generalized Forwarding

• Match: 12+ header fields

• Action: forward, drop, modify, etc.

• Programmable per flow table

Flexible, open API

Flow Table Structure

A flow table entry consists of three components:

Flow Table Entry = (Header Fields, Counters, Actions)
Header Fields — match pattern with wildcards; Counters — packets/bytes matched; Actions — what to do on match

Match-Plus-Action Algorithm (OpenFlow)

for each packet received: for each flow table entry (in priority order): if match(packet.headerFields, entry.pattern): entry.counters.packets++ entry.counters.bytes += packet.size execute(entry.actions) break if no match found: send packet to controller (or drop)
Common Mistake: Assuming flow entries are checked in any order. Entries have explicit priority values — higher priority entries are matched first. When priorities are equal, the most specific (fewest wildcards) entry wins.

Worked Examples — Match-Plus-Action

Example 1: Simple IP Forwarding via Flow Table

A switch has a flow table with two entries. A packet with IP dst = 10.1.2.3 arrives on port 2.

Entry 1: match(IP dst = 10.1.1.*, priority=10) → forward(port 3)
Entry 2: match(IP dst = 10.1.2.*, priority=10) → forward(port 4)

Result: Packet matches Entry 2 (10.1.2.* covers 10.1.2.3). Forwarded out port 4.

Example 2: Priority Disambiguation

A packet has IP src = 192.168.1.5, IP dst = 10.0.0.1, TCP dst port = 80.

Entry A: match(IP dst = 10.0.0.*, priority=5) → forward(port 1)
Entry B: match(IP src = 192.168.1.*, IP dst = 10.0.0.1, TCP dst=80, priority=20) → drop

Result: Entry B has higher priority (20 > 5). Packet is dropped even though both match.

Example 3: Multi-Action Processing

A packet with VLAN ID = 100 arrives. The matched entry specifies two actions.

Entry: match(VLAN ID = 100) → [strip_vlan, forward(port 5)]
Action 1: Strip the VLAN tag from the packet header.
Action 2: Forward the modified packet out port 5.

Result: The VLAN tag is removed, and the plain Ethernet frame exits port 5.

OpenFlow 1.0 Match Fields

OpenFlow 1.0 defines 12 match fields that span the physical layer (port), the link layer (Ethernet), the network layer (IP), and the transport layer (TCP/UDP). Each field can be set to an exact value or a wildcard.

OpenFlow 1.0 Flow Match Structure (12 fields): ┌─────────────────────────────────────────────┐ │ Ingress Port │ Physical port of arrival │ │ Ethernet src │ 48-bit MAC address │ │ Ethernet dst │ 48-bit MAC address │ │ Ethernet Type │ 0x0800 (IPv4), 0x0806...│ │ VLAN ID │ 12-bit VLAN identifier │ │ VLAN Priority │ 3-bit 802.1p priority │ │ IP src │ 32-bit IPv4 address+mask │ │ IP dst │ 32-bit IPv4 address+mask │ │ IP Protocol │ TCP=6, UDP=17, ICMP=1 │ │ IP ToS │ 8-bit Type of Service │ │ TCP/UDP src port│ 16-bit transport src │ │ TCP/UDP dst port│ 16-bit transport dst │ └─────────────────────────────────────────────┘
Common Mistake: Confusing wildcard matching with CIDR subnet matching. In OpenFlow, IP source and destination fields use a bitmask (not CIDR prefix length). For example, 10.1.0.0/255.255.0.0 is equivalent to a 16-bit prefix length.

Wildcards and Bitmasks

Each field in a flow entry can be either an exact value or a wildcarded value. For IP fields, a bitmask specifies which bits must match. The priority field resolves conflicts when multiple entries match.

Wildcard Semantics:
match(header, pattern) = (header & mask) == (value & mask)
A field matches if the header bits (masked) equal the pattern bits (masked). A mask of 0 means "wildcard" (match anything).

Evolution of OpenFlow Match Fields

While OpenFlow 1.0 defined 12 match fields, more recent versions of the OpenFlow specification have grown this set to 41 match fields [Bosshart 2014]. This expansion reflects the demand for finer-grained control over network traffic as SDN deployments matured.

Design Constraints: Why Some Fields Cannot Be Matched

You may wonder why certain header fields — such as the TTL (Time-to-Live) field or the datagram length — are not included among the matchable fields. The answer lies in the fundamental tradeoff between functionality and complexity. The "art" in choosing an abstraction for generalized forwarding is to provide enough functionality to be useful without over-burdening the abstraction with too much detail that would compromise performance or complicate the interface.

This design philosophy is captured well by computer architect Butler Lampson:

Lampson's Principle of Abstraction [Lampson 1983]:
"Do one thing at a time, and do it well. An interface should capture the minimum essentials of an abstraction. Don't generalize; generalizations are generally wrong."

In the context of OpenFlow, the designers deliberately limited the match fields to the most commonly useful set — those spanning L2 through L4 — rather than attempting to expose every possible header field. Adding TTL or datagram length matching would add complexity to the switch hardware and the controller interface with limited practical benefit, as those fields rarely appear in forwarding policies.

Worked Examples — Match Fields

Example 1: MAC-Layer Filtering

Configure a flow entry that matches all ARP packets (EtherType = 0x0806) from a specific source MAC.

Eth Type = 0x0806, Eth src = AA:BB:CC:DD:EE:FF, all other fields = wildcard
Action: forward to controller

Result: Only ARP packets from AA:BB:CC:DD:EE:FF are intercepted; all other traffic continues normally.

Example 2: Subnet Traffic Matching

Match all traffic to or from subnet 10.10.0.0/16 with TCP destination port 443 (HTTPS).

IP src = 10.10.0.0/255.255.0.0, IP dst = 10.10.0.0/255.255.0.0
IP proto = 6 (TCP), TCP dst port = 443

Result: Any HTTPS session involving the 10.10.x.x subnet is matched.

Example 3: VLAN-Aware Forwarding

Match all packets with VLAN ID = 200 and priority = 5 (highest) from a specific ingress port.

Ingress port = 3, VLAN ID = 200, VLAN priority = 5
All other fields = wildcard

Result: High-priority VLAN 200 traffic arriving on port 3 is isolated for special processing.

Quick Reference Card

12 fields: Ingress port, Eth src/dst/type, VLAN ID/priority, IP src/dst/proto/ToS, TCP/UDP src/dst

Wildcard: Bitmask per field; all zeros = match anything

Priority: Integer; higher value = checked first

Default: Table-miss entry with lowest priority catches unmatched packets

OpenFlow Actions

When a packet matches a flow entry, the switch executes the associated action set. Actions determine what happens to the packet — it may be forwarded, dropped, modified, or sent to the controller.

Action Types

ActionDescriptionUse Case
Forward(port)Send packet out a specific physical portNormal routing/switching
FloodSend on all ports except ingressBroadcast, learning switch
DropSilently discard the packetFirewall, access control
Modify-FieldRewrite a header field (e.g., MAC, IP, VLAN)NAT, tunneling, tagging
Send-to-ControllerEncapsulate and forward to SDN controllerFirst-packet handling, policy
Enqueue(port, queue)Place on specific QoS queueTraffic shaping, QoS
Common Mistake: Assuming forward and flood are the same. Forward(port) sends to exactly one port. Flood sends to all ports except the one the packet arrived on. Flooding without loop prevention can cause broadcast storms.

Action Set Execution

A flow entry can specify a list of actions that execute sequentially. The order matters — a modify-field action followed by forward changes the packet before forwarding.

Action Set Processing: for each action in entry.actions: switch action.type: case FORWARD: output packet to specified port case DROP: discard packet (stop processing) case MODIFY_FIELD: packet.header[field] = newValue case SEND_TO_CONTROLLER: encapsulate and send via OpenFlow protocol case FLOOD: output to all ports except ingress case ENQUEUE: place packet on QoS queue

Worked Examples — Actions

Example 1: DNAT via Modify-Field

Rewrite the destination MAC and IP for traffic arriving on port 2 destined to a virtual IP.

Match: ingress=2, IP dst=10.0.0.100
Action list: [modify_field(IP dst → 10.0.0.50), modify_field(Eth dst → 00:11:22:33:44:55), forward(port 5)]

Result: The packet's IP destination is rewritten to 10.0.0.50, its MAC is rewritten, and it is sent out port 5.

Example 2: Traffic Mirroring via Multiple Actions

Forward normal traffic while sending a copy to a monitoring port.

Match: IP dst = 10.1.1.0/24, TCP dst = 80
Action list: [forward(port 3), forward(port 10)] // port 10 = monitoring

Result: HTTP traffic to 10.1.1.x is forwarded normally (port 3) AND a copy goes to the monitor (port 10).

Example 3: Drop Suspicious Traffic

All traffic from a known attack source IP is dropped before it reaches internal servers.

Match: IP src = 198.51.100.5
Action: drop

Result: Every packet from 198.51.100.5 is silently discarded. No other entries are checked after the drop.

Quick Reference Card

Forward: Send to one or more physical ports

Drop: Silently discard — acts as firewall rule

Modify-Field: Rewrite any header field

Send-to-Controller: Escalate to SDN controller for policy decision

Counters: Track packets, bytes, and duration per entry

Network Application Examples

These examples show how OpenFlow flow table entries combine match fields and actions to implement real network functions.

Example A: Simple Layer-3 Forwarding

Two switches (s1, s2) forward packets based on destination IP subnet. Hosts h1 and h2 are on different subnets behind s1 and s2 respectively.

Network topology: h1 (10.3.0.1) ── port 1 ─ [s1] ── port 4 ── [s2] ── port 2 ── h2 (10.2.0.1) Flow table for s1 (highest priority first): Priority Entry Pattern Action 20 ingress=1, IP src=10.3.*.*, IP dst=10.2.*.* forward(4) 15 IP dst=10.2.*.* forward(4) 10 ingress=4, IP src=10.2.*.*, IP dst=10.3.*.* forward(1) 5 (table-miss, all wildcards) send_to_controller
Example 1: h1 sends to h2

Packet: IP src=10.3.0.1, IP dst=10.2.0.1, arrives on port 1 of s1.

Entry with priority 20 matches (ingress=1, IP src=10.3.*.*, IP dst=10.2.*.*).

Result: Forwarded out port 4 toward s2.

Example 2: h2 sends to h1

Packet: IP src=10.2.0.1, IP dst=10.3.0.1, arrives on port 4 of s1.

Entry with priority 10 matches (ingress=4, IP src=10.2.*.*, IP dst=10.3.*.*).

Result: Forwarded out port 1 toward h1.

Example B: Load Balancing

An OpenFlow switch distributes incoming HTTP traffic across two server pools based on TCP port 80. The ingress port determines which server pool handles the request.

Load balancer flow table on s1: Priority Entry Pattern Action 30 ingress=1, TCP dst=80 forward(2) → Server Pool A 30 ingress=2, TCP dst=80 forward(3) → Server Pool B 20 TCP dst=80 forward(2) → default to Pool A 10 (table-miss) send_to_controller
Example 3: HTTP request from external link

Packet: TCP dst=80, arrives on port 1 (external uplink).

Entry priority 30 matches: ingress=1, TCP dst=80 → forward(2).

Result: Sent to Server Pool A (port 2).

Example 4: HTTP request from internal network

Packet: TCP dst=80, arrives on port 2.

Entry priority 30 matches: ingress=2, TCP dst=80 → forward(3).

Result: Sent to Server Pool B (port 3). Traffic is load-balanced by source.

Example C: Stateful Firewall

A firewall switch only permits traffic from specific trusted sources while dropping all other traffic. The controller installs rules dynamically.

Firewall flow table on s1: Priority Entry Pattern Action 100 IP src=203.0.113.0/24, TCP dst=443 forward(4) 100 IP src=203.0.113.0/24, TCP dst=80 forward(4) 50 IP dst=10.0.0.0/8 drop 10 (table-miss) send_to_controller
Example 5: Permitted traffic

Packet: IP src=203.0.113.5, TCP dst=443.

Priority 100 entry matches (IP src in 203.0.113.0/24, TCP dst=443).

Result: Forwarded out port 4 to internal network.

Example 6: Blocked traffic

Packet: IP src=198.51.100.99, IP dst=10.0.0.5.

Priority 50 entry matches (IP dst in 10.0.0.0/8).

Result: Packet is dropped. Note: The more specific forward rules don't match because IP src is not in 203.0.113.0/24.

Example D: Virtual Networks with Flow Tables

In homework problems, students explore how flow tables can be used to create virtual networks — two or more logically separate networks (each with their own independent and distinct forwarding behavior) that use the same physical set of packet switches and links. This is a direct application of the generalized forwarding abstraction: by installing different flow entries for different tenants, a single physical switch fabric can host multiple isolated virtual networks.

Example 7: Two Virtual Networks Sharing a Switch

Consider a physical switch s1 that must support two virtual networks, Red and Blue. Packets from each virtual network are identified by their ingress port and VLAN tag. Each virtual network must have independent forwarding behavior — meaning a packet in the Red network cannot leak into the Blue network.

Virtual Red: ingress ports {1,2}, VLAN ID = 10 → forward according to Red's routing table
Virtual Blue: ingress ports {3,4}, VLAN ID = 20 → forward according to Blue's routing table
Cross-virtual-network traffic is implicitly dropped because no flow entry matches Red traffic destined for Blue's ports, and vice versa.

Result: Two independent virtual networks operate on the same physical switch, each with its own forwarding semantics.

Beyond OpenFlow: P4 — Richer Programmability

The match-plus-action flow tables of OpenFlow represent a limited form of programmability — the controller can install arbitrary (match, action) pairs, but the set of matchable fields and the set of possible actions are fixed by the specification. P4 (Programming Protocol-independent Packet Processors) [P4 2020, Bosshart 2014] is a language that provides even richer programmability designed specifically for datagram processing at line rate:

  • Variables — maintain state across packets
  • General-purpose arithmetic — compute header field values
  • Boolean operations — complex conditional matching logic
  • Functions — reusable processing blocks
  • Conditional statements — if/else branching in the data plane
  • Custom header formats — parse any protocol, not just Ethernet/IP/TCP
  • Custom actions — programmer-defined processing primitives

While OpenFlow fixes the match fields and predefined actions, P4 allows the programmer to define the entire packet-processing pipeline — including the parser, match tables, and action logic — all while maintaining line-rate performance on target hardware.

FeatureOpenFlowP4
Header definitionsFixed (12 fields)Programmer-defined
Match typesExact + wildcardExact, ternary, LPM, range

TargetOpenFlow switchesASICs, FPGAs, NPUs, software
ProgrammabilityLimited (fixed fields + actions)Full (custom headers + logic)

Quick Reference Card

Simple forwarding: Match IP dst subnet → forward to next-hop port

Load balancing: Match ingress + TCP port → different server pools

Firewall: Match trusted source IPs → forward; match internal dest → drop

P4: Fully programmable match-action pipeline; custom headers and actions

Flow table = API: The controller programs switch behavior remotely

Common Mistake: Thinking that OpenFlow and P4 are competing technologies. OpenFlow is a protocol for the control-data plane interface. P4 is a language for programming the data plane itself. They can be used together — P4 to implement an OpenFlow-compatible pipeline.
