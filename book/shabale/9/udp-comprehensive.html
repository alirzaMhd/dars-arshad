Connectionless Transport: UDP

Computer Networking — Complete Guide for 20/20 Exam

UDP Overview

UDP (User Datagram Protocol), defined in RFC 768, is a no-frills, bare-bones transport protocol. Aside from multiplexing/demultiplexing and light error checking, it adds nothing to IP. If an application developer chooses UDP, the application is almost directly talking with IP.

UDP Service Model:
Unreliable, Connectionless Datagram Delivery
No handshaking, no reliability, no congestion control, no flow control
Thought Experiment: The "Vacuous" Transport Protocol

Suppose you wanted to design a no-frills, bare-bones transport protocol. You might first consider a vacuous transport protocol — on the sending side, take messages from the application and pass them directly to the network layer; on the receiving side, take messages from the network and pass them directly to the application.

But you must do a little more than nothing! At minimum, the transport layer must provide multiplexing/demultiplexing to pass data between the network layer and the correct application-level process. UDP does just about as little as a transport protocol can do — and that's exactly its strength.

Why Choose UDP?

Finer Application Control

UDP sends data immediately when the app passes it. No congestion-control throttling. Ideal for real-time apps that need a minimum sending rate.

No Connection Establishment

UDP "blasts away" without formal preliminaries. No three-way handshake delay — saving 1 RTT before data starts flowing.

No Connection State

UDP maintains no send/receive buffers, congestion-control params, or sequence numbers. A UDP server can support many more clients than a TCP server.

Small Header Overhead

UDP: 8 bytes header vs TCP: 20 bytes. This matters for applications with many small messages (e.g., DNS queries).

Applications Using UDP

Application Protocol Why UDP?
Domain Name System DNS Avoids connection-establishment delay; tiny messages
Network Management SNMP Must work under network stress when TCP would fail
Streaming Multimedia DASH, RTP Tolerates small loss; needs consistent rate, not congestion-throttled
Internet Telephony SIP/RTP (typically) Delay-sensitive; loss-tolerant; poor reaction to TCP congestion control
QUIC (HTTP/3) QUIC over UDP Reliability at app layer; avoids TCP head-of-line blocking
"Have Your Cake and Eat It Too"

An application using UDP can build reliability into the application itself (using ACKs, sequence numbers, timers). This allows reliable communication without being subjected to TCP's congestion-control rate limits. The QUIC protocol (Section 3.8) is a prime example — it implements reliability at the application layer over UDP. The application can "have its cake and eat it too" — reliable delivery without TCP's transmission-rate constraints.

UDP has NO congestion control. If everyone streams high-bit-rate video over UDP without regulation, routers overflow and the network collapses. Uncontrolled UDP can crowd out TCP sessions.

UDP Segment Structure

The UDP segment has an 8-byte header followed by application data. The header consists of four 2-byte fields:

UDP Segment Format:
+--------+--------+--------+--------+
| Source Port | Destination Port |
+--------+--------+--------+--------+
| Length | Checksum |
+--------+--------+--------+--------+
| Application Data ... |
+---------------------------------------+
Field Size Description
Source Port 2 bytes (16 bits) Port number of sending process (0-65535). Used as return address.
Destination Port 2 bytes (16 bits) Port number of destination process. Used for demultiplexing.
Length 2 bytes (16 bits) Length of UDP segment in bytes (header + data). Minimum = 8 (header only).
Checksum 2 bytes (16 bits) Error detection over segment + pseudo header. 1s complement sum.
Length Field Formula:
Length = 8 + len(Application Data)
Where 8 is the fixed header size in bytes. Minimum value = 8 (empty data).
Maximum value = 65535 bytes (theoretical, limited by IP datagram size in practice).

The application data field contains the payload — for DNS it's the query/response, for streaming audio it's audio samples, etc.

UDP Checksum

The UDP checksum provides error detection — determining whether bits in the segment have been altered during transit (by noise in links or memory errors in routers).

Checksum Calculation:
Checksum = ~(sum of all 16-bit words with 1s complement wrap-around)
Sender computes the 1s complement of the 1s complement sum (wrapping overflow).
Receiver adds all 16-bit words including checksum — result must be all 1s (0xFFFF) if no errors.

Checksum Example (from textbook)

Given three 16-bit words:

Word 1: 0110011001100000
Word 2: 0101010101010101
Word 3: 1000111100001100

Sum 1+2: 1011101110110101
Add 3: 0100101011000010 (overflow wrapped around)
1s Compl: 1011010100111101 ← Checksum

At Receiver (all 4 words including checksum):
Sum: 1111111111111111 ← No errors detected!

Why UDP Checksum When Link Layer Checks?

Reasons for UDP Checksum

• Not all link-layer protocols provide error checking

• Bit errors can occur in router memory (not detected by link)

• End-end principle: functions must be implemented at the highest level where they are needed

End-End Principle

Since certain functionality (error detection) must be implemented on an end-end basis: "functions placed at lower levels may be redundant or of little value when compared to the cost of providing them at the higher level." [Saltzer 1984]

UDP provides error detection but NOT error recovery. If the checksum fails, some implementations simply discard the damaged segment; others pass it to the application with a warning. Applications that need reliability must add it themselves.

Worked Examples: UDP

Example 1: Checksum Calculation with 4 Words

Given: Four 16-bit words: 1100110011001100, 1010101010101010, 1111000011110000, 0000111100001111

Step 1: Sum word 1 + word 2:

1100110011001100
+ 1010101010101010
= 0111011101110110 (with carry out=1, wrapped)
= 0111011101110111

Step 2: Add word 3:

0111011101110111
+ 1111000011110000
= 0110011101100111 (carry=1, wrapped)
= 0110011101101000

Step 3: Add word 4:

0110011101101000
+ 0000111100001111
= 0111010101110111 (no overflow)

Step 4: 1s complement of each bit:

Checksum = 1000101010001000

At the receiver, adding all 5 words together (including checksum) gives 1111111111111111 if no errors.

Example 2: DNS over UDP — Latency Advantage

Scenario: A DNS query is sent to a resolver 50ms away (RTT=50ms).

UDP path: Query sent immediately (t=0) → Reply received (t=25ms). Total: 25ms (plus DNS server processing).

Hypothetical TCP path: SYN (t=0) → SYN-ACK (t=25ms) → ACK+Query (t=50ms) → Reply (t=75ms). Total: 75ms.

UDP is 3x faster for this simple query due to no connection establishment.

Example 3: UDP Segment Length Calculation

Scenario: An application sends 1460 bytes of data via UDP.

Step 1: UDP header = 8 bytes

Step 2: Length field = header + data = 8 + 1460 = 1468 bytes

Step 3: This fits within a typical Ethernet MTU of 1500 bytes (1468 + 20 IP header + 14 Ethernet = 1502... but if Ethernet MTU = 1500, IP fragmentation may be needed).

Answer: Length field value = 1468. The segment can hold max 65527 bytes of data (65535 - 8).

In practice, UDP payloads are limited by the path MTU to avoid fragmentation.

Example 4: UDP vs TCP — Server Capacity Comparison

Scenario: A server has memory for connection state. TCP requires ~4KB per connection (send/receive buffers, congestion state).

TCP server with 4GB RAM: 4GB / 4KB = ~1,048,576 concurrent connections

UDP server with 4GB RAM: No per-connection state. Can handle potentially millions more clients since no state is stored per client.

The memory savings from UDP's connectionless design allow servers to scale dramatically higher for applications like DNS and SNMP.

When to Use UDP

• DNS queries

• SNMP network management

• Streaming media

• VoIP / Internet telephony

• DHCP (bootstrapping)

Common UDP Mistakes

• Assuming UDP is reliable (it's not)

• Forgetting checksum calculation steps

• Miscomputing 1s complement wrap-around

• Thinking UDP has congestion control
