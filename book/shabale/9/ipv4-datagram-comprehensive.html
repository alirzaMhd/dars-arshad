IPv4 Datagram Header Structure

The IPv4 datagram is the network-layer packet used by the Internet Protocol. The standard header is 20 bytes (without options). Every field has a specific role in routing, fragmentation, and error detection.

Standard Header Size (no options):
Header = 20 bytes
The IP datagram header has a fixed 20-byte portion when no options are present
Maximum Datagram Size:
Max Size = 216 - 1 = 65,535 bytes
The 16-bit Total Length field limits datagrams to 65,535 bytes total (header + payload)
Header + TCP Overhead:
IP Header (20) + TCP Header (20) = 40 bytes
Every TCP segment incurs 40 bytes of network+transport layer overhead

The HLEN field counts in 32-bit words, NOT bytes. A value of 5 means 5 x 4 = 20 bytes. If HLEN=7, the header is 28 bytes long. Always multiply HLEN by 4 to get the byte count.

Worked Examples

Example 1: Calculating Payload Size

An IPv4 datagram has Total Length = 1200 bytes and HLEN = 5. What is the payload size?

Step 1: HLEN = 5 means header = 5 × 4 = 20 bytes
Step 2: Payload = Total Length - Header = 1200 - 20 = 1180 bytes

Example 2: Protocol Field Interpretation

A router receives an IPv4 datagram with Protocol field = 6. What transport-layer protocol should receive the payload at the destination?

Protocol number 6 corresponds to TCP. The destination host's IP layer will pass the datagram payload to the TCP module for processing. If Protocol = 17, it would be passed to UDP.

Example 3: TTL and Header Length

A captured datagram has the first 20 hex bytes: 45 00 00 3C 1C 46 40 00 40 06 B1 E6 C0 A8 00 01 C0 A8 00 02. Determine the version, header length, and TTL.

Byte 1 (0x45):
  High nibble = 4 → IPv4
  Low nibble = 5 → header = 5 × 4 = 20 bytes
Byte 9 (0x40): TTL = 64 (decimal)
Byte 10 (0x06): Protocol = 6 (TCP)

IP Fragmentation

When an IP datagram is larger than the Maximum Transmission Unit (MTU) of the outgoing link, the router fragments it into smaller pieces. Fragments are reassembled at the destination host, not at intermediate routers.

Fragment Offset Encoding:
Offset (bytes) = Fragment Offset field value × 8
The 13-bit offset field stores the position divided by 8 (since offset must be on 8-byte boundaries)
Number of Fragments:
N = ceil( (Payload Length) / (MTU - Header Length) )
Each fragment carries its own IP header (20 bytes typically)
Maximum Data per Fragment:
Max Data per Fragment = (MTU - Header) rounded down to nearest multiple of 8
Fragment payloads must be multiples of 8 bytes (except the last fragment)

Fragmentation Fields

FieldBitsRole in Fragmentation
Identification16All fragments of the same datagram share the same ID
Flag: Reserved (R)1Always 0
Flag: Don't Fragment (DF)1If set=1, router drops datagram instead of fragmenting
Flag: More Fragments (MF)1MF=1 means more fragments follow; MF=0 means last fragment
Fragment Offset13Position of this fragment's data in the original datagram (in 8-byte units)
Fragment payloads (except the last) MUST be multiples of 8 bytes. If your computed payload is not a multiple of 8, truncate it down to the nearest multiple. The last fragment can be any size.

Worked Examples

Example 1: Basic Fragmentation

A 4000-byte IP datagram (20-byte header, 3980-byte payload) must traverse a link with MTU = 1500 bytes. How many fragments, and what are their offsets?

Max data per fragment: floor((1500 - 20) / 8) × 8 = floor(1480/8) × 8 = 185 × 8 = 1480 bytes
Fragment 1: offset = 0, data = 1480 bytes, MF=1
Fragment 2: offset = 185 × 8 = 1480, data = 1480 bytes, MF=1
Fragment 3: offset = 370 × 8 = 2960, data = 3980 - 2960 = 1020 bytes, MF=0
3 fragments total. All use Identification = same value.

Example 2: DF Flag Set

A host sends a datagram of 2000 bytes (including header) with DF=1 over an Ethernet link (MTU=1500). What happens?

The datagram (2000 bytes) exceeds the MTU (1500 bytes). Since DF=1 (Don't Fragment), the router drops the datagram and sends an ICMP "Fragmentation Needed" error message back to the source.

Example 3: Reassembling Offsets

Three fragments arrive at the destination with the following offset and MF values: (offset=0, MF=1), (offset=185, MF=1), (offset=370, MF=0). What is the total reassembled payload size?

Fragment 1: bytes 0-1479 (1480 bytes)
Fragment 2: bytes 1480-2959 (1480 bytes)
Fragment 3: starts at 370 × 8 = 2960. Since MF=0, this is the last.
To find Fragment 3 payload size, we need the Total Length field. If Total Length = 1040, then payload = 1040 - 20 = 1020 bytes.
Total reassembled payload = 1480 + 1480 + 1020 = 3980 bytes

Header Checksum

The IPv4 header checksum protects only the header (not the payload). It must be recomputed at every hop because the TTL field changes. The algorithm is the Internet checksum: 1s complement sum of all 16-bit words in the header.

Internet Checksum Algorithm:
Checksum = ~( ∑ (header 16-bit words in 1s complement) )
The checksum is the 1s complement of the 1s complement sum of all 16-bit words in the header (with the checksum field itself treated as zero during computation)

Checksum Computation Pseudocode

// Input: array of 16-bit words representing IP header (checksum field = 0) // Output: 16-bit Internet checksum function computeInternetChecksum(words[]): sum = 0 for each word in words: sum = sum + word // ordinary binary addition if sum > 0xFFFF: // carry-out detected sum = (sum & 0xFFFF) + 1 // wrap-around (end-around carry) checksum = ~sum & 0xFFFF // ones' complement return checksum // Verification at receiver: // Compute checksum over entire header INCLUDING checksum field // If result == 0, no error detected
The IP checksum only covers the HEADER, not the payload. TCP and UDP have their own checksums covering the entire segment. The IP checksum must be recomputed at every router because TTL changes. This is a significant processing cost — which is why IPv6 removed the header checksum entirely.

Worked Examples

Example 1: Simple Checksum Calculation

Given three 16-bit header words: 0x4500, 0x003C, 0x1C46. Compute the checksum.

Sum: 0x4500 + 0x003C = 0x453C
Add next: 0x453C + 0x1C46 = 0x6182 (no carry)
1s complement: ~0x6182 = 0x9E7D
(For a full header, all 10 words of the 20-byte header would be summed)

Example 2: End-Around Carry

Sum two 16-bit words: 0xFFFF + 0x0001.

Ordinary sum: 0xFFFF + 0x0001 = 0x10000 (this is 17 bits)
End-around carry: 0x0000 + 1 = 0x0001
This is the 1s complement sum. The 1s complement (~0x0001) = 0xFFFE would be the stored checksum.

Example 3: Verification at Receiver

At the destination, the full header (including checksum field) is processed. The computed 1s complement sum of all words = 0xFFFF. What does this mean?

If the full header sum (including checksum) = 0xFFFF, then after taking 1s complement we get ~0xFFFF = 0x0000. A result of 0 indicates no errors detected. Any non-zero result means a bit error was detected, and the datagram is typically discarded.

Time-to-Live (TTL) Field

The 8-bit TTL field prevents datagrams from looping forever in the network. Each router decrements TTL by 1. When TTL reaches 0, the router drops the datagram and sends an ICMP Time Exceeded message to the source.

TTL Behavior:
TTLnew = TTLold - 1   (if TTLold > 0 → forward; if TTLold = 0 → drop)
Decremented exactly once per router hop
Some operating systems set initial TTL to 64 (Linux), 128 (Windows), or 255 (Solaris). When analyzing network traces, the initial TTL minus the current TTL equals the number of router hops traversed.

Worked Examples

Example 1: Hop Count from TTL

A Linux host sends a packet with initial TTL=64. The packet arrives at the destination with TTL=51. How many routers did it traverse?

Hops = Initial TTL - Arrival TTL = 64 - 51 = 13 routers

Example 2: TTL Expiration

A datagram with TTL=1 arrives at Router A. After decrement, what happens?

Router A decrements TTL from 1 to 0. The router drops the datagram and sends an ICMP "Time Exceeded" (Type 11) message back to the source IP address.

Example 3: Traceroute Mechanism

Traceroute sends packets with TTL=1, then TTL=2, then TTL=3, etc. What happens at each step?

TTL=1: First router decrements to 0, drops it, sends ICMP Time Exceeded. Source records RTT and Router A's IP.
TTL=2: First router forwards (TTL 2→1), second router decrements to 0, drops, sends ICMP. Source records Router B's IP.
TTL=N: Eventually reaches destination. Destination sends ICMP Port Unreachable (or the application response). Source now knows the entire path and per-hop RTTs.

Encapsulation in IPv4

The IP datagram's payload field typically carries a transport-layer segment (TCP or UDP). The 8-bit Protocol field tells the destination host which upper-layer protocol should receive the de-encapsulated data.

Protocol Number Mapping:
Protocol Number = 6 → TCP  |  Protocol Number = 17 → UDP
The protocol number in IP plays a role analogous to port numbers in transport layer — it binds the network layer to the transport layer above it
IPv4 + TCP Overhead Ratio:
Overhead % = 40 / (40 + Application Data) × 100%
For small application messages (e.g., 40 bytes), overhead = 40/(40+40) = 50%

Protocol number (IP header) and port number (TCP/UDP header) serve different purposes. Protocol number identifies which transport protocol is used (TCP=6, UDP=17). Port number identifies which application process (e.g., HTTP=80, DNS=53). They operate at different layers — do not confuse them!

Worked Examples

Example 1: Overhead Calculation

An application generates 100 bytes of data every 10ms, encapsulated in TCP then IP. What is the percentage of header overhead?

IP header: 20 bytes
TCP header: 20 bytes
Total header: 40 bytes
Total datagram: 40 + 100 = 140 bytes
Overhead %: 40/140 × 100 = 28.57%

Example 2: Identifying the Protocol

A captured IP datagram shows header byte 10 (1-indexed) = 0x11. What transport protocol is being carried?

The Protocol field is at byte 10 in the IP header. 0x11 = 17 decimal. Protocol number 17 = UDP. So the payload is a UDP segment.

Example 3: IPv6 Transition — Tunneling

Two IPv6 routers communicate through an IPv4-only network. An IPv6 datagram (40B header + 100B payload) must be tunneled. What is the total size of the IPv4 datagram carrying it?

IPv4 header: 20 bytes
IPv4 payload (the entire IPv6 datagram): 40 + 100 = 140 bytes
Total IPv4 datagram: 20 + 140 = 160 bytes
The IPv4 Protocol field would be 41, indicating the payload is an IPv6 datagram.
