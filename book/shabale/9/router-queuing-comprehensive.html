Queuing in Routers

Computer Networking: A Top-Down Approach — Kurose & Ross — Chapter 4

Input Queueing

In a router with input-buffered switching, packets arriving on an input port are placed in a queue at that input port when the switching fabric is busy. This occurs when Rswitch (the rate of the switching fabric) is not fast enough to transfer all arriving packets simultaneously.

Quick Reference Card
Definition: Packets wait at input ports when the switching fabric cannot keep up
Root Cause: Rswitch < N × Rline
Key Risk: Head-of-Line (HOL) blocking
Buffer Sizing: B = RTT × C

Buffer Sizing Formula

Traditional Buffer Sizing Rule
B = RTT × C
Where B = buffer size (bits), RTT = round-trip time (seconds), C = link capacity (bps). A router needs enough buffering to store one RTT's worth of data.
Large Number of TCP Flows (Modern)
B = RTT × C / √(2N)
Where N = number of long-lived TCP flows sharing the link. As N grows, statistical multiplexing allows smaller buffers.

Worked Examples

Example 1.1 — Basic Input Queue Buffer Sizing

A router has a line rate C = 10 Gbps and the average RTT of flows is 50 ms. Calculate the required input buffer size using the traditional rule.

▸ Solution:

B = RTT × C = 0.050 s × 10 × 109 bps = 500 × 106 bits = 62.5 MB

This is the amount of data a TCP sender can transmit in one RTT before seeing an ACK.

Example 1.2 — Multiple TCP Flows Buffer Sizing

If N = 100 long-lived TCP flows share the same 10 Gbps link (RTT = 50 ms), what buffer size does the modern formula recommend?

▸ Solution:

B = (RTT × C) / √(2N) = (500 Mb) / √(200) = 500 / 14.14 = 35.36 Mb ≈ 4.42 MB

With 100 flows, statistical multiplexing reduces required buffering by a factor of ≈14 compared to the traditional rule.

Example 1.3 — Determining Queue Depth from Arrival Rate

Four input lines each at 1 Gbps arrive at a switch fabric with capacity 2.5 Gbps. If packets are 1500 bytes each, estimate how quickly the input queue grows under sustained full load.

▸ Solution:

Aggregate arrival rate = 4 × 1 Gbps = 4 Gbps. Switch capacity = 2.5 Gbps. Excess rate = 4 − 2.5 = 1.5 Gbps.

In 1 second, excess data = 1.5 Gb = 187.5 MB. Each packet = 1500 B, so queue grows at 187.5 MB / 1500 B = 125,000 packets/second.

When Does Input Queuing Occur?

Input queuing occurs when the switching fabric cannot keep up with the aggregate arrival rate. However, if Rswitch (switching fabric transfer rate) is N times faster than Rline (line rate), then only negligible queuing will occur at input ports. This is because even in the worst case where all N input lines simultaneously receive packets destined for the same output, each batch of N packets can be cleared through the fabric before the next batch arrives.

Condition for Negligible Input Queuing
Rswitch ≥ N × Rline
When the switching fabric is at least N times faster than the line rate, all N input ports can be serviced before the next packet arrival, eliminating persistent input queues.
Example — Negligible Input Queuing

A router has N = 8 input ports each at Rline = 1 Gbps. The switching fabric operates at Rswitch = 10 Gbps. Is Rswitch fast enough to prevent input queuing?

▸ Solution:

Required Rswitch = N × Rline = 8 × 1 Gbps = 8 Gbps. Actual Rswitch = 10 Gbps ≥ 8 Gbps. Yes — negligible input queuing.

Even in the worst case where all 8 inputs send to the same output, the fabric can clear all 8 packets before the next packet arrives (1 Gbps → one packet every ~1.2 μs at 1500 bytes).

Head-of-Line (HOL) Blocking

HOL blocking occurs when the packet at the front of an input queue is destined for a busy output port. All packets behind it are blocked—even if their output ports are free. This severely limits throughput.

Key Insight: Under HOL blocking, the maximum throughput of an input-buffered switch is limited to approximately 58% of capacity, regardless of how fast the switching fabric is.
Quick Reference Card
Definition: Front packet blocks others behind it when its output is busy
Max Throughput: ~58% under uniform random traffic
Cause: Single FIFO queue per input port
Mitigation: Virtual Output Queues (VOQs)

Key Formula

Maximum Achievable Throughput (HOL)
λmax ≈ 0.586 × Rswitch
For a uniform traffic pattern, the maximum arrival rate per input port before the queue grows unbounded is about 58.6% of the switching fabric rate.

Worked Examples

Example 2.1 — Throughput Loss from HOL

An input-buffered switch has 8 input ports, each at 10 Gbps, and the switching fabric can run at 80 Gbps. What is the effective throughput per port under HOL?

▸ Solution:

Even though the fabric could handle 80 Gbps, HOL blocking limits each port to ~58.6% of its line rate:

Effective throughput per port = 10 Gbps × 0.586 = 5.86 Gbps

Total effective throughput = 8 × 5.86 = 46.88 Gbps (only 58.6% of the switch's 80 Gbps capacity is usable).

Example 2.2 — Queue Growth Near the HOL Threshold

An input port has arrival rate λ = 0.55 (relative to line rate) and service rate μ = 1.0. The HOL blocking factor reduces the effective service rate to μeff = 0.586 for each port. Is the queue stable? If λ = 0.60, what happens?

▸ Solution:

At λ = 0.55, λ < μeff = 0.586 ⇒ queue is stable.

At λ = 0.60, λ > μeff = 0.586 ⇒ queue grows unbounded.

This is why HOL blocking is so dangerous: only ~2.4% above threshold causes instability.

Example 2.3 — Mitigation with Virtual Output Queues

A 4-port router using simple input FIFO queues sees 55% throughput. After switching to Virtual Output Queues (VOQs), throughput reaches 95%. Calculate the improvement.

▸ Solution:

Instead of one FIFO per input, VOQ maintains one queue per output port at each input. This eliminates HOL because a packet destined for a free output is not blocked by one destined for a busy output.

Throughput gain = (95% − 55%) / 55% = 40 / 55 = 72.7% improvement

Output Queueing

In an output-buffered switch, packets are transferred from inputs to outputs immediately through a fast switching fabric (Rswitch ≥ N × Rline). Queuing only occurs at the output port when multiple input packets arrive simultaneously for the same output.

Even when the switching fabric is N times faster than the line rate, output queues still form due to traffic contention.

Quick Reference Card
Definition: Packets queue at the output port when multiple inputs target one output
Switch Speed: Rswitch ≥ N × Rline
Key Mechanisms: Drop-tail, RED, PIE, CoDel
Drop-tail: Drops arriving packet when buffer is full

Explicit Congestion Notification (ECN)

ECN [RFC 3168] is a mechanism that provides explicit congestion signaling without dropping packets. Instead of dropping a packet to signal congestion (as RED does probabilistically), an ECN-capable router marks the ECN bits in the IP packet header before the buffer is full. The receiver echoes this signal back to the sender, which then reduces its transmission rate.

ECN Marking (Section 3.7.2)
ECN = ECT(0), ECT(1), or CE
The IP header uses two bits: ECT (ECN-Capable Transport) set by the sender, and CE (Congestion Experienced) set by the router. When CE is set, the receiver marks the TCP ACK with ECE (ECN-Echo) to notify the sender of congestion.
⚠ Note: ECN requires support from both endpoints. If either endpoint is not ECN-capable, the router falls back to dropping packets. ECN is particularly valuable for latency-sensitive, loss-intolerant applications.

Buffer Management Formulas

Drop-tail Queue Behavior
P(drop) = max(0, (Q − B) / Q)
When queue occupancy Q reaches buffer limit B, arriving packets are dropped. Q is measured in packets or bytes.
Average Queue Length (RED)
avg_Q = (1 − w) × avg_Q + w × Q
RED maintains an exponentially weighted moving average of queue length. w is a small weight (typically 0.002). Drop probability increases as avg_Q moves between minth and maxth.

Worked Examples

Example 3.1 — Output Queue Buildup at Full Load

A 16-port router has Rline = 1 Gbps and Rswitch = 32 Gbps (twice N × Rline = 16 Gbps). Under uniform random traffic, each output port receives packets from 16 inputs. If each input sends at 50% load, what is the offered load to one output?

▸ Solution:

Each input sends 0.5 Gbps. Each output gets traffic from all 16 inputs. Fraction of each input's traffic destined to a given output = 1/16 (uniform).

Load per output = 16 × 0.5 Gbps × (1/16) = 0.5 Gbps = 50% utilization.

Even with a fast fabric, output queues form when aggregate demand to an output exceeds the output line rate.

Example 3.2 — Drop-tail Buffer Overflow

An output buffer has capacity B = 100 packets. Traffic arrives at rate λ = 1200 pkts/s and the output line transmits at μ = 1000 pkts/s. How long until the buffer overflows?

▸ Solution:

Net queue growth rate = λ − μ = 200 pkts/s. Starting from empty, time to fill 100 packets = 100 / 200 = 0.5 seconds.

After 0.5 s, every new packet is dropped (drop-tail). After the burst subsides, the buffer drains at 1000 pkts/s.

Example 3.3 — RED Early Detection

A RED-enabled output queue has minth = 20 pkts, maxth = 60 pkts, maxp = 0.1. The average queue length is 40 packets. Compute the drop probability.

▸ Solution:

P(drop) = maxp × (avg_Q − minth) / (maxth − minth)

P(drop) = 0.1 × (40 − 20) / (60 − 20) = 0.1 × 20/40 = 0.1 × 0.5 = 0.05 (5%)

RED probabilistically drops packets before the buffer fills, signalling TCP senders to slow down proactively.

Modern AQM: PIE and CoDel

Beyond RED, two more recent Active Queue Management (AQM) policies have been widely deployed to keep queuing delay low while maintaining high throughput:

PIE — Proportional Integral controller Enhanced [RFC 8033]
p(t) = α × (Q(t) − Qref) + β × (Q(t) − Q(t − Δt))
PIE uses a control-theoretic approach: it calculates a drop probability based on both the current queue deviation from a reference (proportional term) and the queue trend (integral term). This allows it to respond quickly to sudden congestion while maintaining stability.
CoDel — Controlled Delay [Nichols 2012]
if (sojourn_time > target) && (count > 0) then drop
CoDel focuses on packet sojourn time (time spent in the buffer) rather than queue length. It maintains a minimum sojourn time over a sliding window. When the minimum sojourn time exceeds a target (typically 5 ms), CoDel enters a dropping regime, with the drop rate increasing as the good queueing time persists.
AQM Evolution
RED (1993): Pioneering AQM; probabilistically drops based on avg queue length
PIE (2013): Control-theoretic; uses proportional-integral of queue deviation
CoDel (2012): Parameter-light; uses sojourn time as the congestion signal
Common Goal: Keep queues small while maintaining high link utilization
⚠ Common Mistake: Assuming a faster switching fabric eliminates all queuing. Output queues form because of contention from multiple inputs to the same output, not because of fabric speed. A 2× faster fabric does not solve the contention problem.

Bufferbloat

Bufferbloat is the phenomenon of persistently large queues in router buffers that cause excessively high delay without improving throughput. It arises when buffers are sized using the traditional B = RTT × C rule in environments with many flows or when buffers are cheap and over-provisioned.

Key Insight: Buffering is a double-edged sword. It absorbs bursts (good), but persistent large queues inflate latency without increasing throughput (bad). The goal is just enough buffering—enough to absorb bursts, not enough to cause bufferbloat.
Quick Reference Card
Definition: Large persistent queues causing high delay
Cause: Over-sized buffers + drop-tail + TCP
Consequence: RTT inflation (100ms → 1s+)
Solution: AQM (RED, PIE, CoDel) + smaller buffers
Real-world: DOCSIS 3.1 added a specific AQM mechanism [RFC 8033, RFC 8034] to combat bufferbloat while preserving bulk throughput performance

Core Formulas

Traditional Buffer Sizing (over-estimates for many flows)
Btrad = RTT × C
Assumes one TCP flow. With N flows, this over-allocates by a factor of √(2N).
Modern Buffer Sizing (avoids bufferbloat)
Bmod = RTT × C / √(2N)
For large N, buffers can be dramatically smaller without sacrificing throughput.
Queuing Delay under Bufferbloat
Dqueue = Q / C
If a buffer holds Q bits and the link rate is C, the queuing delay is Q / C. With bufferbloat, Q ≈ B even under moderate load.

Worked Examples

Example 4.1 — Bufferbloat Delay Inflation

A home router has a 1 MB buffer on a 10 Mbps DOCSIS link. RTT to a server is 30 ms without queuing. When the buffer is full, compute the additional queuing delay and the inflated RTT.

▸ Solution:

Dqueue = 1 MB / 10 Mbps = 8 Mb / 10 Mbps = 0.8 seconds = 800 ms

Inflated RTT = 30 ms (base) + 800 ms (queuing) = 830 ms

The user experiences 830 ms RTT for web browsing—extremely noticeable lag—even though throughput remains 10 Mbps.

Example 4.2 — Buffer Sizing Comparison

A link with C = 100 Mbps, RTT = 100 ms, and N = 500 TCP flows. Compare the traditional vs modern buffer recommendation.

▸ Solution:

Btrad = 0.1 s × 100 Mbps = 10 Mb = 1.25 MB

Bmod = 10 Mb / √(2 × 500) = 10 Mb / √(1000) = 10 / 31.62 Mbps = 316 Kb ≈ 39.5 KB

The traditional rule over-allocates by 31.6×, creating massive bufferbloat potential.

Example 4.3 — DOCSIS 3.1 AQM Benefit

A DOCSIS 3.1 cable modem previously had a 500 KB buffer with drop-tail. After enabling PIE AQM, the average queue occupancy drops from 80% to 10%. Link speed is 50 Mbps. What is the delay reduction?

▸ Solution:

Before AQM: Q = 500 KB × 0.8 = 400 KB = 3.2 Mb. Dqueue = 3.2 / 50 = 64 ms

After AQM: Q = 500 KB × 0.1 = 50 KB = 0.4 Mb. Dqueue = 0.4 / 50 = 8 ms

Delay reduction: 64 − 8 = 56 ms savings (87.5% reduction). Throughput remains unchanged.

Example 4.4 — Bufferbloat: ACK Clocking and Persistent Queues

A home router sends TCP segments to a remote game server. The path has a base RTT of 200 ms and one packet is transmitted from the queue every 20 ms.

▸ ACK clocking explained:

When a burst of packets arrives at the queue, one packet is transmitted every 20 ms. When the first ACK arrives (at t = 200 ms), the TCP sender immediately transmits another packet, which is queued at the tail. This creates a steady-state where the queue always holds exactly five packets. The end-to-end pipe is fully utilized (throughput is maximized), but the queuing delay is constant and persistent. The interactive application (the game) experiences this delay even though throughput is fine.

This is the essence of bufferbloat: good throughput, terrible delay. The buffer absorbs the ACK clock, preventing TCP from naturally draining the queue. With RTT = 200 ms and one packet every 20 ms, the pipeline holds 10 packets; the additional 5 packets in the queue inflate RTT by 100 ms without increasing throughput.

1. High latency — ping RTT > 2× base RTT under load
2. Good throughput, bad responsiveness — downloads fast but web pages lag
3. Latency under load >> latency idle — classic bufferbloat indicator
The Bufferbloat Lesson [Kleinrock 2018]
"Not only is throughput important, but also minimal delay is important."
Kleinrock's reminder that network design must consider both throughput and delay. Bufferbloat demonstrates that optimizing for throughput alone (oversized buffers) can severely degrade delay without any throughput benefit.
