DHCP (Dynamic Host Configuration Protocol)

Computer Networking — Kurose & Ross Ch.4 | Comprehensive Guide

What is DHCP?

DHCP (Dynamic Host Configuration Protocol) is a plug-and-play (zeroconf) protocol that allows a host to obtain an IP address automatically when it connects to a network. The network administrator configures the DHCP server so that each host receives an IP address from the server's address pool without manual configuration.

Core Principle:
Automatic IP Configuration = Plug & Play Networking
Host gets everything it needs to communicate — no manual setup required

Key Concept: Lease

DHCP does not permanently assign IP addresses. Instead it leases them for a finite time (hours or days). When the lease expires, the host must renew or obtain a new address. This allows efficient reuse of the limited IPv4 address space.

DHCP Client-Server Architecture

DHCP follows a client-server model. The client (a host joining the network) initiates communication with the DHCP server. The server manages a pool of addresses and assigns them on request.

Common Mistake: DHCP is NOT a routing protocol

DHCP only handles IP address assignment, not routing. A host that gets a new IP via DHCP must still rely on the default gateway (also provided by DHCP) for off-subnet communication.

Worked Examples

Example 1: Fresh Network Join

A laptop connects to a campus Wi-Fi network. The DHCP server has a pool of 254 addresses (192.168.10.1/24). The server assigns 192.168.10.42 with a 24-hour lease.

Result: Laptop can now reach the internet via gateway 192.168.10.1, resolve names via DNS 8.8.8.8, all without manual configuration.

Example 2: Address Pool Exhaustion

A conference network with a DHCP pool of 100 addresses (192.168.50.100–199) has 100 connected hosts. A 101st host sends a Discover message.

Result: The server has no available addresses to offer. The host receives no Offer and cannot join the network. Solution: reduce lease times or expand the pool.

DHCP does not have a built-in queue — the request is simply ignored if no addresses are free.
Example 3: Lease Renewal Timing

A phone obtained IP 10.0.0.77 with an 8-hour lease at 8:00 AM. According to RFC 2131, the client should attempt renewal at 50% of lease time (T1 = 4 hours), then rebind at 87.5% (T2 = 7 hours).

At 12:00 PM (T1): client sends unicast Request to the original server. If no response by 3:00 PM (T2): client broadcasts to any server. If lease expires at 4:00 PM without renewal: client must stop using the address.

Warning: Subnet Mobility Problem

When a host moves to a new subnet (e.g., from home to a café), DHCP assigns a new IP address. Any ongoing TCP connections using the old IP will break — TCP connections are identified by (source IP, source port, dest IP, dest port). The host must re-establish connections under the new IP. This is a fundamental limitation of DHCP-based mobility.

DHCP Message Format & Options

DHCP messages are carried inside UDP datagrams. The format evolved from BOOTP and shares the same basic structure. Key fields include operation code (1=request, 2=reply), hardware type, transaction ID (xid), client IP address (ciaddr), your IP address (yiaddr), server IP address (siaddr), gateway IP address (giaddr), client hardware address (chaddr), and variable-length options.

giaddr4 bytesRelay agent IP (set by DHCP relay)
chaddr16 bytesClient hardware (MAC) address
optionsvariableSubnet mask, router, DNS, lease time, etc.
Magic Cookie & Options

Every DHCP message contains a 4-byte magic cookie (0x63825363) indicating DHCP options follow. The options field is variable length and uses a Type-Length-Value (TLV) structure. Common options include Subnet Mask (type 1), Router (type 3), DNS (type 6), IP Address Lease Time (type 51), DHCP Message Type (type 53), and Server Identifier (type 54). The option list is terminated by a 255 byte.

Example 4: Decoding DHCP Options

A DHCP Offer message contains: Option 53 = 2 (Offer), Option 1 = 255.255.255.0 (subnet mask), Option 3 = 192.168.1.1 (gateway), Option 51 = 43200 (12-hour lease in seconds), Option 54 = 192.168.1.10 (server ID).

The client now knows the offered IP, network boundaries, where to send off-subnet traffic, how long the lease lasts, and which server to renew with.

The Four-Step DHCP Process (DORA)

The DHCP protocol uses a four-message handshake known by the acronym DORA: Discover, Offer, Request, Acknowledge. The client begins in INIT state (no IP) and transitions to BOUND state (has a valid lease) after successful completion.

INIT (no IP) → DHCP Discover (broadcast) → DHCP Offer (broadcast) → DHCP Request (broadcast) → DHCP ACK (broadcast) → BOUND (has IP)

Algorithm Pseudocode

CLIENT BEHAVIOR (DHCP Client State Machine): State: INIT → Broadcast DHCPDISCOVER to 255.255.255.255:67 → Source IP: 0.0.0.0, Source Port: 68 → Set xid = random transaction ID → Transition to SELECTING state State: SELECTING → Wait for DHCPOFFER messages (timeout = T) → Collect offers from 0 or more servers → Select one offer (usually first received) → Broadcast DHCPREQUEST containing: • Option 54: selected server identifier • Option 50: requested IP address → Transition to REQUESTING state State: REQUESTING → Wait for DHCPACK (or DHCPNAK) → If DHCPACK received: • Configure interface with offered IP • Set lease timer = offered lease time • Set T1 = 0.5 × lease, T2 = 0.875 × lease → Transition to BOUND state → If DHCPNAK received or timeout: → Restart from INIT State: BOUND (normal operation) → At T1 (50% lease): unicast DHCPREQUEST to server → If ACK received: reset lease timer, stay BOUND → At T2 (87.5% lease): broadcast DHCPREQUEST → If ACK received: reset lease timer, stay BOUND → If lease expires: → transition to INIT SERVER BEHAVIOR (simplified): On receiving DHCPDISCOVER: → If pool has available IP: • Select IP from pool • Create binding entry (IP + client MAC) • Broadcast DHCPOFFER with yiaddr = proposed IP • Include options: mask, gateway, DNS, lease, server ID → Else: silently drop On receiving DHCPREQUEST: → If requested IP is still available: • Commit binding (reserve IP permanently for lease) • Broadcast DHCPACK with yiaddr = confirmed IP → Else: • Broadcast DHCPNAK (negative acknowledgment)

Step-by-Step Breakdown

Step 1: DHCP Discover (Client → Server)

The newly connected host has no IP address, so it broadcasts a DHCP Discover message to 255.255.255.255 (limited broadcast) with source IP 0.0.0.0. The message is sent via UDP on port 67 (server). Every device on the subnet receives this broadcast, but only DHCP servers process it.

Key: Source = 0.0.0.0:68 Dest = 255.255.255.255:67 Broadcast

Step 2: DHCP Offer (Server → Client)

One or more DHCP servers respond with an Offer message, also typically broadcast (unless the client set the broadcast flag to 0). The Offer contains a proposed IP address (yiaddr), subnet mask, default gateway, DNS server, lease time, and the server's identifier. The client may receive multiple offers.

yiaddr = Proposed IP Option 54 = Server ID Lease time = Option 51

Step 3: DHCP Request (Client → Server)

The client selects one offer and broadcasts a DHCP Request message. This is broadcast so that all DHCP servers on the subnet know which offer was accepted (unselected servers can return their offered IPs to the pool). The Request echoes the selected server's ID (Option 54) and the requested IP (Option 50).

Option 50 = Requested IP Option 54 = Selected server Still broadcast!

Step 4: DHCP ACK (Server → Client)

The selected server confirms the assignment with a DHCP ACK message. It commits the binding in its database. The client configures its network interface with the assigned IP and sets timers for renewal. The client is now BOUND and can communicate on the network.

Server commits binding Client configures interface BOUND state

Worked Examples

Example 1: Complete DORA Cycle

A new host with MAC address AA:BB:CC:DD:EE:FF connects to an Ethernet network with a single DHCP server (192.168.1.1). The server's pool ranges from 192.168.1.100 to 192.168.1.200.

  1. Discover: Host broadcasts from 0.0.0.0:68 to 255.255.255.255:67 with xid=0x1234, chaddr=AA:BB:CC:DD:EE:FF.
  2. Offer: Server responds with yiaddr=192.168.1.100, mask=255.255.255.0, gateway=192.168.1.1, DNS=8.8.8.8, lease=86400s, server ID=192.168.1.1.
  3. Request: Host broadcasts with Option 50=192.168.1.100, Option 54=192.168.1.1, same xid=0x1234.
  4. ACK: Server confirms with yiaddr=192.168.1.100, same configuration parameters. Host configures interface.

Host 192.168.1.100 is now operational with full network access. Total time: typically under 1 second.

Example 2: Multiple DHCP Servers

A subnet has two DHCP servers: Server A (pool: 10.0.0.10–50) and Server B (pool: 10.0.0.51–100). A client broadcasts a Discover.

  1. Both servers receive the Discover and each sends an Offer: Server A offers 10.0.0.10, Server B offers 10.0.0.51.
  2. The client accepts Server A's offer (first received). It broadcasts a Request with Option 54 = Server A's ID (10.0.0.1).
  3. Server A sends ACK. Server B sees the Request (not selecting it) and returns 10.0.0.51 to its free pool.

The Request is broadcast precisely so that all servers learn which offer was accepted and can reclaim unselected offers.

Example 3: DHCPNAK Scenario

A client attempts to Request IP 10.0.0.5 (its previous address from a different subnet). The DHCP server checks its pool and sees that 10.0.0.5 is not in any configured range.

Server sends DHCPNAK. The client must restart from INIT state (new Discover). This prevents clients from self-assigning invalid IPs and maintains pool integrity.

DHCPNAK can also occur if the requested IP is already leased to another host (detected via conflict detection or binding database lookup).
Common Mistake: Broadcasting in Step 3

Students often ask: "Why does the client broadcast the Request in Step 3 instead of unicasting to the selected server?" The answer: broadcasting ensures that all DHCP servers on the subnet know which offer was accepted. Unselected servers can immediately return the offered IP to the pool. If the Request were unicast, unselected servers would only reclaim the IP after a timeout, wasting addresses temporarily.

+-----------+ | INIT | <-- (lease expires or NAK) +-----------+ | (broadcast Discover) | v +-----------+ | SELECTING | <-- collects Offers +-----------+ | (broadcast Request) | v +-----------+ | REQUESTING| <-- waits for ACK/NAK +-----------+ | | (ACK) | | (NAK/timeout) v v +--------+ +-------+ | BOUND | | INIT | +--------+ +-------+ | (T1 timer: 50% lease) | v +-----------+ | RENEWING | -- unicast Request to server -- +-----------+ | (ACK or T2 timer) | +------+------+ | | (ACK) (T2: 87.5%) | | v v +--------+ +-----------+ | BOUND | | REBINDING | -- broadcast Request -- +--------+ +-----------+ | | (ACK) | | (lease expires) v v +--------+ +-------+ | BOUND | | INIT | +--------+ +-------+

State Summary

INIT: No IP, no lease

SELECTING: Waiting for offers

REQUESTING: Waiting for ACK

BOUND: Valid lease, normal op

RENEWING: Attempting unicast renewal at T1

REBINDING: Attempting broadcast at T2

Important Timers

T2: 87.5% of lease (rebind)

Lease expiry: 100%

Grace period: none

DHCP Relay Agent

In many real-world networks, a single DHCP server serves multiple subnets. Since DHCP Discover messages are broadcast (limited to the subnet), they cannot cross routers by default. The DHCP relay agent (typically built into the router) solves this.

How DHCP Relay Works

The relay agent intercepts broadcast DHCP messages on a subnet and forwards them as unicast to a known DHCP server on another subnet. It sets the giaddr (gateway IP address) field to its own IP on the client's subnet, so the server knows which subnet the client is on and can assign an appropriate IP from the correct pool.

RELAY AGENT BEHAVIOR: On receiving DHCPDISCOVER (broadcast, port 67): → Set giaddr = IP of receiving interface → Forward as unicast to configured DHCP server → Note: do not modify chaddr, xid, or options On receiving DHCPOFFER/ACK (from server): → Remove giaddr (set to 0) → Forward as broadcast or unicast (per flags) to client's subnet → Use ARP or switching table to deliver to client
Example 1: DHCP Relay Across Subnets

Network topology: Subnet A (192.168.1.0/24) and Subnet B (10.0.0.0/24) connected by a router. DHCP server is on Subnet A at 192.168.1.10. A host joins Subnet B.

  1. Host on Subnet B broadcasts Discover on 10.0.0.0/24.
  2. Router (relay agent) receives it on its 10.0.0.1 interface, sets giaddr=10.0.0.1, and unicasts to 192.168.1.10:67.
  3. Server sees giaddr=10.0.0.1, knows client is on 10.0.0.0/24, selects IP from pool for that subnet.
  4. Server replies (Offer/ACK) to relay at 10.0.0.1, which forwards to client on Subnet B.

One DHCP server serves both subnets. Without relay, a separate DHCP server would be needed on each subnet.

Example 2: Corporate Network with 10 Subnets

A company has 10 VLANs (one per department) and wants a single DHCP server in the server room. Each VLAN's router interface is configured as a DHCP relay pointing to 10.0.0.10:67.

The DHCP server maintains 10 separate pools. The giaddr field differentiates which pool to draw from. Total management: one server instead of ten. No hardware redundancy is lost — a second server can be added for failover.

Common Mistake: Relay vs. Proxy

DHCP relay is often confused with DHCP proxy. A relay simply forwards messages without modification (except setting giaddr). A proxy terminates the DHCP conversation and creates a new one on the client's behalf. Relays are transparent; proxies act as intermediaries. Most routers implement relays, not proxies.

Lease Renewal & Release

DHCP leases are designed for efficient address reuse. A host does not keep an IP forever — it must periodically renew. The renewal process uses two timers (T1 and T2) computed from the lease duration.

Lease Timers (RFC 2131):
T1 = 0.5 × Lease_Time  |  T2 = 0.875 × Lease_Time
T1: Attempt unicast renewal. T2: If no response, attempt broadcast rebinding.
LEASE RENEWAL ALGORITHM: State: BOUND → Wait for T1 timer to fire State: RENEWING → Unicast DHCPREQUEST to original server (ciaddr = current IP) → Include Option 53 = 3 (Request) → If DHCPACK received before T2: • Reset lease timer = lease time from ACK • Reset T1, T2 timers → Return to BOUND → If DHCPNAK received: → Transition to INIT (must get new IP) State: REBINDING (T2 fired, no ACK yet) → Broadcast DHCPREQUEST (ciaddr = current IP) → Any server on subnet can respond → If DHCPACK received: • Reset all timers → Return to BOUND → If DHCPNAK received: → Transition to INIT → If lease expires: → Transition to INIT (must stop using IP) GRACEFUL RELEASE (client-initiated): → Send DHCPRELEASE to server → Include Option 53 = 7 (Release) → Server marks IP as free → Client transitions to INIT
Example 3: Lease Renewal with Server Restart

A host has a 24-hour lease on IP 172.16.0.50. At T1 (12 hours), the host attempts unicast renewal but the DHCP server is temporarily down for maintenance.

  1. T1 (12h): Unicast Request → no response. Host continues using the IP.
  2. T2 (21h): Broadcast Request → server is back up. Server responds with ACK, same IP, refreshed 24-hour lease.
  3. Host resets timers, stays BOUND. No interruption to network service.

The two-tier renewal (unicast then broadcast) provides resilience against short server outages. The host has 87.5% of the lease time to handle failures before needing to find a new IP.

Common Mistake: DHCPRELEASE is NOT required

A client can simply stop using its IP (e.g., shutting down) without sending a DHCPRELEASE. The server will reclaim the address when the lease expires. However, sending a release is good practice for mobile devices that may not be back before the lease expires — it allows immediate reuse of the address.

ISC DHCP & Practical Deployment

The Internet Systems Consortium (ISC) provides the most widely used open-source DHCP implementation. ISC DHCP runs on most Unix-like systems and supports both server and relay functionality.

DHCP Security Considerations

• Rogue DHCP server: An attacker on the subnet can offer malicious IP configs (e.g., a fake gateway for MITM).

• DHCP snooping: Switch feature that filters untrusted DHCP messages, allowing only authorized servers.

• Starvation attack: Attacker floods Discover messages with fake MACs to exhaust the address pool (DoS).

• Mitigation: Use DHCP snooping, port security, and rate limiting on access ports.

Example 4: Static Reservation vs. Dynamic Pool

A network administrator configures a DHCP server with a dynamic pool (192.168.1.100–200) and a static reservation for the file server (MAC: AA:BB:CC:DD:EE:FF → IP: 192.168.1.5).

The file server always gets 192.168.1.5 (useful for DNS A records, firewall rules). Other hosts get dynamic addresses from the pool. If the file server uses a different MAC (e.g., NIC replacement), it will get a different IP unless the reservation is updated — a common operational pitfall.

Example 5: DHCP Over Wi-Fi (802.11)

A smartphone connects to a café Wi-Fi. The access point bridges the wireless client to the wired subnet. The DHCP exchange occurs exactly as in Ethernet, but the initial association (802.11 authentication/association) happens first.

The smartphone receives IP 10.0.0.42 with a 1-hour lease. After 30 minutes, the user moves to a different café. The old lease eventually expires, and the phone gets a new IP at the new location. Any VoIP call or streaming session using the old IP will break — this is why mobility protocols like MIPv6 or seamless handoff are needed on top.

Important: DHCPv6 is NOT identical to DHCPv4

In IPv6, hosts can configure their IP address via SLAAC (Stateless Address Autoconfiguration) without any DHCP server. DHCPv6 is optional and typically used to provide DNS server addresses and other configuration parameters that are not available from Router Advertisements. The four-message DORA process becomes a four-message process in DHCPv6: Solicit → Advertise → Request → Reply.
