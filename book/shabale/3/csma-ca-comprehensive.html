CSMA/CA

Carrier Sense Multiple Access with Collision Avoidance — Complete Guide for 20/20 Exam

CSMA/CA Protocol Overview

CSMA/CA is a channel access method used in wireless local area networks (Wi-Fi, IEEE 802.11). Unlike wired Ethernet which uses CSMA/CD (Collision Detection), wireless networks cannot detect collisions while transmitting because a station cannot listen to its own signal. CSMA/CA therefore focuses on collision avoidance rather than detection.

Core Principle:
Sense → Wait (if busy) → Attempt to Avoid → Transmit → Wait for ACK
Stations listen before transmitting and use multiple mechanisms to minimize collision probability

Why CSMA/CD Cannot Work in Wireless?

Problem 1

Signal Strength Mismatch

A station's own transmission overwhelms any incoming signal, making it impossible to detect a simultaneous collision at the receiver.

Problem 2

Hidden Terminal Problem

Two stations can both communicate with the same access point but not with each other — they are hidden from one another.

Problem 3

Exposed Terminal Problem

A station may hear a transmission from a nearby node and wrongly conclude it cannot transmit, even though its intended receiver is far away.

Problem 4

Fading and Attenuation

Wireless signals degrade over distance. A collision signal may be too weak for the sender to detect even though the receiver is affected.

CSMA/CA Key Techniques

Technique 1

RTS/CTS Handshake

Request to Send / Clear to Send exchange reserves the channel before data transmission, reducing the chance of collision.

Technique 2

NAV (Network Allocation Vector)

A virtual carrier sense mechanism. Stations that hear RTS or CTS set a timer (NAV) and defer transmission for the indicated duration.

Technique 3

IFS (Inter-Frame Spacing)

Different waiting times between frames create priority levels. Control frames (ACK, CTS) get shorter waits and thus higher priority.

Technique 4

Random Backoff

After sensing an idle channel, stations wait a random backoff time before transmitting, reducing simultaneous access attempts.

Exam Tip: CSMA/CA is used in IEEE 802.11 (Wi-Fi). CSMA/CD is used in IEEE 802.3 (Ethernet). Never mix them up!

RTS/CTS Mechanism — Step by Step

Before transmitting a data frame, the sender initiates a short handshake. This reserves the channel and notifies nearby stations of the impending transmission.

Complete Handshake Sequence:
Sender → RTS → Receiver → CTS → Sender → DATA → Receiver → ACK
RTS and CTS frames are very short. A collision during this phase wastes far less bandwidth than a collision during data transmission.
1
Carrier Sense: Sender listens to the channel. If idle, it waits for DIFS duration to confirm the channel remains idle.
2
RTS Frame Sent: Sender transmits a Request to Send frame containing source address, destination address, and the duration of the planned transmission (used for NAV calculation).
3
CTS Frame Received: Receiver responds with a Clear to Send frame after waiting SIFS. CTS contains the destination address and the same duration field. This confirms the channel is clear from the receiver's perspective.
4
NAV Updated: All stations within range of either the sender (who heard RTS) or the receiver (who heard CTS) set their NAV timer. They will not attempt to transmit until NAV expires.
5
Data Transmission: Sender waits SIFS after receiving CTS, then transmits the data frame.
6
ACK Received: Receiver waits SIFS, then sends an ACK to confirm successful reception. All stations reset their NAV to idle.
Why RTS/CTS is Effective

If a collision occurs during RTS/CTS, only a very small frame is lost (a few hundred bytes). Without RTS/CTS, a collision during data transmission could waste thousands of bytes. The overhead of RTS/CTS is justified when data frames are large or the network is congested.

  • • Source MAC address
  • • Destination MAC address
  • • Duration / NAV value

CTS Frame Contains

  • • Destination MAC address
  • • Duration / NAV value
  • • Confirmation of clear channel

NAV (Network Allocation Vector)

NAV Duration Calculation:
NAV = SIFS + CTS_duration + SIFS + DATA_duration + SIFS + ACK_duration
The NAV value embedded in RTS or CTS frames tells other stations how long the channel will be occupied

The NAV is a virtual carrier sense mechanism. Each station maintains a NAV timer. When a station hears an RTS or CTS frame (even if it is not the intended recipient), it extracts the duration field and sets its own NAV timer. While NAV > 0, the station treats the channel as busy and does not attempt to transmit.

How NAV Works:

1
Station hears RTS or CTS frame on the channel
2
Extracts the duration field (NAV value) from the frame header
3
Sets its NAV timer to this duration value
4
NAV timer counts down. Station defers all transmission while NAV > 0
5
When NAV reaches 0, station can compete for channel access normally
Key Point: NAV provides virtual carrier sensing. Physical carrier sensing (listening to signal energy) combined with virtual carrier sensing (NAV) gives the complete picture of channel status.

IFS (Inter-Frame Spacing)

IFS Priority Hierarchy:
SIFS < PIFS < DIFS
Shorter IFS = Higher priority. After the channel becomes idle, only stations waiting for the shortest IFS can transmit first.
IFS Type Full Name Duration (typical) Used For Priority
SIFS Short IFS ~10 μs ACK frames, CTS frames, polling responses Highest
PIFS PCF IFS ~30 μs AP in Point Coordination Function (PCF) mode Medium
DIFS DCF IFS ~50 μs Regular data frames in DCF (distributed coordination function) Lowest
Why IFS Matters — Priority Example

When the channel becomes idle after a transmission:

• ACK sender waits only SIFS (10 μs) → transmits ACK immediately

• Regular data sender must wait DIFS (50 μs) → still waiting when ACK is sent

• Result: ACK always gets priority over new data, ensuring reliable delivery

IFS and Backoff Interaction

After DIFS wait, a station also waits a random backoff time. This prevents multiple stations from transmitting simultaneously the moment the channel becomes idle.

Backoff slot time: typically 20 μs (varies by standard)

Backoff value = random integer × slot time

Worked Examples

Example 1: NAV Calculation

Given: SIFS = 10 μs, CTS = 20 μs, DATA = 100 μs, ACK = 20 μs

RTS frame contains NAV = ?

NAV = SIFS + CTS + SIFS + DATA + SIFS + ACK
NAV = 10 + 20 + 10 + 100 + 10 + 20 = 170 μs

All stations within range of sender or receiver must wait 170 μs before attempting transmission.

Example 2: Collision Avoidance with Hidden Terminal
Station A Station B (AP) Station C | | | |--- RTS --------->| | | |--- CTS ------->| (C hears CTS, sets NAV) |<-- CTS ----------| | | | | |--- DATA -------->| | | | | (C's NAV active, C stays silent) |<-- ACK ----------| | | | | | (NAV expires) | | | C can now attempt to transmit

Result: Without NAV, Station C would have transmitted during A's data frame, causing a collision at B. RTS/CTS + NAV prevents this.

Example 3: IFS Priority in Action

Situation: Station has both an ACK and a data frame ready to send when channel becomes idle.

Timing:

• Channel becomes idle at t = 0

• ACK waits SIFS (10 μs), sends at t = 10 μs

• Data waits DIFS (50 μs), would send at t = 50 μs

• Data cannot send because ACK is already using the channel at t = 10 μs

Result: ACK transmitted first. Control frames always have priority.

Example 4: RTS/CTS Overhead Analysis

Given: Data frame transmission time = 1000 μs, RTS = 20 μs, CTS = 20 μs

Without RTS/CTS:

• Collision wastes 1000 μs (entire data frame)

With RTS/CTS:

• RTS/CTS overhead = 20 + 20 = 40 μs

• Collision wastes only 20 μs (RTS frame only)

• Bandwidth saved per collision: 980 μs (98%)

RTS/CTS is especially beneficial when data frames are large and collisions are frequent.

Example 5: Full Transmission Sequence

Given: DIFS = 50 μs, Backoff = 3 slots × 20 μs = 60 μs, RTS = 20 μs, SIFS = 10 μs, CTS = 20 μs, DATA = 100 μs, ACK = 20 μs

Total time from idle to complete:

Total = DIFS + Backoff + RTS + SIFS + CTS + SIFS + DATA + SIFS + ACK
Total = 50 + 60 + 20 + 10 + 20 + 10 + 100 + 10 + 20 = 300 μs

Effective throughput = Data bits / Total time. Higher overhead reduces effective throughput.

CSMA/CD vs CSMA/CA — Detailed Comparison

Feature CSMA/CD (Collision Detection) CSMA/CA (Collision Avoidance)
Network Type Wired Ethernet (IEEE 802.3) Wireless Wi-Fi (IEEE 802.11)
Collision Strategy Detect and recover Avoid and prevent
Collision Detection Yes — compare TX vs RX signal No — cannot detect while transmitting
RTS/CTS Not used Used (optional, but recommended)
NAV Not used Virtual carrier sense
ACK Required No (handled by upper layers) Yes — every unicast frame
IFS (Inter-Frame Spacing) Not used Used for priority (SIFS/PIFS/DIFS)
Minimum Frame Size 64 bytes (for detection time) None (avoids collision, not detects)
After Collision Send jam signal, then backoff Re-attempt after random backoff
Backoff Binary exponential backoff Random backoff with slot time
Hidden Terminal Not an issue (wired) Handled by RTS/CTS
Efficiency High when collisions are rare Lower due to RTS/CTS overhead
Exam Tips:
1. CSMA/CD = wired (Ethernet), CSMA/CA = wireless (Wi-Fi) — this is the #1 distinction
2. CD detects collisions by comparing TX vs RX energy; CA avoids them via handshake
3. RTS/CTS is the signature mechanism of CSMA/CA
4. NAV is virtual carrier sense — physical carrier sense is listening to signal energy
5. IFS creates priority: shorter wait = higher priority (SIFS > PIFS > DIFS)
6. ACK is mandatory in 802.11 for unicast frames
7. Minimum frame size in CSMA/CD ensures detection time; not needed in CSMA/CA
8. Binary exponential backoff is used in CSMA/CD; random backoff in CSMA/CA

Hidden Terminal & Exposed Terminal Problems

Hidden Terminal Problem

The Problem

Station A and Station C are both within range of Station B (access point), but A and C are out of range of each other. Neither can hear the other's transmission. If both transmit to B simultaneously, their signals collide at B, but neither A nor C can detect the collision.

Station A Station B (AP) Station C | | | | (A cannot hear C)| | | | (C cannot hear A)| | | | |--- DATA -------->|<--- DATA -------| | | COLLISION! | | (A doesn't know)| (C doesn't know)| | | |

RTS/CTS Solution

1. Station A sends RTS to B

2. B responds with CTS — Station C hears this CTS (even though it can't hear A)

3. C sets its NAV timer and does not transmit

4. A safely transmits data to B without collision

Exposed Terminal Problem

The Problem

Station B is transmitting to Station A. Station C is within range of B and hears B's transmission. C wants to transmit to Station D (which is out of range of B). Because C hears B's signal, C assumes the channel is busy and defers — even though C's transmission to D would not interfere with B's reception at A.

Station B Station A Station C Station D | | | | |--- DATA -------->| | | | | (C hears B) | | | | C defers... | | | | (but C→D wouldn't interfere!) |

Why RTS/CTS Helps (partially)

When C hears an RTS from B intended for A, C can determine that its own transmission to D would not interfere with B's reception at A (since D is out of range of B). However, standard CSMA/CA is conservative — C will still defer. This is the exposed terminal problem, and it reduces spatial reuse but does not cause collisions.

Key Takeaway for Exams

Hidden Terminal: Causes collisions. Solved by RTS/CTS + NAV.

Exposed Terminal: Reduces throughput (unnecessary deferral). Partially addressed but not fully solved by CSMA/CA.
