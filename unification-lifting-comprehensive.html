UNIFICATION & LIFTING

Chapter 8: First-Order Logic Inference — Comprehensive Guide

What is Unification?

Unification is the process of finding a substitution that makes two logical expressions identical. In First-Order Logic (FOL), unification is the fundamental operation that enables automated inference by matching patterns with variables against concrete facts or other patterns.

Core Idea
UNIFY(θ₁, θ₂) = θ such that SUBST(θ, θ₁) = SUBST(θ, θ₂)
Find substitution θ that makes both expressions equal when applied

Why Unification Matters

Propositional logic inference (Modus Ponens) works only when propositions match exactly. FOL introduces variables, so we need a way to match terms with variables. Unification solves this by computing the most general substitution that aligns two expressions.

Propositional MP

Requires exact match

From P and P→Q, derive Q

No variables involved

Generalized MP

Uses unification

From P(x) and P(A)→Q, derive Q with x=A

Variables are substituted

Key Terminology

Constant

A specific object: John, A, 5

No variables, no arguments

Variable

A placeholder: x, y, z

Can be bound to any term

Function

Takes args, returns term: Father(x), Mother(y)

Output is a term

Predicate

Returns truth value: Knows(x,y), Loves(x,y)

Output is T/F

Variables vs Constants

Variables appear in rule antecedents and can be substituted. Constants are fixed values. Mixing them up causes unification to fail or produce wrong results.

Substitution

A substitution θ is a set of variable-to-term bindings: {x/t₁, y/t₂, ...}. Applying θ replaces each variable with its bound term.

SUBST Operation
SUBST({x/John, y/z}, Knows(x,y)) = Knows(John, z)
Replace x with John, y with z in the expression
Substitution Examples

SUBST({x/A}, P(x)) = P(A)

SUBST({x/f(y)}, P(x)) = P(f(y))

SUBST({x/A, y/B}, P(x,y)) = P(A,B)

SUBST({x/y}, P(x,x)) = P(y,y)

Generalized Modus Ponens (GMP)

GMP extends propositional Modus Ponens to handle variables and function symbols. It combines unification with logical deduction.

GMP Rule
From: P₁, P₂, ..., Pₙ and (P₁' ∧ P₂' ∧ ... ∧ Pₙ' → Q')
If UNIFY({P₁,...,Pₙ}, {P₁',...,Pₙ'}) = θ
Then: SUBST(θ, Q')
If we know the premises and a rule whose antecedents unify with them, derive the consequent under the substitution

How GMP Lifts Propositional MP

Propositional MP: From P and P→Q, derive Q.
GMP: From P(x) and P(A)→Q(x), derive Q(A). The unifier θ={x/A} bridges the gap between the variable form and the constant form.

Example 1: Simple GMP

Knowledge base:

• Knows(John, x) → Happy(x) — "John makes everyone happy"

• Knows(John, Jane)

Unification: UNIFY(Knows(John, x), Knows(John, Jane)) = {x/Jane}

Result: SUBST({x/Jane}, Happy(x)) = Happy(Jane)

Example 2: Multiple Premises

Knowledge base:

• Rich(x) ∧ Happy(x) → Satisfied(x)

• Rich(Alice)

• Happy(Alice)

Unification: θ = {x/Alice}

Result: SUBST(θ, Satisfied(x)) = Satisfied(Alice)

Example 3: Function Symbols

Knowledge base:

• Likes(x, Food(x)) → Happy(x)

• Likes(John, Pizza)

• Food(Pizza)

Unification: UNIFY(Likes(x, Food(x)), Likes(John, Pizza))

Need x=John and Food(John)=Pizza. But Food(John) ≠ Pizza. This fails unless we have Food(John)=Pizza as fact.

Example 4: Transitive Relations

Knowledge base:

• Ancestor(x, y) ∧ Ancestor(y, z) → Ancestor(x, z)

• Ancestor(Mary, Tom)

• Ancestor(Tom, Sue)

Step 1: Unify first two atoms: θ₁ = {x/Mary, y/Tom}

Step 2: Apply to rule body: Ancestor(Mary, Tom) ∧ Ancestor(Tom, z) → Ancestor(Mary, z)

Step 3: Unify Ancestor(Tom, z) with Ancestor(Tom, Sue): θ₂ = {z/Sue}

Result: Ancestor(Mary, Sue)

GMP Completeness

GMP is sound (never derives false conclusions) but not complete for all FOL inference. It only fires when all antecedents of a rule match. Some valid conclusions require chaining or resolution, which go beyond GMP.

GMP Formal Statement

Generalized Modus Ponens
p₁, p₂, ..., pₙ, (p₁' ∧ p₂' ∧ ... ∧ pₙ' → q')
where UNIFY({p₁,...,pₙ}, {p₁',...,pₙ'}) = θ
Therefore: SUBST(θ, q')
All pᵢ must unify with their corresponding pᵢ' under the same substitution θ
Example 5: Two-Rule Chain

Knowledge base:

• Smart(x) ∧ Rich(x) → Happy(x)

• Happy(x) → Succeed(x)

• Smart(Bob)

• Rich(Bob)

Step 1: GMP with rule 1: θ₁ = {x/Bob}, derive Happy(Bob)

Step 2: GMP with rule 2: θ₂ = {x/Bob}, derive Succeed(Bob)

Result: Succeed(Bob)

UNIFY Algorithm — Complete Pseudocode

The UNIFY algorithm takes two expressions and returns the Most General Unifier (MGU) or failure. It works recursively on the structure of terms.

function UNIFY(x, y, θ) returns substitution or FAILURE θ = COPY(θ) if θ = FAILURE then return FAILURE else if x = y then return θ else if VARIABLE?(x) then return UNIFY-VAR(x, y, θ) else if VARIABLE?(y) then return UNIFY-VAR(y, x, θ) else if COMPOUND?(x) and COMPOUND?(y) then if SYMBOL(x) ≠ SYMBOL(y) or LENGTH(x) ≠ LENGTH(y) then return FAILURE for i = 1 to LENGTH(x) do θ = UNIFY(ATOM(i, x), ATOM(i, y), θ) return θ else if LIST?(x) and LIST?(y) then return UNIFY(HEAD(x), HEAD(y), UNIFY(TAIL(x), TAIL(y), θ)) else return FAILURE function UNIFY-VAR(var, x, θ) returns substitution or FAILURE if var/val ∈ θ then return UNIFY(val, x, θ) else if x/val ∈ θ then return UNIFY(var, val, θ) else if OCCUR-CHECK?(var, x) then return FAILURE else return ADD(var/x, θ) function OCCUR-CHECK?(var, x) returns true/false if var = x then return true else if COMPOUND?(x) then for each arg in ARGS(x) do if OCCUR-CHECK?(var, arg) then return true return false
Occur-Check is Critical!

Without the occur-check, UNIFY(x, f(x)) would produce x/f(x), which creates an infinite circular substitution. The occur-check prevents this by detecting when a variable appears inside the term it's being unified with.

Step-by-Step Traces

Trace 1: UNIFY(Knows(John, x), Knows(John, Jane))
1. Both are compound with same functor "Knows" and arity 2
2. Unify first args: UNIFY(John, John, {}) = {} (same constant)
3. Unify second args: UNIFY(x, Jane, {}) — x is variable
4. UNIFY-VAR: no existing binding, occur-check: x not in Jane → OK
5. Add x/Jane → θ = {x/Jane}
Trace 2: UNIFY(Knows(John, x), Knows(y, Bill))
1. Both compound "Knows", arity 2
2. Unify first args: UNIFY(John, y, {}) — y is variable
3. UNIFY-VAR: no binding, occur-check OK → θ = {y/John}
4. Unify second args: UNIFY(x, Bill, {y/John}) — x is variable
5. UNIFY-VAR: no binding for x, occur-check OK → θ = {y/John, x/Bill}
Trace 3: UNIFY(Knows(John, x), Knows(x, Elizabeth))
1. Both compound "Knows", arity 2
2. Unify first args: UNIFY(John, x, {}) — x is variable
3. UNIFY-VAR: no binding, occur-check OK → θ = {x/John}
4. Unify second args: UNIFY(x, Elizabeth, {x/John})
5. x already bound to John: UNIFY(John, Elizabeth, {x/John})
6. John ≠ Elizabeth → FAILURE

Note: After first binding, the second occurrence of x is already resolved to John, which cannot unify with Elizabeth.

Trace 4: UNIFY(Knows(x, x), Knows(Jane, Jane))
1. Both compound "Knows", arity 2
2. Unify first args: UNIFY(x, Jane, {}) — x is variable
3. UNIFY-VAR: no binding, occur-check OK → θ = {x/Jane}
4. Unify second args: UNIFY(x, Jane, {x/Jane})
5. x bound to John: UNIFY(Jane, Jane, {x/Jane})
6. Same constants → θ = {x/Jane}
Trace 5: UNIFY(Knows(x, x), Knows(Jane, Bill))
1. Both compound "Knows", arity 2
2. Unify first args: UNIFY(x, Jane, {}) → θ = {x/Jane}
3. Unify second args: UNIFY(x, Bill, {x/Jane})
4. x bound to Jane: UNIFY(Jane, Bill, {x/Jane})
5. Jane ≠ Bill → FAILURE

x cannot be both Jane and Bill simultaneously.

More Unification Examples

Example 6: Function Symbols — UNIFY(P(x, f(y)), P(A, f(B)))
1. Both compound "P", arity 2
2. First args: UNIFY(x, A, {}) → θ = {x/A}
3. Second args: UNIFY(f(y), f(B), {x/A})
4. Both compound "f", arity 1. Unify args: UNIFY(y, B, {x/A}) → θ = {x/A, y/B}
Example 7: Nested Functions — UNIFY(f(g(x)), f(g(A)))
1. Both compound "f", arity 1
2. Unify args: UNIFY(g(x), g(A), {})
3. Both compound "g", arity 1. Unify: UNIFY(x, A, {}) → {x/A}
Example 8: Occur-Check — UNIFY(x, f(x))
1. x is variable, check if x appears in f(x)
2. f(x) is compound with arg x. Does x = x? Yes!
3. OCCUR-CHECK returns true → FAILURE

This prevents the infinite substitution x/f(f(f(...))).

Example 9: Partial Overlap — UNIFY(f(x, g(y)), f(g(z), w))
1. Both compound "f", arity 2
2. First args: UNIFY(x, g(z), {}) → θ = {x/g(z)}
3. Second args: UNIFY(g(y), w, {x/g(z)})
4. w is variable: UNIFY-VAR(w, g(y), {x/g(z)})
5. No binding for w, occur-check: w not in g(y) → OK
6. θ = {x/g(z), w/g(y)}
Example 10: Different Arities — UNIFY(P(x), P(A, B))
1. Both compound "P" but different arity: 1 vs 2
2. LENGTH(x) ≠ LENGTH(y) → FAILURE
Example 11: Different Functors — UNIFY(P(x), Q(x))
1. Compound terms with different symbols: P ≠ Q
2. SYMBOL(x) ≠ SYMBOL(y) → FAILURE
Example 12: Chain of Bindings — UNIFY(P(x, y), P(A, z)) ∧ UNIFY(P(z, w), P(B, C))
1. First unification: θ₁ = {x/A, y/z} or equivalently {x/A} (z remains variable)
2. Second unification with θ₁: UNIFY(P(z, w), P(B, C), {x/A})
3. z is variable: z/B, w is variable: w/C
4. Combined θ = {x/A, z/B, w/C}
Example 13: Complex Occur-Check — UNIFY(x, f(x, A))
1. x is variable, term is f(x, A)
2. Check args of f: does x = x? Yes!
3. OCCUR-CHECK returns true → FAILURE

Most General Unifier (MGU)

The Most General Unifier is the substitution that is at least as general as any other unifier. If θ is an MGU for expressions e₁ and e₂, then for any other unifier θ', there exists a substitution γ such that SUBST(γ, SUBST(θ, e)) = SUBST(θ', e).

MGU Definition
θ is an MGU of e₁, e₂ iff:
1. SUBST(θ, e₁) = SUBST(θ, e₂)  (θ is a unifier)
2. For any unifier θ', ∃ γ such that θ' = γ ∘ θ  (θ is most general)
The MGU makes no "unnecessary" bindings — it only binds what's required for unification

Why MGU is Preferred

Using the MGU instead of any arbitrary unifier preserves the most flexibility for future inference steps. An over-specific unifier might prevent valid inferences that require different bindings.

Comparing Unifiers

Expressions: Knows(John, x), Knows(y, z)

All unifiers:

• θ₁ = {x/A, y/John, z/A} — valid but over-specific

• θ₂ = {x/z, y/John} — valid and general

• θ₃ = {x/B, y/John, z/B} — another specific unifier

MGU: θ₂ = {x/z, y/John} — most general, leaves z free

Note: θ₁ and θ₃ are both instances of θ₂ with γ={z/A} and γ={z/B} respectively.

MGU Uniqueness

Expressions: P(x, A), P(B, y)

Unifiers: {x/B, y/A}, {x/B, y/A, z/C}, {x/B, y/A, w/D}, ...

MGU: {x/B, y/A} — minimal set of bindings

The MGU is unique up to renaming of variables. All other unifiers are more specific instances of it.

Comparing Unifiers
θ₁ ≤ θ₂ iff ∃ γ such that θ₂ = γ ∘ θ₁
θ₁ is at least as general as θ₂ if we can specialize θ₁ into θ₂ by applying additional substitutions

Properties of MGU

• Exists when expressions are unifiable

• Unique up to variable renaming

• Minimal set of bindings

• Preserves flexibility for future

Computing MGU

• UNIFY algorithm always returns MGU

• Does not add redundant bindings

• Occur-check ensures well-founded

• Recursive structure handles nesting

Standardizing Apart

When applying inference rules, the same variable might appear in different rules. Standardizing apart renames variables in each rule to avoid collisions. This ensures each rule's variables are independent.

Standardizing Apart
For each rule application, rename all variables to fresh names not used elsewhere.
Two instances of the same rule must not share variable names
Variable Collision Danger

Without standardizing apart, applying the same rule twice can cause variables to incorrectly share values, leading to wrong conclusions.

Example: Variable Collision

Rule: Owns(x, y) → Buys(x, y) — "If x owns y, x buys y"

Facts: Owns(Alice, Book1), Owns(Bob, Book2)

Without standardizing apart:

• Apply rule to fact 1: θ = {x/Alice, y/Book1} → Buys(Alice, Book1)

• Apply rule to fact 2: x and y are already bound! Cannot unify properly.

With standardizing apart:

• Instance 1: Owns(x₁, y₁) → Buys(x₁, y₁)

• Instance 2: Owns(x₂, y₂) → Buys(x₂, y₂)

• Now each has independent variables, no collision.

Example: Chained Rules

Rule 1: P(x) → Q(x)

Rule 2: Q(x) → R(x)

Fact: P(A)

Standardized:

• Rule 1 becomes: P(x₁) → Q(x₁)

• Rule 2 becomes: Q(x₂) → R(x₂)

Step 1: Apply rule 1: θ₁ = {x₁/A}, derive Q(A)

Step 2: Apply rule 2: θ₂ = {x₂/A}, derive R(A)

Without standardizing, both rules share x, so x₁=A would affect rule 2 prematurely.

Example: Multiple Rule Uses

Rule: Likes(x, y) → Happy(x)

Facts: Likes(Alice, Cats), Likes(Alice, Dogs), Likes(Bob, Birds)

Three separate instances needed:

• Instance 1: Likes(x₁, y₁) → Happy(x₁)

• Instance 2: Likes(x₂, y₂) → Happy(x₂)

• Instance 3: Likes(x₃, y₃) → Happy(x₃)

Each gets its own fresh variables, allowing independent unification.

When to Standardize

• Every rule use

• Chained inference

• Same rule, multiple facts

Naming Convention

• Use subscripts: x₁, x₂, x₃

• Or use different names: x, y, z

• Fresh names must be globally unique

STORE and FETCH Operations

STORE and FETCH are the core operations for an inference engine's knowledge base. STORE adds sentences to the KB with indexing, while FETCH retrieves sentences that match a query via unification.

STORE(s)
STORE(s): Index sentence s by its predicate symbol and arguments
Stores the sentence in a hash table keyed by predicate name for O(1) lookup
FETCH(q)
FETCH(q): Return all sentences s in KB such that UNIFY(q, s) ≠ FAILURE
Retrieves all sentences unifiable with query q

Predicate Indexing

Sentences are indexed by predicate symbol. When FETCH receives a query with predicate P, only sentences with predicate P are considered. This reduces the search space dramatically.

Indexing Example

KB contains:

• Knows(John, Jane)

• Knows(Bob, x)

• Likes(Alice, Pizza)

• Happy(Tom)

Index structure:

• Knows → [Knows(John, Jane), Knows(Bob, x)]

• Likes → [Likes(Alice, Pizza)]

• Happy → [Happy(Tom)]

FETCH(Knows(John, y)): Only check Knows index → finds Knows(John, Jane) with θ={y/Jane}

Subsumption and Redundancy

A sentence φ subsumes ψ if there exists a substitution θ such that SUBST(θ, φ) ⊆ ψ. Subsumed sentences can be pruned from the KB to save space and avoid redundant inference.

Subsumption Test
φ subsumes ψ iff ∃ θ: SUBST(θ, φ) ⊆ ψ
φ is more general than ψ — all instances of φ are covered by ψ
Subsumption Example

KB contains:

• Knows(John, x) — "John knows everyone"

• Knows(John, Jane) — "John knows Jane"

Subsumption: Knows(John, x) subsumes Knows(John, Jane) with θ={x/Jane}

Action: Knows(John, Jane) is redundant — can be removed from KB.

Hash Table Optimization

The KB uses a hash table where:

Key

Predicate symbol: Knows, Likes, Happy

O(1) lookup to find all sentences with that predicate

Value

List of sentences: [s₁, s₂, s₃, ...]

All sentences sharing the same predicate

FETCH with Unification

KB Index:

• Knows → [Knows(John, Jane), Knows(Bob, x), Knows(y, z)]

Query: FETCH(Knows(Alice, w))

Step 1: Look up "Knows" in hash table

Step 2: Try unification with each:

• UNIFY(Knows(Alice, w), Knows(John, Jane)) → FAIL (Alice ≠ John)

• UNIFY(Knows(Alice, w), Knows(Bob, x)) → FAIL (Alice ≠ Bob)

• UNIFY(Knows(Alice, w), Knows(y, z)) → {y/Alice, w/z} → SUCCESS

Result: Returns [Knows(y, z)] with θ={y/Alice, w/z}

Subsumption Lattice

Sentences form a lattice ordered by subsumption:

• Most general: P(x) — "P is true for everything"

• More specific: P(A) — "P is true for A"

• Most specific: P(A) ∧ P(B) — "P is true for A and B"

Higher nodes subsume lower nodes. Pruning lower nodes (instances) preserves completeness because they can be regenerated from the general form.

Side-by-Side: Pattern Matching vs Unification

Pattern matching: match(P(x, A), P(B, A)) → {x/B}

• x is variable, A and B are constants in pattern

• Data P(B, A) has no variables

• One-directional: pattern variables map to data

Unification: unify(P(x, A), P(B, y)) → {x/B, y/A}

• Both x and y are variables (from different expressions)

• Both expressions can have variables

• Bidirectional: variables from both sides are bound
