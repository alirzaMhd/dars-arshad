Three-Way Handshake

Before two application processes can exchange data, they must handshake to establish parameters. The client initiates, the server responds, and the client acknowledges — three segments total.

Handshake Step 1: SYN
SYN=1, seq=client_isn
Client chooses random initial sequence number (client_isn), sets SYN bit, sends to server. No application data.
Handshake Step 2: SYNACK
SYN=1, seq=server_isn, ack=client_isn+1
Server allocates buffers, chooses its own initial sequence number (server_isn), acknowledges client's SYN.
Handshake Step 3: ACK
SYN=0, seq=client_isn+1, ack=server_isn+1
Client acknowledges server's SYNACK. SYN bit set to 0. This segment may carry application data. The client also allocates buffers and variables to the connection in this step.
Rock Climber and Belayer Analogy

A rock climber and belayer use a three-way handshake identical to TCP's to ensure both sides are ready before the climber begins ascent. The climber signals readiness (SYN), the belayer confirms and signals own readiness (SYNACK), and the climber acknowledges (ACK) before starting to climb (data transfer).

Key Properties

• Full-duplex: both sides can send simultaneously

• Point-to-point: exactly two hosts

• State initialized: buffers, seq numbers, window sizes

• MSS negotiated during handshake

Why Three-Way?

• Prevents stale SYN from old connection

• Ensures both sides agree on initial seq numbers

• Two-way handshake is vulnerable to duplicate SYNs

• Three-way provides synchronization with bounded state

Common Mistake: The SYN bit is set to 1 only during the first two steps. After the connection is established (Step 3 onward), the SYN bit is always 0. Do not confuse SYN with data-carrying segments.
Protocol Detail: The initial sequence numbers (client_isn, server_isn) are chosen randomly to prevent security attacks. A predictable ISN allows attackers to forge TCP segments.

Connection Teardown

Either endpoint can close a TCP connection. The standard four-way teardown uses FIN and ACK segments to gracefully release resources.

Teardown Step 1: Client FIN
FIN=1, seq=x
Client application calls close(), sending FIN segment to server.
Teardown Step 2: Server ACK
ACK, seq=y, ack=x+1
Server acknowledges the FIN. Connection half-closed: server can still send data.
Teardown Step 3: Server FIN
FIN=1, seq=y, ack=x+1
Server finishes its data transmission and sends its own FIN.
Teardown Step 4: Client ACK
ACK, seq=x+1, ack=y+1
Client acknowledges server's FIN. Client enters TIME_WAIT (30s–2min) before full closure.

Half-Close State

After Step 2, the connection is half-closed:

• Client → Server: closed

• Server → Client: still open

• Server can finish sending data

TIME_WAIT Purpose

• Ensures final ACK reaches server

• Allows retransmission of final ACK if lost

• Prevents delayed segments from new connection

• Duration: 30s, 1min, or 2min (OS-dependent)

Common Mistake: The teardown is often called a "four-way handshake" but it is actually 4 segments, not 4 steps in a single exchange. The server can send its FIN together with its data, combining Steps 2 and 3 in some implementations.

TCP State Machine

TCP connections transition through well-defined states. The client and server have different state sequences.

Client States

CLOSED → [send SYN] → SYN_SENT → [recv SYN+ACK, send ACK] → ESTABLISHED → [send FIN] → FIN_WAIT_1 → [recv ACK] → FIN_WAIT_2 → [recv FIN, send ACK] → TIME_WAIT → (timeout) → CLOSED

Server States

CLOSED → [create listen socket] → LISTEN → [recv SYN, send SYN+ACK] → SYN_RCVD → [recv ACK] → ESTABLISHED → [recv FIN, send ACK] → CLOSE_WAIT → [send FIN] → LAST_ACK → [recv ACK] → CLOSED

Client States

CLOSED — No connection

SYN_SENT — SYN sent, waiting for SYNACK

ESTABLISHED — Data transfer

FIN_WAIT_1 — FIN sent, waiting for ACK

FIN_WAIT_2 — ACK received, waiting for FIN

TIME_WAIT — Waiting for delayed segments

Server States

CLOSED — No connection

LISTEN — Waiting for SYN

SYN_RCVD — SYN received, SYNACK sent

ESTABLISHED — Data transfer

CLOSE_WAIT — FIN received, waiting to close

LAST_ACK — FIN sent, waiting for ACK

Common Mistake: A server never enters FIN_WAIT_1 or FIN_WAIT_2. Those are exclusively client states. The server's teardown path goes through CLOSE_WAIT and LAST_ACK instead.

SYN Flood Attack & Port Scanning

SYN Flood Attack

Attackers send many SYN segments without completing the handshake. Each SYN causes the server to allocate buffers and variables for a half-open connection and then send a SYNACK. The server waits for the client's ACK to complete the third step of the three-way handshake, but it never comes. Eventually (often after ~1 minute), the server terminates the half-open connection. By flooding with rapid SYNs, the attacker exhausts server resources — a classic denial-of-service (DoS) attack.

SYN Cookie Defense
cookie = hash(src_IP, src_port, dst_IP, dst_port, secret)
Server uses cookie as initial sequence number instead of allocating state. Only allocates resources when valid ACK returns.

SYN Flood

• Attacker sends massive SYN volume

• Server allocates buffers per SYN (before handshake completes!)

• Half-open connections exhaust memory

• Legitimate clients denied service (DoS)

• First documented: CERT SYN 1996

• Defense: SYN cookies [RFC 4987]

SYN Cookies

• No state allocated on SYN receipt

• ISN = hash(connection_id, secret)

• Valid ACK contains cookie + 1

• Server recomputes hash to verify

• Deployed in all major OSes

RST Segment — Rejecting Unwanted Segments

What happens when a host receives a TCP segment whose port numbers or source IP do not match any ongoing socket? For example, if a host receives a TCP SYN packet with destination port 80 but is not running a Web server, the host sends a special reset segment with the RST flag set to 1. This tells the source: "I don't have a socket for that segment. Please do not resend."

Nmap Port Scanning

nmap sends SYN segments to target ports and classifies outcomes:

Received Interpretation Meaning
SYNACK Port is OPEN Application running on that port
RST Port is CLOSED No application on that port, but no firewall blocking
Nothing Port is BLOCKED Firewall dropped the SYN segment

nmap can also scan open UDP ports, probe firewalls and their configurations, and even detect operating system and application versions by manipulating TCP connection-management segments. Freely available at nmap.org.

Security Alert: nmap is a dual-use tool. System administrators use it to audit networks, but attackers use it to identify vulnerable services. Always ensure you have permission before scanning a host.

Worked Examples

Example 1 — Three-Way Handshake Walkthrough

Setup: Client with ISN=1000, Server with ISN=5000.

Step 1 (Client→Server): SYN=1, seq=1000

Step 2 (Server→Client): SYN=1, seq=5000, ack=1001

Step 3 (Client→Server): SYN=0, seq=1001, ack=5001

Question: Why does the client use seq=1001 in Step 3, not 1000?

Answer: The SYN segment itself consumes one byte of sequence number space, even though it carries no data. The client's next byte after the SYN is seq 1001. This ensures reliable delivery of the SYN itself.

Example 2 — Connection Teardown with Lost ACK

Scenario: During teardown, the client's final ACK (Step 4) is lost.

Sequence:

1. Client sends FIN (seq=2000) → Server

2. Server ACKs (ack=2001) → Client

3. Server sends FIN (seq=7000, ack=2001) → Client

4. Client sends ACK (ack=7001) → (LOST)

What happens next? Server's FIN timer expires, server retransmits FIN. Client, still in TIME_WAIT, re-sends the ACK. After successful ACK, both close.

Key insight: TIME_WAIT exists specifically to handle this case. The client waits 30s–2min before fully closing.

Example 3 — SYN Cookie Calculation

Setup: Server receives SYN from IP=192.168.1.10, port=34567, dst port=80. Secret=42.

Cookie computation:

cookie = hash(192.168.1.10, 34567, server_IP, 80, 42) = 0x8A3F1B2C (simplified example)

Server sends SYNACK with seq=0x8A3F1B2C. No state allocated.

Client responds: ACK with ack=0x8A3F1B2C+1 = 0x8A3F1B2D

Server verifies: recomputes hash(192.168.1.10, 34567, server_IP, 80, 42) = 0x8A3F1B2C. Since 0x8A3F1B2C+1 = ack value, the ACK is valid. Server allocates full connection state.

Result: Legitimate client connected. Attacker's bogus SYN consumed zero server resources.
